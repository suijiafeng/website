前端代码评审怎么做才有效：不是挑语法，而是提前发现维护风险

2023-02-26
前端基础构建与模块化

不少团队都做代码评审，但做着做着会进入一个低效状态。

评审内容常常集中在分号要不要、命名够不够优雅、这一行能不能再简洁一点。这些问题不是完全没价值，但如果评审长期停留在这个层面，更重要的风险往往会被漏掉。

前端代码评审真正要解决的，不是让每一行代码看起来都符合某个人的偏好，而是在功能上线前，尽量早地发现行为风险、维护成本和团队协作问题。

代码评审的目标不是“挑毛病”

更合理的理解应该是：代码评审是在功能上线前，尽可能早地发现后续维护成本和行为风险。

也就是说，评审不只是看“能不能跑”，更要看：

  • 改动边界是否清楚
  • 逻辑是否容易出错
  • 后面的人能不能接手
  • 有没有引入新的复杂度
  • 失败路径是否有处理
  • 是否破坏已有业务逻辑

一个好的评审意见应该能说明风险，而不是只表达喜好。比如“这里命名不好”不如“这个变量表示的是筛选后的列表，但名字叫 list，后面维护时很容易和原始列表混淆”。

状态流转是否清晰

前端不少 bug，不是出在渲染，而是出在状态流转混乱。

例如：

  • 一个状态被多个地方同时改
  • 本地状态和服务端状态混在一起
  • 提交流程和展示状态耦合
  • loading 和 disabled 状态不一致
  • 请求失败后页面仍然显示成功状态

评审时可以顺着用户操作走一遍：进入页面、修改内容、提交、失败、重试、离开页面。只看 happy path 通常不够。

组件边界是否合理

一个组件是不是承担了太多职责，是评审里非常值得看的点。

如果一个组件同时负责请求接口、数据转换、展示渲染、弹窗控制、路由跳转和埋点，那即使当前能跑，后面也很容易变成维护热点。

可以重点看几个信号：

  • props 数量越来越多
  • 组件里同时出现多个业务流程
  • 一个改动需要理解整页所有状态
  • 子组件反向修改父组件内部状态
  • UI 组件里混入大量接口细节

组件不是拆得越碎越好，而是边界要清楚。展示组件可以关心样式和交互，业务容器可以关心请求和状态，中间通过明确的数据结构连接。

异常路径有没有考虑

很多代码在正常路径下没有问题，但一旦接口失败、字段为空、数据延迟返回，就容易暴露问题。

评审时可以多问一句：如果这里失败，会发生什么？

常见异常路径包括：

  • 接口返回空数组
  • 接口返回字段缺失
  • 用户没有权限
  • 用户重复点击提交
  • 上传文件超出大小
  • 网络中断后重试
  • 页面卸载时请求还没结束

不要把格式工具负责的事情留给人做

如果团队还在评审里花很多时间讨论缩进、引号、分号、单行还是多行，说明自动化工具还没有承担它该承担的工作。

格式问题交给 Prettier 或 ESLint，评审重点应该放在工具不容易判断的地方：

  • 业务规则是否正确
  • 抽象是否过早
  • 错误处理是否统一
  • 组件边界是否清楚
  • 性能风险是否明显
  • 测试是否覆盖关键逻辑

小结

前端代码评审不是挑语法，也不是证明谁更懂代码。它的核心价值是提前发现维护风险。

一个有效的评审应该重点关注状态流转、组件边界、异常路径、错误处理、测试覆盖和业务逻辑是否被破坏。格式和简单规则交给工具，评审者把精力放在真正需要上下文判断的地方，团队才能从代码评审里获得稳定收益。
