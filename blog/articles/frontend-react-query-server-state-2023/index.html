React Query 管服务端状态：别再手写一堆 loading 和 error

2023-01-13
React前端基础构建与模块化

很多 React 项目一开始请求数据都很直接。

这段代码在一个页面里没问题，但项目里每个列表、详情、弹窗都这么写，很快会出现重复请求、错误处理不一致、刷新逻辑散落、组件卸载后还在 setState 等问题。

我第一次明显感受到这个问题，是一个后台列表页。列表、筛选、详情抽屉、编辑弹窗都在各自请求同一份数据。用户改完状态后，有的地方刷新了，有的地方还是旧的。最后不是接口慢，而是前端不知道哪份数据才是最新的。

React Query 解决的不是“少写几行请求代码”，而是把接口数据当成服务端状态来管理。

服务端状态和本地状态不一样

本地状态是前端自己拥有的，比如弹窗开关、当前 tab、输入框值。

服务端状态是后端拥有的，比如用户列表、订单详情、配置项。前端只是缓存了一份副本。

这份副本有几个特点：

  • 会过期
  • 可能被其他用户修改
  • 需要重新请求
  • 可能请求失败
  • 多个组件可能同时使用
  • 修改后需要同步缓存

如果把服务端状态当普通 useState，这些问题都要自己处理。

缓存不是脏东西

很多人刚用 React Query 时，一看到“缓存”就紧张，担心数据不新。

缓存不是为了骗人，而是为了控制数据新鲜度。比如用户从列表进详情，再返回列表，没必要每次都重新白屏加载。先显示缓存，再后台重新验证，体验通常更好。

我的使用习惯

我会把 React Query 用在这些地方：

  • 列表和详情数据
  • 字典和配置
  • 搜索结果
  • 分页和无限加载
  • 需要缓存和刷新的一切接口数据

不适合放进去的：

  • 输入框临时值
  • 弹窗开关
  • 当前 hover 状态
  • 未提交的表单草稿

服务端状态和本地状态分清楚后，组件会轻很多。React Query 不是替代所有状态管理，而是专门把“来自服务端的那一类状态”管好。
