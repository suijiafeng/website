前端 CI/CD 实践：把发布从手工步骤变成可回放流程

2022-08-16
构建与模块化前端基础

很多前端项目早期发布都很手工：本地跑一下 build，确认没报错，然后把 dist 上传到服务器。项目小的时候还能接受，但团队协作后，这种方式很容易出问题。

有人忘了跑 lint，有人用错 Node 版本，有人本地依赖和线上不一致，有人把未构建的代码发了出去。CI/CD 的价值就是把这些容易漏掉的步骤固定成流水线。

GitHub Actions 已经足够成熟，用它给前端项目搭建基础流水线成本不高。

我第一次真正重视 CI/CD，是因为一次很小的中后台改动。页面只是加了一个筛选项，本地看起来没问题，但发布时用了同事电脑上的 Node 版本，构建产物里有一处语法没有被正确降级，线上老浏览器白屏。那次问题不复杂，但排查过程很消耗人：先怀疑接口，再怀疑缓存，最后才发现发布环境和开发环境不一致。

从那以后，我对前端流水线的理解变了。它不是“自动点一下部署按钮”，而是让每次发布都可检查、可追踪、可复现。

CI 先解决质量门禁

CI 的第一目标不是部署，而是确保代码合并前经过统一检查。

基础步骤通常包括：

  • 安装依赖
  • 运行 lint
  • 运行测试
  • 运行 build

如果项目依赖新语法或特定构建工具版本，Node 版本更要明确。不要让 CI 默认使用“当前最新”，否则某天镜像升级后可能突然坏掉。

我现在会把 Node 版本当成项目契约的一部分，而不是个人习惯。README、.nvmrc、CI 配置最好保持一致。否则新同事接手项目时，第一天就可能陷在“为什么我装不上依赖”的问题里。

过期流水线要能自动取消

PR 开发过程中，经常会连续 push 多次。如果每一次提交都完整跑一遍构建，队列会被旧任务占住，反馈反而变慢。

这样线上报错时，可以知道是哪次发布引入的问题。

没有版本信息的错误监控，很难和发布记录对应起来。

构建产物也要尽量保持不可变。一个常见问题是：verify 阶段 build 一次，deploy 阶段又重新 build 一次。这样两个阶段的产物不一定完全一致，尤其当构建里包含时间戳、随机 hash 或远程资源时更明显。

更稳的做法是 verify 阶段生成 artifact，deploy 阶段只下载并发布同一份 artifact。这样线上出现问题时，可以明确知道发布的是哪一份产物，而不是“应该是刚才 build 的那份”。

artifact 还可以顺手带一份发布元信息。比如构建后生成 dist/version.json：

页面或监控系统能读取这个文件，线上排查时就不用猜当前环境到底跑的是哪次提交。静态站尤其需要这个，因为部署平台、CDN 和浏览器缓存之间隔了好几层，光看 GitHub 上最后一次成功 workflow 不一定能证明用户访问到的就是那份产物。

部署失败要停下来

流水线里每一步失败都应该阻止后续步骤。

发布流程尤其要谨慎。构建失败就不应该部署，测试失败也不应该部署。

我也不建议在部署脚本里默默吞掉错误。比如上传 CDN 失败、刷新缓存失败、通知失败，这些都应该明确暴露出来。可以把通知失败设置成非阻塞，但构建和上传失败不能假装成功。

前端 CI/CD 不只关心静态资源。发布后如果接口错误明显上升，也应该能回滚。

回滚流程最好也写成明确步骤，而不是出事时临场发挥。我的习惯是至少保留三类信息：

  • 当前线上版本
  • 上一个稳定版本
  • 回滚命令或平台入口

如果项目走静态资源发布，回滚可能是切回上一份 artifact；如果走容器发布，可能是切回上一镜像 tag。前端不要只关心“怎么发上去”，也要提前想清楚“怎么撤回来”。

前端 CI/CD 的核心价值，是把质量检查和发布步骤标准化。每个人本地环境不同没关系，最终都要经过同一条流水线。

一个合格的前端流水线至少应该固定 Node 版本，使用 lockfile 安装依赖，运行 lint、test、build，区分部署环境，保护密钥，并记录发布版本。做到这些，项目发布会从“靠人记得”变成“靠流程保证”。
