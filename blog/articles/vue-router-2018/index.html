Vue Router 重组：页面从 5 个涨到 40 个后，路由表该怎么收回秩序

2018-10-03
Vue组件与状态

路由表一开始很小的时候，大家都容易把它当成“页面地址登记簿”。等页面涨到几十个之后，路由其实早就变成了项目骨架：模块怎么分，布局怎么套，权限放哪层，列表和详情关系怎么挂，全会回到这里。

真正出问题的信号也很明显：你已经不记得某类页面写在文件哪一段了，新同事问“新页面该往哪放”，你给不出比“搜个类似的照着写”更好的答案。到这一步，再继续往七百行路由表上堆条目，只会让结构越来越失控。

所以这次整理我没有先改代码，而是先把页面关系重新画了一遍，后面的所有重组都从这一步长出来。

上周我申请了三天，把整张路由表推倒重理了一遍。趁着放假有空，把这次整理里想明白的事记下来。技术栈是 Vue 2.5 加 vue-router 3.0，脚手架是年中升的 Vue CLI 3。

页面少的时候，路由只是"从 A 跳到 B"；页面多了以后，路由就是项目的骨架——列表页和详情页怎么组织，后台模块怎么拆，权限页放在哪一层，布局组件怎么复用，这些事最后都会回到路由设计上。这是我这半年被 41 个页面教会的第一课。

整理第一步：先画页面关系，不是先改代码

刚学 Vue Router 的时候，我的注意力全在 API 上：router-link、this.$router.push、动态参数怎么取。这些当然要会，但这次整理让我确信，真到项目里，更关键的是路由和页面结构是否一致。路由本身没有层级感，页面代码通常也会跟着乱——我们那七百行就是证据。

所以动手改代码之前，我先在白板上画了一下午页面关系：哪些页面共享布局，哪些页面属于同一业务域，哪些页面需要权限，哪些页面之间有"列表进详情"的父子关系。画完发现 41 个页面其实就五个业务域加两种布局，乱只是因为它们从来没被这样看过。

这些问题比跳转 API 更早决定代码结构。后面所有的重构动作，都是照着这张图做的。

布局收编：嵌套路由很适合后台

后台最常见的结构就是外层菜单和头部固定，中间内容区切换。膨胀期我们的做法很粗暴：每个页面组件里都 import 一遍布局组件包着自己——41 个页面 41 次。这种场景下，嵌套路由才是自然的写法：

嵌套路由有个新手最容易栽的坑，我四月刚搭项目时就中过：子路由的 path 别加前导斜杠。我写成 { path: '/users', component: UserList } 放在 children 里，结果访问 /admin/users 死活进不去，访问 /users 反而能进。原因是子路由 path 以 / 开头会被当成绝对路径，直接挂到根上，不再拼父级前缀。去掉斜杠写 path: 'users'，它才会老实拼成 /admin/users。

还有就是父级布局组件里千万别忘了放 <router-view />。这次整理期间我帮同事排查过一个"子路由不显示"的问题，找了半天，最后发现他新写的 AdminLayout 模板里光画了菜单和头部，忘了放内容出口，子组件渲染了个寂寞。嵌套几层就要有几个 router-view，这是嵌套路由的命脉。

props 还能传函数和对象形式，比如把 query 也一起映射进 props：props: route => ({ id: route.params.id, page: route.query.page })，组件就彻底不碰 $route 了。

立家法：params 和 query 各管什么

整理期间我发现 41 个页面里，参数传递的写法五花八门，有人用 params 传筛选条件，有人把 id 塞进 query。这次立了条家法，先分清两类参数：

  • params：路径的一部分，例如 /article/12
  • query：查询条件，例如 /articles?page=2&keyword=vue

详情页身份标识放 params：

筛选条件放进 query 有个隐藏福利：刷新页面或复制链接时，用户看到的仍然是同一个筛选状态。我们的后台运营特别吃这一套——她们筛出一批异常订单，把链接甩到群里，别人点开就是同一个列表，不用再口述"你筛一下状态选待处理、时间近七天"。query 等于把页面状态做成了可分享的快照。

params 这边有个大坑值得专门记一笔：用 name + params 跳转，params 不会出现在 URL 里。比如 this.$router.push({ name: 'article-detail', params: { id: 5 } })，如果路由 path 里没有声明 :id 占位符，地址栏是看不到这个 id 的——跳转能成，但你一刷新，params 就丢了，组件拿到的 id 是 undefined，页面直接报错。膨胀期我们有三个页面用 params 传非路径参数，全在这次整理里被揪出来改掉了。

所以家法很死板：凡是刷新后还得活着的标识，一律走 path 占位符（/article/:id）；纯粹的列表筛选、分页用 query。别图省事用 params 传一堆非路径参数，那东西刷新即焚。

另外 query 的值都会被转成字符串，query: { page: 2 } 取出来 this.$route.query.page 是字符串 "2"。拿去做计算或者传给后端要不要转 number，心里得有数，这种隐式类型问题排查起来很费神。

用户进了订单模块，大概率会在订单列表、订单详情、退款几个页面之间转，把它们打成一个 chunk，第一次进模块加载一次，后面几个页面秒开。反过来，要是把全站 41 个页面都拆成独立小 chunk，又会变成"每点一个页面 loading 一下"，请求数暴增，体验也碎。

懒加载还要配套做两件事，不然体验是打折的。一是切换时要有过渡 loading，否则慢网络下点了链接半天没反应，用户以为卡死了又点一遍。二是 import() 失败要兜底——部署上线后旧 chunk 的 hash 文件名被覆盖，停留在旧页面的用户去点一个新页面，会去请求一个已经不存在的 js，直接报 Loading chunk failed。我们生产九月初真出过这事，最后是加了个全局监听，捕获到 chunk 加载失败就刷新一次：

注意这里用的是 to.matched.some(...) 而不是 to.meta.requiresAuth。因为 meta 不会从父路由继承到子路由——你在 /admin 上标了 requiresAuth，子路由 /admin/users 的 to.meta 里并没有它。to.matched 是从根到当前路由匹配到的整条记录链，用 some 扫一遍才能正确判断"这条路径上任何一层要不要登录"。这个细节我一开始不知道，写成了 to.meta.requiresAuth，结果父路由加了 auth 子路由全裸奔，八月份安全自查时被揪出来，惊出一身冷汗。

守卫适合做"能不能进入页面"的判断，不适合塞大量业务逻辑。进入页面后的数据请求、表单初始化、局部状态，还是应该留给页面组件处理。全局守卫每次路由跳转都要跑，你往里塞个同步等待的接口请求，全站跳转都会被它拖慢——这种全局性能债很隐蔽，等发现卡了再回来拆很麻烦。膨胀期我们的 beforeEach 里一度塞了埋点、权限、面包屑计算三摊事，这次整理只留下了权限判断。

整理完之后

上周五重构分支合并，新的 router/index.js 加五个模块文件，最长的一个不到一百二十行。周一产品那三个新页面，同事十分钟就加完了，加完还顺手告诉我该属于哪个 chunk——这是四月那张 5 个页面的路由表给不了的东西，也是七百行那张给不了的。

Vue Router 学起来不难，真正难的是把它和页面结构一起设计清楚。页面少时随便写都能跑，页面多了以后，路由就是项目骨架，骨架搭得清楚，后面很多代码都会跟着轻下来。好的路由设计应该让人一眼看懂页面关系：哪些页面共享布局，哪些页面属于同一模块，哪些页面需要权限，哪些状态可以通过 URL 还原。这次从 5 到 41 的膨胀教会我的就是这些——下个项目，这张关系图我会在写第一条路由之前就画好。
