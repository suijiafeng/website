前端盒模型为什么总出问题：从 width 到 box-sizing 一次讲清

2021-01-08
前端基础

刚开始学 CSS 时，盒模型通常是比较早接触到的概念。

看定义并不难：一个元素由内容区、padding、border 和 margin 组成。可一到真实页面开发里，很多布局问题最后都会绕回盒模型。

明明宽度写的是 200px，为什么元素实际占的空间比 200 大？明明两个盒子一行放得下，为什么一加 padding 就被挤下去了？这些问题背后，基本都和盒模型有关。

我记得刚工作那会儿做一个商品列表页，设计稿上一行四个卡片，间距均匀。我照着标注写完，本地看着没毛病，结果一提测就被打回来——卡片莫名其妙换行成了三个一排，最后一个掉到下面去了。当时我对着 Flex 的 flex-wrap、justify-content 改了半天都没用，后来才发现根本不是布局的事，是卡片加了 padding 之后实际宽度超了，累计起来一行装不下。从那以后我才真正开始认真理解盒模型，而不是停留在"背概念"。

盒模型到底在描述什么

浏览器渲染一个块级元素时，不是只看内容本身的宽高。

它会把元素理解成一个有层次的盒子：

  • 最里面是内容区
  • 内容外面是内边距 padding
  • 再外面是边框 border
  • 最外层的间距是外边距 margin

如果只看一个元素的视觉尺寸，真正参与结果计算的通常不止 width 和 height。

  • 左右 border 共 4px

这里有个排查小技巧我一直在用：在浏览器开发者工具里选中元素，右侧 Computed 面板最下面会画出一张盒模型示意图，蓝色是内容区、绿色是 padding、黄色是 border、橙色是 margin，每一层的具体数值都标在上面。我每次遇到"宽度对不上"的问题，第一步不是去翻 CSS，而是先看这张图，哪一层多出来的一目了然。比反复在代码里加 console.log 量尺寸快多了。

很多布局错位不是浏览器算错了，而是我们脑子里默认的“宽度”概念和浏览器理解的“宽度”概念不是一回事。说白了，浏览器算的是"内容 + padding + border"，我们脑子里想的往往是"这个框最后多宽"，两边对不上，结果就跑偏了。

为什么默认盒模型容易让人误判

CSS 默认的 box-sizing 是 content-box。

它的意思是：width 和 height 只描述内容区，不包含 padding 和 border。

这在理论上很清晰，但在写页面时不够直观。因为我们很多时候想控制的是“这个盒子最终占多宽”，而不是“内容区占多宽”。

  • 栅格布局
  • 表单输入框
  • 卡片组件
  • 响应式容器

如果项目一开始就统一使用 border-box，后面很多宽度计算都能简单一些。

在 border-box 下，这就是三列正好占满，padding 和 border 都吃进 33.333% 里，不用再去算"减掉 border 还剩多少"。换成 content-box，你就得写成 width: calc(33.333% - 34px) 这种东西——34 是左右 padding 32 加左右 border 2 的总和。哪天 UI 说边框改 2px，你还得回来把这个魔法数字改成 36，非常容易漏。

不过有个边界行为要提醒：在 border-box 下，如果 padding + border 已经大于等于你设的 width，内容区会被压到 0，多出来的内容直接溢出，而不会把盒子撑大。border-box 守的是“盒子外沿尺寸”这条线——装不下就让内容自己溢出，这点偶尔会让人意外。

margin 不会算进盒子，但一样会影响布局

很多人第一次理解盒模型时，会把 margin 也当成盒子内部的一部分。严格说它更像盒子和外部环境之间的距离。

它不会占用内容区，也不会被背景色覆盖，但它会影响元素之间的位置关系。

另外，垂直方向上还有一个常见现象叫外边距合并（margin collapse）。相邻块级元素的上下 margin 不一定简单相加，而可能取较大的那个值。这也是很多人一开始调间距时容易困惑的地方。

举个我真遇到过的例子：上一个元素 margin-bottom: 20px，下一个元素 margin-top: 30px，按直觉中间应该空 50px，结果实际只有 30px——浏览器取了两者的较大值。这个可以贴一段自己量：

把 .a 的 margin-bottom 从 20 调到 25，再跑一遍还是输出 30（25 仍小于 30），这就是文章开头说的"改了没反应"。改到比 30 大，比如 40，输出才会跟着变成 40。我当时是想加大间距，把 margin-bottom 从 20 调到 25，结果界面纹丝不动，因为 25 还是小于 30，合并后仍然是 30。这种"改了没反应"最折磨人。

更坑的是父子之间也会合并：如果父元素没有 padding、border、也没开 BFC，子元素的 margin-top 会"穿透"出去变成父元素的外边距，导致父元素整体往下跑。后来我处理间距，但凡涉及垂直 margin 又出现诡异现象的，要么改用 padding，要么干脆给父级加一个 overflow: hidden（或现在更推荐的 display: flow-root）开 BFC 把合并切断。Flex 和 Grid 容器里的子项默认不会发生 margin 合并，这也是我后来更愿意用它们布局的一个隐性好处。

如果还在默认 content-box 下，width: 100% 指的是内容区 100%，再加上 padding 和 border，输入框就可能超出父容器。

这类问题在移动端尤其明显，因为屏幕窄，哪怕多出几个像素也会导致横向滚动或者边框被挤出。

所以很多基础样式里都会把输入类控件也纳入 border-box 体系。

这里还有个容易被忽略的点：表单控件（input、textarea、button、select）在不少浏览器里默认 box-sizing 行为本来就不太一致，历史上有些表单元素默认就是 border-box。如果你只对普通元素统一了 content-box、又没显式给表单控件指定，就会出现"明明设了一样的 width，文本框和按钮宽度却差几像素"的问题。统一用 border-box 通配一遍正好把这块也抹平了。

什么时候需要特别留意盒模型

我自己经验里，下面几类布局最容易踩坑：

  • 百分比宽度和固定 padding 混用
  • 多列布局要求严格对齐
  • 组件宽高需要和设计稿精确对应
  • 列表项加边框后突然换行
  • 表单控件 100% 宽度溢出

只要出现“宽度看着没问题，但结果不对”的情况，先检查盒模型，通常比先怀疑 Flex 或 Grid 更高效。

盒模型本身不复杂，复杂的是心里的默认预期

我后来带新人时，第一节 CSS 课就讲这个——不是因为它难，而是它太底层、绕不开，几乎所有元素都受它影响。一旦对宽度、内边距、边框的关系理解不稳，后面布局就会不断冒出对不上的小偏差，而你还会先去怀疑 Flex 或 Grid。

所以我现在更倾向于把它当项目级约定来看：全局统一 border-box、清楚 width 到底描述什么、知道垂直 margin 会合并、必要时用 BFC 切断合并。这几件事做扎实，很多 CSS 问题会直接消失。
