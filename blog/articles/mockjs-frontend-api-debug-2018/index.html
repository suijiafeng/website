Mock.js 联调前的接口模拟：别让页面开发一直等后端

2018-08-11
前端基础构建与模块化

前后端并行开发这件事，听起来很美好：需求评审完，后端去搭接口，前端去画页面，到了某个约定的时间点两边一拼，皆大欢喜。现实是，后端的接口往往比页面晚两三天，有时候表设计推翻重来，接口能拖一个星期。而我这边页面骨架早就搭好了，列表、表单、分页全在那儿干等着数据，进度报表上就只能写"等接口"。

被这么卡过几次之后，我开始认真用 Mock.js。它解决的不是"造假数据"这种小事——console.log 一个写死的数组也能造假数据——它解决的是让前端在没有后端的情况下，跑通一条完整的、贴近真实的请求链路：发请求、收响应、解析、渲染、处理错误。等真接口上线，把开关一关，请求自然落到后端，页面代码一行不用动。

但我也踩过反方向的坑：mock 写得太爽，造了一堆后端根本不会返回的字段和结构，等联调时才发现两边对不上，页面大面积返工。所以这篇想说的不只是"怎么用 Mock.js"，更是"用它的时候哪些地方千万别想当然"。

我当时用的是 Mock.js 1.0.1，配 Vue CLI 3 起的项目，请求库是 axios。下面的代码都是这个组合下实际跑过的。

先把接口契约定下来，再动手 mock

最容易出问题的环节，恰恰是最不起眼的一步：字段约定。

我刚开始图快，页面需要什么字段我就 mock 什么字段，名字也随手起。比如用户状态我写 status，后端最后返回的是 userStatus；我以为列表在 data.list，后端给的是 data.records（用了 MyBatis-Plus 的分页对象）。联调那天，页面一片空白，控制台没报错，因为我取的字段全是 undefined。那一下午基本都在改字段名。

后来我们组定了规矩：mock 之前，接口的响应外层结构必须先和后端在文档里写死。最外层统一长这样：

code 为 0 表示成功，非 0 是各种业务错误码；data 是真正的数据；message 给前端兜底展示用。这个壳子一旦定下来，mock 和真实接口都按它来，里面 data 的具体字段哪怕暂时拍脑袋，外层也不会错。

我的经验是：外层结构和分页字段一定要和后端确认，内层业务字段可以先猜，但要标注清楚是"待确认"。返工成本最高的永远是结构，不是某个具体字段名。

基础用法：让模板帮你造数据

Mock.js 真正好用的地方是它的数据模板语法（DTD）。你不用手写一百条假数据，写个生成规则就行。

这里几个语法值得记一下，都是我后来天天用的：

  • 'records|10' 表示生成 10 个元素的数组，模板是后面那个对象。
  • 'id|+1': 1 表示从 1 开始，每条递增 1，这样列表里 id 不会重复——很重要，因为不少表格组件用 id 当 :key，重复了渲染会出诡异问题。
  • 'age|18-60': 1 生成范围内整数；如果写 'price|10-100.2' 就是带两位小数的浮点。
  • @cname、@email、@datetime 是占位符，调的是 Mock.Random 里的方法。

Mock.js 的原理这里要点一下，不然容易踩坑：它在浏览器里重写了 XMLHttpRequest，拦截匹配到的请求，直接返回 mock 数据，请求根本没出网络。所以你在浏览器的 Network 面板里看不到这些请求——我第一次用的时候盯着 Network 找了半天没找到，还以为没生效，其实数据早就回来了。要确认是否命中，看页面渲染或者在 mock 回调里打日志，别盯着 Network。

另外，因为它拦的是 XHR，所以如果项目里用 fetch 发请求，Mock.js 1.x 是拦不住的。我们当时全线 axios（基于 XHR），刚好没这问题，但这个限制得知道。

别只 mock 成功：错误和空数据才是页面最脆弱的地方

这是我最想强调的一点。大多数人 mock 都只造一条 happy path 的成功数据，页面看着挺好，一上线遇到真实的错误码、空列表、超长文案，立刻原形毕露。

错误处理没人测，是因为 mock 里压根没有错误。我后来习惯给关键接口都准备好"会失败的版本"。

加延迟：让 loading 状态有机会现身

本地 mock 是秒回的，loading 一闪而过甚至根本不出现。结果就是按钮的 loading 态、列表的骨架屏、防重复提交逻辑，全都没机会测。等到了测试环境网络一慢，用户疯狂点按钮，重复下单的 bug 就来了。

这里提醒一个隐蔽的坑：Mock.js 重写了全局的 XMLHttpRequest。哪怕你只 mock 了 /api/users，所有走 XHR 的请求都会先过它的拦截层，没匹配上的才放行到真实网络。所以千万别在测试环境、预发环境误开 mock——我们就出过一次事故，测试环境 VUE_APP_MOCK 忘了关，结果部分请求被 mock 拦了返回假数据，测试同学对着假数据测了半天提了一堆"bug"。开关的判断条件里加上 NODE_ENV === 'development' 这层兜底，就是那次之后加的。

几个我后来形成的习惯

用了一段时间，沉淀下来几条不算大道理但很实用的原则：

  • mock 数据结构永远跟着后端文档走，不跟着页面方便走。页面需要什么，是在拿到约定结构之后再从里面取，而不是反过来让 mock 迁就页面。
  • mock 文件和真实接口的请求层共用同一套封装。getUsers 这类函数不区分 mock 还是真实，区别只在最外层那个引不引入 mock 的开关。这样切换才真正零成本。
  • happy path、错误、空、超长，四种数据都要造。只造第一种等于没测页面的健壮性。
  • 正则匹配 + 函数响应是默认姿势，字符串精确匹配只适合那种永远不带参数的固定接口。

Mock 只是让前端能独立验证交互与边界，不是替代后端契约。把外层结构和分页先和后端对齐，造好错误、空数据和延迟，并把 mock 开关做得一键可控，联调时的返工就会大幅减少。到最后，关掉开关后页面自然落到真实接口上。
