Mock.js 接口模拟：页面别等接口，先把请求链路跑通

2018-08-11
前端基础构建与模块化

console.log 一个写死的数组，谁都会写。但这只能让页面"看起来有东西"，跑不通真正的请求链路——发请求、收响应、解析、渲染、loading、错误处理，这一整条路一步都没走过，等真接口来了照样一堆问题现原形。这个道理我是被接口拖过好几次之后才想透的：列表、筛选、分页、弹窗全写完了，页面还在干等数据，后端一句"再两三天"，最后常常就是一周。继续等下去，只会让前端所有问题都堆到联调那天一起爆发。

于是我把 Mock.js 正式接进了项目，让前端在没有后端的情况下把请求、响应、loading、错误和空数据都先走一遍完整流程。等真接口上线，开关一关，请求自然落到后端，页面代码一行不用动。

当时的组合是 Mock.js 1.0.1，项目还是 vue-cli 2.x 的 webpack 模板起的，请求库 axios 0.18。下面的代码都是这个组合下实际跑过的。

字段名对不上：两边各说各话

我刚开始图快，页面需要什么字段我就 mock 什么字段，名字随手起。用户状态我写 status，列表我放在 data.list 里，痛痛快快开发了三天。

然后后端的接口来了。联调第一天，页面一片空白，控制台一个错都没报——因为我取的字段全是 undefined。对方返回的用户状态叫 userStatus，列表在 data.records 里（用的是 MyBatis-Plus 的分页对象，字段名是框架定的）。我拿着两份 JSON 去找负责这块接口的同事："怎么没按我 mock 的字段来？"对方反问："你 mock 的时候问过我吗？"

谁都没错，谁都有错。那一下午基本都在改字段名，改到后面双方坐下来定了规矩：mock 之前，接口的响应外层结构必须先在文档里写死。最外层统一长这样：

code 为 0 表示成功，非 0 是各种业务错误码；data 是真正的数据；message 给前端兜底展示用。这个壳子一旦定下来，mock 和真实接口都按它来，里面 data 的具体字段哪怕暂时拍脑袋，外层也不会错。

这次的教训是：外层结构和分页字段一定要和后端确认，内层业务字段可以先猜，但要标注清楚是"待确认"。返工成本最高的永远是结构，不是某个具体字段名。后来团队干脆把这份约定写进了 wiki，新接口先补文档再动手，两边都省心。

让模板帮我造数据，别手写一百条

契约定好之后才轮到 Mock.js 真正的看家本领：数据模板语法。你不用手写一百条假数据，写个生成规则就行。

几个语法值得记一下，都是我这几周天天在用的：

  • 'records|10' 表示生成 10 个元素的数组，模板是后面那个对象。
  • 'id|+1': 1 表示从 1 开始每条递增 1，列表里 id 不会重复——很重要，因为不少表格组件用 id 当 :key，重复了渲染会出诡异问题。
  • 'age|18-60': 1 生成范围内整数；写 'price|10-100.2' 就是带两位小数的浮点。
  • @cname、@email、@datetime 是占位符，调的是 Mock.Random 里的方法。

Mock.js 的原理这里必须点一下，不然会像我一样闹笑话：它在浏览器里重写了 XMLHttpRequest，拦截匹配到的请求直接返回 mock 数据，请求根本没出网络。所以浏览器的 Network 面板里看不到这些请求——我第一次用的时候盯着 Network 找了半天，以为没生效，差点把配置推倒重来，其实数据早就回来了。要确认是否命中，看页面渲染或者在 mock 回调里打日志，别盯着 Network。

另外，因为它拦的是 XHR，项目里如果有人用 fetch 发请求，Mock.js 1.x 是拦不住的。我们全线 axios（基于 XHR），刚好没这问题，但这个限制得知道，不然哪天混进一个 fetch 请求，mock 对它无效还查不出为什么。

Mock.Random 也不是只有内置的那几个占位符，团队里但凡有重复出现的假数据规则，我都会用 Mock.Random.extend 注册成自定义方法，比如订单号有固定前缀加日期加流水号的规则：

联调那天，错误处理全是漏的

真接口接上之后还有一场硬仗。后端接口有时返回 code: 50001 库存不足，有时慢到超时，测试同学还造了一堆空数据的账号。我的页面在这些场景下要么白屏、要么按钮能连点五次、要么"暂无数据"的占位图压根没画。负责接口的同事看着我修 bug，来了句："你不是 mock 了好几天吗？"

我 mock 了，但只 mock 了成功。大多数人都这样：造一条 happy path 的数据，页面看着挺好，一遇到真实的错误码、空列表、超长文案，立刻原形毕露。错误处理没人测，是因为 mock 里压根没有错误。

加延迟：本地秒回是假象，loading 才有机会现身

这里提醒一个隐蔽的坑：Mock.js 重写了全局的 XMLHttpRequest，哪怕你只 mock 了 /api/users，所有走 XHR 的请求都会先过它的拦截层，没匹配上的才放行到真实网络。所以千万别在测试环境、预发环境误开 mock——七月出过一次事故，测试环境的构建里 mock 开关忘了关，部分请求被拦下返回假数据，测试同学对着假数据测了半天，提了一堆"bug"给后端，后端查了一晚上日志毫无异常，第二天黑着脸来问我怎么回事。开关判断里加 NODE_ENV === 'development' 这层兜底，就是那次之后加的。

mock 是契约的演练，不是契约的替代

八月初，订单项目联调只用了一天半，比排期省了一半。负责后端的同事难得夸了一句："这次字段一个没对错。"其实不是谁更细心，是这次动手前双方先把文档写死了。

用了一个多月，沉淀下来几条不算大道理但很实用的原则：

  • mock 数据结构永远跟着后端文档走，不跟着页面方便走。页面需要什么，是在拿到约定结构之后再从里面取，而不是反过来让 mock 迁就页面。
  • mock 文件和真实接口的请求层共用同一套封装。getUsers 这类函数不区分 mock 还是真实，区别只在最外层那个引不引入 mock 的开关。这样切换才真正零成本。
  • happy path、错误、空、超长，四种数据都要造。
  • 正则匹配 + 函数响应是默认姿势，字符串精确匹配只适合永远不带参数的固定接口。

这一个多月和后端的三次交涉，根源都不是工具不会用，而是两边的"契约"没对齐：字段名各说各话、参数场景没覆盖、失败路径没人管。Mock.js 只是让前端能独立演练这份契约，把该踩的坑在联调之前踩完。它替代不了和后端坐下来把文档写死的那半个小时——那半个小时，才是联调从一周缩到一天半的真正原因。
