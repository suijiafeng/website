深拷贝和浅拷贝：对象复制这道题，项目里真会踩坑

2019-03-08
JavaScript前端基础

深拷贝和浅拷贝是很经典的面试题。

它看起来像基础概念，但项目里确实经常踩坑。表单编辑时改了临时对象，结果列表也变了；Vuex 里直接改了引用数据，页面状态串了；弹窗取消时，本来应该回滚的数据已经被改掉。

这些问题背后都是对象引用。

我印象最深的一次线上 bug 就跟这个有关。一个商品编辑弹窗，点「编辑」把列表里那条数据塞进表单，用户改了几个字段又点「取消」——结果列表里那行也跟着变了。测试提单说「取消按钮没用」，我查了半天 cancel 方法逻辑明明没错，最后才反应过来：表单拿的就是列表对象本身的引用，用户在表单里改，等于直接改了列表里的数据，根本没有「副本」可言，取消时也就无从回滚。这道题别看面试问得多基础，真正能在项目里第一时间反应过来「这是引用问题」的人，其实没那么多。

基本类型和引用类型

a 和 b 指向同一个对象。栈里存的是同一个堆地址，改谁都是改那块堆内存。理解这点就能解释一堆「灵异现象」：函数参数传对象进去，函数里改了属性外面也变了（传的是引用的拷贝，指向同一对象）；两个看着一模一样的对象 {a:1} === {a:1} 却是 false（地址不同）。这些都不是 bug，是引用类型的本性。

数组同理，数组也是对象。var b = a 之后 b.push(1)，a 也多了一项。我早期把这种「共享」当过 feature 用，省了来回赋值，结果埋下一堆隐患，后来宁可多写一行拷贝也不敢图省事了。

展开运算符也是浅拷贝：

Object.assign 和展开运算符本质一样，都只复制第一层、嵌套对象仍是共享引用。数组的 slice()、concat()、[...arr] 同理，都是浅拷贝。

那是不是浅拷贝就没用？恰恰相反，我项目里九成的「复制」需求用浅拷贝就够了。关键看你的数据结构有多深。如果对象就一层、全是基本类型（很多表单数据就是这样），{ ...form } 完全够用，没必要上深拷贝那套重家伙。开头那个编辑弹窗的 bug，因为表单字段都是平铺的字符串和数字，我最后就是用 this.form = { ...row } 一行修好的。

真正需要深拷贝的，是那种带嵌套对象/数组、而你又要独立修改内层的场景。判断标准很简单：你会不会去改嵌套那一层？ 会，就得深；不会（只读或只换整个引用），浅拷贝足矣。别一看到「复制」就条件反射上深拷贝。

为什么 Date 不能直接 Object.keys 遍历拷贝？因为它的时间值存在内部槽里，不是普通可枚举属性，遍历出来是空的，拷出来就是个 Invalid Date。RegExp 同理，source 和 flags 得显式拿出来重建。这俩是最常被忽略的，我第一次手写就栽在 Date 上，拷完一打印 Invalid Date 一脸懵。

另外这个递归版有个理论隐患：对象嵌套特别深时会爆栈（Maximum call stack size exceeded）。正常业务数据没那么深，不用管；真遇到（比如某些树形结构无限嵌套），得改成用栈/队列的迭代写法，但那属于面试加试题了，项目里我从没真碰上过。

项目里什么时候需要深拷贝

常见场景：

  • 编辑表单临时副本
  • 弹窗取消回滚
  • Vuex 状态快照
  • 拖拽排序前备份
  • 复杂配置复制

但不要到处深拷贝。深拷贝有性能成本，也可能让引用关系丢失。

比如列表渲染时每次都深拷贝大数组，会影响性能。更好的方式是明确哪些地方需要隔离修改，哪些地方只读。

举两个我实际拿捏过的尺度。Vuex 里我反对「为了不报 mutation 警告就到处 cloneDeep 整个 state」，那性能账很亏；正确做法是只在 mutation 里改、组件拿到的当只读用。表单编辑场景，我会按数据深浅来选：平铺表单 { ...row } 浅拷贝就够，带嵌套的（比如带 SKU 列表的商品）才上深拷贝，而且只拷要编辑的那部分，不整个对象一锅端。

还有个反直觉的坑：深拷贝会切断所有引用关系。有时候这正是你要的（隔离），但有时候你其实依赖某些共享引用（比如内部缓存、DOM 节点引用、事件回调），深拷贝一刀切下去，这些全断了，功能反而坏掉。所以深拷贝不是「更安全的拷贝」，它是「语义不同的拷贝」，用之前想清楚你到底要不要断引用。

浅拷贝复制第一层，深拷贝递归复制嵌套结构。JSON 方法简单但限制多，手写深拷贝要考虑数组、对象、特殊类型和循环引用。

面试问这题，是因为它能看出你是否理解对象引用。项目里真正要做的是判断什么时候需要隔离数据，什么时候不该为了省心到处深拷贝。
