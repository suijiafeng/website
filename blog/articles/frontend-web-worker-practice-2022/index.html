Web Worker 实践：把耗时任务从主线程里挪出去

2022-10-11
前端基础JavaScript性能与缓存

前端页面卡顿时，很多人第一反应是减少 DOM、优化 CSS、拆分组件。这些方向都可能有用，但如果真正的问题是 JavaScript 长任务占满主线程，就需要换一个思路。

浏览器主线程负责很多事情：执行 JS、处理用户输入、样式计算、布局、绘制。一个复杂计算如果连续跑几百毫秒，用户就会感觉页面卡住。Web Worker 的价值，就是把一部分耗时任务从主线程挪出去。

随着前端承担的数据处理越来越多，Worker 在后台系统、数据可视化、文件处理、音视频处理里变得更常见。

我第一次明显感受到 Worker 的价值，是做一个导入校验页面。用户上传几万行数据后，前端要做格式检查、重复项检查和预览。如果全部在主线程跑，输入框、滚动和按钮都会卡住。把解析和校验挪到 Worker 后，任务总耗时不一定大幅下降，但页面终于能正常响应了。

什么任务适合 Worker

适合放进 Worker 的任务通常有几个特点：

  • 计算耗时明显
  • 不需要直接操作 DOM
  • 输入输出可以序列化
  • 对响应性要求高

常见场景包括：

  • 大文件解析
  • CSV、Excel 数据预处理
  • 图片压缩
  • 搜索索引构建
  • 数据可视化前的聚合计算
  • 加密、哈希、压缩

不适合 Worker 的任务也很明确：

  • 直接修改 DOM
  • 依赖大量浏览器 UI API
  • 非常轻量的小计算
  • 和主线程频繁来回通信的细碎任务

Worker 不是万能性能开关。它解决的是主线程被计算占用的问题，不解决网络慢、图片大、布局抖动这些问题。

所以使用前我会先录一次 Performance，看是不是主线程长任务。如果瓶颈是接口慢或渲染列表太大，Worker 不是第一优先级。

大数据通信要注意成本

把任务放进 Worker 不代表没有成本。数据传输本身也会消耗时间。

如果你把一个很大的数组频繁传来传去，性能可能并不会变好。对于 ArrayBuffer 这类数据，可以使用 Transferable Objects，把所有权转移过去，避免复制。

转移后，主线程里的 buffer 就不能继续使用了。这是性能和所有权之间的交换。

处理大文件、二进制数据时，这个细节很重要。

对于更大的数据，还要考虑分块。一次把所有内容都读入内存再传给 Worker，可能会造成内存峰值过高。导入、解析、压缩这类任务最好能分阶段处理，并持续回报进度。

Worker 数量也要控制

不要每个任务都无限创建 Worker。

Worker 本身也有启动和内存成本。批量任务里，如果一次创建几十个 Worker，页面同样可能变慢。我一般会控制成一个 Worker 或一个小型 Worker 池，根据任务类型限制并发。

这和请求并发控制很像，目标不是把机器打满，而是让页面保持可用。

那次导入页改完以后，我对 Worker 的看法反而更克制了。

它确实能把耗时计算从主线程挪出去，让页面保持响应；大文件解析、数据预处理、图片压缩、复杂计算都很适合。但它不负责让接口变快，也不负责解决渲染列表太大、布局抖动、图片没压缩这些问题。

所以我现在会先录 Performance，确认卡顿真的是 JS 长任务，再决定要不要上 Worker。上了以后也要把通信成本、错误结构、任务取消和构建路径处理好。否则 Worker 只是把复杂度从一个线程搬到另一个线程，排查起来更绕。
