前端离线缓存实践：Service Worker 不是随手注册就完事

2024-09-27
前端基础性能与缓存

Service Worker 很强，但也很容易把项目搞复杂。

它能缓存静态资源、支持离线访问、加速重复访问，甚至做后台同步。但如果缓存策略没想清楚，也可能让用户长期拿到旧页面，接口数据错乱，线上修复迟迟不生效。

我见过一个 PWA 项目，注册 Service Worker 后看起来很快，结果发布新版本后部分用户一直停留在旧 JS。客服让用户刷新，用户刷新了也没用，因为旧 SW 还在控制页面。最后只能加版本提示和强制更新逻辑。

离线缓存不是“加个 sw.js”，而是一套版本和数据策略。

先理解 Service Worker 生命周期

Service Worker 有几个关键阶段：

新 SW 下载后不会立刻控制当前页面。只要旧页面还开着，它通常会停在 waiting。等所有旧页面关闭，新 SW 才 activate。

这就是为什么你发布了新版本，用户不一定马上拿到。

HTML 不适合长期 Cache First。否则入口 HTML 旧了，后面所有资源路径也可能旧。

接口更要谨慎。订单状态、余额、权限这类数据不要离线缓存后当真。离线时可以展示“当前无网络，数据可能不是最新”，但不能让用户误以为操作成功。

预缓存要控制范围

预缓存可以让关键资源离线可用，但不要把整个站点都塞进去。

适合预缓存：

  • 应用壳 HTML
  • 核心 JS/CSS
  • logo 和基础图标
  • 离线兜底页

不适合预缓存：

  • 大量历史页面
  • 用户私有数据
  • 大图和视频
  • 频繁变化的接口响应

缓存太大不仅浪费存储，还可能触发浏览器清理。移动端存储资源更紧张，浏览器会按自己的策略清掉缓存，不能把 Cache Storage 当永久数据库。

离线页面要讲清楚状态

离线兜底页不要只写“出错了”。

用户需要知道：

  • 当前是网络不可用
  • 哪些内容还能访问
  • 哪些操作不能提交
  • 是否可以重试

API 错误要区分网络失败和业务失败

离线场景里，API 错误处理必须更细。

网络失败可以提示稍后重试或保存本地草稿；业务失败要让用户修改字段；未知失败要上报。不要把所有错误都说成“网络异常”。

如果支持离线提交，还要设计队列、重放、冲突处理和幂等。这个复杂度不低，不要轻易承诺“离线也能完整使用”。

我的离线缓存清单

上线 Service Worker 前，我会检查：

  • HTML、静态资源、接口是否使用不同缓存策略
  • 新版本发布后用户能否感知并更新
  • 离线兜底页是否预缓存
  • 用户私有数据是否避免长期缓存
  • API 错误是否区分网络失败和业务失败
  • 缓存版本是否能清理旧资源
  • 监控是否能看到 SW 版本和命中情况

Service Worker 是一层代理。代理一旦写错，问题会发生在浏览器和服务器之间，排查比普通前端 bug 更麻烦。

所以我的态度是：能带来明确收益再上，策略尽量简单，关键数据不要乱缓存，版本更新一定要可控。
