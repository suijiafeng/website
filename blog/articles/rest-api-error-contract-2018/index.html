REST 接口错误约定怎么谈：message 不能每个接口都不一样

2018-09-18
前端基础构建与模块化

前后端联调时，最消耗精力的从来不是正常数据，而是错误。正常数据无非是把字段渲染出来，结构对不上大不了改个映射。可错误处理是散落在每一个 .catch 里的，一旦后端各个接口对"出错"的表达方式不一致，前端就会被逼着写一堆 if-else 去猜对方到底想说什么。

去年接的这个后台管理系统，对接的后端分三个模块各自维护：用户模块、商品模块、订单模块，接口分别出自不同的人手，入职时间不同，师承不同，也没有统一规范。联调到第二周，把三个模块的接口在"失败"这件事上的表达方式列了个清单，发现光是"出错了"，就收到过这些花样：

最离谱的是订单模块有个接口，业务出错时 HTTP 返回 200，body 里塞个 code: -1；而真正服务器异常的时候直接甩回一坨 500 的 HTML 错误页，JSON.parse 当场抛异常，连 message 都拿不到。页面里写的 error.response.data.message，碰到这些就全线崩溃，要么显示 undefined，要么干脆白屏。

拿着这份清单去找三位后端同事沟通，第一次开口，商品模块那位同事的回答很有代表性："msg 和 message 不都一样吗，你兼容一下呗。"

当然可以兼容——问题是兼容五种，还是兼容永远的第 N 种？那阵子才真正理解一件事：接口错误如果没有约定，烂账最后一定会全部转嫁到前端的 catch 块里。 后面按沟通的几个回合，把最后定下来的东西和中间的分歧都摊开。

先把"成功"的壳子统一

第一轮沟通没有直接谈错误，先谈成功。因为错误结构要统一，前提是成功结构也统一——如果连成功长什么样都不固定，前端连"这次到底成没成"都要现猜。

这里有个我自己踩过的坑，写出来警醒后人：别让请求层"吞掉"业务失败然后返回个空对象。早期为了图省事，我把业务失败的时候直接 return null，结果页面里 then 照样执行，拿到 null 又去访问属性，错误被掩盖得更深，报错栈指向的地方和真正出错的地方隔着十万八千里。失败就要 reject，让它干干净净走到 catch，这是底线。

errors 这个字段的格式，是和用户模块那位同事分歧最大的一处。他想给数组 [{ field, message }]，理由是"将来一个字段可能有多条错误"。前端坚持用对象，因为表单回填本来就是按字段名查的，数组每次都得 find 一遍。对方抛出"扩展性"，反问一句"你现在有哪个接口一个字段能报两条错？"——想了半天，一个都举不出来。最后折中：单条错误就用对象 { field: message }，确实需要多条的极少数接口才升级成 { field: [msg1, msg2] }，前端做下兼容。规范这东西，能简单就别提前为想象中的需求买单。

这一轮还顺带定下一个小字段，后来救过好几次场：每个错误响应里带一个 traceId，是后端日志链路里这次请求的唯一标识。用户报障时截图里带着 traceId，后端直接拿它去捞日志，不用再问"您大概几点操作的"。这个字段前端一行代码都不用写逻辑，只在错误弹窗的角落里展示出来，成本几乎为零，收益极大。

HTTP 状态码和业务 code 的地盘划分

这是分歧最大、也是收益最大的一轮讨论。核心主张一句话：HTTP 状态码表达协议层，业务 code 表达业务层，两者不能混用。

HTTP 状态码回答的是"这次请求在传输和鉴权层面发生了什么"：

  • 200 请求正常到达并处理（哪怕业务失败，只要服务正常响应了，也算 200）——这一条后面被修正了，往下看
  • 401 没登录 / token 失效
  • 403 登录了但没权限
  • 404 资源不存在
  • 500 服务端自己挂了

业务 code 回答的是"在业务规则层面发生了什么"：名称重复、库存不足、验证码错误、订单状态不允许操作……这些是后端业务逻辑主动判定的结果，跟 HTTP 协议没半毛钱关系。

这个问题讨论了整整一个下午，分成两派。商品模块那位同事是全 200 派：只要服务正常处理了请求，HTTP 就是 200，对错全看 body 里的 code。理由是前端逻辑统一、网关配置省事。用户模块那位同事是语义 HTTP 派：业务失败就该用对应的 4xx，校验失败用 422，权限不够用 403，符合 REST 语义，监控告警直接拿状态码做。

两边说的都有道理，也都有硬伤。全 200 的问题是：网关、监控、浏览器 Network 面板全是绿的，出了业务问题在监控曲线上完全看不出来——运维同学听到这句当场表态反对全 200。语义 HTTP 的问题是：4xx 的细分粒度就那么几个，业务错误五花八门根本不够分，硬套只会造出"到底该用 409 还是 422"的神学争论。

最后的取舍是分层混用：鉴权和资源这类天然属于协议层的，老老实实用 401/403/404；纯业务规则的失败（名称重复、库存不足）统一走 400，再用 body 里的业务 code 细分。这样监控可以靠"4xx/5xx 比例"做粗粒度告警，前端又能靠业务 code 做精细处理，两边都不亏。

会上一致通过、写进纪要的还有一条红线：最不能接受的是两个极端——所有错误都返回 200（监控瞎了），或者所有业务错误都甩 500（运维半夜被告警叫醒，结果只是用户输错了验证码）。500 是"程序员的锅"专用，业务规则失败不配占用 500。 订单模块那个业务失败返回 500 HTML 页的接口，就是在这一轮被点名整改的。

message 的文案归谁管

前面几轮定下来之后，又冒出来一个谁都没想到要谈的问题：message 里的文案到底归谁写？

导火索是商品模块那句 "msg": "stock not enough"——英文的，因为对方抄的异常信息直接往外抛。还有订单模块的"系统繁忙，请稍后再试"，实际上是数据库连接池满了，这句文案把一个该告警的事故说成了用户侧的正常提示。

最后定的分工是：message 是给用户看的，必须是中文、可直接展示；给程序看的信息走 code 和 traceId。后端不确定文案怎么写的时候宁可写得笼统（"操作失败"），由前端按 code 映射成更精确的文案兜底。这样文案的最终解释权在前端，后端不用为"提示语不够友好"背锅，双方都轻松。这条约定看起来鸡毛蒜皮，但它把"报错文案改一个字要发一次后端版本"这种荒唐事彻底消灭了。

前端只维护一个转换层

规范定了归定了，老接口不可能一夜全改，新来的后端也未必第一天就守规矩。所以前面所有约定，落到前端代码上就是一件事——把后端千奇百怪（以及未来可能再变）的错误，收敛成一个稳定的内部结构。这个函数叫 normalizeError，整个项目所有报错都先过它：

body.message || body.msg 这种兼容写法，就是规范落地过渡期的产物。规范定了之后老接口按排期慢慢改，前端做一层兼容，让新老接口平滑共存——这是转换层最大的价值：脏活只脏在一个地方。 后端哪天又冒出个 error 字段，只改这一行，不用满项目搜 catch。

顺带一提 502 和 503：这两个多半不是后端应用给的，是 Nginx 这类网关在后端挂掉或重启时代播的，body 里根本不会有我们约定的结构。这也是 defaultMessageByStatus 必须存在的原因——契约管得了自己人，管不了网关。

定下的东西要落在纸上，不能落在嘴上

这套结构再好，如果只活在那几次沟通的口头共识里，下个季度新来的后端同学一上手照样我行我素。最后干了三件事把共识固化下来。

一是把错误码维护成一张表，业务 code 按模块分段（用户模块 40000-40099，商品模块 41000-41099……），前后端共享同一份，前端甚至可以据此做错误码到文案的兜底映射：

二是在 Mock 阶段就让 Mock 数据严格遵守这个结构。我们用的 Mock 平台（YAPI 那类）里，每个接口的失败用例都按契约造好，这样联调前前端的 catch 逻辑已经测过了，真接上去基本不返工。

三是把整份约定写进了接口文档的第一页，新接口评审时第一条检查项就是"错误结构是否符合契约"。规矩写在文档第一页和写在某次群聊记录里，是完全不同的两种约束力。

约定落地之后

上个月的一次迭代里，订单模块的新接口第一次联调就零返工——错误结构、字段级 errors、traceId 一个不缺，前端的 catch 一行没改。对照五月份对着 "stock not enough" 和 500 HTML 页排查半天的经历，这一套约定省下来的联调时间是实打实的。

错误约定不是形式，而是协作的润滑剂：统一成功和失败的结构，把协议层和业务层分开，字段级错误带上字段名，message 只给用户看、code 和 traceId 给程序看，最后在前端做一层 normalizeError 收口。把脏活藏在一处，项目的健壮性和联调效率都会显著提升——起点只是把那份"失败花样清单"列出来，拉着后端一条条对齐。

这套约定也不是一次定死就完事。往后接手新模块时，第一件事仍然是把接口的错误响应过一遍，看它是不是老实遵守这份契约——三个月前守规矩的接口，换了个人维护也可能悄悄跑偏，normalizeError 里那些兼容分支就是留给这种"渐渐跑偏"用的安全网。
