前后端接口错误约定：message 不能每个接口都不一样

2018-09-18
前端基础构建与模块化

前后端联调时，最消耗我精力的从来不是正常数据，而是错误。正常数据无非是把字段渲染出来，结构对不上大不了改个映射。可错误处理是散落在每一个 .catch 里的，一旦后端各个接口对"出错"的表达方式不一致，前端就会被逼着写一堆 if-else 去猜测对方到底想说什么。

去年接一个后台管理系统，对接的后端是三个人分模块写的，没有统一规范。我大概数了一下，光是"失败"这件事，我就遇到过这些花样：

最离谱的是有个接口，业务出错时 HTTP 返回 200，body 里塞个 code: -1；而真正服务器异常的时候直接给我一坨 500 的 HTML 错误页，JSON.parse 当场抛异常，连 message 都拿不到。我当时在每个页面里写的 error.response.data.message，碰到这些就全线崩溃，要么显示 undefined，要么干脆白屏。

那阵子我才真正理解一件事：接口错误如果没有约定，烂账最后一定会全部转嫁到前端的 catch 块里。 后来我跟后端一起把错误契约拉出来定死，前端只维护一个统一的转换层，整个项目的报错体验和代码量才回到正轨。这篇就把当时定下来的东西和踩过的坑整理一遍。

先把"成功"的壳子统一

错误结构要统一，前提是成功结构也统一。如果连成功长什么样都不固定，前端连"这次到底成没成"都要现猜。我们最后定的是经典的三段式：

code === 0 表示业务成功，data 放真正的数据，message 给个可读文案（成功一般用不上，但留着方便兜底）。请求层只认 code，不认别的：

这里有个我踩过的坑：别让请求层"吞掉"业务失败然后返回个空对象。早期为了图省事，我把业务失败的时候直接 return null，结果页面里 then 照样执行，拿到 null 又去访问属性，错误被掩盖得更深。失败就要 reject，让它干干净净走到 catch，这是底线。

定 errors 这个字段的时候，我和后端为格式吵过一架。他们一开始想给数组 [{ field, message }]，理由是"将来一个字段可能有多条错误"。我坚持用对象，因为表单回填本来就是按字段名查的，数组每次都得 find 一遍。最后折中：单条错误就用对象 { field: message }，确实需要多条的极少数接口才升级成 { field: [msg1, msg2] }，前端做下兼容。规范这东西，能简单就别提前为想象中的需求买单。

HTTP 状态码和业务 code 各管各的

这是当时争议最大、也是收益最大的一条约定：HTTP 状态码表达协议层，业务 code 表达业务层，两者不能混用。

HTTP 状态码回答的是"这次请求在传输和鉴权层面发生了什么"：

  • 200 请求正常到达并处理（哪怕业务失败，只要服务正常响应了，也算 200）—— 这点后面要修正，往下看
  • 401 没登录 / token 失效
  • 403 登录了但没权限
  • 404 资源不存在
  • 500 服务端自己挂了

业务 code 回答的是"在业务规则层面发生了什么"：名称重复、库存不足、验证码错误、订单状态不允许操作……这些是后端业务逻辑主动判定的结果，跟 HTTP 协议没半毛钱关系。

这里有个经典的两难，我们反复掂量过：业务失败到底该用 HTTP 200 还是 4xx？ 两种流派：

  • 全 200 派：只要服务正常处理了请求，HTTP 就是 200，对错全看 body 里的 code。好处是前端逻辑统一，坏处是网关、监控、浏览器开发者工具的 Network 面板全是绿的，出了业务问题在监控曲线上完全看不出来。
  • 语义 HTTP 派：业务失败用对应的 4xx（比如校验失败用 422，权限不够用 403）。好处是符合 REST 语义、监控告警能直接用状态码做，坏处是 4xx 的细分粒度有限，业务错误五花八门根本不够分。

我们最后的取舍是分层混用：鉴权和资源这类天然属于协议层的，老老实实用 401/403/404；纯业务规则的失败（名称重复、库存不足）统一走 400，再用 body 里的业务 code 细分。这样监控可以靠"4xx/5xx 比例"做粗粒度告警，前端又能靠业务 code 做精细处理，两边都不亏。

最不能接受的就是两个极端：所有错误都返回 200（监控瞎了），或者所有业务错误都甩 500（运维半夜被告警叫醒，结果只是用户输错了验证码）。500 应该是"程序员的锅"专用，业务规则失败不配占用 500。

核心：前端只维护一个转换层

把约定写成文档，而不是靠口头

最后想说的是流程层面的事。这套结构再好，如果只活在某次联调的口头约定里，新来的后端同学一上手照样我行我素。我们当时干了两件事：

一是把错误码维护成一张表，业务 code 按模块分段（用户模块 40000-40099，商品模块 41000-41099……），前后端共享同一份，前端甚至可以据此做错误码到文案的兜底映射；二是在 Mock 阶段就让 Mock 数据严格遵守这个结构，这样联调前前端的 catch 逻辑已经测过了，真接上去基本不返工。

小结

接口错误约定是前后端协作里最容易被忽略、又最折磨人的地方。回头看，真正起作用的就几条：成功和失败用固定形状，HTTP 状态码和业务 code 分层各管各的，字段错误带上字段名，前端只维护一个 normalizeError 收口所有脏活，401 这类全局错误在请求层统一拦截。

前端最怕的从来不是接口失败，而是每个接口失败得都不一样。错误结构一旦稳定，catch 块就能从"逐个猜谜"变成"统一处理"，页面体验和代码维护一起变好——这点投入，绝对值回票价。
