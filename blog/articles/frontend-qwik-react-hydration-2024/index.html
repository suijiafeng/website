Qwik 和 React Hydration 的区别：为什么它强调可恢复性

2024-03-21
前端基础React性能与缓存

现代前端框架经常讨论一个问题：页面已经在服务端渲染了，为什么浏览器还要下载大量 JavaScript 再执行一遍？

这就是 Hydration 相关讨论的核心。

Qwik 提出的 Resumability，也就是“可恢复性”，就是为了解决这类成本。

React Hydration 做了什么

React 服务端渲染会先在服务端生成 HTML。

浏览器拿到 HTML 后，页面能先显示出来。但如果要让页面具备交互能力，React 还需要下载 JavaScript，并在客户端重新建立组件树和事件绑定。

这个过程就是 Hydration。

它的好处是模型统一，React 组件在服务端和客户端都能工作。

问题是：页面越大，需要下载和执行的 JavaScript 越多，Hydration 成本也越高。

Qwik 的思路

Qwik 更强调按需恢复交互。

它不希望页面一加载就把所有交互逻辑都执行一遍，而是尽量把交互代码拆得更细，并在真正需要时再加载。

比如一个页面底部有反馈按钮，用户没有滚动到那里时，就没必要提前下载和执行对应逻辑。

这背后的目标很简单：让首屏少做事。

可恢复性为什么重要

可恢复性关注的是：服务端已经做过的工作，客户端能不能接着用，而不是重做一遍。

如果浏览器只需要知道“这个按钮需要交互时加载哪段代码”，而不是立即重建完整应用状态，启动成本就会下降。

这对内容型页面、营销页、长页面、低端设备和弱网环境都很有意义。

React 也能优化，但需要更多手工设计

React 当然也有很多优化方式：

  • 代码分割
  • 懒加载
  • Suspense
  • Server Components
  • 局部交互组件

但很多优化需要开发者主动设计边界。

Qwik 则试图把“什么时候加载什么 JavaScript”变成框架默认策略。

小结

React Hydration 和 Qwik Resumability 的区别，本质是客户端启动成本的处理方式不同。

React 更偏向恢复完整应用交互模型，Qwik 更强调按需加载和按需恢复。理解这点，有助于我们重新思考：页面首次加载时，用户真的需要那么多 JavaScript 吗？
