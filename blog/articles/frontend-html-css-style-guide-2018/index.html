给团队立一份 HTML 和 CSS 风格指南：从一次改按钮颜色的事故说起

2018-10-11
前端基础CSS

样式规范最能暴露价值的时候，不是新页面刚开始写，而是你只想改一个颜色，却发现根本不知道全项目到底有多少处在偷偷用它。一个本该半小时结束的小改动，最后拖成一天半，问题通常不在颜色本身，而在命名、作用域和样式职责从来没被约束过。

我们组当时就是这种状态。两个老项目一个新项目，样式各写各的：有人 class 全用拼音缩写，有人爱写 .box1、.box2 一路编号下去，还有人恨不得把样式全堆进一个八百多行的 style.css。我全局搜 background，搜出来几十处蓝色，有十六进制的、有 rgb 的、还有两处大小写不一样的同一个色值。哪个是按钮、哪个是标签、哪个早就没页面在用了，没人说得清。我不敢批量替换，只能一处一处开页面肉眼确认。

改完那天晚上我在组会上说了这事，组长拍板：立规范，我执笔。接下来两周，我把这份 HTML/CSS 风格指南从初稿磨到落地，中间吵了好几架，也捡回来不少自己都没想明白过的基础知识。

写之前我先想清楚了一件事，也写在了指南第一页：**规范不是为了把每个人的习惯磨成一样，而是为了减少沟通成本。**一个人写的页面，另一个人接手时，应该能快速看懂结构、样式职责和命名意图。风格规范省的不是写代码的时间，而是改代码、删代码、交接代码的时间——这次换颜色的事故就是明证，写的时候人人都快，改的时候集体趴窝。

第一节先写最不起眼的：文档头

初稿第一节我写的是文档声明和 <head>，被同事笑"这也要写？谁不知道 DOCTYPE"。我还真有故事回敬他。

年初接手的一个老页面，布局怎么调都差几个像素，width 的表现完全不讲道理。查了半天 CSS 没查出毛病，最后发现是页面顶上压根没有 <!DOCTYPE html>，IE 直接进了怪异模式（quirks mode），盒模型算法都变了——padding 算不算进 width 都跟标准模式不一样，量好的间距自然全错位。这种问题最坑的地方是它不报错，只是"看起来不对"，你会下意识怀疑自己的 CSS，根本想不到是文档声明的事。

所以指南第一条就是标准的 HTML5 骨架：

lang、charset、title 这些信息也不许随手省略。它们不影响你把页面"画出来"，但会影响浏览器、搜索引擎和辅助技术理解页面。charset 尤其要放在 <head> 很靠前的位置——它得在浏览器开始解析正文之前就确定编码，否则中文页面可能先以默认编码解析了一段，再回头重解，偶尔会闪一下乱码。lang="zh-CN" 看着没用，但读屏软件会根据它选中文语音引擎，搜索引擎也用它判断页面语言，写上几乎零成本。

顺着这节我还补了一条基线样式的约定。之前两个项目一个用某年从网上抄的 reset（* { margin: 0; padding: 0; } 那种一刀切），一个啥都没用，同一个组件搬过去表现就不一样。讨论后统一引 normalize.css：它不是粗暴清零，而是把各浏览器的默认样式修到一致、保留合理的默认值。基线不统一，后面所有"为什么这个组件在那边长得不一样"的问题都查不到头。

主标题用 h1，段落用 p，导航用 nav，主内容用 main，列表用 ul、ol、li。不要为了样式方便就到处使用 div——样式交给 CSS，结构交给合适的标签。语义化不是为了"显得专业"，而是让页面结构自己说话。

讨论"到底该用什么标签"时我贡献了一个自己的土办法，后来直接进了指南：把 CSS 全关掉，光看 HTML 渲染出来的样子。如果关了样式之后，标题还是标题、列表还是列表、导航还是一组链接、内容层级还读得通，那语义大概率是对的。如果关了样式整个页面糊成一坨没头没尾的文字，说明结构信息全靠 CSS 在撑，标签没承担它该承担的含义。读屏软件用户"看到"的，差不多就是关掉 CSS 之后那个样子。

按钮和链接也别混。我们老项目里有大把 <div onclick="..."> 当按钮用的，视觉上没差别，但它不能被 Tab 聚焦、不能用回车和空格触发、读屏软件也不会读成"按钮"。能用 <button> 就别用 div，能用 <a href> 跳转就别拿 JS 模拟。原生元素白送你一堆键盘和无障碍行为，自己用 div 重新实现一遍既费劲又容易漏。

BEM 唯一让人不爽的是类名长，article-card__header-title--active 这种写起来累，写 .box1 的同事第一个抗议。我们的折中是：组件块名尽量短（用 .card 而不是 .article-list-item-card），元素层级别套太深，超过两层 __ 一般说明这个组件该拆了。命名长短是表象，套太深说明组件粒度有问题，这才是要警惕的信号。

长选择器还有个隐蔽的代价是特异性（specificity）。上面那条选择器特异性高得离谱，后面谁想覆盖它，要么写一条同样冗长的选择器，要么干脆甩个 !important。我数了数老项目，!important 出现了六十多次，逐个往回追，基本都能追溯到早期某几条特异性失控的选择器——大家覆盖不动就开始升级武器，最后整个样式表进入"特异性军备竞赛"，谁也压不住谁。

所以指南里立了一条朴素的纪律：尽量只用单层 class 选择器，特异性拉平，需要区分状态就加修饰类。!important 原则上不用，真用了必须写注释说明为什么。一旦发现自己想写 !important，先停下来想想是不是某个选择器太重了，把它降下来比硬覆盖健康得多。

顺带把浏览器前缀的乱象也一起清了。老项目里 -webkit-、-moz- 前缀是手写的，有的写全了有的漏了，还有几处前缀写了标准属性反而忘了。新项目是 Vue CLI 3 起的，构建链里本来就带 autoprefixer，我们统一在 package.json 里配好 browserslist（要兼容到 IE11），前缀全部交给工具生成，手写前缀从此在 review 里见一次打回一次。至于 CSS 自定义属性（变量），我个人很想上——主题色改一处生效全站，正对这次事故的病根——但 IE11 不支持，我们的客户里 IE11 还是验收硬指标，只能先在纯内部工具里试水，指南里标为"观望"。

格式：能交给工具的，别指望人自觉

指南最后一部分是格式，包括这些最基础的规则：

  • 缩进一致
  • 属性顺序尽量稳定
  • 不写无用代码
  • 删除不用的选择器
  • 避免过深嵌套

落地：一张贴在 review 模板里的清单

规范写完不能只躺在 wiki 里。我把它压缩成一张检查清单，直接贴进了我们合并请求的描述模板，每次提交前快速过一遍：

  • 页面是否有清楚的标题层级
  • 交互控件是否有可访问名称
  • 图片 alt 是否准确
  • CSS 类名是否表达业务或组件含义
  • 是否存在无用选择器和重复声明
  • 是否有过深嵌套或过强选择器
  • 同类组件的结构和命名是否一致

这些检查不复杂，但能拦住很多后续维护问题。

到这周为止，规范跑了三个多星期。上周设计又来微调了一次辅助色，这回我搜的是组件前缀，二十分钟改完提测，没漏一处。写 .box1 的同事在群里发了句"行吧，服了"。

**写规范不是怕人变笨，而是让团队在交接和改动时少猜多数错。**语义化标签、清晰命名、稳定格式与可访问性，这些基础日后会省下大量沟通和排查时间。把能交给工具的规则自动化，让人把精力放回设计与逻辑上，至于剩下那些工具管不了的，就靠这份指南和每次 review 里多问的那一句"这个类名，半年后你还认得吗"。
