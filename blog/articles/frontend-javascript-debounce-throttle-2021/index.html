防抖和节流怎么选：不是背定义，而是先看事件有多频繁

2021-06-02
前端基础

前端里很多交互事件都不是“偶尔触发一次”，而是短时间内会连续触发很多次。

最典型的有：

  • 输入框输入
  • 页面滚动
  • 浏览器窗口缩放
  • 鼠标移动

如果每次触发都立刻执行昂贵逻辑，很容易造成性能浪费或者重复请求。这时候防抖和节流就会派上用场。

说个我自己印象很深的事。早年接手一个后台管理项目，列表页有个搜索框，产品反馈“输得越快越卡，结果还乱跳”。我打开 Network 一看，输 订单 两个字居然发了五六个请求，回来的顺序还乱七八糟，最后界面显示的是中间某次的结果。那一刻我才真正意识到，高频事件不加控制，浪费的不只是机器资源，还有用户对这个产品“靠不靠谱”的感觉。后来我习惯了一个动作：凡是绑 input、scroll、resize、mousemove 这种事件，第一反应先打开 DevTools 数一数它一秒钟触发多少次，心里有数了再决定怎么压。

两者看起来像，目标其实不一样

防抖的思路是：等一等，直到用户停下来再执行。

节流的思路是：别执行得太频繁，固定一段时间内最多执行一次。

用最朴素的话说：

  • 防抖适合“最后一次才重要”
  • 节流适合“过程中的连续反馈也重要”

我喜欢拿电梯来类比。防抖像电梯关门：只要还有人进来，它就一直等，直到没人动了才真正走，所以中间那些“进来一个人”的瞬间都被忽略，只认最后那一刻。节流则像水龙头开到固定流量：不管你怎么拧，每秒就出这么多水，多了也不给，保证均匀输出。理解了这两个画面，后面遇到任何场景，我基本不用查资料就能定方向——是“等用户停手”，还是“匀速给反馈”。

说得再精确一点，区别就在“计时器在什么时候重置”：防抖是每次触发都把计时器清零重来，所以只要事件还在连续发生就永远不执行，直到最后一次之后安静地等满 delay 才执行一次；节流是固定窗口内最多执行一次，窗口没到的触发直接忽略，窗口一到就放行，事件再密也按这个频率匀速吐。一句话——防抖关心“最后一次”，节流关心“频率”。

输入框搜索为什么常用防抖

例如联想搜索里，用户每输入一个字符都可能触发查询。

如果完全不做控制，输入 javascript 可能会连续发出很多次请求，不仅浪费资源，界面结果也容易来回闪。

这类场景更适合防抖：

用户只有在短时间内停止输入后，真正的查询逻辑才会执行。

这个版本能用，但实际项目里我踩过几个坑，慢慢补出了更完整的写法。

第一个坑是 delay 取值。一开始我图省事写了 500ms，测试时同事抱怨“感觉很迟钝”。后来调到 300ms 左右才舒服。这个数字没有标准答案，但有个经验：搜索联想我一般用 250~350ms，太短压不住请求，太长用户会觉得卡。表单校验类的可以更长，到 500ms 也没人在意。

第二个坑是“用户明明已经输完、还得再等一个 delay”。比如用户粘贴了一段文字，意图很明确，没必要再等。这时候 leading（首次立即执行）就有用了。我后来常用的版本带了配置项，还顺手返回一个 cancel，因为组件卸载时不取消定时器，回调里访问已销毁的 state 会直接报错，这个 React 项目里特别容易遇到：

还有个容易忽略的点：this 和事件对象。如果你把回调直接挂在 DOM 上，里面又用到了 e.target，记得别在 setTimeout 里访问原始事件对象——老浏览器会做事件池复用，等定时器跑的时候 e 可能已经被回收，属性全变 null。要用就先把需要的值取出来存进闭包。这个坑我在一个移动端项目排查了快一下午，最后发现是合成事件被复用了。

滚动监听为什么经常用节流

滚动事件触发频率很高，如果每触发一次都立刻计算布局、读取位置、发埋点，性能会非常吃紧。

但滚动类场景通常又不适合等到用户完全停下才更新，因为页面过程中的反馈也很重要，比如：

  • 懒加载检测
  • 返回顶部按钮显隐
  • 吸顶状态判断

这个时间戳版本简单可靠，但它有个特征我吃过亏：它是 leading 触发、没有 trailing。意思是最后一次触发如果落在间隔内，会被直接丢掉。表现出来就是“滚动停下那一刻的状态没更新”。比如返回顶部按钮，用户停在某个位置，结果按钮显隐判断停留在上一次节流点，状态错了。后来我都用时间戳加定时器的混合版，保证最后一帧也会补上：

另外提一句 Date.now() 的事。早些时候我见过有人用 new Date() 取时间，每次触发都 new 一个对象，高频场景下纯属浪费；用 Date.now() 拿时间戳就够了，更省。要是对精度有更高要求、又跑在支持的环境里，performance.now() 是更稳的选择，它不受系统时间被改的影响。

还有一种节流我现在更偏爱：如果回调干的是改样式、移动元素这类要落到画面上的活，与其用固定毫秒数，不如直接用 requestAnimationFrame 节流——它天然跟着浏览器的渲染节奏走（通常 60fps、约 16.6ms 一帧），既不会比屏幕刷新更快地白做计算，也不会因为 delay 取小了在一帧内重复触发。做法是用一个标志位挡住，直到下一帧才放行：

不是所有高频事件都必须处理

很多时候我们一提性能优化，就会先想要不要加防抖节流。但更应该先问的是：这个事件真的需要监听吗？监听后真的每次都要做事吗？

例如某些需求只是“滚动到底时触发一次加载”，那比起挂一个复杂的 scroll 回调，也许更好的办法是用更合适的观察机制或者更少的判断时机。

这里我必须提一下 IntersectionObserver。以前做懒加载和无限滚动，我都是 scroll 里 getBoundingClientRect 一通算，再套个节流，写得又长又容易错，还会强制触发重排。自从换成 IntersectionObserver，整段逻辑清爽太多，而且它本身就是浏览器在主线程外帮你做判断，根本不用我再去节流：

放一个不可见的“哨兵”元素在列表底部，它进视口就触发加载，比手写滚动判断稳得多。同理，纯展示类的滚动动效，能用 CSS 的 position: sticky 解决就别去监听 scroll 算吸顶。我的原则变成了：能不监听就不监听，实在要监听再谈防抖节流。

也就是说，防抖节流是在控制已有事件成本，不是替代事件设计本身。

实际坑点通常在“时机预期”不一致

防抖和节流最容易出问题的地方，不是函数写不出来，而是和业务预期不匹配。

例如：

  • 输入框用了节流，导致用户停下来后结果不是立刻最准的那次
  • 滚动监听用了防抖，过程中的 UI 反馈明显滞后
  • 按钮点击做了防抖，却误伤了正常双击场景

所以选择之前，一定要先想清楚：我到底要的是最终结果，还是过程中的连续响应？

按钮防抖那条我单独说一下，因为太典型了。最初为了防止用户狂点提交按钮重复下单，我给点击事件套了防抖，结果测试反馈“点了没反应，要点两下才出来”——因为防抖会等 delay 之后才执行，第一下被吞了。这种“防重复提交”的需求，其实要的是节流的 leading（第一下立刻执行、后面一段时间内屏蔽），或者干脆用一个 loading 标志位：请求发出去就置 true、禁用按钮，回来再放开。逻辑明确，用户也有明确的视觉反馈。我现在的判断是：表单提交、支付这类按钮，宁可用 loading 锁，也不轻易用防抖，因为防抖的“延迟感”会让用户以为没点上。

它们解决的是频率问题，不是所有异步问题

还有一个常见误解，是把防抖节流当成接口并发控制方案。

它们确实能减少触发次数，但如果请求已经发出，后续还涉及取消旧请求、只保留最新结果、避免顺序覆盖，那就不是单靠防抖节流能完全解决的了。

前端里很多交互问题最终都不只是“少执行几次”，还要考虑结果一致性。

我现在搜索框的标配，是防抖配上请求取消。早些年用 axios 我会存一个 cancelToken，每次发新请求前先把上一个取消掉；后来浏览器原生的 AbortController 普及了，写法更干净：

会选比会背更重要

那次搜索框的乌龙之后，我面试问防抖节流也不再让人写实现了，就问一句"按钮防重复提交该用哪个"——能答到"其实更适合用 loading 锁"的人，基本就不用再问别的了。我自己的判断也收敛成两句：频繁输入、最终结果更重要，用防抖；连续触发、过程反馈也重要，用节流。判断顺了，大部分场景不会太纠结。

但别把防抖节流当成万能药，它们只是第一层削峰。搜索框做了防抖，前一个请求若回得更慢仍可能覆盖后一个更准的结果——这已经是“异步结果顺序”问题，得靠取消旧请求或只认最新结果来兜（前面那段 AbortController 配防抖就是干这个的）；滚动做了节流，如果回调里还在做大量布局计算或每次都读最新 DOM，照样卡。所以真正做得好的频率控制，开发者感觉是页面更稳，用户则完全感觉不到系统在“等”他——这要靠你在削峰之外，继续盯着回调够不够轻、结果会不会过期、有没有比监听事件更合适的实现。
