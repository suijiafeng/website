防抖和节流怎么选：不是背定义，而是先看事件有多频繁

2021-06-02
前端基础

前端里很多交互事件都不是“偶尔触发一次”，而是短时间内会连续触发很多次。

最典型的有：

  • 输入框输入
  • 页面滚动
  • 浏览器窗口缩放
  • 鼠标移动

如果每次触发都立刻执行昂贵逻辑，很容易造成性能浪费或者重复请求。这时候防抖和节流就会派上用场。

两者看起来像，目标其实不一样

防抖的思路是：等一等，直到用户停下来再执行。

节流的思路是：别执行得太频繁，固定一段时间内最多执行一次。

用最朴素的话说：

  • 防抖适合“最后一次才重要”
  • 节流适合“过程中的连续反馈也重要”

输入框搜索为什么常用防抖

例如联想搜索里，用户每输入一个字符都可能触发查询。

如果完全不做控制，输入 javascript 可能会连续发出很多次请求，不仅浪费资源，界面结果也容易来回闪。

这类场景更适合防抖：

用户只有在短时间内停止输入后，真正的查询逻辑才会执行。

滚动监听为什么经常用节流

滚动事件触发频率很高，如果每触发一次都立刻计算布局、读取位置、发埋点，性能会非常吃紧。

但滚动类场景通常又不适合等到用户完全停下才更新，因为页面过程中的反馈也很重要，比如：

  • 懒加载检测
  • 返回顶部按钮显隐
  • 吸顶状态判断

这时节流更合适，因为它能控制执行频率，同时保留持续反馈：

不是所有高频事件都必须处理

很多时候我们一提性能优化，就会先想要不要加防抖节流。但更应该先问的是：这个事件真的需要监听吗？监听后真的每次都要做事吗？

例如某些需求只是“滚动到底时触发一次加载”，那比起挂一个复杂的 scroll 回调，也许更好的办法是用更合适的观察机制或者更少的判断时机。

也就是说，防抖节流是在控制已有事件成本，不是替代事件设计本身。

实际坑点通常在“时机预期”不一致

防抖和节流最容易出问题的地方，不是函数写不出来，而是和业务预期不匹配。

例如：

  • 输入框用了节流，导致用户停下来后结果不是立刻最准的那次
  • 滚动监听用了防抖，过程中的 UI 反馈明显滞后
  • 按钮点击做了防抖，却误伤了正常双击场景

所以选择之前，一定要先想清楚：我到底要的是最终结果，还是过程中的连续响应？

它们解决的是频率问题，不是所有异步问题

还有一个常见误解，是把防抖节流当成接口并发控制方案。

它们确实能减少触发次数，但如果请求已经发出，后续还涉及取消旧请求、只保留最新结果、避免顺序覆盖，那就不是单靠防抖节流能完全解决的了。

前端里很多交互问题最终都不只是“少执行几次”，还要考虑结果一致性。

会选比会背更重要

我后来对防抖节流的理解越来越简单：

  • 频繁输入，最终结果更重要，用防抖
  • 连续触发，过程反馈也重要，用节流

如果这个判断顺了，大部分场景不会太纠结。

前端很多基础技巧都这样，不是看你能不能背出定义，而是你能不能把它放进具体交互里判断。防抖和节流之所以常见，就是因为高频事件太多，而用户体验和性能之间又必须平衡。

频率控制之外，还要继续想“结果会不会过期”

例如搜索输入框做了防抖，确实减少了请求次数，但如果前一个请求回来得更慢，仍然可能把后一个更准确的结果覆盖掉。这时候问题已经不只是“触发太频繁”，而是“异步结果顺序不稳定”。

同样，滚动监听做了节流，也不代表性能问题自动解决。如果回调里还是做了大量布局计算，或者每次都依赖最新 DOM 状态，页面依然可能卡。

所以防抖和节流更像第一层削峰，而不是完整方案。很多业务场景里还要继续考虑：

  • 是否需要取消旧请求
  • 是否只保留最后一次结果
  • 回调本身够不够轻
  • 有没有比事件监听更合适的实现方式

真正好的频率控制，应该让用户几乎感觉不到

如果用户能明显感觉到：

  • 输入后结果总慢半拍
  • 滚动反馈发涩
  • 按钮点击偶尔像失灵

那通常说明策略和业务目标并没有对齐。防抖节流真正做得好时，开发者会感觉页面更稳，用户则不会觉得系统在故意“等”他。
