Vite 插件入门：理解钩子，比照着模板改更重要

2022-06-06
前端基础构建与模块化

Vite 用起来很简单，但真正遇到项目定制需求时，插件能力就很重要。

比如自动注入变量、转换特殊文件、处理 HTML、添加开发服务器中间件、生成构建产物清单，这些都可以通过插件完成。

插件不是只有框架作者才会写。很多业务项目里的工程化小需求，如果长期靠手工脚本拼接，反而更难维护。理解 Vite 插件的钩子模型后，可以把这些定制逻辑放到更清楚的位置。

我开始写 Vite 插件，是因为一个很普通的需求：每次构建时生成版本信息，页面右下角能看到环境、commit、构建时间，错误上报里也要带上这些字段。最开始用脚本改文件，后来发现 dev、build、测试环境各走各的逻辑，很快就乱了。把它收进插件后，入口反而清楚很多。

所以我现在看插件，不会先想“这个 API 怎么写”，而是先问一句：这个需求到底发生在构建流程的哪个阶段？

Vite 插件是什么

Vite 插件本质上是一个对象。

这个对象里会声明插件名称，以及在不同构建阶段要执行的钩子函数。

Vite 在启动、解析配置、加载模块、转换代码、生成产物时，会按顺序调用这些钩子。

插件对象里最重要的是 name。它不仅用于日志和调试，也会帮助你在插件列表里定位问题。不要随手写一个模糊名字，尤其是团队内部插件。

命名清楚，后面看到构建日志时就知道这段逻辑来自哪里。

如果插件是团队内部用的，我还会在名字里加上范围前缀，例如 internal:。这样遇到构建报错时，可以一眼区分问题来自业务插件、框架插件，还是第三方插件。

常用钩子

刚开始写插件，不需要一次记住所有钩子。

先理解几个常见的就够了：

  • config：修改 Vite 原始配置
  • configResolved：读取最终解析后的配置
  • configureServer：扩展开发服务器
  • transformIndexHtml：处理 index.html
  • resolveId：自定义模块解析
  • load：自定义模块内容
  • transform：转换模块代码
  • generateBundle：生成构建产物前处理文件

不同需求对应不同钩子，不要所有逻辑都塞进 transform。

可以简单理解为：

  • 想改配置，用 config
  • 想知道最终配置，用 configResolved
  • 想处理 HTML，用 transformIndexHtml
  • 想让某个虚拟模块存在，用 resolveId 和 load
  • 想改源码内容，用 transform
  • 想处理最终产物，用 generateBundle

钩子选错，插件就会变得很别扭。例如生成构建清单放在 transform 里就不合适，因为 transform 面对的是单个模块，不适合处理最终 bundle。

我常用下面这个判断方式：

需求更适合的钩子
读取最终配置configResolved
给 dev server 加 mock 或代理中间件configureServer
注入 HTML 标签或全局脚本transformIndexHtml
提供 virtual:* 模块resolveId + load
转换某类源码文件transform
统计最终产物、生成 manifestgenerateBundle

这张表不完整，但足够帮助新人避免“所有逻辑都塞到 transform”。

区分开发和构建

有些插件只应该在开发时运行，有些只应该在构建时运行。

开发和构建的上下文不一样。开发服务器更关注中间件、热更新、调试体验；生产构建更关注产物、压缩、静态资源和部署信息。把两者混在一起，容易出现“开发正常，构建失败”或“构建正常，开发很慢”的问题。

我见过一个插件在 dev 模式里每次请求都重新扫描整个目录，开发时页面一刷新就卡。后来把目录扫描放到启动阶段，并且只监听目标文件变化，开发体验才正常。插件代码也要把性能当回事，它运行在构建链路里，慢一点会被所有开发者反复感受到。

源码转换还要注意 source map。如果插件只是很小的替换，map: null 问题不大；如果插件做了较复杂的代码生成，最好生成正确的 source map，否则调试时断点会对不上。

还有一个经验是：不要轻易用字符串替换处理复杂 JavaScript。简单宏替换可以，涉及语法结构时最好用 AST。字符串替换短期很快，长期容易在注释、字符串字面量、边界语法上翻车。

pre 会更早执行，post 会更晚执行。不要滥用它，但当你需要在框架插件处理前改源码，或者在所有处理之后收集结果时，它很有用。

插件顺序问题通常比较隐蔽。遇到“单独运行正常，和另一个插件一起就异常”的情况，要优先检查执行顺序和处理范围。

插件之间也要尽量少共享隐式状态。比如一个插件写临时文件，另一个插件再读这个文件，顺序一变就出问题。能通过 Vite/Rollup 的上下文传递，就不要依赖难以追踪的全局变量或临时文件。

错误处理和日志

插件内部也需要清楚的错误处理。比如读取文件失败、解析配置失败、转换代码失败，都应该给出明确错误信息。

不要让用户只看到一个底层异常堆栈，却不知道是哪个插件、哪个阶段出错。

调试日志也要克制。开发时可以输出详细信息，生产构建中不要刷屏。必要时可以通过环境变量控制 debug 输出。

插件开发要能联调

写插件时，最好准备一个示例项目。

插件目录负责源码和打包，示例项目负责真实引用插件。这样每次修改插件，都能快速确认效果。

常见做法是：

  • 插件源码用 TypeScript 写
  • 使用 tsup 或类似工具打包
  • examples 目录里准备 Vue、React 或原生示例
  • 本地通过 workspace 或 link 引用插件

没有示例项目的插件，很容易只在想象中可用。

除了示例项目，还要准备最小测试用例。插件很容易被路径、系统差异、构建模式影响。至少要覆盖：

  • dev 模式是否生效
  • build 模式是否生效
  • Windows 和 macOS 路径是否兼容
  • 目标文件不存在时是否有清晰错误
  • 多次启动是否有缓存污染

工程化插件的问题往往不在 happy path，而在各种边界。

我现在还会额外检查两件事：一是插件多次运行是否会生成重复内容，二是插件失败时是否能给出可读错误。内部插件出问题时，报错信息最好带上插件名、输入文件和处理阶段，不要只把底层异常原样扔出来。

Vite 插件的关键不是背 API，而是理解构建流程。

先明确需求发生在哪个阶段，再选择对应钩子。能写出稳定插件后，很多工程化定制就不用靠手工脚本硬凑了。

我现在写 Vite 插件时，会先把需求放到构建流程里定位：它是配置问题、模块解析问题、源码转换问题，还是产物处理问题。阶段定位清楚，插件结构通常就不会乱。
