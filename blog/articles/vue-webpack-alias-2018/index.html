Vue 项目 Webpack 路径别名：别再让目录重构变成数 `../../..`

2018-02-09
Vue构建与模块化

路径别名的价值，通常要等到你第一次大规模挪目录时才会突然变得无比具体。平时多写几层 ../../.. 好像只是丑一点，真要拆模块、改目录、重组页面时，它会瞬间变成最耗时间的那部分工作。

这次个人中心重构就是这样。业务本身不复杂，真正拖时间的不是逻辑改造，而是每挪一个文件，就得回头数一遍路径层级。重构做到一半我就明白了：这不是“多敲几个点”的小麻烦，而是结构性地在放大目录调整成本。

挪一个文件，断一串引用

拆目录的第一个动作是把 views/user/detail 挪到 views/account/detail。文件一挪，页面白屏，控制台一串 Module not found。打开文件一看，顶上是这样的：

文件的层级变了，这些 ../../../ 全部失效，得一个个重新数：从新位置往上跳几层能到 src，再往下进 services。挪一个文件改一次还能忍，这次要挪二三十个文件，每个文件头上五六条 import，我改到下午三点，眼睛已经不认识 .. 这两个点了。

更气人的是 review 环节。同事帮我看 PR，盯着一行 ../../../../components/UserCard.vue 数了半天，回了句"你这里好像少了一层"。我本地一跑，果然 Module not found——这种 bug 一点技术含量都没有，纯粹是路径本身太脆弱了。

还有一处让我心里发毛的：拆目录前我想先全局搜一遍"哪些文件引用了 user 目录"，结果发现根本搜不全。同一个模块，在不同文件里可能是 ../services/user、../../services/user、../../../services/user，搜索关键词都统一不了。重构最怕的就是"我不确定还有没有漏的"，而相对路径天然制造这种不确定。

这里顺便说一下配置本身。如果是自己搭的 webpack 项目，别名配置在 resolve.alias，可以按需要多加几条：

那条 'vue$': 'vue/dist/vue.esm.js' 也值得看懂再留着：vue$ 结尾的 $ 表示精确匹配，作用是把 import Vue from 'vue' 指到带编译器的完整构建版本。Vue 的 npm 包默认入口是 runtime-only 构建，不含模板编译器，如果代码里有 template: '<App/>' 这种运行时编译的写法，用默认入口会报 "You are using the runtime-only build" 的错。别名不只是缩短路径的工具，它还能决定"同一个包名到底解析到哪个文件"，这是它比字符串替换深一层的能力。

resolve.extensions 也别照抄不理解。配了 ['.js', '.vue', '.json'] 之后，import Foo from '@/components/Foo' 会依次尝试 .js、.vue、.json。顺序有讲究——如果目录里同时存在 Foo.js 和 Foo.vue，webpack 会先命中 .js，这种隐蔽的命中错误排查起来很费劲。我这次重构后定下的习惯是：组件 import 明确带 .vue 后缀，或者干脆避免同名文件。

理解配置比只会抄导入路径重要。我见过有人项目跑不起来，报 Module not found: Can't resolve '@/...'，折腾半天才发现是拿了个精简模板，@ 根本没配——如果他知道这个别名只是 resolve.alias 里一行普通配置，而不是 Vue 的"魔法语法"，五分钟就能定位。

搜索的问题也顺带解决了。所有地方都写 @/services/user 之后，全局搜这个字符串就能找到全部引用点，重构前心里有底了。

对新人也友好。这个需求做完没几天来了个实习生，他看 @/services/user 大概能猜到在 src/services 下；要是看到 ../../../services/user，第一反应是去数当前文件在第几层，注意力全耗在路径推理上。我带他的时候专门讲了一句：写 import 时脑子里想的应该是模块名，不是目录树的相对位置。

这里最容易踩的坑是两份配置对不上。jsconfig.json 里的 paths 必须和 webpack 的 alias 严格对应，包括 baseUrl 的基准目录。我就撞过一次：webpack 里加了 @components，jsconfig.json 忘了同步，结果打包没问题、编辑器跳转失效，查了好久才意识到是两边没对齐。现在每次新增别名，我都把这两个文件当成"必须成对改"的东西。

别名要表达边界，不是越多越好

尝到甜头之后我一度想给每个二级目录都开别名：@views、@store、@router、@mixins 排一大串。冷静下来想了想，收手了——配置太多，导入路径反而失去统一感，团队里有人写 @/views/Home、有人写 @views/Home，风格五花八门，搜索和重构会更乱。

最后定下来的尺度是：

  • @ 指向 src，这是主力
  • 真正高频共享的目录（我们是 @components、@services）才单独开别名
  • 业务模块内部优先用相对路径
  • 跨模块依赖才用别名

存量代码怎么迁：别一把梭

我们项目里那些历史遗留的深层相对路径，我没有一次性全替换。定的节奏是：

  • 别名配置先加上，三处（webpack、jsconfig、eslint）同步
  • 新代码一律用别名
  • 改到旧文件时顺手把该文件的 import 调整掉
  • 最后再考虑集中清理

上线前还结结实实栽了一个坑：大小写。Mac 和 Windows 的文件系统默认对大小写不敏感，@/components/userCard 和 @/components/UserCard 在本地都能跑；一部署到 Linux 服务器，文件系统大小写敏感，构建直接 Module not found。这种问题本地永远复现不了，只有 CI 或线上才暴露。后来我发现 vue-cli 的模板其实在开发配置里带了 CaseSensitivePathsPlugin，作用就是让本地构建也按大小写敏感来校验；自己搭的项目装一个 case-sensitive-paths-webpack-plugin 挂上即可，把问题堵在提交之前：

需求交付之后

个人中心改版最后按时上线了。这个需求真正的收获不是那两个新目录，而是它逼我把路径这件"小事"想清楚了：别名不是为了少写几个 ../，是为了让依赖关系稳定——文件挪位置不断引用、全局搜索搜得全、新人一眼看懂模块来源。

工程化很多时候就体现在这种地方：不是让代码显得更高级，而是让后面的人少看几眼就能明白文件关系。下次再有人问我"配别名值不值"，我会把那个数了一下午 ../ 的周一讲给他听。
