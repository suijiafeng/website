Vue 项目里的路径别名为什么值得配：不是偷懒，是在降低维护成本

2018-02-09
Vue构建与模块化

项目目录一深，前端里最先变难看的往往不是业务逻辑，而是导入路径。

你会开始看到这种东西：

第一次还能接受，文件一多以后，这种路径本身就会变成维护负担。我自己就遇到过这样的情况：review 同事 PR 时看到一行 ../../../../，下意识地想去数到底跳了几层，结果数完发现还少写了一层 ..，本地跑不起来——这种 bug 一点技术含量都没有，纯粹是路径本身太脆弱了。

路径别名不是为了让代码看起来更短，而是为了让依赖关系更稳定。这两年带过几个 Vue 项目，越到后期越能体会到这个区别：短只是表象，稳才是真正省时间的地方。

这就是路径别名真正降低维护成本的地方。我有一次重构，把整个 views/user 目录拆成了 views/account 和 views/profile 两块，二三十个文件挪了位置。用相对路径的那个老分支，光改 import 就改了大半天，还漏改了几处导致打包报错；后来同样的操作在用了别名的项目里，几乎是把文件夹拖过去就完事了，import 语句一个都不用动。那一刻我才算真正理解了别名的意义——它把"我在哪"和"我依赖谁"这两件事解耦了。

还有一个容易被忽略的好处：别名让代码搜索变得可靠。当所有地方都写 @/services/user，我在编辑器里全局搜这个字符串就能找到全部引用点。可如果是相对路径，同一个模块在不同文件里可能是 ../services/user、../../services/user、../../../services/user，搜一次根本搜不全，重构时心里特别没底。

目录结构调整时会省很多事

相对路径最麻烦的一点，是它过于依赖当前位置。

只要文件换个目录，很多引用都得跟着改。项目越大，这种成本越明显。

用了别名以后，路径更像是在描述“我依赖哪个模块”，而不是“我从这里往上跳几层再往下找”。

这个差别在团队协作里尤其明显。新人接手项目，看到 @/services/user 大概能猜到是在 src/services 下；可看到 ../../../services/user，他第一反应是去数当前文件在第几层，注意力全耗在路径推理上，根本没空想业务。我现在带新人，会专门讲一句：写 import 的时候你脑子里想的应该是模块名，而不是目录树的相对位置。

这里有个细节值得多说一句：resolve.extensions 决定了你能不能省略后缀。配了 ['.js', '.vue', '.json'] 之后，import Foo from '@/components/Foo' 会依次尝试 .js、.vue、.json。注意顺序是有讲究的——如果 .js 排在 .vue 前面，而你的目录里同时存在 Foo.js 和 Foo.vue，webpack 会优先选中 .js，这种隐蔽的命中错误排查起来很费劲。我后来养成的习惯是：组件文件要么明确带上 .vue 后缀，要么干脆避免同名文件，省得给自己挖坑。

大多数 Vue 项目默认已经把 @ 指向 src，但你仍然要知道它从哪里来。理解配置比只会复制导入路径更重要。我见过有人项目跑不起来，报 Module not found: Can't resolve '@/...'，折腾半天才发现是脚手架版本不同，@ 根本没配上——如果他知道这个别名是 resolve.alias 里一行普通配置，而不是 Vue 的"魔法语法"，五分钟就能定位。

这一步我以前总忘，结果就是：项目能正常打包运行，但在 VS Code 里点 @/components/UserCard 跳不过去，光标悬上去也没有类型提示，写代码全靠记忆。配上 jsconfig.json 之后，Ctrl+点击直接跳到文件，自动补全也认得别名了，体验完全是两回事。

这里最容易踩的坑是两份配置对不上。jsconfig.json 里的 paths 必须和 webpack 的 alias 严格对应，包括 baseUrl 的基准目录。我就遇到过 webpack 配了 @components，但 jsconfig.json 里漏了这条，结果打包没问题、编辑器跳转失效，查了好久才意识到是两边配置没同步。所以每次新增别名，我都会顺手把这两个文件一起改掉，把它们当成"必须成对出现"的东西。

别名要表达边界，不要越配越乱

别名不是越多越好。配置太多以后，导入路径反而会失去统一感。

比较稳的做法是：

  • @ 指向 src
  • 高频共享目录可以单独起别名
  • 业务模块内部优先用相对路径
  • 跨模块依赖才使用稳定别名

我自己摸索出来的一条经验是：相对路径其实在传递一个信号——"这两个文件关系很近，是一伙的"。同目录下的 ./UserAvatar.vue 一看就知道是 UserCard 的内部零件，跟着 UserCard 一起移动、一起删除。可一旦换成 @components/user/UserAvatar.vue，这层"内部关系"反而被抹平了，看起来像是从外部引进来的公共组件。所以局部用相对、跨模块用别名，不只是风格问题，它本身就在表达模块的亲疏关系。

至于别名该配几个，我现在的尺度比早年保守很多。早期我恨不得给每个二级目录都起个别名，@views、@store、@router、@mixins 排一大串，结果团队里有人写 @/views/Home、有人写 @views/Home，导入风格五花八门，搜索和重构反而更乱。后来我基本只留 @ 指向 src，顶多再给 @components、@services 这两个真正高频共享的目录单独开别名，其余一律走 @/xxx。少即是多，这话在别名配置上特别成立。

改别名前要注意迁移成本

如果一个老项目已经到处使用深层相对路径，不建议一次性大范围替换。更稳的方式是：

  • 新增别名配置
  • 新代码优先使用别名
  • 修改旧文件时顺手调整局部导入
  • 最后再考虑集中清理

路径改动看起来简单，但会影响大量文件。迁移时最好配合构建和测试一起做，确保没有遗漏大小写、扩展名和目录层级问题。

大小写这个坑我专门栽过一次。Mac 和 Windows 的文件系统默认对大小写不敏感，@/components/userCard 和 @/components/UserCard 在本地都能跑；可一旦部署到 Linux 服务器，文件系统对大小写敏感，构建直接 Module not found。这种问题本地永远复现不了，只有 CI 或线上才会暴露，排查时特别懵。所以我后来在 CI 里加了一个 case-sensitive-paths-webpack-plugin，让本地构建也按大小写敏感来校验，把问题提前堵在提交前。

真要做大规模替换，纯手工改不现实，也容易漏。我一般会写个小脚本，配合正则把 ../../../services 这类批量换成别名，但换完一定要全量跑一遍构建 + 单测兜底。正则替换最怕误伤字符串字面量或注释里的路径，所以我不太敢一把梭，宁可分目录小批量替换、每批都跑一次构建确认无误，再进行下一批。

Webpack 路径别名看起来只是一个小配置，但它会持续改善项目的可读性。

工程化很多时候就体现在这种小地方：不是让代码显得更高级，而是让后面的人少看几眼就能明白文件关系。

好的别名不是为了隐藏路径，而是为了把项目结构表达得更清楚。
