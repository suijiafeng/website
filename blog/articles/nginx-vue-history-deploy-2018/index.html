Vue history 模式部署：本地能打开，不代表线上刷新不 404

2018-10-16
Vue构建与模块化

项目里有人嫌 URL 上那个 # 难看，提了个需求说能不能去掉。我当时想，不就是把 Vue Router 的 mode 从 hash 改成 history 吗，一行的事。改完本地 npm run dev，路由跳转、刷新都正常，提测一切顺利。结果发到测试服务器，QA 在 /user/list 页面按了下 F5，直接给我截了张 Nginx 的 404 页面过来。

这一行代码改动背后要担的风险，跟代码量完全不成比例。mode: 'history' 把"前端路由"这件事从浏览器内存里，搬到了和服务器博弈的层面：本地 npm run dev 内置的 dev server 已经帮你把回退规则配好了，所以感觉不到问题；但线上要用什么服务器、有没有做同样的回退、有没有二级目录、有没有 CDN，这些都不是前端一行 mode 配置能包办的。本地能跑，跟线上刷新能跑，是两件需要分别确认的事。

为什么 hash 没事，history 会 404

得先把这事的根儿想明白，不然每次出问题都只能照着别人贴的配置抄，抄错了也不知道为什么。

hash 模式的 URL 长这样：https://example.com/#/user/list。# 后面的部分浏览器是不会发给服务器的，它只会把 https://example.com/ 这个请求发出去，拿回 index.html，剩下的 /user/list 全靠 Vue Router 在前端用 hashchange 事件自己解析。所以不管你怎么刷新，服务器收到的永远是根路径，永远有东西返回，自然不会 404。

history 模式靠的是 HTML5 的 history.pushState，URL 变成了干净的 https://example.com/user/list。在 SPA 内部点击跳转时，是 JS 调 pushState 改地址栏，并没有真的发请求，所以也没问题。但你一旦按下刷新，或者直接把这个地址甩给别人在新标签页打开，浏览器就会老老实实把 GET /user/list 发给服务器。而服务器的磁盘上根本没有 /user/list 这个文件或目录——它只有一个 index.html 和一堆打包出来的静态资源。Nginx 找不到，按默认行为就回了 404。

所以这不是 bug，是预期之内的行为。解决思路也就清楚了：让服务器在找不到真实文件时，统一把 index.html 吐回去，剩下的交给前端路由接管。

关键就是 try_files $uri $uri/ /index.html; 这一句。它的执行顺序是：先按 URL 找有没有对应的真实文件（$uri），没有就看是不是目录（$uri/），还没有就回退到最后那个参数 /index.html。注意最后一个参数前面带了 /，是一个 URI 而不是文件名，找不到对应资源时 Nginx 会内部重定向到它——这正是我们要的兜底。

这里有个我栽过的细节：最后那个 fallback 千万别写成 try_files $uri $uri/ =404;，那是默认模板里常见的写法，但对 SPA 来说就等于"找不到就报 404"，等于没配。还有人写成 index.html（不带斜杠），效果和带斜杠在大多数情况下一样，但语义上不规范，建议老老实实写 /index.html。

改完记得 nginx -t 测一下语法再 nginx -s reload，别直接重启把别的站点也搞挂了。

补一句 alias 和 root 的坑：在 location /admin/ 里用 root /var/www; 的话，Nginx 会去 /var/www/admin/ 找，路径会拼上 location；而用 alias /var/www/admin/; 则是直接替换。两者混用是经典翻车点，我一般在子目录场景下统一用 alias 并且结尾都带斜杠。

缓存策略：长缓存资源，但别缓存入口

部署能跑之后，下一个问题是发版。我发了个新版本，自己刷新看到了，但产品经理那边死活还是旧的，让他清缓存才好。这就是 index.html 被缓存惹的祸。

Vue 打包出来的 JS、CSS 文件名都带 contenthash，比如 app.3f2a1b.js，内容一变文件名就变。这种文件可以放心长缓存，因为它永远不会"内容变了名字没变"：

但 index.html 恰恰相反，它的文件名固定，内容却每次发版都变（因为里面引用的 hash 资源名变了）。如果它被长缓存，用户拿到的还是旧入口，旧入口引用的还是旧 hash，新资源根本加载不到，发版等于没发：

no-cache 不是"不缓存"，而是"每次用前都要回服务器验证一下"（配合 ETag/Last-Modified），命中就返回 304，没变就用本地的，变了就拉新的。这样既保证用户每次都能拿到最新入口，又不至于每次都全量下载。规则就一句话：带 hash 的资源往死里缓存，不带 hash 的入口文件不许缓存。

但 proxy_pass 后面那个结尾斜杠的有无，转发结果天差地别，我为这个查了一下午抓包：

  • proxy_pass http://backend:3000/;（带斜杠）：请求 /api/user 会被转成 http://backend:3000/user，/api 这段被吃掉了。
  • proxy_pass http://backend:3000;（不带斜杠）：请求 /api/user 原样转成 http://backend:3000/api/user，前缀保留。

到底要哪种，取决于后端接口本身带不带 /api 前缀。判断的唯一靠谱办法不是猜，是在后端打日志看它实际收到的 URL，或者 tcpdump 抓一下。我现在的习惯是把转发头也补全，不然后端拿到的 Host 和真实 IP 都是 Nginx 的：

别让 try_files 把接口也回退成 HTML

这是个很隐蔽的坑，也是最容易让人怀疑人生的一个。如果你的接口走相对路径、又没有单独配 location /api/，那么请求接口时一旦命中了那条 try_files ... /index.html，后端 404 或者接口路径没匹配上，Nginx 就会把 index.html 这段 HTML 当作响应返回给前端。

表现就是：前端 axios 报 Unexpected token < in JSON at position 0——因为它拿 JSON 解析器去解析 <!DOCTYPE html> 开头的一坨 HTML。第一次遇到这个报错的人很难联想到是 Nginx 配置问题，往往会在前端代码里翻半天。

解决办法就是让接口的 location 优先级高于页面回退，并且接口的 location 里绝对不要写 try_files ... /index.html。location /api/ 会先于 location / 匹配到带 /api/ 的请求，接口的归接口、页面的归页面，互不污染。

浏览器这一头：pushState 不是万能的

服务器这一头配完，浏览器这一头也有边界要交代清楚。history.pushState 是 HTML5 History API 的一部分，IE10 以下完全不支持，Vue Router 在这些浏览器上会自动降级用 hash——这个降级是路由库帮你兜的底，不需要业务代码判断。但要注意的是，pushState 改变地址栏不会触发页面刷新，也不会触发 window.onhashchange；监听地址变化得用 popstate 事件，这个事件只在用户点浏览器前进后退按钮、或者调用 history.back()/forward()/go() 时触发，代码里主动调 pushState/replaceState 是不会触发它的，Vue Router 内部对这一层做了封装，自己写原生路由时这个细节很容易漏。

另外，pushState 第一个参数 state 对象经常被忽略。它会被浏览器保存起来，用户按后退时可以从 event.state 里原样取回，适合存一些"回到这个历史记录时要恢复的状态"（比如列表页的滚动位置、筛选条件），比自己拿 sessionStorage 转存更贴合场景，只是这块状态大小有限制（不同浏览器几百 KB 到几 MB 不等），不能塞太大的数据。

SSR 与预渲染：另一条不用求服务器的路

如果 SEO 是主要诉求而不是单纯为了好看，其实还有一条路完全绕开这套 Nginx 回退配置——服务端渲染。Nuxt.js 当时刚出到 1.x，能把 Vue 项目跑成一个 Node 服务，每个路由请求都在服务端真实渲染出完整 HTML 再吐给浏览器，爬虫和用户看到的是一样的内容，也不存在"刷新 404"这回事，因为每个路径请求都会落到 Node 进程里被正常处理，而不是指望静态文件服务器兜底。代价是要多维护一个 Node 服务、服务端和客户端的代码要同构，改造成本比配几行 Nginx 大得多，一般只有真的在意 SEO 的对外页面才值得上。

折中方案是预渲染（prerender-spa-plugin 这类 webpack 插件），构建时用无头浏览器把几个约定好的路由跑一遍，生成对应路径的静态 HTML 文件，放到磁盘上对应目录。这样 /user/list 请求真的能在磁盘上找到一个 user/list/index.html，连 Nginx 回退都用不上。局限是路由数量得提前枚举，动态路由（比如带 id 的详情页）没法穷举生成，只适合路由数量有限、内容相对静态的场景，我在官网这类页面上用过，中后台系统不合适。

history 到底值不值得

这一圈配下来，history 模式换来的就是 URL 好看、以及对 SEO 稍微友好一点（纯 SPA 不做 SSR，SEO 提升有限）。代价是每上一个新环境、换一个运维、加一层 CDN 或者网关，都得重新确认回退规则在不在。CDN 那层尤其容易忘——有的 CDN 默认只回源静态文件，回退逻辑得在 CDN 控制台单独配置错误页面映射，否则 Nginx 配得再对也白搭。

如果是内部系统、没人在乎 URL 里那个 #，直接用 hash 模式能省掉这一整套部署心智负担。要用 history，就得认下"它是个前后端要约定好的契约"这件事，而不是前端单方面改一行就完事。

history 模式导致的刷新 404，根源是服务器没把前端路由兜底到 index.html。除了那条 try_files，二级目录的资源前缀、入口文件的缓存策略、接口代理的转发规则也必须对齐，缺一个环节，问题就会换个样子重新出现。
