Vue 组件单元测试：先测行为，不要一上来测实现

2018-06-02
Vue构建与模块化

给 Vue 项目补单元测试时，很多人第一反应是：组件这么多，要测到什么时候？

其实不必一开始就覆盖所有组件。测试最应该先保护那些稳定、关键、容易出错的逻辑。尤其是工具函数、权限判断、请求错误转换、复杂表单校验，这些地方比纯展示组件更值得测。

我们团队补测试是被一次线上事故逼出来的。有人重构了一个金额格式化函数，把"分转元"的除法改错了方向，单测没有、code review 也没看出来，结果上线后所有订单金额都大了一百倍，客服电话被打爆。复盘的时候大家达成一个共识：不是所有代码都要测，但那些一旦错了就会出大事、又容易被悄悄改坏的纯逻辑，必须有测试兜着。这之后我们才慢慢把单测铺开，而且严格按"价值优先级"来，不盲目堆覆盖率。

先说下当年的工具链背景。2018 年 Vue 项目做单测，主流是 jest + @vue/test-utils + vue-jest + babel-jest，用 vue-cli 3 的话 vue add unit-jest 一条命令就把配置生成好了。比起更早的 karma + mocha 那套要在真实浏览器里跑，Jest 自带 jsdom、自带断言和 mock、还能算覆盖率，配置成本低很多，这也是当时大家集体转向 Jest 的原因。

像 1.005.toFixed(2) 在 JS 里因为浮点表示其实会得到 '1.00' 而不是 '1.01'，这种坑只有把边界写进用例里才会被逼着面对。我现在写工具函数，常常是先把这些刁钻用例列出来，再回头改实现，相当于拿测试当需求文档用。

组件测试关注用户行为

不要测试组件内部变量叫啥，而要测试用户能看到什么。

如果以后组件内部从 data 改成 Vuex，只要用户行为不变，测试就不应该失败。

这里用 shallowMount 而不是 mount 是有意的：shallowMount 会把子组件都替换成占位的桩，只渲染当前组件本身。好处是测试不会因为某个深层子组件的改动而连带挂掉，关注点更集中，跑得也快。我的经验是大部分组件用 shallowMount 就够，只有当行为确实依赖真实子组件渲染（比如要点子组件触发出来的按钮）时才上 mount。

异步更新要等 nextTick

Vue DOM 更新是异步的。触发事件后马上断言，经常会失败。

异步测试要写清楚等待点，否则用例会变得不稳定。

flushPromises 不是 Jest 自带的，得装 flush-promises 这个小包，它的作用是把当前所有挂起的微任务（Promise 回调）跑完。一个组件里如果是"请求回来 → 改 data → DOM 更新"这条链，往往要同时等 Promise 和 nextTick：

我吃过最大的亏就是"偶发失败"的异步用例——本地跑十次过九次，CI 上时不时红一次。根因几乎都是漏了某个等待点，断言跑在了 DOM 更新之前。这种时好时坏的用例比没测还糟，因为它会让团队慢慢不信任测试，最后干脆 --ci 里跳过。所以异步测试我宁可多写一两行 await，也绝不靠 setTimeout 去"赌"它更新完了。

接口一定要 mock 掉，这点也得强调。单测里真去打后端，慢、不稳定、还可能污染数据，跟单测"快而确定"的初衷完全相反。Jest 的 jest.fn().mockResolvedValue(...) / mockRejectedValue(...) 就够覆盖成功和失败两条路径了。

不要滥用快照

快照测试看起来省事：

但大组件快照很容易变成一大坨 HTML。失败时很难判断是正常变化还是问题。

我只在非常稳定的小组件里用快照。大部分时候，明确断言文本、按钮状态、事件触发更好。

快照测试最大的隐患是"无脑 update"。失败了，开发图省事直接 jest -u 把快照刷新一遍，于是测试永远是绿的，但它早就不保护任何东西了——这跟没测一样，还更骗人。我见过一个几百行的组件快照，改一行样式就 diff 出一大片，根本没人会逐行去看那串 HTML 到底是该变还是不该变，最后大家条件反射地 -u。所以我对快照的态度是：只给那种"输出本来就该一字不差固定下来"的小东西用，比如一个图标组件、一段格式化后的提示文案。

mock 时间和定时器

还有一类很常见但容易写得很别扭的测试：依赖时间的逻辑。比如防抖、倒计时、轮询。真用 setTimeout 等，测试就会慢得让人想砸键盘。Jest 提供了假定时器，可以"手动快进时间"：

jest.advanceTimersByTime 把时间"拨"过去，瞬间完成原本要等 300ms 的事。我以前测倒计时组件傻乎乎地用真定时器，一个用例跑好几秒，整个测试套件慢到没人愿意在本地跑。换成假定时器之后，几百个用例几秒钟跑完，体验天差地别。记得测完用 useRealTimers 还原，不然会影响后面的用例。

单元测试的价值在于保护关键行为：优先覆盖工具函数、业务规则和错误转换，组件测试聚焦用户可见的行为而非内部实现。别追求表面覆盖率，写能给重构带来信心的用例，这才是真正有价值的测试。
