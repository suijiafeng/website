Jest + Vue 单元测试：公共逻辑没有测试兜底，改 A 就会坏 B

2018-06-02
Vue构建与模块化

回归问题最让人难受的一点，是你改的功能本身没错，真正炸掉的却是另一个你根本没点开的页面。公共纯逻辑一旦没有测试兜着，这种"改 A 坏 B"的事故就只能靠运气避开。

这次出问题的就是一个所有人都觉得很安全的工具函数 formatMoney。为了给营销页加千分位，顺手把里面那行"分转元"的除法也"优化"了一下。活动页自测没问题，真正出事的是订单列表——它用的也是同一个函数，方向改反之后，所有金额都一起大了一百倍。

我改的是 A（活动页的千分位），坏的是 B（订单页的金额）。这就是最经典的回归：改动本身在自己的场景里是对的，它波及到的其他调用方，没有任何东西替我盯着。code review 没看出来——diff 里只有几行"看起来更简洁"的改动；我自己也不可能把全站几十个用到 formatMoney 的页面都点一遍。

大家很快达成一个共识：不是所有代码都要测，但那些一旦错了就会出大事、又容易被悄悄改坏的公共纯逻辑，必须有测试兜着。如果 formatMoney 当时有哪怕三行单测，我那下"顺手优化"在本地就会跑红，根本走不到线上。

这之后的两周，把单测在项目里铺开。下面就按这个过程往下讲：工具怎么选、先测什么、踩了哪些坑。

工具链：为什么是 Jest

先说选型。眼下 Vue 项目做单测，社区主流是 jest + @vue/test-utils（官方测试工具库，现在还是 beta 版本号，但已经很能打）+ vue-jest（让 Jest 认识 .vue 文件）+ babel-jest。我们是 vue-cli 2.x 的 webpack 模板项目，没有现成的测试预设，这套是手动装手动配的。

对比更早的 karma + mocha 那套要起真实浏览器跑用例，Jest 自带 jsdom 模拟 DOM 环境、自带断言和 mock、还能一条命令算覆盖率，配置成本低太多，跑起来也快——这是大家最近集体转向 Jest 的原因。

配置里有两处是 Vue 项目必须处理的，不配用例根本跑不起来。一是路径别名：项目代码里到处是 @/utils/format 这种 webpack 别名，Jest 不认识 webpack 配置，得用 moduleNameMapper 再声明一遍；二是样式等非 JS 资源，import 进来会让 Jest 报错，也用它映射成空模块：

这两行 moduleNameMapper 是我配环境时卡得最久的地方——报错信息只说找不到模块，完全不提示是别名没映射。写在这里，后来者少查一小时。

从出问题的函数开始：工具函数最适合先测

铺测试的第一步，没有碰任何组件，而是直接给出问题的 formatMoney 补测试。

测试：

这类测试简单、稳定、价值高。项目里金额、日期、权限判断、参数处理、请求错误转换、复杂表单校验，都比纯展示组件更值得先测。很多人补测试的第一反应是"组件这么多，测到什么时候"，其实根本不必一开始覆盖所有组件——按价值优先级来，先保护稳定、关键、容易被悄悄改坏的逻辑。我的事故就是最好的反面教材：坏的不是组件，是一个二十行的工具函数。

写工具函数测试我很快养成一个习惯：边界值一定要补全，正常值反而次要。真正会出 bug 的几乎都在边界上：

像 1.005.toFixed(2) 在 JS 里因为浮点表示实际得到 '1.00' 而不是 '1.01'，这种坑只有把边界写进用例里才会被逼着面对。我现在写工具函数，常常先把刁钻用例列出来再回头改实现，相当于拿测试当需求文档用。

补完这组用例，把五月那次错误的"优化"重新敲了一遍——npm test，红了一片。这片红要是早两周存在，那通客服电话根本不会响。

补充说一句金额处理的题外话：formatMoney 这类函数本质是在处理浮点数精度问题，行业里更稳妥的做法是全程用整数分做运算，只在最后展示的一瞬间才转成元、拼上千分位分隔符，而不是像上面这版一样在中途就做除法。如果项目里金额计算涉及多次加减乘除（比如订单总价 = 单价 × 数量 - 优惠），提前转成浮点元来算，误差会一路累积、越滚越大；全程用分做整数运算，误差就没有生长的土壤。这条经验没有直接写进这次的测试里，但值得记一笔，作为后续重构 formatMoney 上游调用链的方向。

组件测试：测用户行为，不测内部实现

工具函数铺完一轮，第二周开始碰组件。这里我先立了一条最重要的原则：不要测组件内部变量叫啥，要测用户能看到什么。

如果以后组件内部从 data 改成 Vuex，只要用户行为不变，测试就不应该失败。测试保护的是行为契约，不是实现细节——实现细节本来就是重构时要随便动的东西，测试咬着它不放，重构就变成了先改代码再改一堆测试的双倍苦役。

这里用 shallowMount 而不是 mount 是有意的：shallowMount 把子组件都替换成占位的桩，只渲染当前组件本身。好处是测试不会因为某个深层子组件的改动连带挂掉，关注点集中，跑得也快。我的经验是大部分组件 shallowMount 就够，只有行为确实依赖真实子组件渲染（比如要点子组件里的按钮）时才上 mount。

断言 DOM 时也别图省事去读组件内部状态。这是我们定下的"测行为、不测实现"对照：

判断一个断言该不该写，我会问自己：用户能感知到这个东西吗？感知不到的内部细节，测了只会在重构时给自己添堵。

行为的另一半是组件对外的输出——自定义事件。子组件 $emit 出去的东西是它和父组件的契约，很值得测，@vue/test-utils 的 emitted() 正是干这个的：

props 进、事件出，把这两头测住，一个组件的对外契约就基本锁死了，内部爱怎么重构怎么重构。

propsData 传入的 props 本身也值得单独测一遍类型校验和默认值这类容易被忽视的边界。Vue 组件里给 props 声明 type、required、default，开发环境下类型不对会在控制台报警告，但警告不会中断渲染，稍不留神就漏看。写一条用例专门验证"不传某个 prop 时用的是默认值"，能在重构时防止有人不小心删掉默认值声明：

这类用例数量不用多，但覆盖到组件对外暴露的每一个"默认行为"，能省下不少后续排查"为什么这个字段突然变了"的时间。

异步更新要等 nextTick：偶发失败比没测更糟

组件测试铺开后，我们遇到了第一批"时好时坏"的用例——本地跑十次过九次，装了 Jenkins 跑 CI 之后时不时红一次。追查下来，根因几乎都是同一个：Vue 的 DOM 更新是异步的，触发事件后马上断言，断言跑在了 DOM 更新之前。

接口请求还要多等一层 Promise：

flushPromises 不是 Jest 自带的，得装 flush-promises 这个小包，作用是把当前所有挂起的微任务（Promise 回调）跑完。一个组件如果是"请求回来 → 改 data → DOM 更新"这条链，往往要同时等 Promise 和 nextTick：

时好时坏的用例比没测还糟，因为它会让团队慢慢不信任测试——红了第一反应不是"我改坏了什么"而是"又抽风了，重跑一下"，最后干脆在 CI 里跳过。所以异步测试我宁可多写一两行 await，也绝不靠 setTimeout 去"赌"它更新完了。等待点写清楚，用例才配叫确定性的。

接口一定要 mock 掉，这点也得强调。单测里真去打后端，慢、不稳定、还可能污染数据，跟单测"快而确定"的初衷完全相反。Jest 的 jest.fn().mockResolvedValue(...) / mockRejectedValue(...) 就够覆盖成功和失败两条路径。另外记得在 beforeEach 里 jest.clearAllMocks()，别让上一个用例的调用记录漏进下一个用例——我们就出过一次断言 toHaveBeenCalledTimes(1) 莫名失败，查半天是前一个用例的调用没清。

统一错误处理是项目质量的基础，也是我第二个重点铺测试的地方——它和 formatMoney 一样，卡在所有请求的必经之路上，一旦错了影响面极大。

写测试的时候我们还顺带争论了一个设计问题：401 要不要在这里转成"跳登录"。讨论下来决定不放——normalizeError 只负责"把杂乱的 error 归一成统一结构"，跳转是上层拦截器的事。一个函数职责越单一，测试越好写，这是写测试反过来推动你把代码拆干净的地方。很多时候一段逻辑"测起来特别别扭"，不是测试的问题，是这段代码本身职责太杂。

不要滥用快照

铺组件测试时，有同事发现了快照测试这个"捷径"：

一行顶几十行断言，看起来血赚。但大组件快照很快变成一大坨 HTML，失败时很难判断是正常变化还是问题。

快照最大的隐患是"无脑 update"。失败了，开发图省事直接 jest -u 把快照刷新一遍，于是测试永远是绿的，但它早就不保护任何东西了——这跟没测一样，还更骗人。我们项目里就出现过一个几百行的组件快照，改一行样式 diff 出一大片，没人会逐行看那串 HTML 到底是该变还是不该变，最后大家条件反射地 -u。发现这个苗头之后我把那个快照删了，换成了几条明确的文本和状态断言。

所以我对快照的态度是：只给那种"输出本来就该一字不差固定下来"的小东西用，比如一个图标组件、一段格式化后的提示文案。大部分时候，明确断言文本、按钮状态、事件触发更好。

mock 时间和定时器

还有一类很常见但容易写得很别扭的测试：依赖时间的逻辑。防抖、倒计时、轮询。真用 setTimeout 等，测试就会慢得让人想砸键盘。Jest 提供了假定时器，可以"手动快进时间"：

jest.advanceTimersByTime 把时间"拨"过去，瞬间完成原本要等 300ms 的事。最初测倒计时组件时用的是真定时器，一个用例跑好几秒，整个测试套件慢到没人愿意在本地跑。换成假定时器之后，几百个用例几秒钟跑完，体验天差地别。记得测完用 useRealTimers 还原，不然会影响后面的用例。

假定时器还有一个容易被忽略的 API：jest.runAllTimers()，作用是把当前所有排队的定时器（不管延迟多久）一口气全部执行完。这个方法要小心用在递归定时器上——如果一个 setInterval 或者递归的 setTimeout 永远不停，runAllTimers 会陷入死循环把测试挂死。轮询、心跳这类没有天然终止条件的定时器逻辑，更适合用 advanceTimersByTime 按需推进几步，而不是图省事上 runAllTimers。

覆盖率：看，但别追

Jest 一句 --coverage 就能吐出覆盖率报告，老板看到那个百分比很容易上头，想定个"覆盖率必须 80%"的指标。我劝住了。

覆盖率数字高不代表安全——给纯展示组件刷一堆"渲染不报错"的用例，数字很好看，什么都没保护。我们的用法是反过来：拿覆盖率报告去找该测而没测的地方，比如 utils/ 目录下哪个函数还是 0%，那才是欠的债。指标只定了一条软的：utils/ 和 api/ 目录下的纯函数新增必须带用例，靠 code review 盯，不靠数字一刀切。

formatMoney 后来又被改过一次

事故过去半个多月，又有同事动了 formatMoney——这次是给负数金额加括号展示。提交之前本地跑了测试，红了两条：那次改动把字符串入参的场景弄坏了。改好、跑绿、再提交，全程没有惊动任何人，也没有再打过一次客服电话。

**单元测试的价值不在覆盖率数字，而在于下一次有人"顺手优化"公共逻辑时，有东西替所有调用方尖叫。**优先覆盖工具函数、业务规则和错误转换，组件测试聚焦用户可见的行为而非内部实现，把异步等待点写清楚，管住快照式的偷懒，这些加起来才是"改 A 不会坏 B"的真正保障。
