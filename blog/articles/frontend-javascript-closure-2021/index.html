闭包为什么既好用又容易出坑：它不是高深概念，而是作用域结果

2021-05-07
前端基础

闭包在前端基础里一直很有代表性。

不少人第一次接触它，会觉得这是一个特别抽象的概念，仿佛只有面试或者高阶技巧里才会出现。实际上，只要你在 JavaScript 里写过函数嵌套、事件回调、工厂函数，基本就已经用到过闭包。

真正需要理解的不是“闭包定义背诵版”，而是它为什么会出现，以及它会带来什么后果。我自己刚工作那会儿也背过“闭包就是能访问外部函数作用域的函数”这种话，背得滚瓜烂熟，可一到 debug 真实代码就照样懵。后来发现，把它和作用域绑在一起看，反而清楚得多。

闭包和作用域是分不开的

JavaScript 函数在定义时，会记住自己所处的词法作用域。这里的关键词是“定义时”，不是“调用时”。很多人栽跟头，就是因为下意识以为函数是在被调用的地方去找变量的——其实不是，它认的是自己出生的地方。

这意味着即使外层函数已经执行完，内层函数仍然可能访问外层作用域里的变量。

按常理说，createCounter 一执行完，它的栈帧、局部变量 count 早该被回收了。但因为返回的那个函数还引用着 count，引擎就不能释放它，只能把这块作用域单独留着。你可以在 Chrome DevTools 的 Sources 面板里打个断点验证——在内层函数停下时展开 Scope，会看到一个 Closure (createCounter) 的分组，count 就明明白白挂在里面。我第一次看到这个面板的时候才算真正“信”了闭包不是玄学，它在运行时是有具体形态的。

顺带说一句，闭包抓的是变量本身，不是变量当时的值。这点后面循环那一节会反复咬人，先记住。

它为什么会这么好用

闭包最直观的价值，是可以把数据和操作绑在一起，并且隐藏内部状态。

刚才那个计数器例子里，外部代码无法直接改 count，只能通过返回的函数操作它。这种模式在下面这些场景里都很常见：

  • 封装私有变量
  • 生成带参数的处理函数
  • 事件回调里保留上下文
  • 函数式组合

我在项目里用得最顺手的一类，是给某个状态加一层“只能这么改”的约束。比如做过一个简单的防重复提交，用闭包把一个 locked 标志关起来，外部根本碰不到它：

called 这个变量谁也改不了，只有 once 内部那段逻辑能动它。这种“私有”不是靠约定（比如下划线开头的变量名靠自觉），而是从语言层面就拿不到，比注释靠谱多了。在没有 #private 字段的年代，这几乎是封装私有状态的唯一干净写法。

所以闭包并不是“特殊技巧”，很多时候它只是函数能力自然延伸出来的结果。

闭包会保留状态，所以也会延长变量生命周期

这是它好用的地方，也是需要注意的地方。

因为只要内部函数还可访问，外层作用域中的某些变量就可能继续存在。

如果这里面保存了很大的对象、DOM 引用或者已经不再需要的数据，又一直没有释放，就可能造成不必要的内存占用。

当然，现代 JavaScript 引擎已经比早年聪明很多，不需要一提闭包就紧张。但如果一个闭包长期持有大块数据，还是值得留意。

排查这类问题有个经验：不用的引用主动置 null，组件卸载时把监听器、定时器都清掉。该让引擎回收的，别用闭包把它们攥在手里。

看到闭包，我现在会先问三件事

闭包的学习重点不在于能不能手写复杂面试题，而在于看到一层层函数返回和回调嵌套时，能不能答出三个问题：哪些变量被继续引用了、这些变量什么时候会变、多个调用方是不是在共享同一份状态。这三件事一清楚，闭包就不神秘了。

前端里很多“记住上下文”的能力都靠它——请求封装把 baseURL 和默认 headers 关进去、表单校验器让每个字段记住自己的规则、列表项点击回调各自携带 id，底层都是“函数创建时把需要的上下文一起带走”。因为 UI 交互天然就是“动作稍后发生、但仍记得当时环境”的过程，闭包才在前端这么常见。

真正会咬人的不是闭包本身，而是状态被悄悄共享：多个回调引用同一个可变变量、工具函数内部偷偷累计状态、两个看似独立的处理函数其实依赖同一块外部数据。短期能跑，长期很难预测。所以我现在看到闭包，会额外留意那个外部变量会不会持续变化、是不是多方共享——是的话就得判断这到底是不是设计本意。理解闭包最实用的地方，就是能提前闻到这种隐式耦合的味道。
