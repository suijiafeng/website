前端组件库设计：复用不是把所有参数都暴露出去

2023-05-12
前端基础组件与状态构建与模块化

组件库最容易走偏的地方，是把“可复用”理解成“什么都能改”。

一个 Button 暴露几十个 props：颜色、圆角、字体、阴影、内边距、hover 样式、图标位置。看起来很灵活，实际是把设计系统的约束全交给业务页面。每个页面都能调一点，最后全站按钮长得都不一样。

好的组件库不是无限自由，而是把常见场景做简单，把不该发生的变化挡在外面。

先区分基础组件和业务组件

基础组件解决通用交互：

  • Button
  • Input
  • Select
  • Modal
  • Tabs
  • Table

业务组件解决业务语义：

  • UserPicker
  • OrderStatusTag
  • PermissionTree
  • PriceInput
  • AuditTimeline

这两类组件不要混在一起设计。

基础组件应该稳定、抽象、少依赖业务。业务组件可以理解业务规则、接口和权限。

我见过有人把“选择用户”的接口逻辑塞进通用 Select，结果 Select 变得越来越重，所有页面都受影响。更好的方式是通用 Select 只负责选择交互，UserPicker 在外层组合它。

props 要表达意图

组件 API 不要只暴露样式细节。

variant 和 size 是设计系统认可的选项。业务开发不需要关心具体颜色和间距。

当然，组件也要允许少量扩展，比如 className 或 style。但扩展口应该是逃生通道，不是常规用法。

默认值要覆盖大多数场景

一个组件如果每次使用都要传很多 props，说明默认值没设计好。

如果这些配置在项目里 80% 都一样，就应该变成默认值，或者封装一个业务层 Modal。

组件库的目标是减少重复决策。常见场景应该开箱即用，少数特殊场景再配置。

组合优于巨型组件

很多组件会越写越大。

样式扩展要有边界

组件库要支持业务布局，但不能让业务随意改内部结构。

我一般会开放：

  • className：挂在根节点
  • style：少量布局调整
  • slots / render props：替换局部内容
  • token：主题和状态变量

不鼓励业务通过深层选择器改内部 DOM：

内部结构一改，业务样式就坏。

如果业务经常需要改某个内部区域，说明组件应该提供 slot，而不是让业务硬覆盖。

文档要写反例

组件文档不要只写 API 表。

更有价值的是：

  • 什么时候用
  • 什么时候不用
  • 常见组合
  • 错误用法
  • 和相似组件的区别

比如 Button 文档里应该说明：普通跳转用 Link，不要用 Button；危险操作用 danger variant；图标按钮必须提供 aria-label。

组件库维护的不是代码本身，而是团队共识。文档就是共识的载体。

我的组件设计清单

设计组件时，我会问：

  • 它是基础组件还是业务组件
  • props 是否表达语义，而不是暴露样式细节
  • 默认值是否覆盖主流场景
  • 是否可以通过组合拆小
  • 扩展口是否稳定
  • 是否避免业务依赖内部 DOM
  • 文档是否说明适用场景和反例

复用不是把所有可能性都塞进一个组件，而是找到稳定的变化轴。组件越基础，越要克制；组件越业务，越要贴近真实场景。
