RAG 与向量检索入门：文档里明明有答案，AI 为什么还答错

2025-06-25
AI构建与模块化

我们内部有一个给运营同事用的文档问答工具，背后接的是各业务线的操作手册和 FAQ。上周有人问它"预售订单能不能改收货地址"，它答了个"可以，在订单详情页修改"。

但手册里白纸黑字写着：预售订单在尾款支付前不允许修改地址。

文档里明明有答案，AI 却答错了。

第一反应通常是"模型不行"，要么怪它幻觉，要么想着换个更大的模型。但我把那次请求的日志翻出来一看，问题根本不在生成这一层：发给模型的检索结果里，压根没有那段"预售订单地址修改"的规则。模型拿到的是三段讲"普通订单改地址"的内容，它其实答得很忠实——忠实于错误的材料。

这就是做 RAG 最容易被忽略的一点：召回不准，生成必错。模型没有义务、也没有能力去回答一个上下文里不存在的问题，它只会拿手头最像的材料硬答。而且错得毫无破绽，语气笃定、格式工整，不去核对原文根本发现不了。

所以这篇想把检索这条链路从头到尾捋一遍：为什么不能直接把文档全塞进 prompt、文本怎么切块、向量检索到底在算什么、以及怎么用土办法评估检索质量。生成侧的评估我三月份写过一篇，这里只盯检索环节。

为什么不直接把文档全塞进 prompt

最朴素的想法是：既然模型答错是因为没看到那段文档，那把所有文档都给它不就行了？

先算账。我们那批操作手册加 FAQ 大概三百多份，粗算下来接近两百万 token。就算现在主流模型的上下文窗口到了 128K 甚至更长，也塞不下。

退一步，就算某天窗口真的能塞下，成本也扛不住。每次问答都把两百万 token 送进去，按当前的 API 价格，一次提问的成本就够买杯咖啡了。运营一天问几百次，一个月下来这个功能的账单会直接被财务打回来。

成本之外还有效果问题。上下文越长，模型对中间部分内容的注意力越弱，这个"lost in the middle"的现象我在六月初写上下文管理那篇里展开过，这里不重复。结论是：长上下文不是免费的，塞得越多，关键信息被稀释得越狠。

所以 RAG（Retrieval-Augmented Generation）的思路其实很直白：不要把所有文档给模型，而是先根据用户的问题把最相关的几段找出来，只把这几段和问题一起发过去。

整条链路拆开是四步：文档切块、向量化入库、检索、生成。前三步都属于检索层，也是这篇的主角。生成那一步反而是最省心的——检索对了，prompt 里让模型"只依据给定材料回答、材料里没有就说没有"，大部分时候它都能做好。

切块：看起来最不起眼，实际影响最大

文档不能整篇入库，得先切成一块一块的片段（chunk），检索的粒度就是这个片段。切块策略听起来是个体力活，实际上它对最终效果的影响，比我预想的大得多。

最开始我用的是最省事的固定长度切块：每 500 字符切一刀。跑起来之后发现两类典型的坏案例。

一类是把一张规则表格从中间切开。前半块有表头没内容，后半块有内容没表头，两块单独看都不知所云，向量化之后的语义自然也是糊的。

另一类是把"前提条件"和"操作步骤"切到了两个块里。检索命中了步骤那块，模型照着答，把前提条件整个丢了——预售订单那个错答，根源就是这个。手册里那一节先写"尾款支付前不允许修改"，隔了四百多字才写普通订单的修改步骤，一刀下去，规则和步骤各在一块，检索只捞回了后者。

后来换成按标题切块。手册本身是 Markdown，按 ## 和 ### 的层级切，每个小节天然是一个语义完整的单元。效果立竿见影，因为写文档的人已经替你做过一次语义分组了，切块只需要尊重这个分组。

一是二次切分时加了 64 token 的重叠（overlap）。相邻两块共享一小段内容，避免关键句子恰好卡在切点上被腰斩。重叠不是越大越好，太大会让库里充满高度相似的块，检索时 top-k 被同一段内容的不同副本占满，反而挤掉了别的相关内容。

二是把小节标题拼回每个子块的开头。这样哪怕一个子块只包含"步骤 3 到步骤 5"，它也带着"预售订单地址修改"这个语义标签，检索时能被正确召回。更进一步的话，可以把文档标题、所属业务线也一起拼进去，块的"自我介绍"越完整，被正确召回的机会越大。

块的大小也是个取舍。块太小，单块信息不完整，模型拿到手还是答不全；块太大，一次召回五块就把上下文撑得很满，噪声比例又上去了。我们试下来 300 到 512 token 是个比较舒服的区间，但这个数字和文档本身的写法强相关，别人的经验值直接抄过来未必合适。

切块的目标不是均匀，是让每一块单独拿出来都能被读懂。固定长度、按标题、加重叠，这三个手段不互斥，我们现在的组合就是"按标题为主、超长小节二次切分加重叠"。

embedding 与相似度：向量检索到底在算什么

切好的块要能被"按语义找到"，靠的是 embedding。

直观理解：embedding 模型把一段文本变成一个高维向量（常见的是 1024 或 1536 维），语义越接近的文本，向量之间的距离越近。"修改收货地址"和"变更配送信息"这两句话没有一个词相同，但它们的向量会靠得很近——这就是向量检索比关键词检索强的地方，它认的是意思，不是字面。

检索时把用户的问题也过一遍同一个 embedding 模型，拿问题向量去库里找距离最近的若干个块向量，通常用余弦相似度来度量。这里有个容易踩的坑：入库和查询必须用同一个 embedding 模型，中途换了模型，整个库要全量重算，不同模型产出的向量空间互相之间没有可比性。

还有一个不那么直观的点：问题和答案在语义上是不对称的。"预售订单能不能改地址"是一个问句，而它要匹配的目标块是一段陈述性的规则条文，两者的"长相"本来就不一样。不少 embedding 模型为此专门区分了 query 和 document 两种编码模式，入库时按 document 编、查询时按 query 编，模型在训练时就学过怎么把"问题"和"能回答它的段落"拉近。用的时候留意一下模型文档里有没有这个约定，编码模式用反了，检索质量会莫名其妙地差一截，而且这种错不会报任何异常。

存储和查询我们没有引入新组件，直接用了 pgvector。业务库本来就是 PostgreSQL，加个扩展就能建向量列和索引，对我们这种几万块规模的内部工具完全够用。

不到百万级向量的场景，先用 pgvector 这类"顺手的选择"，别急着为选型开会。专门的向量数据库解决的是规模和运维问题，不是效果问题，效果的大头在切块和检索策略上。

表里那个 biz_line 字段是后来加的。不同业务线的手册里有大量长得很像的规则（比如自营和 POP 店铺的售后政策），不加过滤时经常互相串台。元数据过滤是最便宜的召回提升手段：能用结构化条件先缩小范围的，不要全指望向量相似度。

top-k 取几、相似度阈值卡多少，都是要调的参数。k 太小容易漏，k 太大又把噪声块塞进上下文，回到"稀释关键信息"的老问题。我们目前是 k=5，再卡一个 0.35 的相似度下限——低于下限说明库里可能根本没有相关内容，这时候与其让模型硬答，不如直接回复"文档里没有找到相关内容"，把问题记下来补文档。

还有一件容易被忘掉的事：文档是会改的。手册更新了，对应的块要重新切、重新算 embedding，不然库里躺着的是旧规则。我们在文档发布流程里挂了个钩子，按 doc_id 删旧块、插新块，每块存一个内容 hash，没变的块跳过重算，省一点 embedding 的调用费。

向量检索的短板：它认语义，不认"字面"

用了一阵之后发现，向量检索也有很典型的失效场景：精确匹配。

运营问"ERR_20431 是什么错误"，向量检索的表现很差。因为 embedding 模型眼里，"ERR_20431"和"ERR_20437"几乎是同一个东西——它们语义上都是"一个错误码"，向量距离近得没法区分。同理还有 SKU 编号、活动 ID、内部系统的专有名词缩写。

这类查询恰恰是关键词检索的主场：一个倒排索引，字面命中，又快又准。三十年前的检索技术在这件事上依然打赢最新的 embedding 模型。

所以现在比较务实的做法是混合检索（hybrid search）：关键词和向量各查一路，再把两路结果合并。合并的经典办法是 RRF（Reciprocal Rank Fusion），不比较两路各自的分数——它们量纲不同没法直接比——只看每个块在各自结果里的排名：

RRF 的好处是简单到不需要调参就能工作，k=60 这个常数用默认值就行。一个块如果同时被两路召回，分数自然叠加排到前面；只被一路召回的也不会被埋没。

关键词那一路在 PostgreSQL 里用 tsvector 全文检索就能做，中文分词麻烦一点，我们用了 zhparser。两路合一路之后，错误码类的查询命中率肉眼可见地上来了，而"换个说法问同一件事"的查询也没有退化。

向量检索和关键词检索不是替代关系，是互补关系，单押任何一路都会在另一类查询上吃亏。

代价当然也有：两路检索意味着两次查询，延迟叠加。我们把两路做成了并发，总耗时取决于慢的那一路，目前整条检索链路在 200ms 上下，对一个问答场景完全可以接受。真要抠延迟，embedding 那一次模型调用才是大头，可以对高频问题的向量做一层缓存。

多轮追问：拿去检索的不一定是用户原话

还有一类失效场景，等到上线后看真实日志才暴露出来：多轮追问。

运营第一句问"自营店铺的运费险怎么退"，答对了；接着追问一句"那 POP 店铺呢"。如果直接拿"那 POP 店铺呢"这五个字去检索，关键词和向量两路都会挂——这句话脱离上文根本没有语义，召回的块五花八门，模型只能瞎答。

解法是在检索之前加一步查询改写：把当前追问和最近几轮对话一起丢给模型，让它改写成一个独立完整的问题，再拿改写结果去检索。

这一步会多一次模型调用，我们用了个小模型来做，延迟和成本都可以忽略。判断要不要改写也有个偷懒办法：问题很短、或者包含"那""这个""它"这类指代词的才走改写，独立成句的问题直接检索。

这个问题给我的提醒是，检索的输入本身也是需要设计的，用户原话不等于最好的查询。往深了走还有 HyDE（让模型先假想一段答案、拿假想答案去检索）这类玩法，我们暂时没上，改写这一步已经把多轮场景的大部分坑填掉了。

召回的块怎么交给模型：拼接和出处

检索层捞回了正确的块，最后一步是把它们和问题拼成 prompt 发给模型。这一步看着琐碎，有两个做法对最终体验影响很大。

第一是拼接顺序。前面说过模型对上下文中间位置的注意力最弱，所以我们把相似度最高的块放在材料区的开头，次相关的靠后，而不是随手按数据库返回顺序拼。块与块之间用明确的分隔符和编号隔开，避免两段不相干的规则被模型读成一段。

第二是强制出处。每个块入库时都带着文档名和小节标题，拼 prompt 时把这些元数据一起给模型，并要求回答末尾列出依据了哪几个编号的材料：

出处这个设计一开始是为了方便我们排查，上线后发现运营比我们更依赖它：答案旁边挂着"来源：售后手册 / 预售订单规则"，点开就能看原文，拿不准的答案自己核对一遍再执行。对内部工具来说，"答案可核对"比"答案更流畅"值钱得多——它把 AI 的输出从"信不信由你"变成了"给你指路"。

反过来，如果模型的回答里出现了材料之外的内容，出处标注也会露馅（它标不出编号，或者胡标）。我们在评估脚本里顺手加了一条检查：回答里标注的材料编号必须真实存在且相似度达标，算是给生成层加了一道便宜的护栏。

评估检索质量的土办法

检索层最大的问题是：它错了没有报错。生成层答得再流畅，你不去核对就不知道底下的召回是错的。所以一定要有办法量化检索本身的质量，而且不用等什么完备的评估平台，土办法就很管用。

我们的做法是攒一个"标准问题集"。从运营真实问过的问题里挑了 60 条，每条人工标注它的答案在哪份文档的哪个小节。标注这件事没法偷懒，我和另一位同事分头标完再互查了一遍，花了一个下午——这一个下午后来证明是整个项目性价比最高的投入。

这个指标一般叫 recall@k。我们最早的固定长度切块版本，recall@5 只有 61%；换按标题切块之后到 78%；加上混合检索到了 89%。每次改动检索策略，跑一遍脚本，几分钟出结果。

没有这个数字之前，所有优化都是玄学；有了这个数字之后，切块策略、top-k、阈值的每次调整都有据可依。有一次我信心满满地把块调小，觉得粒度细了召回该更准，结果 recall@5 掉了 6 个点——单块信息不完整，相似度反而算不准。没有脚本，这种"感觉是优化实际是退化"的改动就直接上线了。

比指标本身更有价值的是那个 misses 列表。没召回的案例逐个看，基本能归成三类。

第一类，文档里确实没写。这不是检索的锅，把问题转给写手册的同事补文档就行。问答工具顺带成了文档缺口的探测器，这是意外收获。

第二类，切块把语义切碎了。回去调切块策略，这类在换成按标题切之后已经很少了。

第三类，问法和文档措辞差太远。运营说"黑号"，文档里写的是"风控受限账户"，embedding 拉不近这个距离。短期的补法是在入库时给块附一段"这块能回答什么问题"的改写；长期看，查询改写（让模型先把用户问题改写成文档腔再检索）和 rerank 模型都是社区里验证过的方向，我们还没做，先把 89% 稳住再说。

recall 之外，偶尔也要看一眼另一面：召回的五块里有几块是真相关的。recall@5 是 100% 但五块里四块是噪声，和五块全中，对生成质量是两回事。这个不用天天盯，每次大改之后抽十条案例把召回的块人肉过一遍，心里就有数了。

顺带一提，评估问题集要持续从线上真实问题里补充。上线前攒的 60 条，和运营实际会问的分布总有偏差，每个月从"用户点了没帮助"的反馈里捞几条加进去，这个问题集才会越来越接近真实。

评估脚本还有个附带的好处：它是回归测试。切块逻辑重构、embedding 模型升级、分词器换版本，跑一遍就知道有没有把之前修好的案例弄坏。检索链路的改动没有类型检查也没有单测能兜住，这 60 条问题就是它的测试集。

检索层修好之后

回到开头那个预售订单的问题。修完切块（"前提条件"和"操作步骤"不再被切开）、加上混合检索之后，同样的问题再问一遍，召回的第一块就是手册里那段"尾款支付前不允许修改地址"，模型的回答也就对了。

生成层什么都没动，一行 prompt 都没改。

recall@5 从 61% 走到 89% 的两次跳变，对应的改动是切块和混合检索，加上多轮改写填掉的追问场景——没有一项和模型有关。

这大概就是做这个工具两个月下来最大的体会：大家讨论 AI 应用时，注意力天然会被模型吸走，但一个文档问答系统的效果上限，往往在文档切块那一刀就定下来了。下次再遇到"文档里有答案但 AI 答错"，先别急着换模型，把那次请求实际召回了什么打出来看看，多数时候答案就在日志里。
