前端构建报错排查：别一看到 webpack 就重装 node_modules

2019-12-20
构建与模块化前端基础

前端项目最让人头疼的报错之一，是构建报错。

页面代码还没跑起来，命令行先红一片。很多人第一反应是删 node_modules、删 lockfile、重新安装。这个办法有时能解决，但也可能掩盖真正原因。我带过几个新人，他们排构建错的第一反应几乎都是 rm -rf node_modules && npm install，跑十几分钟，结果错误一模一样，因为根本不是依赖的问题。

我自己被构建报错坑得最惨的一次，是上线前半小时本地 build 突然挂了，命令行刷出几百行红字。当时心一横删了 node_modules 重装，等了二十分钟，错误还在。后来冷静下来翻到最上面那条，发现是同事改了一个组件的文件名大小写，跟我没关系。那次之后我就养成了习惯：构建报错先别动手，先读，按顺序排查。

构建问题最好按顺序排查。下面这套顺序是我这两年攒下来的，基本能覆盖八成以上的日常报错。

先看第一条有效错误

为什么强调“第一条有效错误”？因为 webpack 的报错经常是雪崩式的。一个模块解析失败，依赖它的模块全都跟着报，最后命令行底部那条往往是“X modules failed”这种汇总信息，看着吓人，其实没什么信息量。真正有用的是最上面那条带具体路径或具体语法的错误。

我的习惯是把命令行往上滚到这次构建的起点，找到第一个红色的 ERROR in 或 Module not found。如果终端刷得太快看不全，可以把输出重定向到文件再慢慢看：

然后用编辑器打开 build.log，搜 ERROR。比在终端里反复滚轮舒服多了。注意要加 2>&1，否则 stderr 的内容不会进文件，而 webpack 很多报错恰恰走的是 stderr。

还有一类容易看走眼的：warning 和 error 混在一起。DeprecationWarning、peer dependency 之类的黄字看着也烦，但它们不会让构建失败。判断标准很简单——构建退出码非 0 才是真挂了，光有 warning 但退出码是 0，那就是能跑的，别把警告当报错去修。

我见过一个很典型的乌龙：有人本地 npm run dev 一直好好的，但 npm run build 报错，于是怀疑是 webpack 生产配置有问题，折腾半天。最后发现是 build 命令里多了个 --mode production，触发了 NODE_ENV=production，而项目里有段代码在生产模式下才会走到，那段代码本身就有 bug。所以 dev 正常、build 报错，很多时候不是构建工具的事，是两种模式跑的是不同分支的代码。

另外提醒一句：vue-cli-service 这种命令是装在 node_modules/.bin 里的，npm scripts 会自动把这个目录加到 PATH，所以 scripts 里直接写命令名就行。但如果你想在终端里手动跑，得用 npx vue-cli-service serve，直接敲 vue-cli-service 多半会提示 command not found——这个坑新人几乎都踩过。

依赖版本

构建报错经常来自依赖版本不匹配。

比如 webpack、webpack-cli、babel-loader、vue-loader、sass-loader 之间都有版本关系。

先看最近是否升级过依赖：

如果 lockfile 变了，也要一起看。

团队项目里不要随意删除 lockfile。它是保证大家依赖一致的重要文件。

我吃过一次大亏：本地装依赖时没用 npm ci，而是 npm install，npm 顺手把 package-lock.json 里某个间接依赖的版本往上抬了一个小版本，我没注意就提交了。结果那个小版本里 node-sass 的预编译二进制和我们 CI 的 Node 版本对不上，CI 直接挂。从那以后我们团队定了规矩：CI 和需要复现问题时一律用 npm ci，它会严格按 lockfile 安装，lockfile 和 package.json 对不上时直接报错而不是悄悄改。

判断版本是不是元凶，有个快办法——看依赖之间的兼容矩阵。比如 sass-loader 版本和 webpack、node-sass 的搭配是有讲究的：

我的经验是，老项目（webpack 4 时代）不要手贱去升 loader 的大版本。这些 loader 的 major 版本经常跟着 webpack major 走，单独升一个，配置项可能整个变了。真要升，连 webpack 一起升，并且预留时间。

判断到底是哪个 loader 出的问题，看报错里的文件后缀和 Module build failed 紧跟的那行模块路径就行。.scss 报错找 sass 链，.vue 报错找 vue-loader，.js 报错找 babel。别一上来就怀疑业务代码，很多时候业务代码一个字没动，是 loader 这条流水线断了。

环境变量

构建时读不到环境变量，也会报错：

确认 .env 文件是否存在，变量前缀是否正确，CI 是否注入了对应值。

vue-cli 这套有个硬规矩：只有 VUE_APP_ 前缀的变量才会被注入到客户端代码里，NODE_ENV 和 BASE_URL 是特例。我见过有人在 .env 里写了 API_BASE=xxx，然后代码里读 process.env.API_BASE，构建出来永远是 undefined，排查半天才想起前缀的事。create-react-app 同理，前缀是 REACT_APP_。

环境变量出问题，读到的往往是 undefined，然后被拼进 URL 变成 http://undefined/api/...，请求直接挂。这种时候别盯着请求层看，往上倒一步看变量从哪来的。我习惯在构建时打一行：

确认值是不是真的注进来了。CI 上尤其要查，因为本地的 .env.local 通常不提交，CI 环境根本没有这个文件，得靠 CI 平台的环境变量配置或者构建脚本显式注入。本地好好的、CI 起来 undefined，十有八九是这个原因。

还有个容易忽略的点：.env 文件改了之后，dev server 不会热更新这些变量，必须重启 npm run dev。我有好几次改了 .env 死活不生效，最后发现是没重启服务，白白怀疑了半天配置。

前端环境变量进入浏览器后不是秘密，不要把敏感 token 放进去。任何 VUE_APP_ 的东西最终都会明文出现在打包后的 JS 里，F12 一搜就有。密钥、内部地址这类一律走后端代理，前端只拿一个对外的接口地址。

不要盲目重装

可以重装依赖，但要知道为什么。

合理场景：

  • node_modules 损坏
  • 切换分支后依赖变化
  • lockfile 更新
  • Node 版本切换

不合理场景：

  • 路径写错
  • loader 配错
  • 语法插件缺失
  • 环境变量缺失

这些问题重装也解决不了。

重装真要做的时候，也讲究方法。删干净一点：

node_modules/.cache 这个目录我专门拎出来说，因为 babel-loader、cache-loader、hard-source 都会往里写缓存，有时候代码改了但构建结果还是旧的，或者出现一些“不可能”的报错，清掉这个缓存就好了。这种诡异问题我一般先清缓存，再考虑动 node_modules。

Node 版本这个隐形变量

很多构建报错的真凶其实是 Node 版本。node-sass 是重灾区——它依赖预编译的二进制，跟 Node 的 ABI 强绑定，换了 Node 大版本，原来装好的 node-sass 就用不了，报：

这时候 npm rebuild node-sass 通常能解决，让它针对当前 Node 重新编译。团队里 Node 版本不统一是个长期隐患，A 用 12、B 用 10，装出来的 node-sass 二进制对不上，互相 pull 完就构建失败。我们后来在根目录放了个 .nvmrc 写死版本，CI 也锁 Node 版本，这类问题少了很多。

配合 nvm use 就能保证大家跑在同一个 Node 上。这一步看着不起眼，但省下的扯皮时间是实打实的。

构建报错要按顺序看：先找第一条有效错误，再确认命令、依赖版本、loader、路径、环境变量。

webpack 报错不等于 webpack 有问题。很多时候它只是把路径、语法、依赖、配置问题暴露出来。排查越有顺序，越少靠玄学重装。

我现在遇到构建报错的固定动作是：读第一条有效错误 → 看是不是自己刚改的东西（git diff / git stash 试一下）→ 判断是路径、语法、loader 还是环境问题 → 实在定位不到再清缓存、查 Node 版本，最后才考虑重装。这套顺序走下来，绝大多数报错十分钟内能定位。把“重装”从第一反应挪到最后一步，是我这几年排构建问题最大的进步。
