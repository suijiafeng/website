用了几年 Next.js 之后，我对它的态度反而更克制了

2024-09-08
React组件与状态

我第一次用 Next.js，是冲着“它把 React 缺的那块补齐了”去的。路由、SSR、打包、图片、部署，一个框架全给你。那阵子我有点上头，新项目不管什么类型，先 create-next-app 再说。

真正改变我判断的不是文档，是后面几个踩过坑的项目。现在我对它的态度比几年前保守得多，但不是因为它不好，而是因为我终于搞清楚它适合解决哪类问题。

我给一个纯中后台硬上了 Next

那是个公司内部的配置平台，特别典型的中后台：登录进去就是表格、表单、权限、审批流。没有 SEO 需求，用户都是内部同事，首屏慢两百毫秒没有人会投诉。

我当时还是习惯性地上了 Next，理由很冠冕堂皇——“以后说不定要做对外页面”。结果整个项目我几乎每个页面顶上都写了 'use client'：表格要交互，表单要状态，弹窗要事件。服务端组件那套能力基本没用上，我反而要时不时绕开 App Router 的数据获取和缓存约定，因为它们是为“服务端先算好”设计的，而我的数据全靠登录后调接口。

干到一半我才肯承认：这个项目用 Vite + React Router 会更轻。构建快、心智简单、部署就是一份静态资源丢到 Nginx 后面。Next 给我的那些服务端能力，在一个登录后才可见、数据全靠接口的后台里，几乎都成了负担。

所以现在接到新项目，我会先问一句很朴素的话：有没有“未登录的陌生人需要尽快看到内容”这种场景？ 纯后台、纯内部工具、纯登录后应用，往往没有。没有的话，我会很认真地考虑不上 Next。

直到一个内容站，我才重新看到它的价值

后来做一个对外的产品官网加博客，情况完全反过来。这种站点要被搜索引擎读到，首屏要快，图片一堆，内容又不是每秒都在变。

这正好是 Next 的主场。页面用静态生成，配一个按小时重新验证的策略，用户访问起来接近纯静态页，运营改了内容也不用每次手动全量构建：

next/image 顺手解决了我以前在移动端最头疼的事——列表缩略图直接用原图、几 MB 往下载。这些能力单独看都不稀奇，但凑在一个框架里、还都是默认可用，确实省了我很多自己搭轮子的时间。

那次之后我才想明白：Next 的价值不在“它能 SSR”，而在它把内容型站点的一堆琐碎问题打了个包。后台用不上这个包，内容站用得上。

'use client' 这条线，我画错过

中后台那个项目还教了我另一件事：客户端边界不能随手画。

我一开始图省事，在很靠上的布局组件上写了 'use client'，想着“反正下面都要交互”。后果是它底下整棵子树都被拖进了客户端世界，bundle 明显变大，hydration 也变慢。

后来我改成默认写服务端组件，只在真正需要状态、事件、浏览器 API 的那个小组件上才加 'use client'，把这条线尽量往下压：

这个调整看着小，但它决定了多少代码会被打进浏览器。我现在 review 别人代码，看到顶层布局挂 'use client' 都会多问一句：真的整棵树都需要吗？

后来我才把背后的机制搞明白：'use client' 不是“这个组件在客户端跑”，而是“从这里开始，往下的整棵导入树都进客户端 bundle”。它是一道模块边界，不是组件边界。一旦某个文件标了 'use client'，它 import 的所有东西——包括那个你以为只是拿来格式化日期的工具函数、那个体积巨大的 markdown 解析库——都会被打包器顺着依赖图拽进浏览器。我当初顶层挂一行，等于把整个 node_modules 里能被引用到的部分都判了“客户端”。

真正反直觉的是：服务端组件可以作为 children 或 props 传进客户端组件，而不会被“传染”成客户端组件。原因是父子之间传的是已经渲染好的 React 元素（一棵序列化后的树），不是组件函数本身。所以下面这种写法，<Comments> 仍然在服务端渲染、它的依赖也不会进 bundle，哪怕它被塞进了一个 'use client' 的壳里：

记住这条“插槽下沉”的写法，比单纯把 'use client' 往下压更有用——很多看起来必须客户端化的布局，其实只要把需要交互的那层做成壳、把内容当 children 传进去就行。我现在画边界的顺序是：先假设全是服务端，遇到 onClick/useState/useEffect/浏览器 API 才停下来，把那一个组件切成客户端，并尽量让它接收 children 而不是自己去 import 内容。

缓存是我栽得最惨的地方

如果说 Next 有什么让我半夜爬起来查问题，那一定是缓存。

有一次运营反馈说，后台改了配置、保存也提示成功了，但前台页面上的数字怎么刷新都不变。我本地怎么都复现不出来——因为开发环境的缓存行为和生产不一样。最后定位到是 Server Action 改完数据后，对应页面的数据没有重新验证，旧的还被缓存着。

但这件事真正可怕的地方在于，它“看起来一切正常”：接口成功、没报错、本地也正常，只有线上的真实用户看到旧数据。从那以后我养成一个习惯，把页面按数据新鲜度分层来想——营销页、文档尽量长缓存；列表页分钟级重新验证；订单、账户、权限这类直接走动态、不缓存；后台改完即时生效的，一定要想清楚谁来触发重新验证。不为了“全部实时”放弃所有缓存，也不为了性能把强一致的数据缓存太久。

那次事故之后我专门去啃了一遍 App Router 的缓存模型，发现它根本不是“一个缓存”，而是四层叠在一起，每层失效方式都不一样，难怪当时一头雾水：

  • Request Memoization：同一次渲染里对同一个 fetch 自动去重，请求结束就没了，只活在单次请求内。
  • Data Cache：fetch 结果的持久缓存，跨请求、跨用户，受 revalidate 和 revalidatePath/Tag 控制——我那次栽的就是这层，数据存住了没人去敲它失效。
  • Full Route Cache：构建/首次访问时把静态路由的 HTML 和 RSC Payload 整个存下来，Data Cache 一失效它才跟着重建。
  • Router Cache：浏览器内存里的客户端缓存，软导航时直接复用，连服务器都不打。它有自己的过期时间，跟服务端那几层完全独立。

理解这个分层，最直接的收益是知道该敲哪一层。我后来把按路径失效换成了按 tag 失效，因为一份数据往往散落在好几个页面上，挨个写 revalidatePath 既容易漏又耦合路由结构。给 fetch 打 tag、改完按 tag 一次性失效，干净得多：

还有个把我坑过第二次的细节：开发环境(next dev)默认几乎不缓存，而 next start 跑的是带满四层缓存的生产行为。所以“本地复现不出来”几乎是缓存类问题的标配。我现在排查这类问题的第一反应不是开 dev，而是 next build && next start 在本地起生产模式，再配合 fetch 的 cache/next 选项逐个确认——能在本地稳定复现，问题就解了一大半。最坑的一个变种是：某个 fetch 不小心被判定成了静态（比如没带任何动态信号），整张路由被 Full Route Cache 固化，无论怎么 revalidateTag 数据都不动，因为根本没走到那层取数逻辑。这种时候得用 export const dynamic = 'force-dynamic' 或在请求里读 cookies()/headers() 把路由“拽”成动态，才肯重新算。

一个慢接口拖垮整页的事故

内容站上线后还遇到过一次更隐蔽的：商品详情页偶发性地“白屏好几秒才一次性出来”。监控看接口都正常，单个都不慢，但页面就是卡在那。

扒下来才发现，是我在一个 async 服务端组件里串行 await 了三个接口——商品、库存、推荐。RSC 的渲染规则是：组件里的 await 没 resolve，这棵子树就产不出 HTML，而我把三个请求写成了一条直线，最慢的那个（推荐，偶尔抖到 2 秒）把整页的首字节都顶住了。本质上是把“服务端渲染”写成了“服务端阻塞”。

我现在怎么判断要不要上

几年下来，我对 Next 的判断其实就收敛成几个问题，按顺序问：这个项目有没有陌生人首屏或 SEO 的诉求？内容是不是大体可缓存、不需要秒级实时？团队愿不愿意花成本去理解它的运行时和缓存模型？前两个有一个为“是”，它就值得上；都为“否”，尤其是纯后台，我会更倾向 Vite 那套轻量组合。

Next 不是更高级的 React，它是把一部分复杂度从你手里搬到了框架约定里。搬对了很省心，搬错了，你会花大量时间和它的约定较劲。我现在比几年前克制，但该上的时候也不犹豫——区别只是，我终于会先问“这个项目到底要不要服务端”，而不是默认它需要。
