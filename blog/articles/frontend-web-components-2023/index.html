Web Components 入门：跨框架复用组件的一种思路

2023-10-09
前端基础组件与状态

前端组件化已经很常见。

Vue 有 Vue 组件，React 有 React 组件，组件能帮我们复用 UI 和交互逻辑。

但问题也很明显：Vue 组件通常不能直接拿到 React 项目里用，React 组件也不能直接给原生页面使用。

Web Components 提供了另一种思路：使用浏览器原生能力封装组件。

它的重点不是取代框架，而是把一部分组件能力下沉到浏览器标准里。对于跨技术栈项目、嵌入式组件、第三方小挂件，这个思路很有价值。

Web Components 是什么

Web Components 不是一个单独的库，而是一组浏览器标准。

它主要包含几部分：

  • Custom Elements：自定义 HTML 标签
  • Shadow DOM：封装组件内部结构和样式
  • HTML Template：定义可复用模板

有了这些能力，就可以写出类似这样的标签：

浏览器可以识别这个自定义元素，并执行对应的组件逻辑。

自定义元素命名必须包含短横线，比如 user-card、app-player。这是标准要求，目的是避免和未来原生 HTML 标签冲突。

我刚开始踩过一个低级坑：图省事把组件命名成 usercard，结果 customElements.define 直接抛 Failed to execute 'define' on 'CustomElementRegistry'，盯着代码看了半天才反应过来是命名规则的问题。还有一次更隐蔽，组件脚本是异步加载的，HTML 里标签先出现、脚本后注册，浏览器对未识别的自定义元素会当成普通 HTMLUnknownElement 渲染，等脚本注册后才"升级"成真正的组件。如果你在升级前就去读它的属性或调方法，会拿到一片空白。后来我习惯用 customElements.whenDefined('user-card').then(...) 来等组件就绪，比盲目 setTimeout 靠谱得多。

生命周期和属性变化

Custom Elements 提供了一组生命周期方法：

  • attributeChangedCallback：监听的属性变化时调用
  • adoptedCallback：元素被移动到新文档时调用

Shadow DOM 的作用

普通组件的样式很容易互相影响。

例如页面里有一个 .title，组件内部也有一个 .title，如果选择器写得不够小心，就可能互相覆盖。

Shadow DOM 可以把组件内部 DOM 和样式封装起来，减少样式污染。

这段样式只影响当前组件内部。

Shadow DOM 还能避免外部脚本随意依赖组件内部结构。外部看到的是一个自定义元素，内部 DOM 可以调整，组件对外 API 主要通过属性、事件和方法暴露。

但 Shadow DOM 也不是没有成本。它会让全局 CSS 不容易穿透进去，调试样式时要多一层结构；某些表单、弹窗、主题系统也要额外设计样式入口。

还有个真实踩过的坑：Shadow DOM 里的字体不会自动继承外面的 @font-face，但 font-family 这个属性本身是继承的，所以经常出现"字体声明在外面、组件里却 fallback 成默认字体"的诡异现象。解决办法是把字体声明放到全局（@font-face 写在 document 级别），组件内部只引用 font-family。同理，全局 reset、Tailwind 这类原子化 CSS 也进不去 Shadow DOM，组件内部该写的基础样式还得自己再写一份，这是用 Shadow DOM 要付的固定成本。

不要让外部直接操作组件内部 DOM。属性输入、事件输出，是更稳定的边界。

事件命名也要谨慎。select 这种名字简单，但在复杂页面里可能和其他组件语义混在一起。对外组件可以考虑带命名空间，比如 user-card-select。这看起来啰嗦一点，但日志、埋点和跨团队接入时更容易定位来源。

composed: true 这个配置我吃过亏。当时做一个嵌在 Shadow DOM 里的下拉组件，派发的事件忘了加 composed，结果事件在 shadow 边界就被拦住，外面的页面怎么都监听不到，控制台又没任何报错，排查起来特别折磨。规律记住就行：只要事件需要被 Shadow DOM 外部的代码听到，composed 就必须是 true，否则它只能在影子树内部冒泡。

属性和事件的边界还有个取舍点：属性（attribute）只能传字符串，传对象或数组就得 JSON.stringify 再 JSON.parse，又丑又容易出错。如果接入方本来就是用 JS 拿到元素引用的，我更倾向于用 property（在类上定义 getter/setter）来传复杂数据，把 attribute 留给那些写在 HTML 里的简单标量值：

它适合什么场景

Web Components 比较适合：

  • 跨 Vue、React、原生页面复用的组件
  • 公司内部多技术栈共用组件
  • 小组件、小挂件、嵌入式功能
  • 不希望强依赖某个框架的 UI 能力

如果组件库要被多个不同框架项目使用，Web Components 会有一定优势。

例如一个公司同时有 Vue2 老项目、React 新项目、静态运营页，如果要共享一个客服浮窗、播放器、支付按钮、埋点组件，Web Components 就比为每个框架写一套更有吸引力。

表单组件不是只包一层输入框

如果 Web Components 要做输入框、日期选择、上传这类表单组件，要提前考虑它怎么和原生表单或框架表单库协作。

普通自定义元素默认不会像 <input> 一样参与表单提交，也不会天然支持校验状态。现代浏览器逐步补齐了 form-associated custom elements 和 ElementInternals，可以让自定义元素更像原生表单控件：

这个方向很有价值，但也意味着组件要处理更多细节：value、disabled、required、校验提示、表单 reset。只做展示组件很轻松，一旦做表单控件，就不能只把 DOM 包起来。落地前还要确认目标浏览器范围，别把它当成和普通 input 一样没有兼容成本的能力。

我之前给几个不同部门的页面提供过一个客服浮窗，最早是分别给 Vue 项目和老的 jQuery 页面各维护一套，光是同步一个文案改动就要改两处、发两次。后来统一成一个 Web Component，对外只暴露一个标签和几个属性，接入文档从两页缩到了几行，维护心智一下子轻了很多。这种"一次构建、到处嵌入"的体验，是它最打动我的地方。

不过对外分发时有几个工程细节要提前想清楚。一是样式隔离要做足，否则你的 widget 进了别人页面，可能被对方的全局 CSS 影响，也可能反过来污染对方——Shadow DOM 在这里几乎是必选项。二是要防重复注册，同一个脚本被引两次，第二次 customElements.define 会直接抛错，我一般会先判断一下：

它不一定替代框架组件

Web Components 是浏览器标准，但不代表它在所有场景都比框架组件好。

Vue 和 React 仍然在状态管理、模板语法、工程生态、开发体验上有优势。

很多业务项目里，直接使用框架组件会更高效。

更合理的理解是：Web Components 适合做跨框架组件，而不是替代所有 Vue、React 组件。

还有一些边界需要提前评估：

  • 服务端渲染和 hydration 支持是否满足项目要求
  • 表单组件是否需要和框架表单库深度集成
  • 主题系统如何穿透 Shadow DOM
  • 事件命名和属性类型如何规范
  • 构建产物是否要兼容旧浏览器

如果只是一个单一 React 后台系统，把所有按钮、表格、表单都改成 Web Components，收益可能不如成本高。

近几年也能看到 Declarative Shadow DOM 这类能力被更多讨论，它让服务端输出 Shadow DOM 成为可能，对 SSR 友好一些。但这不等于 Web Components 的 SSR 问题就全部消失了。跨框架组件真正落地时，还要看目标浏览器、构建产物、样式加载、hydration 方式和组件升级时机。

Web Components 的价值在于让组件脱离具体框架，直接运行在浏览器标准之上。

当你需要跨技术栈复用组件时，它值得考虑；如果只是单一 Vue 或 React 项目，优先使用本框架组件通常更简单。

我更愿意把 Web Components 看成一种“边界组件”方案：当组件要跨项目、跨框架、跨页面分发时，它很适合；当组件只服务当前框架应用时，框架组件通常更高效。
