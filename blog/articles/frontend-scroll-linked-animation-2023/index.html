滚动驱动动画入门：让页面动画跟着滚动走

2023-08-24
前端基础CSS

很多网页都会做滚动相关动画。

比如页面滚动时进度条变长、标题吸顶、图片视差移动、内容逐步出现。

过去这类效果通常依赖 JavaScript 监听滚动位置，再手动修改元素样式。

滚动动画本身不新，但它很容易从“增强体验”变成“制造负担”。所以讨论这类效果时，我更关心两个问题：动画是否真的服务内容，以及实现方式是否会给性能和维护带来过多成本。

  • 滚动事件触发频繁
  • 需要节流或 requestAnimationFrame
  • 需要计算滚动距离和页面高度
  • 多个动画会让逻辑变复杂

我自己最早踩的坑是 scrollHeight - innerHeight 这个分母。它不是常量。页面里只要有图片懒加载、字体回流、折叠面板展开，这个值就会变，进度条就会突然往回跳一下。后来我学乖了，要么在内容稳定后重新测一次，要么干脆监听 ResizeObserver，在文档高度变化时刷新缓存的 maxScroll，而不是每帧重新读 DOM。

还有一个容易忽略的点：移动端 Safari 的地址栏会随滚动伸缩，innerHeight 跟着变。如果进度条计算依赖它，滚到底部时进度可能卡在 0.97 而不是 1，看着很别扭。我最后给结果加了个 Math.min(progress, 1) 兜底，虽然不优雅，但比用户看到“永远差一点”的进度条强。

如果只是让动画进度跟随滚动，CSS 原生能力会更适合。

传统 JavaScript 写法不是不能用，而是需要写得很谨慎。至少要避免在 scroll 回调里频繁读写布局属性，尤其是同时读取 offsetHeight、getBoundingClientRect，再写 style。读写交错会增加浏览器重新计算布局的压力。

如果必须用 JavaScript，通常会用 requestAnimationFrame 合并更新：

这不能让逻辑自动变快，但至少能避免滚动事件触发多少次就更新多少次。scroll 在快速滑动时一秒能触发上百次，而屏幕一秒最多刷新 60 次（高刷屏 120 次），rAF 的作用就是把多余的回调合并掉，让计算节奏对齐屏幕刷新。

另外提一句监听器本身。我习惯给 scroll 加上 { passive: true }：

这是承诺回调里不会调用 preventDefault，浏览器就不用等 JS 执行完再决定要不要滚动，滚动手感会明显跟手。很多人不知道这个标记，结果在低端安卓机上滚动一卡一卡的，查半天以为是动画太重，其实是监听器把滚动主线程拖住了。

还有一种场景不需要每一帧都跟随滚动，只关心“滚动结束后做点事”，比如同步当前章节、保存阅读位置、懒更新目录高亮。这类逻辑不要硬塞进 scroll 高频回调里。浏览器逐步支持 scrollend 事件后，这类需求可以写得更直接；不支持时再用定时器 debounce 降级。

我以前把目录高亮写在 scroll 里，每滚一下就遍历所有标题算位置。文章长一点 CPU 就飙。后来改成滚动中只做轻量状态，滚动结束后再修正高亮，体验反而更稳定。

什么是滚动驱动动画

滚动驱动动画的核心思想是：动画进度不再由时间决定，而是由滚动位置决定。

普通动画是“3 秒内从 0 到 100%”。

滚动动画是“页面从顶部滚到底部时，从 0 到 100%”。

这样用户滚得快，动画就快；用户停下，动画也停下。

这里要区分两类效果：

  • 跟随整个页面滚动进度，比如阅读进度条
  • 跟随某个元素进入视口的进度，比如图片进入时淡入、卡片移动

前者更像页面级时间线，后者更像视口级时间线。实现时如果把两者混在一起，动画就容易出现触发位置不准确、移动距离难调的问题。

在 CSS 滚动时间线里，这两类分别对应 scroll() 和 view()。scroll() 描述的是某个滚动容器的整体进度，view() 描述的是某个元素相对视口进出的进度。我第一次做视差时图省事，全用 scroll() 去算单个图片的位移，结果发现图片在长页面里几乎不动——因为它的进度被整个文档的滚动距离稀释了。换成 view() 之后，进度才回到“这张图自己进出视口”的尺度上，调参一下子就直观了。一句话记忆：要看整页用 scroll()，要看某个元素自己用 view()。

适合哪些场景

滚动驱动动画适合：

  • 页面阅读进度条
  • 图片视差效果
  • 内容进入视口时变化
  • 横向滚动展示
  • 长页面中的分段动画

这些效果的共同点是：动画和滚动位置强相关。

我会按需求强度选择实现方式：

  • 只需要进入视口后出现：优先 IntersectionObserver
  • 需要跟随页面整体进度：考虑 CSS 滚动时间线或简单滚动计算
  • 需要复杂分段、编排、多元素联动：考虑成熟动画库或明确的状态机

不要把所有滚动效果都写成全局 scroll 监听。页面里滚动相关逻辑一多，后期很难判断哪个监听器影响哪个元素。

不过也不要滥用 will-change：

它可以提示浏览器提前优化，但如果给大量元素都加上，反而会增加内存压力。只给确实会频繁动画的少量元素使用。

我现在的做法是动态加 will-change：动画开始前用 JS 加上，动画结束后去掉，而不是写死在 CSS 里常驻。常驻的 will-change 等于让浏览器一直为这些元素准备独立的合成层，几十上百个元素都这样，移动端内存很快就吃紧，反而更卡。

判断一个属性是否“便宜”，可以记个粗略的分级：transform 和 opacity 通常只走合成，最便宜；color、background 这类只重绘，中等；width、height、top、margin 会触发布局重排，最贵。滚动动画基本只该碰第一档。验证的时候打开 DevTools 的 Rendering 面板，勾上 Paint flashing，如果滚动时大片区域闪绿，说明有不该重绘的地方在动，顺着找一般能揪出某个改了 top 或 height 的样式。

调试时我还会录一段 Performance，看 Main 线程有没有长任务。滚动动画如果每一帧都跑复杂 JS，哪怕只改 transform，也可能因为脚本计算太重而掉帧。不要只盯 CSS 属性，滚动链路里脚本、布局、绘制、合成任何一环超预算，用户看到的都是卡。

一个实用标准是：先在低端手机或浏览器性能降速模式下看。如果只在自己的高性能电脑上顺滑，很可能只是机器替你掩盖了问题。

使用时要保持克制

滚动动画很容易做得过多。

如果一个页面里每滚动一点都有大量元素移动、旋转、缩放，用户会觉得累，性能也可能变差。

比较好的原则是：

  • 用在关键视觉反馈上
  • 动画幅度不要太夸张
  • 不要影响正文阅读
  • 保留无动画时的基本可用性

动画是增强体验，不应该成为阅读障碍。

兼容和降级

滚动驱动动画的 CSS 新能力在 2023 年已经可以进入现代浏览器的渐进增强方案，但仍然需要关注浏览器支持。实际项目里不要假设所有用户都能使用最新语法。

比较稳的策略是：

  • 内容默认可见，不依赖动画才出现
  • CSS 新特性只作为增强
  • 关键反馈提供 JavaScript 或静态降级
  • 不把核心操作藏在动画里

比如阅读进度条没有显示，用户仍然能正常阅读文章；卡片没有淡入动画，内容也应该直接可见。这样新能力即使不生效，也不会影响核心体验。

滚动驱动动画让 CSS 能直接表达“动画跟随滚动进度”这类关系。

它可以减少一部分滚动监听代码，让进度条、视差和页面动效更清晰。实际项目中仍然要关注浏览器支持，并为关键内容保留稳定的基础体验。

我现在做滚动动画时，会先判断它是“进入视口触发”还是“跟随滚动进度”。前者通常交给 IntersectionObserver，后者再考虑 CSS 滚动时间线或滚动计算。选对模型，比一开始就堆动画代码更重要。
