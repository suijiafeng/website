Vue + Webpack 代码分割：首屏 3.4MB 时，应该先拆哪里

2018-04-14
Vue构建与模块化性能与缓存

首屏 3.4MB 的 app.js，在办公室内网里可能只是“还好吧”，放到真实用户的 4G 网络上，就是实打实的十几秒白屏。性能问题最容易被拖着不管的原因，也恰恰在这里：开发环境和用户环境差得太远。

这类问题真要查，第一步不是先猜图片、猜接口、猜压缩参数，而是先把自己变成那个用户。网络降速、缓存关掉、重新打开页面之后，真正拖时间的大块头会自己浮出来。

把自己变成那个用户

我做的第一件事，是让自己的浏览器变得和投诉用户一样慢。Chrome DevTools 的 Network 面板里把 throttling 调到 Fast 3G，勾上 Disable cache，退出登录，重新打开系统。

白屏。圈转了二十二秒，登录页才出来。

我盯着 Network 里的瀑布图，凶手一眼就能锁定：一个叫 app.js 的文件，传输体积 3.4MB，未压缩前更夸张。它不加载完，页面上一个像素都渲染不出来。

用户只是想登录进来看个仪表盘，凭什么要先下 3.4MB 的 JS？我把这个文件的来路翻了一遍：里面塞满了 ECharts、富文本编辑器、xlsx 导出库，还有一堆压根没人访问的旧页面。单页应用最容易被忽略的问题，就是"什么都先打进来"——页面少的时候感觉不到，模块一多，首屏体积和初始化时间就这么一点点垒起来，直到有用户忍不住投诉。

能用，但不直观，而且不支持 webpackChunkName 这类 magic comment。webpack 2 之后官方就推荐统一用动态 import()，配合 babel-plugin-syntax-dynamic-import 让 Babel 认得这个语法（我们还在 Babel 6，这个插件必须装，否则直接报 parse error）。这次我把全项目的 require.ensure 一并替换掉，统一成 () => import()。

还有个细节差点被我忽略：给 chunk 起名不只是为了好看。不命名的话，webpack 默认生成 0.js、1.js 这种数字命名，将来线上有 chunk 加载失败，你在日志里看到"1.js 404"，根本不知道是哪个页面炸了。每个 chunk 配上有意义的名字，是给未来排查问题的自己留活路。

重型库和低频组件，该拆到自己的 chunk 里

路由拆完，树图上还有几块显眼的大色块：图表、富文本编辑器、xlsx 导出。它们的共同点是重、而且低频——不是每个页面都用。

但这招我当场就踩了个反例。改造上头的时候，我把一个表格页上"总是会展示"的图表也做成了点击后才加载，测试环境自己一用就后悔了：每次进页面都得手动等图表 loading 转一圈，体验比直接打进首屏还差。能拆出去的前提是"用户大概率不会用到它"，一个几乎必然出现的模块，拆分省下的体积抵不过那次额外的等待和闪烁。

判断一个重组件该不该懒加载，我的土办法是回树图上看它带进来多少 KB。像 ECharts 这种动辄几百 KB 的库，哪怕用得不算特别少也值得拆；几十 KB 的小组件，拆出去多一次请求反而不划算。体积和频率要一起看，不能只凭感觉。

ECharts 本身还有一层可挖：全量引入太重，可以只引用到的图表类型和组件：

按需引完再配合懒加载，图表这块从六百多 KB 掉到两百出头。

顺带统一一下体积口径，不然优化前后没法对话。webpack 输出的是未压缩体积，用户实际下载的是 Nginx gzip 之后的传输体积，两者能差三四倍。我们后来在群里汇报一律说清楚是哪个数：analyzer 树图上看 parsed size 定位问题，Network 面板看 transfer size 衡量用户体感。gzip 这层也检查了一遍——运维原来只对 html 开了压缩，.js 没配进 gzip_types，白白多传了不少，一行配置的事。

分析阶段我还顺手用了一次 Chrome DevTools 里的 Coverage 面板（快捷键唤出 Command Menu 敲 coverage 就能找到）。它录制页面加载和交互过程中，每个 JS/CSS 文件到底有多少字节被真正执行过，红色部分就是"下载了但没用上"的死代码。那次一录才发现，首屏加载的 app.js 里有将近一半标红——不少是从没被路由到过的旧页面代码，另一部分是引入了但业务里已经没人调用的工具函数。这个证据比树图更直观，直接把"这些页面该拆出去"的判断钉死了，也顺带扒出几个可以整个删掉的废弃组件。

公共依赖怎么分，webpack 4 的新玩法

我们这个项目年初刚咬牙从 webpack 3 升到了 4（二月刚发布，当时升级踩的坑够写另一篇）。webpack 3 时代拆公共包用的是 CommonsChunkPlugin，配置又绕又难懂；webpack 4 直接把它废了，换成 splitChunks：

把 node_modules 里的第三方库单独拆成 vendors，业务代码频繁改、库不常动，浏览器缓存就能长期吃住 vendors 这块。

这类配置我劝你别一开始就抄网上的"最佳配置"往里贴。splitChunks 有几个默认阈值得先知道，否则你会奇怪"为什么我引了个库它没被拆出来"：默认 minSize 是 30000（约 30KB），小于这个体积的模块不会被单独拆成 chunk；minChunks 默认是 1，被引用一次就进入分包判断。这些默认值多数场景够用，真要调也得基于树图分析有的放矢。

我们还多拆了一层：把 vue、vue-router、vuex 这几个几乎不会变的框架核心单独归到一个 framework 组，和其它第三方库分开：

理由是这几个包升级频率极低，业务里三天两头改的是别的依赖和自己的代码；框架单独一个 chunk，只要版本没变，用户浏览器可以一直吃着这块缓存，不会因为升级了某个业务用到的小库就连带把 Vue 本体也重新下载一遍。priority 要比默认的 vendors 组高，不然这几个包会先被 vendors 那条规则收走。

顺便说句公道话：如果没有打包器，你很难优雅地把应用切成多个按需加载的模块。webpack 在背后做的是找出依赖关系、生成独立 chunk、在运行时按需拉取——你写起来只是一行动态导入，真正复杂的事情全在它肚子里。

发版当晚，chunk 加载失败又是一个坑

改造完打包一看：首屏 JS 从 3.4MB 掉到 700KB 出头。Fast 3G 下登录到首屏可见的时间几乎砍半。我把对比截图贴进了群里。

当晚十点，测试在群里喊："线上有人点导出页直接白屏！"

我打开报错日志，一行 Loading chunk 7 failed。想了几分钟才明白过来：代码分割之后，页面运行时会多出资源加载这个环节，而发版正是它最脆弱的时刻——用户在旧版本页面停留着没刷新，我这边部署了新版本，带 hash 的 chunk 文件名全变了，旧文件已经被清掉。用户这时点一个还没加载过的懒加载页面，浏览器去请求那个已经不存在的旧 chunk，404，页面卡死。

预加载要克制，别跟首屏抢带宽

拆完之后有同事提议："既然拆开了，能不能空闲时偷偷把其它页面预取回来？这样点过去就是秒开。"

想法很自然，但要克制。浏览器本来就有 <link rel="prefetch"> 这个机制——空闲时低优先级地拉"将来可能用到"的资源；还有 <link rel="preload">，是高优先级、和当前资源并行抢着加载的，适合"马上就要用"的依赖。这两个方向完全相反，用反了后果挺严重：把次要页面标成 preload，等于跟首屏资源抢带宽，反而拖慢首屏。看 webpack 的 issue，社区已经在讨论用 magic comment 直接标注 prefetch，眼下还没发布，我用的是土办法——挑一两个确定会跳转的页面，手动往 head 里插 link，或者在鼠标悬停菜单项时提前触发那个 import()：

但全量预取我坚决没做。用户刚进首页，后台就偷偷拉几十个根本不会访问的页面 chunk，把本来就不宽裕的带宽占满——代码分割省下来的首屏资源，转头又被预取拿回去了。预加载这东西，宁可不做，也不要无脑全开。

别为了拆而拆

最后泼自己一盆冷水：chunk 不是越多越好。拆得太碎，请求数变多、资源管理复杂、公共依赖重复加载的判断也更难。最自然的拆分单位还是页面、重模块和低频功能，而不是把所有组件都切成单独 chunk。

我给自己列了几个判断问题，每次想拆的时候过一遍：

  • 这段代码是否影响首屏
  • 用户是否一定会用到它
  • 它是否依赖很重的第三方库
  • 拆出去以后是否会造成明显的等待
  • 同一业务链路是否会频繁连续访问

代码分割本质上是在"首屏速度"和"后续加载"之间做取舍。

三张工单最后都关掉了

四月初，运营在群里回了句："那个用户说现在打开挺快的。"三张关于首屏慢的工单，全部关闭。

webpack 的代码分割真正帮用户省下的，不是那 2.7MB 体积数字，而是第一次进入页面时不必要的等待。Vue 应用做大之后，按需加载不是"可选项"，是结构设计的一部分——越早铺好，后面的性能债越少。新项目立项第一天就该把路由懒加载铺上，不用等它长肥了再回头治。

比较务实的顺序是：先用 bundle analyzer 看清现状，再做路由级懒加载，然后拆重模块、按需引重型库，最后根据分析结果调 splitChunks。这样既能控制首屏体积，也不会把项目拆成难维护的碎片。
