Vue 项目里的代码分割：Webpack 真正帮你省下了什么

2018-04-14
Vue构建与模块化性能与缓存

单页应用最容易被忽略的一个问题，就是“什么都先打进来”。

页面少的时候感觉不到，模块一多，首屏体积和初始化时间就会慢慢拉高。用户明明只访问了首页，却被迫把后台设置页、表单向导、图表模块一起下载了。

这就是代码分割存在的理由。

我对这件事印象最深的一次，是接手一个做了一年多的后台项目。打开 Network 一看，首屏一个 app.js 干到 3.4MB，未压缩前更夸张。里面塞满了 ECharts、富文本编辑器、xlsx 导出库、一堆压根没人访问的旧页面。用户登录进来只想看个仪表盘，却要先把整个系统的代码下载一遍。后来光是把路由改成懒加载，首屏 JS 就掉到了 700KB 出头，登录到首屏可见的时间几乎砍半。那次之后我就养成习惯：项目一立项就先把路由懒加载这套铺好，不等它长肥了再回头治。

代码分割不是高级优化

很多人第一次接触 Webpack 的代码分割，会把它当成“后面再说的优化项”。可对 Vue 这种页面越来越多的单页应用来说，它其实很早就值得考虑。

因为只要页面结构明确、访问路径分层，自然就会想到：

  • 首页不该加载后台页代码
  • 列表页不该提前加载编辑器
  • 低频弹窗没必要跟首屏一起进来

代码分割的目标不是让构建结果看起来更复杂，而是让用户只下载当前阶段真正需要的代码。

Vue 路由懒加载就是最常见的切入点

在 Vue 项目里，代码分割最直接的入口通常就是路由级拆分。

这行代码带来的不只是“写法更现代”，而是明确告诉打包器：这部分代码可以等真正访问时再加载。

低频重模块也适合拆出去

除了路由，低频出现的重组件也适合按需加载。

例如图表、富文本编辑器、文件预览、地图组件，都可能让首屏包体积明显变大。

我踩过一个反例：当时图省事，把一个表格页上"总是会展示"的图表也做成了点击交互后才加载。结果用户每次进页面都得手动等图表 loading 转一圈，体验反而比直接打进首屏更差。后来我才想明白——能拆出去的前提是"用户大概率不会用到它"，如果一个模块在页面里几乎必然出现，拆分省下的体积根本抵不过那次额外的加载等待和闪烁。

判断一个重组件该不该懒加载，我的土办法是看打包分析里它带进来多少 KB。像 ECharts 这种动辄几百 KB 的库，哪怕用得不算特别少也值得拆；而几十 KB 的小组件，拆出去多一次请求反而不划算。体积和频率要一起看，不能只凭感觉。

Webpack 帮你做的，不只是拆文件

如果没有打包器，你很难优雅地把应用切成多个按需加载的模块。

Webpack 在这里做的是：

  • 找出依赖关系
  • 生成独立 chunk
  • 在运行时按需拉取

splitChunks 有几个默认阈值值得知道，否则你会奇怪"为什么我引了个库它没被拆出来"。默认 minSize 是 30000（约 30KB），小于这个体积的模块不会被单独拆成 chunk；minChunks 默认是 1，表示被引用一次就可能进入分包判断。这些默认值多数场景够用，真要调也是基于分析结果有的放矢，而不是抄一份网上的"最佳配置"贴进去。

处理加载失败

代码分割后，页面运行时会多一次资源加载。网络断开、部署期间资源更新、浏览器缓存不一致，都可能导致 chunk 加载失败。

chunk 加载失败这件事，刚上线懒加载的项目几乎一定会遇到，而且很容易被误判成"代码 bug"。最典型的场景是发版：用户在旧版本页面停留着没刷新，这时你部署了新版本，带 hash 的 chunk 文件名变了，旧的文件在 CDN 上已经被清掉。用户这时点一个还没加载过的懒加载页面，浏览器去请求那个已经不存在的旧 chunk，直接 404，页面卡死。

预加载要克制

Webpack 支持通过 magic comment 提示浏览器预取资源：

预取适合“用户很可能下一步会访问”的页面，不适合把所有懒加载资源都提前拉下来。否则代码分割省下来的首屏资源，很快又会被预取拿回去。

这里要分清 webpackPrefetch 和 webpackPreload 两个 magic comment，它们经常被搞混。prefetch 生成的是 <link rel="prefetch">，浏览器会在空闲时才去拉资源，优先级很低，适合"将来可能用到"的页面；preload 生成 <link rel="preload">，是和父 chunk 并行高优先级加载的，适合"当前这个 chunk 马上就要用到"的依赖。用反了后果挺严重——把次要页面标成 preload，等于跟首屏资源抢带宽，反而拖慢首屏。

我的经验是 prefetch 谨慎用、preload 几乎不用。Vue CLE 项目里 Vue CLI 默认会给所有异步路由自动加 prefetch，项目大了之后这反而成了负担：用户刚进首页，后台就在偷偷预取几十个根本不会访问的页面 chunk，把网络占满。所以我一般会在 vue.config.js 里把默认的全量 prefetch 关掉，只对极少数确定会跳转的页面手动加：

别为了拆而拆

代码分割当然有好处，但也不是 chunk 越多越好。

拆得太碎，可能带来：

  • 请求数变多
  • 资源管理复杂
  • 公共依赖重复加载判断更难

所以最自然的拆分单位通常还是页面、重模块和低频功能，而不是所有组件都切成一个单独 chunk。

可以按这几个问题判断是否值得拆：

  • 这段代码是否影响首屏
  • 用户是否一定会用到它
  • 它是否依赖很重的第三方库
  • 拆出去以后是否会造成明显的等待
  • 同一业务链路是否会频繁连续访问

代码分割本质上是在“首屏速度”和“后续加载”之间做取舍。

Webpack 的代码分割真正省下来的，不只是几百 KB 体积，而是用户第一次进入页面时不必要的等待。

Vue 应用做大之后，按需加载几乎不是“可选项”，而是结构设计的一部分。你越早理解这一点，后面的性能成本越低。

比较务实的顺序是：先做路由级懒加载，再拆重模块，最后根据构建分析结果调整公共包。这样既能控制首屏体积，也不会把项目拆成难维护的碎片。
