Lighthouse CI 与性能预算：让优化成果在 CI 里守得住

2022-09-24
前端基础性能与缓存构建与模块化

性能优化最让人沮丧的不是做的时候难，而是守的时候贵。六月我们给商家端的几个核心页面做过一轮优化：首页 LCP 从 4 秒出头压到 2.5 秒左右，主包体积砍了 30%。上周例行用 Lighthouse 跑了一遍，LCP 回到了 3.4 秒，主包体积基本涨回了优化前。三个月，二十几次业务迭代，每次 PR 单看都没问题——加一个营销组件、引一个日期库、放开一张更大的头图——没有任何一次改动"值得"被拦下来，但叠在一起，六月的成果就没了。

这件事的教训不是"同事不重视性能"。指望每个写业务的人在每次提交时心里都装着 LCP，这个要求本身就不成立，就像不能指望大家靠自觉保持代码风格一致——风格问题我们早就交给 lint 了。**性能同样需要一道机器把守的闸门：越线的提交直接挡在合并之前，而不是三个月后靠人手动测出来。**所以这两周我把 Lighthouse CI（LHCI）接进了 GitHub Actions，这里把配置思路和踩到的坑记一下。

先算一笔账：这道闸门本身的成本。每个 PR 多跑三分钟 CI、一份需要维护的阈值配置、偶尔的误报要人工确认。收益是六月那种规模的优化（前后投入了大约两人周）不再需要每季度重做一次。这笔账怎么算都是划算的，前提是把误报率压到大家不烦它的程度——后面会讲，这恰恰是配置里最花心思的部分。

LHCI 的基本形态

@lhci/cli 做的事情可以概括成三步：把你的构建产物起起来（或者指向一个已部署的地址），对指定 URL 跑若干次 Lighthouse，然后按你配置的断言判定通过还是失败。配置放在项目根的 lighthouserc.js：

url 列表怎么选也是个成本问题。每多测一个页面，CI 时长就按"运行次数乘页面数"往上走，全站几十个路由不可能都进闸门。我的取舍是只放两类页面：流量最大的（首页、商品列表）和结构上有代表性的（一个典型的表单页曾经想加进去，后来发现它的资源构成和列表页几乎一致，就撤了）。闸门测的是"代表性样本"，不是"全量覆盖"——公共依赖的回退在任何一个页面上都会现形，页面独有的问题则按业务权重决定值不值得占一个测试位。

我们的页面是纯静态产物加接口的中后台形态，staticDistDir 直接指向 dist 就行，LHCI 会起一个静态服务器。接口数据是个问题——CI 环境连不上真实后端，页面白拿一堆请求失败。我的处理是给构建加了一个 VITE_MOCK_FOR_LHCI 开关，CI 构建时让请求层返回一份固定的 mock 数据。测的数据必须是固定的，否则接口返回的商品列表今天 20 条明天 200 条，性能分数的波动就没法归因到代码上。

固定 mock 也有它自己的维护义务，这点提前想清楚了才没掉坑里。mock 的数据形状要跟着接口演进走：接口加了字段而 mock 没加，页面某个组件渲染出兜底状态，测出来的 LCP 可能反而"变好"——因为最重的那块内容根本没渲染。所以这份 mock 数据我没有另起炉灶，直接复用了单测里已经在维护的那套 fixture，接口变更时单测先红，mock 跟着修，闸门的数据自然保持新鲜。另外 mock 的量级要贴近真实：商品列表页真实用户看到的是 20 条带图的行，mock 也给 20 条带图的行，图片用固定的本地占位图，体积和真实缩略图相当。

顺带记一下另一种形态：如果项目不是纯静态产物而是要起一个 Node 服务（比如 SSR），配置里用 startServerCommand: 'npm run start' 替代 staticDistDir，LHCI 会先把服务拉起来、等 startServerReadyPattern 匹配到日志里的就绪标志再开测。我们暂时用不上，但内部有个 Nuxt 的项目以后要接的话就是这条路。

upload.target 先用了官方的临时公开存储，报告链接保留几天，够 PR 评审时点开看火焰图。之后如果要留长期趋势，再自建 LHCI Server，眼下没到那一步。

还有一个和我们产品形态强相关的配置决定：跑桌面模式。Lighthouse 默认按移动端模型测——模拟中端手机的 CPU 降速加慢速 4G——这对 C 端页面是合理的默认值，但我们是商家用的中后台，用户几乎全在办公室的台式机和宽带上，按手机模型测出来的 LCP 和真实使用场景完全对不上，阈值也没法定。LHCI 里通过 settings 切换：

preset: 'desktop' 换成桌面的屏幕尺寸、更温和的 CPU/网络节流模型。onlyCategories 把 SEO 和 PWA 类目直接关掉——内部系统不需要搜索引擎收录，测了也是噪音，还省时间。skipAudits 用来排除个别不适用的审计项，我们内网静态资源暂时走 HTTP/1.1，这一项年内没有改造计划，让它每次都黄着只会训练大家忽略黄色。配置的原则是让每一条输出都值得被看，不适用的检查宁可显式关掉，也不要留着当背景噪音。

登录态：中后台绕不开的一关

中后台还有个 C 端项目遇不到的拦路虎：几乎所有有价值的页面都在登录之后。LHCI 直接测只能测到登录页本身，那个页面快不快没人关心。官方给的方案是 puppeteerScript——在 Lighthouse 开测之前，先用 Puppeteer 把登录流程走完，种下会话：

配置里挂上 puppeteerScript: './lhci-login.js'，账号密码走 GitHub Actions 的 secrets 注入，专门建了一个只读权限的测试账号。这里有个一开始没想到的坑：登录后的 token 我们存在 localStorage 而不是 cookie 里，而 Lighthouse 某些模式下每次运行会清存储，导致第二次运行时页面被重定向回登录页，指标全部失真——表现是三次运行里总有一两次 LCP 离谱地小（登录页比业务页轻得多）。排查了一个下午，最后在 collect 配置里关掉存储重置才稳定下来。如果多次运行的离群值总是朝同一个方向偏，先怀疑测到的根本不是同一个页面。

assertions：分数线还是指标线

断言怎么配，我一开始想得很省事——categories:performance 不低于 0.85，一条搞定。试跑几天后把这条降级成了警告，原因是综合分数是个好仪表盘，但是个糟糕的闸门。分数是十来个指标加权算出来的，一次 PR 让 TBT 恶化了 300ms，可能因为 LCP 恰好快了一点而分数不动；反过来分数掉了 3 分，你也要翻报告才知道是谁的责任。闸门要的是"违反了哪条规矩"一目了然，所以主力断言应该压在具体指标上：

阈值怎么定也有讲究。我没有直接抄 Google 给 LCP 定的 2.5 秒"good"线，而是先让 LHCI 在当前代码上跑了一周，看清楚每个指标的基线和波动范围，然后把线画在"当前水平再留一点余量"的位置——LCP 现在稳定在 2.4 到 2.6 之间，线就画在 2.8。这条线的含义不是"我们的目标"，而是"不许比现在更差"。防回退和做优化是两件事，闸门只负责前者；等下一轮优化把水平抬上去，再把线跟着收紧。

审计项类的断言（unused-javascript 这些）我全设成 warn。它们提示的是优化机会，不是回归事故，用 error 挡人合并只会让大家学会无视 CI 的红色。

细心的话会发现断言列表里没有 TTI 和 Speed Index。不是漏了，是权衡过放弃的。TTI 是我试跑那一周里波动最大的指标，同一个 commit 三次运行能差出 20%，它的定义（最后一个长任务之后的安静窗口）决定了它对时序抖动极其敏感，拿它做 error 级断言纯粹是给自己制造假警报。Speed Index 衡量视觉内容的填充速度，中后台页面的首屏就是一个布局骨架加一张表格，LCP 已经把"主要内容何时可见"覆盖得差不多了，再加一条高度相关的线，除了多一个要维护的阈值没有额外收益。断言列表不是越全越好，每加一条线都要回答"它拦下的问题是不是别的线拦不下的"。

阈值也不必一刀切。首页和商品列表页是六月优化的重点、也是商家用得最多的两个页面，线可以收紧；剩下那些低频的设置页，先松一点，免得闸门刚上线就到处报警。LHCI 支持按 URL 模式覆写断言：

budgets.json：体积是最稳的那条线

时间类指标再怎么控制环境都有波动，但资源体积是完全确定的——构建产物多大就是多大，跑一百次都一样。所以体积预算是整套断言里信噪比最高的部分，六月那次"主包悄悄涨回去"的问题，靠它一条就能挡住。LHCI 支持直接挂 Lighthouse 的 budgets 格式：

配置里用 assert.budgetsFile: './budgets.json' 引进来。单位是 KB，按传输体积（压缩后）算。third-party 那条计数预算是我特意加的：埋点、客服 SDK、验证码，这类第三方脚本每一个接进来时都说"就几 KB"，但它们带来的主线程开销和体积不成比例，数量本身就值得设限。

体积预算还有个额外的好处：它失败时的报错信息谁都看得懂。"script 超出预算 47KB"比"TBT 从 380ms 涨到 460ms"更容易让提交者自己定位问题——多半是新引的那个依赖，rollup-plugin-visualizer 打开一看就清楚。

选型时我也考虑过更轻的路子：只做体积这一件事的话，size-limit 或者 bundlesize 这类工具接进 CI 更快，直接对着构建产物文件算体积，连浏览器都不用起。如果当初的问题只有"主包悄悄变大"，我可能就选它们了。最后还是选了 LHCI 全家桶，因为六月退化的不只是体积——LCP 的回退里有一部分来自一张没压缩的运营头图和一个同步加载的第三方脚本，这些是"页面怎么加载"层面的问题，只盯产物文件是看不见的。体积预算管住"发出去多少"，指标断言管住"用户等了多久"，两层各有各的盲区，我需要它们都在。不过 size-limit 有个 LHCI 给不了的能力：它能对单个入口文件分别设限，粒度比 Lighthouse 按资源类型汇总的预算细。以后如果要按路由 chunk 精细管控，可能会两个一起上，眼下先不叠加工具。

budgets.json 里其实还能写第三类预算——timings，直接对 FCP、TTI 这些时间指标设线。我没用它，因为它和 assertions 里的指标断言功能重叠，而 assertions 的报错输出和 warn/error 分级都更好用。一套约束写在两个地方，将来改阈值的人多半只改一处，宁可让 budgets.json 只管体积这一件它最擅长的事。

波动：假警报比没有警报更糟

真正决定这套东西能不能活下来的，是波动处理。Lighthouse 的时间类指标受 CI 机器负载影响很大，GitHub Actions 的 runner 性能又不保证一致。头几天试跑，同一个 commit 连跑两次，LCP 能差出 600ms，performance 分数能差 5 分。这种波动如果直接怼到断言上，大家一周之内就会学会"红了就 re-run"，闸门名存实亡。

三个手段把波动压到了可接受的范围。第一是 numberOfRuns: 3，LHCI 默认对数值型断言取多次运行的中位数，把偶发的离群值滤掉；断言上还可以按条指定 aggregationMethod，比如对特别关心的指标用 pessimistic 取最差值——我在 CLS 上用了它，布局抖动这种事，三次里出现一次也说明隐患真实存在，不该被中位数抹掉。我试过把运行次数加到 5，稳定性提升有限，CI 时长倒是实打实多了两分钟，3 次是我们的平衡点。第二是 Lighthouse 本身的模拟节流（simulated throttling）——它跑在固定的 CPU 和网络节流模型上，比不加节流直接测裸机稳定得多，这是默认行为，别手贱关掉。第三是前面说过的固定 mock 数据，把服务端的不确定性摘出去。

三管齐下之后，时间类指标的波动收敛到 5% 左右。所以我给阈值统一留了 10% 的余量：宁可放过一次 3% 的真实小回退，也不要每周两次假警报。小的回退会在下一次真回退时一起撞线，但被假警报磨掉的信任回不来。

还有一个观察记下来备用：波动和 CI 的并发编排有关。我们的 workflow 里原来 lint、单测、LHCI 三个 job 并行，试跑期有几次 LCP 异常偏高，翻 Actions 的日志发现那几次恰好是三个 job 被调度到同一时段挤在一起跑。把 LHCI 改成用 needs 排在单测之后串行执行，异常值明显少了。runner 是共享的虚拟机，Lighthouse 这种对 CPU 敏感的活，别让它和别的重活抢同一台机器的时间片。

跑了几天之后 QA 那边提了个合理的需求：能不能看到"这个 PR 相对 main 分支变好还是变坏"，而不只是"有没有越线"。这其实是 LHCI Server 的活——它存下每次运行的结果，给出分支间的对比和时间趋势图。自建需要一个小服务加一个数据库，成本不大，我排到了下个迭代。眼下的临时方案是把 main 分支每天定时跑一次的结果存成 artifact，人肉对比，糙但够用。

被拦下之后：给提交者的排查路径

闸门要能被接受，被拦的人得能自救，不能每次都来找我。所以配置合完我顺手在项目 README 里写了一段"红了怎么办"，核心是一条可以自己走完的排查路径。

第一步看 PR 的 check 详情，确认超的是哪条线。体积类的问题最直接：本地跑 npm run build:lhci 之后打开 visualizer 的产物图，新引入的依赖会非常显眼地占着一块。这次拦下 ECharts 那位同事就是自己走到这一步解决的——换成按需引入，体积回到线内。指标类的问题要多走一步，点开 LHCI 上传的报告链接，Lighthouse 报告里的 Opportunities 和 Diagnostics 两栏基本会把肇事者点出来：渲染阻塞的资源、超长的主线程任务、没有设尺寸的图片，都有具体的文件名和数字。

如果报告还看不出来，就本地复现：

collect 和 assert 是可以拆开跑的，本地改一版、跑一轮、看一次断言结果，比推到 CI 上等三分钟快得多。这条路径写下来之后，两周里没有人因为 LHCI 的红色来找过我，这比任何指标都更能说明闸门的运行成本可控。

顺带记一个体积预算的边界：它管得住构建产物，管不住运行时才加载的东西。六月那张没压缩的运营头图，其实不在 dist 里——它是运营在后台传的素材，URL 从接口下发。CI 里 mock 数据指向的是一张固定的测试图，所以线上素材再大，闸门也看不见。这个口子得用别的手段堵：素材上传的入口加了尺寸和体积校验，超限的图在上传时就压缩或者打回。CI 闸门守的是代码仓库这一侧的边界，从数据侧流进页面的开销，要在数据的入口设防。

推行：闸门不能从第一天就咬人

技术之外，怎么把这道闸门推进团队的日常，是我提前想好的部分。直接上 required check 等于某个周一早上所有人的 PR 突然开始被一个陌生工具拦截，哪怕拦得都对，第一印象也毁了。所以前两周所有断言全部跑 warn 级别——CI 照跑、结果照写进 PR，但不拦人。这两周的用处有三个：让波动问题在不伤人的情况下暴露出来（localStorage 那个坑就是这段时间修的）、让阈值在真实的 PR 流量上校准、也让大家先习惯"PR 里多了一块性能报告"这件事本身。周会上演示过一次怎么读 check 详情之后，才把核心指标切到 error。

阈值本身的修改也定了个简单规矩：lighthouserc.js 和 budgets.json 加进了 CODEOWNERS，改这两个文件的 PR 需要我或者资深前端批。不是不信任大家，而是放松阈值必须是一个显式的、有人签字的决定，不能混在业务改动里顺手完成——不然闸门的下场和代码注释一样：谁被挡了谁改线，半年后线就退到毫无约束力的位置。反过来，放松请求本身也有价值：如果一个正当的业务需求确实需要 60KB 的新依赖，那就该正大光明地改预算并留下记录，闸门的目的是让性能开销变得可见、可讨论，不是禁止一切增长。

warn 级别的项也得有归宿，不然它们就是永远黄着的装饰品。现在的约定是每次迭代的技术评审会上过一遍最近累积的 warn：unused-javascript 连续几周指向同一个 chunk，就立一张优化卡进 backlog；确认短期不会处理的，要么挪进 skipAudits 显式关掉，要么留着但在配置注释里写明原因。warn 的价值在于它是免费的观察哨，但观察哨的报告没人看的话，不如撤掉哨位——留一堆无人认领的黄色警告，最后连红色的公信力都会被拖累。

还有一个容易被忽略的稳定性因素：Lighthouse 自己的版本。它的评分模型隔一阵就会调整，权重一变，代码没动分数也会漂。所以 workflow 里 @lhci/cli@0.9.x 是锁了小版本的，升级 LHCI（连带它内嵌的 Lighthouse）要当成一次独立的变更来做：先在分支上跑一轮对比，确认新版本下的基线，必要时同步调阈值，再合进主干。让"尺子本身变了"和"被测的东西变了"永远别发生在同一次提交里。

新页面的接入也定了个轻量的约定：不是每个新路由都自动进闸门（前面说过测试位是有成本的），但新的一级功能模块上线前，负责的同事要自己跑一轮本地 lhci，把结果贴在上线检查单里。这一步不设通过线，纯粹是让"这个页面目前什么水平"在上线时留个底——将来它如果流量涨到值得进闸门，基线是现成的，不用再花一周去试跑。

实验室数据的边界

最后得把这套东西的能力边界说清楚，不然容易产生虚假的安全感。Lighthouse 在 CI 里跑出来的是实验室数据（lab data）：固定的设备模型、固定的节流参数、固定的 mock 数据、无缓存的首次访问。它回答的问题是"这次代码变更让页面变快还是变慢了"——变量只有代码，所以答案可信。

但它回答不了"我们的用户实际体验如何"。用户用什么机器、什么网络、访问的是冷缓存还是热缓存、登录态带来多少额外请求，这些实验室里全是假设。去年写 Core Web Vitals 的时候我记过 Google 的口径：排名信号用的是 CrUX 里的真实用户数据，不是你自己跑的 Lighthouse 分。所以完全可能出现 CI 里绿油油、真实用户 P75 却很难看的情况，反过来也一样。

这条边界还牵出一个团队里已经出现过两次的困惑："我本地 DevTools 里跑 Lighthouse 是 92 分，CI 里怎么才 85？"答案几乎从来不是谁错了，而是环境不同：本地 DevTools 默认的节流模式、你机器的 CPU、开着的浏览器插件（广告拦截器会显著改变请求数）、甚至登录态的差别，都会让两边的分数没有可比性。我在 README 里加了一条：和闸门争论时，只认 CI 环境里的数字——本地的 Lighthouse 适合做优化时的快速反馈，不适合做裁判。要复现 CI 的结果，用前面那组本地 lhci 命令，别用 DevTools。

有个具体的例子能说明这条边界有多硬：FID。它衡量用户第一次交互的输入延迟，而实验室里没有用户，没人去点页面，所以 Lighthouse 根本测不出 FID，只能用 TBT 当代理指标——主线程被长任务阻塞的总时长，和"如果这时候有人点了会等多久"强相关但不是一回事。我的断言里压 TBT 而不是假装能压 FID，就是这个原因。反过来，CLS 这种布局稳定性指标实验室和现场都能测，但数值经常对不上：实验室只看首屏加载那几秒，真实用户会往下滚、会触发懒加载、会遇到迟到的推送条，现场的 CLS 几乎总是更差。读实验室数据时要清楚每个指标是"直接测到的"还是"代理出来的"，拿 TBT 的改善直接对外宣称"交互延迟优化了多少"，是要被打脸的。

这两件事对应两套工具：CI 里的实验室数据管"防回退"，线上的真实用户监控（RUM）管"看现状"。后者我们现在只有性能平台上很粗的采集，怎么把 Web Vitals 的现场数据收好、分位数怎么看，是另一个话题，这里不展开，先把 CI 这一半立住。

现在这道闸门跑了两周，拦下过一次真实的回退：一个 PR 引入了完整的 ECharts 而不是按需引入，script 预算直接超了 180KB，提交的同事看到报错自己就改了，前后没有任何人需要去"盯"。六月的优化成果这次能不能守过下一个三个月，年底见分晓——至少这一次，守着它的不再是我的记性。
