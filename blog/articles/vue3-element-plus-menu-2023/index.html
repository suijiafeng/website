Vue3 中封装 Element Plus 无限级菜单的基本思路

2023-09-17
Vue前端基础

后台系统里经常会有侧边菜单。

普通菜单只有一两级还好，一旦菜单来自接口，并且层级不固定，就需要封装一个支持无限级的菜单组件。

在 Vue3 和 Element Plus 中，实现这类菜单的关键是两点：统一数据结构，递归渲染菜单项。

这类组件看起来只是 UI 递归，但实际项目里通常还会牵涉路由、高亮、权限、图标、折叠状态和接口数据清洗。如果这些逻辑边界不清楚，菜单组件很容易越写越重。

我之前接手过一个项目，菜单组件有快 400 行，模板里塞满了 v-if，权限判断、图标判断、路由判断全揉在一起。改一个小需求都得提心吊胆，因为你不知道哪个分支又会触发别的逻辑。后来重写时我把它彻底拆开，组件本身才不到 60 行，剩下的逻辑全挪到了数据处理那一层。这里记一下当时的思路。

递归组件的关键是 key 要稳定。不要用数组下标作为 key，否则菜单顺序变化或权限过滤后，组件状态可能错乱。

具体会错乱成什么样？我遇到过的情况是：用 el-sub-menu 的展开/折叠是组件内部状态，如果用下标做 key，权限过滤砍掉前面一个菜单后，后面菜单的下标整体前移，Vue 复用了 DOM 但状态对不上，结果就是你点开了 A 菜单，刷新权限后展开的却是 B。用稳定的 index 做 key 能彻底避免这个问题，反正我们前面已经保证 index 唯一了。

有个细节得提一下：Element Plus 的图标是一个个组件，全量按需引入还好，但如果你想把所有图标都注册进 iconMap，包体积会很可观。我们项目后台菜单图标其实就十来个，所以手动维护这个映射完全够用，也更可控——设计稿上没有的图标，根本不会被打进包里。如果图标种类特别多，再考虑用 import.meta.glob 之类的方式动态加载。

另外别忘了 resolveIcon 返回 null 时模板那个 v-if 要兜住，否则 <component :is="null" /> 在某些版本里会报警告。折叠菜单（collapse）时图标尤其重要，因为这时候标题被收起来了，用户只能靠图标认菜单，没图标的一级菜单折叠后就是一片空白，很难用。

权限过滤放在哪里

菜单权限过滤最好在数据进入组件前完成，而不是在递归模板里到处判断。

最后一行用于去掉没有路径、也没有可见子菜单的空节点。权限过滤如果不处理空父级，侧边栏里很容易出现点不开的菜单。

路由跳转和 index

Element Plus 的 el-menu 支持 router 模式，这时 index 通常会作为路由路径使用。但实际项目里，index 不一定总等于 path。

我更倾向于明确约定：

  • 如果开启 router，index 使用可跳转路径
  • 如果不开启 router，点击事件里根据 path 手动跳转

不要一会儿用 code，一会儿用 path。菜单高亮和跳转逻辑一旦混乱，后面会很难排查。

如果 path 为空，说明它可能不是可点击菜单项，要在数据层提前处理清楚。

还有一个坑是 router 模式下的外链。后台菜单偶尔会配一个外部地址，比如跳到某个监控平台。el-menu 的 router 模式会拿 index 当路由 path 喂给 router.push，外链 https://... 直接就跳挂了。这种我一般在数据转换时打个标记，渲染时单独处理，用 window.open 跳出去，而不是让它走 vue-router：

实际项目要注意什么

无限级菜单看起来通用，但实际项目里还要考虑：

  • 菜单权限过滤
  • 路由地址和菜单 index 的对应关系
  • 图标动态渲染
  • 折叠时标题显示
  • 刷新页面后高亮当前路由
  • 菜单数据为空时的兜底

这些逻辑不要全部塞进递归项里，否则组件会越来越重。

还有两个边界经常被忽略：

  • 菜单层级过深时，交互体验会变差
  • 菜单数据可能存在循环引用或重复 index

接口异常也要有统一兜底。菜单接口失败时，不要让整个布局白屏。可以把错误收敛成统一结构，再决定跳登录、展示无权限，还是展示重试按钮：

菜单是后台系统的入口，它的错误处理要比普通列表页更谨慎。用户没有菜单时，要能区分“没有权限”和“接口加载失败”，这两种状态给人的提示完全不同。

Vue3 封装 Element Plus 无限级菜单，说到底就是树形数据加递归组件。

先把菜单数据整理清楚，再把外层配置和单项渲染拆开，后续接权限、路由和图标都会更容易维护。

我现在做这类菜单，会把它拆成三层：接口数据转换、权限和路由规则、递归 UI 渲染。三层分开以后，菜单组件本身就不会承担太多业务细节。
