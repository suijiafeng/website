HTML 和 CSS 代码风格：团队协作时最容易忽略的基础

2018-10-11
前端基础CSS

写 HTML 和 CSS 不难，难的是团队里很多人长期一起写，还能保持清楚、稳定、好维护。

代码风格规范的价值就在这里。它不是为了限制写法，也不是为了把每个人的习惯磨成一样，而是为了减少沟通成本。一个人写的页面，另一个人接手时，应该能快速看懂结构、样式职责和命名意图。

这类基础规范越早统一，后面越少返工。

我是吃过亏才信这套的。早些年带过一个三四个人的小组，没立规矩，大家各写各的：有人 class 全用拼音，有人爱写 .box1、.box2，有人样式恨不得全堆在一个几百行的 style.css 里。三个月后想改个公共按钮的颜色，全局搜 background 搜出来几十处，没人敢删，因为不知道哪个还在用。那次之后我才真正理解，风格规范省的不是写代码的时间，而是改代码、删代码、交接代码的时间——而这部分在项目生命周期里占的比重，远比写的时候大。

使用标准的 HTML5 文档类型

这样浏览器会以标准模式渲染页面，避免一些历史兼容模式带来的奇怪问题。我真见过有人页面顶上漏了 <!DOCTYPE html>，结果 IE 进了怪异模式（quirks mode），盒模型算法都变了，width 把 padding 算进去还是不算进去都不一样，量好的间距全错位。排查这种问题最坑的地方是，它不报错，只是"看起来不对"，你会下意识去怀疑自己的 CSS，根本想不到是文档声明的事。

lang、charset、title 这些信息也不要随手省略。它们不影响你把页面"画出来"，但会影响浏览器、搜索引擎和辅助技术理解页面。charset 尤其要放在 <head> 很靠前的位置——它得在浏览器开始解析正文之前就确定编码，否则中文页面可能先以默认编码解析了一段，再回头重解，偶尔会闪一下乱码。lang="zh-CN" 看着没用，但读屏软件会根据它选中文语音引擎，搜索引擎也用它判断页面语言，写上几乎零成本。

HTML 要尽量语义化

HTML 不只是把内容放到页面上。

合适的标签能让页面结构更清楚，也有利于可访问性、SEO 和后期维护。

例如：

  • 页面主标题用 h1
  • 段落用 p
  • 导航用 nav
  • 主要内容用 main
  • 列表内容用 ul、ol、li

不要为了样式方便就到处使用 div。样式应该交给 CSS，结构应该交给合适的 HTML 标签。

我自己判断该用什么标签有个土办法：把 CSS 全关掉，光看 HTML 渲染出来的样子。如果关了样式之后，标题还是标题、列表还是列表、导航还是一组链接、内容层级还读得通，那语义大概率是对的。如果关了样式整个页面就糊成一坨没头没尾的文字，那说明结构信息全靠 CSS 在撑，标签其实没承担它该承担的含义。读屏软件用户看到的，差不多就是关掉 CSS 之后那个样子。

按钮和链接也别混。我见过太多 <div onclick="..."> 当按钮用的，视觉上没差别，但它不能被 Tab 聚焦、不能用回车/空格触发、读屏软件也不会读成"按钮"。能用 <button> 就别用 div，能用 <a href> 跳转就别拿 JS 模拟。原生元素白送你一堆键盘和无障碍行为，自己用 div 重新实现一遍既费劲又容易漏。

BEM 唯一让人不爽的是类名长，article-card__header-title--active 这种写起来累。我的折中是：组件块名尽量短（用 .card 而不是 .article-list-item-card），元素层级别套太深，超过两层 __ 一般说明这个组件该拆了。命名长短是表象，套太深说明组件粒度有问题，这才是要警惕的信号。

所以我现在写 CSS 有条朴素的纪律：尽量只用单层 class 选择器，特异性拉平，需要区分状态就加修饰类。!important 一年也用不了几次，真用了一定写注释说明为什么。一旦发现自己想写 !important，先停下来想想是不是某个选择器太重了，把它降下来比硬覆盖健康得多。

把规范落到检查清单

代码风格不要只停留在口头约定。每次提交前，可以快速过一遍：

  • 页面是否有清楚的标题层级
  • 交互控件是否有可访问名称
  • 图片 alt 是否准确
  • CSS 类名是否表达业务或组件含义
  • 是否存在无用选择器和重复声明
  • 是否有过深嵌套或过强选择器
  • 同类组件的结构和命名是否一致

这些检查不复杂，但能拦住很多后续维护问题。

写规范不是怕人变笨，而是让团队在交接和改动时少猜多数错。语义化标签、清晰命名、稳定格式与可访问性，这些基础日后会省下大量沟通和排查时间。把能交给工具的规则自动化，让人把精力放回设计与逻辑上。
