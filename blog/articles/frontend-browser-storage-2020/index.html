浏览器存储方式简单梳理：Cookie、sessionStorage 和 localStorage 有什么区别

2020-04-18
前端基础

前端开发里经常会遇到“这个数据要不要存在浏览器里”的问题。

这时大家最常接触到的几种能力通常是：

  • Cookie
  • sessionStorage
  • localStorage

它们都能在浏览器端保存数据，但用途和边界并不完全一样。

选择浏览器存储时，不应该只问“能不能存”，还要问：存多久、谁能读、会不会随请求发送、是否敏感、失效后怎么恢复。

Cookie 的特点

Cookie 出现得比较早，最重要的特点之一是，它可以随请求一起带到服务端。

这也是它在登录状态、会话相关场景里经常被提到的原因。

但 Cookie 本身不适合保存太多数据，因为它体积有限，而且每次请求都可能附带。

Cookie 更适合服务端需要参与识别的场景，例如会话标识、灰度标记、部分安全策略。

设置 Cookie 时要关注几个属性：

  • HttpOnly：禁止 JavaScript 读取，降低 XSS 窃取风险
  • Secure：只在 HTTPS 下发送
  • SameSite：限制跨站请求携带 Cookie 的方式
  • Path / Domain：控制作用范围
  • Max-Age / Expires：控制过期时间

如果是登录态这类敏感信息，通常不应该直接放进可被 JavaScript 读取的 Cookie，更不应该放进 localStorage。

sessionStorage

sessionStorage 更适合保存当前会话期间的数据。

它的典型特点是：

  • 只在当前标签页会话中有效
  • 页面关闭后通常会清除

所以它适合一些短期状态，例如当前页面的临时输入、某个流程中的中间值等。

localStorage

localStorage 的特点是保存时间更长。

只要用户没有手动清除，数据通常会一直保留。

它适合：

  • 用户偏好设置
  • 搜索历史
  • 草稿缓存

但也要注意，不要把敏感信息随意长期存在本地。

不要把访问令牌、身份证号、银行卡号、完整用户资料这类敏感信息放进 localStorage。一旦页面存在 XSS 风险，这些数据都可能被脚本读取。

它们最大的区别是什么

可以从两个角度看：

1. 生命周期

  • Cookie 可以设置过期时间
  • sessionStorage 跟随当前会话
  • localStorage 更持久

2. 是否自动参与请求

  • Cookie 会和请求一起发送
  • sessionStorage 和 localStorage 不会自动带给服务端

这个区别非常关键。

还可以再补两个角度：

3. JavaScript 是否可读

  • 普通 Cookie 可以被 document.cookie 读取
  • HttpOnly Cookie 不能被 JavaScript 读取
  • sessionStorage 和 localStorage 可以被 JavaScript 读取

4. 作用范围

  • Cookie 受 Domain、Path 和 SameSite 影响
  • sessionStorage 通常限制在当前标签页会话
  • localStorage 在同源页面之间共享

同源是一个关键边界：协议、域名、端口都相同，才属于同源。

localStorage 的同步问题

localStorage 是同步 API。读写少量偏好没问题，但不要把它当数据库频繁读写大对象。

怎么选择

可以按这个思路判断：

  • 服务端每次请求都需要识别：优先 Cookie，注意安全属性
  • 当前标签页临时流程数据：sessionStorage
  • 长期本地偏好，丢失可恢复：localStorage
  • 大量结构化数据或离线能力：考虑 IndexedDB
  • 敏感数据：尽量不要交给前端可读存储长期保存

存储方案没有绝对最好，只有和数据风险、生命周期、读写方式匹配。

写在最后

浏览器端存储方式很多，但关键还是要理解它们各自的边界。

Cookie 更偏会话和服务端协同，sessionStorage 更适合短期会话数据，localStorage 更适合本地长期偏好类信息。只要把生命周期和使用场景理清楚，选择起来就不会太混乱。

更专业的选择还要考虑安全属性、同源边界、异常处理和数据是否敏感。前端存储不是免费的便利，任何长期保存在用户浏览器里的数据，都应该有明确理由。
