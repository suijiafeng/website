PWA 和 Service Worker：为什么发了新版，用户还是拿到旧文件

2018-04-21
前端基础性能与缓存

Service Worker 最吓人的地方，不是第一次接上去时资源秒开，而是你以为自己已经发了新版，用户那边却还在拿旧文件。普通资源更新出问题，通常刷新几次总能碰巧好；SW 一旦把旧文件缓存住，刷新本身都可能继续帮它发旧版本。

第一次认真踩这个坑时，最开始完全没往 SW 上想。bug 明明已经修了、版也发了，页面却怎么刷都是旧的。先怀疑构建错了，又怀疑 CDN 没刷新，来回查了一圈才反应过来：问题根本不在服务器，而在浏览器和网络之间多出来的那层代理。

这也是 Service Worker 真正需要敬畏的地方：它不是一个"缓存插件"，而是一个能接管请求的独立层，说了算的是它，不是你发了新版本它就照办。它最麻烦的地方在于错误是滞后且不可控的——代码早就改对了，用户那边却卡在某个旧版本里出不来，连"让他刷一下"都救不了，因为刷新拿到的还是缓存。

下面按填坑的实际顺序，把注册、缓存策略、更新流程、调试和收尾清理这几块逐一摊开。

初体验第一课：它是个独立线程，注册也有讲究

注册很简单：

Service Worker 不运行在页面主线程里，它可以拦截请求、管理缓存、处理离线逻辑。它本质上是一个 Worker，没有 DOM、没有 window，跟页面之间只能靠 postMessage 通信。

有几个前提条件我一开始没注意，各卡了我一回。一是 SW 只在 HTTPS 下才能注册（localhost 例外，本地开发能用 http），我有次在测试环境用的是 http 域名，注册代码静默失败，连个像样的报错都没有，盯着控制台看半天才想起这茬。二是它有作用域（scope）的概念——放在 /js/sw.js 注册，默认作用域就是 /js/，只能拦这个路径下的请求；想拦整站，文件就得放在根目录 /service-worker.js。这也是为什么大家都习惯把它扔根目录。

顺便说句历史：这个赛道的前任叫 AppCache（<html manifest="..."> 那套），声明式的、坑多到有专门的檄文骂它，现在已经在废弃的路上。SW 用可编程的方式把控制权还给了开发者——但控制权拿回来，责任也一起回来了，我这次翻的车就是证明。

注册时机我也调整过。一开始在页面加载时就注册，后来发现它会和首屏资源抢带宽，干脆挪到 load 事件之后，让首屏先跑完：

破解"改了不生效"：那个叫 waiting 的状态

要弄明白我那次发版为什么不生效，得先啃它的生命周期。SW 的安装、激活、更新都有自己的规则，不是你发布新 JS 后用户立刻就用上。状态机大致是 installing → installed(waiting) → activating → activated。

最关键、也最反直觉的是中间那个 waiting 状态：浏览器检测到 service-worker.js 文件有变化（字节级 diff）时，会在后台默默装一个新的 SW，但新 SW 装好后不会立刻接管页面，而是卡在 waiting，一直等到所有用旧 SW 的标签页都关掉，下次再打开才轮到它上岗。刷新不算关。

我那次"改了不生效"的根因就在这——运营的标签页从来没彻底关干净过，新 SW 永远在 waiting 里排队。理解了这个状态机，后面所有更新策略才有的放矢。

第二课：缓存策略要按资源类型分，别一把梭

我第一版 SW 犯的另一个错，是把所有请求都用同一种策略。不要这样。

静态资源适合 cache first（缓存优先，命中就直接返回，省一次网络往返）：

但 cache first 用在带 hash 文件名的构建产物上才安全（比如 app.3f9a2.js）——文件内容一变，文件名就变，相当于一个全新的 URL，旧缓存自然废弃，永远不会有"内容更新了但 URL 没变"的尴尬。

反过来，千万别拿 cache first 去缓存 index.html。index.html 的 URL 是固定的，里面引的却是带 hash 的 JS——一旦 html 被 cache first 缓存死了，用户拿到的永远是旧 html，旧 html 引的是旧 hash 的 JS，新版本的入口根本进不来，整套 hash 机制直接失效。坦白交代：我那次翻车的真正元凶，就是把入口 html 也给 cache first 了。html 这种"内容会变、URL 不变"的资源，要用 network first（网络优先，拿不到再退回缓存）或者 stale-while-revalidate（先用缓存秒出、同时后台悄悄更新下次用）：

接口数据通常不适合长期缓存。尤其用户信息、订单、权限这类，缓存错了比慢更严重——想象用户已经退登了，权限接口还吐着缓存里的旧数据，那就不是性能问题而是安全事故了。接口要不要进 SW 缓存，按"数据陈旧多久用户能忍"来定，而不是"缓存了能快多少"。

我现在把资源分成四类：

  • 构建产物：JS、CSS、字体
  • 图片资源：可缓存但要考虑更新
  • 内容接口：可短期缓存
  • 用户接口：尽量实时

落地时在 fetch 事件里按 URL 分流：构建产物走 cache first，入口 html 走 network first，内容接口走 stale-while-revalidate 并给过期时间，用户相关接口和带 Authorization 的请求干脆直接放过、连碰都不碰：

那句 method !== 'GET' 的判断是被现实教的：POST、PUT 这些带 body 的请求，Cache API 根本存不了，硬塞直接报错。我一开始没加判断，一个表单提交的 POST 进了缓存逻辑就抛异常，整个 fetch 处理挂掉，连带正常请求都受影响。只缓存 GET，这条写进肌肉记忆。

每一类缓存用独立的 cache name（static-v1、html-cache、api-cache），清理时能按需清，不会一锅端。版本号带在名字里，发版时在 activate 事件里把旧版本的 cache 全删掉（后面更新那节会用到）。

第三课：更新流程，让用户自己按下刷新键

修好缓存策略，回头解决 waiting 排队的问题。SW 更新后新版本不一定马上接管当前页面，用户可能还在旧页面里继续操作。最粗暴的做法是监听接管事件直接刷：

更温和的是显示提示：

但光有提示还不够，得先把"新 SW 卡在 waiting"疏通掉。我折腾几轮后固化下来的完整流程是：注册后监听 updatefound，新 SW 装好（进入 waiting）时弹个提示条；用户点"刷新"，页面给 waiting 的 SW 发一条 skipWaiting 消息让它立刻上岗，再 reload。

那个 refreshing 锁是必须的，否则 controllerchange 可能触发多次，页面反复 reload 陷入刷新循环——这个我也真撞上过，页面闪个不停，吓一跳。

skipWaiting() 要慎用，它让新 SW 跳过等待立刻接管。如果页面里的 JS（旧版本）和新 SW 缓存的资源版本对不上，可能出现资源错配。所以我只在"用户主动点了刷新、马上要 reload"的前提下才调它，绝不在 SW 一装好就无脑 skipWaiting。

还有条底线：不要悄悄更新关键资源，尤其后台系统。用户正在填表时突然刷新，体验会很差——我们运营有次写了半小时的工单，被我早期那版"自动 reload"一下清了个精光，找我算账算了一星期。内容站、营销页这种"看完就走"的可以激进点自动更新；后台系统、表单密集的应用，老老实实弹提示让用户自己选时机刷，是对用户的基本尊重。

第四课：调试，先学会把缓存清干净

这一个多星期里，Chrome DevTools 的 Application 面板成了我打开频率最高的地方：

  • 查看 Service Worker 状态
  • unregister
  • 清 Cache Storage
  • 勾选 Update on reload
  • 模拟离线

开发时发现"代码明明改了，页面还是旧的"，先检查 Service Worker。很多时候不是 webpack 没编译，而是缓存没更新——这句话我现在贴在工位上。

我的开发习惯是：本地调试时把 Update on reload 一直勾着，它会在每次刷新时强制重新拉取并激活 SW，省掉一堆 waiting 的扯皮；再配合 Network 面板的 Disable cache，基本能保证看到的就是最新代码。但切记这俩是给开发用的，别把"绕过缓存"的逻辑写进生产代码。

还有几个排查时帮我省过命的点。一是 SW 里 console.log 的输出不在页面的 Console 里，得在 Application → Service Workers 那里点进 SW 的专属调试上下文，或者直接看 chrome://inspect/#service-workers——我一开始对着页面 console 找日志找了半天，啥都没有。二是 Cache Storage 里能直接看到每个 cache 存了哪些 URL、内容是什么，"到底缓存命中没命中"用眼睛一看便知，比瞎猜强。三是改完 SW 逻辑老被旧 SW 干扰时，最干脆的办法是点 Clear storage 的"Clear site data"，把 SW、Cache、localStorage 一把全清，回到干净状态重来。

线上排查更被动，因为你没法让用户开 DevTools。所以我在 SW 里把版本号打进 cache name，又做了个诊断页，用 caches.keys() 把当前缓存的版本读出来上报——至少能知道用户卡在哪个版本。这点小预埋，出事时值千金。

排查过程中我还养成了一个习惯：怀疑是 SW 在捣鬼时，先去 Application 面板看一眼 Service Workers 那一栏里有没有多个版本同时列着。正常情况下应该只有一个 activated 的实例；如果看到一个 activated 加一个 waiting，说明新版本已经装好但还没轮到接管，这时候不用怀疑代码，先把标签页关掉重开，或者手动点一下 skipWaiting 按钮，很多"为什么线上还是旧的"的疑问在这一步就有答案了。

顺带记两笔更边缘的坑

一个是 no-cache 和 no-store 的区别，我这次也是现学现用。SW 注册用的那个入口脚本 service-worker.js 本身，浏览器默认最多缓存 24 小时才去检查更新——如果服务端返回的响应头里给它设了很长的 max-age，你发的新版本 SW 可能一整天都不会被浏览器发现。稳妥做法是给 service-worker.js 这一个文件单独配 Cache-Control: no-cache，让浏览器每次都发条件请求去问一声"变了没"，别指望它自己聪明地绕过强缓存。

第五课：别把错误响应缓存成"永久错误"

缓存 fetch 结果时，要判断响应状态：

不要把 500、404、登录页重定向缓存成正常资源。否则错误会被放大——从"这一次请求失败"变成"以后每次都从缓存里拿到这个失败结果"，而且 SW 缓存比浏览器 HTTP 缓存顽固得多，用户根本刷不掉。

更隐蔽的坑是 type === 'opaque' 的响应。跨域请求（引第三方 CDN 的资源、用 mode: 'no-cors'）拿到的是不透明响应，你读不到它的 status（永远是 0），也判断不了到底成没成。我把一个跨域字体文件缓存了下来，CDN 那边其实返回了 403，但响应是 opaque，我的判断逻辑没拦住，结果一个坏掉的字体被缓存死，整站字体显示异常还查不出原因。现在我对 opaque 的态度是：要么明确知道它安全才缓存，要么干脆不缓存跨域资源。

response.type !== 'basic' 把同源以外的响应都挡在缓存门外，是我后来加的保险。还有个细节上面代码里已经体现了——response 是个流，body 只能被读一次，要既返回给页面又存进缓存，必须先 clone() 再分别用，不然就是 "already used" 报错。

第六课：缓存得有人扫，不然会长成垃圾山

Cache Storage 是有配额的，超了浏览器会按策略把你的缓存整个清掉（连同精心缓存的离线资源），得不偿失。我在 activate 事件里做版本清理——发新版时把 cache name 的版本号一改，旧版本的缓存在激活时统一删掉：

末尾的 self.clients.claim() 让激活后的 SW 立刻接管当前已打开的页面，和前面 skipWaiting 的更新流程配套。对于内容接口那种 stale-while-revalidate 的缓存，还得在写入时给每条记录加时间戳，读的时候判断过期就丢——Cache API 本身不带 TTL，这个得自己实现，别指望它自动过期。

半个月体验下来

顺带记两笔这次一起玩到的东西。一是 manifest.json，配上名字、图标、display: standalone，安卓 Chrome 上真能"添加到主屏幕"，打开没有地址栏，像模像样一个 App，演示给产品看的时候他眼睛都亮了。二是手写 SW 折腾了这一大圈之后，我去看了 Google 新出的 Workbox 3（上个月刚发布，接替之前的 sw-precache 和 sw-toolbox），预缓存、路由策略、过期清理全是现成的——要是再上一个正经生产项目，我大概率直接用它，把这些坑外包给工具。

回到开头那次翻车。总结成几句话：按资源类型选策略，带 hash 的静态资源 cache first、入口 html 必须 network first；只缓存 GET，挡住错误响应和跨域 opaque；更新靠 updatefound / skipWaiting / controllerchange 协同，让用户决定何时刷新；缓存要版本化，在 activate 里清旧数据。缓存策略想清楚之前，Service Worker 宁可不上。 快一点用户未必感激，但拿到一个刷不掉的旧版本，用户是真的会骂人的——我们运营可以作证。
