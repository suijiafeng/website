PWA 和 Service Worker：缓存好用，但更新最容易翻车

2018-04-21
前端基础性能与缓存

PWA 听起来很美：离线可用、添加到桌面、资源秒开。真正接入 Service Worker 后，我最深的感受是，缓存确实好用，但更新最容易翻车。

我第一次踩这个坑印象太深了。给一个内部系统接了 Service Worker，本地测得好好的，资源秒开，美滋滋上线。第二天紧急修了个 bug 发版，结果运营那边反馈说"改的地方根本没生效"。我自己刷新页面也还是旧的，强刷（Ctrl+Shift+R）才偶尔好使。当时一脑门汗，以为是 webpack 没打包对、CDN 没刷新，折腾了快一个小时，最后才反应过来：是 Service Worker 把旧的 JS 缓存住了，新版本根本没接管页面，用户拿到的是被 SW 从缓存里塞回来的旧文件。那一刻我才真正理解，Service Worker 是横在浏览器和网络之间的一道代理，它说了算，不是你发了新版本它就听话。

普通前端资源出问题，刷新一下通常能解决。Service Worker 一旦缓存了旧资源，用户可能刷新很多次还是旧版本。缓存策略不清楚，PWA 会从性能优化变成线上事故来源。而且它最阴险的地方在于：错误是滞后且不可控的——你这边代码早就对了，用户那边却卡在某个旧版本里出不来，你连"让他刷一下"都解决不了，因为刷新拿到的还是缓存。所以我后来的态度是：Service Worker 这东西，缓存策略想清楚之前，宁可不上。

Service Worker 是独立线程

注册：

Service Worker 不运行在页面主线程里，它可以拦截请求、管理缓存、处理离线逻辑。它本质上是一个 Worker，没有 DOM、没有 window，跟页面之间只能靠 postMessage 通信。

有几个前提条件当年没注意也卡过我。一是 Service Worker 只在 HTTPS 下才能注册（localhost 是个例外，本地开发能用 http），我有次在测试环境用的是 http 域名，注册代码静默失败，连个像样的报错都没有，盯着控制台看半天才想起来这茬。二是它有作用域（scope）的概念——放在 /js/sw.js 注册，默认作用域就是 /js/，只能拦截这个路径下的请求；想拦整站的请求，文件就得放在根目录 /service-worker.js。这也是为什么大家都习惯把它扔根目录。

注册时机我也调整过。一开始直接在页面加载时就注册，后来发现它会和首屏的资源加载抢带宽，干脆挪到 load 事件之后，让首屏先跑完：

这也意味着它的生命周期和页面不完全一致。安装、激活、更新都有自己的规则，不是你发布新 JS 后用户立刻就用上。它的状态机大致是 installing → installed(waiting) → activating → activated。最关键、也最反直觉的是中间那个 waiting 状态：当浏览器检测到 service-worker.js 文件有变化（字节级 diff），它会在后台默默装一个新的 SW，但新 SW 装好后不会立刻接管页面，而是卡在 waiting，一直等到所有用旧 SW 的标签页都关掉，下次再打开才轮到它上岗。我那次"改了不生效"的根因就在这——用户一直没把标签页彻底关干净（刷新不算关），新 SW 永远在 waiting 里排队。理解了这个状态机，后面所有更新策略才有的放矢。

资源缓存要分类型

不要把所有请求都用同一种缓存策略。

静态资源适合 cache first（缓存优先，命中就直接返回，省一次网络往返）：

但 cache first 用在带 hash 文件名的构建产物上才安全（比如 app.3f9a2.js）——文件内容一变，文件名就变，相当于一个全新的 URL，旧缓存自然就废弃了，永远不会有"内容更新了但 URL 没变"的尴尬。反过来，千万别拿 cache first 去缓存 index.html。index.html 的 URL 是固定的，里面引的却是带 hash 的 JS——一旦 html 被 cache first 缓存死了，用户拿到的永远是旧 html，旧 html 引的是旧 hash 的 JS，新版本的入口根本进不来，整套 hash 机制直接失效。我那次翻车的真正元凶就是不小心把入口 html 给 cache first 了。html 这种"内容会变、URL 不变"的资源，要用 network first（网络优先，拿不到再退回缓存）或者 stale-while-revalidate（先用缓存秒出、同时后台悄悄更新下次用）。

接口数据通常不适合长期缓存。尤其是用户信息、订单、权限这类数据，缓存错了比慢更严重——想象一下用户已经退登了，权限接口还吐着缓存里的旧数据，那就不是性能问题而是安全事故了。我的原则是：接口要不要进 SW 缓存，按"数据陈旧多久用户能忍"来定，而不是"缓存了能快多少"。

我会把资源分成：

  • 构建产物：JS、CSS、字体
  • 图片资源：可缓存但要考虑更新
  • 内容接口：可短期缓存
  • 用户接口：尽量实时

缓存策略要按业务新鲜度决定。具体怎么落地，我一般在 fetch 事件里按 URL 分流：构建产物走 cache first，入口 html 走 network first，内容接口走 stale-while-revalidate 并给一个过期时间，用户相关接口和带 Authorization 的请求干脆直接放过、连碰都不碰：

这里有个新手常忽略的点：只缓存 GET 请求。POST、PUT 这些带 body 的请求，Cache API 根本存不了，硬塞会直接报错。我一开始没加 method 判断，一个表单提交的 POST 进了缓存逻辑就抛异常，整个 fetch 处理挂掉，连带正常请求都受影响。

每一类缓存最好用独立的 cache name（static-v1、html-cache、api-cache），清理的时候能按需清，不会一锅端。版本号带在名字里，发版时在 activate 事件里把旧版本的 cache 全删掉，这是控制缓存膨胀和强制更新的重要手段（后面更新那节会用到）。

更新提示很重要

Service Worker 更新后，新版本不一定马上接管当前页面。用户可能还在旧页面里继续操作。

不过光有提示还不够，得先解决前面说的"新 SW 卡在 waiting"的问题。完整的更新流程我后来固化成这样：注册后监听 updatefound，新 SW 装好（进入 waiting）时弹个提示条；用户点"刷新"，页面给 waiting 的 SW 发一条 skipWaiting 消息让它立刻上岗，再 reload。

那个 refreshing 锁是必须的，否则 controllerchange 可能触发多次，页面会反复 reload，陷入刷新循环——这个我也真的撞上过，页面闪个不停，吓一跳。

skipWaiting() 这个 API 要慎用，它会让新 SW 跳过等待立刻接管。如果页面里的 JS（旧版本）和新 SW 缓存的资源版本对不上，可能出现资源错配。所以我只在"用户主动点了刷新、马上要 reload"的前提下才调它，绝不在 SW 一装好就无脑 skipWaiting。

不要悄悄更新关键资源，尤其是后台系统。用户正在填表时突然刷新，体验会很差——我见过最惨的是用户写了半小时的工单，SW 自动 reload 一下全没了。所以内容站、营销页这种"看完就走"的，可以激进点自动更新；后台系统、表单密集的应用，老老实实弹提示让用户自己选时机刷，是对用户的基本尊重。

调试要学会清缓存

Chrome DevTools 里 Application 面板很重要：

  • 查看 Service Worker 状态
  • unregister
  • 清 Cache Storage
  • 勾选 Update on reload
  • 模拟离线

开发时如果发现“代码明明改了，页面还是旧的”，先检查 Service Worker。很多时候不是 webpack 没编译，而是缓存没更新。

我自己的开发习惯是：本地调试时把 Application 面板里的 Update on reload 一直勾着，它会在每次刷新时强制重新拉取并激活 SW，省掉一堆 waiting 的扯皮；再配合 Network 面板的 Disable cache，基本能保证看到的就是最新代码。但要切记上线前确认这俩是给开发用的，别把"绕过缓存"的逻辑写进生产代码。

还有几个排查时帮我省过命的点。一是 SW 里 console.log 的输出不在页面的 Console 里，得在 Application → Service Workers 那块点进 SW 的专属调试上下文，或者直接看 chrome://inspect/#service-workers，我一开始对着页面 console 找日志找了半天，啥都没有。二是 Cache Storage 里能直接看到每个 cache 里到底存了哪些 URL、内容是什么，"到底缓存命中没命中"用眼睛一看便知，比瞎猜强。三是改完 SW 逻辑老是被旧 SW 干扰时，最干脆的办法就是点一下 Clear storage 的"Clear site data"，把 SW、Cache、localStorage 一把全清，回到干净状态重来。

线上排查更被动，因为你没法让用户开 DevTools。所以我会在 SW 里把它的版本号打到一个固定 cache name 上，必要时让用户访问一个诊断页，用 caches.keys() 把当前缓存的版本读出来上报，至少能知道用户卡在哪个版本——这点小预埋，出事时值千金。

不要缓存错误响应

缓存 fetch 结果时，要判断响应状态：

不要把 500、404、登录页重定向缓存成正常资源。否则错误会被放大——它会从"这一次请求失败"变成"以后每次都从缓存里拿到这个失败结果"，而且 SW 缓存比浏览器 HTTP 缓存更顽固，用户根本刷不掉。

这里有个特别隐蔽的坑是 type === 'opaque' 的响应。跨域请求（比如引了第三方 CDN 的资源、用了 mode: 'no-cors'）拿到的是不透明响应，你读不到它的 status（永远是 0），也判断不了到底成没成。我有次把一个跨域的字体文件缓存了下来，CDN 那边其实返回了 403，但响应是 opaque，status 看着是 0、ok 是 false，我的判断逻辑没拦住，结果一个坏掉的字体被缓存死，整站字体显示异常还查不出原因。后来我对 opaque 响应的态度是：要么明确知道它是安全的才缓存，要么干脆不缓存跨域资源。

response.type !== 'basic' 这个判断把同源以外的响应都挡在缓存门外，是我后来加的保险。还有个细节前面代码里已经体现了——response 是个流，body 只能被读一次，要既返回给页面又存进缓存，必须先 clone() 再分别用，不然就是"already used"报错。

缓存清理：别让它无限膨胀

最后补一个容易被忘掉的环节：缓存得有人管，否则会越积越多。Cache Storage 是有配额的，超了浏览器会按策略整个清掉你的缓存（连同你精心缓存的离线资源），得不偿失。

末尾那个 self.clients.claim() 让激活后的 SW 立刻接管当前已打开的页面，配合前面 skipWaiting 的更新流程用。对于内容接口那种 stale-while-revalidate 的缓存，还得在写入时给每条记录加个时间戳，读的时候判断是否过期、过期就丢——Cache API 本身不带 TTL，这个得自己实现，别指望它自动过期。

Service Worker 带来强大能力也带来复杂性：按资源类型选策略（带 hash 的静态资源可 cache-first，入口 html 用 network-first），别缓存非 GET 或跨域 opaque 的失败响应；更新靠 skipWaiting/controllerchange 的协同并让用户决定何时刷新；缓存要版本化并在 activate 时清理旧数据。想稳妥上生产，优先考虑 Workbox 等成熟方案。快一点用户未必感激，但拿到一个刷不掉的旧版本，用户是真的会骂人的。
