PWA 和 Service Worker：缓存好用，但更新最容易翻车

2018-04-21
前端基础性能与缓存

PWA 听起来很美：离线可用、添加到桌面、资源秒开。真正接入 Service Worker 后，我最深的感受是，缓存确实好用，但更新最容易翻车。

普通前端资源出问题，刷新一下通常能解决。Service Worker 一旦缓存了旧资源，用户可能刷新很多次还是旧版本。缓存策略不清楚，PWA 会从性能优化变成线上事故来源。

Service Worker 是独立线程

注册：

Service Worker 不运行在页面主线程里，它可以拦截请求、管理缓存、处理离线逻辑。

这也意味着它的生命周期和页面不完全一致。安装、激活、更新都有自己的规则，不是你发布新 JS 后用户立刻就用上。

资源缓存要分类型

不要把所有请求都用同一种缓存策略。

静态资源适合 cache first：

接口数据通常不适合长期缓存。尤其是用户信息、订单、权限这类数据，缓存错了比慢更严重。

我会把资源分成：

  • 构建产物：JS、CSS、字体
  • 图片资源：可缓存但要考虑更新
  • 内容接口：可短期缓存
  • 用户接口：尽量实时

缓存策略要按业务新鲜度决定。

更新提示很重要

Service Worker 更新后，新版本不一定马上接管当前页面。用户可能还在旧页面里继续操作。

如果应用有明显版本变化，最好提示用户刷新：

更温和的方式是显示提示：

不要悄悄更新关键资源，尤其是后台系统。用户正在填表时突然刷新，体验会很差。

调试要学会清缓存

Chrome DevTools 里 Application 面板很重要：

  • 查看 Service Worker 状态
  • unregister
  • 清 Cache Storage
  • 勾选 Update on reload
  • 模拟离线

开发时如果发现“代码明明改了，页面还是旧的”，先检查 Service Worker。很多时候不是 webpack 没编译，而是缓存没更新。

不要缓存错误响应

缓存 fetch 结果时，要判断响应状态：

不要把 500、404、登录页重定向缓存成正常资源。否则错误会被放大。

小结

PWA 能改善加载体验，但 Service Worker 不是简单的缓存开关。静态资源、接口数据、用户数据要使用不同策略，更新流程要有提示，错误响应不能乱缓存。

缓存越靠近用户，越要谨慎。让页面快很重要，让用户拿到正确版本更重要。
