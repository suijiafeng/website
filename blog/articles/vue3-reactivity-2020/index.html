Vue 3 响应式变化初看：Proxy 带来的不只是写法变化

2020-06-27
Vue组件与状态

Vue 3 刚出来的时候，我对它的第一印象其实不是 Composition API，而是响应式系统换成了 Proxy。

那段时间我看了不少迁移文章，很多内容都在讲“Vue 2 用 Object.defineProperty，Vue 3 用 Proxy”。这句话当然没错，但如果只停在这里，很容易把它当成一个底层实现八卦。后来我真正把一些 Vue 2 项目里的写法迁到 Vue 3，才慢慢意识到：响应式的变化影响的不只是源码结构，它会改变你对状态的信心。

以前有些写法我会下意识避开。比如给对象新增字段、直接通过索引改数组、处理嵌套结构时，我脑子里总会多一层“这玩意儿能不能被追踪到”的担心。Vue 3 之后，这种心理负担少了不少。

我为什么在意响应式

响应式不是 Vue 的边角能力，它就是你每天写组件时踩在脚下的地板。

一个输入框变了，界面要更新；一个请求回来，列表要刷新；一个筛选条件调整，统计值要重新计算。我们平时写业务代码时很少把这些动作叫作“响应式系统”，但它们全都依赖这一层。

Proxy 带来的不是“可以随便写”

不过我不太喜欢把 Vue 3 的响应式变化讲成“终于没有限制了”。这会让人误解。

Proxy 解决的是一类追踪能力问题，不代表状态可以随便堆、随便改。响应式越强，反而越需要你更认真地组织状态。因为框架能追踪更多变化，混乱的状态也会更容易把影响扩散出去。

我现在写 Vue 3 时，会更注意把状态分成三类：

  • 原始状态：接口返回、用户输入、页面内部控制值
  • 派生状态：从原始状态计算出来的结果
  • 副作用：请求、存储、埋点、外部组件同步

ref 和 reactive 不是风格之争

刚开始写 Vue 3 时，我也纠结过 ref 和 reactive 怎么选。后来我的判断变得简单了：如果是一个独立值，我用 ref；如果是一组强相关的状态，我才用 reactive。

我不太会为了“少写 .value”把所有东西都塞进一个大 reactive 对象。这样短期舒服，长期会让状态边界变模糊。

写在最后

Vue 3 响应式改动之所以值得关注，不是因为底层名词更新了，而是因为它改变了我写业务代码时的心理模型。

Proxy 让很多以前别扭的地方变顺了，但它没有替我们解决状态设计。真正值得带走的不是“Vue 3 更强了”这句结论，而是：框架能追踪更多变化以后，我们更应该认真区分原始状态、派生状态和副作用。

响应式越自然，越不能把状态写得随意。这是我后来才真正体会到的地方。
