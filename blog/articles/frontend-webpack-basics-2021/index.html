为什么前端项目离不开构建工具：以 Webpack 为例看打包在做什么

2021-08-27
前端基础

很多人刚接触现代前端项目时，都会被构建工具吓一跳。

明明写的是浏览器页面，为什么还要打包、转译、处理资源、区分开发和生产环境？如果只从“让页面跑起来”看，构建工具似乎有点重。但只要项目稍微复杂一点，就会发现它其实是在帮前端管理复杂度。

我自己最早是从 <script> 标签一个一个往 HTML 里塞过来的。那时候没有构建概念，写个 jQuery 插件就再加一行标签，顺序还不能乱，jquery.js 必须排在前面，不然控制台直接报 $ is not defined。后来项目里脚本多到二十几个，每次上线都要手动数着压缩、改 HTML 里的引用，改一个忘一个是常有的事。直到团队引进了 Webpack，我才意识到之前那些“手动劳动”其实都是构建工具该干的活。

浏览器能执行代码，不代表它能直接接住整个项目

浏览器最终确实执行 JavaScript、解析 CSS、渲染 HTML。

但真实项目代码往往不是一份简单脚本，而是：

  • 拆成很多模块
  • 引用了样式和图片
  • 使用了较新的语法
  • 需要区分不同环境配置

如果没有构建工具，这些内容很难以稳定方式组织和交付。

举个最直白的例子。我在一个组件里写了 import { debounce } from 'lodash-es'，又顺手 import styles from './Button.module.css'，旁边还有 import logo from './logo.png'。这三行如果直接丢给浏览器，浏览器只认第一行的 ESM 语法（而且还得是带 type="module" 的环境），后两行它完全不知道该拿 CSS 和 PNG 怎么办——它根本没有“把 CSS 当成模块导入”这个概念。是 Webpack 在中间做了翻译，把这些非 JS 资源也纳入了同一套依赖体系里。

更别说语法问题。我写的可选链 user?.profile?.name、空值合并 count ?? 0，在 2018 年那会儿的安卓 webview 里直接是语法错误，整个文件都不执行。当时还真因为没转译，导致某款低版本机型上整页白屏，排查了大半天才发现是语法兼容的锅。这种事经历一次，就明白构建那一层不是可有可无的。

Webpack 解决的核心问题是什么

Webpack 最核心的思路可以概括成一句话：把前端项目里彼此依赖的资源，整理成浏览器更容易消费的产物。

这里的资源不只是 JavaScript，还可能包括：

  • CSS
  • 图片
  • 字体
  • 其他静态文件

它通过分析依赖图，把原本分散在很多文件里的内容按规则打包起来。

这个“依赖图”不是抽象说法。Webpack 从一个入口文件开始，顺着 import/require 一路爬，每碰到一个引用就把对应文件拉进来，再继续往下爬它的依赖，最后形成一棵从入口辐射出去的树。配置上其实就是这么几行最朴素的骨架：

我刚开始最容易忽略的就是 [contenthash] 这个细节。一开始图省事直接写死 bundle.js，结果上线后用户浏览器一直拿旧缓存，新功能死活不生效，还得让人家硬刷。后来才懂，文件名里带内容 hash，内容没变 hash 不变、缓存命中，内容一变 hash 就变、自动失效，这才是构建工具帮你做缓存的正确姿势。

为什么这对前端工程化很关键

一旦你有了模块化代码，就会马上碰到几个现实问题：

  • 浏览器如何识别这些模块关系
  • 样式和资源如何一起参与构建
  • 不同页面如何共享公共代码
  • 上线时如何压缩和优化产物

这时构建工具就不再只是“可选配件”，而变成项目基础设施。

Loader 和 Plugin 为什么会被反复提到

很多人一学 Webpack 就被这两个词包围。

可以先用很朴素的方式理解：

  • Loader 更像是把某类资源变成 Webpack 能继续处理的形式
  • Plugin 更像是在构建流程某个阶段插入能力

前者解决“文件怎么读”，后者解决“流程里要额外做什么”。理解到这一步，很多配置项就没那么抽象了。

Loader 有个我吃过亏的点：它是从右往左（从下往上）执行的。比如处理 CSS 那条规则 use: ['style-loader', 'css-loader']，真实顺序是先 css-loader 把 CSS 解析成 JS 模块、处理里面的 @import 和 url()，再交给 style-loader 把它通过 <style> 标签插进页面。我有次顺手把两个写反了，构建直接报错，盯着看了半天才反应过来是顺序的事。处理 Sass 就在最右边再加一个：['style-loader', 'css-loader', 'sass-loader']，链条越长越要记住这个方向。

Plugin 则是挂在 Webpack 整个生命周期的钩子上的。最常用的两个，一个把 CSS 从 JS 里抽成独立文件（生产环境必备，不然样式全塞在 JS 里、白屏时间长），一个自动生成 HTML 并把带 hash 的产物注入进去：

HtmlWebpackPlugin 是我后来再也离不开的。没它之前，我得手动维护 HTML 里那串带 hash 的脚本和样式引用，每次构建 hash 一变就得手改，简直是灾难。有了它，产物叫什么名字它自己往模板里塞，这种活就该交给工具。

构建工具的价值，不只是为了兼容新语法

有些人提到 Webpack，第一反应是“让浏览器能用更新的 JS 语法”。这当然是它的一部分价值，但远不是全部。

更完整地看，它还承担了：

  • 资源依赖整理
  • 代码压缩与拆分
  • 开发环境调试支持
  • 生产环境优化

这也是为什么一个前端项目的构建配置，往往和目录结构、发布流程、性能策略都有关联。

拿“代码拆分”举例，这是真正能直接影响用户体验的一块。我们有个后台项目，最初打出来一个两兆多的大 bundle，首屏要等用户把整个应用都下载完才渲染。后来用路由懒加载把它拆开，首屏体积一下降到几百 K：

publicPath：源码一行没错，线上资源全 404

我不觉得每个前端都得精通构建配置，但至少得知道改它可能牵动什么、产物和源码之间隔着什么，否则资源路径一异常就完全无从下手。坑最深的就是 publicPath。我们项目部署在 CDN 的子目录下，开发时一切正常，一上线 JS 和图片全 404。盯着 Network 面板看了好久才发现，产物里引用资源的路径前缀不对——本该是 https://cdn.xxx.com/app/，结果配置里还是默认的 /。改成下面这样才好：

Tree Shaking 不是配一下就生效，有前提

代码拆分之外，另一块减体积的是 Tree Shaking——把没被用到的导出删掉。但它不是开了就万能，有几个前提我踩坑后才搞明白：

第一，必须是 ESM。前面那篇模块化里说过，import/export 是静态的，Webpack 才能静态分析出谁没被用到；如果某个依赖只发了 CommonJS 产物，require 是运行时动态的，摇不动。所以引库时优先选带 ESM 产物的（比如 lodash-es 而不是 lodash）。

第二，得让构建工具相信“删掉没用的导出不会出事”。问题在于很多模块有副作用——比如顶层就执行了注册全局、打补丁、引入 CSS。Webpack 不敢贸然删有副作用的模块，于是要靠 package.json 里的 sideEffects 字段来声明：

想确认 Tree Shaking 到底有没有真的把死代码摇掉，造个最小例子就能验：写个 utils.js 导出两个函数 used() 和 neverUsed()，入口只 import { used } 并调用它，然后 npx webpack --mode production 打一次包，去产物里搜函数名——grep -r neverUsed dist/ 应该一条都搜不到，被摇掉了；而 used 的逻辑还在。注意一定要用 --mode production（development 模式不做这步压缩剔除，照样能搜到），而且导出得是 ESM 的 export，CommonJS 的 module.exports 摇不动。搜得到搜不到，是黑白分明的事，比看 bundle 体积变化直观。

填 false 表示“整个包都没副作用”。我有次给一个包图省事写了 "sideEffects": false，结果它顺手把一个只为副作用而 import './styles.css'（没有任何具名导入）的语句也当垃圾删了，样式直接丢失——CSS 这种纯副作用导入一定要在白名单里留着。

开发和生产其实是两套构建，搞混了就容易翻车

我刚上手时一直以为开发和上线跑的是同一套东西，后来才明白差别大了去了。开发时我用 webpack-dev-server，图的是改完代码热更新（HMR）秒生效、错误能定位到源码行。

HMR 不是整页刷新，这是它和 live-reload 的关键区别。dev-server 和浏览器之间维持一条 WebSocket 长连接，文件一改、Webpack 增量编译出变化的那个模块，通过这条连接把新模块（以及一个 hash 清单）推给浏览器运行时；运行时再把旧模块替换成新的，只重渲染受影响的部分，页面状态（比如表单里填了一半的内容、当前打开的弹窗）能保住。这也是为什么 HMR 需要框架配合——React/Vue 的相应插件知道“某个组件换了，怎么在不丢 state 的前提下重渲染它”，纯 JS 模块则得自己写 module.hot.accept 接住更新，否则会退化成整页刷新。

devtool 这个选项本身就是一组取舍。开发追求快和准，eval-cheap-module-source-map 用 eval 包代码、构建和 rebuild 都快，能映射到源码行（module），但列信息（cheap 省掉了）差一点，日常够用。生产则不该把 source map 直接随包暴露——要么用 source-map 生成独立 .map 文件、只上传给 Sentry 这类错误平台而不部署到公网，要么干脆 hidden-source-map（产物里不写 //# sourceMappingURL 注释，但 map 仍生成供平台用）。我见过有人开发配置直接拿去打生产包，结果体积没压、还把整套源码 map 暴露在线上，安全和性能两头吃亏。所以我都是 webpack.dev.js 和 webpack.prod.js 分开写，用 webpack-merge 抽公共部分。

生产那套的其余追求是：压缩、Tree Shaking、把 process.env.NODE_ENV 替换成 "production"（很多库靠这个判断剔除开发期的警告代码）。

文件名里那个 hash，决定了缓存能不能命中

回到开头那个写死 bundle.js 被缓存坑了的事，这里再说清楚 hash 的几种粒度，因为选错了缓存策略就废了。Webpack 给文件名占位符有三种：[hash] 是整次构建一个值，任何文件变了所有产物 hash 全变——等于改一行业务代码、第三方 vendor 包的缓存也全失效，最差；[chunkhash] 按 chunk 算，同一个 chunk 没变就不变；[contenthash] 按单个文件内容算，最细，CSS 和 JS 分别独立。

这条「内容不变 hash 不变」的承诺，自己验一下就放心了：连着 npx webpack --mode production 构建两次、中间一个字都不改，对比两次 dist/ 里的文件名，带 [contenthash] 的那些产物名字会一模一样；随便改一行业务代码再构建第三次，只有受影响的那个 chunk 文件名的 hash 段会变，vendor 包的名字纹丝不动。这正是缓存能持续命中的根据。

顺带说个排查产物时很实用的细节：source map 配没配、配的哪种，扒一眼产物末尾就知道。打包产物 JS 文件的最后一行，配了能定位的 source map 时会有一句 //# sourceMappingURL=...；用 hidden-source-map 时这行不会写进产物（map 文件照样生成、供 Sentry 用）；devtool 设成 false 则连 map 都不生成。线上误带源码 map 还是已经摘干净，看产物尾巴这一行有没有、指向哪里，比翻配置快。

所以生产环境我一律用 [contenthash]：业务代码改了，只有业务 chunk 的 hash 变、vendor 包 hash 不动，用户浏览器对 vendor 的缓存继续命中。这也是前面 splitChunks 把 node_modules 抽成单独 vendor 包的意义所在——把“几乎不变的第三方依赖”和“天天改的业务代码”分开，让缓存的命中率最大化。两者配合才有效果，单独用哪一个都打折扣。
