DocumentFragment：批量插入 DOM 时的一个实用技巧

2020-11-08
前端基础JavaScript性能与缓存

操作 DOM 是前端里很常见的事情。

但频繁操作 DOM 也容易带来性能问题，尤其是循环插入大量节点时。

DocumentFragment 的作用就是：先在内存里组装一批节点，最后一次性插入页面。

它不是一个神秘的性能开关，而是一个轻量的临时容器。用得合适时，它能让批量 DOM 操作更清楚，也减少直接碰真实页面的次数。

我第一次认真用它，是做一个没上框架的运营活动页。后端一次返回上千条记录，要画成一个长列表，纯 jQuery 时代的写法是 for 循环里不停 append，结果低端机上点一下卡好几秒，肉眼可见地一行一行往外蹦。换成 fragment 先在内存里拼好再一次性塞进去，立刻就顺了。从那以后这招就成了我处理“原生 JS 批量建节点”的默认手段。

说在前面，DocumentFragment 是浏览器原生 API，不依赖任何库，IE 时代就有，兼容性完全不用操心。它本质就是一个游离在文档之外的节点容器——你往里塞节点不会触发页面渲染，因为它根本不在页面上。

例如这种写法就不太好：

插入后立刻读取布局信息，会增加浏览器同步计算的压力。这个现象有个专门的名字叫“强制同步布局”（forced synchronous layout），有些工具里会报成 layout thrashing（布局抖动）。原理是：浏览器为了省事，会把你的 DOM 写操作攒着批量处理；可一旦你读 offsetHeight、offsetTop、getBoundingClientRect() 这类几何信息，它为了给你一个准确的值，不得不立刻把前面攒的写全部结算一遍。写、读、写、读交替，就等于逼它一次次重算，循环里这么干特别要命。

我在 Chrome 的 Performance 面板里见过这种火焰图——一大片紫色的 Layout 条密密麻麻排着，每一条对应一次循环。把读操作挪出循环、或者改用 fragment 离线拼装之后，那片紫色就消下去了。所以 fragment 真正帮上忙的，不光是“少 append 几次”，更是天然把“拼装”和“查询布局”这两件事隔开了——你在 fragment 上根本读不到有意义的布局信息，也就不会手贱去读，从源头上避开了抖动。

这个“插入后被掏空”的特性新手很容易栽。我见过有人想复用同一个 fragment 插到两个地方，结果第二次插进去啥都没有——因为第一次 append 时 fragment 里的节点已经被“搬”走了，它只是个搬运工，不留副本。如果真要插两份，得 fragment.cloneNode(true) 克隆一份再插。

还有一点容易忽略：fragment 自己不会出现在最终 DOM 里。这其实是优点——不像你拿一个真 <div> 当容器，最后页面上会多一层无意义的包裹元素。fragment 插完就消失，子节点直接成为目标父元素的孩子，DOM 结构干干净净。

用 template 生成复杂结构

如果每个列表项结构比较复杂，可以用 <template> 保存静态结构，再克隆节点。

这种写法比大量字符串拼接更适合复杂节点，也能继续使用 textContent 避免把用户输入当 HTML 执行。

<template> 这个标签我特别推荐。它里面的内容浏览器不会渲染、不会加载（图片不会发请求、脚本不会执行），纯粹是个“待克隆的模子”，通过 .content 拿到它的 DocumentFragment。比起在 JS 里一层层 createElement + appendChild 手搭复杂结构，把静态骨架写在 HTML 里、JS 只负责填数据，结构和逻辑分得很清楚，改样式直接改 template 就行。

克隆时记得传 cloneNode(true)——参数为 true 才是深克隆，连子节点一起复制；写成 false 或不传只克隆最外层那个空壳，里面的 .user-name、.user-role 全没了，querySelector 直接报 null。这个我也忘传过一次，对着 “Cannot set property textContent of null” 愣了半天。

另外，template.content.firstElementChild 用的是 firstElementChild 而不是 firstChild，是为了跳过模板里换行、缩进产生的文本节点。firstChild 很可能拿到一个空白文本节点，又是一个会让人摸不着头脑的坑。

它适合哪些场景

DocumentFragment 适合：

  • 一次渲染大量列表
  • 批量创建表格行
  • 批量插入下拉选项
  • 原生 JS 操作 DOM 的工具函数

如果项目使用 Vue、React 这类框架，通常框架已经帮你处理了很多渲染优化，不需要手动到处使用它。

更准确地说，框架里不应该频繁绕过框架去直接操作 DOM。DocumentFragment 更适合原生 JS、工具脚本、轻量页面或框架外的局部增强。

我自己用它最多的几个场景：埋点/监控 SDK 这种不能依赖框架、得跑在各种宿主页面上的脚本；浏览器插件往别人页面里注入内容；还有老项目里某个性能瓶颈点的局部优化。Vue、React 里我基本不碰它——你在 React 里手动 fragment 操作 DOM，下一次组件重渲染会把你的改动覆盖掉，得不偿失。顺带一提，React 里的 <Fragment>（<>...</>）和这个 DocumentFragment 名字像、思想也有点像（都是“不留多余包裹”），但完全是两个东西，别混为一谈。

还有一类隐藏收益：当你要往一个已经很大的列表里追加节点时，fragment 让你只触碰一次真实 DOM，浏览器只需要做一次插入和重排。哪怕现代浏览器对连续 append 优化得不错，一次性插入在逻辑上也更可控，代码读起来意图也更明确——“我要批量加这一坨”，而不是“我循环里一个个往页面塞”。

事件委托和 fragment 是绝配。想想看，如果你在循环里给每个 li 都 addEventListener，一千条数据就是一千个监听器，又占内存，列表一重渲染老节点被替换掉、监听器还可能残留（取决于你怎么清的）。把监听器挂在父级 #list 上，靠事件冒泡接住所有子项的点击，无论列表怎么增删重渲，监听器始终就那一个，新加的节点天然就“带”事件。

委托里那行 event.target.closest("[data-id]") 很关键：用户点的可能是 li 内部的某个 <span> 或 <strong>，event.target 是那个内层元素，得用 closest 往上找到带 data-id 的那个 li。后面再加一句 list.contains(item) 做个保险，确认找到的节点确实在这个列表里，避免 closest 越界匹配到外面去。这两步我现在写委托几乎是肌肉记忆。

DocumentFragment 最值得记住的不是 API 名字，而是那句老办法：先离线组装，再一次插进去。

真到几百上千个节点的渲染，或者 Performance 面板里已经能看到 Layout 飘红，它就很顺手；只是插三五个节点时，硬上 fragment 反而像是在给自己加戏。实际写列表时，我会顺手把几件事一起处理掉：用户内容用 textContent，整块更新用 replaceChildren，点击交互交给父节点事件委托。这样性能、安全和后续交互是一套思路，不是各补各的补丁。
