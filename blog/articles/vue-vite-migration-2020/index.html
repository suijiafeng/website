把 Vue 项目迁到 Vite 之前，先想清楚你迁的是速度，还是整套工程假设

2020-08-08
Vue构建与模块化

Vite 很快，这一点几乎不用太多证明。问题是，项目迁移从来都不只是“新工具更快，所以换过去”。

我第一次认真考虑把 Vue 项目迁到 Vite 时，也被它的启动速度打动过。那种“终于不用等”的感觉很直接。但冷静下来之后，我发现真正难的不是跑起一个 demo，而是弄清楚旧项目里到底依赖了多少 Webpack 时代的工程假设。

迁移工具链最怕的是只看到收益，看不到债务。

迁移前最该先看什么

通常至少要先盘一盘这几类东西：

  • 自定义 Webpack 配置有多少
  • 别名、环境变量、插件是否深度绑定
  • 第三方 loader 是否很多
  • 构建脚本和部署流程有没有耦合

如果这些东西很重，迁移就不只是换个启动命令。

快是收益，但不是全部收益

Vite 最明显的优势确实是开发快。

但迁移值不值得，最终还是看两件事：

  • 迁移成本高不高
  • 长期收益能不能覆盖这次改动

我现在评估迁移收益，会把它拆成三类：

  • 开发体验：启动、热更新、局部修改反馈
  • 工程维护：配置复杂度、插件生态、团队理解成本
  • 交付质量：生产构建结果、兼容性、部署流程稳定性

只说“快”是不够的。快当然重要，但如果迁移后构建脚本变脆、部署流程没人敢碰，收益就会被维护成本吃掉。

先迁边界小的项目

如果团队之前没迁过，我不建议一上来就拿最复杂的后台主应用开刀。

更好的方式是先选一个边界清楚的项目：

  • 页面数量不太多
  • Webpack 自定义配置少
  • 第三方 loader 少
  • 部署链路简单
  • 有基本回归测试

先把迁移流程跑通，比直接挑战最大项目更有价值。团队会在小项目里摸清楚 alias、环境变量、代理、样式、构建产物、部署脚本这些细节。

保留回退方案

工具链迁移不是只改代码，也要考虑失败时怎么退。

我会尽量保持几个原则：

  • 不在迁移中顺手重构业务
  • 不同时升级一堆无关依赖
  • 保留旧构建分支或明确回退路径
  • 迁移前记录构建产物和核心页面行为
  • 迁移后跑完整 lint、build 和核心页面回归

如果迁移过程中发现问题，很容易有人说“顺便把这块也改了”。这通常会把风险放大。迁移的目标应该先是等价替换，再谈优化。

接口错误和代理配置也要验证

开发环境迁移时，代理配置很容易被忽略。页面能打开，不代表接口链路正常。

我会怎么判断值不值得迁

如果一个项目每天都有人开发，启动慢、热更新慢已经明显影响效率，而且构建配置没有过度魔改，我会认真推动迁移。

如果一个老项目很稳定，一年只改几次，Webpack 配置又深又旧，那我不会为了“技术更新”强行迁。工具链升级应该服务项目，不应该变成团队的情绪出口。

Vite 是好工具，但好工具也要放在合适的项目节奏里。

Vue 项目迁到 Vite，最怕的不是踩坑，而是预期太轻。

如果把它看成一次工具升级，准备往往不够；如果把它看成工程假设切换，很多判断就会更稳。

我现在更愿意把迁移看成一次“工程体检”：借这个机会看清项目依赖了哪些旧约定、哪些配置没人敢动、哪些流程其实已经不健康。迁移成功不只是跑上 Vite，而是团队重新掌握了自己的构建系统。
