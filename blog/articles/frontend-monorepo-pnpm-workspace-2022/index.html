前端 Monorepo 与 pnpm workspace：多包项目先把边界想清楚

2022-12-06
构建与模块化前端基础

前端工程化里，Monorepo 的讨论越来越多。组件库、后台系统、移动端 H5、工具包、业务 SDK，如果都拆成独立仓库，版本联动和本地调试会变得麻烦；如果全部塞进一个应用，又会让边界模糊。

Monorepo 的目标不是“把所有代码放进一个仓库”，而是让多个相关包在一个仓库里协同开发。

pnpm workspace 是很实用的选择。它安装快、磁盘占用低，对多包项目支持也比较直接。

我第一次觉得 Monorepo 有价值，是在组件库和几个后台应用同时迭代的时候。一个按钮组件改了状态样式，三个应用都要验证；一个请求包改了错误结构，业务应用和移动 H5 都要跟着调。如果分散在多个仓库里，本地联调和版本同步会消耗很多时间。

但我也见过反例：几个几乎没关系的项目硬放进一个仓库，最后只是让安装、权限、CI 都变复杂。所以我现在看 Monorepo，第一反应不是“要不要上”，而是“这些包是否真的需要一起演进”。

什么时候适合 Monorepo

适合 Monorepo 的场景：

  • 多个应用共享组件库
  • 前端应用和工具包频繁联动
  • UI 组件、业务组件、主题包需要一起开发
  • 多个包需要统一 lint、test、build
  • 本地调试跨包依赖很频繁

不适合的场景：

  • 项目之间几乎没有共享
  • 团队权限边界非常独立
  • 发布节奏完全不同且互不影响
  • 仓库已经很大但没有治理能力

Monorepo 会提升协作效率，也会提升治理要求。没有边界意识的 Monorepo，很快会变成一个更大的混乱仓库。

一个很实用的判断是：如果一个改动经常需要同时改多个包，并且希望一次 PR 里完成验证，Monorepo 会有明显收益。如果只是为了“看起来统一”，收益就很可疑。

workspace:* 表示使用当前 workspace 内的包。这样本地开发时，修改 @acme/ui 可以被应用直接引用，不需要先发布到 npm。

这里有个很容易漏的细节：不要把 workspace 包写成普通版本号，比如 "@acme/ui": "^0.1.0"。这样 pnpm 可能会去 registry 找包，而不是强制使用本地 workspace。内部包之间我一般都用 workspace:* 或 workspace:^，让依赖关系明确指向仓库内包。

依赖应该装在哪里

Monorepo 里依赖管理最容易混乱。

我的规则是：

  • 某个包运行时需要的依赖，装在该包 dependencies
  • 某个包构建或测试需要的依赖，装在该包 devDependencies
  • 全仓库统一工具，比如 eslint、prettier、typescript，可以装在根目录
  • 不要让包依赖根目录里偶然存在的运行时依赖

版本发布要提前设计

Monorepo 发布通常有两种模式：

  • 固定版本：所有包使用同一个版本号
  • 独立版本：每个包单独升级版本

固定版本简单，适合强绑定的一组包。独立版本灵活，适合工具包、组件库分别演进。

小团队一开始不要把发布流程设计得过于复杂。可以先内部使用 workspace，不急着发布到 npm。等包边界稳定后，再引入 Changesets 之类的版本管理工具。

CI 不要一开始就全仓库重跑

Monorepo 早期全量跑 lint、test、build 没问题，简单可靠。

但包多起来以后，CI 会越来越慢。这个时候就要考虑 affected 范围：改了 packages/ui，需要跑依赖它的应用；只改文档，不一定要全量构建。

API 错误和共享请求包

很多 Monorepo 会抽一个 packages/request，给多个应用复用请求逻辑。这是好事，但要把错误结构设计稳定。

共享请求包一旦被多个应用依赖，破坏性改动影响会很大。统一错误结构、明确版本、补测试都很必要。

共享包越底层，越要保守。比如 request、auth、config、ui theme 这些包，一次改动可能影响所有应用。它们的 API 要少而稳定，破坏性改动最好通过版本和迁移说明来做，不要在业务迭代里顺手改掉。

我现在看一个团队要不要上 Monorepo，会先问它有没有“必须一起改、一起验证”的真实需求。

有，pnpm workspace 会很舒服：本地联调少很多发包和切仓库的折腾，组件库、请求包、主题包和业务应用可以在同一个 PR 里完成验证。没有，只是把几个项目堆进一个仓库，那它只会把安装、权限、CI 和发布都变复杂。

Monorepo 真正难的不是工具，而是边界：哪些代码应该成为包，哪些依赖应该声明在哪里，哪些脚本要全量跑，哪些包需要独立发布。先把包职责想清楚，再让 pnpm workspace 提高协作效率，顺序不能反。
