前端 Monorepo 与 pnpm workspace：多包项目先把边界想清楚

2022-12-06
构建与模块化前端基础

前端工程化里，Monorepo 的讨论越来越多。组件库、后台系统、移动端 H5、工具包、业务 SDK，如果都拆成独立仓库，版本联动和本地调试会变得麻烦；如果全部塞进一个应用，又会让边界模糊。

Monorepo 的目标不是“把所有代码放进一个仓库”，而是让多个相关包在一个仓库里协同开发。

pnpm workspace 是很实用的选择。它安装快、磁盘占用低，对多包项目支持也比较直接。

什么时候适合 Monorepo

适合 Monorepo 的场景：

  • 多个应用共享组件库
  • 前端应用和工具包频繁联动
  • UI 组件、业务组件、主题包需要一起开发
  • 多个包需要统一 lint、test、build
  • 本地调试跨包依赖很频繁

不适合的场景：

  • 项目之间几乎没有共享
  • 团队权限边界非常独立
  • 发布节奏完全不同且互不影响
  • 仓库已经很大但没有治理能力

Monorepo 会提升协作效率，也会提升治理要求。没有边界意识的 Monorepo，很快会变成一个更大的混乱仓库。

依赖应该装在哪里

Monorepo 里依赖管理最容易混乱。

我的规则是：

  • 某个包运行时需要的依赖，装在该包 dependencies
  • 某个包构建或测试需要的依赖，装在该包 devDependencies
  • 全仓库统一工具，比如 eslint、prettier、typescript，可以装在根目录
  • 不要让包依赖根目录里偶然存在的运行时依赖

版本发布要提前设计

Monorepo 发布通常有两种模式：

  • 固定版本：所有包使用同一个版本号
  • 独立版本：每个包单独升级版本

固定版本简单，适合强绑定的一组包。独立版本灵活，适合工具包、组件库分别演进。

小团队一开始不要把发布流程设计得过于复杂。可以先内部使用 workspace，不急着发布到 npm。等包边界稳定后，再引入 Changesets 之类的版本管理工具。

API 错误和共享请求包

很多 Monorepo 会抽一个 packages/request，给多个应用复用请求逻辑。这是好事，但要把错误结构设计稳定。

共享请求包一旦被多个应用依赖，破坏性改动影响会很大。统一错误结构、明确版本、补测试都很必要。

小结

pnpm workspace 让前端 Monorepo 的起步成本变低，但 Monorepo 的核心仍然是边界设计。哪些代码应该成为包，哪些依赖应该声明在哪里，哪些脚本要全量跑，哪些包需要独立发布，这些问题比工具本身更重要。

如果只是把多个项目放在一个仓库里，却没有依赖边界、构建边界和发布边界，Monorepo 只会放大混乱。先把包职责想清楚，再让 pnpm workspace 帮你提高协作效率。
