JavaScript 里的 this 为什么总让人别扭：它不是指向写代码的人

2021-04-21
前端基础

JavaScript 里 this 一直是很有代表性的一个坑。

它不难遇到，但很容易理解得不稳定。很多人刚学时会把 this 想成“当前函数所在对象”，结果一换调用方式就乱了。我自己刚入行那两年，定位过不少诡异的 bug，最后查到根上都是 this 跑偏了——明明上一行还好好的，换个地方调一下就变成 undefined，或者悄悄指到了 window 上。

真正要抓住的是：this 不是在函数定义时固定死的，它和函数是怎么被调用的关系更大。我后来把一句口诀放在脑子里：看谁在点号左边。绝大多数日常场景，this 就是调用时点号左边那个东西；没有点号、直接调用的，才需要去想严格模式和全局对象那一套。这句话不严谨，但能帮我在 review 代码时第一时间嗅出哪里会出问题。

为什么 this 容易让人误会

平时看代码时，我们习惯根据书写位置理解语义。

例如一个函数写在对象里，直觉上就会觉得它里的 this 应该指向这个对象。但 JavaScript 并不是总按“写在哪里”来决定 this，而是更看“怎么调用”。

这也是为什么同一个函数，换一种调用方式，this 就可能变。

也正因为行为不够直观，很多项目开发里会尽量避免依赖这种不明确的 this。

箭头函数的一个重要特点，是它没有自己的 this，而是继承外层作用域的 this。

不过箭头函数也不是万能的。它因为没有自己的 this，所以并不适合所有需要动态绑定上下文的场景。有几个地方我是明确不用箭头函数的：

  • 对象方法：写成箭头函数后，this 会沿用定义时的外层作用域（通常是模块顶层或 window），而不是这个对象。
  • 需要 this 指向触发元素的事件回调，前面已经说过。
  • 原型方法、构造函数：箭头函数没有 prototype，也不能 new，强行用直接报错。
  • 任何依赖 arguments 的老式函数：箭头函数同样没有自己的 arguments。

我的习惯是：默认写箭头函数，只有在“这个函数需要自己的动态 this”时才退回普通函数。这条规则覆盖了我日常九成以上的场景。

call、apply、bind 本质上是在控制调用上下文

这三个方法总被一起讲，本质上都和手动指定 this 有关。

这意味着你可以不改变函数定义位置，只改变它执行时绑定的上下文。三者的区别说穿了很简单：call 和 apply 都是立即执行，差别只在传参——call 一个个传，apply 用数组传；bind 不执行，而是返回一个永久绑定好 this 的新函数。

apply 在 ES6 展开运算符出来之前用得很多，比如求数组最大值要写 Math.max.apply(null, arr)，现在直接 Math.max(...arr) 就行了，apply 的这类用法基本退场。

bind 倒是一直没被淘汰。React 还在用 class 组件的那几年，构造函数里清一色 this.handleClick = this.handleClick.bind(this)，就是为了把方法传给 JSX 当回调时不丢 this。这里有个细节坑过我：bind 一旦绑定就锁死了，再 call 也改不动。

在一些工具函数、数组借用方法（比如 Array.prototype.slice.call(arguments) 把类数组转真数组）、老代码兼容场景里，这类写法还挺常见。新代码里我更愿意用箭头函数和扩展运算符替代，但读老项目时这套还是绕不开。

真实项目里最稳的做法，往往是少制造模糊上下文

我后来对 this 的态度越来越务实：理解它很重要，但写代码时要尽量少依赖不清楚的 this。

例如：

  • 回调里优先用箭头函数或显式参数
  • 组件方法里明确调用入口
  • 工具函数尽量做成纯函数

这样一来，就算你懂 this 的规则，也不用天天和它较劲。

JavaScript 的灵活性有时就是这样，它给了你很多可能，但项目维护更看重稳定。this 不是不能用，而是要知道什么时候它会帮你，什么时候它只会制造歧义。

this 真正让人难受的，是它经常在“看起来差不多”的代码里变化

例如同样是调用一个函数，写成对象方法调用、事件回调、定时器回调，或者把方法先取出来再执行，this 结果就可能完全不同。也正因为这种差异往往藏在调用方式里，而不是藏在函数体里，所以它特别容易造成误判。

很多人不是不知道 this 有规则，而是规则一旦进入真实项目语境，就不再像单独小例子那么直观。

在团队代码里，少制造模糊上下文通常更重要

我后来越来越少把 this 当成“必须灵活使用的能力”，而更倾向于把它当成一个需要谨慎对待的上下文机制。因为项目里更重要的通常不是写法能不能成立，而是后来的人能不能一眼看明白。

这也是为什么很多代码会偏向：

  • 用显式参数代替隐式上下文
  • 用箭头函数稳定回调里的外层引用
  • 让工具函数尽量保持纯粹

理解 this 当然必要，但真正成熟一点的写法，往往是在理解之后主动减少歧义。
