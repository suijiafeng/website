JavaScript 里的 this 为什么总让人别扭：它不是指向写代码的人

2021-04-21
前端基础

JavaScript 里 this 一直是很有代表性的一个坑。

它不难遇到，但很容易理解得不稳定。很多人刚学时会把 this 想成“当前函数所在对象”，结果一换调用方式就乱了。

真正要抓住的是：this 不是在函数定义时固定死的，它和函数是怎么被调用的关系更大。

为什么 this 容易让人误会

平时看代码时，我们习惯根据书写位置理解语义。

例如一个函数写在对象里，直觉上就会觉得它里的 this 应该指向这个对象。但 JavaScript 并不是总按“写在哪里”来决定 this，而是更看“怎么调用”。

这也是为什么同一个函数，换一种调用方式，this 就可能变。

事件处理里也很容易踩 this

前端开发里常见的一类误区，发生在 DOM 事件回调中。

例如有人以为回调里的 this 一定是外层组件实例，结果实际上它可能是触发事件的元素，或者在某些封装里根本不是你期待的值。

也正因为这样，很多现代前端代码会倾向于少依赖隐式 this，而是显式使用参数、闭包或实例引用。

箭头函数为什么能缓解一部分困扰

箭头函数的一个重要特点，是它没有自己的 this，而是继承外层作用域的 this。

不过箭头函数也不是万能的。它因为没有自己的 this，所以并不适合所有需要动态绑定上下文的场景。

call、apply、bind 本质上是在控制调用上下文

这三个方法总被一起讲，本质上都和手动指定 this 有关。

这意味着你可以不改变函数定义位置，只改变它执行时绑定的上下文。

在一些工具函数、数组借用方法、老代码兼容场景里，这类写法还挺常见。

真实项目里最稳的做法，往往是少制造模糊上下文

我后来对 this 的态度越来越务实：理解它很重要，但写代码时要尽量少依赖不清楚的 this。

例如：

  • 回调里优先用箭头函数或显式参数
  • 组件方法里明确调用入口
  • 工具函数尽量做成纯函数

这样一来，就算你懂 this 的规则，也不用天天和它较劲。

JavaScript 的灵活性有时就是这样，它给了你很多可能，但项目维护更看重稳定。this 不是不能用，而是要知道什么时候它会帮你，什么时候它只会制造歧义。

this 真正让人难受的，是它经常在“看起来差不多”的代码里变化

例如同样是调用一个函数，写成对象方法调用、事件回调、定时器回调，或者把方法先取出来再执行，this 结果就可能完全不同。也正因为这种差异往往藏在调用方式里，而不是藏在函数体里，所以它特别容易造成误判。

很多人不是不知道 this 有规则，而是规则一旦进入真实项目语境，就不再像单独小例子那么直观。

在团队代码里，少制造模糊上下文通常更重要

我后来越来越少把 this 当成“必须灵活使用的能力”，而更倾向于把它当成一个需要谨慎对待的上下文机制。因为项目里更重要的通常不是写法能不能成立，而是后来的人能不能一眼看明白。

这也是为什么很多代码会偏向：

  • 用显式参数代替隐式上下文
  • 用箭头函数稳定回调里的外层引用
  • 让工具函数尽量保持纯粹

理解 this 当然必要，但真正成熟一点的写法，往往是在理解之后主动减少歧义。
