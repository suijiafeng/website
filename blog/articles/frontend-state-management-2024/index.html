前端状态管理分层：不是所有状态都该进全局 store

2024-02-23
前端基础React构建与模块化

前端状态管理最容易走向两个极端。

一种是所有状态都放组件里，兄弟组件一通信就开始 props drilling；另一种是所有状态都丢进全局 store，结果页面输入框、弹窗开关、接口缓存、登录用户、筛选条件全混在一起。项目越大，状态越像一团线。

我以前很喜欢“统一状态管理”这个说法。后来做后台系统多了才发现，统一不等于全局。真正重要的不是选 Redux、Zustand 还是 Pinia，而是先分清状态属于哪一类。

状态至少分四类

这四类状态的生命周期完全不同。

弹窗开关离开页面就没意义；接口数据需要缓存和重新验证；筛选条件可能要支持分享链接和刷新恢复；登录用户则影响整个应用。把它们都塞进一个 store，只会让边界变模糊。

本地状态就近放

如果一个状态只影响一个组件或一小块区域，就近放。

这个弹窗状态没有必要进全局 store。它的生命周期和按钮绑定，放远了反而增加理解成本。

状态提升也要谨慎。只有多个组件确实需要共享同一份状态时，才提升到最近公共父级。不要因为“以后可能用到”提前全局化。

我在 review 代码时经常问一句：这个状态如果放到全局，谁负责清理？如果回答不上来，通常说明它不该全局。

服务端状态不要手写成普通 state

接口数据不是普通 UI 状态。

它至少包含：

  • 数据本身
  • loading
  • error
  • 过期时间
  • 请求去重
  • 重新拉取
  • 分页和增量加载
  • 乐观更新

成熟项目里，我更倾向于把服务端状态交给 React Query、SWR 或框架自带的数据层。它们解决的是“接口数据作为缓存资源”的问题，不只是少写几个 useState。

URL 状态应该放进 URL

搜索页、列表页、报表页的筛选条件，很多时候应该进 URL。

这样有几个好处：

  • 刷新页面后状态不丢
  • 链接可以分享
  • 浏览器前进后退符合预期
  • 服务端渲染更容易拿到参数

如果筛选条件只存在内存 store，用户刷新后就回到默认值；复制链接给同事，对方看到的是另一份结果。这对业务系统很不友好。

当然，不是所有状态都要进 URL。弹窗开关、输入中的临时草稿、未提交表单就不适合。判断标准很简单：这个状态是否属于页面地址的一部分？别人拿到这个地址，是否应该看到同样视图？

全局状态要少而稳定

真正适合全局的状态应该少，而且相对稳定。

典型例子：

  • 当前登录用户
  • 权限信息
  • 主题模式
  • 语言
  • 全局通知配置

这些状态的特点是：很多地方要读，变化频率不高，生命周期接近整个应用。

全局 store 里最怕放高频变化状态，比如输入框值、鼠标位置、滚动位置。它们一变就可能带动大量订阅者更新。即使用了选择器，也会增加调试复杂度。

状态重复是很多 bug 的根源

另一个常见问题是同一份状态存两份。

比如 URL 里有 page=2，store 里也有 page: 2，组件本地还有一个 currentPage。三份状态只要有一份没同步，就会出现页面显示和接口参数不一致。

我更喜欢明确“单一来源”：

  • URL 能表达的筛选条件，以 URL 为准
  • 服务端数据，以 query cache 为准
  • 表单输入，以表单库或字段状态为准
  • 全局用户，以 auth store 为准

其他地方需要时派生，不要复制。

这种派生值没必要再存一份 isAdmin，除非计算成本真的很高。

状态管理的核心不是把状态放到一个“高级工具”里，而是让状态的位置、生命周期和使用范围匹配。

工具选型当然重要，但分层比工具更重要。状态边界清楚了，用什么库都不至于太乱；边界不清楚，再好的库也会变成全局变量仓库。
