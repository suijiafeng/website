异步我是被几个线上 bug 教明白的：竞态、白屏和静默失败

2024-09-07
前端基础

有很长一段时间，我以为自己异步写得挺好——await fetch()、套个 try/catch、错误打个日志，齐活。回调地狱、Promise 链、async/await 是怎么一步步演进的，这些我都讲得出来。真正让我发现自己只是“语法会了”的，是几个上线之后才暴露的问题。

第一个：搜索框为什么老是显示上一次的结果

最早翻车的是一个带实时搜索的输入框。用户输入，我就发请求、回来就渲染，逻辑直白得不能再直白。测试也没问题。

但偶尔会出现一个诡异现象：用户明明搜的是 next，列表里却是 react 的结果。盯了很久才反应过来——这是竞态。用户先打了 react，又很快改成 next，两个请求都发出去了，偏偏 react 那个回得更晚，于是它的结果覆盖了 next 的。

不过 abort 也不是万能的。有一次我把取消逻辑加上之后，监控里突然冒出一大堆 AbortError 上报，差点以为出了新 bug。后来才想明白：取消本身就是预期行为，我却把它当成真错误上报了。所以归一错误的时候，得显式把它摘出去——这也是为什么上面 catch 里要先判 error.name === 'AbortError'。后端那边也有坑：浏览器虽然断开了连接，但请求可能已经打到服务端、数据库写操作照样执行了，对于非幂等的接口（比如 POST 提交），客户端 abort 并不等于服务端没做事。我现在的原则是：abort 只用在“纯读、可重复发”的 GET 上，写操作宁可在前端做按钮置灰 + 请求去重，也不轻易取消。

如果不想自己维护 controller，还有一种更声明式的写法是用“最新请求 id”来兜底，即使旧请求回来了也直接丢弃，适合那些拿不到 signal 的老接口：

第二个：一个不重要的接口，白了整个首页

第二个坑更让我长记性。有个工作台首页要同时拉好几块数据：用户信息、待办、通知、还有一块“推荐内容”。我顺手用了 Promise.all，干净利落：

问题是 Promise.all 只要有一个 reject，整体就 reject。某天推荐服务抖了一下，结果是——整个首页白屏。一个最不重要的模块，把用户信息和待办这些核心内容一起拖下了水。

我这才分清楚两种场景。强依赖、缺一不可的数据（比如订单详情里的订单、商品、支付信息），用 Promise.all 是对的，少一个这页就没意义。但首页这种“各模块相互独立、坏一个不该影响其他”的，应该用 Promise.allSettled，让每块自己决定成功还是降级：

现在我做聚合请求，会先问一句：这一组里有没有“可以坏、坏了页面还能用”的成员？有，就别用 all 把它们绑死在一起。

这件事还有个被忽略的尾巴：Promise.all 早退（fast-fail）只是“不再等”，并不会去取消另外那几个还在飞的请求。换句话说推荐服务挂了那次，用户信息、待办其实照样请求完了，只是结果被丢进了垃圾桶。如果这些请求带副作用——比如某个接口会埋点、会扣配额——你以为 all reject 了就万事大吉，实际它们都偷偷执行完了。要真正连带取消，得自己用一个共享的 AbortController：

第三个：批量导入说成功了，其实一半没存

还有一个特别隐蔽的。做一个配置批量导入功能，我循环保存每一条：

测试小数据量一切正常，上线后用户反馈“导入完成了，但数据只进去一部分”。原因是 forEach 根本不会等里面的 await——它一口气把所有回调同步跑完就返回了，showToast 在任何一条真正保存完之前就弹了出来，中途某条失败了我也完全不知道。

往底层看一眼就更清楚了。async 函数的返回值永远是一个 Promise，函数体执行到第一个 await 就会“挂起并立刻 return 一个 pending 的 Promise”给调用方。forEach 的实现大致是 for (i...) callback(item)，它拿到的就是这堆 pending 的 Promise，但它的签名里压根没有“收集返回值”这一说，更别提 await 了——它把返回值直接扔掉。于是真实的执行顺序是：同步地把 N 个 saveItem 都发起（停在各自第一个 await 上），forEach 返回，showToast 执行，然后这帮异步任务才在微任务/宏任务队列里陆续完成。失败的那几条 reject，没人接，就变成 unhandledrejection 飘走了。

更阴险的是 .map(async ...) 不带 Promise.all 收口的写法——它至少返回了 Promise 数组，看起来“好像处理了”，但只要你没去 await 那个数组，行为和 forEach 是一模一样的。我后来在 ESLint 里直接开了 no-floating-promises（TypeScript 项目用 @typescript-eslint/no-floating-promises），让“漏掉的 await”在编译期就报红，比上线后靠用户反馈强太多了。

顺便说个 fetch 的反直觉点

上面几个坑还逼我认真对待错误处理。fetch 有个很坑新人的设定：只要服务器有响应，哪怕是 404、500，Promise 也是 fulfilled 的，只有网络断了、跨域失败、请求被取消才会 reject。所以光 await fetch() 再 .json() 是不够的，必须自己看 response.ok，并且把各种来源的错误归一成同一个结构，上层才能用同一套 toast 和上报去处理。

串行太慢、全并行又把后端打挂：限流的中间地带

for...of 和 Promise.all 是两个极端。那次批量导入修好之后没多久又来一桩：用户一次性导一千多条，我老实用 for...of 串行，结果跑了快两分钟，用户以为卡死了狂点刷新。换成 Promise.all 一把梭，一千个请求同时怼出去，后端的连接池直接被打满，DBA 在群里 @我。

顺手补一个 event loop 的认知：await 到底让出了什么

排查上面那些时序问题，绕不开 event loop。有个对比能一秒看清宏任务和微任务的差别：

两个反直觉点我吃过亏。其一，async 函数在第一个 await 之前是同步跑的，所以别以为把代码塞进 async 函数就自动“异步”了、就不卡主线程了——一段重计算放在 await 之前，照样卡。其二，await 后面那一截是微任务，会插在当前宏任务尾巴、下一个 setTimeout 之前执行；这意味着如果你在一个紧凑的循环里疯狂产出微任务（比如递归 await Promise.resolve()），UI 渲染（属于宏任务之间的间隙）可能一直得不到机会，页面看着就像“假死”。当年我有个进度条死活不动，就是被一坨连续微任务把渲染时机挤没了，往循环里塞一个 await new Promise(r => setTimeout(r)) 主动让出一个宏任务，进度条立刻活了。

我现在写异步前会先问自己几句

这几个 bug 之后，写异步对我来说不再是“能不能 await 出来”，而是几个习惯性的自问：这几个任务之间有没有依赖，决定串行还是并行；其中有没有可以坏掉、坏了也不影响整体的，决定 all 还是 allSettled；结果会不会过期被覆盖，决定要不要取消；最后，错误有没有被明确地往上抛、而不是被我悄悄咽下去。

回调、Promise、async/await 解决的只是“怎么把异步写顺”；竞态、降级、取消、错误归一，解决的才是“线上会不会出事”。前者让代码能跑，后者才让它经得起真实用户折腾。
