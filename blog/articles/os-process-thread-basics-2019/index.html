进程和线程：写前端也绕不开的操作系统基础

2019-01-09
杂项

进程和线程是计算机基础里很常见的面试题。

刚做前端时，可能觉得这些离页面很远。可真到项目里，浏览器多进程、Node 单线程、Web Worker、页面卡顿、服务端并发，这些问题都会把你拉回到操作系统基础上。

理解进程和线程，不是为了背定义，而是为了知道程序到底怎么运行。

我对这套概念从"会背"到"真懂"，是被几个具体问题逼出来的：为什么 Chrome 开几个标签页内存就吃掉好几个 G？为什么一段死循环能把整个页面卡死、连关闭按钮都点不动？为什么后端同事说"加机器没用，得加进程数"？这些问题背后都是进程线程的运行模型。下面把我陆陆续续想明白的东西串起来讲。

什么是进程

进程可以理解为正在运行的程序实例。

打开一个浏览器、启动一个 Node 服务、运行一个构建命令，操作系统都会为它分配资源。进程有自己的内存空间、文件句柄、环境变量等。

不同进程之间默认是隔离的。一个进程崩了，不应该直接把另一个进程的内存改坏。

浏览器里，一个标签页、渲染进程、插件进程、GPU 进程这些概念经常被提到，本质上都是为了隔离和稳定。

Chrome 这套多进程架构，平时用感受不深，出问题时就懂它的好。早年单进程浏览器，一个标签页的网页崩了，整个浏览器跟着完蛋，你开的几十个标签页全没了。Chrome 把每个标签页（粗略说）放进独立的渲染进程，一个页面崩了只是那个标签变成"哎呀崩溃了"，别的标签照常用——这就是进程隔离的价值。代价就是费内存，每个进程都要独立的一份内存空间和运行环境，所以 Chrome 吃内存是出了名的，这不是 bug，是它拿内存换稳定性和安全性的设计取舍。

安全上也是同理。渲染进程被沙箱关起来，权限很低，不能直接读你硬盘、不能随便发起任意系统调用，真正要访问文件、网络这些能力得通过 IPC 去求主进程（Browser 进程）。这样即使某个网页利用漏洞攻破了渲染进程，也被困在沙箱里，伤不到系统。

什么是线程

线程是进程里的执行单元。

一个进程可以有多个线程，它们共享进程的内存空间，但各自有执行栈。

共享内存带来方便，也带来风险。多个线程同时读写同一份数据，就可能出现竞争问题。

这也是为什么多线程编程里经常要考虑锁、同步、原子操作。

进程和线程的核心区别就在这"共享"二字上。进程之间内存隔离，想通信得靠 IPC（管道、共享内存、消息等），开销大但安全；同一进程内的线程共享内存，通信方便（改个共享变量就行）、创建也比进程轻，代价是要自己处理数据竞争。

数据竞争听起来抽象，举个最经典的例子就懂了：两个线程同时对一个变量 count 做 count++。这一行看着是原子的，其实是"读出 count、加一、写回"三步。两个线程交错执行，可能都读到 5、都加成 6、都写回 6，加了两次结果只涨了 1。这种 bug 还特别恶心，它依赖线程调度的时序，时有时无，本地复现不出来，线上偶尔抽风。所以多线程代码要用锁把这种临界区保护起来，但锁用多了又有死锁和性能问题。前端写 JS 基本不用直面这些，但理解了它，你才会明白为什么 JS 把自己设计成单线程是一种"用简单换安全"的选择——根本不让你共享内存，竞争问题从源头上就没了。

并发和并行

并发是看起来同时处理多个任务。

并行是真正同时执行多个任务。

单核 CPU 上也可以并发，操作系统通过时间片切换，让多个任务轮流执行。多核 CPU 才能让多个任务真正并行执行。

JavaScript 在浏览器主线程里一次只能执行一段 JS，但浏览器整体不是单线程。网络、定时器、渲染、事件处理背后都有不同模块协作。

我自己记这两个词的方式：并发是"一个人同时招呼好几桌客人"——他其实一次只服务一桌，靠快速来回切换让每桌都觉得没被晾着；并行是"好几个服务员各管各的桌"，是真的同时在干。单核 CPU 靠时间片切换实现并发，看着像同时跑，说白了还是轮流；多核才能真并行。

这个区分对判断性能瓶颈很关键。如果你的任务是 I/O 密集型（大量等网络、等磁盘，CPU 大部分时间在闲着等），那并发模型就够用了，开一堆线程或者用事件循环让 CPU 在等待的间隙去干别的活，效率很高——这正是 Node 擅长的场景。但如果是 CPU 密集型（比如大量计算、图片处理），单靠并发没用，因为 CPU 一直满负荷，切来切去也变不出更多算力，这时候才真正需要多核并行。搞混这两者，会出现"我明明加了异步/多线程，怎么还是慢"的困惑。

上下文切换

CPU 从一个线程切到另一个线程，需要保存当前状态、恢复另一个线程状态，这叫上下文切换。

切换不是免费的。线程太多时，CPU 可能花很多时间在切换上，真正执行任务的时间反而变少。

这也是为什么服务端并发不是"线程越多越好"。

上下文切换为什么有成本？因为 CPU 切换线程时要把当前线程的寄存器、程序计数器、栈指针这些"现场"保存起来，再加载下一个线程的现场，还可能伴随 CPU 缓存失效、TLB 刷新。单次切换是微秒级，听着不多，但线程开成几千个、每秒切换几万次，这部分开销就吃掉可观的 CPU，真正干活的时间反而被挤占。

这就解释了后端那句"加机器不如调进程/线程数"是什么意思——不是越多越好，而是要匹配 CPU 核数。一个 8 核机器，开几千个忙碌线程纯属互相抢 CPU、疯狂切换；CPU 密集场景下，线程数接近核数往往最优。这也是为什么后来流行协程（goroutine、async/await 这类）：协程的切换由程序在用户态自己调度，不用陷入内核，比线程切换轻量得多，能用很少的线程撑起海量并发的 I/O 任务。Node 的事件循环、Go 的 goroutine，走的都是这个思路——别让操作系统替你频繁切换重量级线程。

JavaScript 为什么说是单线程

通常说 JavaScript 是单线程，指的是 JS 执行主线程。

这样的代码会卡住页面，因为主线程被占满了，用户点击、渲染更新都没机会执行。

异步请求不会阻塞等待，但回调最终还是要回到主线程执行。重计算任务如果放在主线程，页面仍然会卡。

关键要理解：主线程不只是跑 JS，渲染（样式计算、布局、绘制）和响应用户交互也都挤在这条线程上，它们和你的 JS 是抢同一份时间的。所以一段同步执行超过几十毫秒的 JS，期间浏览器就没法重绘、没法响应点击，表现就是页面"假死"。我真遇到过：前端做一个上万行的本地数据排序加格式化，全在主线程同步跑，结果一点按钮页面卡住一两秒，鼠标都转圈。

理解了这点，优化方向就清楚了。要么把大计算切成小块，用 requestIdleCallback 或者 setTimeout(fn, 0) 分批做，每做一块就把主线程让出来给渲染和交互喘口气；要么把计算整个挪走，这就引出了下面的 Web Worker。判断一个任务该不该担心卡顿，就看它会不会长时间霸占主线程——网络请求不会（它在后台等，回调才占主线程一下下），纯计算会。

Web Worker 的意义

Web Worker 可以把一部分计算挪到另一个线程：

Worker 不能直接操作 DOM，但适合处理大文件解析、图片压缩、复杂计算。

Worker 跑在另一条线程上，所以它的计算不会卡住主线程的渲染和交互，前面那个排序卡顿的问题，丢进 Worker 算完再 postMessage 回来更新视图就解决了。要注意几个真实的限制：Worker 和主线程不共享内存，它们之间靠消息传递通信，数据是结构化克隆（拷贝）过去的，传一个超大对象本身也有序列化开销，别指望零成本；Worker 里拿不到 document、window，所以纯粹是干算的，算完把结果传回主线程由主线程更新 DOM。

实际用下来，Worker 适合"算得久、又不需要碰 DOM"的活：大 JSON/CSV 解析、图像处理、加解密、复杂的数据聚合。不值得为了几毫秒的小计算专门开 Worker，开 Worker 和通信本身有成本。这正是进程线程基础在前端的落地——你得先理解"主线程是稀缺资源、共享内存有代价"，才知道什么时候该把活儿挪到另一条线程、挪过去要付出什么。

Node 的单线程误解

Node 的 JavaScript 执行也是单线程，但 Node 底层有线程池处理文件系统、DNS、加密等任务。

所以"Node 是单线程"不能简单理解成"Node 什么都只能一个一个做"。它的事件循环让大量 I/O 任务可以高效处理，但 CPU 密集型任务仍然会阻塞主线程。

这点我在一个 Node 接口服务上栽过跟头。服务平时跑得好好的，QPS 也不低，直到有个接口要在请求里做一段同步的密集计算（当时图省事用了同步加密）。结果只要这个接口被调到，整个服务的所有请求都卡住了——因为那段 CPU 计算把唯一的 JS 主线程占满，事件循环根本没机会去处理其他请求的回调。这就是 Node 最经典的坑：一个慢的同步操作，拖垮的不是一个请求，是整个进程的所有请求。

应对办法也对应着前面这些概念。利用多核，就用 Node 的 cluster 模块或 PM2 起多个进程，每个进程一条事件循环，正好把多个 CPU 核吃满（这是多进程并行）。单个进程里要做重计算，就别在请求处理里同步跑，挪到 worker 线程或者干脆拆成独立的计算服务。还有个最朴素的原则：能用异步 API 就别用同步 API，fs.readFileSync 这种 Sync 结尾的在请求处理路径里基本是禁用的，它会同步阻塞事件循环。把"主线程很宝贵、别让它干等或死算"这个意识带到 Node 里，就能躲掉一大半性能事故。

进程是资源分配单位，线程是执行单位。多进程更隔离，多线程共享内存但更容易有并发问题。

前端面试问这些，不是让你写操作系统，而是让你理解浏览器、Node、Web Worker、页面卡顿背后的运行模型。知道程序怎么跑，才能更好判断性能问题在哪里。
