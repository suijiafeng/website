事件循环到底在忙什么：为什么同步代码后面还有一堆异步顺序问题

2021-05-20
前端基础

JavaScript 的事件循环是一个特别典型的话题。

大家都知道它重要，也知道前端里有同步和异步，但一旦遇到 setTimeout、Promise、DOM 事件、接口回调混在一起时，执行顺序还是很容易判断错。

原因通常不是某个 API 太难，而是没有建立一套稳定的执行顺序理解。

我自己也是在踩了几次坑之后才慢慢把这套模型理顺的。早期写业务的时候，我经常凭"感觉"判断哪段先执行，结果一遇到 Promise 和 setTimeout 混在一起就抓瞎，只能靠加 console.log 一行行试。后来才意识到，事件循环其实是一个有明确规则的机制，把规则搞清楚，比记一百道输出题都管用。

JavaScript 为什么需要事件循环

浏览器里的 JavaScript 大多数时候是单线程执行的。

这意味着它同一时刻只能做一件事。如果一个操作会等待很久，比如网络请求、定时器、用户点击，脚本不可能一直卡在那里干等。

事件循环存在的意义，就是让这些异步任务在时机成熟后回到主线程继续执行，而不是阻塞整个页面。

这里有个我刚入行时一直没绕明白的点：JavaScript 是单线程，但浏览器不是。真正去发网络请求、跑定时器倒计时、监听用户输入的，是浏览器另外开的线程（或者说一堆 Web API）。这些活儿在主线程之外干，干完了把回调"塞"进任务队列，主线程闲下来的时候再回头取出来执行。所以严格说，单线程的是"执行 JS 代码"这件事，而不是整个浏览器。

先执行的是当前调用栈里的同步代码

这一点最基础，也最重要。

不管页面里后面挂了多少定时器、Promise 或点击事件，JavaScript 运行时首先会把当前调用栈里的同步代码执行完。

我喜欢用"调用栈"这个词来想这件事。当前所有同步代码都是在调用栈里一层层压进去、执行完再弹出来的，只有当整个调用栈彻底清空（也就是这一轮同步代码全跑完），事件循环才会去任务队列里捞下一个任务。换句话说，异步回调永远抢不到同步代码的执行权，它只能等。

“0 毫秒” 不等于立刻执行

这是很多人第一次接触定时器时最容易误解的地方。

setTimeout(fn, 0) 的意思不是马上执行，而是“最早在当前同步代码结束后，把这个回调放到后续可执行队列里”。

所以只要同步代码还没跑完，它就不可能先执行。

理解这一点后，很多“为什么 0 毫秒不是最先打印”的困惑就会消失。

还有个更隐蔽的点：就算同步代码已经跑完，setTimeout(fn, 0) 也未必真的"立刻"执行。浏览器对定时器有最小延迟限制，HTML 规范里嵌套层级超过 5 层后会被钳制到至少 4ms。所以靠 setTimeout(fn, 0) 想做高频精确调度是不靠谱的，我后来做动画相关的东西，宁可用 requestAnimationFrame，把节奏交给浏览器的渲染时机，而不是赌定时器的精度。

我还踩过一个相关的坑：页面切到后台标签页时，浏览器会把定时器的频率压得很低（很多浏览器钳制到 1 秒一次甚至更慢）。当时做了个轮询，用户切到别的标签页回来发现数据"卡住"了，查了半天才发现是后台节流。后来对实时性要求高的轮询，我改成了页面 visibilitychange 时主动刷新一次，而不是傻等定时器。

Promise 回调为什么常常比定时器更早

实际开发里另一个常见现象是：明明 Promise 写在后面，结果它的回调比 setTimeout 更早执行。

这背后是不同类型任务调度优先级的问题。对于前端日常理解来说，至少要知道一点：并不是所有异步任务都在同一个队列里排队，Promise 的后续回调通常会比普通定时器更早得到处理机会。

具体一点说，异步任务分两类：宏任务（macrotask）和微任务（microtask）。常见归类我列一下，省得每次都查：

  • 宏任务：setTimeout、setInterval、setImmediate（IE/Node）、MessageChannel、requestAnimationFrame（严格说是渲染前的特殊队列，但调度上按“下一帧的宏任务”理解不会错）、DOM 事件回调、<script> 整体。
  • 微任务：Promise.then/catch/finally、queueMicrotask、MutationObserver、await 之后的代码。

关键规则是：每执行完一个宏任务，事件循环会把当前微任务队列里的任务全部清空，然后才去取下一个宏任务。所以微任务的"插队"能力很强，会在下一个宏任务之前全部执行完。

一轮事件循环的完整顺序在脑子里大致是这样：取一个宏任务执行（最开始那个宏任务就是整段同步脚本）→ 执行过程中产生的微任务进微任务队列 → 当前宏任务一执行完，立刻把微任务队列全部清空（清空过程中新产生的微任务也要在这一轮接着清，所以前面那个 Promise.resolve().then(loop) 才会饿死宏任务）→ 微任务清空后，浏览器可能进行一次渲染（重新计算样式、布局、绘制）→ 然后才回头取下一个宏任务。记住“宏任务之间夹着微任务清空和可能的渲染”这条主线，绝大多数输出题都能推出来。

真正难查的 bug，是时机预期错位

很多前端 bug 既不是接口失败也不是数据丢失，而是对执行时机判断错了：以为状态更新后下一行就拿得到新值、以为定时器一定在某个回调前执行、以为 DOM 已经更新其实还没渲染。这类问题表面没有语法错误、偶尔还能正常工作，所以特别隐蔽。

我印象最深的一个：给表单做提交，提交后要读 DOM 上某元素的最新高度去做滚动定位，我直接在改完数据的下一行就读，结果永远是旧值。折腾半天才明白——框架更新 DOM 也是异步的（要等微任务或下一帧），我那行同步代码跑的时候 DOM 压根没变。后来改成在框架“更新后”钩子或等下一帧里再读就好了。一句话：改完数据不等于 DOM 已经变好，读 DOM 要等浏览器把这一轮处理完。

还有个常见的“loading 闪一下”也是同源问题：

接口太快，loading 从 true 到 false 几乎在同一帧内完成，中间没给渲染留时间，用户看到的就是一个闪一下的转圈。解法是给 loading 加最小展示时长、或快速返回时干脆不展示——本质都是在和渲染时机做妥协。

这些都说明，事件循环不是面试题里的摆设。接口回调、输入响应、定时轮询、Promise 链、动画调度，写异步就躲不开它。我现在排 React 里“状态更新后立刻读值还是旧的”这类问题，第一反应已经不是怀疑框架 bug，而是先问“这一行执行时事件循环走到哪了”。起点永远是那句最朴素的话：先把当前同步代码跑完，再清微任务，再到下一个宏任务。这条顺序感稳了，后面学框架调度、状态批处理、更复杂的异步控制都会轻松很多。

上一篇防抖和节流怎么选：不是背定义，而是先看事件有多频繁下一篇闭包为什么既好用又容易出坑：它不是高深概念，而是作用域结果
