刚开始用 Vue3 时，最容易踩的几个坑

2023-06-07
Vue前端基础

Vue3 已经很成熟，但从 Vue2 或 Options API 迁移过来时，还是很容易写出一些“能跑但不太对”的代码。

很多坑不是语法不会，而是对组合式 API 和响应式规则理解不够清楚。Vue3 的写法更灵活，也意味着组件逻辑的边界更需要开发者自己管理。

我从 Vue2 迁到 Vue3 时，最大的不适应不是 .value，而是逻辑组织方式变了。Options API 会把 data、methods、watch 分栏放好；Composition API 更自由，但自由也意味着你可以把请求、表单、弹窗、权限全写进一个 setup 里。写得顺手不代表边界清楚。

基本类型不要直接用 reactive

reactive 适合对象、数组、Map、Set 这类引用类型。如果是数字、字符串、布尔值，应该使用 ref。

不要这样写：

基本类型不能被 reactive 正常包装。一个简单判断是：单个值用 ref，结构化对象用 reactive。当然，对象也可以用 ref，这取决于你希望整体替换对象，还是更常修改对象内部字段。

如果对象需要整体替换，比如接口返回的详情对象，我更倾向用 ref<User | null>(null)。如果是表单这种长期修改内部字段的对象，用 reactive 会更顺。不是 ref 和 reactive 谁更高级，而是看更新方式。

好的组合式函数应该职责明确，例如只处理请求、表单、分页、弹窗或权限中的一类问题。

我不太喜欢万能的 useTablePage。一开始它能帮你快速做列表，后来加权限、批量操作、导出、缓存、路由同步，参数会越来越多。组合式函数最好小而专注，可以组合使用，而不是变成另一个配置平台。

生命周期里注意清理副作用

组合式 API 让事件监听和定时器更容易散落在函数里，清理就更重要。

定时器、订阅、WebSocket、全局事件都应该在组件卸载时清理。否则页面切换后，旧逻辑可能还在运行。

还有一个迁移期常见问题：在模块顶层直接调用 Pinia store 或依赖组件上下文的 composable。很多 composable 只能在 setup 或已经创建 app 后调用，放到模块顶层可能在初始化顺序上出问题。能延后到函数内部，就不要过早执行。

模板里 ref 自动解包，不代表到处都自动

Vue 的自动解包很方便，但也容易让新人误判。模板里 count 可以直接用，脚本里要 count.value；reactive 对象里的 ref 会被解包，但数组、Map 里又不是同一套表现。遇到不确定的响应式问题，先把数据结构简化，不要把 ref、reactive、toRefs 混成一团。

我刚迁 Vue3 时，总想把 Options API 的写法平移过去：data 换成 ref，methods 挪成函数，watch 照旧堆。跑是能跑，但组件很快又乱成一团。

后来才慢慢调整过来：基本类型用 ref，复杂对象看更新方式选 reactive 或对象 ref；脚本里老老实实写 .value；解构前先想响应式会不会断；props 仍然保持单向数据流；能用 computed 表达的派生值，就别塞进 watch；组合式函数也要有边界，不要把所有逻辑都搬进一个大 composable。

Vue3 真正改变的不是几个 API 名字，而是组件逻辑的组织方式。这个习惯转过来以后，Vue3 才会变轻，而不是换一种写法继续写大组件。
