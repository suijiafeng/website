前端性能优化应该先看哪里：别一上来就想着大招

2021-12-10
前端基础

前端性能优化是一个很容易让人焦虑的话题。

因为它涉及的面太广：资源加载、接口响应、渲染卡顿、动画流畅度、打包体积、缓存策略，几乎每一层都能谈性能。也正因为这样，很多人一提优化就容易直接奔着“大招”去，反而忽略最基础的判断顺序。

性能问题首先要先定位，不要凭感觉改

页面慢有很多种慢：

  • 首屏白屏时间长
  • 内容出来了但交互卡
  • 列表滚动不流畅
  • 某个操作点击后响应慢

这些问题背后的原因很可能完全不同。如果不先区分是哪一类，再多优化动作也可能打偏。

例如首屏慢更可能和资源加载、构建产物、缓存策略有关；交互卡则可能和渲染、事件处理、DOM 更新频率有关。

我吃过一次很典型的亏。当时有个列表页用户反馈“卡”，我想当然以为是渲染问题，花了大半天把列表拆成虚拟滚动，结果上线后体感几乎没变。后来打开 Performance 面板录一段才发现，真正的瓶颈是每次滚动都同步调了一个排序函数，几千条数据排一遍，主线程被占满，渲染再快也没用。那次之后我养成了习惯：先录制再下结论，别让“看起来像”左右判断。

先看影响最大的地方

很多性能瓶颈不是细枝末节，而是几个比较明显的问题：

  • 脚本体积过大
  • 图片资源过重
  • 重复请求过多
  • 页面一次性渲染数据太多

这些问题带来的影响往往比某几个微优化大得多。

拿脚本体积来说，我接手过一个项目首屏 JS 打出来 2MB 多，光下载加解析就好几秒。后来用 rollup-plugin-visualizer（webpack 那边是 webpack-bundle-analyzer）出了个图，一看全是 moment 带着几十种语言包、还有整包引入的 lodash。处理起来其实不复杂：

想知道下载下来的代码到底有多少根本没跑到，不用猜，Chrome DevTools 自带的 Coverage 面板就能量。打开方式：DevTools 里按 Cmd/Ctrl+Shift+P 调出命令菜单，输入 Coverage、选 Show Coverage，点左上角圆形录制按钮刷新页面。跑完它会按文件列出每个 JS/CSS 的总字节数和「Unused Bytes」百分比，红色是未执行、蓝色是执行过的。我在一些项目首页上常看到首屏阶段某些 JS 未使用比例到 70%、80%——这些就是白下载、白解析的字节，是拆包和懒加载最该下手的地方。

光是这两处替换，加上把不影响首屏的路由组件改成动态 import() 懒加载，首屏包就瘦了一半还多。这种“大头”改一次，比抠十个小函数的收益都大。

体积砍下来之后，还可以在加载顺序上做文章。浏览器渲染首屏要走一条关键渲染路径：拿到 HTML→构建 DOM→解析 CSS 构建 CSSOM→合成渲染树→布局→绘制，CSS 和首屏要用的 JS 会阻塞这条路径上的渲染。能帮上忙的是几个资源提示，但各管各的、别混用：

我吃过的亏是 preload 用过了头——一股脑把十几个资源都标成 preload，等于谁都不优先，反而把真正该先到的字体和首屏图挤后面了。它是“纠正优先级”的工具，不是“调高所有优先级”。

所以我通常更推荐先处理大头，再考虑更细的技巧。否则很容易在局部花很多时间，却没明显改善体验。

用户感知比指标名字更重要

性能当然可以用很多指标衡量，但最终页面快不快，还是体现在用户感知上。

例如：

  • 页面是不是很久都没内容
  • 点击后有没有及时反馈
  • 输入时会不会掉帧
  • 切换页面有没有明显卡顿

如果一个优化动作不能改善这些体验，只是让某个数字看起来更漂亮，那它的价值要再判断。

这两年大家慢慢都在用 Core Web Vitals 那套指标，我觉得它好就好在每个指标都对应一种真实感受，而不是凭空造出来的数字：

  • LCP（最大内容绘制）对应“主要内容多久能看到”，Google 给的“良好”阈值是 2.5s 以内
  • FID（首次输入延迟）对应“第一次点了之后多久有反应”，良好阈值是 100ms 以内
  • CLS（累计布局偏移）对应“内容会不会突然乱跳”，良好阈值是 0.1 以内

这几个值不用死记，但记住量级有用：LCP 卡在两三秒以上、首次交互延迟上到一两百毫秒，用户是能明显感觉到的。它们衡量的也分别是不同阶段——LCP 关心首屏内容多久画出来，FID 关心页面可交互之后第一次点下去跟不跟手，这俩经常被混着说成“快慢”，其实是两码事：首屏内容出来了，不代表主线程腾出来能响应点击。

前端性能不只是下载速度

不少人一提性能，就只盯着资源体积。

资源大小当然重要，但它只是前端性能的一部分。页面真正展现给用户，还要经过解析、执行、渲染和交互——下载慢会卡、执行太重会卡、渲染不合理同样会卡，性能优化不能只盯网络层。

我遇到过一个很反直觉的例子：接口返回的 JSON 不到 100KB，下载几乎瞬间完成，但页面就是要卡个一两秒才出来。后来发现是拿到数据后在前端做了一堆嵌套循环去拼层级关系，几千条数据 O(n²) 地跑，主线程直接卡死。网络这一层一点问题都没有，问题全在 JS 执行上。把那段逻辑改成用 Map 建索引、一次遍历搞定后，卡顿立刻消失。

下载快不代表页面就快，解析、执行、渲染每一步都可能是瓶颈。

“少做事”通常比“更聪明地做事”更划算

性能优化里一个很朴素但很有效的原则是：能少做就少做。

例如：

  • 不必要的请求别发
  • 不必要的渲染别做
  • 不必要的监听别挂
  • 不必要的大资源别下

这类优化看起来不炫，但往往最稳定。因为它不是在原有复杂度上继续补救，而是直接减少了系统要处理的工作量。

最常见的“多做事”就是高频事件没节流。scroll、resize、input 这些一秒能触发几十上百次，回调里要是还干重活，主线程很快就顶不住。我现在写这类交互几乎是条件反射地包一层防抖或节流：

这些都不是什么高级技巧，但它们真正减少了运行时要处理的工作量，比事后补救扎实得多。

渲染层面同理，最常见的“多做事”是没必要的重排（reflow）。改了几何相关的属性——宽高、位置、字体大小，或者读取 offsetTop、offsetWidth 这类会触发同步布局的值——浏览器就得重新算一遍布局；只改颜色、背景这类不影响布局的，则只触发重绘（repaint），便宜得多。我栽过的典型坑是在循环里一边读 offsetWidth 一边改 style，读写交替会逼浏览器反复重算布局（layout thrashing），几百次循环能卡出明显掉帧。修法是把读和写分开批处理，或者改用 transform/opacity 做动画——这俩能走合成线程，根本不碰布局和重绘。

首屏、交互和长列表，是三类完全不同的问题

按用户感知去拆，前端性能至少能分出三类，解决方式完全不同，混在一起看只会得到一堆不痛不痒的微优化：

  • 首屏慢：更偏资源加载、构建产物、缓存和关键渲染路径
  • 交互慢：更偏事件处理、状态更新、同步计算和主线程占用
  • 长列表卡：更偏渲染数量、滚动处理和节点更新策略

具体到长列表，我踩过的最大的坑是“一次性把上万条数据全渲染成 DOM 节点”。哪怕数据已经在内存里了，浏览器创建和布局这么多节点本身就要花掉好几秒，滚动还持续掉帧。真正有效的做法是只渲染可视区域那一屏，也就是虚拟滚动：

实际项目里我一般不自己手写，vue-virtual-scroller、react-window 这类成熟库已经把边界情况处理得很好了。但原理一定要懂，不然遇到不定高度行、横向虚拟滚动这些场景就抓瞎。判断要不要上虚拟滚动也有个朴素标准：列表稳定就几十条，分页就够了；动辄成百上千还要平滑滚动，才值得引入这套复杂度。

把性能前移到日常和 CI

性能很少靠一次专项行动救回来，更多是靠日常判断慢慢维持。所以我做了一件成本很低但收益不错的事：给构建产物体积加了个监控，每次打包后看一眼主包大小，超阈值 CI 直接报警，谁不小心整包引了个大库提交时就能发现，不用等用户抱怨慢了才回头查。

最后还有一点：优化动作要对着真实用户路径来。后台系统里用户最常抱怨的可能不是首页多慢，而是筛选后表格更新太卡；内容站点里最关键的也许不是动效，而是文章首屏和图片。先搞清楚用户最常停在哪个页面、影响体验的到底是进入速度还是操作反馈、慢是偶发还是稳定复现，优化才不会花了时间却没改善用户真正感知到的慢。那次“虚拟滚动改完几乎没效果”的教训说到底就是这个——不录 Performance 不下结论，先定位再找大头，已经是我现在的肌肉记忆。
