Web Animations API 与 FLIP：列表重排动画为什么该用 transform 反演而不是直接改位置

2021-07-17
前端基础CSSJavaScript

这周做运营位卡片拖拽排序的动画，同一个视觉效果写了两版，Performance 面板录出来的结果差距大到值得记一篇。

效果很简单：用户拖动一张卡片松手后，其余卡片各自滑到新位置。第一版直接给卡片绝对定位，松手时改 top/left 加 transition，二十张卡片同时动的时候，六百块的安卓测试机上帧率掉到 20fps 出头，Performance 里紫色的 Layout 块一帧接一帧铺满时间线。

第二版换成 FLIP 思路，让 DOM 直接跳到新位置、再用 transform 做视觉上的位移动画，同一台机器稳定 55fps 以上，Layout 只在重排那一瞬间出现一次。

同一个“从 A 点移动到 B 点”，浏览器眼里是两种完全不同的工作量。top/left 属于布局属性，每一帧的变化都要走完整的渲染流水线：重新计算布局、重绘、合成——而且一张卡片的位置变化可能牵连兄弟元素跟着重新布局，二十张卡片一起动就是二十份布局账单乘上每秒六十帧。

transform 不参与布局，主流浏览器会把做了 transform 动画的元素提升成独立的合成层，位移由合成器线程处理，主线程哪怕在忙着执行 JS，动画照样丝滑。opacity 同理，这两个是动画属性里的“白名单”。

道理团队里人人会背，但“元素要移动到一个由布局决定的新位置”这个场景里，怎么让 transform 去表达一段本质上是布局变化的位移，就是 FLIP 要解决的问题。先划一句边界：这篇讲的是 JS 驱动的动画，纯 CSS 的 transition/animation 声明式动画是另一套东西，这里只在对比时提到。

CSS transition 在列表重排场景下为什么失灵

先看第一版为什么被迫用 top/left。transition 的工作前提是：某个属性从值 A 连续变化到值 B，浏览器在两个值之间插值。这要求“旧位置”和“新位置”必须体现在同一个可过渡的 CSS 属性上。

绝对定位加 top/left 恰好满足——每张卡片的位置就是两个具体数值，改数值就有动画。所以性能最差的写法反而是最顺手的写法，这是这个场景最坑人的地方。

而正常文档流里的列表，卡片的位置是布局算出来的，不体现在任何一个具体属性上。排序变化的本质是 DOM 节点顺序变了，浏览器视角里这不是“属性从 A 变到 B”，而是“元素瞬间出现在了新位置”——没有中间状态，transition 没有可以插值的东西，元素直接瞬移。

删除和插入同理：被删元素后面的所有卡片集体瞬移补位，transition 全程沉默。flex 布局里改 order、grid 里改行列同样如此，只要位置变化是布局引擎算出来的，transition 就插不上手。

**transition 能处理“状态过渡”，处理不了“布局突变”。**要给布局突变加动画，就得自己把突变前后的位置差算出来，翻译成 transform 喂给浏览器。这个翻译过程就是 FLIP。

FLIP：First、Last、Invert、Play

FLIP 是 First、Last、Invert、Play 四个词的缩写，思路只有一句话：先让 DOM 瞬移到最终状态，再用 transform 把元素“骗”回旧位置，然后播放一段回到零点的动画。拆开是四步：

First：DOM 变化之前，记下每个元素当前的位置。

Last：执行 DOM 变化（排序、插入、删除），让浏览器同步布局，记下每个元素的新位置。

Invert：算出新旧位置的差值，给元素设置一个反向的 transform，把它在视觉上顶回旧位置。这一步完成后，DOM 已经在新位置，用户看到的还是旧画面——中间没有任何一帧闪动。

Play：把 transform 动画到 none，元素从旧位置平滑滑向它真正的新位置。

聪明的地方在于成本分布：布局的账只在 DOM 变化那一瞬间结一次，之后的每一帧都是纯 transform，全程合成器接管。用原生 JS 手推一遍，给一个列表做洗牌动画：

两个容易踩的细节。第一，getBoundingClientRect 会强制同步布局。First 阶段逐个读没问题（此时布局是干净的），但如果 Last 阶段边读位置边写样式，读一次、写一次、下一次读又要重算布局——经典的 layout thrashing，元素一多每帧几十毫秒就耗在反复布局上了。所以上面把“读所有 Last 位置”和“写所有 transform”拆成了两个独立的循环，先批量读、再批量写，整个过程只触发一次布局计算。

第二，Invert 之后必须保证浏览器“看到”反向 transform 的初始状态，再开始过渡。如果用 CSS transition 来做 Play 这一步，需要先设置 transform、强制一次同步布局（读一下 offsetHeight）、再加过渡类名，三步缺一不可，顺序错了就是瞬移，而且这段代码解释给别人听总要费一番口舌。

上面用 element.animate() 就没这个问题——起始帧和结束帧都在关键帧数组里声明清楚了，浏览器自己保证从第一帧开始播。这正是我这次顺势把 Web Animations API 引进来的直接原因。

位移之外，FLIP 同样能处理尺寸变化。卡片点开变成展开态、宽高都变了，直接过渡 width/height 是和 top/left 一样的布局属性陷阱；FLIP 的做法是把尺寸差换算成 scale——Invert 阶段设 transform: translate(dx, dy) scale(sx, sy)，其中 sx = first.width / last.width。要注意 transform-origin 得统一到左上角，不然位移和缩放的叠加会算错位置：

用 scale 模拟尺寸变化有个众所周知的副作用：子元素（文字、图片）会跟着被拉伸，展开动画期间文字有一瞬间是变形的。要完全规避得给子元素做反向 scale 补偿，成本翻倍。

我们的卡片展开动画实测拉伸不明显（尺寸变化不到 20%），就没做补偿——300 毫秒里 15% 的文字形变肉眼几乎捕捉不到，这种钱不值得花。变化幅度大的场景（缩略图放大成详情页）才需要认真处理。

顺带说一个发现：Vue 的 <transition-group> 的 move 动画，底层用的就是 FLIP。翻它的源码，updated 钩子里做的事和上面的手推版一模一样——记旧位置、拿新位置、算差值、设反向 transform、下一帧加 v-move 类名触发过渡。我们项目里简单的列表排序动画其实一直在无意识地享受 FLIP，这次是因为拖拽排序的动画要跟手势联动、<transition-group> 包不住，才需要手写。

知道它内部是 FLIP 之后，v-move 偶尔不生效的老问题也好解释了：元素上残留的行内 transform、或者 CSS 里 transition 属性被别的规则覆盖，都会打断那四步里的某一步。以前遇到这种问题只会挨个瞎试，现在能按步骤定位是断在 Invert 还是 Play。

element.animate()：命令式动画的正主

Web Animations API（下面简称 WAAPI）给每个元素提供了 animate() 方法，参数是关键帧数组和时间配置，语义上和 CSS 的 @keyframes + animation 完全对应，只是从声明式变成了命令式：

在 FLIP 这种起止值要用 JS 现算的场景里，WAAPI 相比“拼 CSS 字符串 + 切换类名 + 监听 transitionend”的老写法，优势非常实在：起始帧直接写在关键帧数组里，不需要先设置样式再强制布局；动画结束后默认自动移除效果，不会在元素上残留一堆行内 transform 等着手动清理；也不用再处理 transitionend 的老坑——属性值没变化时不触发、多个属性各触发一次、动画被打断时不触发，每一条都曾经让回调逻辑出过 bug。

**WAAPI 和 CSS 动画不是两套引擎，而是同一套动画模型的两个入口。**浏览器内部把 CSS animation/transition 也表示成同样的 Animation 对象，document.getAnimations() 能把页面上正在跑的动画全捞出来——包括纯 CSS 声明的那些。我拿它做过一个实用的调试小工具：

播放控制：Animation 对象才是真正的增量

animate() 的返回值是一个 Animation 对象，这是 WAAPI 相对 CSS 动画真正拉开差距的地方。CSS 动画的播放控制只有 animation-play-state 一个属性可用，暂停之外的需求——倒放、跳转进度、变速——都得靠 hack。Animation 对象直接给了完整的控制面：

其中 reverse() 在交互动画里特别好用。抽屉面板展开到一半用户又点了收起，老写法要么等展开动画放完再收（迟钝），要么瞬间切换（生硬），要么自己记录进度、算反向动画（麻烦且容易错）。

WAAPI 里一句 anim.reverse()，从当前帧原路返回，进度和速度都是对的。这周拖拽卡片的“拖出边界回弹”就是用它做的，代码量是老写法的三分之一。

要注意 finished 在动画被 cancel() 时会 reject 一个 AbortError。组件销毁时取消动画是常规操作，这个 Promise 不挂 catch 的话，控制台里全是未捕获的 rejection，还会惊动错误监控——我们的 Sentry 上周就收进来一批这种噪音。相比之下 onfinish 回调没有这个心智负担，不需要组合多个动画的简单场景，用回调反而省事。

composite：两段动画叠加而不是互相覆盖

animate() 的 options 里还有个 composite 参数，控制多个动画作用在同一属性上时怎么合成。默认值 replace，后启动的动画直接覆盖先前的——这在“用户连续快速触发同一个动画”时会出现跳变：第二次动画从关键帧声明的起始值重新开始，无视元素当前的实际位置，视觉上就是猛地闪一下再重播。

composite: 'add' 让新动画的效果叠加在旧动画之上。典型场景是卡片上“点一下弹跳一次”的反馈：用户连点三下，replace 模式下前两次被粗暴掐断；add 模式下三段弹跳叠加，视觉上是幅度更大的连续弹动，自然得多。

还有个 accumulate 模式，语义是累积——每段动画位移 10px，三段叠出 30px——和 add 的区别在 transform 这类列表值属性上才看得出来。这类叠加语义纯 CSS 动画至今没有对应写法，是命令式入口独有的能力。

不过这个参数我最终没敢用在生产上，原因在下一节。

Safari 的现实与降级

WAAPI 在 Chrome 和 Firefox 上已经成熟，核心的 element.animate()、播放控制、finished Promise 都可以放心用。Safari 是拖后腿的那个：14.1 之前只有残缺的部分实现，今年四月随 iOS 14.5 发布的 Safari 14.1 把大部分核心能力补齐了，animate()、getAnimations()、播放控制这些都能用。

但缺口还在：composite 合成模式 Safari 目前不支持，传了也当 replace 处理；部分 timing 细节的行为和 Chrome 有出入，我在 iOS 上就遇到过 fill: 'forwards' 配合 cancel() 时残留状态和 Chrome 不一致的情况。“主流可用、Safari 逐项验证”是我现在对 WAAPI 的定位，每用到一个新能力，先查支持表、再真机试一遍，不能想当然。

所以我们现在的策略分三层。核心路径（FLIP 列表动画）只用 animate() 加基本 timing 参数这个交集，这部分 Safari 14.1 是可靠的，上线前在 QA 的 iPhone 上真机过了一遍。

锦上添花的能力（composite 叠加）先不上，连点弹跳暂时退回“动画播放中就忽略新的点击”这个保守策略，等 Safari 跟进再说。

对还停留在 iOS 13 及以下的那部分用户——后台数据看大概还有 7% 的移动端流量——做特性检测降级：

社区还有个 web-animations-js 官方 polyfill，可以在老浏览器上补齐 API 本身。我们评估后没引：压缩后几十 KB，而降级路径用 transition 手写也就二十行；polyfill 是用 JS 逐帧驱动的，性能上拿不到原生实现走合成器的好处，等于花了体积买一个“API 写法统一”。

**动画是增强型体验，降级到“效果略糙但能动”比为了写法统一多背一个 polyfill 划算。**中后台系统的浏览器环境本来就以 Chrome 为主，这个决定做得不纠结。

还有一个跟兼容无关但必须提的克制点：transform 动画会把元素提升成合成层，层是占显存的。二十张卡片同时动、动画结束后层自动释放，没问题；但如果给长列表里几百个元素预先挂上 will-change: transform 之类的提示“备战”，层爆炸带来的内存开销反而会让低端机更卡。

合成层是动画期间的临时快车道，不是常驻配置，FLIP 这种“动的时候才有 transform”的模式天然符合这个原则，这也是它比“所有卡片永远绝对定位 + transform 定位”的方案更健康的原因之一。DevTools 的 Layers 面板可以直接看当前页面的合成层数量和内存占用，怀疑层太多的时候去数一数。

回到那两版代码

拖拽排序最后上线的是 FLIP + element.animate() 的版本。代码量其实比第一版 top/left 方案还少——不用维护绝对定位的坐标计算，列表回归正常文档流，响应式布局白捡。Performance 面板里那条曾经铺满 Layout 紫块的时间线，现在只剩排序瞬间的一根，后面全是合成器在干活，主线程闲着。

同一个“卡片移到新位置”，一种写法让浏览器每帧重排整个列表，另一种写法让浏览器只在开头算一次账、剩下的交给合成器抄近路。FLIP 本质上不是什么高深技巧，就是把“布局的事一次做完、动画的事全给 transform”这个原则，落实到“目标位置由布局决定”的场景里而已。那台六百块的安卓机现在滑得和我工位上的 MacBook 没什么区别，这篇的目的也就达到了。
