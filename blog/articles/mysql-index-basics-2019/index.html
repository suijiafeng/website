MySQL 索引基础：为什么加了索引，查询还是可能慢

2019-04-11
数据可视化与存储

前端虽然不直接写很多 SQL，但接口慢时，经常会听后端说“查库慢”“索引没走”。

面试里也常问索引。即使主要做前端，懂一点数据库索引，对理解接口性能、分页慢、搜索慢都有帮助。

我自己是被一个线上慢查询逼着学进去的。当时有个列表接口偶尔要五六秒才返回，前端被投诉。我以为是接口逻辑问题，查了半天没头绪，最后后端把那条 SQL 单独拿出来跑，加 EXPLAIN 一看，几十万行的表全表扫描。加了个合适的索引，查询从 5 秒降到 20 毫秒。那次我才意识到，很多看起来像"前端慢"的问题，根子在数据库怎么取数据。后面分享的内容，基本都是那段时间踩坑攒下来的。

顺便说一句，看一条 SQL 到底走没走索引、走的哪个索引，最直接的办法就是在前面加 EXPLAIN：

重点看几列：type（ref/range 通常不错，ALL 是全表扫描要警惕），key（实际用到的索引，为 NULL 说明没走索引），rows（预估扫描行数，越小越好）。这是排查慢查询最基本的工具，比凭感觉猜靠谱多了。

索引是什么

索引可以理解为数据库为了快速查找数据建立的目录。

没有索引时，查询可能要一行一行扫：

如果 email 上有索引，数据库可以更快定位到对应记录。

这个类比可以再具体一点：没索引就像在一本没有目录的书里找某个词，只能从第一页翻到最后一页；有索引就像查字典，先按拼音定位到大致位置，再翻几页就到了。区别在于全表扫描的耗时随数据量线性增长，几百行无所谓，几百万行就是灾难；而走索引（B+ 树）的查找次数大致随数据量对数增长，百万级和千万级的差距并不大。这就是为什么数据量小的时候加不加索引没感觉，一旦上量，差距是几个数量级的。

为什么常说 B+ 树

MySQL InnoDB 常用 B+ 树索引。

B+ 树适合范围查询，也能保持较低的树高。数据量很大时，查询仍然能通过较少次数的磁盘读取定位。

不需要把树结构画得很复杂，但要知道：索引不是哈希表那么简单，它既支持等值查询，也支持范围查询和排序优化。

为什么是 B+ 树而不是哈希或者普通二叉树，面试经常追问，理解了也确实有用。哈希索引等值查询很快，但它不保留顺序，没法做 between、>、order by 这类操作，遇到范围查询就退化成全表扫了。普通二叉树在最坏情况下（比如自增主键顺序插入）会退化成一条链表，树高失控。B+ 树是多叉的，一个节点能放很多键，所以即使几千万行数据，树高通常也就三四层——意味着一次查询最多三四次磁盘 IO 就能定位。而且 B+ 树只在叶子节点存数据，叶子之间还用链表串起来，范围查询时顺着叶子链表扫一段就行，特别顺。这几个特性凑一起，才让它成了关系型数据库索引的默认选择。

另外提醒一点，索引的有效性跟字段的区分度强相关。给一个只有"男/女"两个值的性别字段建索引基本没意义，因为一查就命中半张表，优化器干脆不走索引直接全表扫。区分度高的字段（比如用户 ID、邮箱、手机号）才适合建索引。

主键索引和二级索引

InnoDB 表数据按主键索引组织。

主键索引叶子节点存整行数据。

普通索引叶子节点通常存主键值，再通过主键查整行，这个过程叫回表。

例如：

如果 email 是普通索引，查到主键后可能还要回表拿 name。

回表的代价容易被低估。它意味着一次查询其实走了两棵树：先在 email 二级索引树上找到主键，再拿主键去主键索引树上找整行。单条查询多一次查找无所谓，但如果是范围查询命中了上万行，每行都回一次表，IO 就被放大成了上万次随机读，慢得很明显。我后来排查一个慢查询，EXPLAIN 看 type 是 range 看着挺正常，但就是慢，最后发现就是命中行太多、回表太频繁。优化器其实也知道回表贵，命中行数太多时它甚至会放弃索引直接全表扫，因为顺序读整表反而比海量随机回表更快——这也是"加了索引却没走"的一种常见原因。

覆盖索引

如果查询字段都在索引里，就不需要回表。

如果索引包含 email 和 id，就可能直接从索引拿到结果。

这叫覆盖索引。InnoDB 里二级索引的叶子节点本来就存了主键值，所以查 id 天然不用回表。如果业务上经常要根据 email 同时查出 name，也可以专门建一个把 name 带上的联合索引 (email, name)，让这个查询完全走索引、不回表。EXPLAIN 时 Extra 列出现 Using index，就说明这条查询命中了覆盖索引。

我用这招实际优化过一个统计接口：原来要 select count(*) 配合几个条件字段，回表回得很惨，把涉及的几个字段做成一个联合索引让它覆盖之后，查询直接在索引上完成，快了一个数量级。代价是这个索引占了额外空间，而且字段越多索引越大，所以覆盖索引也不能无脑往里塞字段，只覆盖高频查询真正需要的列。

这就是最左前缀原则。可以把联合索引 (status, created_at) 想象成先按 status 排序、status 相同再按 created_at 排序的一本电话簿。你知道姓（status）能直接定位，但只知道名（created_at）不知道姓，就只能整本翻——索引帮不上忙。

实际建联合索引时，字段顺序怎么排是个需要动脑子的事，排错了索引就白建。我的经验是把等值查询的字段放前面、范围查询的字段放后面。因为一旦在某个字段上用了范围条件（>、<、between、like 'x%'），它后面的字段就用不上索引排序了。举个例子，如果查询大多是 where status = 1 and created_at > ?，建 (status, created_at) 就对；要是建成 (created_at, status)，因为 created_at 是范围条件，status 那一段就利用不上了。这个顺序问题我吃过亏，索引建了查询还是慢，调换一下字段顺序立刻就好了。

模糊查询前缀 %：

这类查询通常很难利用普通索引。因为 B+ 树是按字段值从左往右排序的，like 'tom%' 这种前缀确定的还能用索引（相当于范围查找），但 %tom 连开头都不确定，索引没法定位，只能全表扫。所以做后缀模糊搜索、全文搜索这类需求，到一定量级就别硬用 like 了，该上 Elasticsearch 之类的搜索引擎。

or 也容易让索引失效。where a = 1 or b = 2，如果只有 a 有索引、b 没有，优化器可能放弃索引走全表扫。!=、not in、is not null 这些也经常用不上索引。这些规则不用死记，养成习惯：写完慢的查询就 EXPLAIN 一下，看 key 是不是 NULL、type 是不是 ALL，比背规则实在。

还有一个我反复见到的坑——分页深翻。limit 100000, 20 这种，MySQL 实际上要先扫描并丢弃前面十万行，再取 20 行，越往后翻越慢。优化办法是记住上一页最后一条的主键，下一页用 where id > 上次的id limit 20 代替大 offset，让索引直接定位起点，这就是常说的"游标分页"。前端做无限滚动列表时，配合这种翻页方式体验会好很多。

索引不是越多越好

索引会提升查询，但会增加写入成本。

插入、更新、删除数据时，索引也要维护。索引太多，写入会变慢，占用空间也会变大。

每多一个索引，就多一棵 B+ 树要维护。插入一行数据，所有相关索引树都得跟着插入并可能触发节点分裂；更新被索引的字段，对应索引也要改。我见过一张表为了应付各种零散查询建了十几个索引，写入性能被拖得很难看，而且其中好几个索引线上根本没查询用到——纯属负担。

所以索引要围绕真实查询场景设计。我的习惯是上线后定期看慢查询日志（开 slow_query_log），针对真正慢、真正高频的查询去补索引，而不是一上来就给每个字段都加。MySQL 5.7 之后还能查 sys.schema_unused_indexes 看哪些索引从来没被用过，定期清理掉这些僵尸索引，写入会轻快不少。

索引是数据库查询性能的基础，但不是加了就一定快。

面试问 B+ 树、联合索引、最左前缀、回表、索引失效，是因为这些问题都对应真实慢查询。前端不一定要调 SQL，但理解这些概念，和后端讨论接口性能时会更有效。
