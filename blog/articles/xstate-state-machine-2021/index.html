状态机思维管复杂交互：从 boolean 标志位爆炸到 XState 建模多步上传

2021-09-25
前端基础JavaScript组件与状态

先把这篇的判断标准摆在最前面，因为这比任何一个库的用法都重要：**当组件的行为取决于"多个布尔字段的组合"而不是任何单个字段本身时，就该考虑把这些布尔收敛成一个状态字段了。**反过来，如果每个布尔各管各的、互不牵连——一个控制弹窗开关、一个控制折叠面板——那它们就是安分的 UI 状态，几个 data 字段足够，谁在这时候引状态机库谁是给团队找麻烦。

这个标准是我最近重构素材中心的分片上传组件时磨出来的。那个组件有些年头了，跑了一年多，功能没大问题，但每次改它都心惊肉跳。打开一看 data：

六个布尔，理论上 64 种组合。业务上合法的状态其实只有七种：空闲、选择中、上传中、已暂停、失败、重试中、完成。剩下五十多种组合——比如 isUploading && isError && uploadFinished 同时为 true——在业务上根本不该存在，但代码层面没有任何东西阻止它们出现。

事实上它们就是会出现：八月有个 bug，用户在上传失败后点重试、重试请求还没回来又点了暂停，isRetrying 和 isPaused 同时为 true，界面上暂停按钮和重试中的 loading 一起转，后续所有分支判断全部错乱。修的方式是在暂停的 handler 里补一句 this.isRetrying = false——这类修法治标不治本，因为每加一个布尔，需要“记得重置”的地方是乘法增长的。

布尔组合爆炸的病根：状态是算出来的，不是声明出来的

回头看这六个布尔，它们其实都在试图回答同一个问题："组件现在处于什么阶段"。答案本该是七选一的枚举，却被拆成了六个独立开关，让每个事件处理函数自己去拨。于是"当前状态"变成了一个从布尔组合里推算出来的隐式概念，模板里到处是这种推算：

每个 v-if 都是一次对隐式状态的猜测，猜的人还得记住所有布尔之间的暗中约定。新需求来了——产品要加一个"上传前压缩"的阶段——就得再加一个 isCompressing，然后把所有现存的 v-if 全过一遍，看哪些要补上 && !isCompressing。改动成本随布尔数量指数上升，这就是标志位方案的天花板。

有限状态机把这件事倒过来：先声明清楚系统有哪几个状态、每个状态下响应哪些事件、事件把状态转移到哪里，非法组合在模型层面就不存在。"上传中"和"重试中"不可能同时成立，因为状态字段只有一个值。

先建模，再谈库：把上传流程画成状态图

重构的第一步不是装 XState，是拿一张纸把流程画出来。状态是名词，事件是动词，箭头是转移：

idle ──SELECT──▶ selecting ──CONFIRM──▶ uploading ──DONE──▶ success
                     │                    │    ▲
                  CANCEL                PAUSE  │RESUME
                     │                    ▼    │
                     ▼                  paused
                   idle
uploading ──FAIL──▶ failed ──RETRY──▶ uploading
failed ──CANCEL──▶ idle

画的过程中就暴露了两个原来靠布尔糊过去的模糊地带。第一个：暂停之后还能不能失败？原实现里可以——分片请求是并发的，点暂停时在途的请求失败会把 isError 置 true，出现“又暂停又失败”的叠加态。画图时被迫做决定：暂停态收到 FAIL 事件一律忽略，等恢复后重新校验分片。

第二个：重试算不算独立状态？原来有个 isRetrying，画图时发现“重试中”和“上传中”对用户、对逻辑都没有区别，就是从 failed 转回 uploading 而已，这个布尔纯属冗余。建模的价值一半在模型本身，一半在建模过程逼你把没想清楚的转移想清楚。

这张图后来在需求评审时直接派上了用场。产品问“断网之后恢复网络要自动续传吗”，我指着图问：自动续传就是 failed 状态自动发 RETRY，那用户手动点了取消之后网络恢复怎么办？三个人对着图讨论了五分钟就把边界敲定了。

**状态图是产品、QA、开发三方都读得懂的语言，这个沟通价值不比代码价值小。**QA 同事甚至照着图设计了用例——每条箭头一个用例，每个“状态收到图上没有的事件”一个反向用例，测试覆盖第一次有了明确的完备性标准。

XState v4 最小用法：createMachine 和 interpret

模型定了，落到代码。XState 是社区里最完整的状态机实现，v4 从 2018 年迭代到现在已经相当稳。核心就两个函数：createMachine 描述状态图，interpret 把静态的图变成一个可以接收事件的运行实例（文档里管它叫 service）：

这里要区分两层东西：**有限的“状态”（idle/uploading/…）放 states，无限取值的“数据”（进度百分比、文件对象、错误信息）放 context。**初学最容易犯的错是把进度也建成状态——进度是连续值，不是离散状态，硬塞进 states 就是灾难。

判断口径：影响“组件响应哪些事件”的是状态，只影响“界面显示什么内容”的是 context 数据。进度从 30% 涨到 60%，组件能干的事没有任何变化，所以它是数据；从 uploading 变成 paused，能响应的按钮立刻不同，所以它是状态。

那个八月的 bug 在新模型下从根上消失了：paused 状态的 on 里没有 RETRY，failed 状态的 on 里没有 PAUSE，乱点按钮发出的事件会被状态机静默忽略，界面不可能进入“又暂停又重试”的叠加态。不再是“记得在某处重置某个布尔”，而是“没画在图上的转移天然不会发生”。

另外提一句 XState 的可视化工具：把 machine 定义贴进官网的 visualizer，直接生成可交互的状态图，点事件按钮能看状态流转。我前面手画的那张图，评审后就是用它重新生成了一份贴进需求文档的。

守卫和动作：转移不只是换个名词

最小用法之外，这次实际用到的还有两个能力，值得展开说说。

第一个是守卫条件（guard）。同一个事件在不同条件下要走向不同状态：CONFIRM 时如果选的文件超过 500MB，不该进 uploading，该直接进 failed 提示文件过大。这种“带条件的转移”用 cond 表达，条件本身是一个纯函数：

数组按顺序求值，第一个 cond 通过的转移生效。旧代码里这段逻辑是 handler 里的 if-else 加两个布尔赋值，现在校验条件和流程走向写在同一个地方，review 时一眼能看出“超大文件走哪条路”。

第二个是进入/退出动作。有些副作用天然绑定在状态上而不是事件上：进入 uploading 就该发起分片请求，离开 uploading（无论去 paused 还是 failed）就该中止在途请求。写在 entry/exit 里，比散在每个事件 handler 里可靠——不管从哪条转移进入这个状态，动作都会执行，不存在“某条路径忘了启动请求”的漏洞：

动作的具体实现通过 interpret 之前的 machine.withConfig 或组件里的选项注入，machine 定义本身保持可序列化——这也是它能贴进 visualizer 可视化的前提，定义里不掺具体的业务函数体。

还有一层意外的对齐红利：后端的上传任务表里本来就有一个 status 字段（枚举值和我的状态图基本一一对应）。前端布尔时代，接口返回的 status 要被翻译成一组布尔赋值，翻译错一个就是 bug；现在前后端说的是同一套名词，恢复页面时拿 status 直接作为状态机的初始状态，这段翻译代码整个删掉了。流程状态本来就该是一等公民，后端早就这么建模了，前端拆成布尔属于自己给自己降维。

什么时候不值得上库

说完好处必须说边界，不然这篇就成了带货文。XState 功能很全——层级状态、并行状态、历史状态、内建的 invoke 副作用管理——但全量学下来曲线不平缓，团队里目前也只有我一个人熟。这次重构我评估过三个方案，最后 XState 只用在了这一个组件上。

引库前还查过体积账：xstate 核心包 gzip 后十几 KB，对中后台不算负担，真正的成本在人——下个接手的同事要先理解“machine/service/context/guard”这套词汇表才能改代码。引一个库等于给这段代码设了一道认知门槛，门槛值不值，取决于门里面的复杂度有多大。

值得上 XState 的信号，在我看来要同时满足两条：一是状态和转移多到"一眼看不全"，需要可视化工具和嵌套结构来管理复杂度（比如这个上传组件，加上审批场景后有九个状态、二十多条转移）；二是流程本身是业务核心、会被反复迭代——正是因为产品每个季度都要往上传流程里加规则，声明式的状态图才能持续摊薄理解成本。如果是一次写完不再动的交互，引库的学习成本摊不掉。

还有一条软性判断：**如果你发现自己在向同事解释组件逻辑时不得不画一张状态图，那代码本身最好也长成状态图的样子。**反之，如果一句话就能说清（"点了就展开，再点就收起"），代码也不该比一句话复杂。

回到那六个布尔

重构后的上传组件上线三周，期间产品加了"上传前压缩"的新阶段——在状态图上 selecting 和 uploading 之间插一个 compressing 状态，加两条转移，模板里加一个 matches('compressing') 的分支，原有代码一行没动。同样的需求落在六个布尔的旧版本上，我估计要动十几处 v-if 外加祈祷没漏。

开头那条标准可以再收一遍：布尔各自独立时，它们是状态；布尔开始组合出"合法"与"非法"时，它们就是一个没被命名的状态机，区别只在于你是让它显式地躺在一张图里，还是让它隐式地散落在每个事件处理函数的赋值语句里。这次是后者欠的债攒到修不动了，才换成前者——下次新写复杂流程，我会在第一个布尔想拉第二个布尔入伙时就警惕起来。
