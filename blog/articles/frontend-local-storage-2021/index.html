localStorage 使用笔记：前端本地存储方便，但别把它当数据库

2021-06-19
前端基础

前端做一些小型功能时，本地存储是一个非常方便的能力。

比如：

  • 保存主题设置
  • 记录搜索历史
  • 缓存草稿内容
  • 记录上次浏览状态

这时不少人会第一时间想到 localStorage。它确实好用，但也很容易被滥用。

我对 localStorage 的态度后来变得很明确：它适合做体验增强，不适合承载业务真相。这个判断是踩过坑之后才有的。

localStorage 的特点

localStorage 最直接的特点有两个：

  • 存储在浏览器本地
  • 数据会长期保留，除非手动清除

它的使用方式也很简单：

这也是它会成为很多前端功能第一选择的原因。

但它还有两个特点经常被忽略：

  • 它是同步 API
  • 它只能存字符串

这意味着它适合少量、低频、结构简单的数据。把它当成一个随手可用的小仓库没问题，把它当数据库就会出事。

还有一个现实限制是容量。不同浏览器、不同环境的限制不完全一样，通常不能假设它可以无限写。大多数桌面浏览器给到每个源 5MB 左右，注意这里算的是 UTF-16 编码长度，一个中文字符占两个字节，所以你存中文草稿的时候，可写的实际字符数大概只有标称的一半。写入超过配额时，setItem 可能直接抛错，所以写入逻辑一定要放在 try...catch 里，而不是只在读取时兜底。

配额这个坑我是真踩过。早期有个页面把用户的操作日志一股脑往 localStorage 里堆，本地测试一切正常，因为我自己的数据量小。结果线上有重度用户用了几个月，攒了一堆，某次写入直接抛 QuotaExceededError，而那段写入逻辑恰好没包 try...catch，把整个初始化流程打断了，页面白屏。更坑的是不同浏览器抛出的错误名还不统一，Safari 早期版本是 QUOTA_EXCEEDED_ERR，Firefox 是 NS_ERROR_DOM_QUOTA_REACHED，所以靠错误名精确判断并不可靠，更稳的做法是只要写入失败就当作"本地不可用"统一降级：

适合存什么

localStorage 更适合保存一些轻量、低风险、用户体验相关的数据，例如：

  • 页面偏好设置
  • 非敏感草稿
  • 最近浏览记录
  • 搜索关键字历史

这些数据就算丢了，影响通常也比较有限。

我判断一个数据能不能放进去，会先问一句：如果这份数据丢了，用户能不能接受？

主题偏好丢了，大不了回到默认主题；搜索历史丢了，体验差一点；草稿丢了，可能就要谨慎，最好给用户明确保存状态。这个问题一问，很多数据的边界就清楚了。

不适合存什么

虽然 localStorage 很方便，但它并不适合所有数据。

特别不建议直接存：

  • 敏感信息
  • 大量结构化数据
  • 强一致性要求很高的数据

因为它本质上只是浏览器提供的一种简单存储能力，不是可靠的业务数据库。

我尤其不建议把 token、身份证号、手机号详情这类敏感信息长期放在 localStorage。只要页面存在 XSS 风险，脚本就可能读到这些数据。localStorage 没有任何 HttpOnly 之类的保护，任意一段同源 JS 都能 localStorage.getItem('token') 把它读走，包括你引入的第三方埋点脚本、广告 SDK、出问题的 npm 依赖。我见过一个项目把登录 token 存在 localStorage，后来接了个第三方客服组件，那个组件的脚本理论上就有能力读到所有本地存储——虽然它没作恶，但这种"把钥匙交到不认识的人手里"的结构本身就不该出现。

前端存储越方便，越要克制。能被 JavaScript 读到的东西，就不要假装它绝对安全。

还有一类数据是“看起来不敏感，但组合起来敏感”。例如用户最近访问的订单、搜索关键词、草稿标题，单独看问题不大，但如果包含业务场景、身份线索或隐私内容，也不应该长期无脑保存。

我还会给每个业务的 key 加一个统一前缀，比如 app:draft、app:theme。原因是 localStorage 是按源（origin）共享的，同一个域名下不同页面、不同功能、甚至不同团队写的代码都在抢这一个命名空间，没有前缀很容易撞 key。我吃过一次亏，两个功能都用了 settings 这个 key，互相覆盖，排查了半天才发现是命名冲突。

它是同步 API

很多人第一次使用时不会特别在意这一点，但 localStorage 的读写是同步的。

在小量数据场景问题不大，但如果你频繁读写，或者存储内容比较大，依然可能影响主线程。

所以它适合轻量场景，不适合高频、大量数据写入。

比如输入框每敲一个字就写一次 localStorage，我现在不会这么做。草稿保存可以加一点防抖：

用户需要的是草稿能恢复，不是每个字符都立刻同步到本地。

为什么同步这件事在大数据量下会咬人？因为 setItem 不只是往内存里塞，浏览器要把数据序列化、落到磁盘、还要保证持久性，这整个过程是阻塞主线程的。我做过一个粗略的对比：存几百字节几乎无感，但当单个 key 的内容到了几百 KB、又在 mousemove 或 scroll 这种高频回调里反复写时，能明显感觉到掉帧。所以除了防抖，能减少写入体积也很有意义——比如只存真正变化的字段，而不是每次把整个大对象 JSON.stringify 再写一遍。

如果草稿很重要，除了防抖，还要考虑保存状态。比如写入失败时不要静默吞掉，至少在 UI 上显示“本地草稿保存失败”。否则用户以为已经保存，刷新后却找不到内容，这类体验问题比直接报错更糟。

用它做用户体验增强很合适

localStorage 最适合做的，其实不是业务主数据，而是体验增强。

比如：

  • 自动记住夜间模式
  • 页面刷新后保留筛选项
  • 输入中断后恢复草稿

这类功能的收益很高，实现成本也低。

还有一个常见场景是跨标签页同步。比如主题切换后，其他标签页也跟着变：

这个能力适合简单同步，不适合复杂通信。复杂状态还是应该交给更明确的状态管理或服务端。

还有一个细节：storage 事件通常不会在当前写入的同一个标签页触发，而是在其他同源页面触发。所以当前页切换主题时，仍然要自己立即调用 applyTheme，不能只等 storage 事件。这个特性其实挺反直觉的，第一次遇到的时候我以为是自己代码写错了，反复调试才发现是规范就这么设计的——storage 事件的本意是"通知别人我改了"，自己当然不需要被通知。

storage 事件还有几个坑值得记一下。event.newValue 在数据被 removeItem 时是 null，所以监听里一定要处理"被删除"这种情况，不能默认它永远是个有效值。另外 event.key 在调用 localStorage.clear() 时也会是 null，这时候意味着所有 key 都没了。它传过来的 newValue 同样是字符串，如果你存的是 JSON，监听里还得再 JSON.parse 一次，记得照样包 try...catch。

如果是更复杂的跨标签通信需求，比如"用户在一个标签退出登录，其他标签要立刻跳登录页"，我后来更倾向用 BroadcastChannel，语义比借 storage 事件传消息清楚得多：

它不需要真的往存储里写一个状态再删掉，避免了"为了发个事件而污染 localStorage"的别扭写法。只在需要兼容老浏览器时，我才会退回去用 storage 事件做这件事。

我会怎么选

如果是用户偏好、低风险草稿、最近搜索，我会考虑 localStorage。

如果是当前标签页里的临时流程数据，我会优先考虑 sessionStorage。

如果是大量结构化数据、离线缓存、复杂查询，我会考虑 IndexedDB。

如果是登录态和安全凭证，我会先和后端一起讨论 Cookie、HttpOnly、SameSite、刷新机制，而不是直接丢进 localStorage。

另外，如果只是为了缓存接口返回结果，也要先问缓存失效策略。什么时候过期？用户退出后是否清除？服务端数据更新后怎么同步？如果这些问题没有答案，把数据塞进本地只会把问题延后。

写在最后

localStorage 是前端开发里一个很实用的工具，但它的定位更像“本地轻量缓存”，而不是一个通用数据库。

只要你清楚它适合什么、不适合什么，就能在很多小功能里很好地提升用户体验。方便当然重要，但边界同样重要。

我现在最警惕的一句话是：“先存在 localStorage 里吧。”这句话有时很实用，有时也意味着我们还没想清楚数据的生命周期和风险。真正稳的做法，是先判断这份数据丢了会怎样、泄露会怎样、结构升级会怎样，再决定要不要存。

上一篇前端为什么也要懂 HTTP：请求能发出去，不代表你真的理解通信下一篇防抖和节流怎么选：不是背定义，而是先看事件有多频繁
