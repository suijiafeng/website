JavaScript 原型链：从 prototype 到 instanceof 一次串起来

2018-02-06
JavaScript前端基础

原型链特别容易被学成一串彼此认识、彼此又连不起来的名词：prototype、__proto__、constructor、instanceof、继承、class。平时写业务时框架会把大部分细节挡掉，于是人很容易产生一种错觉，好像这些概念自己也算懂了。

组里排了一次原型链的技术分享，轮到我准备的时候，第一件要做的事就是把这种"好像懂了"的错觉拆掉。分享没有照着 PPT念，而是留了一块白板，从一个最朴素的问题开始：prototype 和 __proto__ 到底是什么关系。后面一路追到手写 new、属性遮蔽、instanceof 判断、组合继承和 class 的底细，整场讲下来几乎每一步都要靠白板上手推才能讲清楚。

准备这场分享才发现，自己过去不是真正理解了原型链，只是长期绕开了它没细想。下面就按分享现场推导的顺序，把当时容易卡住的地方一起写清楚。

第五问：写一个继承，别用 class

最后一段，写一个 Dog 继承 Animal，不用 class，用组合继承的老写法：

Animal.call(this, name) 继承实例属性，Object.create 继承原型方法。这里容易冒出一个问题：Object.create 那行，写成 Dog.prototype = Animal.prototype 行不行？

不行。看起来能跑，但这等于让父子共用同一个原型对象——往 Dog.prototype 上加 bark，Animal 的实例也会平白多出一个 bark，子类的改动漏到父类去了。Object.create 的意义就是新建一个原型继承自 Animal.prototype 的干净对象，父子各管各的。

那 Dog.prototype = new Animal() 这种老写法呢？毛病有两个：一是父类构造函数被调用了两次（这里一次、Animal.call 里一次）；二是父类实例属性被挂到子类原型上，又回到了第四问那个"引用类型共享"的坑。所以"组合继承 + Object.create"——也叫寄生组合继承——才是公认最干净的方案。业务里现在少写了，但看老插件和库源码时照样会遇到。

前面提到过继承时 constructor 容易弄丢，具体丢在哪一行？就是 Dog.prototype.constructor = Dog 这行如果被漏掉。因为整个 Dog.prototype 被替换掉了，原来指回 Dog 的 constructor 也跟着没了，不补的话 new Dog().constructor 会是 Animal，依赖 constructor 判断类型的代码就会出错。替换原型之后手动补 constructor，这两行要当成一个整体来记。

串起来看

把整场分享梳理的点列一遍：new 的返回值判断、读写不对称、constructor 补回、Dog.prototype = Animal.prototype 的陷阱——每一个单独看都是小知识点，串起来其实都在回答同一个问题：对象自己没有这个属性时，接下来去哪里找；以及顺着这条链，什么被共享、什么各自拥有。

prototype、__proto__、new、instanceof、继承、class，看着是六组概念，其实是一条链的六个观察角度。这条链想通以后，再读老项目里的构造函数、看第三方库怎么挂方法、排查 instanceof 为什么不符合预期，都会轻松很多。class 只是把写法收整了一层，糖纸底下还是那套原型。

再补一个分享后自己顺手验证的细节：Object.setPrototypeOf(obj, proto) 是 Object.create 之外另一个能改原型的标准方法，区别在于 Object.create 是"新建对象时就指定原型"，Object.setPrototypeOf 是"给已存在的对象换原型"。两者都比直接赋值 __proto__ 规范，但无论哪一种，运行时动态改原型都会让引擎的内部优化失效，属性查找的隐藏类会被打乱，性能上不算便宜——真实项目里，原型关系最好在对象创建的那一刻就定下来，别在后续逻辑里动态修改。
