JavaScript 原型链：为什么面试总喜欢从 prototype 问起

2018-02-06
JavaScript前端基础

原型链也是前端面试的常客。

很多人平时写业务时不直接碰 prototype，尤其是用了 Vue、React 之后，组件写法已经把很多细节藏起来了。但只要接手工具库、老代码、插件扩展，还是会遇到构造函数、原型方法和继承。

原型链不是为了背概念，而是为了理解 JavaScript 对象是怎么找属性的。

我对原型链真正"开窍"，不是在面试现场，而是在排一个诡异线上 bug 的时候。当时项目里引了一个老的地图插件，我们给它的实例方法做了点扩展，结果发现改一个实例的配置，所有地图实例的配置都跟着变了。查了半天才发现，插件作者把默认配置对象写在了 prototype 上，所有实例共享同一个引用。那一刻我才明白，原型链不是面试用来为难人的概念，它实实在在地决定了对象之间"共享什么、各自拥有什么"。从那以后我读任何库的源码，看到 prototype 都会多看两眼。

还有一个常被绕进去的点：Person.prototype 上有个 constructor 属性，默认指回 Person 本身。所以 p.constructor === Person 成立，但这个 constructor 是顺着原型链从 Person.prototype 上找到的，p 自己并没有。后面讲继承时，重写原型会把这个 constructor 弄丢，得手动补回来。

继承写法

常见组合继承：

Animal.call(this, name) 继承实例属性，Object.create 继承原型方法。

这里 Dog.prototype = Object.create(Animal.prototype) 这一句很关键，也很容易写错。我见过有人图省事写成 Dog.prototype = Animal.prototype，看起来能跑，但这等于让父子共用同一个原型对象，往 Dog.prototype 上加方法会污染到 Animal，子类的改动会漏到父类去。Object.create 的意义就是新建一个原型继承自 Animal.prototype 的干净对象，父子各管各的。

紧接着那句 Dog.prototype.constructor = Dog 也别漏。因为整个 Dog.prototype 被替换掉了，原来指回 Dog 的 constructor 也没了，不补的话 new Dog().constructor 会变成 Animal，有些依赖 constructor 判断类型的代码就会出错。

顺带说一下为什么不直接用更老的 Dog.prototype = new Animal() 这种写法。它的毛病有两个：一是父类构造函数被调用了两次（这里一次、Animal.call 里一次），二是父类实例属性会被挂到子类原型上，又回到了"引用类型共享"那个坑。所以"组合继承 + Object.create"（也叫寄生组合继承）才是当年公认最干净的方案。这类写法在业务里少了，但看老插件和库源码时仍然会遇到。

不过有两点跟函数构造器不一样，值得记一下：class 不会被变量提升（用之前必须先声明），类体内部默认是严格模式。理解原型链以后，class 也就没那么神秘了——它是更安全、更省心的语法糖，但糖纸底下还是那套原型。

我现在很少在业务代码里手写一套原型继承，但这块还是绕不过去。

prototype、__proto__、new、instanceof 看着像几组零散概念，其实都在解释同一件事：对象自己没有这个属性时，接下来去哪里找。这个链路想通以后，再读老项目里的构造函数写法、看第三方库怎么挂方法、或者排查 instanceof 判断为什么不符合预期，都会轻松很多。class 只是把写法收整了一层，底下那条原型链并没有消失。
