移动端 H5 拍照功能怎么做

2023-01-31
前端基础移动与小程序

很多移动端页面都会遇到拍照需求。

比如上传头像、拍证件照、提交工单图片、上传现场照片。在 H5 页面里，实现拍照最常见的方式是使用文件选择框，而不是直接控制手机摄像头。

这类需求看起来简单：点按钮、拍照、上传。但真实项目里还会遇到兼容性、图片过大、方向旋转、权限失败、用户取消、上传重试等问题。

我做过一次工单现场拍照，最开始以为半天能搞定，结果真机测试一圈问题全出来了：iPhone 拍出来方向不对，安卓低端机压缩大图时页面卡死，企业微信 WebView 里 capture 表现和浏览器不一样，用户取消拍照还被当成上传失败弹了 toast。这个需求后来让我记住了，H5 拍照难点不在“调起相机”，而在“拍完之后稳定处理”。

如果业务运行在微信、企业微信、钉钉或自家 App WebView 里，还要确认容器有没有自己的相机能力。有些容器的 JS SDK 能拿到更稳定的拍照结果，也能处理权限提示；但这会带来平台绑定。我的习惯是先用标准 input 做基础方案，再按目标容器决定是否接 SDK 增强。

读取用户拍摄的图片

用户拍照或选择图片后，可以通过 change 事件拿到文件。

URL.createObjectURL 适合做本地预览，速度快，也不需要把图片转成 base64。预览完成后调用 URL.revokeObjectURL，可以释放临时地址占用的资源。

预览时不要忘了加载失败态。移动端相册里可能有损坏图片、云端未下载完成的图片，img.onerror 要能给用户明确提示，而不是留一个空白预览框。

什么时候用 FileReader

如果后续逻辑需要 base64，可以使用 FileReader：

但 base64 通常会让体积变大，不适合大图上传。除非接口明确要求 base64，或者你需要把图片嵌入到某段文本数据里，否则更推荐直接上传 File 或 Blob。

我现在基本不主动把照片转 base64。base64 会增加大约三分之一体积，还会占用更多内存。低端手机上一张几 MB 的图转成字符串，很容易让页面卡住。能传二进制，就传二进制。

移动端拍出来的图片可能很大，一张照片几 MB 很常见。如果不做限制，上传会慢，也容易失败。

上传错误要统一处理。网络断开、文件过大、服务端校验失败、登录过期，给用户的提示不应该都叫“上传失败”。我会把错误归一成稳定结构，再在页面展示明确行动：重试、重新选择、重新登录，或者联系管理员。

多图上传时不要并发全开。五六张现场照同时压缩、同时上传，低端手机很容易卡死。我通常会把压缩和上传都排队，最多同时处理 2 个，并把每张图的状态拆开：待压缩、压缩中、待上传、上传中、失败、成功。这样用户知道哪张失败了，也能只重试失败的那张。

移动端照片经常有两个问题：体积太大，方向不对。

方向问题通常和 EXIF 信息有关。部分浏览器会自动处理，部分场景不会。如果业务对证件照、现场照方向要求严格，需要在目标设备上测试，必要时读取 EXIF 并修正方向。

压缩也要控制节奏。一次性把多张大图都丢进 canvas，主线程会明显卡。多图上传时可以排队处理，或者限制一次最多选择几张。对现场工单这种场景，用户宁愿看到“正在压缩第 2/5 张”，也不愿意页面直接假死。

用户取消也要处理

用户打开相机后可能取消拍照，这不是错误。代码里要允许 files[0] 不存在，并且不要弹出“上传失败”。

那次工单拍照之后，我再也不敢只在桌面浏览器里验证 H5 相机功能。

input type="file" 配合 accept 和 capture 是最常见也最稳的起点，但它不能保证每个 WebView 都按你想的方式打开相机，也不能替你处理大图压缩、方向、取消、重试和权限提示。

拍照功能真正被用户感知的，不是“相机有没有调起来”，而是拍完以后能不能预览清楚、压缩不卡、方向不歪、上传失败能重试、取消时不乱报错。只要目标环境里有微信、企业微信、钉钉或自家 App WebView，真机矩阵就不能省。

上一篇前端代码评审怎么做才有效：不是挑语法，而是提前发现维护风险下一篇移动端适配入门：做前端页面时，别把响应式理解成只改宽度
