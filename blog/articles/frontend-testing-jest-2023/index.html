前端测试和 Jest 入门：别等到线上出问题才想起测试

2023-10-20
前端基础测试

给一个从没写过测试的项目补第一批用例，我从不碰最复杂的页面。第一批我只挑输入输出清楚的纯逻辑：工具函数、数据转换、权限规则、金额计算、还有那些曾经在线上出过 bug 的地方。原因很实际——这些代码写起来快，失败也好定位，最容易让团队亲身感受到"测试不是负担，而是在替我们记住规则"。

这个起步顺序不是一开始就想清楚的，是被一次事故推着定下来的。有回一个权限判断改坏了，页面上按钮显示得好好的，用户一点提交却被后端拒了，查下来是前端把"作者可编辑草稿"这条规则漏掉了归档状态。那个函数只有十几行，却被好几个页面复用。从那以后，我给自己定了这套优先级：先给权限、金额、格式化、状态机这类纯逻辑补测试，因为它们最容易被复用，也最适合自动化兜底。这篇就顺着这个顺序，用 Jest 把从哪起步、怎么下手一步步走一遍。

之所以强调"从哪起步"，是因为大多数项目不写测试不是因为不认同测试，而是不知道第一个用例该落在哪、一想到"要给整个项目补测试"就觉得工程量吓人、干脆不动。破这个局的办法不是喊口号，是找一个投入最小、收益最直观的切口先跑起来。纯逻辑就是这个切口——它不依赖渲染、不依赖浏览器、输入输出一目了然，一两个用例就能让人看到"改坏了会立刻报红"的实感。测试习惯是靠一次次这种小收益攒出来的，不是靠一份完美的测试方案立起来的。

先分清测试的三类，好知道起点在哪

常见前端测试大致三类，分清楚才知道第一批该落在哪一类。

单元测试关注最小的逻辑单元——工具函数、数据转换、权限判断、表单校验。它运行快、定位准，正是前端测试最该起步的地方。集成测试关注多个模块一起工作是否正常，比如组件渲染后用户输入、点提交、页面是否展示正确结果。端到端测试更接近真实用户，会启动浏览器，模拟登录、跳转、点击、提交整套流程，覆盖面强但维护成本也高，跑得慢、还容易因为环境或时序问题偶发地失败。

这三类不是互相替代，更合理的组合是：关键纯逻辑多写单元测试，核心交互写少量集成测试，最重要的业务链路再用端到端兜底。但别一上来就追求"测试金字塔"多漂亮——先让团队尝到收益更重要。一个历史 bug 被测试拦住，比一份宏大的测试计划更能说服大家继续写。所以起步就落在单元测试这一层，这是投入产出比最高的入口。

起步清单：从哪些地方下手

Mock 要克制，别把真实逻辑 mock 没了

起步阶段有个很容易走偏的地方是滥用 mock。Jest 能模拟函数、模块、时间和接口请求，但 mock 用太多，测试反而失真。最常见的反模式是把所有依赖都 mock 掉，最后只验证"某个 mock 函数被调用了"——这种测试看着覆盖了代码，实际没验证任何业务结果。

更好的原则是：纯函数尽量不 mock；时间、随机数、网络请求可以 mock；优先断言用户能观察到的结果；别过度依赖内部实现细节。测数据转换函数时直接断言输出即可；测带接口请求的逻辑时可以 mock 网络层，但仍要关注最终状态是否正确。

判断一个 mock 该不该加，我有个粗略的标准：这个依赖是不是"不确定"或"有副作用"的。时间、随机数、网络、文件系统这些每次跑结果可能不同、或者会真的对外产生影响的，该 mock，把它们固定住测试才可复现；而一个普通的纯函数依赖，本身就确定，mock 它只会让测试离真实行为更远。mock 是用来隔离不确定性的，不是用来图省事绕过真实逻辑的，这条界一旦想清楚，滥用的情况就少很多。

如果项目已经用 fetch 或 Axios，比起把业务函数内部依赖都 mock 掉，我更推荐用 MSW 这类方式在网络边界拦请求。这样测试仍接近真实请求流程，又不会真打到后端。对表单提交、错误提示、重试这类逻辑，在网络边界 mock 比 mock 某个内部函数可靠得多——mock 的位置越靠外层、越贴近真实边界，测试就越有效。

快照测试：能用，但别滥用

Jest 有个快照测试很方便，一行 toMatchSnapshot() 就能把组件输出存下来、之后比对有没有变。它适合锁那些"不该轻易变"的输出，但特别容易被滥用成偷懒工具——给一堆组件无脑打快照，看着覆盖率上去了，实际上没人真去读快照内容。结果就是组件一改，一堆快照红，大家习惯性 --updateSnapshot 一把过，快照就彻底失去了守护作用。我的判断是：快照只用在输出稳定、且你会认真读快照 diff 的地方，多数业务组件宁可写几条明确的行为断言，也别用大快照糊过去。

覆盖率是底线，不是目标

起步阶段还要摆正对覆盖率的态度。覆盖率能当参考，但不能只追数字。一个项目 90% 覆盖率不代表真稳，一个关键业务流程没测到，风险照样很高；反过来覆盖率暂时不高，但关键工具函数、权限规则、订单金额计算都有测试，价值就已经很明显。

更合理的目标是：重要逻辑有测试，容易改坏的地方有测试，核心流程有基本保障。覆盖率可以当底线，比如新增工具函数至少有基本测试，但别把它当唯一目标。为了凑覆盖率去测 getter、简单渲染、无分支代码，收益很低；把精力放在分支、边界、历史 bug 和核心业务规则上，性价比高得多。

关于 Vitest：我在观望，但没急着换

写到这里得提一句最近社区聊得多的 Vitest。它跟着 Vite 起来，主打和 Vite 配置共用、启动更快，API 又基本对齐 Jest，迁移成本看着不高。我们有个用 Vite 的新项目我拿它试了试，跑起来确实快，watch 模式反馈很跟手。

但我暂时没把主力项目从 Jest 换过去，原因很实际：一是我们不少项目还是 webpack 构建，跟 Vite 生态绑不到一起，换过去反而多一层适配；二是 Vitest 现在还在 0.x，版本迭代快、偶尔有行为变动，作为一个要长期跑在 CI 里的门禁，我更想等它再稳一稳。新的、走 Vite 的项目可以直接上 Vitest 尝鲜，存量 Jest 项目没必要为了追新硬迁——测试框架的价值在稳定和团队熟悉度，不在版本号新。这个判断和这篇一贯的态度一致：先让测试跑起来、有收益，工具选型是后面的事。

回到开头那个起步顺序。给没测试的项目补第一批用例，我依旧不碰最复杂的页面，先挑纯函数、工具方法、权限规则、金额计算、历史 bug 这些输入输出清楚的地方。它们写得快、失败好定位，最容易让团队感受到测试在替自己记住规则。Jest 的优势恰好也在这——启动成本低、反馈快，适合覆盖前端项目里大量的基础逻辑。等这层底座稳了，再慢慢往上补组件测试和端到端流程，整个测试体系会长得自然很多。
