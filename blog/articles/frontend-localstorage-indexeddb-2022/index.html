localStorage、IndexedDB 和 Cookie：前端本地存储怎么选

2022-07-08
前端基础JavaScript构建与模块化

前端本地存储很容易被一句“放 localStorage 吧”带过。

但不同存储方案差异很大。登录态、用户偏好、草稿、大文件缓存、离线数据、接口缓存，不应该都用 localStorage。选错了，轻则性能差，重则安全风险和数据错乱。

我见过一个项目把几 MB 的表格缓存塞进 localStorage，页面打开时同步 JSON.parse，低配电脑明显卡。还有项目把长期 token 放 localStorage，后来做 XSS 排查时压力很大。

本地存储要先看数据类型和风险。

localStorage 适合小而简单的数据

localStorage 的优点是简单：

适合存：

  • 主题
  • 语言
  • 简单用户偏好
  • 不敏感的小型配置

它的问题也明显：

  • 同步 API，会阻塞主线程
  • 容量有限
  • 只能存字符串
  • 被 JS 直接读取
  • 没有过期机制

所以不要存大数据，也不要存高敏感数据。

如果存对象，要处理解析错误：

本地数据可能被用户或插件改坏，不能默认可信。

sessionStorage 适合会话内临时状态

sessionStorage 和 localStorage 类似，但生命周期是当前标签页会话。

适合：

  • 多步骤表单临时状态
  • 当前 tab 的筛选条件
  • 登录跳转临时参数

刷新页面还在，关闭标签页就没了。

不要用它做跨标签页共享。不同标签页 sessionStorage 隔离，这有时是优点，有时是坑。

Cookie 适合和请求一起发送的数据

Cookie 最大特点是会随请求发送。

适合：

  • 服务端鉴权
  • SSR 需要读取的偏好
  • CSRF token

Cookie 要控制大小，因为每次请求都会带上。不要把大对象塞 Cookie。

高风险登录态建议使用 HttpOnly Cookie：

HttpOnly 能防止 JS 读取，降低 XSS 窃取 token 的风险。但它会自动随请求发送，所以要考虑 CSRF。

IndexedDB 适合大量结构化数据

IndexedDB 是异步的，容量更大，适合复杂本地数据：

  • 离线草稿
  • 大列表缓存
  • 文件元数据
  • 客户端数据库
  • PWA 离线数据

它的 API 原生写起来比较繁琐，项目里通常会用封装库。

IndexedDB 适合“真的需要本地数据库”的场景。不要为了存一个主题色就上它，也不要把它当永久可靠存储。浏览器在存储压力下可能清理站点数据。

Cache Storage 适合请求和资源缓存

Service Worker 常配合 Cache Storage 缓存资源：

  • JS/CSS
  • 图片
  • HTML fallback
  • 接口响应

它适合按 Request/Response 模型缓存，不适合当普通 key-value 数据库。

接口响应缓存要谨慎。用户私有数据、权限数据、支付状态不要随便长期缓存。缓存命中快，但旧数据也快。

敏感数据尽量少存

前端存储的安全原则很简单：能不存就不存，必须存就缩短生命周期。

不要在本地长期存：

  • 明文密码
  • 长期 token
  • 身份证、银行卡等敏感信息
  • 权限完整快照

如果业务必须保存草稿，敏感字段要考虑加密、过期和清理。但前端加密密钥如果也在前端，安全收益有限，不要自欺欺人。

API 错误和存储错误都要处理

本地存储也会失败。

比如 Safari 隐私模式、存储空间满、用户禁用存储，都可能让写入异常。

如果保存草稿失败，要提示用户，而不是静默丢数据。接口失败、本地保存失败都要有可理解的反馈。
