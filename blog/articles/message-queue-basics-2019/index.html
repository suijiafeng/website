消息队列基础：为什么有些操作不适合在接口里立刻做完

2019-11-16
杂项

有些接口很慢，不是因为代码差，而是它做的事情太多。

用户下单后，要扣库存、生成订单、发短信、发通知、写日志、同步数据。如果所有事情都在一个接口里同步完成，接口会很重，也更容易失败。

消息队列的价值，就是把一些可以延后处理的任务拆出去。

我第一次真正意识到这点，是有一年双十一前压测下单接口。单接口 RT（响应时间）平时 80ms 左右，压到一定并发后直接飙到 2s 以上。后端拉出火焰图一看，时间几乎全花在调用第三方短信网关和写一张审计日志大表上——这两件事跟"订单是否创建成功"根本没关系，却拖垮了整条链路。把它们丢进队列以后，下单接口 RT 立刻回到 100ms 以内。那次之后我才理解，队列不是什么高大上的中间件，它解决的就是"非关键步骤不该卡住关键步骤"这个朴素的问题。

那一年我们用的是 RabbitMQ，后来部分高吞吐场景换成了 Kafka。不同队列侧重点不一样，但要解决的核心问题是相通的，下面这些点跟具体选型关系不大。

同步处理的问题

如果发短信服务慢，用户就要等。

如果发邮件失败，订单要不要失败？这就需要业务判断。

很多非核心步骤可以异步处理。

我们当时踩过一个更隐蔽的坑：发短信用的第三方网关偶尔会超时，但我们的 HTTP 客户端默认超时设的是 30s。结果就是高峰期一旦短信网关抖动，下单接口被这 30s 拖着，连接池很快被打满，整个下单服务雪崩。排查了大半天才定位到，根因不是短信失败，而是"一个不重要的下游把重要的上游拖死了"。这种问题在同步链路里几乎无解，只要还在一个调用栈里，下游的延迟和故障就会传导上来。

后来我固定了一个判断标准：一个步骤要不要留在同步链路里，看它失败时订单该不该跟着失败。扣库存失败，订单必须失败，留在链路里；短信发失败，订单照样成立，那就该异步。把这条想清楚，哪些动作往队列里塞就很自然了。

使用消息队列

接口只做关键链路，把后续任务交给消费者处理。

这里有个容易被新手忽略的细节：消息应该在什么时机发？我见过一种写法是先发消息再写数据库，结果消费者收到消息去查订单时，订单还没落库，查了个空。正确的顺序是先把订单和库存这些核心数据落库成功，再发消息。更严谨的做法（如果团队上了规模）会用本地消息表或事务消息：把"发消息"这个动作和业务数据放在同一个数据库事务里，先写一张待发送消息表，再由一个后台任务捞出来投递，保证"业务成功"和"消息发出"要么都成、要么都不成。2019 年 RocketMQ 的事务消息就是干这个的，不过大多数中小团队用本地消息表 + 定时补偿就够了。

系统之间耦合会更低。

解耦带来的实际好处，是改一边不用动另一边。原来短信、积分、推送这些逻辑全堆在下单接口里，每加一个"下单后要做的事"，都得改下单代码，回归测试整条链路。用了发布订阅之后，新增一个"下单后给用户发会员成长值"的需求，会员服务自己去订阅 ORDER_CREATED 就行，下单服务一行代码都不用动。这种"订单系统不知道、也不需要知道有谁在消费它的消息"的状态，就是解耦真正值钱的地方。

不过解耦也不是没代价。消息一旦成了多个系统之间的契约，字段就不能随便改了。我们吃过一次亏：订单服务把消息里一个字段从 orderId 字符串改成了数字类型，下游三个消费者全挂了，因为它们按字符串解析。所以消息体的结构最好从一开始就当成对外 API 来对待，加字段可以，改类型、删字段要非常谨慎，必要时做版本兼容。

削峰

活动高峰时，请求瞬间很多。

如果所有任务都直接打到下游服务，下游可能扛不住。

消息队列可以先把任务排队，消费者按能力慢慢处理。

这就是削峰。

打个我们当时常用的比方：下游服务每秒只能稳定处理 500 个任务，但活动开始那一瞬间涌进来 5000 个。没有队列，这 5000 个全砸到下游，下游直接被压垮，连本来能处理的 500 个也一起没了，全军覆没。有了队列，5000 个先在队列里排着，下游还是按每秒 500 的节奏匀速消费，大概十秒就能把这波峰值消化掉。代价是部分任务会有几秒延迟，但这对发短信、发积分这类异步任务完全可以接受。

削峰能成立有个前提：这些任务确实允许延迟。如果是要求实时返回结果的查询，队列帮不上忙，反而会把延迟问题藏起来。另外要盯紧队列的堆积量，我们配了告警，队列里堆积超过一定阈值就报警——堆积持续上涨通常意味着消费速度长期跟不上生产速度，那就不是削峰而是要扩消费者或者优化消费逻辑了。削峰削的是瞬时尖峰，不是用来扛长期的处理能力不足。

重复消费

消息队列里很重要的问题是：消息可能被重复消费。

所以消费者要做幂等。

为什么消息一定会重复？因为绝大多数队列保证的是"至少一次"（at-least-once）投递，而不是"恰好一次"。设想消费者处理完业务、正准备给队列回 ack 确认时，机器突然重启了——队列没收到 ack，会认为这条消息没处理成功，于是重新投递。业务其实已经执行过一遍了，但队列不知道。想做到严格的"恰好一次"成本极高，所以行业里的通用做法是：接受重复投递，由消费者自己保证幂等。

消息丢失

还要考虑消息是否可靠。

生产者发送失败怎么办？队列宕机怎么办？消费者处理失败要不要重试？这些都是消息队列系统要处理的问题。

具体落到配置上，可靠投递通常要把几个环节都拧紧：生产者发送后等待队列的确认（confirm），没确认到就重发；队列本身要开持久化，让消息落盘而不是只在内存里，否则 Broker 一重启消息就没了；消费者要等业务真正处理完再 ack，而不是一收到就 ack。这三个环节但凡漏一个，消息都可能在某个缝隙里丢掉。我们早期就是消费者用了自动 ack，结果消费逻辑抛异常时消息已经被确认掉了，相当于静默丢消息，排查起来非常痛苦，因为没有任何报错。

消费失败的消息也不能无限重试。一条因为数据格式错误而必然失败的消息，重试一万次还是失败，反而会卡住后面正常的消息。我们的做法是设定重试上限，比如重试 3 次还失败就投到死信队列（DLQ），单独人工排查，不让它阻塞主流程。

前端不直接处理这些，但要知道：接口返回成功，不代表所有异步任务都已经完成。

前端体验

如果某些任务是异步的，页面文案要准确。

比如上传大文件后，服务端进入转码队列，前端不应该提示“处理完成”，而应该提示“上传成功，处理中”。

我处理过一个真实的客诉：用户上传视频，前端拿到接口 200 就提示"发布成功"，用户立刻去个人主页找，结果看不到——因为视频还在后台转码队列里排队。用户以为发布失败，又传了一遍，于是同一个视频出现两次。后来我们把状态说清楚：上传完成只提示"已上传，处理中"，前端轮询或者用长连接监听处理结果，转码成功了再变成"已发布"。文案从"成功"改成"处理中"，客诉直接降下来一大截。

异步链路下，前端要习惯"提交"和"完成"是两件事。设计交互时多问一句：这一步服务端是同步做完了，还是丢进队列异步做？答案不同，给用户看的文案和状态机就得不同。

顺序问题

还有个我觉得新手特别容易忽略的点：消息默认是不保证全局顺序的。同一个订单先后发了"已支付"和"已退款"两条消息，如果它们被分到不同的队列分区、由不同消费者并发处理，完全可能"已退款"先被处理、"已支付"后被处理，状态就乱了。

需要顺序的场景，得把相关消息路由到同一个分区（比如 Kafka 按 orderId 做分区 key），保证同一个订单的消息进同一个分区、被同一个消费者按序消费。但这又会牺牲并发度。所以我的经验是：能不依赖顺序就别依赖，消费逻辑尽量设计成跟顺序无关，比如带上状态版本号、只接受比当前更新的状态。实在绕不开顺序，再用分区 key 这种手段，而且要清楚它会限制扩展性。

消息队列常用于异步处理、系统解耦和流量削峰。

面试问消息队列，通常会问重复消费、消息丢失、幂等和最终一致性。前端理解它，有助于设计更准确的页面状态和错误提示。
