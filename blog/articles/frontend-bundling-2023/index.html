前端打包优化经验：包体积不是只靠压缩就能降下来的

2023-07-02
前端基础构建与模块化性能与缓存

提到前端打包优化，很多人的第一反应是开 gzip、开 brotli、做压缩、分包。

这些都重要，但它们更多是结果优化，而不是根因优化。项目包体积越来越大，并不是因为压缩没做好，而是因为依赖结构、代码组织和资源策略本身就不够克制。

打包优化真正要解决的，是用户首屏到底下载了什么、执行了什么，以及哪些内容本不该这么早出现。

我第一次认真做打包优化，是因为一个中后台首页从“能接受”变成了“肉眼能等”。当时大家第一反应都是开压缩、调 splitChunks，但 bundle 分析图一打开就很尴尬：首页包里混进了图表库、富文本编辑器、Excel 导出库，还有一个只在报表页才会用到的地图 SDK。压缩能省一点，但真正的问题是这些东西根本不该跟首页一起下载。

从那以后，我看打包优化会先问两个问题：这个模块是不是首屏必须，用户是不是一定会用。答案不是的，就先从加载时机上找空间。

先弄清楚体积到底是怎么长起来的

一个前端包变大，常见来源通常有：

  • 引入了过大的第三方库
  • 首屏加载了本不该首屏加载的代码
  • 公共依赖拆分不合理
  • 图片、图标、字体资源过重
  • 工具函数或组件重复打进多个 chunk
  • 多语言、编辑器、图表等低频模块提前加载

如果不先定位来源，只盯着构建配置调参数，优化通常很快进入瓶颈。

更合理的第一步是做 bundle 分析。看清楚每个 chunk 里有什么、哪些依赖最大、哪些模块重复出现，再决定怎么改。

分析工具不用迷信某一个。Webpack 可以用 webpack-bundle-analyzer，Vite/Rollup 可以看 rollup-plugin-visualizer，Next.js 也有对应 analyzer。工具只是把体积可视化，真正要做的是把图里的模块和业务场景对上。

我一般会记录三个数字：首屏 JS 总体积、最大 chunk 体积、首屏实际执行耗时。只看压缩后体积不够，因为 300KB 的 JS 下载完还要解析和执行，低端设备上这一步经常比下载更明显。

不要把“功能能跑”当成依赖引入标准

很多包体积问题，都是从一行 import 开始的。

比如为了一个简单日期格式化，引入完整日期库；为了几个图标，引入整套图标包；为了一个弹窗，带进整套 UI 框架。这类问题最常见，也最容易被忽视，因为功能层面完全没问题。

但从长期看，依赖使用要有一个基本原则：引入的不是“功能”，而是“长期成本”。

评估依赖时可以看几个问题：

  • 是否真的需要第三方库
  • 是否支持按需导入
  • 是否会影响首屏包
  • 是否已有同类依赖
  • 是否会增加运行时成本
  • 是否容易被未来替换

有时手写几十行稳定代码，比引入一个大依赖更合适。

当然，也不要为了“零依赖”走极端。密码强度、日期时区、富文本解析、图表渲染这类问题，自己写的隐藏成本可能更高。我的判断标准是：业务规则是否稳定、边界是否复杂、库的体积和维护状态是否匹配需求。简单格式化可以手写，复杂领域能力不要硬造。

路由级拆分是最基本的一步

如果一个页面用户根本没访问，理论上它相关的代码就不应该在首屏里出现。

这也是代码分割最直接的价值。对于多页面或后台系统来说，路由级拆分通常是最先该做的事情。它不是锦上添花，而是把不必要的首屏负担拿掉。

组件级懒加载也要谨慎

有些团队在发现包大之后，会开始把很多组件都做成懒加载。

这不是不行，但要分场景。如果组件本身很轻、用户几乎一定会看到，那为了“拆得更碎”而懒加载，收益未必大，反而会增加请求碎片和复杂度。

更适合懒加载的通常是：

  • 富文本编辑器
  • 图表模块
  • 大型表格
  • 低频弹窗
  • 管理后台高级筛选面板
  • 代码编辑器

也就是说，真正重、真正低频的模块优先拆。懒加载的目标不是 chunk 越多越好，而是让用户先拿到当前需要的内容。

拆出去以后也要考虑用户体验。一个低频弹窗如果用户点开后才开始下载 800KB 编辑器，界面空等两秒，也会被认为卡。可以在用户靠近动作时预加载，比如鼠标悬停按钮、进入某个页面后空闲时再加载低频模块。拆包不是把问题推迟，而是把成本放到更合适的时间。

图片和图标常常是被低估的体积来源

不少人会盯着 JS 包，却忽略了静态资源。

实际项目里下面这些都很常见：

  • 首页大图未压缩
  • 多个页面重复加载大图资源
  • 只需要几个图标，却引入整套图标包
  • 字体文件过大
  • 多套字体字重同时加载
  • 移动端加载桌面端尺寸图片

这些问题加起来，用户感知可能比 JS 包还明显。图片应该做尺寸裁剪、格式优化和懒加载；字体应该限制字重和字符集；图标优先按需导入。

我后来会把图片也纳入“打包体检”。很多页面 JS 优化半天省了 80KB，结果首屏一张未压缩 PNG 就 1.8MB。WebP、AVIF、响应式图片、懒加载这些手段不新，但对用户感知很直接。尤其移动端，不要让手机加载桌面尺寸的海报图。

公共代码不是越集中越好

做公共 chunk 拆分时，一个常见误区是：只要公共就全抽出来。

问题在于，如果一个公共 chunk 非常大，而其中大部分内容其实只服务少数页面，那它反而会成为新的负担。用户访问首页时，被迫下载后台报表才用到的依赖，这就是拆分策略不合理。

公共代码拆分不是追求“集中”，而是追求“合理复用”。

比较稳的原则是：

  • 框架运行时可以稳定抽出
  • 多数页面都用的基础组件可以抽出
  • 低频页面的大依赖不要进入首屏公共包
  • 变化频繁的业务代码不要和稳定依赖混在一起

这样也有利于浏览器缓存。稳定依赖不常变，业务代码频繁变，分开后缓存命中率会更好。

但公共包也别切得过度。我们有次把 vendor 拆得非常细，结果首屏请求数暴涨，HTTP/2 下问题小一点，但在弱网和老 WebView 里仍然有调度成本。后来收敛成“稳定框架依赖一组、核心组件一组、低频大依赖按页面拆”，首屏更稳。

缓存策略也是打包优化的一部分

打包优化不只是让文件变小，也包括让用户不要重复下载没变的文件。

内容不变，文件名不变，浏览器就可以长期缓存。内容变化，文件名变化，用户会自动下载新版本。

这要求构建产物和服务器缓存头配合好。HTML 通常不能长期缓存，因为它要引用最新资源；带 hash 的 JS、CSS、图片可以设置更长缓存。

分析工具一定要用

如果一个项目已经明显变重，最不应该做的事情就是靠猜优化。

这时最有效的办法通常是：

  • 看 bundle 分析图
  • 看每个 chunk 的组成
  • 找出最大的第三方依赖
  • 找出重复出现的模块
  • 对比优化前后的首屏资源大小

很多优化方向只要一可视化，就会非常明显。比如一个图表库进入了首页包、一个富文本编辑器被公共组件间接引用、一个工具库被两种方式重复打包。

优化前后也要留记录。我会把分析图截图、关键体积数字和改动原因写进 PR。否则几个月后有人又把大依赖引回首屏，大家只知道包变大了，却不知道当初为什么拆出去。

体积预算最好能自动卡住

打包优化最怕只靠人肉记忆。今天大家刚优化完都很谨慎，过两个月新需求一赶，某个大依赖又被顺手塞回首屏。我的做法是给构建产物加一个简单的体积预算，超了就在 CI 里失败。

真正长期有效的优化，往往是结构优化

例如：

  • 避免滥引第三方库
  • 限制公共模块膨胀
  • 拆分高成本页面
  • 减少重复资源
  • 让低频功能延后加载
  • 保持依赖引入方式一致
  • 为资源设置合理缓存策略

这些事情比单纯调构建参数更费脑子，但通常也更有长期价值。

我现在做打包优化，会把它当成一次项目结构体检，而不是构建参数调参。

先看首屏实际下载和执行了什么，再看哪些依赖不该进首屏，哪些低频页面该拆，哪些公共 chunk 已经膨胀，哪些资源应该走缓存和按需加载。每次优化都要留下体积数字、分析图和改动原因，不然后面很容易又被一行 import 打回原形。

压缩、分包、缓存当然重要，但真正决定包体积的，通常还是代码和依赖本身的组织方式。结构合理，很多优化会自然发生；结构混乱，再多构建技巧也只是延后问题爆发。
