Redis 缓存基础：接口快了，也要小心缓存穿透和雪崩

2019-11-23
数据可视化与存储

去年我接手过一个内容站的详情页接口，平均响应时间 800ms，高峰期直接飙到 2s 以上。老板的原话是“点开一篇文章要转半天圈”。我拉慢查询日志一看，问题全在那几条带联表的文章查询上——文章表、作者表、标签表、计数表，一个详情页背后是四五次 join。

后来我没动 SQL，只在前面加了一层 Redis，p99 从 2s 掉到 60ms。那一刻我以为缓存是银弹。但接下来几个月踩的坑，让我明白：加缓存只是把“查得慢”的问题，换成了“查得不对、查得不一致、某一刻全部失效”的一堆新问题。

下面这些是我那段时间留下来的实战经验。代码基于当时用的 Node.js + ioredis，逻辑放到任何语言都通用。

过期时间：我曾经把它当成无所谓的参数

EX 600 表示 600 秒后过期。一开始我觉得这数字随便填填就行，结果吃了大亏。

过期时间得按数据的“可容忍陈旧度”来定，而不是拍脑袋：

  • 文章正文、作者简介这类几乎不变的内容，缓存 10 分钟甚至 1 小时都行；
  • 阅读数、点赞数这种高频变动又不要求精确的，我会单独缓存，给个短 TTL，比如 30 秒；
  • 库存、价格、余额、权限这类一旦读错就出事故的，要么不缓存，要么 TTL 极短并配合主动失效。

我当年犯的错是把所有东西塞进一个大对象一起缓存 10 分钟，结果点赞数十分钟才更新一次，用户狂点没反应，跑来投诉。后来我把“静态正文”和“动态计数”拆成两个 key、两套 TTL，问题才消停。

记住一句话：缓存不是越久越好，越久意味着脏数据存活越久。

缓存穿透：查一个根本不存在的东西

穿透指的是请求的数据在数据库里压根不存在，所以缓存永远建立不起来，每次都 miss，每次都打到 DB。

缓存击穿：一个热点 key 失效的瞬间

击穿是穿透的“单点高并发”版本：某个非常热的 key（比如首页置顶文章）刚好过期的那一瞬间，成百上千个请求同时发现 miss，于是同时去查数据库、同时写缓存。数据库被这一波瞬时流量打得喘不过气。

我第一次遇到是一篇爆款文章，缓存 TTL 到点的那一秒，监控上 DB 的 QPS 出现一根尖刺。解决思路是保证同一时刻只有一个请求去回源，其它请求等它。我用 Redis 的 SET NX 做了个简易互斥锁：

除了加锁，还有两种思路看场景用：

  • 热点 key 不设过期，改成由后台定时任务主动刷新，永远读到的是有效缓存（逻辑过期）；
  • 逻辑过期：value 里存一个 expireAt 字段，物理上永不过期，读到逻辑过期就异步触发一次刷新，返回旧值给当前用户，避免任何人卡住。

我现在首页这种超级热点用的是逻辑过期，用户体验最平滑——没人会因为缓存刷新而等待。

缓存雪崩：一大批 key 在同一秒集体阵亡

雪崩比击穿更吓人：不是一个 key，是一大片 key 在同一时间一起失效，瞬间所有读请求都穿到数据库。

我中招的原因特别低级——某次批量预热缓存，我写了个循环把上万篇文章一次性灌进 Redis，全都是 EX 600。结果 10 分钟后，这上万个 key 在同一秒钟集体过期，DB 直接被打挂，告警电话半夜把我吵醒。

数据一致性：这才是缓存最难的部分

前面几个问题都有相对标准的解法，唯独一致性，是真没有完美方案。核心矛盾是：数据库更新了，缓存里还是旧的，怎么办。

更新时常见的几种策略，我都踩过：

先更新数据库，再删缓存（推荐，Cache-Aside 的标准做法）

为什么是删而不是改？因为如果两个请求并发更新，“写缓存”的顺序可能和“写库”的顺序错乱，导致缓存里留下旧值。删除则是幂等的，下次 miss 自然会读到最新的库数据。

这个方案仍有个极小概率的不一致窗口：读请求 miss 后查到旧库值，还没写缓存，写请求就更新了库并删了缓存，最后读请求把旧值写了回去。概率极低，但存在。

先删缓存，再更新数据库：并发下问题更明显——删完缓存还没更新库，另一个读请求就把旧值又缓存了进来，结果脏数据存活到下次过期。我一般不单独用这个。

延迟双删：先删缓存 → 更新库 → 等几百毫秒 → 再删一次缓存，用第二次删除清掉中间可能被读请求写回的脏值。

消息/binlog 订阅刷新：用 canal 这类工具订阅 MySQL 的 binlog，库一变就发消息去删/刷缓存。一致性最好、对业务代码侵入最小，但要多维护一套中间件，适合数据量和团队都到了一定规模的项目。

我的取舍原则：先问业务能接受多旧的数据。文章正文晚几秒一致完全无所谓，用“更新库 + 删缓存”就够；账户余额这种就别缓存，或者走强一致方案。别一上来就追求强一致，多数业务根本不需要，徒增复杂度。

前端这块也得跟着理解这条链路。用户点“保存”后，列表接口可能因为缓存还没失效而短时间返回旧数据。我的做法通常是两种：要么保存成功后前端做乐观更新，本地先把新值显示出来；要么对刚提交的数据强制带个跳过缓存的参数回源一次。提示语也别写“保存成功，数据已更新”这种把话说死的，因为后端链路上它可能还没真正“处处更新”。

回头看，加缓存最大的认知升级是：它不是“让接口变快”这么简单的一行 redis.get，而是你主动在系统里引入了一个会过期、会失效、会和数据库不一致的旁路状态，你得为这个状态的所有异常负责。

穿透、击穿、雪崩、一致性，本质上都是在问同一件事——当缓存不在、缓存集体消失、缓存和真相对不上的时候，你的系统会怎样。面试官问缓存，多半也不是想听你背 Redis 命令，而是看你有没有真的在这些边界上摔过、想过。

前端虽然不直接维护 Redis，但只要理解了这条链路，就知道哪些数据天然有延迟、哪些“保存成功”其实是“最终会成功”，从而把页面状态和提示做得诚实又顺手。这种对后端链路的体感，往往比多写两个组件更值钱。
