webpack 4 迁移：默认行为更香了，升级链路也更容易卡哪

2018-03-05
构建与模块化

webpack 4 这种大版本升级，最吸引人的从来不是“版本号变了”，而是它承诺能替你删掉很多你早就不想维护的祖传配置。可升级真正难的地方也恰恰在这里：核心包升级了，不代表周边 loader、插件和脚手架都会同步跟上。

我手上的这个后台系统正好适合做试验。webpack 3 的配置文件加起来六七百行，里面叠着好几任同事的“祖传优化”，谁也不敢动，每次冷启动构建都要一分多钟。webpack 4 的默认行为看起来很香，但真正开始迁移之后，报错也来得一样快。

所以这篇不按发布时间线讲，而是按迁移链路里最容易卡住的点往下拆：核心包、CLI、抽 CSS、vue-loader 和配置收缩到底各自会冒什么问题。

第一个下马威：webpack 不认识自己了

顺带一提，webpack 4 不再支持 Node 4 了，要求 Node 6.11.5 以上，官方推荐直接上 Node 8 用最新的 LTS。我们 CI 上的构建机还停在一个老版本 Node，也是这次一并升的。升级构建工具之前先对一遍运行环境的版本要求，能省掉一轮莫名其妙的语法报错。

mode：新世界的第一道分界线

装好之后再跑，构建能动了，先甩给我一条黄字警告：

mode 是 webpack 4 最重要的新概念：

开发环境：

它直接决定默认优化行为。mode: 'production' 默认开启压缩（UglifyJsPlugin）、Scope Hoisting（作用域提升），并把 process.env.NODE_ENV 设成 "production"；mode: 'development' 关掉压缩、给出更友好的 sourcemap 和模块命名。

那条警告我一开始没在意，结果开发环境的代码莫名其妙被压缩了，断点打不进去，debug 时傻眼——因为不写 mode 时 webpack 按 production 兜底。这条警告不是啰嗦，是真的会改变构建行为，第一时间把两个环境的 mode 显式写上。

写上 mode 之后，老配置里一批东西可以删了。比如手动那行 new webpack.DefinePlugin({ 'process.env.NODE_ENV': '"production"' })，mode 已经帮你做了，留着不报错，但属于冗余。这里有个坑要提醒：如果你只加了 mode 而没删旧的 UglifyJsPlugin，可能出现压缩跑两遍、或者新旧插件版本打架的诡异情况。我的做法是先删掉明显重复的优化配置，让默认行为跑起来，再根据产物分析决定要不要补。

这一步其实是整个迁移里最爽的部分：**六七百行配置删到剩三百多行，删掉的每一行都对着文档确认过"默认行为已覆盖"。**那些没人敢动的祖传优化，借着这次大版本终于有了合法的清理理由——费劲的不是删，是搞清楚它们当初为什么加。

CommonsChunkPlugin 死了，splitChunks 万岁

老项目里这种配置很典型：

webpack 4 直接把 CommonsChunkPlugin 移除了，构建报错，没有商量余地。替代品是 optimization.splitChunks：

从旧的迁到新的，思路上有个根本变化值得说清楚。CommonsChunkPlugin 是"自上而下"指定的：你手动声明哪些是公共 chunk、谁优先级高，多个实例之间还有顺序依赖，经常互相打架。splitChunks 是"自动按规则提取"的：你定一组条件（体积阈值、被引用次数、来源目录），webpack 自己判断哪些模块该拆出来。别用写 CommonsChunkPlugin 的老思维去硬套新配置，我第一天就是想"精确复刻"原来的三个 CommonsChunkPlugin 实例，越写越拧巴，后来干脆先用默认策略跑起来，看主包和 vendor 包是否合理，某个大库进了首屏主包再针对性拆。

迁移时撞上一个具体问题：老项目用 CommonsChunkPlugin 单独抽了一个 manifest（运行时代码）chunk 来稳定 vendor 的 hash。webpack 4 里这个职责改由 optimization.runtimeChunk 接管：

不把 runtime 单独抽出来，每次改业务代码，vendor 包的 hash 也可能跟着变，长缓存就白做了。这个点不在 splitChunks 里，是单独一项配置，迁移时很容易漏掉。

loader 和 plugin：尝鲜期真正的雷区

webpack 4 才发布一周，生态还没完全跟上，报错最多的根本不是 webpack 本身，而是周边的 loader 和 plugin。遇到构建错误别只盯着 webpack 版本，先看错误栈里实际报错的是谁。

栽得最狠的是 extract-text-webpack-plugin。这个老牌抽 CSS 插件在 webpack 4 下直接不兼容，构建报一堆 Tapable.plugin is deprecated 之类的错。查 issue 才知道两条路：一是装它的 4.0.0-beta.0，社区先顶着用；二是官方这几天刚发布了一个专门的新插件 mini-css-extract-plugin，还是 0.x 版本，被定为以后的正路。我在分支上把两条路都试了，beta 版能跑但警告不断，最后咬牙上了新插件——反正整个升级就是在尝鲜，不差这一个。配置写法整个变了，ExtractTextPlugin.extract({...}) 那套要换成在 module.rules 里用 MiniCssExtractPlugin.loader 替代 style-loader：

新插件毕竟刚出生，issue 列表还很热闹，我在生产构建上盯了好几遍产物才敢合分支。

vue-loader 也闹了脾气。当前的 14.x 在 webpack 4 下能跑，但部分场景会冒出 deprecation 警告，去仓库一看，作者已经在讨论专门适配 webpack 4 的下一个大版本了，据说要引入一个配套的 plugin、写法会有大改。眼下我把 vue-loader 和 css-loader 升到各自最新的兼容小版本，先稳住。html-webpack-plugin 则要升到刚发的 3.x 才认 webpack 4。这几个版本卡点没事先列清单，升级过程就是不停地"改一个错冒出下一个错"，特别消磨耐心。教训是：动手前先把官方 migration guide 和各 plugin 的 webpack 4 支持状态列个清单，比边撞边查高效得多——尝鲜期尤其如此，很多插件的"支持 webpack 4"就发生在这一两周，issue 比文档新。

升级步骤我最后收敛成一套保守流程：

  1. 升 webpack 和 webpack-cli
  2. 保持业务代码不动
  3. 逐个升级 loader，一次一个
  4. 跑开发环境
  5. 跑生产构建
  6. 对比 dist 产物

一次升级太多依赖，失败后根本不知道是谁干的。

官方吹的构建提速，要用数据验

发布博客里说构建速度最高能快 98%。这种数字听听就好，自己的项目自己测：

我在迁移前后各跑了三次取平均：webpack 3 冷启动构建 74 秒，webpack 4 降到 41 秒。没有 98% 那么神，但接近砍半，团队每天几十次构建，这个提升是实打实的。

stats.json 可以拖进官方的 analyse 工具，或者用 webpack-bundle-analyzer 出矩形树图：

树图一眼就能看出谁占体积大头。我这次靠它抓到两个和 webpack 版本无关的老问题：一是 lodash 整包被打进来了，其实只用到几个方法，换成 lodash/get 这种按需引入就好；二是 moment 把全部语言包都带上了，体积比业务代码还大。这俩处理完，生产包直接小了一截。如果构建快了但包体大了很多，这次升级也不算成功——我盯的就是冷启动构建时间和生产包体积这两个数。

说到速度，webpack 4 配合 cache-loader 或 HardSourceWebpackPlugin 做二次构建缓存，热更新还能再快一档。但缓存类插件我有顾虑：偶尔缓存脏了，改了代码不生效，排查反而浪费时间。所以只在确实嫌慢的大项目开发环境开，CI 上一律禁用，保证线上构建始终是干净的。

一周之后

分支合进主干那天，我在群里发了两个数字：构建 74 秒到 41 秒，配置六七百行到三百出头。有同事问值不值得这么早升，我的答案是分情况：有独立分支、有产物对比手段、项目又苦构建久矣，那现在升，坑都是新鲜的，社区 issue 里全是并肩踩坑的人；如果构建链路复杂、插件依赖冷门，等生态再跟进一两个月也不迟。

对我来说这次尝鲜最大的收获不是 41 秒，而是被迫把每一行配置的存在理由重新问了一遍。**把大版本迁移当成一次清理和学习配置的机会：先保证能跑，再逐步删冗余，用数据驱动优化。**新工具会一直来，理解每项改动的原因，比追着版本号跑重要得多。
