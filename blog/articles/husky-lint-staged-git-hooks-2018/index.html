Husky 和 lint-staged 落地记：一个没删的 console.log 堵了流水线二十分钟之后

2018-08-23
构建与模块化

我们组今年初接手一个三年前的老项目，第一周我就被各种鸡毛蒜皮的提交搞得够呛。有人 var 和 let 混着用，有人缩进是 tab 有人是空格，还有人把 console.log 直接提交进了主分支。这些都不是什么大 bug，但每次 code review 都要花时间挑这些毛病，review 的人和被 review 的人都烦。

最离谱的一次，我合并完一个同事的分支，本地一跑就报 ESLint 错误，结果 CI 因为这个挂了红，把后面排队等部署的几个分支全堵住了。一个没删干净的未使用变量，让整条流水线停了二十多分钟。那天我就下决心，必须把这类低级问题挡在提交之前，而不是等 CI 红了才发现。

CI 当然能兜底，但 CI 的反馈链路太长了：推上去、排队、装依赖、跑完整流程，快则三五分钟，慢则十几分钟。等你看到红叉，注意力早就切到别的事情上去了，再切回来修，上下文丢得七七八八。本地的 Git hook 不一样，它在 git commit 那一刻就给你反馈，错就错在眼前，改起来也最便宜。Husky 和 lint-staged 就是干这个的：前者负责把脚本挂到 Git 的钩子上，后者负责让检查只针对这次改动的文件，而不是整个仓库。

结果第二天就被同事在群里 @ 了。我们那个项目 src 下有近两千个文件，全量 ESLint 一遍要四十多秒。改一行代码、提交一次、等四十秒，谁受得了？没两天大家就学会了 git commit --no-verify，等于这道关形同虚设。

问题的关键在于：这次提交只动了两三个文件，凭什么要检查全部？ lint-staged 解决的就是这件事——它从 Git 暂存区（staged）拿到本次要提交的文件列表，把这个列表喂给你配置的命令，只检查这些文件。

改成这样之后，提交一两个文件基本是秒级反馈。这里有个容易踩的细节：数组里的命令是按顺序执行的，lint-staged 会把匹配到的文件路径追加在每条命令后面。也就是说上面实际执行的是 eslint --fix file1.js file2.vue，而不是 eslint --fix 然后再读配置去扫目录。所以千万别在命令里再写上路径或 glob，否则就变成全量了，这个坑我亲手踩过。

最后那行 git add 也很关键。因为 eslint --fix 和 prettier --write 会就地改写文件，如果不重新 git add，被自动修复后的内容不会进入这次提交，提交进去的还是修复前的版本。

这里顺带说说大仓库下"只对暂存文件跑"为什么不只是快一点，而是关乎这道关能不能活下来。我们那个 src 近两千文件的项目，全量 lint 一次四十多秒，如果每次提交都这样，一天提交十几次，光等 lint 就耗掉小半个钟头——任何一道慢到让人想绕过的检查，最终都会被绕过，这不是纪律问题，是人性。lint-staged 从暂存区取文件列表，本质上是把检查成本从"和仓库规模成正比"压成了"和本次改动量成正比"。改一个文件就检一个文件，仓库再大也不影响单次提交的体感。这个设计是它能在大仓库里落地的前提，而不是锦上添花。

大仓库还有个能顺手拿的加速点：lint-staged 默认会并发跑不同 glob 分组的任务。也就是 *.{js,vue} 那组和 *.{json,md} 那组是并行的，互不等待。同一组内部的命令数组才是串行（因为后一条依赖前一条 --fix 的结果）。知道这个分界，配置时就有意识地把彼此独立的文件类型拆成不同 glob，让它们并行，而不是笼统地用一个大 glob 把所有类型串成一条长链。

这里还藏着一个我栽过的“部分暂存”坑。假设一个文件你只 git add 了其中几行（用 git add -p 那种），剩下的改动还在工作区没暂存。这时 lint-staged 跑 --fix 改的是磁盘上的整个文件，连你没打算提交的那部分一起格式化了，最后 git add 又把整个文件塞进暂存区——你以为只提交了那几行，结果一大坨没准备好的改动也跟着上去了。我在 lint-staged 的 GitHub 上翻到过讨论这个问题的 issue，作者有意做自动 stash 来保护未暂存的改动，但我们在用的 7.x 上还没有好方案。所以那阵子我养成了习惯：要做部分提交时，先确认没有混在一起的脏改动，宁可分两次干净地提。工具再贴心，也架不住边界情况，自己心里得有数。

版本背景交代一下：年初接手项目时里面装的还是 husky 0.14，hook 是写在 package.json 的 scripts 里、靠 precommit 这种命名约定生效的。这个月我把它升到了 1.0 的 rc 版，配置挪进了独立的 husky.hooks 块——本文以新写法为准。rc 版敢不敢用见仁见智，我们先在内部项目吃螃蟹，跑了两周还算安分；你如果用的还是 0.14，记得把下面配置里的 husky.hooks 换回 scripts.precommit，两代写法差别不小。

Husky 是怎么把脚本塞进 Git 的

Git 本身就支持 hook，机制很简单：.git/hooks/ 目录下放着一堆脚本，命名固定，比如 pre-commit、commit-msg、pre-push。你 git commit 的时候，Git 会去执行 .git/hooks/pre-commit，如果这个脚本退出码非零，提交就被中止。

但 .git 目录不会被纳入版本控制，你没法把 hook 脚本提交到仓库让别人共享。Husky 干的事情就是：在 npm install 的时候，通过一个 postinstall 钩子，自动往 .git/hooks/ 里写入桥接脚本，让 Git 的钩子转而去读 package.json 里你的配置。这样团队每个人 clone + install 之后就自动装上了同一套 hook。也正因为它挂在 postinstall 上，.git/hooks 里的桥接脚本是每次 npm install 重新生成的——所以万一有人的 hook 没生效，让他重跑一次 npm install 往往就好了，不必手动去 .git/hooks 里翻。

提交信息规范化这件事，单看好像有点强迫症，但它的回报在后面。我们统一了前缀之后，用 conventional-changelog 这类工具就能直接从提交记录生成版本变更日志，发版时不用再手工扒拉这次改了啥；fix: 和 feat: 还能驱动语义化版本号自动 bump。也就是说 commit-msg 这道关换来的不只是好看的 git log，而是后面一整条自动化链路的输入。当然规则别一上来就卡死，我们最初只校验类型前缀和不超长，body 之类的留作可选，门槛太高同样会逼出 --no-verify。

commitlint 的规则也值得挑着开。@commitlint/config-conventional 那套默认规则里有几条是硬性的、有几条是可以放宽的。我们保留了 type-enum（类型必须是 feat/fix/docs/refactor 等约定内的值）和 header-max-length（标题别太长，一般卡 72），因为这两条直接影响 changelog 生成和 git log 可读性；而 subject-case（标题首字母大小写）这类偏个人风格的，我们直接关掉了，中文提交信息谈大小写本来就没意义。规则集不是越严越好，是越"和后续自动化真正相关"越好，跟自动化无关的规则卡得越死，越是在给 --no-verify 制造理由。

提交时这些会自动跑。检查失败提交就被拦下，开发者修完重新 git add、再 commit 即可。第一次给团队装上的时候，有个同事提交被拦了，还以为 Git 坏了，跑来问我。所以上线这种东西最好提前在群里说一声，并写清楚失败了怎么办。

细心的人会发现 .ts 的链路里没有类型检查，这是我交过学费的点：别试图在 pre-commit 里对暂存文件跑 tsc --noEmit。lint-staged 会把文件名追加到命令后面，而 tsc 一旦接收具体文件名就会忽略 tsconfig.json，路径别名、全局类型全不认，报一堆假错——我对着那堆莫名其妙的报错查了半天才反应过来。全量 tsc --noEmit 又太慢，跟"提交要快"的诉求直接冲突。所以我的结论很干脆：类型检查不进 pre-commit，丢给 CI 全量跑，那里才是它该待的地方。

pre-commit 太快、CI 太慢，中间还缺一档：pre-push

用了一阵之后我发现钩子这条链上有个空档。pre-commit 快到秒级，只跑格式化和增量 lint；CI 完整但反馈要三五分钟起。中间那些"比格式化重、但又不该等到 CI 才发现"的检查——比如一轮完整的单元测试——放哪都别扭：塞进 pre-commit，每次提交都等，太重；全交给 CI，等推上去排队才发现挂了，白白占一轮流水线。

Git 的 pre-push 钩子正好补这一档。它在 git push 那一刻触发，而人一天提交很多次、push 的次数少得多，所以在这里跑一次全量测试，节奏是能接受的：

这样就形成了三档递进：pre-commit 管格式和当前改动，快到无感；pre-push 在推之前把全量单测跑一遍，把"编译不过、单测挂了"这类问题挡在推送之前，省掉一趟 CI 往返；CI 在干净环境里跑构建、集成测试、完整 lint，做最终裁决。每一档都比后一档快、比前一档全，问题在哪一档暴露，就在哪一档最便宜地修掉。

pre-push 也有它的分寸。全量 E2E、需要起真实后端的集成测试，我一样不往里放——push 前等两三分钟还勉强，等十分钟没人受得了，--no-verify 又会回来。pre-push 我只放"纯本地、不依赖外部服务、几十秒能跑完"的那部分，再重的坚决留给 CI。

还有个细节：pre-push 钩子拿得到"要推到哪个远端、哪些分支"的参数（Git 通过标准输入传进来）。理论上可以据此做"只在推 master 时才跑全量测试、推个人特性分支时放宽"的差异化策略。我们没做那么细，觉得规则一分岔就容易出"我这条分支怎么没拦住"的困惑，还是所有 push 一视同仁更省心——但知道有这个口子在，将来真需要精细控制时不至于抓瞎。

规则要轻，别把 pre-commit 当 CI 用

pre-commit 的核心诉求是快，快到大家感觉不到它存在。我的经验是这道关只放这些：

  • eslint --fix：能自动修的直接修
  • prettier --write：格式问题机器解决，人别操心
  • 改动文件相关的类型检查（如果做得到增量）
  • 跟改动强相关的少量单元测试

而下面这些，我试过往 pre-commit 塞，最后全部撤了：

  • 全量构建（webpack 打包一次几十秒到几分钟，提交一次等这么久没人能忍）
  • 全量 E2E（动辄几分钟，还可能 flaky，本地环境也未必齐全）
  • 慢的集成测试、跨服务测试

有阵子我图省事，把 jest（全量）挂在了 pre-commit，结果随着用例越来越多，提交越来越慢，同事的 --no-verify 又回来了。后来我改成只用 jest 的 --findRelatedTests，让它只跑跟本次改动文件相关的测试：

--findRelatedTests 会根据模块依赖图找出受影响的测试文件，--bail 让它一失败就停。这样提交一个文件通常只跑几个相关用例，几秒钟搞定。慢的、全量的，统统留给 CI。要注意 --findRelatedTests 是靠静态依赖图反查的，如果你的测试是通过运行时动态 require、或者纯 mock 数据间接覆盖某个模块，它可能漏判、认为这个改动"没有相关测试"而一个用例都不跑——所以它是加速手段，不是完整性保证，真正的完整覆盖还得靠 pre-push 或 CI 里那趟全量。

一句话：提交前的检查要快，CI 要完整，两者职责不同，别混。

Git 给了逃生口：

加上它就跳过所有 pre-commit / commit-msg 钩子。我不主张完全禁止它——有时候你就是要提交一个半成品 WIP 临时存一下，或者紧急修复线上故障，没工夫等检查。逃生口该留。

但如果你发现团队里天天有人在 --no-verify，那不是人的问题，是配置的问题。要么 hook 太慢，要么规则太激进（比如把一些有争议的、还在讨论的 lint 规则设成了 error 级别，逼着大家就范）。这种时候正确的做法是回头优化规则和速度，而不是发文件三令五申禁止绕过。工具应该让正确的路成为最省事的路，靠纪律去对抗工具的别扭，长期一定输。

我们当时就专门花了半天，把几条争议大的规则从 error 降到 warn，把全量测试换成增量，--no-verify 的使用频率肉眼可见地降下来了。

ESLint 和 Prettier 别在同一条链上打架

把 eslint --fix 和 prettier --write 串在一条 lint-staged 链里，一开始给我惹过一个来回打架的麻烦：两个工具都想管格式，规则又不完全一致。ESLint 里如果开着 semi、quotes、indent 这类格式规则，Prettier 又按自己的一套排版，结果就是一个文件被 prettier --write 排成 A 样，紧接着 eslint --fix 又改回 B 样，甚至两边规则相冲时 eslint --fix 修不动、只能报 error 把提交拦下，人还一脸懵。

2018 年社区已经把这条边界理清楚了，做法是让两个工具各管一摊：格式交给 Prettier，代码质量交给 ESLint。落地就是装 eslint-config-prettier，把它挂在 ESLint 配置 extends 的最后一位：

eslint-config-prettier 的作用是关掉 ESLint 里所有和 Prettier 冲突的格式类规则。这样 ESLint 只负责揪 no-unused-vars、no-undef 这类真正的代码问题，排版彻底让给 Prettier，两者不再在同一处较劲。理清这层之后，lint-staged 那条 eslint --fix 后接 prettier --write 的链才真正稳定下来，不再出现改来改去、反复触发的怪现象。

本地 hook 不是安全边界，CI 才是

这点必须说清楚，因为我见过有人装了 husky 就以为高枕无忧，把 CI 的检查给砍了，这个念头必须打消。

本地 hook 有太多可以绕开的方式：有人没跑 npm install，hook 根本没装上；有人用的 Git 客户端（某些 GUI 工具）不走标准 hook；有人直接 --no-verify；甚至有人本地 Node 版本不对，hook 静默失败。本地 hook 只是便利，不是保障。

这里面"GUI 客户端不触发 hook"最隐蔽，因为它不报错、静默通过。有些图形化 Git 工具执行提交时用的是自己内置的、精简过的环境，PATH 里找不到 node，桥接脚本一执行就失败或被跳过，用户还以为检查跑过了。所以真要把关，绝不能指望"大家本地都装好了 hook 且都用命令行提交"这种一厢情愿的前提。

我们的分支保护规则要求这条流水线必须绿才能合并。本地 hook 负责把九成的低级问题在提交那一刻就拦掉、给开发者最快的反馈，CI 负责最终把关、对所有人一视同仁。两者叠加，既快又稳。

有个 CI 相关的坑我也补一下，是配 CI 时冒出来的。husky 靠 postinstall 往 .git/hooks 写桥接脚本，可 CI 环境里往往根本没有 .git 目录（浅克隆、或者构建缓存里只有代码没有 git 信息），husky 的 postinstall 就会打印一串警告甚至报错，让 npm ci 那一步看着像出了问题。更本质的是，CI 里压根不需要安装 Git hook——CI 不 git commit，装了也没用。所以在 CI 脚本里加一个环境变量把 husky 的安装跳过更干净：

这也顺带点破一件事：本地 hook 和 CI 检查的关系是"分工"，不是"两遍跑同一件事"。有人误以为要在 CI 里也把 hook 触发一遍才算保险，其实不然——CI 要做的是直接、显式地跑 npm run lint、npm test、npm run build 这些命令，它检查的是"这份代码本身合不合格"，跟本地有没有装 hook、开发者提交时钩子跑没跑，完全无关。hook 是给写代码的人用的即时反馈，CI 是给合并这个动作用的准入闸门，两者输入相同、目的不同，各跑各的，不必也不该互相依赖。

换行符：Windows 和 Mac 混编时的隐形提交噪音

装上 Prettier 自动格式化之后，团队里冒出过一类奇怪的 diff：明明只改了一行逻辑，Git 却显示整个文件几百行全变了。查下来是换行符——有人在 Windows 上开发，编辑器保存成 CRLF，Mac 和 Linux 上是 LF，prettier --write 一跑，把整个文件的换行统一成它认定的样式，于是每一行都算"改过"。这种提交混进来，code review 时想找出真正改动的那一行得大海捞针，git blame 也被搅乱。

根治要靠两处配合。一是仓库根目录放一个 .gitattributes，让 Git 在提交时统一把文本文件的换行归一化成 LF：

二是 Prettier 侧显式指定换行样式，别让它跟着操作系统跑：

两边都钉死成 LF 之后，换行符引发的整文件 diff 就消失了。这件事和 hook 本身没直接关系，但它是自动格式化落地后一定会遇到的配套问题——工具帮你统一了风格，也就意味着任何不统一都会被它放大成一次改动，换行符这种平时看不见的差异首当其冲。跨平台的团队，这两个配置最好在接入 lint-staged 的同一时间就一并加上，免得头一周被满屏假 diff 搞得人心惶惶。

把低级格式问题交给 husky + lint-staged，能让 code review 把时间花在设计与逻辑上。原则很简单：检查要快、规则要小且明确、能自动修的就自动修。别试图把 CI 的全部检查挪到 pre-commit，职责分清楚才能长期奏效。
