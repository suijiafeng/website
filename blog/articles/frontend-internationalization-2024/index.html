前端国际化工程：不只是把中文替换成英文

2024-10-31
前端基础构建与模块化

国际化很容易被低估成“加一个语言包”。

真正做起来会发现，问题远不止文案替换。英文比中文长，德语更长；日期格式不同，货币符号不同；复数规则不同；有些语言从右往左；路由、SEO、缓存、翻译流程都会受影响。

我第一次做国际化时，只把页面文案抽成了 JSON。上线英文版后，按钮撑爆、表格列错位、日期仍然是中文格式、接口错误还是中文。那次之后我明白，国际化是工程能力，不是翻译任务。

国际化最怕的是语言包没人维护。

翻译内容也要有上下文。只给翻译人员一个 submit，他不知道是“提交订单”还是“提交审批”。key、截图、说明都很重要。

我的经验是，语言包要按模块维护，新增文案和功能代码一起提交。不要等上线前统一补翻译，那时最容易漏。

我的国际化清单

做国际化前，我会确认：

  • 文案 key 是否稳定且按模块组织
  • 是否避免句子拼接
  • 日期、数字、货币是否使用 locale 格式化
  • 布局是否能容纳长文案
  • 是否需要 RTL，CSS 是否使用逻辑属性
  • 路由、SEO、缓存是否带语言维度
  • 缺失翻译是否能在开发或 CI 暴露
  • API 错误是否用 code 做本地化映射

国际化不是把中文翻译成英文，而是让产品能在不同语言、地区和书写习惯下稳定运行。越早把这些工程边界想清楚，后面扩语言越轻松。
