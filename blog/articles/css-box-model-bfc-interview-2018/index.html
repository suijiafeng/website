盒模型和 BFC：CSS 面试题背后，其实是布局边界

2018-07-26
CSS前端基础

CSS 面试里经常问盒模型和 BFC。

我刚工作那两年特别烦这种问题，觉得这就是背书：盒模型不就是那几层嘛，BFC 不就是 overflow: hidden 嘛，问这个能看出什么水平？后来自己写页面写多了才发现，面试官问这两个，其实是在变相确认你写布局的时候脑子里有没有“边界”这个概念——为什么设置了宽度还被撑开？为什么两个 margin 莫名其妙合并了？为什么父元素死活包不住浮动子元素，高度塌成一条线？这些天天遇到的“怪现象”，背后全是这两条规则在起作用。

我自己的体会是：盒模型决定一个元素到底占多大地方，BFC 决定一块区域和外面是不是互相干扰。把这两件事想清楚，CSS 调试就从“瞎试”变成“能推理”。下面这些都是我在真实项目里被坑过、然后回头补的课，技术背景是 2018 年——还在用 float 做布局，flex 刚普及，IE 也还没完全退场。

IE 盒模型为什么会被人骂

面试还经常顺带问一句“标准盒模型和 IE 盒模型有什么区别”。这其实是一段历史遗留。

早期 IE（IE6 在怪异模式下）的盒模型是另一套算法：你写的 width 直接就是元素的总宽度（含 padding 和 border），content 区会被 padding 和 border 往里挤。也就是说，同样一段代码：

在标准浏览器里元素实际占 242px，在老 IE 怪异模式下却只占 200px，里面的内容区被压成了 158px。同一份 CSS 两套渲染结果，当年跨浏览器适配能把人逼疯，所谓的“盒模型 bug”大半是这么来的。

后来 W3C 把这两种算法都标准化进了 box-sizing：

  • content-box：标准盒模型，width 只算内容区，这是默认值。
  • border-box：IE 那套，width 算到 border 外边缘为止。

讽刺的是，当年被当成 bug 的 IE 算法，反而是大家现在更想要的那套。所以与其说 IE 盒模型“错了”，不如说它只是“没按标准来”，而标准后来又承认了它的合理性。理解这段，再看 box-sizing 就顺理成章了。

还有一点容易忽略：box-sizing 只影响 width / height 的计算口径，对 margin 完全没作用。margin 永远是加在盒子外面的，不管你是哪种盒模型。这也引出下一个坑——margin 合并。

margin 合并

两个垂直方向相邻块元素的 margin 可能合并：

它们之间的距离是 30px，而不是 50px——取两者里较大的那个，不是相加。这个规则刚开始很反直觉，我第一次遇到是做一个文章列表，每个 item 上下都给了 margin: 20px 0，本以为相邻两项之间会有 40px 间距，结果量出来只有 20px。当时还以为是浏览器吞了我的样式，查了文档才知道这是规范规定的“相邻外边距折叠”（margin collapsing）。

折叠只发生在垂直方向（block 方向），水平方向的 margin 从来不合并。而且只对普通流里的块级元素生效——一旦元素是 float、是 inline-block、是绝对定位，或者父子之间隔着 BFC，折叠就不会发生。这也是为什么后面讲 BFC 的时候，它能顺手解决一部分 margin 问题。

父子元素之间也可能发生 margin 合并：

子元素的 margin 可能“跑到”父元素外面——你想让子元素离父元素顶部 20px，结果整个父元素连同它的背景一起往下挪了 20px，子元素和父元素顶部反而贴在一起。这个坑我栽得最多的场景是做卡片：卡片标题加了 margin-top 想和卡片边框留点空，结果整张卡片往下漂，标题却顶到了卡片上沿，背景色露出一截在卡片上方。

之所以发生，是因为父子之间没有任何“隔断”——没有 border、没有 padding、没有 BFC，子元素的上 margin 就直接和父元素的上 margin 折叠到一起，穿透了出去。

什么是 BFC

BFC 可以理解成一个独立的布局区域。里面的元素布局不会影响外面，外面的浮动也不会影响里面。

常见触发方式：

  • overflow: hidden
  • display: flow-root
  • float 非 none
  • position: absolute
  • display: inline-block

老项目里最常见的是 overflow: hidden，因为它兼容性最好、写法最短，副作用大家也基本能接受。

我自己理解 BFC 的方式是把它想象成一个“结界”：结界里发生的事（浮动、margin 折叠）不会漏到外面，外面的浮动也进不来影响里面的排版。一旦某个元素满足了上面任意一个触发条件，它就升级成了一个 BFC 容器。这套“结界”心智模型，对解释下面几个经典场景特别好用。

这里有个坑：不同触发方式的副作用差别很大。float 和 position: absolute 会改变元素本身的脱标行为，inline-block 会让宽度收缩，overflow: hidden 会裁剪溢出内容。真正“只开 BFC、不带其他副作用”的，其实是 display: flow-root，可惜当时支持度还不够。所以挑触发方式之前，得先想清楚你愿意接受它附带的哪些行为。

但我在真实项目里更常用 clearfix，原因前面也提过——overflow: hidden 会裁剪溢出内容，要是子元素里有个带阴影的卡片或者绝对定位的角标，可能就被切掉了。clearfix 只清浮动，不裁内容：

这是当年几乎每个项目都会抄进 base.css 的“万能清浮动”。它的原理和 BFC 不一样：它是在父元素末尾插入一个看不见的块级元素，让这个元素 clear: both 去“顶”住前面的浮动，从而把父元素高度撑开。很多脚手架（比如 bootstrap）里都内置了这段，团队里直接 class="clearfix" 一加就完事。

我的选择标准很简单：单纯想清浮动、又怕裁剪内容，用 clearfix；既想清浮动、又顺便想隔离 margin 折叠、还确定内部没有需要溢出的东西，才用 overflow: hidden。

BFC 避免文字环绕浮动

.main 创建 BFC 后，不会和左侧浮动重叠。这在左右布局里很常见。

这个技巧我以前做后台管理系统的两栏布局时天天用：左边固定宽度的侧边栏 float: left，右边主内容区不写宽度、只给一个 overflow: hidden。神奇的地方在于，右侧的 BFC 会自动避开左侧浮动占据的区域，剩下多少空间它就占多少，相当于一个“自适应剩余宽度”的效果，连百分比都不用算。

它的原理还是“结界”：BFC 的边框不会和外部浮动元素重叠，所以浏览器会把 .main 整体往右推到不和 .left 重叠的位置。在 flex 还没普及的那几年，这是做自适应两栏最干净的写法之一。当然 2018 年我新写的布局基本都直接上 flex 了，这套 float + BFC 的方案更多是用来读懂和维护老代码。

不要滥用 overflow hidden

overflow: hidden 能触发 BFC，但也会裁剪内容。

如果里面有下拉菜单、阴影、浮层，可能被裁掉。用它之前要确认没有溢出内容需要展示。

我吃过一次大亏：给一个列表容器随手加了 overflow: hidden 清浮动，过了几周产品要在每行右边加一个鼠标悬停才出现的操作下拉菜单，结果下拉一展开就被容器边缘齐刷刷切掉一半，怎么调 z-index 都没用——因为根本不是层级问题，是父容器把溢出部分裁了。当时排查了好久才想起来是早先那句 overflow: hidden 埋的雷。后来的教训是：用 overflow: hidden 当清浮动手段时，最好写个注释说明用途，免得后人（包括几周后的自己）看不出它是来清浮动的，还是真的要裁内容。

能用 clearfix 解决清浮动时，不一定非要用 overflow。规则就是：overflow: hidden 是“顺便能清浮动”，它的本职工作是裁剪溢出，别把副作用当主功能用。

我后来再看这块，基本不会把盒模型和 BFC 当成两道孤立的题背。

盒模型管的是尺寸怎么落到页面上，BFC 管的是一块区域怎么和外面的浮动、margin、子元素高度划清边界。宽度被撑开、margin 合并、父元素高度塌陷、浮动把布局挤歪，这些问题看着零散，往下拆大多都绕不开这两套规则。把规则想明白以后，调 CSS 时会少很多“试一下看行不行”的动作。
