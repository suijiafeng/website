盒模型和 BFC：从 margin 合并到清除浮动，把布局边界讲清

2018-07-26
CSS前端基础

盒模型和 BFC 常被写成零散的面试题，真落到页面上，考的其实一直是同一件事：布局边界。一个元素明明写了 width，为什么视觉上还是被撑大；两个上下相邻的块级元素，为什么间距有时相加、有时塌成一个；父元素为什么会包不住浮动子元素。

组里那次 CSS 分享，前辈没有让我继续讲组件案例，而是直接把问题拽回这些基础处境：width: 200px、padding: 20px、border: 1px solid 的 div 到底占多宽；box-sizing 为什么会改答案；margin 合并什么时候发生，什么时候不会；BFC 为什么能清浮动，又为什么不只是"加个 overflow: hidden"这么简单。

问题一旦连起来，我原先那套"项目里踩过坑，所以大概会用"的理解立刻散了。**前辈追问的不是名词定义，而是我脑子里有没有一张完整的布局边界图。**于是我把这条追问链重新理了一遍，把每个现象、规则和副作用串回同一个框架里。

第二问：IE 盒模型为什么会被人骂

"为什么会有两套盒模型？"这一问考的是历史。

早期 IE（IE6 在怪异模式下）的盒模型是另一套算法：你写的 width 直接就是元素的总宽度（含 padding 和 border），content 区被 padding 和 border 往里挤。同样一段代码：

在标准浏览器里元素实际占 242px，在老 IE 怪异模式下却只占 200px，里面的内容区被压成 158px。同一份 CSS 两套渲染结果，早年间做跨浏览器适配能把人逼疯，所谓的"盒模型 bug"大半是这么来的。

后来 W3C 把两种算法都标准化进了 box-sizing：

  • content-box：标准盒模型，width 只算内容区，默认值。
  • border-box：IE 那套，width 算到 border 外边缘为止。

讽刺的是，当年被当成 bug 的 IE 算法，反而是大家现在更想要的那套——写 width: 200px 就占 200px，这才符合直觉。所以与其说 IE 盒模型"错了"，不如说它只是"没按标准来"，而标准后来又承认了它的合理性。这段历史我分享会上讲全了，算是挽回一点分。

第四问：30 还是 50——margin 合并，我开始冒汗的地方

"上面的元素 margin-bottom: 20px，下面的 margin-top: 30px，间距多少？"

我答对了结果：30px，取两者里较大的那个，不是相加。这是规范规定的"相邻外边距折叠"（margin collapsing）。我第一次遇到它是做文章列表，每个 item 上下都给了 margin: 20px 0，本以为相邻两项间距 40px，量出来只有 20px，当时还以为浏览器吞了我的样式。

但接下来的追问我就磕磕绊绊了："什么情况下不折叠？"完整答案是：折叠只发生在垂直方向（block 方向），水平 margin 从来不合并；而且只对普通流里的块级元素生效——一旦元素是 float、是 inline-block、是绝对定位，或者两者之间隔着 BFC 边界，折叠就不会发生。所以"怎么让间距变成 50px"至少有三条路：把其中一个改成 inline-block、给一个包一层开了 BFC 的容器，或者最实在的——别对着折叠规则较劲，间距只从一个方向给（比如统一只用 margin-bottom），从源头绕开。

然后是我最心虚的追问："父子之间会折叠吗？"会，而且这是我实际项目里栽得最多的：

子元素的 margin 会"穿"到父元素外面——你想让子元素离父元素顶部 20px，结果整个父元素连同背景一起往下挪了 20px，子元素反而和父元素顶部贴在一起。我栽得最疼的场景是做卡片：卡片标题加 margin-top 想和卡片边框留点空，结果整张卡片往下漂，标题顶到卡片上沿，背景色露出一截在卡片上方。

之所以发生，是因为父子之间没有任何"隔断"——没有 border、没有 padding、没有 BFC，子元素的上 margin 就直接和父元素的上 margin 折叠到一起，穿透出去了。解决方式好几种，本质都是塞一个隔断：

第五问：BFC 到底是什么，触发方式效果一样吗

"你刚才说 overflow: hidden 能解决，为什么能？"——这就是把我问到语塞的那一问。答案是 BFC。

BFC 可以理解成一个独立的布局区域。里面的元素布局不会影响外面，外面的浮动也不会影响里面。我当场给自己造了个心智模型：结界。结界里发生的事（浮动、margin 折叠）不会漏出去，外面的浮动也进不来。一旦某个元素满足触发条件，它就升级成一个 BFC 容器。

常见触发方式：

  • overflow: hidden
  • display: flow-root
  • float 非 none
  • position: absolute
  • display: inline-block

而前辈那句"它们效果一样吗"，才是这道题的真正分水岭。开出来的 BFC 是一样的，副作用完全不一样：float 和 position: absolute 会让元素本身脱离普通流，布局整个变掉；inline-block 会让宽度收缩成内容宽；overflow: hidden 会裁剪溢出内容。真正"只开 BFC、不带其他行为"的只有 display: flow-root，IE 全不认，用在生产里就是埋雷。所以挑触发方式之前，得先想清楚你愿意接受它附带的哪些行为——老项目里 overflow: hidden 最常见，不是因为它最好，是因为它兼容性最好、写法最短、副作用大家基本能接受。

这个答案我分享会当场只说出了一半。现在把它补完整，下次谁再问，我能从"结界"讲到每种触发方式的代价。

但真实项目里我更常用 clearfix，原因前面已经埋下了——overflow: hidden 会裁剪溢出内容，子元素里要是有带阴影的卡片或绝对定位的角标，可能就被切掉。clearfix 只清浮动，不裁内容：

这是几乎每个项目都会抄进 base.css 的"万能清浮动"。它的原理和 BFC 不一样：在父元素末尾插入一个看不见的块级元素，让它 clear: both 去"顶"住前面的浮动，从而撑开父元素高度。Bootstrap 这类框架里都内置了这段，团队里 class="clearfix" 一加就完事。

我的选择标准：单纯清浮动、又怕裁内容，用 clearfix；既想清浮动、又顺便想隔离 margin 折叠、还确定内部没有需要溢出的东西，才用 overflow: hidden。

第七问：两栏自适应布局，float + BFC 的老手艺

前辈最后出了道小布局题："左边栏固定 200px，右边自适应，不用 flex 怎么写？"这题我熟，做后台管理系统时天天写：

左边固定宽度浮动，右边主内容区不写宽度、只给一个 overflow: hidden。神奇的地方在于，右侧的 BFC 会自动避开左侧浮动占据的区域，剩多少空间它就占多少，相当于"自适应剩余宽度"，连百分比都不用算。原理还是"结界"：BFC 的边界不会和外部浮动元素重叠，浏览器会把 .main 整体推到不和 .aside 重叠的位置。这也顺带解决了文字环绕浮动的问题——不开 BFC 时 .main 里的文字会绕着浮动元素排。

我还顺嘴提了圣杯和双飞翼布局——三栏、中间自适应且优先渲染，靠 float 加负 margin 把左右两栏"拉"上去。前辈笑了笑说不用展开，"现在都 flex 了"。确实，现在新写的布局我基本直接上 flex，这套 float + BFC + 负 margin 的手艺，更多是用来读懂和维护老代码，偶尔翻出来给新人讲讲历史。

倒是他补了一个我没防备的小追问："两个 display: inline-block 的元素并排，中间那条几像素的缝哪来的？"我答上来了：HTML 源码里标签之间的换行和空格被渲染成了一个空白符，处理办法要么标签写成一行不留空隙，要么父元素 font-size: 0 再在子元素上重设字号。inline-block 参与的是行内格式化上下文，空白符、vertical-align 基线对齐这些行内规则都会掺和进来——图片底部那条神秘的 3px 空隙也是同一族问题，给图片 display: block 或 vertical-align: bottom 就没了。块级世界的边界归 BFC 管，行内世界的怪事大多归基线和空白符管，这两套规则分清楚，CSS 的"灵异现象"能少一大半。

第八问，也是最后一问

分享会临近尾声，前辈又问："给一个列表容器加了 overflow: hidden 清浮动，几周后要在每行加一个 hover 出现的下拉菜单，会发生什么？"

这题我秒答，因为它就是发生在我身上的事故：下拉一展开就被容器边缘齐刷刷切掉一半，怎么调 z-index 都没用——根本不是层级问题，是父容器把溢出部分裁了。我当时排查了好久才想起来是早先那句 overflow: hidden 埋的雷。教训是：用 overflow: hidden 当清浮动手段时，最好写个注释说明用途，免得后人（包括几周后的自己）看不出它是来清浮动的还是真要裁内容。overflow: hidden 是"顺便能清浮动"，它的本职工作是裁剪溢出，别把副作用当主功能用。

前辈听完点了点头，说："你看，这些题你其实都遇到过。"

第九问，散会后自己补的一问：IFC 和 BFC 是不是一回事

前辈走后，我又想起一个白天没被问到、但经常和 BFC 混着说的概念：行内格式化上下文（IFC）。BFC 管的是块级元素怎么摆、怎么互相隔离；IFC 管的是一行里的行内元素怎么排、怎么对齐基线。之前提到的 inline-block 元素之间的空白缝隙、图片底部的 3px 空隙，本质都是 IFC 的行为，不归 BFC 管。这两套上下文经常在同一个页面里同时存在——一个 display: block 的容器内部，如果子元素都是行内或 inline-block，容器对外表现为参与 BFC，但容器内部排布子元素时用的是 IFC 的规则。分不清这两层，很容易把"文字对不齐"的问题错怪到浮动或定位上去排查。

还有一点值得记一笔：BFC 的" B "指的是 block，理论上还有对应的 IFC（行内）、GFC（grid，网格容器自身也会创建格式化上下文）、FFC（flex）。日常吵得最多的是 BFC，因为它历史最久、触发方式最杂、副作用也最容易被忽略；flex 和 grid 容器本身也会创建自己的格式化上下文，只是它们的排布规则足够新、足够独立，很少有人拿"BFC 的老问题"去套它们，才显得没那么高频。

把这条追问链收拢成两句话

这场分享会给我最大的收获不是答没答上来，而是发现自己明明每个坑都踩过，却从来没把它们串成一套规则。盒模型管的是一个元素到底占多大地方——width 的口径、padding 和 border 算不算在内、margin 永远在盒子外面。BFC 管的是一块区域和外面互不干扰——margin 折叠被边界挡住、浮动被算进高度、浮动不与 BFC 重叠。宽度被撑开、margin 合并、父元素高度塌陷、浮动挤歪布局，这些看着零散的怪现象，往下拆全绕不开这两套规则。

把规则想明白之后，调 CSS 会少很多"试一下看行不行"的动作——分享会上被问住的那几秒冷汗，也算给下次给新人讲课攒好了一份完整教材。
