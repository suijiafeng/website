栈、队列和树：前端面试里的数据结构不是白问的

2019-07-16
JavaScript

刚工作那两年我一直觉得数据结构是算法课的事，跟我天天写表单、调样式没关系。直到有一次接了个后台权限系统，接口返回一坨扁平的菜单数据，要我渲染成左侧多级折叠菜单，还要根据角色把没权限的节点连同它的子树一起砍掉。我一开始用了三层嵌套的 for 循环硬怼，写到第二天自己都看不懂了，改个需求要动五个地方。后来组里一个老哥过来瞄了一眼，说你这就是个树啊，递归一下不就完了。那一刻我才反应过来：原来面试官天天问的栈、队列、树，不是为了为难我，是这些东西真的天天在用，只是我以前没把它们认出来。

这里把我这几年踩过的坑串一串，讲讲这三个结构在前端项目里到底长什么样、什么时候该用、用的时候容易栽在哪。

栈：后进先出，撤销和回溯的本质

栈的规则就一句话：后进先出（LIFO）。最后放进去的，最先拿出来。JS 里压根不需要专门实现一个栈类，一个数组配 push 和 pop 就是个现成的栈。

可以在控制台直接验证它的「后进先出」：

最容易理解的例子是函数调用栈。你写个递归忘了写终止条件，浏览器报 Maximum call stack size exceeded，那个 stack 就是调用栈——每调一层函数压一个帧进去，函数返回再弹出来，爆栈就是压进去的没机会弹出来，把空间撑满了。浏览器的前进后退、编辑器的撤销重做，本质也都是栈。

我自己用得最多的实战场景是括号 / 标签匹配。早期做一个简易的公式编辑器，要校验用户输入的括号是不是配对的，这就是栈的经典用法：

这里有个我当时栽过的坑：只判断左右括号数量相等是不够的。([)] 左右括号各两个，数量对，但顺序是错的。必须用栈才能保证「最近打开的最先关闭」这个嵌套关系。我最初版本就是数数量，结果用户输入 [(]) 也判过了，被测试同学逮个正着。

栈的思路还能往外延伸。比如做一个面包屑导航的「返回上一级」，或者实现一个简单的状态回退，都可以维护一个栈，每进一层 push，每退一步 pop。再比如把递归改成迭代——递归本质就是在用系统的调用栈，当数据层级太深可能爆栈时，可以自己拿一个数组当栈来手动模拟，这点后面讲树的遍历会用到。

队列：先进先出，控制并发的利器

队列跟栈正好相反，先进先出（FIFO），像排队买奶茶，先来的先被服务。数组用 push 进队、shift 出队就行：

队列最有价值的实战场景是并发控制。我当年做过一个批量上传图片的功能，用户一次选几十张，如果一股脑全发出去，浏览器对同一域名的并发连接本来就有上限（一般 6 个），剩下的请求全在那干等，而且后端也容易被打挂。正确做法是维护一个等待队列，同时只跑固定数量的请求，跑完一个就从队列里取下一个补上：

这里有两个细节是我踩过坑才记住的。一是 tasks 里存的得是「返回 Promise 的函数」，不能直接存 Promise，因为 Promise 一创建就立刻执行了，那样所谓的并发限制根本拦不住，请求早就全发出去了。二是 results[current] = res 用下标存，是为了保证结果顺序跟输入一致——队列是先进先出，但每个请求的耗时不一样，回来的顺序是乱的，靠下标对齐才不会错位。

再说个更底层的：浏览器的事件循环里那些宏任务（setTimeout、事件回调）排的就是一个任务队列，一个一个先进先出地执行。理解了队列，再去看事件循环为什么是那个执行顺序，会顺很多。

树：层级关系的天然表达

前端遇到的层级数据基本都是树：左侧菜单、组织部门、多级评论、文件目录、路由配置、省市区三级联动。树的特点是每个节点可以有若干子节点，从根一路往下分叉。

栈、队列、树这三样，刚学时觉得离业务很远，真正写过几个项目就会发现它们无处不在：括号校验、撤销回退靠栈，批量请求的并发控制靠队列，菜单、权限、评论、目录这些层级数据全是树。面试官问这些不是在炫技，是想看你能不能在一坨需求里认出背后的结构——一旦认出来，原本要堆几百行 if-else 的活，常常十几行递归就解决了。

把这几个结构的「脾气」记牢：栈是后进先出、队列是先进先出、树是递归的。下次再碰到嵌套数据或者要排队执行的场景，先别急着撸循环，想想它是不是其中之一。
