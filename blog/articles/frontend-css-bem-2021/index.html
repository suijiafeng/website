CSS 命名为什么影响维护成本：BEM 这类约定到底在帮什么

2021-09-14
前端基础

前端页面写到一定规模，CSS 最容易出现的问题通常不是不会写样式，而是样式越来越难改。

今天改一个按钮颜色，明天发现另外一个页面也被连带影响；一个组件明明只是局部样式，结果类名写得太泛，后面谁都不敢复用。

这类问题看起来像优先级冲突，往深一点看其实和命名方式有很大关系。

类名不是随便起个能认出来就够了

很多小项目里，大家习惯写：

  • .title
  • .content
  • .box
  • .item

短期当然方便，但文件一多、页面一多，这些名字几乎一定会重复。更麻烦的是，它们本身表达的信息太弱，后来的人只看类名，根本不知道它属于哪个模块、承担什么职责。

所以 CSS 命名真正要解决的，不只是“这个类名有没有语义”，而是“它的作用域和职责是否清楚”。

BEM 的核心价值不是格式，而是边界

BEM 之所以经常被提到，不是因为它长得有多高级，而是它试图把一个组件内部结构表达清楚。

大致思路是：

  • Block 表示一个独立模块
  • Element 表示模块内部元素
  • Modifier 表示状态或变体

只看命名，你大概就能知道哪些元素属于 card 这个模块，哪些是它的状态变体。

命名规范的收益，通常在项目变大后才体现

刚开始写页面时，很多人会觉得这些规则有点麻烦，似乎多此一举。

但一旦项目里组件增多、页面变多、协作人数变多，命名统一带来的收益会迅速放大：

  • 类名冲突减少
  • 组件边界更清楚
  • 样式搜索和定位更容易
  • 复用和重构成本更低

也就是说，命名规范本质上是在给长期维护提前铺路。

它不是唯一方案，但问题一定要解决

当然，CSS 命名不只有 BEM 一条路。

有的团队会基于组件化方案限制作用域，有的会用工具链提供的局部样式能力，有的会结合设计系统做更统一命名。具体方案可以不同，但要解决的问题其实差不多：

  • 全局污染怎么避免
  • 组件边界怎么表达
  • 状态样式怎么命名

如果这些不解决，项目只会越来越靠“谁改得小心”来维持。

好命名不是装规范，而是降低沟通成本

我后来越来越觉得，类名写得清楚，本质上是在减少团队内部的沟通负担。

当你看到：

  • .user-card__avatar
  • .user-card__name
  • .user-card--loading

就比看到一堆 .avatar、.name、.active 更容易理解代码上下文。

这并不是因为前者更“专业”，而是它把模块归属讲清楚了。

CSS 维护体验很多时候不是输在技术，而是输在约定

样式系统好不好维护，经常不是由某个高级特性决定的。

更多时候取决于团队有没有建立一种一致的写法，让大家知道什么样的类名算清楚，什么样的嵌套算过深，什么样的状态表达更稳定。

所以我一直觉得，命名规范看起来不像高技术含量的话题，但它对前端项目长期健康影响很大。BEM 之类的方案真正有价值的地方，也正在这里。

命名一旦开始含糊，最先上涨的通常是沟通成本

项目初期大家都知道 .title 指哪个标题，.item 指哪个列表项，看起来完全够用。可一旦页面和组件越来越多，同一个名字会在很多地方重复出现，语境却完全不同。

这时最明显的问题往往不是页面立刻出 bug，而是所有人的判断速度都慢下来了：

  • 搜索一个类名会出现很多无关结果
  • 改一个样式前很难确定影响面
  • 新人接手时要靠试错理解结构

也就是说，命名不清带来的第一笔成本，往往不是渲染结果，而是团队整体维护效率。

命名规范真正要保住的是边界

BEM 常被误解成“类名必须很长”。但它真正有价值的地方，不是下划线和中划线本身，而是它在逼你把这些关系说清楚：

  • 哪个是独立模块
  • 哪个是模块内部元素
  • 哪个是状态或变体

只要边界表达稳定，即使团队最后不是完全照搬某种命名方案，样式维护体验也会明显提升。CSS 最怕的从来不是名字长一点，而是名字看不出归属、状态看不出层次、修改时不知道会不会牵连别处。

类名一旦和结构脱节，重构会变得特别痛苦

很多旧项目的样式难改，不是因为 CSS 本身复杂，而是类名和页面真实结构已经长期脱节。比如一个叫 .left-box 的类后来不在左边了，一个叫 .small-title 的类后来变成了主标题，一个叫 .active 的状态被十几个组件共用却语义各不相同。

这种时候，类名不再是辅助理解的工具，反而成了历史包袱。你每改一次都得先猜它现在到底代表什么。

命名规范真正保护的是“后来的人”

写样式的人当然知道当前页面在做什么，但半年以后接手的人未必知道。

所以我一直觉得，好的命名规范不是写给当前作者自己看的，而是写给后来维护的人看的。它的价值在于让别人不用打开页面猜半天，也能大致判断：

  • 这个类属于哪个模块
  • 它描述的是结构、元素还是状态
  • 修改它时大概率会影响哪一层

前端很多长期可维护性问题，最后都落在这种很基础的命名约定上。
