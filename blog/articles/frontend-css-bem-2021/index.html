CSS 命名为什么影响维护成本：BEM 这类约定到底在帮什么

2021-09-14
前端基础

前端页面写到一定规模，CSS 最容易出现的问题通常不是不会写样式，而是样式越来越难改。

今天改一个按钮颜色，明天发现另外一个页面也被连带影响；一个组件明明只是局部样式，结果类名写得太泛，后面谁都不敢复用。

我印象最深的一次，是接手一个跑了两年的后台项目。改一个表单提交按钮的边距，结果测试反馈说订单详情页的导出按钮也歪了。一查才发现，两处共用了一个 .btn-primary，而且还有人在某个深层选择器里写了 .form .btn-primary { margin-left: 12px } 这种东西。改它，那边崩；不改它，这边丑。最后只能新加一个类、把旧的留着不动，技术债又厚了一层。

这类问题看起来像优先级冲突，往深一点看其实和命名方式有很大关系。说到底，CSS 没有像 JS 那样天然的模块作用域，所有类名都在一个全局命名空间里抢地盘，谁写得晚、谁权重高，谁就赢。命名约定要做的，就是用人为的纪律去补上这个语言层面缺失的隔离。

类名不是随便起个能认出来就够了

很多小项目里，大家习惯写：

  • .title
  • .content
  • .box
  • .item

短期当然方便，但文件一多、页面一多，这些名字几乎一定会重复。更麻烦的是，它们本身表达的信息太弱，后来的人只看类名，根本不知道它属于哪个模块、承担什么职责。

我自己踩过的一个典型坑是 .active。一开始它是导航栏高亮用的，后来标签页选中也叫 .active，再后来表单校验通过的输入框也来一个 .active。某天产品要把导航高亮从蓝色改成品牌色，我直接在全局样式里改了 .active，结果半个站的"选中态"全跟着变了。那一刻我才真正意识到，命名太泛不是写得丑的问题，是会真的让你不敢动手。

还有个隐性代价是搜索。当你想定位一个 .box 在哪定义、被谁用，编辑器里一搜出来上百个结果，根本没法判断改哪个安全。一个好类名应该是几乎全局唯一的，搜出来就那么一两处，定位成本接近于零。

所以 CSS 命名真正要解决的，不只是“这个类名有没有语义”，而是“它的作用域和职责是否清楚”。

BEM 的核心价值不是格式，而是边界

BEM 之所以经常被提到，不是因为它长得有多高级，而是它试图把一个组件内部结构表达清楚。

大致思路是：

  • Block 表示一个独立模块
  • Element 表示模块内部元素

命名规范的收益，通常在项目变大后才体现

刚开始写页面时，很多人会觉得这些规则麻烦、多此一举。但一旦组件、页面、协作人数都涨上来，命名统一的收益会迅速放大：类名冲突减少、组件边界清楚、搜索定位容易、复用和重构成本更低。

我后来带新人时给过一个很土但好用的判断标准：删一个组件的时候，你能不能放心地把它对应的那一段 CSS 整块删掉，而不担心连累别人？如果类名都带着 Block 前缀、彼此隔离，答案基本是肯定的，.user-card 相关的样式删了就删了。如果到处是 .title、.wrapper，你删之前得先全局搜一遍、心里打鼓，那这套命名就是没起到作用。能不能放心删，是检验作用域是否清晰最实在的尺子。

它不是唯一方案，但问题一定要解决

当然，CSS 命名不只有 BEM 一条路。

有的团队会基于组件化方案限制作用域，有的会用工具链提供的局部样式能力，有的会结合设计系统做更统一命名。具体方案可以不同，但要解决的问题其实差不多：

  • 全局污染怎么避免
  • 组件边界怎么表达
  • 状态样式怎么命名

拿我接触过的几种方案对比一下，思路会更清楚：

  • CSS Modules：构建时把 .title 编译成 .Card_title__a1b2c 这种带哈希的唯一类名，作用域是工程层面强保证的，写的时候反而可以用短名字。代价是脱离了构建环境（比如纯静态页、或者要给样式写文档），类名就不可读了。这件事不用信我空口说——随便找一个用了 CSS Modules 的页面（比如不少 Next.js 站点），在浏览器 Elements 面板里选中一个组件节点，看它的 class 属性，你会看到的不是你源码里写的 title，而是 Card_title__a1b2c3 这种带哈希后缀的真实类名（默认格式是 [name]_[local]__[hash]，hash 那段随内容变化）。这正是它能保证全局不冲突的原因：两个组件都写 .title，编译后的哈希不同，井水不犯河水。
  • CSS-in-JS（styled-components 等）：样式跟组件彻底绑死，连命名这一步都省了，但运行时有开销，SSR 也要额外处理，团队不熟时容易写出难调试的样式。
  • BEM：纯靠人肉约定，没有任何工具门槛，一个 .css 文件配一套规范就能上。缺点也正是这点——它不强制，靠的是 review 和自觉，一旦有人偷懒写了 .title，约定就出现破口。

我自己的取舍是：用 React／Vue 这类有 scoped 能力的工程，优先吃工具链的红利（Vue 的 <style scoped>、CSS Modules）；但即便用了 scoped，组件内部的类名我还是会沿用 BEM 的命名思路，因为 scoped 只解决了"不污染外面"，解决不了"组件内部自己读不读得懂"。两者其实不冲突，是不同层次的事。

如果这些都不解决，项目只会越来越靠“谁改得小心”来维持。

真落地时，我会把 BEM 规则收窄一点

BEM 如果只停留在“两个下划线、两个中划线”的格式，很快就会变成另一种形式主义。真正能减少维护成本的，是几条足够具体的规则。

第一，Block 不要直接复用页面名，尽量用组件名。.user-page__title 看着清楚，但这个标题一旦挪到弹窗或抽屉里，名字就开始撒谎；.user-card__title 更稳定，因为它描述的是组件，而不是当前位置。

命名描述“是什么”，不描述“长什么样”

很多旧项目的样式难改，是因为类名和真实结构长期脱节：一个叫 .left-box 的类后来挪到了右边，一个叫 .small-title 的类后来变成了主标题。这种时候类名不再帮你理解代码，反而成了历史包袱——每改一次都得先猜它现在到底代表什么。

所以我后来给命名定了一条规矩：类名描述“是什么”，不描述“长什么样”。.alert--error 比 .red-text 强，因为红色总有一天会变，但“错误提示”这个语义不会变；.sidebar 比 .left-box 强，因为它哪天挪到右边了名字也不至于自打脸。按表现命名，等于把当下的视觉决策焊死在类名里，UI 一改版，类名立刻开始撒谎。

回到 BEM——它常被误解成“类名必须很长”，但下划线和中划线本身不是重点，重点是它逼你把“哪个是模块、哪个是模块内部元素、哪个是状态变体”这三层关系说清楚。即便团队最后没完全照搬，只要这条边界表达稳定，样式就好维护。说穿了，命名规范保护的不是当前写代码的人——他知道这页在干什么——而是半年后接手、得靠类名判断影响面的那个人。
