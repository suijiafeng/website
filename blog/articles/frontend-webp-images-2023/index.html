前端 WebP 图片使用入门：让图片更小，页面更快

2023-09-15
前端基础性能与缓存

图片通常是网页里最占体积的资源之一。

如果一个页面里有很多商品图、封面图或内容配图，图片太大就会直接影响加载速度。用户打开页面时，需要等待更多流量下载完成，体验自然会变差。移动端网络不稳定时，这个问题会更明显。

WebP 就是为了解决这类问题而常用的一种图片格式。它不是唯一答案，但在前端图片优化里非常值得掌握。

我以前做图片优化时犯过一个错误：只盯格式转换。把 JPG 转成 WebP 后体积确实小了，但移动端仍然慢，因为页面还是加载 2000px 宽的大图。后来才明白，图片优化至少有三层：格式、尺寸、加载时机。只做其中一层，收益经常打折。

WebP 是什么

WebP 是 Google 推出的一种图片格式。它的特点很直接：在保证图片观感接近的情况下，文件体积通常可以比 JPG、PNG 更小。

对前端来说，这意味着：

  • 页面加载更快
  • 图片占用带宽更少
  • 移动端访问更省流量
  • 图片很多的页面更容易优化
  • CDN 缓存成本可能更低

所以在电商、博客、资讯站、后台系统封面图等场景里，WebP 都很常见。

不过 WebP 不是简单替代所有图片格式。照片、插画、透明图、动图的优化策略并不完全一样。选择格式前，要先看图片内容和使用场景。

现在还会经常看到 AVIF，它在很多场景下压缩率更好，但编码成本、兼容性和画质表现也要验证。我的习惯是：关键业务图不要只按格式流行程度选，先拿真实图片做一组对比，看体积、清晰度、边缘和颜色过渡。

为什么不能只放 WebP

WebP 已经被大多数现代浏览器支持，但实际项目里仍然要考虑兼容性。

如果只写一个 WebP 图片地址，遇到不支持 WebP 的浏览器时，图片可能无法正常显示。更稳妥的做法是：优先提供 WebP，同时准备一张 JPG 或 PNG 作为兜底。

特别是面向企业内网、旧设备、App 内嵌 WebView 的项目，不要只看桌面 Chrome 的表现。上线前要确认目标用户实际使用的浏览器。

如果有 CDN 图片处理能力，也可以让 CDN 根据请求头自动返回 WebP/AVIF。这样业务代码不用到处拼不同格式地址，但要确认缓存 key 是否包含格式维度，否则可能出现不支持 WebP 的客户端拿到 WebP 缓存的事故。

这里最关键的是 Vary: Accept。浏览器请求图片时会在 Accept 头里告诉服务端自己支持什么格式，例如是否支持 image/avif、image/webp。如果 CDN 根据 Accept 返回不同格式，却没有把 Accept 放进缓存维度，第一批支持 WebP 的用户可能把 WebP 响应缓存到边缘节点，后面不支持 WebP 的老 WebView 也拿到同一个缓存，图片就挂了。

图片优化不只是格式，还包括尺寸。

sizes 不要随便写。它描述的是图片最终在页面里的展示宽度，不是原图宽度。如果 sizes 写得过大，浏览器会选择过大的资源；写得过小，高 DPR 屏幕上又会糊。图片策略要和布局一起看。

转换 WebP 要注意质量

WebP 的目标不是把文件压到越小越好，而是在体积和画质之间找到平衡。

如果压缩质量太低，图片会出现明显块状、颜色断层或边缘模糊。对于商品图、头像、作品集这类需要看清细节的图片，过度压缩会直接影响用户判断。

常见做法是：

  • 照片类图片使用有损 WebP
  • 图标、透明图根据情况使用 PNG、SVG 或无损 WebP
  • 关键视觉图保留更高质量
  • 缩略图可以压得更激进
  • 转换后做人工抽查

不要只看文件大小，也要看实际显示效果。

我会抽查几类图：人像、商品细节、浅色渐变、带文字的海报、透明图。不同内容对压缩的敏感点不一样。特别是带文字的图片，压缩稍微激进一点就会糊，不能只看平均压缩率。

如果图片是 LCP 元素，比如首页 hero 图或文章首图，就不要懒加载，反而应该尽早加载，必要时配合 fetchpriority="high" 或框架的图片组件优先级设置。首屏图片和列表长尾图片的策略应该不同。

我现在做图片优化，不会再只盯着“是不是 WebP”。

先看图片是不是按真实展示尺寸输出，再看格式和压缩质量，接着看首屏图和非首屏图的加载策略，最后才是 CDN 转码、缓存和兼容兜底。WebP 很有用，但它只是其中一环。

图片越多的页面，越要把这几件事一起做：WebP 优先、JPG/PNG 兜底、响应式尺寸、合理压缩质量、懒加载、固定宽高比例和目标浏览器验证。少做任何一块，最终体验都可能打折。
