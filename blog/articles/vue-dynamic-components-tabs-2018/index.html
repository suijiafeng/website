Vue 动态组件和 keep-alive：后台 tab 页别每次都重新加载

2018-10-28
Vue前端基础

我接手过一个 CRM 后台，产品同学提的第一个需求不是加功能，而是「这破系统能不能别一切回去就把我刚填的筛选条件清空」。运营每天要在「客户列表」「订单详情」「跟进记录」几个 tab 之间来回横跳，列表页有十几个筛选条件，翻到第 8 页去看某条订单，回来一看——筛选没了、页码归零、滚动条弹回顶部。一天下来重复劳动的怨气全堆在我们前端头上。

这事儿的根子在于：每次切 tab，Vue 都把上一个路由组件销毁了，再切回来又重新 create 一遍，所有组件内 state 自然清零。要解决它，绕不开两个东西——动态组件和 keep-alive。下面记录的是我踩过的坑和后来真正落地的方案，技术栈是 Vue 2.5 + vue-router 3.0，2018 年后台项目的标配。

先搞清楚「动态组件」到底动态在哪

很多人一上来就用 keep-alive 包 router-view，但其实动态组件（<component :is>）和路由缓存是两条腿，搞混了后面会很乱。

动态组件是这样的：

currentComponent 是个字符串或组件对象，它一变，Vue 就卸掉旧组件、挂上新组件：

这种写法适合「同一个壳子里换内容」的场景，比如一个配置向导分好几步，每步是一个组件；或者一个 tab 容器，tab 内容由配置数据驱动、跟路由没关系。它最大的特点是不走路由，URL 不变，刷新页面状态就没了。

后台 tab 大多数情况要的是另一种——路由级别的页面缓存，地址栏要变、要能分享链接、要能前进后退。所以下面的重点会放在 keep-alive + router-view 上。但记住动态组件这条路存在，有些纯前端交互（比如一个弹窗里的分步表单）用它反而比硬塞进路由清爽。

keep-alive：让组件「离开但不死」

把 router-view 包进 keep-alive，路由组件切走时就不销毁，而是被「冻」在内存里：

这时候组件的生命周期会变。原来切走是 beforeDestroy / destroyed，现在变成 deactivated；切回来不再是 created / mounted，而是 activated：

这里有个我当年栽过的坑：列表页的数据请求我习惯性写在 created 里。加了 keep-alive 之后，列表数据是「保住了」，但产品又提需求——从详情页改完数据返回列表，列表得显示最新的。结果因为 created 只跑一次，回来的列表还是旧数据。

我的处理原则是把「请求时机」分两类：

  • 要保留状态、不需要刷新的：请求留在 created，靠 keep-alive 把 state 冻住，回来啥都不动。
  • 要保留筛选条件、但数据可能变了的：请求挪到 activated，但筛选条件、页码这些查询参数本身存在组件 data 里不动，activated 时拿着这些参数重新拉数据。

这样运营回到列表，筛选条件原封不动，但能看到刚改的最新数据，两头都满足。

滚动位置也是同理。keep-alive 不会自动帮你恢复滚动条，因为 DOM 虽然没销毁，但浏览器的滚动是挂在外层容器上的。我的做法是 deactivated 时记下 scrollTop，activated 时还原：

include / exclude：别什么页面都缓存

keep-alive 不加约束的话，所有路由组件都会被缓存，内存只增不减，后台开一天能卡到飞起。而且有些页面就不该缓存——比如「新建订单」，每次进来都该是干净的空表单，你缓存它干嘛。

用 include 白名单控制：

include 匹配的是组件的 name，不是路由的 name，也不是文件名。这是另一个超容易踩的坑：我第一次配好了发现死活不缓存，查了半天，原因是组件压根没写 name。

include 可以是数组、逗号分隔的字符串、也可以是正则。后台动态 tab 一般用数组，因为要动态增删。另外提一句，Vue 2.6 才支持给 include 传组件实例匹配，2018 年大部分项目还在 2.5，老老实实用 name 字符串就好。

关闭 tab 一定要清缓存，否则是个隐形内存泄漏

这是当初最隐蔽的一个 bug。用户点 tab 上的小叉关页面，我只做了从 visitedTabs 移除、跳到相邻 tab，UI 上看页面是「关了」。但 cachedViews 里没删，组件实例还冻在内存里。

后果有两个：一是内存一直涨；二更坑——用户重新打开同一个页面，keep-alive 发现缓存里有，直接复活旧实例，于是看到的是上次关闭前的脏状态，根本不是新页面。用户一脸懵：我不是关了吗，咋还是老样子。

所以关 tab 必须两边一起清：

「刷新当前页」怎么做：keep-alive 反而碍事了

后台还有个高频需求：tab 上点「刷新」，把当前页彻底重来一遍。难点在于 keep-alive 把组件冻住了，你 this.$router.push 到自己的路由，组件根本不会重新创建。

我试过几个办法，最后稳妥的是「先把它踢出缓存，跳个空中转路由，再跳回来」：

中转路由那一下让组件经历了一次真正的销毁和重建。比起 this.$forceUpdate() 或者给 router-view 加 key 这类偏方，这个方案干净，而且 element-admin 那套模板也是这么干的，经过验证。

表单页和详情页：别盲目跟着缓存

列表、查询这类页面缓存收益最大，但编辑表单页我建议默认不缓存，这是血泪教训。

场景是这样：用户打开「编辑客户 A」，填了一半切走，又打开「编辑客户 B」。如果这俩走的是同一个路由组件（/user/edit/:id），keep-alive 又缓存了它，Vue 会复用同一个组件实例——A 没填完的数据就串到了 B 的表单上。轻则数据错乱，重则把 A 的内容存到了 B 头上，线上事故。

根因是 keep-alive 缓存的粒度是「组件」，不是「组件 + 参数」。同一路由不同 :id 用的是同一个缓存实例。两条出路：

一是干脆别缓存编辑页，进来就请求，离开就销毁，最省心：

二是如果非要缓存，就在 beforeRouteUpdate 里按参数重新加载——因为同路由切 :id 不会触发 created，只会触发 beforeRouteUpdate：

还有个更暴力但有效的隔离手段：给 router-view 套 key，让不同参数被当成不同组件，逼着它重建：

不过加了 fullPath 作 key，缓存基本就失效了（每个 path 都是新实例），所以这招和缓存是互斥的，按需取舍。我的实际选择是：列表/查询页缓存、用 name；编辑/详情页不缓存、靠 beforeRouteUpdate 处理参数变化。

几个方案放一起对比

需求方案注意点
同壳换内容、不走路由<component :is>刷新即丢状态
tab 切走保留状态keep-alive 包 router-view组件必须有 name
控制谁缓存include + meta.keepAlive匹配 name 非路由名
关 tab同步删 cachedViews不删会内存泄漏+脏状态复活
刷新当前页踢缓存 + redirect 中转路由比 forceUpdate 可靠
编辑页防数据串不缓存 / beforeRouteUpdate缓存粒度是组件非参数

keep-alive 确实能把后台 tab 体验救回来，运营再也没因为筛选条件丢失骂过街。但它不是开了就万事大吉的开关，真正花功夫的是缓存范围的控制、关闭时的清理、刷新的实现，以及哪些页面不该碰它。

我现在的判断标准很简单：这个页面用户离开后再回来，希望看到原样还是看到干净的？想看原样的（列表、查询、看板）就缓存；想要干净的（新建、编辑、带参数详情）就别缓存。缓存从来不是越多越好，它是用内存和复杂度换体验，得算账。
