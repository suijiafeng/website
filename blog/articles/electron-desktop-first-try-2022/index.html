Electron 桌面端初探：主进程、渲染进程与 contextIsolation 下的 IPC

2022-04-23
前端基础构建与模块化JavaScript

一个工具要不要做成桌面端，我现在的判断标准很朴素：它是不是需要浏览器给不了的能力。需要读写本地任意目录、需要常驻系统托盘、需要注册全局快捷键、需要和本机的其它程序打交道——满足其中一条，桌面端才有讨论的价值。反过来，如果一个工具的全部诉求就是"展示数据、填表单、点按钮"，那它属于浏览器，包一层桌面壳除了多一个要分发升级的安装包，什么都得不到。

这个标准不是凭空想的。运营同事那边有个日常工作：从几个内部系统导出数据文件，按固定规则改名、归类到本地目录，再把处理过的文件批量上传回另一个系统。之前给他们做的 Web 版工具卡在两个地方——浏览器下载的文件只能进"下载"目录，没法直接落到他们整理好的目录结构里；批量上传要靠人手动多选文件，一天几十次，怨气很大。这两条都撞在浏览器沙箱的边界上，File System Access API 那套东西倒是能解决一部分，但我们内网还有一批老 Chrome，覆盖不了。于是这个需求成了我第一次认真碰 Electron 的理由。

Electron 现在（四月）的稳定版是 17，18 也刚发不久，文档比我几年前偶尔瞟一眼时完整了太多。花了两周把这个壳做出来，过程里最大的收获不是"会用 Electron 了"，而是把它的进程模型和安全模型想明白了——这两件事没想明白之前，网上抄来的代码能跑，但你不知道为什么这么写。

两个进程：谁在跑 Node，谁在跑页面

Electron 应用至少有两个进程。主进程是入口，跑在 Node.js 环境里，负责创建窗口、管理应用生命周期、访问操作系统能力（文件系统、菜单、托盘、对话框）。渲染进程是每个窗口里跑的那个"浏览器页面"，环境和 Chrome 里的一个 tab 几乎一样。

前端页面本身没什么特别的，我直接用 Vite 起了个 Vue 3 项目，win.loadFile 加载构建产物，开发时用 win.loadURL('http://localhost:5173') 指向 dev server。渲染进程里写的就是普通前端代码，Electron 没有改变你写页面的方式，它改变的是页面能"够到"什么。

有一个 Vue 项目落到 loadFile 场景下必踩的坑值得先记下来：路由必须用 hash 模式。createWebHistory 在 file:// 协议下没有服务器帮你做 fallback，刷新或者直达一个子路由就是白屏，控制台里连报错都不明显。换成 createWebHashHistory 一切正常。同理，Vite 构建时 base 要设成 './'，否则产物里的绝对路径资源在 file 协议下全部 404。这两个坑都不是 Electron 的错，是"页面不再由 HTTP 服务器伺候"这个前提带来的连锁反应。

而页面能"够到什么"这件事，正是我第一天就踩进去的地方。

nodeIntegration 为什么别开

网上很多老教程（尤其是两三年前的）给的方案是在 webPreferences 里打开 nodeIntegration: true，然后在页面里直接 require('fs') 读写文件。我照着试了一下，在 Electron 17 上直接不行——因为从 Electron 12 开始，contextIsolation 默认开启，页面的 JS 上下文和 preload 的上下文是隔离的，就算开了 nodeIntegration，页面里也拿不到 Node 的东西。

一开始我是有点烦躁的，觉得官方在给简单需求加门槛。把安全文档读完之后改了看法。渲染进程本质上是个浏览器页面，它会加载我们的业务代码、第三方 npm 包、可能还有远程内容。如果页面上下文里直接摆着完整的 Node 能力，那么任何一处 XSS 都不再是"改改页面"的问题，而是"在用户机器上任意执行代码"的问题——require('child_process').exec 就在那里等着。浏览器花了二十年建起来的沙箱，一个 nodeIntegration: true 就全拆了。

所以正确的心智模型是：渲染进程保持"就是个网页"的待遇，所有需要系统能力的操作，去求主进程帮忙。中间的桥梁是 preload 脚本。

preload 与 contextBridge：只暴露动词，不暴露能力

preload 脚本跑在渲染进程里，但它是个特殊位置：能访问一部分 Node API，又能通过 contextBridge 往页面的 window 上安全地挂东西。契约感很强的一点是，你挂什么，页面就只能用什么。

注意这里暴露的不是 ipcRenderer 本身，而是包了一层的具体函数。文档里专门警告过不要把 ipcRenderer 整个透传出去——透传了就等于允许页面向主进程发任意频道的消息，隔离等于白做。**preload 暴露的应该是一组业务动词（选目录、整理文件），而不是一个通用信道。**这个原则和我们平时封装 axios 实例不让业务代码乱传 header 是一个思路，只是这里的后果严重得多。

有一个细节值得记：handle 的处理函数里收到的参数是经过结构化克隆的，函数、类实例这些传不过去。我一开始想把一个带方法的规则对象直接传过去，报错之后才意识到 IPC 的边界本质上是序列化边界，跨进程传的只能是数据。这反而逼着我把"规则"设计成了纯 JSON 描述，主进程按描述执行——现在再读这段代码，这个被迫的设计比原来的更干净。

electron-builder 与体积的现实

开发跑通了，打包用的 electron-builder，配置不算复杂：

第一次打出 Windows 安装包的时候我盯着文件大小看了几秒：一个功能上就是"选目录、改文件名"的工具，安装包 70 多 MB，装完接近 200MB。原因不神秘——每个 Electron 应用都自带一份完整的 Chromium 和 Node.js 运行时，这是架构决定的地板价，怎么优化业务代码都降不下去。

在内网分发的场景里这个体积可以接受，运营同事不在乎多占 200MB 磁盘。但这件事校准了我的预期：**Electron 的成本模型是"用磁盘和内存换开发效率"，接受不了这个交换的场景就不该选它。**顺带说一句，最近看到社区在讨论一个用 Rust 做壳、复用系统 WebView 的新方案叫 Tauri，说体积能小一个数量级，不过还没到 1.0，我先观望，眼下不影响选型。

打包还有一个躲不开的话题是签名。macOS 上没有开发者证书签名的应用，用户要去安全设置里手动放行；Windows 上没签名的安装包会被 SmartScreen 拦一道。内部工具可以教用户点"仍要运行"，要是对外分发，证书的钱和流程就得提前算进成本里。

自动更新：先做个最省事的版本

桌面端和 Web 最大的运维差异在这里。Web 应用发布即生效，桌面应用发出去就收不回来了，用户停在旧版本上你毫无办法——除非做自动更新。

electron-builder 配套的 electron-updater 把这件事的门槛降得挺低。我们没有上 GitHub Releases（内网不通外网），就在内部静态服务器上放构建产物和一个 latest.yml，客户端启动时检查：

checkForUpdatesAndNotify 是最省事的模式：后台静默下载，下载完弹系统通知，用户下次退出应用时自动装上。第一版我就到此为止，没做强制更新、没做增量更新。差分更新（blockmap）electron-builder 也支持，Windows 的 NSIS 目标默认就会生成，实测从 1.0.1 升 1.0.2 只下载了十几 MB，比全量体面多了。

但是自动更新给我提了个醒：发桌面版本的心态要比发 Web 谨慎一档。Web 上线发现问题可以五分钟回滚，桌面端一个坏版本推出去，就算你立刻发修复版，也要等所有用户的客户端各自完成一轮"检查—下载—重启"。所以这个工具的发布节奏我定成了攒一批改动发一次，而不是像 Web 后台那样随改随发。

哪些需求其实用 Web 就够

做完这个项目，回到开头那个判断标准，我可以把它说得更具体了。这次真正用到 Electron 独有能力的功能只有三个：dialog.showOpenDialog 拿到真实目录路径、fs 直接读写整理文件、托盘常驻方便运营随手唤起。也就这三个功能撑起了做桌面端的理由。

而项目里剩下 80% 的代码——列表、表单、规则配置界面、调内部系统的接口——全是普通 Web 代码，放浏览器里跑一模一样。这提示了一个很实际的结构：把桌面壳做薄，业务尽量留在 Web 技术这一侧。我们的整理规则配置页后来干脆做成了主系统里的一个普通页面，桌面端只负责"拿着规则去执行"这最后一步。这样规则相关的迭代照常走 Web 发布，不用等桌面版本的更新周期。

评估阶段运营还提过几个"顺便做进去"的需求，我都挡回了浏览器：看数据报表——Web 够；接收系统通知——内部 IM 的机器人比系统托盘气泡靠谱；导出 Excel——浏览器下载没有任何问题。这些需求单看都能在 Electron 里做，但每做一个，桌面壳就厚一分，更新的包袱就重一分。

所以两周下来，Electron 本身没有给我惊喜也没有惊吓：进程模型清楚、IPC 的安全设计经得起推敲、打包和更新的工具链成熟，体积是明码标价的代价。真正值得留下来的是开头那条边界——需要系统能力的功能才配进桌面壳，其余的，浏览器仍然是它们最好的家。运营的文件整理需求解决了，而我判断，短时间内团队不会有第二个需求能跨过这条线。
