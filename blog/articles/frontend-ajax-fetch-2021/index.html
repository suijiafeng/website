从 Ajax 到 Fetch：前端请求方式的演进到底带来了什么

2021-10-06
前端基础

前端开发离不开请求。

页面展示数据、提交表单、刷新列表、加载详情，这些动作几乎都要和服务端通信。

如果把时间往前拉，大家最熟悉的方式可能是 Ajax；再往后，Fetch 逐渐成为更常见的写法。它们都能完成请求，但带来的开发体验并不完全一样。

Ajax 解决了什么问题

Ajax 最重要的价值，是让页面不必整页刷新也能和服务端交换数据。

这在早期前端开发里是一次很大的改变，因为它让页面开始具备更强的交互性和动态性。

大家最熟悉的实现通常是 XMLHttpRequest。

这个写法并不是不能用，但确实比较底层。

它的底层感主要体现在几个地方：

  • 需要关心 readyState
  • 成功和失败判断分散
  • 响应内容需要自己解析
  • 超时、取消、错误提示都要额外处理

如果只是一个简单请求，这些代码还能接受。一旦页面里有十几个接口，每个地方都写一遍状态判断，维护成本就会很快上来。

Fetch 为什么更容易被接受

Fetch 更贴近现代 JavaScript 的编码方式。

它的 API 更简洁，也更容易和 Promise、async/await 组合。

相比 XMLHttpRequest，这种写法的优势主要体现在：

  • 更容易阅读
  • 更容易封装
  • 更适合现代异步流程

两者的差异不只是“新旧”

不少人会简单理解成“Fetch 就是更现代的 Ajax”，但更准确地说，它们代表了两种不同层级的开发体验。

XMLHttpRequest 更像底层接口，你需要自己处理很多状态变化。

Fetch 则更像一个围绕请求流程设计得更现代的抽象。

请求封装的重要性

无论使用 Ajax 还是 Fetch，真正影响项目维护体验的，往往不是底层 API 本身，而是你有没有做好请求层封装。

例如：

  • base URL
  • 通用 headers
  • 错误处理
  • token 注入
  • 超时控制

如果这些都散落在页面里，请求方式再现代，项目后期也会很难维护。

超时和取消请求

Fetch 默认没有传统意义上的 timeout 参数。如果接口长时间不返回，请求可能一直挂着。实际项目里通常会用 AbortController 做超时控制：

取消请求在页面切换、搜索联想、弹窗关闭时也很有用。比如用户连续输入搜索关键字，旧请求比新请求更晚返回，就可能把新结果覆盖掉。取消旧请求，或者在响应回来时检查请求序号，都是常见处理方式。

需要注意的是，被取消的请求也会进入异常分支。封装层最好能区分“用户主动取消”和“真正失败”，否则用户每次快速输入都可能看到错误提示。

GET 和 POST 的边界

请求方式不只是后端的事情，前端也应该明确它们的语义。

一般来说：

  • 读取数据用 GET
  • 创建数据用 POST
  • 整体更新用 PUT
  • 局部更新用 PATCH
  • 删除数据用 DELETE

实际项目未必每个接口都严格遵守，但前端代码里至少应该保持清晰的命名和调用边界。比如 loadArticles、createArticle、deleteArticle 比 handleRequest1 这种名字更能表达意图。

从工具切换到抽象思维

很多技术演进表面看起来只是 API 更新，实际上还有一个更关键的问题是推动开发者思维变化。

从 Ajax 到 Fetch，更有价值的变化不只是代码少了几行，而是前端异步请求开始更自然地融入整体工程结构。

请求层做好以后，页面代码会轻很多。它不用关心底层用的是 XMLHttpRequest、Fetch，还是第三方库；只要返回的数据结构稳定，业务层就能稳定工作。

这也是我后来对请求代码的一个判断标准：不是看它是否用了最新 API，而是看它能不能让页面少处理协议细节、少重复错误逻辑、少暴露不稳定边界。

写在最后

从 Ajax 到 Fetch，是前端请求方式一次很自然的演进。前者解决了页面局部更新的问题，后者则让请求代码更容易和现代 JavaScript 编程方式结合。

工具当然会变化，但真正值得沉淀的是请求层的组织方式。只要这层思路清楚，用什么接口都不会太乱。
