WebSocket 重连和心跳：实时不等于一直在线

2023-08-18
前端基础JavaScript

WebSocket 看起来很简单。

但真实环境里，连接会断，网络会抖，浏览器会休眠，代理会超时，服务端会重启。实时系统不是建一个连接就完事，重点是连接断了以后怎么办。

我做过一个告警大屏，第一版只监听 onmessage。本地跑一晚上没问题，到了客户现场，内网代理十几分钟没消息就断连接。页面还显示“在线”，实际上已经收不到任何告警。那次之后我才认真补了心跳和重连。

连接状态要显式管理

用户界面也要能表达状态。比如大屏右上角显示“连接中 / 已断开，正在重试”。否则用户看到旧数据，还以为系统正常。

心跳用来发现半开连接

有些连接断了，浏览器未必马上触发 close。尤其是移动网络、代理、电脑休眠恢复后，会出现“看起来连着，其实收不到消息”的半开状态。

可以定时发 ping：

如果一段时间没收到 pong，就主动 close，让重连逻辑接管。

心跳间隔不要太短。太频繁会浪费电量和服务端资源，移动端尤其明显。具体间隔要结合业务实时性和网络环境。

重连要退避，不要疯狂连

断线后立即重连一次可以，但不能失败后每 100ms 连一次。服务端重启或网络故障时，这会形成风暴。

加一点随机抖动，可以避免大量客户端同时重连。

用户主动退出或页面卸载时，不应该触发重连。要区分“意外断开”和“主动关闭”。

消息要考虑丢失和重复

WebSocket 连接断开期间，消息可能丢。重连后服务端可能补发，也可能要求客户端拉取最新快照。

对重要消息，最好有序号：

客户端记录最后处理的 seq。重连后带上：

服务端可以补发缺失消息，或者告诉客户端重新拉全量。

如果业务不能保证消息补发，前端至少要在重连后重新请求一次关键数据。不要假设断线期间什么都没发生。

重复消息也要处理。网络重试、服务端补发都可能导致重复。关键操作要有 idempotency，前端渲染也要按 id 合并，而不是无脑 append。

页面可见性会影响连接

浏览器标签页切后台后，定时器可能被降频，移动端甚至会挂起页面。心跳和重连都可能变慢。

API 错误和鉴权过期要处理

WebSocket 也会遇到鉴权问题。

token 过期时，服务端可能关闭连接或返回错误消息：

前端不能一直重连。要刷新 token 或引导登录：

API 错误必须进入状态机。否则用户登录过期后，客户端可能无限重连，服务端日志被刷满。

我的 WebSocket 清单

上线实时功能前，我会检查：

  • 是否有显式连接状态
  • 是否有心跳检测半开连接
  • 重连是否有退避和最大次数
  • 主动关闭是否不会触发重连
  • 重连后是否能补消息或刷新快照
  • 是否处理重复消息
  • 页面恢复可见时是否校验连接
  • 鉴权失败是否停止重连并给出处理

实时不是“永远在线”，而是断了能发现、能恢复、恢复后数据仍然可信。
