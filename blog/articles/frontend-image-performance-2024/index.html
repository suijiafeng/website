前端图片性能优化：LCP 慢很多时候不是 JS 的锅

2024-04-12
前端基础性能与缓存

很多前端性能排查一开始都会盯着 JavaScript。

包是不是太大，组件是不是重复渲染，接口是不是慢。这些当然重要，但真实项目里，首屏慢很大一部分问题来自图片：主图太大、尺寸不对、懒加载误用、没有宽高、CDN 没压缩。

我做过一个活动页，Lighthouse 上 LCP 一直很差。最开始大家都怀疑 React hydration，后来打开性能面板才发现，LCP 元素是一张首屏 banner，设计稿导出 3000 多像素宽，线上移动端也在加载原图。JS 优化了一圈，不如把图处理对来得直接。

先找到 LCP 元素

图片优化不要泛泛而谈，先看 LCP 是谁。

如果 LCP 是首屏大图，那优化重点就是这张图；如果 LCP 是标题文字，就别把时间浪费在压缩小图标上。

Chrome DevTools 的 Performance 面板可以看到 LCP 标记，Web Vitals 上报也可以带上元素信息。拿到元素后再看几个问题：

  • 图片实际显示尺寸是多少
  • 下载的资源尺寸是多少
  • 文件大小是多少
  • 是否被懒加载延迟了
  • 是否有宽高导致布局稳定
  • 是否走了 CDN 压缩和缓存

我见过最常见的问题是“显示 360px，下载 2000px”。这不是高清，这是浪费。

响应式图片要让浏览器选对资源

不同设备需要不同尺寸图片。不要一张大图打天下。

srcset 告诉浏览器有哪些资源，sizes 告诉浏览器这张图在不同视口下大概显示多宽。浏览器会结合 DPR 和网络情况选择合适资源。

sizes 写错会直接导致选图错误。如果移动端实际显示全屏宽，却写成 800px，浏览器可能下载过大的图；如果桌面端显示很大，却写得太小，图片会糊。

在 Next.js 里用 next/image 也是同样逻辑。组件帮你生成不同尺寸，不代表你可以忽略 sizes。尤其是 fill 模式，如果不写准确 sizes，很容易让浏览器下载比需要更大的资源。

首屏图不要懒加载

懒加载适合首屏以下的图片，不适合 LCP 图片。

如果这张图是首屏主图，loading="lazy" 反而会让浏览器晚点请求，LCP 更慢。

一定要写宽高

图片不写宽高，很容易造成 CLS。

浏览器可以在图片下载前预留空间，页面不会等图片回来后突然下跳。

格式选择要看内容

图片格式不是越新越好，要看内容和兼容。

常见选择：

  • SVG：图标、logo、简单矢量图
  • WebP：大多数照片和插图
  • AVIF：压缩率更高，但编码慢，兼容要确认
  • PNG：需要透明且边缘清晰的图片
  • JPEG：兼容兜底，照片类仍然常见

如果有图片服务，最好让服务端根据 Accept 头自动返回 AVIF/WebP/JPEG。前端也可以用 picture：

不要为了追新格式牺牲稳定性。线上用户浏览器、企业 WebView、内嵌环境都可能有兼容问题。

占位图要服务体验

图片加载前可以用占位：

  • 固定背景色
  • 低质量模糊图
  • 骨架屏
  • 主色块

占位的目标是降低突兀感，而不是制造更多闪烁。我见过有页面给每张小图都做复杂 blur placeholder，结果 HTML 和 CSS 变重，收益很小。

对首屏大图，低质量占位有意义；对列表小缩略图，固定比例和背景色通常就够了。

图片优化清单

我排查图片性能时会按这个顺序：

  1. 确认 LCP 元素是不是图片
  2. 检查显示尺寸和下载尺寸是否匹配
  3. 给首屏关键图去掉 lazy，并提高优先级
  4. 给图片补 width / height 或 aspect-ratio
  5. 使用 WebP / AVIF，并保留兜底
  6. 首屏以下图片再懒加载
  7. 配好 CDN 缓存和压缩
  8. 监控不同设备下的 LCP 变化

图片优化最重要的是别猜。找到关键图片，压对尺寸，控制优先级，预留空间，通常就能解决一大半问题。
