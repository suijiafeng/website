浏览器渲染流程：重排和重绘为什么会让页面卡

2019-10-12
前端基础性能与缓存

页面卡顿时，很多人第一反应是 JavaScript 写多了。

这当然可能，但浏览器渲染本身也会消耗时间。DOM 变化、样式计算、布局、绘制，每一步都可能让页面变慢。面试问重排和重绘，背后其实是在问你是否理解浏览器如何把代码变成屏幕上的像素。

从 HTML 到页面

浏览器大致会做这些事：

  1. 解析 HTML，生成 DOM 树
  2. 解析 CSS，生成 CSSOM 树
  3. 合成渲染树
  4. 计算布局
  5. 绘制
  6. 合成显示

DOM 描述结构，CSSOM 描述样式。两者结合后，浏览器才知道每个元素长什么样、放在哪里。

这里有几个工程上很要紧的细节，我吃过亏才记住的：

  • CSS 会阻塞渲染。 CSSOM 没构建完，浏览器不会去渲染（不然会出现没样式的“裸 HTML”闪一下，也就是 FOUC）。所以一个又大又慢的 CSS 文件会拖住首屏。我后来都把关键样式内联进 HTML，非关键的异步加载。
  • JS 默认会阻塞 DOM 解析。 浏览器解析到 <script> 就停下来下载并执行，因为脚本可能 document.write 改 DOM。把不影响首屏的脚本加 defer（保证顺序、DOMContentLoaded 前执行）或 async（下载完就执行、不保证顺序），别一股脑塞 <head> 里。
  • JS 还会被 CSSOM 阻塞。 因为脚本可能读样式（比如 getComputedStyle），所以一个挂在前面的 CSS 没下完，后面的内联脚本也得等。这个隐藏依赖当年坑了我很久——明明 JS 不大，却迟迟不执行，最后发现是前面一个 CSS 慢。

理解这条链路，才知道“为什么白屏”往往不是 JS 慢，而是关键资源把渲染卡住了。

什么是重排

重排也叫 reflow，指的是布局计算重新发生。

会触发重排的操作包括：

  • 修改元素宽高
  • 修改 margin、padding
  • 改变字体大小
  • 添加或删除 DOM
  • 改变窗口大小
  • 读取某些布局属性

什么是重绘

重绘也叫 repaint，指元素几何位置不变，但外观变了。

读写布局不要交错

危险写法：

读取 offsetHeight 可能强制浏览器把之前的布局计算完成。读写交错会造成多次重排——这有个专门的名字叫“布局抖动”（layout thrashing）。浏览器本来很聪明，它会把你一连串的 DOM 写操作攒起来，到一帧结束时一次性批量算布局。可你中间插一个“读”，它为了给你准确值，被迫立刻刷新布局，这个批处理的优化就被打断了。循环里读一次写一次，N 次循环就是 N 次强制重排。

更好的方式是先把要读的全读完，再统一写：

如果读写本身没法分开（比如每个元素要读自己的高度再设别的），可以拿两个数组分两批：先一轮循环把所有需要的布局值读出来存数组，再一轮循环统一写回。核心思想就是把读和写在时间上分开，别交错。我后来定了个规矩：循环体里绝对不出现 offsetXXX/getBoundingClientRect 这种读布局的代码，需要的话提到循环外面去。

批量修改 DOM

频繁插入 DOM：

可以用文档片段：

DocumentFragment 是个游离在 DOM 树外的容器，往里塞节点不会触发任何重排，最后整体 appendChild 一次，只重排一次。1000 个节点从 1000 次重排降到 1 次，差别巨大。

类似思路还有几个我常用的：

  • 先脱离文档，改完再放回。 要对一个已经在页面里的节点做大量修改，可以先 display:none 把它从渲染中摘掉（这步触发一次重排），改完再显示（再一次重排），中间所有改动都不触发重排。两次重排换掉中间几十次，划算。
  • 克隆改完再替换。 node.cloneNode(true) 拿个离线副本，改完用 replaceChild 换上去，原理一样。
  • 拼字符串一次 innerHTML。 渲染长列表时，与其循环 createElement + appendChild，不如拼好 HTML 字符串一次 innerHTML 赋值，往往更快（虽然有 XSS 风险，数据要转义）。

减少 DOM 插入次数，页面会更稳。这些技巧的共同点都是：把多次会触发重排的操作，合并成一次。

动画尽量用 transform

移动元素时：

通常比改 left 更适合动画。

left 可能触发布局，transform 更容易走合成层，动画更流畅。

差别得说透。改 left 走的是“布局 → 绘制 → 合成”全流程，每一帧都要在主线程重算，主线程一忙（比如有 JS 在跑）动画就掉帧、卡顿。而 transform 和 opacity 如果元素被提升到独立的合成层，它的动画可以交给 GPU 在合成阶段处理，不经过主线程的布局和绘制，所以即使主线程在忙，动画也能保持丝滑。这就是为什么同样是移动一个盒子，transform: translateX() 比 left 顺滑得多。

怎么让元素上合成层？常见办法：

will-change 是提前给浏览器打招呼“我待会儿要改 transform”，让它提前把元素提升成层、准备好。

当然，不要滥用合成层。大量元素都提升层，也会占内存——每个合成层都要单独占一块显存来存它的位图。我见过有人给页面里几百个列表项全加 will-change，结果内存暴涨，低端机直接卡死甚至崩溃。will-change 要按需加、用完即撤（动画结束后设回 auto），别当成万能加速咒语全局乱撒。一个判断标准：只给“真的会持续动”的元素加，静态元素不要碰。

高频回调要节流，别每次都改 DOM

scroll、resize、mousemove 这种事件触发频率极高，一秒可能几十上百次。如果回调里直接改 DOM 或读布局，等于一秒内逼浏览器重排几十次，必卡。

光靠猜没用，得看数据。Chrome DevTools 的 Performance 面板录一段操作，火焰图里：

  • 紫色块是 Layout（重排），多且密就是布局抖动。
  • 绿色块是 Paint（重绘），大面积绿色说明绘制区域太大。
  • 鼠标悬上去，如果看到 “Forced reflow is a likely performance bottleneck” 的警告，那就是有代码在读写交错强制同步布局——点进去能直接跳到那行 JS。

我现在排查卡顿基本不靠脑补，录一段、看火焰图、找最宽的那块往下钻，比读十遍代码快。Rendering 面板里还能开 “Paint flashing”，页面上重绘的区域会闪绿框，肉眼就能看出是不是有不该重绘的地方在反复刷。

浏览器渲染不是黑盒。DOM、CSSOM、布局、绘制、合成每一步都有成本。

面试问重排和重绘，是因为它们能解释很多页面卡顿。项目里要少做无意义 DOM 操作，避免读写布局交错，批量修改节点，动画优先考虑 transform 和 opacity。
