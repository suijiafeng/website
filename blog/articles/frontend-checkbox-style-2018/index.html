自定义 checkbox 该怎么做：保留原生 input 才是正路

2018-05-10
前端基础CSS

自定义 checkbox 最常见的误区，不是颜色没对上，而是为了还原设计稿，先把原生控件整个扔掉。这样确实能更快画出一个“长得像”的方块，但键盘焦点、表单取值、可访问性这些原生能力也会一起被你扔掉。

我这次就是这么翻车的。设计稿里的品牌蓝复选框和浏览器默认样式差得太远，我下意识就走了最偷懒的路：拿 div 加 JS 自己画一个，点击切换 class，选中态补个对勾，两个小时搞定，像素级还原。

它看起来很像，真正的问题却都在提测之后才开始出现。

第一张 bug 单：键盘 Tab 切不过去

QA 的操作习惯是填表单不碰鼠标，Tab 一路切过去。切到我的"复选框"——焦点直接越过去了。div 默认不在 tab 顺序里，我压根没想过这件事。

第二张：表单提交收不到值。div 不是表单控件，没有 name 和 value，form 序列化时它就是个透明人。我当时是在 JS 里手动收集状态的，但这个表单后来被另一个同事复用，他按常规表单写法取值，取了个空。

第三张最扎心：公司有个大客户对系统有无障碍要求，验收用读屏软件过了一遍，我的复选框在读屏里就是一段普通文本，不播报"复选框"，不播报选中状态，空格键按下去也没反应。无障碍测试直接挂掉。

那几天我一边修一边意识到一个以前从没认真想过的问题：一个控件好不好用，鼠标用户往往感觉不到差别，但只用键盘的人、用读屏软件的人马上就会发现问题。 我做的那个东西只是"看起来像复选框"——真正稳定的 checkbox，是鼠标能点、键盘能切换、表单能提交、读屏软件能理解。原生 <input type="checkbox"> 把这些全做好了，是我亲手把它扔掉的。

修补了两天越修越多之后，我决定推倒重来：保留原生 input，只动样式。下面是这次返工的完整记录。

这里有个我在这次返工里踩的小坑：用 for/id 时，页面上 id 必须唯一。后台系统经常循环渲染一堆复选框，我偷懒把 id="agree" 写死在了循环模板里，出来全是同一个 id，点第二个切换的是第一个，调了半天才发现。后来的习惯是拿数据里的唯一字段拼 id，比如 :id="'agree-' + item.id"，别图省事写常量。

顺带说一下另一条路：appearance: none（加 -webkit- 前缀）可以把原生控件的默认外观整个抹掉，然后直接在 input 本身上画样式，连旁边的 span 都省了。我试了半天最后放弃——各家浏览器对 appearance 的支持和抹掉之后剩下什么都不一致，IE 干脆不认，伪元素在 input 上的表现也各家有各家的脾气。在 checkbox 这件事上，"隐藏原生 + 兄弟元素画皮"仍然是兼容性最稳的方案，Element UI 的 checkbox 拆开看也是这个套路：label 套着一个视觉隐藏的 input 和一个画样式的 span。

不需要额外 JavaScript 就有选中效果。对比我那个 div 版——监听 click、toggle class、再想办法把状态同步给表单——高下立判。我特别喜欢这个方案的一点是：状态的真相永远在 input 上，CSS 只是被动跟着 :checked 走。 不用手动同步、不用监听 change 再 toggle class，少了一整类"状态不一致"的 bug。div 版被 QA 抓到过一个"快速连点后视觉状态和实际提交值相反"的 bug，就属于这一类，原生方案里它根本不可能发生。

这里用相邻选择器 + 是有讲究的：它要求 .checkbox-box 紧跟在 input 后面，中间插了别的元素就选不中了，那时得换通用兄弟选择器 ~。我一般保持 input 紧贴着 box，结构稳定，选择器也最简单。

那个对勾用的是 border 画法——一个旋转 45 度的方块，只留右边和下边两条边。比起放一张对勾图片或者 icon font，纯 CSS 画的对勾在高分屏上永远清晰，也不多一次请求。尺寸要自己微调，width、height、border-width 三个值配合 box 的大小调，调到对勾居中、比例顺眼为止。这块没有公式，我就是对着屏幕拧了二十分钟，设计师坐我旁边说"再往下一像素"。

返工第四步：焦点态是这次返工里最容易被忽略的一环

被那三张 bug 单教育之后，我给焦点状态补了课。键盘用户 Tab 切到复选框时，需要知道当前焦点在哪里，所以选中框上要有可见的焦点样式：

为什么用 :focus-visible 而不是 :focus？因为 :focus 鼠标点一下也会触发，那个描边框会在鼠标用户点完之后赖着不走——我们设计师看到第一版就说"把那个框去掉"。:focus-visible 只在浏览器判断为键盘操作时才出现，鼠标点击不显示，两边都照顾到。它现在还很新，规范都没完全定稿，老浏览器不支持也无所谓——退化成没有焦点框，至少不会比原来更差，讲究的话可以加官方那个 focus-visible polyfill。

如果担心兼容，可以做个兜底：先给 :focus 一个保守样式，再用 :focus:not(:focus-visible) 把鼠标态的去掉。

但千万别为了"好看"直接写 outline: none 把焦点框一刀切掉——那等于把键盘用户晾在原地，完全不知道焦点跑哪去了。我在 div 版里就是这么干的（div 加了 tabindex 之后出现焦点框，我嫌丑给 none 掉了），现在想起来脸热。

而这还只是补了最基础的交互。和原生 checkbox 相比，它没有更简单，只是把浏览器已经做好的事情重新做了一遍——而且还远没补齐：原生 checkbox 在表单里自动带上 name/value 参与提交，<div> 不会，得额外塞一个隐藏 input 去同步状态；原生还支持 indeterminate（半选）这种第三态，自己模拟又是一摊代码；读屏软件对原生 checkbox 的播报是现成的，自定义的得自己把 aria-checked 维护对。表单语义丢失、键盘操作不自然、可访问性变差、提交要额外处理、状态同步容易出错——我那三张 bug 单，张张都在这个清单里。

这次之后我给团队定了条规矩：除非设计稿要的效果原生 input 配 CSS 实在做不出来（这种情况极少），否则一律保留原生控件。 省下来的不只是开发时间，更是无障碍、表单提交、键盘交互这些隐性维护成本。

五月初，这版重新提测：QA 的键盘流一路 Tab 到底，表单取值正常，读屏播报"复选框，未选中"，无障碍验收一次通过。设计师对着像素稿量了一遍，也挑不出毛病——好看和好用，从来就不是二选一。

回到这次折腾给我留下的东西。美化 checkbox 的方法有很多，但最重要的一条是不要丢掉它原本的表单语义：保留原生 input，把视觉交给旁边的样式元素，让 :checked、:disabled、:indeterminate 这些伪类自然驱动表现。这样既能满足设计稿，又不破坏键盘、读屏和表单行为。这部分代价在写的时候看不见，等真出问题时返工成本却很高——我的三张 bug 单和四天返工可以作证。简单、稳妥、可维护，胜过把控件完全自造一遍。
