组件 props 和 events 设计：少传大对象，少暴露内部细节

2022-03-11
前端基础组件与状态Vue

组件复用的核心不是把代码拆出去，而是设计一个稳定的使用方式。

很多组件刚抽出来时很好用，后面需求一多，props 越加越多，事件越来越细，插槽到处开，最后组件内部结构被业务页面摸得一清二楚。看起来复用了，实际只是换了个地方耦合。

组件 API 要像接口一样设计。props 是输入，events 是输出，插槽是扩展点。边界不清，组件就会越来越难维护。

props 不要直接传整块业务对象

这没问题，但要看组件真正需要什么。如果组件只显示名字和头像，传整个 user 会让它和业务模型绑定太深。

插槽是扩展点，不是后门

插槽很强，但开太多会让组件失去控制。

这些是合理扩展点。

这种 API 很快会变成维护负担。

插槽应该对应稳定结构：头部、底部、空状态、操作区。不要把临时需求直接变成公共 slot。

默认行为要清楚

组件要有合理默认值。

如果每次使用都要传一堆配置，说明组件没有把常见场景照顾好。

默认值也要文档化。否则调用方不知道哪些可以省略，哪些必须传。

API 错误不要藏在组件里

有些业务组件内部会发请求，比如用户选择器远程搜索。

错误不要只 console.error。组件至少要展示失败状态，或者通过事件把错误抛给外部：

内部请求越多，组件越业务化。通用组件要谨慎内置请求。

我的组件 API 清单

设计 props/events 时，我会检查：

  • props 是否足够窄
  • 是否传了不必要的大业务对象
  • props 是否表达语义，而不是样式细节
  • events 是否描述对外动作
  • v-model 是否只用于值组件
  • 插槽是否是稳定扩展点
  • 默认值是否覆盖常见场景
  • 内部 API 错误是否有处理

组件 API 一旦被很多页面使用，就很难改。前期多想一点边界，后面能少还很多债。
