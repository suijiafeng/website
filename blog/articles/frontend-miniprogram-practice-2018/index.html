小程序开发实践：一个 Web 前端的水土不服记，从找不到 DOM 到 setData 卡顿

2018-08-16
前端基础移动与小程序

组长把我叫过去："商城小程序缺人，你去支援两个月。"我心想小程序不就是写在微信里的网页么，WXML 像 HTML，WXSS 像 CSS，还有 JS，能有多难。

第一天下午我就水土不服了。想给一个节点加个 class，条件反射地敲 document.querySelector——调试器告诉我 document is not defined。没有 document，没有 window，没有 DOM。想用熟悉的 axios，发现只能 wx.request。想照 Vue 的习惯动态拼个组件出来，发现模板是静态声明的，连 v-if 那种灵活度都要换成 wx:if 的规矩重学。

带教的同事看我一脸懵，扔过来一句话，后来证明是整个支援期最值钱的一句："别把它当缩小版浏览器。小程序是逻辑层和渲染层两个线程，你的 JS 和页面根本不在一个世界里，中间隔着一道序列化通信。"

这道"墙"解释了后面几乎所有坑的根源——setData 为什么贵、为什么不能频繁调、为什么传大对象会卡、模板里为什么调不了方法，全是因为数据要跨线程序列化搬运，而模板那边根本看不到你 JS 里的函数。理解了这堵墙，很多坑自然就会绕着走。

不服之二：CSS 世界的度量衡变了

第二个不适应是样式。小程序里的样式不是完整浏览器环境，有些 Web 里习惯的写法直接受限——最典型的是 WXSS 的 background-image 不能引本地文件，我把设计师给的背景图放进项目目录、路径写对了就是不显示，查了文档才知道是平台规则。

实际开发中，图片资源一般就这几条路：

  • 用线上图片地址（传 CDN）
  • 用小程序的 image 组件（它可以用本地资源）
  • 小图标用 iconfont 或雪碧图
  • 构建时统一处理静态资源

不要默认把 Web 项目的 CSS 直接搬过来，搬之前先过一遍平台限制。

度量衡也换了。小程序用 rpx 做尺寸适配：

rpx 的换算逻辑是把屏幕宽度固定当成 750rpx，设计稿如果是 750 宽，量多少写多少，特别省心。它解决的是不同设备宽度下的比例适配，但不代表所有场景都只用 rpx，两个坑我都踩过：

一是 1rpx 的边框在某些屏幕上会被算成 0 物理像素，直接消失——列表分隔线时有时无，我在自己手机上死活复现不了，借了台同事的手机才看到。细线我后来宁可用 1px，或者干脆上 transform: scale 那套 0.5px 方案。

二是字体。纯按 rpx 缩放的话，大屏手机上字被放得偏大，反而不好看。我一般字体用固定的 px，只让布局尺寸跟着 rpx 走，设计师看过真机后也认可这个折中。

还有个跨页面共享样式的小问题：每个页面的 wxss 是隔离的，公共样式得写在 app.wxss 里，或者用 @import。我习惯把按钮、卡片这些通用样式放 app.wxss，省得每个页面复制一遍。但 app.wxss 里的样式是全局的，类名起太通用（比如 .title）很容易和页面局部样式打架，所以全局类名我一律加前缀，.g-card、.g-btn 这样。

不服之三：setData，这个项目教我最深的一课

真正让我理解那堵"墙"的，是七月初的一次卡顿排查。商品列表页拉到两三百条之后，勾选一个商品的复选框，整个页面能肉眼可见地顿一下。同样的交互放浏览器里毫无压力，我一度怀疑是微信的问题。

带教的同事让我看勾选的代码。当时的写法是：把整个 list 拷一份、改一项、再整个 setData 回去。他说："你算算这一下搬了多少数据。setData 不是普通赋值，每一次调用，数据都要从逻辑层序列化、跨线程传给渲染层。你为了改一个布尔值，把几百条商品从头搬了一遍。"

顺着这次排查，setData 的几条纪律都立起来了：

  • 合并多次数据更新，别连着调
  • 只更新页面真正需要的字段
  • 避免一次传入很大的对象
  • 列表数据分页加载

这次排查之后，setData 的用法在我这里就定了型：更新必要字段，合并相邻更新，避免大对象来回过墙。

不服之四：页面之间怎么"说话"

Web 里的单页应用，页面间共享状态有 Vuex 这类现成方案。小程序这边我第一次遇到的需求是：列表页进详情页，详情页改了数据，回到列表页要刷新。

可选的路子有几条：

  • 返回时无脑重新请求列表
  • 用全局状态保存变化
  • 通过事件或页面栈找到上一个页面并更新

getCurrentPages() 这招我用过，但用多了真会后悔。它有几个隐患：一是页面栈可能因为 redirectTo、reLaunch 变化，pages.length - 2 不一定是你以为的那个列表页；二是直接改别的页面的 data，等于把两个页面的内部状态焊死，哪天列表页字段名一改，详情页这边静默就坏了，而且很难想到去那儿找原因。页面之间如果开始频繁互相改数据，说明状态边界需要重新设计。

后来稍复杂的场景，我更倾向往 getApp().globalData 上挂状态：详情页改完数据，往 globalData 写个 productUpdated 标记，列表页 onShow 时读一下决定要不要刷新。逻辑收口到一个地方，比页面之间互相伸手干净得多。真到了订单、购物车这种多页面共享的复杂状态，就该考虑正经的状态管理方案了，土办法撑不住。判断标准也简单：只要发现自己在算"上一页是第几个"，基本就该换思路了。

顺带一个导航相关的坑：页面栈是有层数上限的，navigateTo 一层层往里叠，叠到顶再跳就直接失败。商品详情里推荐商品又能点进另一个详情，这种"详情套详情"的链路特别容易撞上限，撞上后跳转静默不生效，用户点了没反应还以为卡了。我们的处理是详情跳详情用 redirectTo 替换当前页，不再加深栈——代价是回退少了一层，产品确认过可以接受。

不服之五：包体积，上线前一周才发现的墙

八月初准备上线，构建时被开发者工具拦下：主包超 2MB，传不上去。Web 开发里包大了顶多首屏慢点，小程序是直接不让你发布，这堵墙硬得多。

翻了一圈找到两个大头：一是有人把好几张几百 KB 的本地大图放进了 images 目录打进主包；二是一个只有活动期间才用的抽奖页面也躺在主包里。处理思路就是分包：

  • 首页、登录、核心路径放主包
  • 低频页面放分包
  • 大资源尽量走 CDN

配置长这样：

图片挪去 CDN、抽奖页和订单流程拆成分包之后，主包降到 1MB 出头，用户首次打开只加载主包，启动也明显快了。主包应该只放启动必须的页面和公共能力；低频、重资源、独立业务流程进分包。

分包有条规则要在规划阶段就想清楚：**分包里的页面不能反过来引用别的分包的资源，公共组件和公共工具只能放主包。**我们拆到一半发现抽奖页用的一个弹窗组件被三个分包共用，只好挪回主包——要是页面结构设计时就按业务边界分好，这种回头路可以省掉。分包目前的不便是跳转要等分包下载，弱网下点进分包页面会有可感知的等待，只能靠 loading 提示兜着；希望平台后面能给出预加载之类的机制。

我专门留了"HTTP 200 但业务失败"这一类的处理——后端很多时候不管成败都返 200，真正的成败在 body 里的 code 字段。新人最容易漏的就是这个，光看 statusCode 以为成功了，结果业务失败、提示也没弹。把这层判断收进统一封装，比指望每个页面都记得检查靠谱得多。

wx.request 还有并发数限制，同时最多 10 个，超了要排队。首页那种一进来并发拉七八个接口再加图片预取的场景，得心里有数，别把关键接口排在队尾。另一个相关的坑是域名白名单：所有请求域名必须在小程序后台配置过、而且必须 HTTPS，本地调试时勾"不校验合法域名"一时爽，真机预览接口全挂——上线前一定拿真机、关掉那个勾选项跑一遍。

两个月支援期的沉淀

八月中旬支援期满，商城小程序上线，我回了原来的组。整理这两个月的水土不服，几乎每一条的根源都是同一句话——小程序不是缩小版浏览器，它是一套受平台约束的应用环境，有自己的运行模型。

逻辑层和渲染层之间那堵墙，决定了模板要薄、setData 要省、data 里只放视图要用的字段；平台的包体积和域名管控，决定了分包和资源策略要提前设计而不是上线前抢救；页面栈的机制，决定了页面通信要设计清楚边界，而不是伸手去改别人的 data。

带教的同事送我走的时候说："你现在踩过的这些，下个从 Web 转过来的人还会原样踩一遍。"如果哪位刚从浏览器世界跨过来的前端也遇上同样的水土不服，先别急着找 document——先把那两个线程的图画在纸上，后面的路会好走很多。
