小程序开发实践：那些前端容易踩到的坑

2018-08-16
前端基础移动与小程序

小程序和普通 Web 页面很像，但不能完全按 Web 的习惯去写。

很多前端第一次写小程序时，会发现模板、样式、数据更新、页面通信都有自己的规则。

如果不了解这些差异，很容易写出能跑但不好维护的代码。

小程序开发最重要的转变，是接受它有自己的运行模型。它不是缩小版浏览器，而是一套受平台约束的应用环境。

我刚转过来的时候吃过不少这种"想当然"的亏。第一反应就是找 document、想 querySelector，结果发现根本没有 DOM；想用熟悉的 axios，发现只能 wx.request；想动态拼个组件出来，发现模板是静态声明的，连 v-if 那种灵活度都没有。最关键的一点要早点想明白：小程序是逻辑层（JS）和渲染层（视图）两个线程，中间隔着一道序列化通信。这道"墙"解释了后面几乎所有性能问题的根源——setData 为什么贵、为什么不能频繁调用、为什么传大对象会卡，全是因为数据要跨线程序列化搬运。理解了这堵墙，很多坑你自然就会绕着走。

模板越薄，页面越容易维护。不要把格式化、筛选、排序都塞到模板表达式里。

这里有个新人特别容易踩的坑：模板的 {{ }} 里调不了你在 Page 里写的方法。我当年理所当然地写了 <text>{{ formatPrice(item.price) }}</text>，调试器里愣是不报错，就是不显示，排查半天才反应过来——模板表达式只能访问 data 里的数据和做简单运算，根本看不到 Page 实例上的方法。所以所有要展示的衍生数据，都得提前在 JS 里算好塞进 data。

正因如此，我后来养成习惯：从接口拿到原始数据后，先在一个地方集中做一遍"展示层加工"，把价格、时间、状态文案这些一次性都转好，再 setData。这样模板里全是现成的字段，既干净又少出错。如果项目复杂，这层加工逻辑还可以抽成独立的格式化函数，单测都好写：

样式资源要注意限制

小程序里的样式不是完整浏览器环境。

有些 Web 中习惯的写法，在小程序里会有限制。例如背景图引用本地资源时，需要注意平台规则。

实际开发中，图片资源一般有几种处理方式：

  • 使用线上图片地址
  • 使用小程序的 image 组件
  • 小图标用 iconfont 或雪碧图
  • 构建时统一处理静态资源

不要默认把 Web 项目的 CSS 直接搬过来。

小程序常用 rpx 做尺寸适配：

它解决的是不同设备宽度下的比例适配，但不代表所有场景都只用 rpx。比如细边框、字体大小和固定间距，仍然要结合真实设计效果判断。

rpx 的换算逻辑是把屏幕宽度固定当成 750rpx，所以设计稿如果是 750 宽，量多少就写多少，特别省心。但有两个坑我踩过：一是 1rpx 的边框在某些屏幕上会被算成 0 物理像素，直接消失，所以细线我宁可用 1px 或者干脆用 transform: scale 那套 0.5px 方案；二是字体，纯按 rpx 缩放的话，大屏手机上字会被放得偏大，反而不好看，我一般字体用固定的 px，只让布局尺寸跟着 rpx 走。

还有个跨页面共享样式的小问题：每个页面的 wxss 是隔离的，公共样式得在 app.wxss 里写，或者用 @import。我习惯把按钮、卡片这些通用样式放 app.wxss，省得每个页面复制一遍。但要注意 app.wxss 里的样式是全局的，类名起太通用（比如 .title）很容易和页面局部样式打架，所以全局类名我会加个前缀，比如 .g-card、.g-btn。

setData 不要过于频繁

小程序更新页面数据主要依赖 setData。

但 setData 不是普通赋值，它会触发数据从逻辑层同步到视图层。

如果频繁、大量调用，会影响性能。

更好的做法是：

  • 合并多次数据更新
  • 只更新页面真正需要的字段
  • 避免一次传入很大的对象
  • 列表数据分页加载

setData 的原则是：更新必要字段，合并相邻更新，避免大对象来回同步。

路径更新 [list[${index}].checked]: true 这个写法我要重点夸一下。早期我不知道有这招，列表里勾一个复选框，都是把整个 list 拷一份、改一项、再整个 setData 回去。列表一长（几百条），点一下都有肉眼可见的卡顿。后来改成只 setData 那一项的路径，差别立竿见影——因为跨线程搬运的数据量从"整个列表"缩成了"一个布尔值"。

还有一个量化的经验：单次 setData 的数据最好控制在几十 KB 以内，官方也建议不要超过 256KB。我们项目里出过一次列表越拉越卡的事故，最后定位到是有人把接口返回的完整对象（带一堆详情字段、富文本）整个塞进列表 data 了，其实列表页只用得到名字和价格。把无关字段在加工阶段砍掉之后，setData 的体积小了一大圈，滚动立马顺了。所以 data 里只放视图真正要用的字段，是个很值钱的纪律。

另外提醒一句，那个 searchTimer 我写在了 Page 外面当模块级变量，如果同一个页面可能存在多个实例（比如 tab 切换不销毁），更稳妥是挂到 this 上，避免几个实例共用一个定时器互相 clear。这种细节单页面跑不出问题，多实例场景才会暴露。

页面之间通信要设计清楚

小程序里经常有这样的流程：

从列表页进入详情页，在详情页修改数据后，回到列表页需要刷新。

这时可以根据场景选择：

  • 返回时重新请求列表
  • 使用全局状态保存变化
  • 通过事件或页面栈找到上一个页面并更新

不要让页面之间互相依赖太深，否则后面会很难维护。

getCurrentPages() 拿上一页 setData 这招我用过，但用多了真会后悔。它有几个隐患：一是页面栈可能因为 redirectTo、reLaunch 变化，pages.length - 2 不一定就是你以为的那个列表页；二是直接改别的页面的 data，相当于把两个页面的内部状态焊死，哪天列表页字段名一改，详情页这边静默就坏了，而且很难想到去那儿找原因。

后来稍微复杂点的项目，我更倾向用一个轻量的全局事件总线或者直接往 getApp().globalData 上挂状态。比如详情页改完数据，往 globalData 写个 productUpdated 标记，列表页 onShow 时读一下决定要不要刷新。逻辑收口到一个地方，比页面之间互相伸手干净得多。当然真到了订单、购物车这种多页面共享的复杂状态，就该考虑上正经的状态管理方案了，土办法是撑不住的。判断标准也简单：只要发现自己在算"上一页是第几个"，基本就该换思路了。

分包能缓解体积问题

小程序对包体积有限制。

如果所有页面和资源都放在主包里，项目变大后很快会遇到体积问题。

分包的思路是：

  • 首页、登录、核心路径放主包
  • 低频页面放分包
  • 大资源尽量走 CDN

这样用户首次打开时加载更快，主包也更容易控制。

主包应该放启动必须的页面和公共能力。低频、重资源、独立业务流程更适合进入分包。

我经手的一个项目就是上线前被体积卡住的。主包死活超 2MB，传不上去。翻了一圈发现两个大头：一是有人把好几张几百 KB 的本地大图放进了 images 目录打进主包，二是一个只有活动期间才用的抽奖页面也躺在主包里。把图片挪去 CDN、抽奖页拆成分包，主包立马降到 1MB 出头。

network: "wifi" 是只在 WiFi 下预下载，省得耗用户流量。这种优化体验上很值——首页加载只扛主包的轻量，用户浏览首页的工夫顺手把下游分包悄悄拉好，点进去就是秒开。要注意分包里的页面不能反过来引用别的分包的资源，公共组件还是得放主包，这点规划阶段就要想清楚，不然拆到一半发现依赖绕不开就尴尬了。

小结

小程序开发不能完全照搬 Web 思维。

模板逻辑要轻，setData 要克制，页面通信要有边界，资源和包体积要提前规划。接口错误也要统一处理，不要把异常分散在每个页面里。

理解这些差异后，小程序项目会稳定很多。写小程序不是把 Web 代码换个语法，而是按平台模型重新组织页面、数据和资源。
