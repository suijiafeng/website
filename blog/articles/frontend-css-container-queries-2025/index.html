容器查询用下来之后：我终于少写了一些页面级补丁样式

2025-07-12
前端基础CSS

我以前写响应式，几乎只靠媒体查询。

屏幕大于多少两列，小于多少一列。这个思路做页面整体布局没问题，但组件化项目写多了以后，我越来越觉得它不够用。

同一个卡片组件，放在首页主栏、侧边栏、弹窗、后台预览区、网格列表里，拿到的空间完全不一样。屏幕宽度相同，不代表组件容器宽度相同。

以前我的处理方式很粗糙：给不同页面加不同 class。

短期能解决问题，长期就开始变味。组件越来越依赖页面环境，复用一次就补一次样式。最离谱的一次，我在一个 post-card 的样式文件里数出了七个不同的页面前缀，.dashboard .post-card、.search-result .post-card、.modal-body .post-card……每个都只差几个像素的内边距和字号。改一处动全身，谁也不敢删，因为不知道哪个页面在依赖它。那阵子我一度怀疑是不是组件粒度切错了，后来才意识到，真正的问题是：组件本该根据自己的处境调整，可我手里只有"视口宽度"这一个信号。

容器查询让我第一次觉得，响应式可以更像组件自己的能力。组件不用再去问"我现在在哪个页面"，而是直接问"我现在有多大"。

真正该看的不是屏幕，而是组件有多少空间

媒体查询回答的是：视口多宽。

容器查询回答的是：组件所在的容器多宽。

这两个问题不一样。

一个后台统计卡片，在宽屏页面的主内容区可能有 600px，在右侧抽屉里可能只有 320px，在仪表盘网格里可能被压到 260px。视口宽度没有变，但组件需要呈现的姿态应该变。

这就是容器查询适合的地方：组件根据自己拿到的空间决定布局。

这段 CSS 的意思很直接：当卡片容器够宽，指标和操作按钮横向排；不够宽，就自然纵向排。

想确认浏览器支不支持，在控制台敲一行就行，返回布尔：

我也建议第一次上手的人亲手跑个最小 demo 把"查容器而不是查视口"这件事看明白。结构很简单：一个 shell 声明容器，里头放一个会响应的子元素。

关键在于观察方式：别去拖浏览器窗口（那是改视口），而是直接拖这个 shell 右下角的 resize 把手。把容器从窄拖到宽，越过 400px 的那一刻 .demo-box 背景就从灰变金；窗口大小自始至终没动。这就是容器查询和媒体查询最直观的区别——你也可以在 DevTools 的 Elements 面板里手动改 shell 的 width，盯着子元素样式在断点处切换。

这里有个我一开始没绕明白的细节：container-type: inline-size 声明在外层的 .metric-card-shell 上，但查询写在内层的 .metric-card 上。容器查询不能查询自己——一个元素既是容器又用 @container 查询自己是不生效的，所以我习惯多包一层 shell 专门当容器，把真正的布局元素放进去。后来这成了我的固定写法：凡是要做容器查询的组件，结构上一定是"shell 负责声明容器 + 内层负责响应"。

为什么是 inline-size 而不是 size？size 会同时建立水平和垂直两个方向的查询上下文，代价是浏览器必须知道容器的高度，于是它会把容器的尺寸从内容里"切断"——也就是容器高度不再由子元素撑开。我有次顺手写了 container-type: size，结果整个卡片塌成了 0 高度，排查了快十分钟才反应过来。绝大多数布局我们只关心宽度，inline-size 只切断行内方向（宽度），高度照常由内容决定，副作用小得多。这是我现在的默认选择，除非真的要按高度做布局，否则不碰 size。

我更喜欢给容器命名

真实项目里，组件嵌套通常比较深。如果只写匿名容器，后面排查样式会有点费劲。

所以我现在更倾向于给容器一个名字：

container-name 不是必须的，但它能让布局依赖更清楚。你一眼能看出这条规则在查询哪个容器，而不是猜最近的查询容器是谁。

我踩过一个小坑：规则没生效时，第一反应不要怀疑浏览器，先检查父级是否真的声明了 container-type，以及目标元素是否在那个容器内部。@container 查询的是最近的、声明了 container-type 的祖先，如果中间被某个没声明容器的层级隔开，或者你查的容器名拼错了（找不到对应名字时，整条规则会被静默忽略，不会报错），样式就会神不知鬼不觉地失效。

命名还顺手解决了另一个问题：嵌套容器的歧义。卡片外面套一层容器，卡片自己又是一层容器，这时候匿名查询只会命中最近的那层，很容易查错对象。给容器起名之后，@container article-card (...) 明确指向那一层，哪怕中间又插了别的容器也不受影响。我现在的命名习惯是直接用组件名，让查询语句读起来就是一句话——"当 article-card 这个容器宽于 520px 时"。

还有个容易忽略的点：容器查询里可以用 cqw、cqi 这类容器相对单位。cqi 是容器行内尺寸的 1%，做卡片内的流式字号很顺手：

字号跟着容器宽度走，而不是跟着视口走。同一个卡片放进窄抽屉，标题自动小一号，不用再为它单独写断点。我把它和容器查询当成一套组合拳：断点负责"换布局"这种离散的跳变，cqi 负责"缩字号、调间距"这种连续的渐变。

它特别适合设计系统和中后台组件

中后台组件经常被复用到很多地方。

比如：

  • 数据卡片。
  • 文章/消息卡片。
  • 筛选工具栏。
  • 表格上方操作区。
  • 详情页信息块。
  • 仪表盘小组件。

这些组件如果只能根据视口变化，就会出现很多页面级补丁。容器查询让组件可以自己判断空间。

比如工具栏：

在宽容器里按钮显示图标和文字，在窄容器里只显示图标。这种逻辑更像组件自己的响应式，而不是页面告诉它“你现在在侧边栏，所以要变小”。

当然，隐藏文字要看场景，图标也要有可访问名称。我一般会给纯图标按钮补一个 aria-label，而不是真的把文字从 DOM 里删掉——display: none 之后屏幕阅读器也读不到它了。容器查询只负责布局，不负责替产品决定信息优先级。

这个工具栏还有个我特别喜欢的连锁反应：因为 .toolbar 本身用了 flex-wrap: wrap，所以即便没命中任何断点，按钮放不下时也会自然换行。容器查询在这里不是"唯一的兜底"，而是叠在 flex 自适应之上的精修。我现在写组件越来越倾向这种分层——先用 flex/grid 的内在自适应扛住大部分情况，再用容器查询处理那几个真正需要"换姿态"的临界点。纯靠断点硬切，断点之间的中间宽度反而最容易出问题。

媒体查询仍然有位置

我不会把容器查询看成媒体查询的替代品。

现在我的划分是：

  • 媒体查询负责页面结构。
  • 容器查询负责组件姿态。

页面结构包括：导航是否折叠、主栏和侧栏是否并排、底部栏是否变成抽屉。这些和视口强相关。

组件姿态包括：卡片横排还是竖排、工具栏是否换行、统计模块一行还是两行、缩略图是否展示。这些更适合看容器。

两者一起用时要注意断点不要互相打架。比如页面在 768px 把两列变一列，组件又在容器 520px 切内部结构，如果断点设计太接近，某些宽度下会反复压缩、换行、撑开。

我现在会多测几个真实内容宽度，而不是只看设计稿上的标准尺寸。具体做法很土但有效：打开 DevTools，拖动那个 shell 容器的宽度，从最窄拖到最宽，盯着看有没有哪一段在反复跳变。有一次我就是这么发现某个卡片在 510px 到 530px 之间会"抖"——页面断点和容器断点离得太近，窗口稍微一晃布局就来回横跳。把组件断点从 520px 挪到 560px，留出足够的缓冲带，问题就消失了。

它不只能查宽度，还有 style 查询

容器查询里我用得最多的当然是尺寸查询，但还有一类容易被忽略的——样式查询（style query），可以根据容器上某个自定义属性的值来决定样式：

它的价值在于把"组件的某种状态"和"这种状态下的样式"解耦开。父级只负责设置 --tone 这个变量，深层的子元素自己去查询并响应，中间不用一层层传 prop 或 class。我在做主题色随上下文切换的徽章时用过一次，省掉了一堆 .is-danger .badge 这种穿透选择器。不过要提醒一句，style query 的浏览器支持比尺寸查询晚，落地前一定要确认目标浏览器范围，别在生产里想当然。

内容溢出不是容器查询能自动解决的

容器查询让我少写了不少补丁样式，但它不是万能的。

标题过长、按钮文案太长、标签太多、数字异常大，这些仍然要有策略：

  • 文本是否换行。
  • 是否允许截断。
  • 最小宽度是多少。
  • 标签列表是否折叠。
  • 关键字段是否必须保留。

我以前有过一种偷懒想法：容器窄了就少展示几个字段。后来发现这不一定是布局问题，可能是信息架构问题。

对于 B 端页面，少展示一个字段可能会影响用户判断。窄容器不是随便删内容的理由，除非产品层面明确了优先级。

我现在的处理顺序大概是：能换行的先换行，能截断的截断时配上 title 或 tooltip 别让信息彻底丢失，实在放不下的关键字段宁可让容器横向滚动，也不轻易 display: none。比如一行指标：

min-width: 0 这行是我反复栽过跟头才记牢的。grid 和 flex 子项默认 min-width: auto，意味着它不会缩到比内容更窄，于是一个超长数字会直接把整个卡片撑破、把容器查询的判断也带歪。加上 min-width: 0 之后，子项才肯老老实实收缩，省略号才会生效。容器查询解决的是"组件该是什么姿态"，但姿态定了之后，内容溢出的兜底还得自己一条条铺。

容器查询让我对响应式布局的理解变了一点。

以前我更多是在写“屏幕到这个宽度，页面怎么变”。现在我会多问一句：“这个组件拿到多少空间时，自己应该怎么变？”

对于组件复用多、页面场景复杂的项目，这个问题更接近真实维护成本。少一点页面级补丁，多一点组件自适应，长期看会轻松很多。

回头看，容器查询带给我最实在的改变其实不是某段炫技的 CSS，而是组件文件夹里那些 .home .xxx、.sidebar .xxx 的补丁选择器一点点消失了。一个组件能不能"拎包入住"，扔进任何容器都不用额外伺候，这是我现在判断它健不健康的一个朴素标准。容器查询不是银弹，它不替你想信息架构、不替你做可访问性、也不替你管断点纪律。但它把"响应式"这件事的颗粒度，从页面级拉回到了组件级——而这恰好是我做组件化项目这些年，一直想要却一直缺的那块拼图。
