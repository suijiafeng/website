前端模块化到底改变了什么：从脚本堆叠到按职责拆文件

2021-07-28
前端基础

前端代码早些年一个很明显的问题，是脚本容易越堆越乱。

功能多了以后，全局变量增多，文件加载顺序越来越敏感，某个脚本漏引或顺序不对，页面就可能直接报错。模块化之所以重要，就是因为它在组织层面解决了这类问题。

我印象很深的一次，是接手一个老项目，页面底部排着十几个 <script> 标签，注释里写着“顺序不要动”。后来真有人为了引一个新插件，把某个脚本往上挪了一行，结果首页直接白屏——因为下面的脚本默认上面那个已经把 window.App 准备好了。这种隐式的、靠加载顺序维系的依赖，是我最早对“模块化到底解决什么问题”有直观感受的开始。它没有任何编译期检查，错了只能在运行时炸给你看。

模块化本质上是在控制依赖关系

一个文件如果什么都能访问、什么都能改，短期看灵活，长期一定难维护。

模块化带来的核心变化是：

  • 每个文件负责什么更明确
  • 依赖从哪里来更明确
  • 对外暴露什么能力更明确

代码不再只是按“页面上有没有效果”组织，而开始按职责和依赖组织。

为什么全局变量方案撑不住复杂项目

当一个项目只有一两个脚本文件时，大家可能直接把函数挂到全局也能跑。

可一旦模块变多，就会出现很多问题：

  • 命名冲突
  • 依赖顺序难管理
  • 复用能力差
  • 测试和重构成本高

你会发现代码并不是不能运行，而是越来越难碰。谁都怕改，改一点就担心牵一大片。

早期大家其实也想了不少办法去绕开全局污染，最常见的就是 IIFE（立即执行函数）加命名空间：

这种写法在当时确实管用，至少不会满屏 var 往 window 上糊。但它解决的只是“命名冲突”这一半问题，依赖关系那一半完全没动——MyApp.utils 到底依赖谁、谁先加载，还是得靠人脑和 <script> 顺序去保证。后来 AMD（RequireJS）、CommonJS 出现，都是在补这后半段：把“我需要谁”写进代码里，而不是写在 HTML 的标签顺序里。

那几年还有个绕不开的东西叫 UMD（Universal Module Definition）。一个库想同时被 <script> 直接引、被 RequireJS 的 AMD 加载、又被 Node 的 CommonJS require，作者没法假设运行环境，于是 UMD 干脆在文件头部判断：有没有 define 且 define.amd（AMD），有没有 module.exports（CommonJS），都没有就挂到全局。今天打开很多老库的 dist/xxx.umd.js，开头那一坨 typeof define === 'function' 的判断就是这个来历。它是“一份产物兼容三套加载方式”的妥协，ESM 普及之后才慢慢不需要了。

只看文件开头，你就知道这个模块依赖了什么。比起在代码中间突然调用一个全局函数，这种方式可读性要高很多。

而且 ESM 的 import/export 和 CommonJS 的 require 有几个关键差别，值得掰开说。

第一是加载时机。require 是运行时的同步函数调用——执行到那一行才去读文件、跑模块代码、返回 module.exports，所以你能把它塞进 if 里按条件加载，能用变量拼路径。ESM 的 import 是静态的，必须写在模块顶层，路径得是字符串字面量；引擎在执行前会先有一个“解析+实例化”的阶段，把整张依赖图先建好再求值（要动态加载得用返回 Promise 的 import()）。

正因为这种“死板”，打包工具才能在不运行代码的情况下，光靠分析语法就把依赖图画出来。这也是 Tree Shaking 能成立的前提——构建工具能确定 date.js 里只有 formatDate 被用到，就敢把同文件里其他没人引的导出删掉。require('./date') 是运行时才求值的动态调用，返回值是个普通对象，工具很难静态判断你最终用了哪些字段，做这种优化就吃力得多。

第二是顶层 await。ESM 允许在模块顶层直接写 await，引擎会把这个模块当成异步模块处理、依赖它的模块也会等它；CommonJS 没有这个能力，require 是同步的，拿不到也等不了 Promise。

循环依赖：两种模块体系的表现不一样

写了 import 不代表结构就一定好。模块拆得过碎、公共层和业务层互相引用，项目一样会乱。模块化提供的是组织能力，不是自动纠错能力，循环依赖就是最典型的反例。

比如 a.js 引 b.js，b.js 又反过来引 a.js，平时跑着没事，某天调整了一下导入顺序，就报出 Cannot read property of undefined。原因是某个模块还没执行完、导出还是 undefined 时，另一个模块就抢先用上了：

这里还有个值得知道的细节：循环依赖在两套体系下的“坏法”不一样。CommonJS 遇到环时，会把当时已经执行到的那部分 module.exports 返回给对方（一个半成品对象），所以你可能拿到一个缺了几个字段的导出，但不一定立刻报错，bug 更隐蔽。ESM 因为是先建图再求值、用的又是 live binding，环里的变量在被赋值前就是 undefined，一旦在顶层立即用它就直接炸出来——更吵，但也更早暴露。

我后来的习惯是：发现循环依赖，先别急着加 hack，而是退一步看是不是两个模块的职责该重新切——通常把它们共同依赖的那部分抽到第三个模块里，环就自然断开了。madge 这类工具可以直接把循环依赖图打出来，接手陌生项目时我一般会先跑一遍心里有个数。

浏览器原生支持 ESM 之后，心态上的一点变化

过去模块化几乎和打包绑死了——你写 import，但浏览器并不认，必须靠 webpack 之类的工具转译成它能执行的格式。后来浏览器原生支持了 <script type="module">，事情就有点不一样了：

type="module" 的脚本默认就是 defer 行为，会等 HTML 解析完再执行，而且默认开启严格模式、有独立作用域，不会再往全局乱挂东西。这意味着开发阶段的小 demo，甚至可以完全不打包，浏览器自己就能顺着 import 把模块一个个拉下来。

当然真上生产我还是会打包——原生 ESM 在网络层面是一个文件一个请求，模块一多瀑布式请求就拖慢首屏，而打包能把它们合并、压缩、做按需拆分。但理解了“模块化本身是语言层的能力，打包只是工程上的优化手段”，再去看构建配置时思路会清楚很多：工具是在帮你解决性能和兼容，而不是模块化必须依赖工具才成立。这层认知，比记住某个 loader 怎么配要管用得多。

导出边界会直接影响后面的维护和打包

模块拆开以后，还有一个容易被忽略的问题：到底导出什么。导出太少，别人只能复制代码；导出太多，模块边界很快就被打穿。我后来更倾向于让一个模块只暴露稳定能力，不暴露内部过程。
