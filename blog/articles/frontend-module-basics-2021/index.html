前端模块化到底改变了什么：从脚本堆叠到按职责拆文件

2021-07-28
前端基础

前端代码早些年一个很明显的问题，是脚本容易越堆越乱。

功能多了以后，全局变量增多，文件加载顺序越来越敏感，某个脚本漏引或顺序不对，页面就可能直接报错。模块化之所以重要，就是因为它在组织层面解决了这类问题。

模块化本质上是在控制依赖关系

一个文件如果什么都能访问、什么都能改，短期看灵活，长期一定难维护。

模块化带来的核心变化是：

  • 每个文件负责什么更明确
  • 依赖从哪里来更明确
  • 对外暴露什么能力更明确

也就是说，代码不再只是按“页面上有没有效果”组织，而开始按职责和依赖组织。

为什么全局变量方案撑不住复杂项目

当一个项目只有一两个脚本文件时，大家可能直接把函数挂到全局也能跑。

可一旦模块变多，就会出现很多问题：

  • 命名冲突
  • 依赖顺序难管理
  • 复用能力差
  • 测试和重构成本高

你会发现代码并不是不能运行，而是越来越难碰。谁都怕改，改一点就担心牵一大片。

模块化最直观的好处，就是依赖关系不再靠猜。

只看文件开头，你就知道这个模块依赖了什么。比起在代码中间突然调用一个全局函数，这种方式可读性要高很多。

同时，这也让构建工具更容易分析项目结构，做打包、拆分和优化。

模块化不仅是语法变化，也是协作方式变化

很多人会把模块化理解成只是 import / export 的写法升级。

其实更深一层看，它改变的是团队协作方式。因为代码一旦按模块组织，大家就更容易围绕清晰边界工作：

  • 公共能力放工具模块
  • 业务逻辑放业务模块
  • 页面层只做组合

这种边界如果立住了，后面维护体验会比“所有逻辑混在一起”好太多。

模块化并不自动带来好结构

当然，写了 import 不代表结构就一定好。

如果模块拆得过碎、循环依赖严重、公共层和业务层互相引用，项目一样会变乱。模块化提供的是组织能力，不是自动纠错能力。

所以真正有价值的，是借这个机制建立更清楚的职责边界。

它为什么会成为现代前端的基础

现在无论是框架项目、组件库还是构建工具链，几乎都默认建立在模块化基础上。原因很现实：

  • 前端项目体量变大了
  • 协作人数变多了
  • 构建和发布流程更复杂了
  • 代码复用需求更高了

在这种背景下，没有模块化几乎很难维持可维护性。

模块化的意义，最后还是回到“代码能不能被长期管理”

前端发展这些年，语法和工具一直在变，但模块化之所以能稳定留下来，是因为它解决的是长期问题。

页面不是一次性脚本，项目也不是只写一个月。只要代码需要迭代、复用和交接，就一定要有一套比全局堆叠更可靠的组织方式。

所以我一直觉得，前端模块化真正改变的，不只是导入导出语法，而是大家终于开始认真对待“代码结构”这件事了。

模块拆分最怕的，不是拆得少，而是拆得没有边界

有些项目虽然文件很多，但并没有真的模块化。因为模块之间的依赖关系非常混乱：工具层可以反向依赖业务层，公共组件偷偷读取页面状态，页面又直接操作基础设施模块。看起来目录很细，实际还是一团逻辑被分散到了更多文件里。

这类结构最容易出现的问题是，文件数量增长了，但职责没有更清楚。后来的人阅读代码时，要在很多文件之间来回跳，才能勉强拼出完整路径。

好的模块结构，应该让新需求更容易落位

我后来越来越重视一个判断标准：需求进来时，团队能不能比较自然地知道代码该加在哪里。

如果结构足够清楚，大家通常不会太纠结。反过来，如果每次新增功能都要先争论“这个东西到底算工具函数、服务层还是页面逻辑”，说明模块边界还没有真正稳定下来。

所以模块化最终要解决的，不只是当前代码能不能分文件，而是项目能不能继续长大。前端工程很多时候就是这样，真正好的结构不会显得多炫，但会在每次迭代时帮你省掉很多判断成本。

模块边界一旦模糊，重构成本会很快抬高

模块化真正值钱的地方，在于它能把变化限制在更小范围内。可如果一个模块既管数据请求、又管页面状态、又顺手操作 DOM，那它虽然被放在单独文件里，也依然会成为高耦合点。

这类模块最麻烦的地方是：

  • 任何小改动都容易牵出连锁影响
  • 很难单独测试或替换其中一部分
  • 逻辑迁移时不知道哪些依赖是隐式的

所以模块化不是“分文件就算完成”，而是要让每个模块的变化原因尽量单一。

好的模块结构会让排查路径更短

这点在真实项目里特别重要。出了问题以后，你如果能大致判断它更可能在请求层、状态层、组件层还是工具层，排查速度会快很多。

前端工程最后比的，不只是能不能把功能写出来，还包括问题出现后能不能快速把范围收窄。模块结构清楚时，这件事会轻松很多。
