Zustand 状态设计：小 store 也要有边界

2023-02-10
React前端基础组件与状态

Zustand 很容易让人喜欢。

API 少，没有 Provider 包裹，写起来直接：

但轻量不代表可以随便放。越是容易写全局状态，越容易把 store 写成新的全局变量仓库。

我见过一个项目，一个 useAppStore 里放了用户信息、主题、列表数据、弹窗状态、表单草稿、分页条件、上传进度。刚开始很方便，后面任何一个状态变化都可能影响一堆组件，没人敢删字段。

Zustand 的重点不是“少写样板代码”，而是让状态边界更清楚。

不要只有一个大 store

除非项目很小，否则不要把所有状态都塞进一个 store。

更好的方式是按领域拆：

拆分的标准不是文件数量，而是生命周期和业务边界。

用户信息和主题状态生命周期接近整个应用；编辑器状态只服务编辑页面；列表筛选条件可能应该放 URL，而不是全局 store。边界不同，就不该混在一起。

这段每次都会返回新对象，如果没有浅比较，可能导致重复渲染。可以使用 shallow，或者拆成多个选择器。

Zustand 的性能优势很大程度来自精确订阅。选择器写宽了，优势就没了。

action 放在 store 里更稳定

我更喜欢把修改逻辑放在 store action 里，而不是组件里直接 set 一堆字段。

组件只表达意图：

这样以后登出要顺便清 token、清权限、跳转登录，都有固定入口。

如果组件到处直接写 setState，业务规则会散掉。

派生状态尽量不要存

能从已有状态算出来的，通常不要再存一份。

不要同时存：

否则用户角色变化时，isAdmin 也要同步更新，一旦漏掉就出 bug。

只有派生计算非常贵，或者需要缓存历史结果时，才考虑存。大多数权限、状态判断、数量统计都可以直接算。

持久化要克制

Zustand 的 persist 很方便：

但不是所有全局状态都应该持久化。

适合持久化：

  • 主题
  • 语言
  • 用户偏好
  • 草稿

不适合持久化：

  • 权限缓存
  • 临时弹窗状态
  • 过期接口数据
  • 高敏感 token

尤其是权限和用户信息，要考虑过期和刷新。把一份旧权限长期存在 localStorage，用户角色变了，前端还按旧权限显示，非常危险。

如果确实要持久化，也要设计版本迁移：

本地存储里的旧数据不会因为你改了代码就自动变新。

服务端数据不要乱放 store

列表、详情、接口缓存通常更适合 React Query / SWR。

如果把接口数据放进 Zustand，就要自己处理 stale、refetch、retry、dedupe、mutation 失效。除非你明确要自己实现这些，否则不如让专门工具处理。

Zustand 更适合客户端拥有的状态：

  • 用户偏好
  • UI 布局
  • 跨组件临时状态
  • 复杂编辑器状态
  • 多步骤流程状态

我的 Zustand 清单

写 store 前，我会问：

  • 这个状态是否真的需要跨组件共享
  • 生命周期是否接近 store 所在领域
  • 是否可以放 URL、表单库或 React Query
  • 选择器是否足够窄
  • 修改逻辑是否有 action 入口
  • 派生状态是否重复存了
  • 持久化是否有过期和迁移策略

Zustand 很轻，但状态本身不轻。工具越自由，越需要边界感。store 小而清楚，比一个万能 store 更可靠。
