栈、堆和垃圾回收：变量为什么有的会被释放，有的不会

2019-02-03
JavaScript

内存相关问题在前端面试里经常出现。

基本类型和引用类型为什么不一样？闭包为什么可能占内存？页面开久了越来越慢，可能是什么原因？这些问题都绕不开栈、堆和垃圾回收。

不需要把底层实现背得很深，但要知道变量和对象大致放在哪里，什么时候可能释放不了。

让我开始认真看待这块的，是一个后台监控大屏页面。它要 7×24 小时挂在电视上不刷新，结果运行一两天后浏览器就卡得不行，最后整个标签页崩溃。功能逻辑完全正确，问题出在内存——每次定时刷新数据都留下点回收不掉的东西，积少成多。那次排查让我明白，前端的内存问题不会报错，它只是慢慢变卡、最后崩掉，反而比报错更难查。这篇就把当时理顺的这套东西记下来。

栈和堆

栈更适合保存函数调用、局部变量等生命周期明确的数据。

堆更适合保存对象、数组、函数这类大小不固定、生命周期不确定的数据。

JavaScript 里可以简单理解：

count 是基本类型，值本身简单。

user 保存的是对象引用，对象内容在堆里。

为什么要分两块？因为栈的管理方式特别简单高效：函数调用时，它的局部变量"压栈"，函数返回时整个栈帧直接"弹栈"，内存自动回收，不需要任何额外判断。这要求栈上的数据大小在编译/解析期就确定，所以适合放数字、布尔这种定长的简单值。而对象、数组的大小是运行时才知道、生命周期也不确定（可能被到处引用、活很久），没法用这种"用完即弹"的方式管理，只能放进堆里，由垃圾回收来决定什么时候释放。

这也解释了一个现象：函数递归太深会爆栈（Maximum call stack size exceeded），因为每层调用都占一个栈帧，栈空间是有限的；但你创建几万个对象一般不会爆栈，因为它们在堆里。我写递归处理树形菜单时就踩过爆栈，数据层级一深直接报错，后来改成用一个数组当显式栈的循环写法才解决——本质上是把调用栈搬到了堆上。

基本类型复制

基本类型复制的是值，互不影响。

引用类型复制

对象复制的是引用，a 和 b 指向同一个堆内对象。

这也是深拷贝和浅拷贝面试题的基础。这事在 Vue/React 里能直接坑到你：我刚学 Vue 时改一个表单，直接把 this.form 赋给 data 里另一个变量再去改，结果原对象跟着变了，因为两个变量指的是同一个堆对象。后来才知道要拷贝。浅拷贝（Object.assign({}, obj) 或 {...obj}）只复制第一层，嵌套对象还是共享引用；要彻底断开，得用深拷贝：

垃圾回收做什么

JavaScript 有垃圾回收机制。开发者通常不需要手动释放内存。

垃圾回收会找出不再可达的对象，然后释放。

例如：

如果没有其他引用指向原对象，它就有机会被回收。

判断"还在不在用"的核心是可达性：从一组根对象（全局对象 window、当前正在执行的函数调用栈等）出发，能顺着引用链走到的对象就是"可达"的、要保留；走不到的就是垃圾，可以回收。早期有些引擎用引用计数（数有几个引用指向它，归零就回收），但引用计数有个致命问题——循环引用回收不掉：A 引用 B、B 引用 A，哪怕外界已经没人用它俩了，它们互相的引用计数都不为零，就泄漏了。现代引擎（V8）用的是标记-清除（mark-and-sweep），从根出发标记所有可达对象，没被标记的统一清掉，天然解决循环引用问题。

还有一点值得知道：GC 不是想触发就触发的，开发者无法精确控制它什么时候跑（window.gc() 只在特殊启动参数下才有）。而且 GC 执行时会短暂"停顿"（Stop-The-World），V8 为了减少卡顿做了分代回收——新创建、很快就死的对象放新生代，频繁快速回收；活得久的晋升到老生代，回收得没那么勤。所以"少产生临时垃圾"对性能是有意义的，比如别在动画的每一帧里疯狂创建对象。

闭包为什么会保留变量

createCounter 执行完后，count 仍然被返回的函数引用，所以不会被释放。

闭包不是坏东西，但它会延长变量生命周期。

只要那个返回的函数还活着（被某个变量、某个事件监听器、某个定时器引用着），count 所在的那块作用域就回收不掉。闭包本身没问题，问题出在你"无意中"用闭包抓住了一个很大的对象，又忘了释放。我遇到过一个典型场景：在循环里给每个 DOM 元素绑事件，回调闭包里引用了循环外一个体积很大的数据对象，结果只要这些元素和监听还在，那个大对象就一直被吊在内存里下不来。

解决思路就是缩小闭包抓取的范围：只把真正用到的字段拿进闭包，别把整个大对象闭包进去；不再需要的引用主动置 null。能用闭包优雅解决的问题就用，但心里要清楚它"记住"了哪些东西，以及这些东西多大、什么时候该放手。

只要 node 变量还引用它，就不一定能释放。这种叫"游离 DOM"（detached DOM），元素已经从页面上摘掉了，但 JS 里还攥着它的引用，于是这个节点连同它下面的整棵子树都释放不掉。在 SPA 里频繁切换页面、列表反复重渲染时特别容易积累这种东西。

这四类坑在框架时代有一点好消息：用 Vue/React 时，组件卸载的生命周期钩子（Vue 的 beforeDestroy、React 的 componentWillUnmount）就是专门给你做清理的地方。我现在的固定习惯是——在哪个生命周期里 addEventListener / setInterval / 建立 WebSocket，就一定在卸载钩子里对应地 remove / clear / close。绑定和解绑成对出现，写的时候一起写，别指望事后补，事后基本都会漏。

注意 removeEventListener 必须传跟绑定时同一个函数引用才能解绑成功，所以别用匿名函数绑事件，否则根本解不掉，这又是一个隐蔽泄漏点。

怎么排查

Chrome DevTools 的 Memory 面板可以拍 heap snapshot，看对象数量和引用关系。

如果页面重复打开关闭某个弹窗，内存一直涨不回落，就要怀疑事件、定时器、闭包或全局缓存。

我排查那个监控大屏时用的具体手法，值得记一下，因为单看一张快照很难下结论。做法是"重复操作 + 对比快照"：先拍一张快照，然后把可疑操作（比如打开关闭弹窗）重复执行几十次，再拍第二张，用 Memory 面板的 Comparison 视图对比两张快照之间新增了哪些对象、增量是多少。如果某类对象（比如某个组件实例、某些 DOM 节点）数量随操作次数线性上涨、从不回落，基本就锁定泄漏点了。

还有个更直观的工具是 Performance 面板里勾上 Memory，录一段操作，看 JS Heap 那条曲线。正常情况是锯齿形——涨上去，GC 一跑又掉回来；如果是阶梯形只涨不跌，那就是在泄漏。在快照里点中泄漏的对象，右下角的 Retainers（引用链）能告诉你到底是谁还在引用它，顺着这条链往上找，通常就能定位到那个忘了清理的事件、定时器或缓存。当年我就是顺着 Retainers 找到一个忘了 clear 的 setInterval，它的回调闭包死死拽着整个组件实例不放。

小结

栈保存调用和简单变量，堆保存对象这类复杂数据。垃圾回收会释放不可达对象，但如果代码里仍然保留引用，对象就不会被回收。

面试问内存，项目里更要注意事件解绑、定时器清理、闭包引用和全局缓存。页面稳定运行，不只是功能正确，也包括资源能正常释放。
