Vue 2 项目尝试 TypeScript：类型安全和开发习惯都要磨合

2018-05-20
VueTypeScript

在 Vue 2 项目里引入 TypeScript，第一感觉不是“更安全”，而是“写法变重了”。

原来一个 .vue 文件里直接写 data、methods、computed，现在要考虑类型、装饰器、this 推断、接口返回结构。小项目里可能觉得麻烦，但项目一大，类型能帮忙挡住不少低级错误。

我是在一个已经跑了大半年的后台项目里动这个念头的。当时的导火索很具体：一个同事把接口返回的 status 字段当成了数字判断，可后端某次改成了字符串 "1"，前端没人发现，灰度上线后列表筛选整个失灵。这种问题用肉眼 review 很难抓，跑一遍也未必触发，但只要那个字段有类型，编译期就会红一片。那次之后我才下决心试 TypeScript，而不是因为它“看起来更专业”。

需要先说清楚 2018 年这套组合的现实：Vue 2 对 TypeScript 的支持是“能用，但不顺手”。vue 官方提供了 Vue.extend 和 vue-class-component，再加上 vue-property-decorator 做语法糖，但 .vue 单文件组件里 <script lang="ts"> 的类型推断要靠 vetur 插件撑着，IDE 时不时给你飘红或者干脆不识别。心理预期摆正了再上手，磨合期会少很多怨气。

另一个要提醒的是，接口类型最好和后端的字段“当下真实情况”对齐，而不是和接口文档对齐。文档经常滞后，后端偷偷加了字段或改了类型很常见。我的做法是把类型定义当成一份“前端这边对契约的理解”，每次联调发现不一致就立刻改类型，让编译器帮你记住这些差异，而不是靠脑子。

unknown 和 any 的区别是：any 会让类型检查彻底失效，沿着这个变量传下去的所有东西都不再检查；unknown 则强制你在用之前先收窄类型，相当于给自己留了个“这里还没处理好”的记号。我的经验是项目里可以全局搜索 as any 和 : any，把它们当成待还的债，每次重构顺手消一两个。一旦放任不管，半年后整个项目就退化成“穿着 TS 外衣的 JS”，类型报错全靠 any 压下去，那还不如不上。

team 里我立过一条软规矩：业务代码禁止裸 any，确实需要的地方要写注释说明原因，比如对接一个类型实在描述不清的第三方 SDK。这条规矩不靠 lint 强制，靠 code review 时互相盯，效果反而比 no-explicit-any 一刀切好——因为总有真该用 any 的场景，规则太死大家就开始用各种花招绕过它。

迁移要分阶段

老项目不要一次性全改。更稳的顺序：

  1. 新文件允许写 TypeScript
  2. 接口返回加类型
  3. 工具函数加类型
  4. Vuex state 和 mutation 加类型
  5. 再考虑组件整体迁移

如果一开始就要求所有 .vue 文件改成 TS，很容易把团队拖进语法细节里。

这个顺序不是拍脑袋排的，而是按“收益除以风险”排的。接口和工具函数是纯逻辑、没有 this 和组件生命周期的干扰，类型最好写、最不容易出幺蛾子，而且一旦加上，整个调用链都受益。组件迁移放最后，是因为它牵扯模板、装饰器、this 推断、第三方组件库的类型缺失，是这套体系里最容易让人崩溃的部分。先把容易的果子摘了，团队尝到甜头，后面推动组件迁移阻力会小很多。

allowJs 这个配置在迁移期很关键，它允许 .ts 和 .js 共存，让你能一个文件一个文件慢慢改，而不是改了一个就整个项目编译不过：

checkJs 先关掉，等纯 JS 文件都收拾差不多了再考虑打开。我们项目这套迁移前后拖了快三个月，中间一直是混合状态在正常上线发版的，没有出现“为了上 TS 停一个迭代”的情况。这点对说服老板和团队很重要——技术升级如果要停业务，多半推不动。

在 Vue 2 中渐进引入 TypeScript 更实际：先从接口与工具函数下手，收获类型带来的信心，再逐步覆盖组件与状态。别把 TypeScript 当成形式，按风险与收益分阶段推进，团队更容易接受也更稳妥。
