Vue 2 项目初尝 TypeScript：一个字段类型引发的冲动，和我按住没全上的理由

2018-05-20
VueTypeScript

类型问题最典型的一种翻车方式，就是后端只改了一个字段的形态，前端代码一行没动，功能却整片失效。没有类型约束时，这类问题太容易从 diff 和自测之间悄悄溜过去。

这次就是一个最朴素的例子：后端把接口返回的 status 从数字 1 改成了字符串 "1"，前端判断写的是 if (item.status === 1)，严格相等，一个都匹配不上。改动小到几乎不值得单独开会，真正落到灰度环境里却是整页筛选全失灵。

我说了一句"这种事要是字段有类型，编译期就红一片了"，说完自己心里一动。TypeScript 这东西我在掘金上看了快一年，Angular 全家桶早就是 TS 写的，Vue 社区里 vue-class-component 也热了一阵，但我一直停留在"看起来很专业"的围观阶段。这次不一样——我第一次有了一个具体的、被真实事故背书的理由，而不是因为它时髦。

当晚我在那个跑了大半年的后台项目上切了个分支，开始动手试。后面就把这一个多月里真正值得记的判断摊开：哪里确实有收益，哪里纯粹是在付摩擦成本，以及为什么最后我没有把它全面铺开。

上手第一天：写法确实变重了

先泼自己一盆冷水。在 Vue 2 项目里引入 TypeScript，第一感觉不是"更安全"，而是"写法变重了"。

原来一个 .vue 文件里直接写 data、methods、computed，想到哪写到哪；现在要考虑类型、装饰器、this 推断、接口返回结构。而且得先说清楚这套组合眼下的现实：Vue 2 对 TypeScript 的支持是"能用，但不顺手"。官方提供了 Vue.extend 和 vue-class-component，再加 vue-property-decorator 做语法糖，但 .vue 单文件组件里 <script lang="ts"> 的类型推断要靠 VS Code 的 vetur 插件撑着，时不时给你飘红或者干脆不识别。听说尤雨溪在 2.5 里专门改进过 TS 的类型定义，Vue.extend 里 this 的推断确实比更早的版本好了不少，但离"顺滑"还有距离。

版本上，现在是 TypeScript 2.8 的时代，2.9 的 RC 已经放出来了。2.8 加的条件类型（conditional types）社区吹得很凶，我承认看不太懂那些类型体操，好在业务代码里暂时用不上。心理预期摆正了再上手，磨合期会少很多怨气——这是我第一周最大的心得。

工程接入本身倒不算难。我们项目是 vue-cli 2.x 的 webpack 模板生成的，没有现成的 TS 选项，手动装 typescript 和 ts-loader，webpack 里给 .ts 加条规则，ts-loader 的 appendTsSuffixTo: [/\.vue$/] 配上，让 .vue 里的 <script lang="ts"> 也能被处理。半天配通。

分支切出来，我没有从组件下手，而是先给接口数据加类型——毕竟事故就出在接口字段上。事后看这是整个尝试里最正确的一步。

比起一上来改所有组件，先给接口加类型收益更明确。写到第三个接口的时候我已经体会到那种"编辑器替你记住一切"的爽感——字段名敲一半自动补全弹出来，拼错立刻飘红。

有个细节我写着写着才想通：role 用联合字面量 'admin' | 'editor' | 'guest' 比单纯的 string 有用得多。业务里经常有 if (user.role === 'admim') 这种手抖拼错，string 类型完全拦不住，但联合类型会直接告诉你这个值不在可选范围内。试验分支跑了两周，光这一条就抓出两三处存量 bug，全是把权限角色拼错导致某个菜单永远不显示的——这些 bug 在线上默默存在了几个月，没有类型系统，可能永远没人发现。

另一个提醒：接口类型要和后端字段的"当下真实情况"对齐，而不是和接口文档对齐。文档经常滞后，后端偷偷加字段改类型很常见——开头那次事故就是明证。我的做法是把类型定义当成一份"前端这边对契约的理解"，每次联调发现不一致就立刻改类型，让编译器帮我记住这些差异，而不是靠脑子。下次后端再改 status 的类型，编译器会第一个替我尖叫。

类组件写法的代价也很实在：它和 Vue 原来的 Options API 是两套心智，团队里有人不熟，维护起来就有成本。我最后在试验分支里定的规矩是：新写的、逻辑复杂的组件用类组件；老的、改动小的用 Vue.extend 包一层补个类型，别强求统一。两种风格并存确实不漂亮，但比为了"整齐"重写一堆稳定运行的页面划算得多。技术债要还，但不必一次性还。

第三方库的声明是同一类问题的另一面。运气好的库自带 .d.ts，或者 DefinitelyTyped 上有 @types/xxx 一装就好；运气不好的（尤其国内一些老组件库、内部 SDK），什么都没有，import 进来就是一片红。这种我就在 global.d.ts 里写一行 declare module 'xxx' 认怂放行——先让工程跑起来，声明以后慢慢补。

我还给试验分支立了条软规矩：业务代码禁止裸 any，确实需要的地方写注释说明原因，比如对接一个类型实在描述不清的第三方 SDK。这条不靠 lint 强制，靠 code review 互相盯，效果反而比一刀切的 no-explicit-any 好——总有真该用 any 的场景，规则太死，大家就开始用花招绕它。

编译速度：一盆没预料到的冷水

有个问题是我上手前完全没想到的：慢。ts-loader 做完整类型检查，改一行代码热更新要等好几秒，比纯 JS 时代明显迟钝。项目再大点这个等待会很伤。

社区的方案是 fork-ts-checker-webpack-plugin：ts-loader 开 transpileOnly 只做转译不做检查，类型检查丢到单独的进程里异步跑。构建速度回来了，类型错误在终端里稍晚一点报出来，不阻塞热更新。装上之后开发体验基本恢复，这个插件建议和 ts-loader 一起装，别等被慢逼疯了再找。

顺带一提，Babel 那边正在憋的 7 还是 beta，据说会带 @babel/preset-typescript、用 Babel 直接剥类型。真到那天转译路线可能又是一变，但现在生产项目我不敢碰 beta，看看就好。

迁移要分阶段——以及为什么我最后按住了

试验分支跑了一个月，五月的迭代里我把接口类型那部分合回了主干。但组件层面的全面迁移，我按住了。先说如果要迁，更稳的顺序：

  1. 新文件允许写 TypeScript
  2. 接口返回加类型
  3. 工具函数加类型
  4. Vuex state 和 mutation 加类型
  5. 再考虑组件整体迁移

如果一开始就要求所有 .vue 文件改成 TS，很容易把团队拖进语法细节里。这个顺序不是拍脑袋排的，而是按"收益除以风险"排的。接口和工具函数是纯逻辑，没有 this 和组件生命周期的干扰，类型最好写、最不容易出幺蛾子，而且一旦加上，整条调用链都受益。组件迁移放最后，因为它牵扯模板、装饰器、this 推断、第三方组件库的类型缺失，是这套体系里最容易让人崩溃的部分。先把容易的果子摘了，团队尝到甜头，后面再推阻力会小很多。

allowJs 这个配置在迁移期很关键，它允许 .ts 和 .js 共存，一个文件一个文件慢慢改，而不是改一个就全项目编译不过：

checkJs 先关掉，等纯 JS 文件收拾得差不多再考虑打开。这一个月我们一直是混合状态在正常发版的，没有出现"为了上 TS 停一个迭代"的情况——技术升级如果要停业务，多半推不动，这点对说服老板和团队很重要。

那为什么组件迁移我按住了？三个原因。一是团队里五个人只有我一个啃过 TS，类组件加装饰器这套对其他人是纯新语言，强推等于把维护成本转嫁给同事；二是 vetur 的 SFC 类型体验还不稳定，飘红误报会消耗大家对类型系统的信任；三是眼下 Vue 2 这套毕竟是靠装饰器和 shim 拼出来的，而官方对 TS 的支持明显还在快速改进——2.5 才刚重写过类型定义，谁知道下个版本又会变成什么样。既然接口类型和工具函数的类型已经把最疼的那类事故（就是四月那次）挡住了，剩下的部分，等生态再熟一熟不亏。

一个月后的结论

回到四月那次事故。上周后端又改了一个字段类型——这次是把列表接口的 total 从数字改成了字符串。编译器在联调当天下午就红给我看了，我改了一行类型、一行取值，十分钟收工，没等它走到灰度。就冲这一下，这一个月的折腾就没白费。

所以我的结论是两头的：TypeScript 在 Vue 2 项目里已经"能用且有真实收益"，但"全面上"的时机未必到了。接口类型、工具函数类型这种低成本高收益的部分，现在就可以加；类组件、Vuex 类型这些磨人的部分，跟着生态节奏走，不抢跑。如果你的团队还没准备好，观望也完全可以——类型系统跑不掉，但被半生不熟的工具链劝退一次，再想推就难了。

我自己会继续在新组件里写 TS，同时盯着 2.9 正式版和官方对 Vue 类型支持的后续动作。等哪天 .vue 文件里的类型推断不再靠插件硬撑，我再来写全面迁移的那篇。
