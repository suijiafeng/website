ESLint + Prettier 落地：风格问题别再留给 code review 争

2018-05-06
构建与模块化前端基础

代码风格一旦还靠 code review 去争，团队迟早会把大量精力浪费在分号、缩进和单双引号这种不会改变业务结果的事情上。真正该做的不是赢下某次争论，而是把“谁说了算”从人挪到工具上。

我们当时就是最典型的反面教材。一个小改动的 diff 里，真正改逻辑的只有三行，剩下二十多行全是格式变动：有人保存时删分号，有人保存时补分号；有人用两个空格，有人用四个。结果每次 review，讨论一半在看逻辑，一半在争样式。

我们四个人维护一个 Vue 项目，没有任何工具约束，全靠口头说"大家尽量统一"。于是每次打开 diff，评论区一半在讨论"这里要不要加分号"，merge 之后下一个人又给你改回去——典型的 style war。而分号要不要、单引号还是双引号、缩进几个空格、对象最后一项要不要拖尾逗号，这些问题本身没有标准答案，争出花来也不会让程序跑得更快。凡是能交给机器判断对错的事情，就不要留给人去争论。 我带着这句话去了下周的会，打算把 ESLint、Prettier、编辑器和提交前检查一起定下来。

会上第一个回合：ESLint 管质量，Prettier 管格式

会一开始阿哲就发难："上 ESLint 呗，semi 规则设成 never，一了百了。"

"设成 never 还是 always，咱俩又得吵一轮。而且我之前试过拿 ESLint 管格式，.eslintrc 里堆一大堆 indent、quotes、semi，每条都要开会定值，最后为'行宽 80 还是 100'又吵了一下午。"

我在白板上把两个工具的定位划开——这是我之前踩坑想明白的，它们根本不是一个东西，硬塞到一起反而互相打架。

ESLint 是 linter，关心的是"这段代码有没有问题"：

  • 声明了没用的变量、import 进来没用的模块
  • == 和 === 混用、变量在声明前就被使用
  • case 穿透、switch 漏 default
  • Vue 里 v-for 没写 key、模板里用了未定义的组件这类框架规则

这些是有对错之分的，改了能减少 bug。

Prettier 是 formatter，它根本不关心代码对不对，只关心"长得齐不齐"：换行和折行、缩进、单双引号、拖尾逗号、行宽。

Prettier 的哲学很激进：它把你的代码先解析成 AST，再完全按自己的规则重新打印一遍，几乎不保留你原来的格式。阿哲听到这里皱眉："那我写的格式全没了？""对，我的也全没了，所有人的都没了——所以输出永远一致。这正是我们最需要的。"

结论写在白板最上面：格式的事全权交给 Prettier，ESLint 只管质量，两边职责不重叠。 否则 ESLint 觉得该换行、Prettier 觉得不该换，保存一次跳一下，能把人逼疯。

第四个回合：编辑器——"我凭什么改我的设置"

方案过了，落地时新的拉扯来了。阿哲用四空格缩进用了八年："我本地爱怎么设怎么设，提交出去对就行了吧？"

理论上对，实践上不行——如果每个人编辑器设置不同，照样出现"我保存时格式化、你保存时不格式化"的局面。最有效的一招是：把推荐的编辑器配置也提交进仓库，而不是写在 README 里靠自觉。VS Code 支持项目级配置，仓库根目录建 .vscode/settings.json：

几点经验：

  • editor.defaultFormatter 一定要指定，否则装了多个格式化插件的人保存时不知道用哪个。
  • eslint.autoFixOnSave 能在保存时顺手修掉可自动修复的质量问题。
  • files.eol: "\n" 强制 LF，这条救过我们一次：阿哲用 Windows，默认 CRLF，有次提交后整个文件的换行符全变了，diff 显示"全文件被修改"。后来又补了个 .gitattributes，写上 * text=auto eol=lf，才彻底治好。

第五个回合：提交这道关，防的就是"总有例外"

本地配置再全，也总有人临时用别的编辑器改一行、或者关掉了 formatOnSave。所以提交这道关必须卡。

提醒一句：husky 0.14 认的就是 "precommit" 这个 script 名（没有横线，不是 pre-commit）。我第一次配的时候照着 Git 文档写成 pre-commit，commit 时一点反应没有，还以为装好了，排查半天才发现是名字不对。

这套流程的关键是 lint-staged 只处理 git add 进暂存区的文件，不是全量。我们这种几百文件的项目，全量跑一次 ESLint 要十几秒，但提交时通常只动了两三个文件，lint-staged 一秒跑完。eslint --fix 和 prettier --write 就地修复，最后 git add 把修复后的内容重新加回暂存区。

千万不要在 pre-commit 里跑全量构建或全量 lint。 我见过一个项目 pre-commit 跑 npm run build，每次提交等三分钟，结果全组学会了 git commit --no-verify 绕过去，hook 形同虚设。提交前检查必须快到让人察觉不到，慢一秒都是在逼大家作弊。

完整的检查链是分层的：

  • 保存时（editor formatOnSave）：最快，改一行救一行；
  • 提交前（precommit + lint-staged）：只查改动文件，秒级；
  • CI 里：跑全量 npm run lint，再加一句 prettier --list-different "src/**/*.{js,vue}" 查有没有漏网的格式不一致，作为最后兜底，挡住所有用 --no-verify 溜过来的。

CI 这层不能省。本地和 hook 都可能被人为绕过，只有 CI 是绕不过去的——MR 红了就是红了，合不进去。阿哲对这层的评价是"防的就是我这种人"，自知之明令人欣慰。

顺带把 .gitignore 和忽略文件也理了一遍。ESLint 和 Prettier 各自认一份忽略清单，.eslintignore 和 .prettierignore，格式和 .gitignore 一样，但它俩不会自动继承 .gitignore 的内容——Prettier 从 1.13 起会读取项目根目录的 .gitignore 作为默认忽略规则的补充，但更早的版本、以及 ESLint，都得单独维护一份忽略清单。我们项目里 dist/、node_modules/、自动生成的 *.d.ts、还有一份历史遗留的、格式故意不动的第三方脚本，都单独进了这两个忽略文件，否则每次全量跑 lint 都要处理一堆不该管的目录，跑起来又慢又容易报出没意义的错误。

给一年半的老项目开闸

规则定了，工具链通了，最后剩下最难的：这个项目已经写了一年半，几百个文件。

我图省事，直接 extends: ['eslint:recommended', 'plugin:vue/recommended']（注意是 recommended 不是 essential，规则严格得多），保存，全量跑一遍——四千多个 error。阿哲凑过来看了眼屏幕："哟，这就是你说的 airbnb 都不敢上的原因？"是的，全组不可能停下需求专门修 lint。

后来摸索出的渐进式接入法：

  1. 先只开最低档。Vue 项目用 plugin:vue/essential（只管必然出错的），JS 用 eslint:recommended，先修掉"会导致运行时报错"的问题，量不大。

  2. 能自动修的先批量修掉。全量跑一次 eslint --fix 和 prettier --write，把格式类、可自动修复的问题一次性铲平，单独提一个 commit，message 写清楚 "chore: 全量格式化，无逻辑改动"，方便 review 的人直接跳过这个 diff。

  3. 存量问题先冻结。实在改不动的历史代码，用行内注释临时关掉具体规则，而不是把整条规则全局关掉：

    这样新代码依然受约束，只是给老代码开了临时豁免，将来重构时再清掉。

  4. 规则逐步加严。等团队适应了，每隔一段时间往上提一档，比如从 vue/essential 升到 vue/recommended，每次只引入一小批新规则，配合一次集中修复。

团队规范的目标是降低沟通成本，不是让大家每天和 linter 打架。规则太激进，结果要么全组花一周修 lint，要么大家集体把检查关掉，两种都是失败。

停战协议

这套东西跑起来两个多星期了。上周我又 review 阿哲的 MR，diff 干干净净，就六行逻辑改动，一条格式评论都没有。我留的三条评论全在讨论边界情况——其中一条他确实漏了个空数组的处理，改了。

会后我把沉淀下来的原则记在了项目 wiki 上：

  • 职责分清：格式归 Prettier，质量归 ESLint，用 eslint-config-prettier 消除冲突；
  • 配置进仓库：.eslintrc、.prettierrc、.vscode/settings.json、.editorconfig、.gitattributes 全部提交，不依赖任何人的本地环境；
  • 分层兜底：保存时格式化挡第一层，precommit + lint-staged 挡第二层，CI 全量检查兜最后一层；
  • 检查要快：提交前只查改动文件，慢了大家就会绕过去；
  • 老项目渐进接入：从最低档起步，先自动修、再冻结存量、最后逐步加严。

这份 wiki 里还留了一条待办：项目里的 CSS/Sass 目前完全没有约束，.scss 文件里选择器嵌套深浅不一、有的用连字符命名有的用驼峰。JS 生态这套 lint + format 的组合思路同样适用于样式表——stylelint 管质量（比如禁止重复的选择器、限制嵌套层级），Prettier 本身也能格式化 CSS/Less/Scss。等这次的 JS 规范跑稳了，下一步就是照着同样的分层思路把 stylelint 接进来，眼下先把这条记在 wiki 里，不急着一次性把所有语言都收拾干净。

至于分号，semi: false 这条配置写进仓库之后就再没人提起过。投票那天起，这个话题在我们组已经永久闭幕。代码风格一旦工具化，code review 就能回归它本该关注的东西：逻辑、设计、边界情况。那四十多条评论的争吵，是我们组为分号吵的最后一架。
