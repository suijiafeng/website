ESLint 和 Prettier：代码风格不要靠口头约定

2018-05-06
构建与模块化前端基础

团队协作里，代码风格是最不值得吵、却最容易吵的东西。

我们组在 2017 年底有过一段很魔幻的日子。当时四个人维护一个 Vue 项目，没有任何工具约束，全靠口头说"大家尽量统一一下风格"。结果是：A 习惯两个空格缩进，B 用四个；C 喜欢加分号，D 觉得 ASI（自动分号插入）就够了；还有人 IDE 默认开了"保存时去掉行尾空格"，另一个人没开。于是每次打开 Git 的 diff，红红绿绿一大片，真正改了逻辑的可能只有三行，剩下二十行全是空格和分号的来回拉锯。Code review 的时候，评论区一半在讨论"这里要不要加分号"，merge 之后下一个人又给你改回去——典型的 style war。

那段时间我才真正理解一句话：凡是能交给机器判断对错的事情，就不要留给人去争论。 分号要不要、单引号还是双引号、缩进几个空格、对象最后一项要不要拖尾逗号，这些问题本身没有标准答案，争出花来也不会让程序跑得更快。ESLint 和 Prettier 的价值，就是把这些没有意义的争论一次性焊死，让所有人写出来的代码"长得一样"，然后大家把脑子省下来去想真正重要的事。

下面这篇是我把这套东西在两三个项目里落地、踩过坑之后整理出来的实战记录。技术栈是 2018 年的主流：Vue 2 + webpack，ESLint 4.x，Prettier 1.x，Node 8。

先分清楚：ESLint 管质量，Prettier 管格式

刚开始我犯过一个错误，以为有了 ESLint 就够了，因为 ESLint 里也有 indent、quotes、semi 这些规则，看起来格式问题它也能管。结果就是 .eslintrc 里堆了一大堆格式相关的规则，每条还要纠结值设成多少，团队内部又开始为"行宽到底是 80 还是 100"开会。

后来我想明白了，这两个工具的定位根本不一样，硬塞到一起反而互相打架：

ESLint 是 linter，它关心的是"这段代码有没有问题"：

  • 声明了没用的变量、import 进来没用的模块
  • == 和 === 混用、变量在声明前就被使用
  • case 穿透、switch 漏 default
  • Vue 里 v-for 没写 key、模板里用了未定义的组件这类框架规则

这些是有对错之分的，改了能减少 bug。

Prettier 是 formatter，它根本不关心代码对不对，只关心"长得齐不齐"：

  • 换行和折行
  • 缩进
  • 单双引号
  • 拖尾逗号
  • 行宽

Prettier 的哲学很激进：它会把你的代码先解析成 AST，再完全按自己的规则重新打印一遍，几乎不保留你原来的格式。所以它能做到"无论你怎么写，输出永远一致"，这正是团队统一最需要的特性。

我的结论是：格式的事全权交给 Prettier，ESLint 只管质量，两边的职责不要重叠。 否则 ESLint 觉得这里该换行、Prettier 觉得不该换行，保存一次跳一下，能把人逼疯（后面会讲怎么用 eslint-config-prettier 彻底解决这个冲突）。

让 ESLint 和 Prettier 不打架

这是当年最坑的一个点，单独拎出来说。

保存时格式化：把问题挡在本地

光有配置文件还不够。如果每个人编辑器设置不同，照样会出现"我保存时格式化、你保存时不格式化"的局面，提交出来还是乱。

最有效的一招是：把推荐的编辑器配置也提交进仓库，而不是写在 README 里靠大家自觉。VS Code 支持项目级配置，在仓库根目录建 .vscode/settings.json：

几点经验：

  • editor.defaultFormatter 一定要指定，否则装了多个格式化插件的人保存时不知道用哪个。
  • eslint.autoFixOnSave（2018 年 ESLint 插件的写法，后来版本改成了 editor.codeActionsOnSave）能在保存时顺手修掉可自动修复的质量问题。
  • files.eol: "\n" 强制 LF，这条救过我一次：组里有人用 Windows，默认 CRLF，提交后整个文件的换行符全变了，diff 显示"全文件被修改"，配合 .gitignore 同级的 .gitattributes 写上 * text=auto eol=lf 才彻底治好。

再在 README 里写一句"请安装 ESLint 和 Prettier 两个 VS Code 插件"，本地这一层就基本闭环了。formatOnSave 能把绝大部分格式问题在你按下 Ctrl+S 的那一刻就消化掉，根本到不了提交那一步。

提交前检查：用 husky + lint-staged 兜住漏网的

本地配置再全，也总有人临时用别的编辑器改一行、或者关掉了 formatOnSave。所以提交这道关必须卡。

注意：husky 1.x 之前的老版本（0.14）配置 key 是 "scripts": { "precommit": ... }，1.x 之后才改成上面这种 "husky": { "hooks": {} } 的结构。如果你照着别人 2016 年的博客抄，很可能 hook 根本没生效，我就被这个坑过——commit 时一点反应都没有，还以为装好了。

这套流程的关键是 lint-staged 只处理 git add 进暂存区的文件，不是全量。一个几百文件的项目，全量跑一次 ESLint 要十几秒，但提交时通常只动了两三个文件，lint-staged 一秒就跑完。eslint --fix 和 prettier --write 会就地修复，最后 git add 把修复后的内容重新加回暂存区。

千万不要在 pre-commit 里跑全量构建或全量 lint。 我见过一个项目 pre-commit 跑 npm run build，每次提交等三分钟，结果全组都学会了 git commit --no-verify 绕过去，hook 形同虚设。提交前检查必须快到让人察觉不到，慢一秒都是在逼大家作弊。

完整的检查链应该是分层的：

  • 保存时（editor formatOnSave）：最快，改一行救一行；
  • 提交前（pre-commit + lint-staged）：只查改动文件，秒级；
  • CI 里：跑全量 npm run lint + 测试，作为最后兜底，挡住所有用 --no-verify 溜过来的。

CI 这层不能省。本地和 hook 都可能被人为绕过，只有 CI 是绕不过去的——MR 红了就是红了，合不进去。

给老项目接入：千万别一次性开满规则

新项目从第一天就配好工具，很轻松。难的是给一个已经写了一两年、几百个文件的老项目接 ESLint。

我第一次干这事的时候，图省事直接 extends: ['eslint:recommended', 'plugin:vue/recommended']（注意是 recommended 不是 essential，规则严格得多），保存，跑一遍——四千多个 error。那一刻是真的绝望，根本没法改，全组也不可能停下需求专门来修 lint。

后来摸索出一套更现实的渐进式接入法：

  1. 先只开最低档。Vue 项目用 plugin:vue/essential（只管必然出错的），JS 用 eslint:recommended，先把"会导致运行时报错"的问题修掉，量不大。

  2. 能自动修的先批量修掉。跑一次 eslint --fix 和 prettier --write 全量，把格式类、可自动修复的问题一次性铲平，然后单独提一个 commit，commit message 写清楚"chore: 全量格式化，无逻辑改动"，方便 review 的人直接跳过这个 diff。

  3. 存量问题先冻结。对实在改不动的历史代码，可以用行内注释临时关掉具体规则，而不是把整条规则全局关掉：

    这样新代码依然受规则约束，只是给老代码开了个临时豁免，将来重构时再清掉。

  4. 规则逐步加严。等团队适应了，再每隔一段时间往上提一档，比如从 vue/essential 升到 vue/recommended，每次只引入一小批新规则，配合一次集中修复。

团队规范的目标是降低沟通成本，不是让大家每天和 linter 打架。规则太激进，结果就是要么全组花一周修 lint，要么大家集体把检查关掉，两种都是失败。

回头看，这套工具链解决的从来不是"代码美不美"的问题，而是把没有标准答案的争论从人的工作流里彻底删掉。

我自己后来固定下来的几条原则：

  • 职责分清：格式归 Prettier，质量归 ESLint，用 eslint-config-prettier 消除两者冲突；
  • 配置进仓库：.eslintrc、.prettierrc、.vscode/settings.json、.gitattributes 全部提交，不依赖任何人本地环境；
  • 分层兜底：保存时格式化挡第一层，pre-commit + lint-staged 挡第二层，CI 全量检查兜最后一层；
  • 检查要快：提交前只查改动文件，慢了大家就会绕过去；
  • 老项目渐进接入：从 recommended 起步，先自动修、再冻结存量、最后逐步加严。

代码风格一旦工具化，code review 就能回归它本该关注的东西——逻辑、设计、边界情况，而不是分号和空格。这才是接 ESLint 和 Prettier 真正赚到的地方。
