React Server Components 落地笔记：真正难的是边界，不是语法

2025-02-18
React组件与状态前端基础

React Server Components 最容易被误解成一个性能技巧。

很多人第一次听到它，会自然地把重点放在“组件可以跑在服务端”“少发一点 JavaScript”“首屏是不是更快”。这些当然是它的重要价值，但真正在项目里用起来之后，我反而觉得最难的不是语法，而是边界。

哪些组件应该在服务端？

哪些交互必须留在客户端？

数据获取、权限判断、缓存和错误处理应该放在哪里？

如果这些问题没想清楚，Server Components 不会自动让项目变清晰，甚至可能让组件边界更难理解。

Server Component 适合什么

我现在会把 Server Component 理解成“默认用于读数据和组织页面结构的组件”。

它适合这些场景：

  • 读取数据库或服务端接口
  • 根据权限决定展示内容
  • 渲染不需要浏览器状态的内容
  • 组装页面级布局
  • 减少客户端 JavaScript 体积

比如一个博客文章页，正文、作者信息、相关推荐、标签列表，大部分都不需要在浏览器里维护状态。它们天然适合放在服务端。

这类代码的好处是很直接：数据在哪里读，页面在哪里组装，用户最终拿到的是已经准备好的内容。组件不需要为了获取数据额外跑一段 useEffect，也不需要先渲染 loading 再补内容。

Client Component 仍然很重要

Server Components 不是为了消灭 Client Components。

只要组件需要浏览器能力，它就应该留在客户端。例如：

  • 输入框状态
  • 弹窗开关
  • 拖拽排序
  • 键盘快捷键
  • 浏览器存储
  • 动画和交互反馈

这种组件的核心是交互状态。它放在客户端是合理的，不需要为了“用 Server Components”而把简单交互绕复杂。

真正的边界在组件树中间

最常见的问题不是“全服务端”或“全客户端”，而是组件树中间的边界怎么切。

一个比较稳的原则是：服务端组件包客户端组件，而不是让客户端组件过早包住整页。

ArticleContent 可以是 Server Component，CommentEntry 可以是 Client Component。页面整体仍然由服务端组织，只有评论输入区需要浏览器状态。

反过来，如果你在很高的位置加了 "use client"，整个子树都会进入客户端边界，很多本来可以留在服务端的组件也被带过去了。

这段代码本身不一定错，但要意识到它扩大了客户端边界。更好的做法可能是把有状态的侧边栏按钮拆出去，不要让整个页面壳都变成客户端组件。

数据获取不要到处散

Server Components 让数据获取变得自然，但也容易让数据获取分散。

每个组件都可以 await，听起来很舒服，后面却可能出现这些问题：

  • 同一个接口被多个组件重复请求
  • 页面里看不出数据依赖关系
  • 缓存策略分散在很多文件
  • 错误处理不统一

所以我更建议在页面级或模块级明确数据边界。组件内部可以读数据，但要有约束。比如核心页面数据在 page 层准备，局部独立模块可以自己读取。

这类写法虽然没有把数据获取“组件化到极致”，但依赖关系更清楚。业务排查时，一眼能看到这个页面依赖哪些数据。

错误处理要统一

服务端组件里读数据失败，不能只靠默认报错页面兜底。

业务里常见的错误至少有几类：

  • 用户未登录
  • 无权限访问
  • 数据不存在
  • 上游接口超时
  • 数据格式异常

这些错误应该有统一的表达，而不是每个组件自己 throw new Error()。

页面层再根据错误类型决定渲染 404、登录页、权限提示，还是通用错误页。Server Components 没有降低错误处理的重要性，反而让服务端错误更早进入渲染链路，必须更认真。

缓存不是默认越多越好

Server Components 和服务端渲染常常会一起讨论缓存，但缓存策略不能只看性能。

文章、商品详情、帮助文档这类内容，缓存收益很高。用户信息、权限、订单状态这类内容，就要谨慎。缓存错了，不只是页面旧一点，可能是展示了不该展示的数据。

我会把数据分成三类：

  • 公共内容：适合缓存，关注更新延迟
  • 用户相关内容：谨慎缓存，关注隔离
  • 实时状态：优先保证准确，不要为了快牺牲正确性

边界清楚之后，缓存策略才有讨论意义。否则一句“服务端组件可以缓存”很容易变成事故来源。

我自己的落地感受

Server Components 最让我喜欢的地方，是它让“读数据的 UI”变简单了。

以前很多页面要先在客户端渲染一个空壳，再用 useEffect 请求数据，然后处理 loading、error、empty、success。现在很多只读页面可以直接在服务端准备好内容，客户端少跑很多无意义状态。

但它也要求团队更有边界意识。过去一个组件随便读浏览器状态、随便发请求、随便放交互，最多是代码乱一点。现在一旦服务端和客户端边界混乱，就会出现更难理解的问题：某个 Hook 不能用，某个对象不能序列化，某段代码跑在了你没预期的位置。

所以我觉得 Server Components 不是“React 又加了一个新功能”，而是在提醒我们重新拆分前端职责：读数据、组装页面、处理交互，不一定都应该发生在浏览器里。

延伸阅读

推荐看 React 官方文档中的 Server Components 和 "use client" 章节，也可以看 Next.js App Router 文档里关于数据获取、缓存、错误处理的说明。阅读时不要只记 API，更要关注它们如何划分服务端和客户端责任。

写在最后

React Server Components 的价值不只是少发 JavaScript，而是让页面结构、数据获取和交互边界重新变得清楚。

如果你把所有组件都往服务端塞，它会很别扭；如果你一遇到交互就把整页变成客户端组件，它也发挥不出价值。真正稳定的落地方式，是让服务端负责数据和结构，让客户端负责必要交互。边界切对了，它才会变成工程收益，而不是新的复杂度。
