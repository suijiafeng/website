npm scripts 项目工作流：把常用命令写进 package.json

2018-07-29
构建与模块化

接手过一个老项目，README 里写着"启动方式见群公告"，群公告又指向某个早就离职同事的 Wiki，Wiki 链接 404。我最后是翻了三个人的本地 shell history，才拼出来一条能跑起来的命令。那天我就下定决心：以后我维护的项目，所有"怎么跑"的知识，都要落在 package.json 里。

package.json 表面上是依赖清单，实际上它的 scripts 字段才是一个团队工作流的真正入口。依赖装好了不等于会用，而 scripts 回答的是另一个问题——这个项目到底"能做什么"、"该怎么做"。命令散落在 README、聊天记录和每个人的肌肉记忆里，是新人接手最大的隐性成本。把开发、构建、测试、检查全收进 npm scripts 之后，新人 cat package.json 就知道这个项目有哪些能力，这件事的价值我后来越体会越深。

先把基础命令统一成四个词

我给自己定的第一条规矩是：任何项目里，启动、构建、检查、测试这四件最常做的事，命令名必须一模一样。不管底层是 webpack 还是别的，对外暴露的入口永远是 dev / build / lint / test。

为什么坚持统一？因为命令名是一种"接口契约"。我在 A 项目里 npm run dev，到了 B 项目还是 npm run dev，大脑就不用做切换。更重要的是 CI 配置、Docker 构建脚本、新人文档全都可以复用同一套词汇。我见过有的项目启动叫 serve，有的叫 start:dev，有的叫 run-local，每次切项目都要重新查一遍，这种摩擦看着小，一天下来其实很耗神。

底层那条 webpack 命令多长、参数多绕，都不该让人手敲。我曾经在没封装的项目里，因为漏写了 --config build/webpack.dev.js，webpack 默认去找根目录的 webpack.config.js，结果跑了个完全错误的配置，调了半小时才反应过来。把它锁进 scripts，这类低级失误就根本不会发生。

npm scripts 是怎么找到 webpack 的

刚开始用的时候我有个困惑：scripts 里直接写 webpack、eslint，但这些都没全局安装，凭什么能跑起来？

答案是 npm 在执行 scripts 时，会把当前项目的 node_modules/.bin 临时加到 PATH 的最前面。所有通过 npm 装的带可执行文件的包（webpack、eslint、jest 这些），安装时都会在 .bin 目录下放一个软链接。所以脚本里写 webpack 等价于写 ./node_modules/.bin/webpack，用的是项目本地那个版本，而不是某人全局装的、版本可能对不上的那个。

这也是为什么我从不建议全局装 webpack/eslint。全局版本和项目 devDependencies 里锁定的版本一旦不一致，就会出现"我这跑得好好的，他那报错"的经典扯皮。命令写进 scripts，版本跟着 package-lock.json（npm 5 之后默认生成），全队用的就是同一个二进制。

pre / post 钩子：好用，但别藏太深

npm scripts 有个约定：对任意脚本 foo，执行时会自动按 prefoo → foo → postfoo 的顺序串起来。这是个很实用的机制，我主要拿它做"强制前置检查"。

npm run build 会先跑 prebuild（lint 和测试都过了才往下走），再真正构建，最后 postbuild 输出一份产物体积报告。lint 不过、测试挂了，构建直接终止——这正是我想要的，把质量门禁焊死在构建前面，谁也绕不过去。

但这个机制有个我踩过的坑：流程被藏得太深，会让人"惊讶"。曾经有个项目把数据库迁移塞进了 prestart，新同事只是想本地跑一下前端，一条 npm start 把测试库的数据全洗了一遍。从那以后我的原则是：pre/post 里只放"幂等的、纯检查类"的步骤（lint、类型检查、测试），任何有副作用的操作（改数据库、发包、推远端）一律做成独立的、名字明确的命令，让人显式地敲，而不是被某个无关命令悄悄触发。

还有一点容易忘：pre/post 是 npm 帮你串的，如果你在脚本里用 && 自己串联，就不会再触发钩子。这俩机制别混着用，不然顺序会让你迷惑。

最常用的动作占据最短的名字（dev、build、lint、test），变体用 : 往下挂。lint:fix 一看就是 lint 的"自动修复"版本，test:watch 是 test 的"监听"版本，不用解释也能猜对。

别让脚本悄悄吞掉错误

这是我见过破坏力最强、又最隐蔽的一类写法：

|| true 的意思是"lint 失败也当成功"，于是 lint 报一堆错，构建照样往下走，质量检查彻底变成摆设。更糟的是，这类构建在 CI 上永远是绿的，没人会去翻日志，问题就这么一路漏到线上。

scripts 的默认行为本来是好的：任何一步非零退出，整条命令就以非零码失败，CI 会标红。我们要做的不是抑制错误，而是不要去抑制它。 除非有非常明确、写了注释说明的理由（比如某个工具在特定版本有已知的误报，且我们已经在别处兜住了），否则 || true、|| exit 0 这类"吞错误"的写法一律不许进仓库。

顺带一个相关的坑：用 && 串联时，前一步失败后面就不会执行，这是对的；但如果你写成 ; 分隔（在某些 shell 脚本里），则无论前面成败都会继续，行为完全不同。在 package.json 里我只用 &&，要并行就交给 npm-run-all，绝不混 ;。

写在最后

npm scripts 是一个项目工作流的门面。它好不好用，直接决定了新人第一天的体验，以及半年后你自己回来还认不认得这个项目。

我自己总结下来就几条：四个核心命令名跨项目统一；用 pre/post 焊死质量门禁，但别把有副作用的操作藏进去；涉及环境变量和文件删除一律走 cross-env、rimraf 这类跨平台工具；命名用冒号分层；最关键的——永远不要写 || true 去吞错误。一份清楚的 package.json，省下的是日积月累的沟通成本，这笔账非常划算。
