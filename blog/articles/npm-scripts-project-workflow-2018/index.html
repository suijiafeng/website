部署命令靠口口相传的项目，我用 npm scripts 把它考古了一遍

2018-07-29
构建与模块化

工程化里最容易被低估的一笔债，不是构建慢，也不是脚手架旧，而是“怎么跑项目”这件事根本没写在仓库里。命令如果只活在 README、聊天记录、某几个人的 shell history 和一台 CI 机器上，新人每接手一次，都会把同样的考古过程重演一遍。

我第一次正面撞上这件事时，仓库里关于启动方式只写了一句“见群公告”，群公告又指向一个已经 404 的离职同事 Wiki。问一圈之后，每个人都能说出一版流程：有人记得本地怎么起，有人记得测试环境怎么打，有人记得线上还要手动拷文件，但没有任何一处把这些步骤完整地落在项目里。

最后我靠翻同事电脑上的 shell history，再从 Jenkins 任务里抠半条命令，才拼出完整流程。也就是从那时起，我才真正把 package.json scripts 当成项目工作流入口来看，而不只是依赖旁边顺手放命令的地方。

把口口相传的命令统一成四个词

我给自己定的第一条规矩是：任何项目里，启动、构建、检查、测试这四件最常做的事，命令名必须一模一样。不管底层是 webpack 还是别的，对外暴露的入口永远是 dev / build / lint / test。

注意 test 是 npm 的内置命令，可以直接 npm test，连 run 都省了，start 同理。其余自定义脚本都得带 run。顺带一个查询技巧：不带参数敲一句 npm run，会把当前项目所有脚本连同它们的实际命令列出来——接手陌生项目时，这一句就是目录页，比翻 README 快。

为什么坚持这四个词统一？因为命令名是一种"接口契约"。我在 A 项目里 npm run dev，到了 B 项目还是 npm run dev，大脑不用做切换。更重要的是 CI 配置、新人文档全都可以复用同一套词汇。我手上几个项目，启动有叫 serve 的、叫 start:dev 的、叫 run-local 的，每次切项目都要重新查一遍，这种摩擦看着小，一天下来很耗神。

底层那条 webpack 命令多长、参数多绕，都不该让人手敲。考古期间我自己就中过招：漏写了 --config build/webpack.dev.js，webpack 默认去找根目录的 webpack.config.js——这项目根目录恰好留着一份废弃配置——跑了个完全错误的构建，调了半小时才反应过来。把命令锁进 scripts，这类低级失误就根本不会发生。

一个困惑：scripts 里的 webpack 是从哪来的

收敛过程中我解开了一个一直没细想的困惑：scripts 里直接写 webpack、eslint，但这些都没全局安装，凭什么能跑起来？

答案是 npm 在执行 scripts 时，会把当前项目的 node_modules/.bin 临时加到 PATH 的最前面。所有通过 npm 装的带可执行文件的包（webpack、eslint、jest 这些），安装时都会在 .bin 目录下放一个软链接。所以脚本里写 webpack 等价于写 ./node_modules/.bin/webpack，用的是项目本地锁定的版本。

这个机制恰好解释了一桩悬案：那位说"跑 webpack -p 就行"的资深同事，他机器上全局装着 webpack 1.x，而项目 devDependencies 里是 3.x——他在命令行裸敲 webpack 用的是全局老版本，"在他机器上是好的"，换台机器就报一堆看不懂的错。这就是为什么我从不建议全局装 webpack/eslint：命令写进 scripts，版本跟着 package-lock.json（npm 5 之后默认生成）走，全队用的就是同一个二进制。

pre / post 钩子：好用，但别藏太深

npm scripts 有个约定：对任意脚本 foo，执行时会自动按 prefoo → foo → postfoo 的顺序串起来。我拿它做"强制前置检查"：

npm run build 会先跑 prebuild（lint 和测试都过了才往下走），再真正构建，最后 postbuild 输出一份产物体积报告。lint 不过、测试挂了，构建直接终止——把质量门禁焊死在构建前面，谁也绕不过去。

但这个机制有个我踩过的坑：流程藏得太深，会让人"惊讶"。之前待过的一个项目把数据库迁移塞进了 prestart，新同事只是想本地跑一下前端，一条 npm start 把测试库的数据全洗了一遍。从那以后我的原则是：pre/post 里只放幂等的、纯检查类的步骤（lint、类型检查、测试），任何有副作用的操作（改数据库、发包、推远端）一律做成独立的、名字明确的命令，让人显式地敲，而不是被某个无关命令悄悄触发。

还有一点容易忘：pre/post 是 npm 帮你串的，如果你在脚本里用 && 自己串联，就不会再触发钩子。这俩机制别混着用，不然执行顺序会让你迷惑。

别让脚本悄悄吞掉错误

收敛快完成时，我在 Jenkins 那个老任务的配置里发现了这个项目最深的一处雷：

|| true 的意思是"lint 失败也当成功"。于是 lint 报着一百多个错，构建照样往下走，CI 上永远是绿的，没人会去翻日志。**这就是为什么这个项目的 lint 形同虚设——不是没配，是配了又被人静音了。**问题就这么一路漏到线上。

scripts 的默认行为本来是好的：任何一步非零退出，整条命令就以非零码失败，CI 会标红。我们要做的不是抑制错误，而是不要去抑制它。除非有非常明确、写了注释说明的理由（比如某个工具在特定版本有已知误报，且已经在别处兜住），否则 || true、|| exit 0 这类"吞错误"的写法一律不许进仓库。那一百多个 lint 错误，我分两周慢慢清完了。

顺带一个相关的坑：用 && 串联时，前一步失败后面就不会执行，这是对的；但如果写成 ; 分隔（在某些 shell 脚本里），无论前面成败都会继续，行为完全不同。在 package.json 里我只用 &&，要并行就交给 npm-run-all，绝不混 ;。

为了让"错误不被吞"从构建阶段提前到提交阶段，我还顺手加了 git 钩子这道闸：husky 接管 git hooks，lint-staged 只检查本次提交涉及的文件——存量烂账一大堆的老项目，全量 lint 卡提交谁也受不了，增量检查是唯一现实的落法：

补一句 build:report 里 -- 的用法：npm run xxx -- 后面的参数 会把 -- 之后的内容透传给底层命令，这样我能复用 build 脚本，只额外加一个开关，不用再复制一整条 webpack 命令。这个 -- 透传也困扰过我，不写它，参数会被 npm 自己吞掉。

ci 这条是给持续集成用的总入口，串行跑 lint → test → build，任何一步挂掉整条就失败。Jenkins 里那坨翻出来的配置被我删到只剩一行 npm run ci——"该跑哪些步骤、什么顺序"的决定权收回 package.json，换 CI 平台时配置几乎不用动。顺带说一句，Vue CLI 3 的 rc 版我在自己的玩具项目里试了试，它默认生成的 scripts 也是 serve / build / lint 这种短名字加冒号变体的路数，看来大家收敛出的方向是一致的。

回到那一天半

组里来了个实习生，我让他自己把项目跑起来，没给任何口头交代。他 clone、npm install、看了眼 npm run 列出的清单，npm run dev，前后十分钟。我最初花的是一天半。

npm scripts 是一个项目工作流的门面，它好不好用，直接决定了新人第一天的体验，以及半年后自己回来还认不认得这个项目。留下的习惯就几条：四个核心命令名跨项目统一；用 pre/post 焊死质量门禁，但别把有副作用的操作藏进去；涉及环境变量和文件删除一律走 cross-env、rimraf 这类跨平台工具；命名用冒号分层；提交前有 husky 把门；最关键的——永远不要写 || true 去吞错误。

那三个人的 shell history 我都截了图存了下来。等哪天有人问我为什么对 package.json 这么较真，就把图发给他看。
