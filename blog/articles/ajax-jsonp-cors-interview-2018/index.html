组内技术摸底被连环追问 Ajax、JSONP 和 CORS 预检：我是怎么一步步露馅的

2018-05-09
JavaScript前端基础

四月底组里搞了一轮技术摸底，说是年中要给几个新人定培养计划，先把老人的底子摸一遍，顺便看看谁能接下半年的分享。轮到我那场，组长开场很客气："看你平时接的都是前后端分离的活儿，那我们就聊聊跨域吧。"

跨域这东西我天天打交道——报错了配代理、让后端加个头，手熟得很。但接下来一个半小时的连环追问让我明白，"会用"和"知道为什么"之间隔着一整条护城河，而组长的每一问都精准踩在护城河里。

回工位的路上我把每一题记在手机备忘录里，这几天翻文档、写 demo、抓包验证，把当时答得含糊的地方全部补齐。被问倒的地方我原样保留，不遮丑，顺带把摸底之外几个相关的边界问题也一并理清。

那句注释里的场景组长也问到了："切页面不取消请求，会出什么 bug？"我正好遇到过：列表页快速来回切，旧请求晚到，把新页面的数据覆盖了，表现是"偶发数据错乱"，复现特别难。axios 里用 CancelToken 做这件事，本质还是调底层的 abort。这一小节勉强守住。

他又补了个开放题："fetch 用过吗？"我说试过，但项目里没上——fetch 不带超时、想中途取消也没有 xhr.abort 这么直接（AbortController 太新，兼容还不敢指望），而且 4xx/5xx 不会 reject，得自己判 response.ok，封装下来不比 axios 省事。他笑了笑："知道这些坑就行。"

第二问："什么叫同源？路径算吗？"

"说说同源策略。"

协议、域名、端口都相同，才算同源。我举了三组例子：

协议不同，不同源。

域名不同，不同源。

端口不同，不同源。

"http://a.com/x 和 http://a.com/y 呢？"——同源。同源只看协议、域名、端口，不看路径。这题我没掉坑，但他说太多候选人答错了。子域名是另一个高频坑：www.a.com 和 api.a.com 之间默认也跨域，公司用二级域名拆服务时几乎必踩。

然后是那个我答得最漂亮的问题："跨域报错时，请求到底发出去了没有？"

发出去了。同源策略是浏览器的安全限制，不是后端接口不能被访问，服务端之间的请求根本没这个限制。 被拦住的请求，你去抓包（Charles、Fiddler），能看到它到了服务器、服务器也返回了 200 和数据——是浏览器在拿到响应后，发现响应头里没有允许当前来源的标记，才不把响应体交给 JS。所以"跨域报错"和"接口挂了"是两码事：前者后端日志里有记录，后者根本没收到请求。我跟后端为这个撕过好几次，最后都是靠抓包定性——服务器有访问日志，那就是浏览器层的跨域，得在响应头上想办法。

组长顺势加了道延伸题："不用 CORS，两个子域名的页面想互相通信，有什么老办法？"我答了 document.domain——两边都设成 document.domain = 'a.com'，iframe 之间就能互访，但只对同一主域的子域有效。他又追了句"任意两个窗口呢？"——postMessage，HTML5 的标准姿势，父页面 iframe.contentWindow.postMessage(data, targetOrigin)，对面监听 message 事件，记得校验 event.origin 再处理，不然就是安全洞。这两个答上来了，全靠年初做过一个跨域名的 SSO 登录页。

"JSONP 的限制呢？"这个能答：只能 GET；错误处理弱（早期浏览器连 script 的 onerror 都不一定有，只能靠超时兜底）；需要后端配合返回函数调用。他补了我没说到位的一点：天然的安全隐患——你等于在执行一段第三方域名返回的 JS，对方返回什么你就跑什么，所以只能用在自己信得过的服务上。它适合老接口和简单的跨域读取，不适合复杂业务提交。新项目我基本不写 JSONP 了，只在对接一些上古第三方接口（某些地图、天气服务的老 API）时才碰到。

"那个 Vary: Origin 是干什么的？"——这题我答上来纯属运气，之前真被坑过：中间有 CDN 或缓存时，不加 Vary 可能把给 A 域名的 CORS 头缓存了发给 B 域名，出现"一会儿能跨域一会儿不能"的玄学问题。

他又抛了一个我彻底没防备的："前端想读后端自定义的响应头，比如分页的 X-Total-Count，直接 headers.get 能拿到吗?"我答"能吧"，错了。默认 JS 通过 CORS 只能读到几个简单响应头（Cache-Control、Content-Type、Expires、Last-Modified、Pragma 这几个），想读自定义的，后端必须额外声明 Access-Control-Expose-Headers: X-Total-Count，否则前端永远拿到 null。回家一查，我之前确实为这个排查过一下午——头其实回来了，是浏览器没暴露给 JS，当时糊里糊涂绕过去了，没往根子上查。同一个坑绕过去和填平，是两回事。

第五问，也是崩得最惨的一问："什么请求会触发预检？"

"OPTIONS 预检请求，什么条件下发？"

我只答出个大概："PUT、DELETE，还有……Content-Type 是 JSON 的时候？"他不置可否，让我把"简单请求"的完整定义说出来。说不出来。这就是当场露馅的感觉。

回来补的完整版：简单请求是指——方法是 GET / POST / HEAD，且 Content-Type 只在 text/plain、multipart/form-data、application/x-www-form-urlencoded 这三种里，并且没带自定义头。满足这些条件的请求不预检，直接发，浏览器拿到响应再校验 CORS 头。

只要破了任何一条——最常见的就是 Content-Type: application/json，或者加了 Authorization、X-Token 这类自定义头——就变成非简单请求，浏览器会先发一个 OPTIONS，问服务器"我接下来要用这个方法、带这些头，你允许吗"。后端要正确响应这条 OPTIONS：

预检通过了，真正的请求才会发出去。

组长讲了个场景让我诊断，而这个场景我真遇到过，算是扳回一城：联调时前端用 axios 发 JSON，控制台报跨域，后端咬定"我 POST 接口配了 CORS"。一抓包，红的根本不是那个 POST，而是它前面那条 OPTIONS——后端只给 POST 配了头，OPTIONS 走到框架里直接 404。浏览器看预检没过，真正的 POST 压根没发。所以后端的 CORS 中间件必须对 OPTIONS 也返回 200 和完整的允许头，很多框架的 cors 中间件默认会处理，手写的就容易漏。

最后一记追问："预检会不会拖慢接口？怎么优化？"——Access-Control-Max-Age，让浏览器在一段时间内不重复预检：

接口请求密集时不配这个，每个非简单请求前都多一条 OPTIONS 往返，白白多一倍请求数。这个我知道概念，说不出头的名字，扣一半分。

现在我排跨域问题有条铁律：先看 Network 里有没有那条 OPTIONS、状态码是多少、响应头全不全，再去看真正的业务请求。 很多跨域问题不是 GET 不通，而是预检没人管。

"为什么代理就不跨域了？"——浏览器请求的是本地开发服务器，同源；开发服务器再转发给后端，而代理是服务端转发，服务端之间没有同源限制，根本不会触发 CORS。这也是为什么本地开发用代理时，预检、响应头那些问题统统不出现，等部署到线上才暴露。

"changeOrigin: true 干什么用的？"——把转发请求的 Host 头改成 target 的域名。有些后端（带域名校验的，或者多个虚拟主机的 Nginx 后面）拿到不对的 Host 会返回 404 或错的站点。需要重写路径时还会用到 pathRewrite：

他最后的陷阱题："所以上了线，代理还管用吗？"——不管用。代理只是开发便利，那台 webpack 服务器生产环境根本不存在，线上仍然要配 Nginx 或后端 CORS。我见过有人本地跑得好好的，上线全跨域，因为他以为代理"解决"了跨域——其实只是开发环境绕过去了。线上更常见的是 Nginx 同域转发，前端和接口挂同一个域名下，连 CORS 都省了：

第七问："跨域失败，你的代码怎么向用户交代？"

最后一问落回工程："请求挂了，你的请求层怎么区分是跨域、是服务挂了、还是业务报错？"

跨域失败时前端不一定能拿到完整响应，请求层要区分网络错误、HTTP 错误和业务错误：

页面不要每个接口自己猜原因。我在 axios 的拦截器里把这层做掉，业务代码只拿到一个规范化的错误对象：

三层错误必须分清，混在一起是联调期扯皮的重灾区：

  • 网络/跨域错误：请求根本没拿到响应，error.response 是空的，status 是 0。提示"网络异常"，可以让用户重试。
  • HTTP 错误：拿到了响应但状态码是 4xx/5xx。401 跳登录、403 提示无权限、500 提示服务异常——按状态码分流。
  • 业务错误：HTTP 是 200，但响应体里后端自定义的 code 不为 0，比如"余额不足""验证码错误"。要把后端的 message 透出来给用户，而不是统一报"服务异常"。

这段我答得顺，因为就是我平时干的活。组长听完点点头："你工程上没问题，底层概念回去再顺一遍，下个月组内分享就讲这个。"

第八问，摸底之后自己补的一问："超时和重试怎么和跨域错误共存"

摸底结束后我自己又想到一层组长没问、但联调时天天遇到的问题：请求超时、被取消和跨域失败，在 error 对象里长得几乎一样，都是 error.response 为空。区分清楚它们，才不会把"接口本来就慢"误判成"又跨域了"。axios 的做法是给不同原因挂不同的标记：

超时配合 timeout 选项、取消配合 CancelToken，两者都不会真正发出跨域请求失败的信号，但表现出来的症状高度相似——排查时先看 Network 面板里那条请求到底有没有变红、有没有 OPTIONS，比对着 error 对象猜靠谱得多。

第九问："重试要不要连着预检一起重试"

组长后来在群里补了一句延伸的场景：接口偶发超时，前端加了重试逻辑，但重试之后跨域反而更容易失败，为什么。答案是非简单请求每次重试都要重新走一次完整的 OPTIONS 预检——除非命中了 Access-Control-Max-Age 的缓存窗口。如果重试间隔比这个窗口长，预检会一次不落地重新发生，网络本来就不稳时，等于把失败概率翻倍。真要做重试，最好把重试次数和退避时间也纳入跟后端的约定里，而不是前端自己悄悄加个 axios-retry 就了事。

跨域这一套，排查顺序我理清楚了：先确认协议、域名、端口到底是不是同源；再看响应头里有没有该有的 Access-Control-Allow-*；如果是非简单请求，看预检 OPTIONS 有没有被网关、鉴权或后端路由挡掉；然后区分超时、取消和真正的跨域失败；最后对照本地代理和线上 Nginx 是不是配了两套。Ajax、JSONP、CORS 这些名词背下来意义不大，能把浏览器限制、服务端响应和请求层错误处理串成一条线，联调时才不会来回甩锅。
