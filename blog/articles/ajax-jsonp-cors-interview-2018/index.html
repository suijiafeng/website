Ajax、JSONP 和跨域：接口联调时最常被问的老问题

2018-05-09
JavaScript前端基础

接口联调是前端日常工作里最容易出问题的环节。

页面写好了，请求发不出去；本地能访问，浏览器报跨域；后端说接口没问题，前端控制台一片红。Ajax、JSONP、CORS 这些概念看起来老，但只要做前后端分离，就绕不开。

我带过几个刚毕业的同学，发现一个共性：他们能熟练用 axios.get 拿数据，但一旦报跨域、一旦预检失败、一旦带 cookie 不生效，就彻底懵了——因为底下那层 XMLHttpRequest、同源策略、响应头到底怎么回事，从来没真正搞清楚过。面试官反复问这些，不是为了刁难，而是这套东西一旦不通，联调就会卡住整个迭代。我自己也是被几次线上事故逼着，才把这块从"会用"补成"知道为什么"。这篇就按我踩坑的顺序，把它们串成一条线。

Ajax 本质上是什么

Ajax 不是某一个库，而是一种在不刷新整个页面的情况下和服务端交换数据的方式。

这里有几个我被问到过、也实打实踩过的细节，值得展开说说。

第一个是 readyState 的五个值，面试经常让你背：0 未初始化、1 open 之后、2 收到响应头、3 正在下载响应体、4 完成。真正有用的其实只有 4，但理解中间几个状态能帮你看懂 progress 事件——比如大文件上传时监听 xhr.upload.onprogress 做进度条，靠的就是这套状态机在底下转。

第二个是 xhr.status === 0 这个坑。很多人以为请求失败一定有个 4xx/5xx，其实跨域被拦、网络断开、请求被浏览器取消时，status 都是 0，responseText 也是空的。我第一次排查"接口明明通了前端却报错"，就是因为 onreadystatechange 里只判了 status >= 200，没处理 0 这种情况，日志里什么都看不到。

切页面不取消请求，是个很隐蔽的 bug。我遇到过列表页快速来回切，旧请求晚到把新页面的数据覆盖了，表现就是"偶发数据错乱"，复现还特别难。axios 那时候用 CancelToken 来做这件事，本质上还是调底层的 abort。

什么是同源策略

浏览器有同源策略。协议、域名、端口都相同，才算同源。

协议不同，不同源。

域名不同，不同源。

端口不同，不同源。

同源策略是浏览器安全限制，不是后端接口不能被访问。服务端之间请求没有这个限制。

这句话我特意强调，是因为太多人误会了。被同源策略拦住的请求，其实是发出去了的——你去抓包（Charles、Fiddler），能看到请求到了服务器、服务器也返回了 200 和数据。是浏览器在拿到响应后，发现响应头里没有允许当前来源的标记，于是不把响应体交给 JS。所以"跨域报错"和"接口挂了"是两码事：前者后端日志里有记录，后者根本没收到请求。我跟后端撕过好几次，最后都是靠抓包定性——只要服务器有访问日志，那就是浏览器层的跨域，跟后端逻辑无关，得在响应头上想办法。

还有个常见误区：同源只看协议、域名、端口，不看路径。http://a.com/x 和 http://a.com/y 是同源的。子域名算不同源，www.a.com 和 api.a.com 之间默认也跨域，这点在公司用二级域名拆服务时几乎必踩。

另外还有一类前端拿不到自定义响应头的坑：默认 JS 通过 CORS 只能读到几个简单响应头，想读后端自定义的（比如分页用的 X-Total-Count、或者 Authorization），后端必须额外声明 Access-Control-Expose-Headers: X-Total-Count，否则前端 response.headers.get 永远是 null。这个我排查过一下午，最后发现头其实回来了，是浏览器没暴露给 JS。

这里要把"简单请求"和"非简单请求"讲清楚，因为这正是预检的触发条件。简单请求是指：方法是 GET / POST / HEAD，且 Content-Type 只在 text/plain、multipart/form-data、application/x-www-form-urlencoded 这三种里，并且没带自定义头。满足这些条件的请求不预检，直接发，浏览器拿到响应再校验 CORS 头。

只要破了任何一条——最常见的就是 Content-Type: application/json，或者加了 Authorization、X-Token 这种自定义头——就变成非简单请求，浏览器会先发一个 OPTIONS 预检，问服务器"我接下来要用这个方法、带这些头，你允许吗"。预检通过了才发真正的请求。

我踩过最典型的一次：联调时前端用 axios 发 JSON，控制台报跨域，后端却说"我 POST 接口配了 CORS 啊"。一抓包发现，红的根本不是那个 POST，而是它前面那条 OPTIONS——后端只给 POST 配了头，OPTIONS 走到框架里直接 404 了。浏览器看预检没过，真正的 POST 压根没发出去。所以后端的 CORS 中间件必须对 OPTIONS 也返回 200 和完整的允许头，很多框架的 cors 中间件默认会处理，手写的就容易漏。

预检也是可以缓存的，Access-Control-Max-Age 能让浏览器在一段时间内不重复预检：

接口请求密集时不配这个，每个非简单请求前都多一条 OPTIONS 往返，白白多一倍请求数。

很多跨域问题不是 GET 不通，而是预检请求没处理。排查时一个铁律：先看 Network 里有没有那条 OPTIONS、它的状态码是多少、响应头全不全，再去看真正的业务请求。

本地代理

开发环境可以用代理解决跨域：

浏览器请求本地开发服务器，由开发服务器转发给后端。浏览器看到的是同源请求。代理是服务端转发，服务端之间没有同源限制，所以根本不会触发 CORS——这也是为什么本地开发用代理时，预检、响应头那些问题统统不出现，等部署到线上才暴露。

changeOrigin: true 这个配置别漏，它会把转发请求的 Host 头改成 target 的域名。有些后端（尤其是带域名校验、或者多个虚拟主机的 Nginx 后面）拿到不对的 Host 会返回 404 或者错的站点，加上这个就好了。需要重写路径时还会用到 pathRewrite：

错误处理要统一

跨域失败时，前端不一定能拿到完整响应。请求层要区分网络错误、HTTP 错误和业务错误。

页面不要每个接口自己猜原因。我一般在 axios 的拦截器里把这层做掉，业务代码只拿到一个规范化的错误对象，不用自己 if error.response：

这里要分清三层错误，混在一起是联调期扯皮的重灾区：

  • 网络/跨域错误：请求根本没拿到响应，error.response 是空的，status 是 0。提示"网络异常"，可以让用户重试。
  • HTTP 错误：拿到了响应但状态码是 4xx/5xx。401 跳登录、403 提示无权限、500 提示服务异常——这些该按状态码分流。
  • 业务错误：HTTP 是 200，但响应体里后端自定义的 code 不为 0，比如"余额不足""验证码错误"。这种要把后端的 message 透出来给用户，而不是统一报"服务异常"。

把这三层在请求层一次性理清，页面就只管展示，排查问题时也能一眼看出错在哪一层。我现在新项目第一件事就是先把这个错误规范化和拦截器搭好，比写业务接口还靠前。

后来我排跨域问题，基本不会一上来就改代码。

先确认协议、域名、端口到底是不是同源；再看响应头里有没有该有的 Access-Control-Allow-*；如果是复杂请求，继续看预检 OPTIONS 有没有被网关、鉴权或后端路由挡掉；最后再对照本地代理和线上 Nginx 配置是不是写了两套。Ajax、JSONP、CORS 这些名词背下来意义不大，能把浏览器限制、服务端响应和请求层错误处理串起来，联调时才不会来回甩锅。
