前端主题切换怎么做：从深色模式到多主题

2022-10-05
前端基础CSS

主题切换是很多前端项目都会遇到的需求。

最常见的是浅色模式和深色模式，也有一些后台系统会支持品牌色切换、多套皮肤或节日主题。

它看起来是视觉问题，实际会影响 CSS 组织方式、组件封装和长期维护成本。

主题系统做得好，后面增加深色模式、多品牌、节日皮肤都比较自然；做得不好，就会变成到处覆盖样式、到处写特殊判断。

主题切换的核心是什么

主题切换不是简单地把背景色改成黑色。

真正需要管理的是一组设计变量：

  • 主色
  • 背景色
  • 文本色
  • 边框色
  • 阴影
  • 禁用态颜色
  • 成功、警告、错误等状态色

如果这些颜色散落在各个 CSS 文件里，后面改主题会非常痛苦。

所以主题切换的第一步不是写切换按钮，而是先定义 token。不要让组件直接依赖具体颜色，而是依赖语义变量。

我现在会把 token 粗略分成三层：

  • 基础色阶：blue-500、gray-100 这类颜色原料
  • 语义 token：color-text-primary、color-bg-panel 这类业务语义
  • 组件 token：button-bg、table-border 这类组件细节

基础色阶适合设计侧管理，业务组件更适合用语义 token。否则深色模式下继续写 gray-100 会很别扭，因为这个名字描述的是颜色本身，不描述它承担的角色。

主题切换里常见问题是页面先显示浅色，随后 JavaScript 运行后再切到深色，用户会看到明显闪烁。

color-scheme 会影响滚动条、表单控件等浏览器原生 UI 的默认配色。它不能替代业务主题，但能减少“页面是深色，输入框还是亮白”的违和感。

注意一定要内联，不能用 <script src> 外链。外链脚本要等额外的网络请求回来才执行，闪烁照样发生。我在一个 Next.js 项目里就为这个折腾过一阵——SSR 出来的 HTML 在服务端根本不知道用户的 localStorage，所以默认渲染浅色，到了客户端水合后才切深色，深色用户每次刷新都会“闪白一下”。最后的办法就是在 <head> 里塞一段 dangerouslySetInnerHTML 的内联脚本，赶在框架水合之前先把 class 打到 documentElement 上。这段脚本会在每个页面 HTML 里重复出现，所以越短越好，别在里面写花活，几行能跑完最理想。

还有个容易忽略的点：如果用 prefers-color-scheme 决定初值，最好把 <meta name="color-scheme" content="light dark"> 也加上，这样浏览器的滚动条、表单控件这些原生 UI 也会跟着深色，不然会出现页面是深色、滚动条却是亮色的割裂感。

组件库主题要单独处理

如果项目使用 Ant Design、Element Plus 这类组件库，主题切换不能只改业务 CSS。

还要看组件库本身支持哪种方式：

  • 是否支持 CSS 变量
  • 是否提供暗黑主题
  • 是否支持运行时切换 token
  • 是否需要单独引入主题样式文件

最理想的情况是：业务样式和组件库主题都由同一套变量或 token 驱动。

以 Element Plus 为例，它本身有一套 CSS 变量。如果业务样式用自己的变量，组件库用另一套变量，就要建立映射关系，而不是各写各的。

这样业务按钮、组件库按钮至少能跟随同一个主色变化。

如果组件库支持运行时 token，比如通过配置提供主题算法，也要确认它和业务 CSS 变量是不是同一份来源。我遇到过业务样式已经切到深色，但组件库弹窗仍然是浅色的情况，本质就是两套主题状态没有同步。

不建议写两套完全独立样式

有些项目会写 light.css 和 dark.css 两套完整文件。

短期看很直接，长期容易出现问题：

  • 两套样式内容重复
  • 新组件容易漏写暗黑样式
  • 修改一个细节要改两处
  • 主题之间差异越来越难控制

如果只是颜色不同，CSS 变量通常更容易维护。

当然，也不是所有差异都适合用变量解决。如果主题之间布局结构、插图资源、动效规则都完全不同，那可能已经不是“主题切换”，而是不同页面皮肤或不同产品形态。这个时候硬塞进一套变量里，反而会让系统复杂。

图片、阴影和图表也要考虑

深色模式里最容易漏的是非 CSS 颜色：

  • 图片和 logo 是否适合深色背景
  • 图表颜色是否仍然可读
  • 阴影在深色背景下是否看得见
  • 代码高亮主题是否同步切换

图表还有一个细节：不要只换背景色，坐标轴、网格线、tooltip、legend、数据色板都要一起换。尤其是数据可视化页面，深色模式下图表对比度不够，会直接影响读数，而不是单纯“不好看”。

可访问性和对比度

主题切换不是只看“好不好看”，还要看文字对比度是否足够。

深色模式里常见问题是正文灰度太低，长时间阅读很吃力；浅色模式里则可能是浅灰文字过淡。设计 token 时要把主文本、次文本、禁用文本分清楚。

不要只通过颜色表达状态。错误、成功、警告最好同时有文字、图标或明确上下文，避免用户只能靠颜色判断。

判断对比度别只靠肉眼，用浏览器 DevTools 的对比度检查或在线工具量一下，正文至少要到 WCAG AA 的 4.5:1。深色模式下我踩过的典型反例是“纯黑底配纯白字”，对比度拉满反而刺眼、发虚，主流做法是底色用接近 #121212 的深灰、正文用略带灰的白，眼睛舒服很多。

切换动画别想当然加

很多人喜欢给切换加个过渡，在根节点写 * { transition: background-color .3s; }。我劝你别这么干。给所有元素加全局过渡，首屏加载和路由切换时所有颜色都会“渐变进场”，看着像页面没加载好；而且元素一多，这个过渡的性能开销很可观。

小结

主题切换的关键是提前抽象颜色变量，而不是到处写固定色值。

简单项目可以用 class + CSS 变量 实现。复杂项目还要结合组件库主题能力，让业务样式和组件库样式保持一致。

我现在做主题系统，会先设计语义 token，再处理主题 class、持久化、系统偏好和首屏防闪。切换按钮只是最后一步，真正的工作是让颜色、组件、图表和状态都能被同一套主题规则驱动。
