CSS transition 入门：实现简单的滑入滑出效果

2018-12-20
前端基础CSS

CSS transition 是最常用的动画能力之一。

它适合处理简单状态变化，比如 hover、展开收起、透明度变化、滑入滑出。

理解它的关键是：先有状态变化，再有过渡动画。

也就是说，transition 本身不会创造状态。它只负责把一个已经发生的样式变化，变得更平滑。

这句话我刚学的时候没当回事，结果吃了不少苦头。最常见的就是：元素一插入页面就想让它淡入，直接给初始 opacity 写 0、加个 transition，再用 JS 把它改成 1，结果发现根本不过渡，啪一下就出来了。原因是浏览器还没来得及把“opacity 为 0”渲染成一帧，就被同一帧里改成 1，它看到的只有最终值，没有起点可言。后来才懂，要么先把元素挂上去、强制读一次 offsetHeight 触发一次布局（俗称强制重排），再改 class；要么用 requestAnimationFrame 把改 class 推到下一帧。状态的“前一帧”必须真实存在过，transition 才有的可过渡。

transition 做了什么

如果一个元素的样式从 A 变成 B，默认会瞬间完成。

加上 transition 后，浏览器会在 A 和 B 之间生成平滑过渡。

当 .box 增加 active 类时，就会向右平滑移动。

这里的两个状态很明确：

  • 默认状态：transform: none
  • 激活状态：transform: translateX(100px)

如果没有这两个稳定状态，动画就会变成“调参数”。写过渡前先把状态想清楚，后面会省很多事。

我的习惯是先把默认态和激活态的样式都写死、确认两个静止画面都对，再加 transition。很多时候动画“怪”不是 transition 写错了，而是两个端点本身就没对——比如激活态忘了归零 transform，或者默认态压根没设初始值。把动画拆成“两张静止图 + 一段过渡”来想，调试会清醒很多。

优先使用 transform 和 opacity

并不是所有 CSS 属性都适合做动画。

通常更推荐过渡：

  • transform
  • opacity

它们更容易被浏览器优化。

像 width、height、top、left 这类属性可能触发布局计算，复杂页面里要谨慎使用。

例如滑入面板不要用 right 从 -280px 变成 0，更推荐用 transform：

前者更容易影响布局计算，后者更容易走合成层，动画也更稳。

为什么差这么多？因为 transform 和 opacity 这两个属性，浏览器可以完全交给 GPU 在合成阶段处理，不需要重新算布局（layout）、也不用重绘（paint），每一帧都很便宜。而 left、width、top 这些会触发 layout，整棵子树都得重新计算位置，列表一长动画就掉帧。我在低端安卓机上测过同一个抽屉效果，用 right 过渡明显一卡一卡，换成 transform 立马顺滑，差距非常直观。

如果想给浏览器一点提示，可以加 will-change: transform，让它提前把元素提升到独立合成层。但这东西别乱撒——每个 will-change 都占显存，整页到处写反而拖慢。我一般只在确实要动、而且动的瞬间才加，动完了去掉。

尊重用户的动画偏好

有些用户会在系统里开启“减少动态效果”。页面动画应该尊重这个设置：

动画是体验增强，不应该成为用户完成操作的障碍。前庭功能敏感的用户看到大幅度的滑动、缩放会眩晕甚至不适，系统里那个“减少动态效果”就是为他们准备的。我现在写组件库会默认带上这段媒体查询，几乎不花什么成本，却是基本的体面。

要注意的是别简单粗暴地把 transition: none 写完就完事——如果你的关闭逻辑依赖 transitionend 来做收尾，禁用过渡后这个事件可能压根不触发，导致面板关不掉。这种情况下，要么把动画时长改成接近 0（比如 0.01ms）保证事件还会发，要么在 JS 里判断 prefers-reduced-motion 走另一条同步关闭的分支。我吃过这个亏，禁用动画后弹窗反而卡死打不开，排查了好一会儿才定位到是 transitionend 没来。

过渡动画适合把明确的状态变化变得更顺滑。实现时先想清楚两端状态，优先用 transform/opacity，并处理遮罩、焦点和“减少动画”的无障碍设置。写动画不是为了炫技，而是为了提升体验——把这些细节照顾到，动画才既好看又靠谱。
