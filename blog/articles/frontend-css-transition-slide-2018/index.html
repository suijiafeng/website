CSS transition 实现抽屉滑入滑出：把几个真正会卡人的坑说清楚

2018-12-20
前端基础CSS

设计师阿箐甩给我一张标注得极其认真的设计稿：页面右侧一个抽屉面板，点按钮从屏幕外滑进来，背后遮罩同步淡入；抽屉里还有一组手风琴式的分类，点标题展开收起。动效标注写着"滑入 300ms，要顺滑、有呼吸感"。

我看了一眼，心想这不就是 transition 的基础用法吗，回她"下午给你看效果"。结果这个"下午"变成了三天——transition 这东西看着简单，真正做起来坑一个没落全踩了一遍。下面按遇到的先后顺序记下来。

动手前先把 transition 的本分说清楚，因为后面每个坑都和这句话有关：**先有状态变化，再有过渡动画。transition 本身不会创造状态，它只负责把一个已经发生的样式变化变得更平滑。**如果一个元素的样式从 A 变成 B，默认瞬间完成；加上 transition，浏览器就在 A 和 B 之间生成平滑过渡：

.box 加上 active 类时，就会向右平滑移动。两个状态很明确：默认态 transform: none，激活态 transform: translateX(100px)。如果没有这两个稳定状态，动画就会变成"调参数"。

我这三天养成的第一个习惯就从这来：**先把默认态和激活态的样式都写死、确认两个静止画面都对，再加 transition。**很多时候动画"怪"不是 transition 写错了，而是两个端点本身就没对——激活态忘了归零 transform，或者默认态压根没设初始值。把动画拆成"两张静止图 + 一段过渡"来想，调试会清醒很多。

阿箐标注里那句"有呼吸感"，落到代码上其实就是速度曲线。ease 是默认值，开头快、结尾慢，大部分场景够用；但抽屉滑入这种，我更喜欢 ease-out——进场快、收尾缓，感觉更跟手。我拿几条曲线做了个对比页给她看，她最后选中的是 cubic-bezier(0.4, 0, 0.2, 1)，进出都比较自然，我打算以后就用它当默认。linear 只留给加载条这种匀速的东西，用在位移上会显得机械、廉价。动效的"高级感"大半藏在曲线里，时长反而其次。

这天上午还顺手立了条规矩：不写 transition: all 0.3s ease;。它看起来省事，但后续任何属性变化都可能被意外动画化。我们项目里真出过：某个卡片写了 transition: all，某天加了个 :hover 改 background-color，连带着旁边 JS 动态改的 width 也跟着慢悠悠地动，页面看着像卡了；更隐蔽的是 hover 时连 box-shadow、color 全在过渡，性能白白浪费。明确写出要过渡哪几个属性，是对未来的自己负责。

这里特意没有用 top/right/bottom/left 的合并简写 inset——那个属性眼下还只是草案里的东西，主流浏览器基本都不认，写了也是白写，老老实实四个方向分开写最稳。

注意那两行 pointer-events，它们是拿一个线上 bug 换来的。我们组之前出过：弹窗关掉之后，遮罩 opacity 是 0 了、看不见了，但 DOM 还在、还是铺满全屏的，用户点页面任何地方都没反应，以为页面死了。opacity: 0 只是看不见，不是不存在，加上 pointer-events: none 让透明遮罩不拦截事件，问题才算断根。

这里还有个细节：pointer-events 不参与过渡（它没有中间态），遮罩淡出时立刻变 none 没问题，但淡入时最好让它在动画一开始就能点。我的做法是把 pointer-events 和 .show 类绑在一起切，不单独动它。

第三天上午：为什么老安卓机上一卡一卡

功能齐了，我拿测试机架上那台低端安卓机过了一遍，抽屉滑动明显掉帧。这才想起我最早随手写的第一版抽屉，用的是 right 从 -280px 过渡到 0：

并不是所有 CSS 属性都适合做动画，通常只推荐过渡 transform 和 opacity。差别在渲染管线上：这两个属性浏览器可以完全交给 GPU 在合成阶段处理，不需要重新算布局（layout）、也不用重绘（paint），每一帧都很便宜；而 left、right、width、height、top 这些会触发 layout，整棵子树都得重新计算位置，页面一复杂动画就掉帧。我在那台安卓机上把两个版本来回切着看，right 过渡一卡一卡，transform 立马顺滑，差距非常直观。

如果内容高度可控，偷懒的招是用 max-height：

但这招有副作用：动画时长是按 max-height 的变化量算的，如果给了一个远大于真实高度的值（内容只有 100px 你写了 1000px），收起时前面 900px 是"空跑"，动画看起来先停顿一下再动，体感很怪——我第一版给了个保险的 9999px，被阿箐一眼看出"收起怎么先愣一下"。所以 max-height 尽量贴着内容的最大可能高度给。

收尾：动画也要给人留退路

提测前我加了最后一块：有些用户会在系统里开启"减少动态效果"，页面动画应该尊重这个设置。前庭功能敏感的用户看到大幅度的滑动、缩放会眩晕甚至不适，系统里那个开关就是为他们准备的：

几乎不花什么成本，却是基本的体面。动画是体验增强，不应该成为用户完成操作的障碍。

但这里有个我吃过亏的连环坑：别简单粗暴写完 transition: none 就完事——如果关闭逻辑依赖 transitionend 做收尾（比如上面的手风琴还原 auto），禁用过渡后这个事件可能压根不触发，收尾逻辑永远等不来。我上次就是禁用动画后弹窗反而卡死打不开，排查了好一会儿才定位到是 transitionend 没来。出路两条：要么把时长改成接近 0（比如 0.01ms）保证事件还会发，要么在 JS 里判断 prefers-reduced-motion 走一条同步关闭的分支。

周五下午给阿箐验收，她拖着时间轴逐帧看完，说了句"呼吸感有了"。这套抽屉加遮罩加手风琴的组合动效最后跑起来很顺滑，但用到的技术点其实还是最初那句话：先有状态变化，再有过渡动画，transition 只负责让已经发生的变化变得平滑。首帧要真实存在过，插入即动画的场景记得强制重排或推后一帧；位移动画用 transform/opacity，别碰触发布局的属性；height: auto 过渡不了，要么 max-height 贴着给，要么 JS 量高度；透明不等于不存在，遮罩记得配 pointer-events；关闭逻辑依赖 transitionend 收尾的，要留意 prefers-reduced-motion 会让这个事件失效。

这次没提到的一点也顺手记一下：transition 和 animation 该怎么选。这次抽屉和遮罩用 transition 是因为它们只有两个状态、由用户操作直接触发，天然适合"状态驱动"这条路；但如果是页面加载时自动播放的、或者需要循环、需要多个关键帧的效果（比如一个加载中的呼吸灯图标、一个提示气泡的持续晃动），transition 就不趁手了，得用 @keyframes 配 animation，它能定义多帧、能设置循环次数、能在不依赖状态切换的情况下自动播放。两者不是谁比谁高级，是分工不同：transition 管"从一个状态到另一个状态"，animation 管"一段独立于状态、自己有生命周期的动作"。这条判断标准我也记进了本子，和前面那几条坑放在一起。
