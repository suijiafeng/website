Node BFF 从聚合层到正经服务：缓存、熔断与治理红线

2024-08-30
构建与模块化组件与状态

在写任何一行 BFF 代码之前，先把账算清楚：加一层 BFF，意味着多一个需要部署、监控、值班的服务，多一个可能在半夜挂掉的故障面，多一段前端团队要自己背的运维责任。

链路从"浏览器、网关、后端"三段变成四段，每个请求多一跳的延迟，每次全链路排查多一个嫌疑环节，每次发布多一个要协调的部署单元。这些成本不会因为"我们只是写写聚合逻辑"就打折，它们是这个架构与生俱来的。

我把这段话写在文章开头，是因为它也写在我们 BFF 项目立项文档的第一页。今年上半年移动端项目立项，前端这边评估之后还是决定上 BFF，但整个团队是先认了这笔账再动手的。

四年前我用 Express 给团队搭过一个 mock 中间层，那是联调工具——挡在前后端之间造假数据，挂了顶多影响开发进度。这次这个是生产服务，挂了影响的是线上用户。两者之间隔着的东西，就是这篇要写的全部内容。

这笔账为什么还是划算

先交代动机，一段说完。

导火索是移动端的订单列表页：它调的是和 PC 中后台同一个订单接口，一条订单返回四十多个字段——PC 端的表格确实要展示那么多列——而移动端列表实际用到的是七个。弱网环境下这个接口的响应体积成了首屏瓶颈。让后端为移动端单独开一套裁剪版接口？排期排到了两个月后，后端的资源永远优先保交易链路，这不是抱怨，是可以理解的现实。类似的事今年已经攒了四五件：移动端要聚合三个接口才能画一个页面、要把后端的枚举码翻译成文案、要不同的分页粒度。

BFF 的核心价值就在这里：把"接口形状适配端"这件事的主导权，拿到离端最近的团队手里。适配需求当天提当天改，不占后端排期。这是收益端；成本端就是开头那段话。两边都摆上桌，团队和后端负责人一起拍的板。

技术选型：Fastify、undici 和 Node 20

选型没有太多戏剧性，一一交代理由。

运行时用 Node 20——LTS，运维的基础镜像现成。Node 22 四月发布了，内置 WebSocket、实验性的类型剥离这些都挺诱人，但它要十月才转 LTS，生产服务不上非 LTS 版本，这条没什么可讨论的。

框架在 Express 和 Fastify 之间选了 Fastify。不是因为跑分——虽然它的 JSON 序列化确实快——而是因为 schema 体系：每个路由的入参和响应都声明 JSON Schema，校验和序列化都基于 schema 做。这正好和我们五月份推的接口契约那套思路接上（契约的事写过一篇，不展开），BFF 对端上暴露的每个接口天然带一份机器可读的定义，端上的 TypeScript 类型直接从 schema 生成。

对后端的 HTTP 调用用 undici，Node 官方维护的 HTTP 客户端。选它的直接理由是连接池和超时控制的粒度：

headersTimeout 和 bodyTimeout 分开设，这个设计很实在——后端服务"迟迟不响应"和"响应了但传得很慢"是两种病，兜底策略不一样。每个下游服务一个独立的 Pool，连接数和超时各自配置，某个服务出问题时，连接池的物理隔离能挡住第一波扩散：订单服务的连接堆满，不影响 BFF 继续调营销服务。

两个细节展开说。

第一是营销角标那个 .catch(() => null)。聚合接口里的每个下游都要先分主次：次要数据源失败必须降级成缺省值，而不是把整个响应拖挂。营销服务出问题，用户看不到角标可以接受；因为角标接口挂了导致用户看不到订单列表，不可以。主次的判断要在写代码的当下做，不能等出了事故再补——补的时候你已经不记得哪个 Promise 是谁了。

第二是响应 schema 在这里兼职做了裁剪的最后一道闸。mobileOrderListSchema 里设了 additionalProperties: false，就算聚合代码哪天手滑把下游的完整对象直接透传出去，Fastify 序列化时也会按 schema 把多余字段削掉，不会把内部字段泄漏到端上。裁剪逻辑靠人自觉，裁剪兜底靠 schema，两道防线。

效果顺带一说：列表接口的响应体积从 61KB 降到 9KB，弱网下首屏的改善肉眼可见，移动端同事验收时的表情比任何压测报告都直观。

鉴权：透传，别自立门户

鉴权是 BFF 最容易越权的地方——这里的越权是架构意义上的。原则定得很死：BFF 不持有任何鉴权的真理，它只做验证和透传；用户身份的签发、刷新、注销，永远在后端的认证服务。

实现是一个 Fastify 的 preHandler 钩子：

往下游转发时，Authorization 头原样透传，下游服务该做的权限校验一点都不能少。BFF 这层验证的意义只是提前拦截明显无效的请求、并且解出 userId 给聚合逻辑用，它不能成为下游放弃校验的理由——否则 BFF 就成了整个安全体系的单点，它一旦有洞，后面全裸。

诱惑是真实存在的。开发中间就有过"要不要在 BFF 里给这个接口加个角色白名单"的讨论，被否了。权限规则一旦在 BFF 里长出第一条，就会长出第二条，三个月后没人说得清一个用户能不能访问某个资源到底由哪一层决定。

顺带在这一层挂了个粗粒度的限流（@fastify/rate-limit，按用户维度），定位不是安全防线——那是网关的活——而是自我保护：移动端某个页面写出死循环调接口的 bug 时，别让一个端的故障把 BFF 打穿、连累其他端。上线一个月真拦下过一次，触发原因是端上一个下拉刷新的重试逻辑写猛了。

缓存：内存 LRU 和 Redis 的边界

BFF 天然是加缓存的好位置，但"加在进程内存还是加在 Redis"这条边界值得写清楚，因为我们一开始就画错过。

判断标准最后收敛成两条。

第一条看一致性要求。进程内存缓存在多实例部署下必然不一致——我们跑三个副本，每个副本各揣一份缓存，写入时间不同、失效时间也不同步。所以只有"短时间内轻微不一致完全无害"的数据，才允许进进程内存。

第二条看容量和访问结构。进程内缓存吃的是容器的内存配额，放不下大集合；它的优势是零网络开销，适合小而热、每个请求都要摸一把的数据。

按这两条切下来的结果：状态码文案表、类目树这种全局配置，进程内 LRU，TTL 五分钟——三个副本的类目树最多差五分钟，无人受害。用的就是 lru-cache：

token 验证结果放 Redis，TTL 三十秒——它量大（每个请求都要验）、又要求跨实例一致失效：用户登出后，三个副本必须同时不再认这个 token，进程内缓存做不到这一点。

用户维度的订单数据，不缓存。一致性要求高、单 key 命中率又低，缓存它属于给自己埋雷。

画错的那次就发生在 token 上：最早图省事把验证结果放了进程内存，测试环境两个副本，QA 报了个"登出之后多刷新几次还能看到数据"的 bug——负载均衡把请求打到了另一个还揣着旧缓存的副本上。这个 bug 在测试环境出现是便宜的，长了记性。

超时、熔断、降级：中间层的生存技能

BFF 位置的凶险在于它的下游是一堆服务，任何一个变慢，都在消耗 BFF 自己的资源。Node 单进程事件循环的模型下，大量挂起的下游请求会堆积连接和内存，下游的慢病传导到 BFF 就是猝死，所以超时是每个下游调用的强制项，没有商量余地。undici 的两个 timeout 是第一道，路由级还有一道总超时兜着——单个下游都没超时、但串起来超了预算的情况也要兜。

超时之上是熔断。八月初压测模拟过物流服务整体变慢的场景：没有熔断时，BFF 的每个请求都要傻等物流接口 3 秒超时才走降级，吞吐直接掉了一个台阶；事件循环延迟也开始爬坡。加了熔断之后，连续失败超过阈值就把这个下游标记为打开状态，后续请求不再真的发出去、直接返回降级值，等冷却期过了进入半开、放少量探测请求试探恢复。

降级的兜底值要在写聚合逻辑的当下就设计好：物流信息降级显示"物流信息更新中"，营销角标降级为不显示，库存状态降级为"以下单页为准"。每一个降级文案都要拿给产品确认，"技术上优雅地降级成一个用户看不懂的空白"不算降级，算事故的另一种形态。这三个文案是和产品坐在一起过的，五分钟的会，省掉未来某次事故追查里"为什么用户看到一片空白"的半小时。

测试：下游不在场的情况下怎么保证自己是对的

BFF 的测试有个结构性难题：它的逻辑几乎全是"调下游、拼数据"，单元测试如果把下游全 mock 掉，剩下能测的东西很薄；集成测试如果依赖真实下游，联调环境的下游三天两头不稳定，CI 会红得毫无信息量。

我们的分层是这样的。纯函数部分——字段映射、buildSkuSummary 这类裁剪逻辑、熔断器状态机——正常单测，这部分覆盖率要求拉满，因为它们是 BFF 里唯一"自己的"逻辑。聚合路由的测试用 Fastify 的 inject 加 undici 的 MockAgent，不起真实服务、不出网络，把下游的响应按契约造出来：

重点测的不是"正常返回长什么样"，而是异常分支：营销接口 500 时角标是不是安静地变成 null、订单接口超时时熔断有没有按预期打开、下游多返回字段时 schema 有没有削掉。BFF 的质量不体现在晴天，全部体现在下游下雨的时候，测试用例的分布要和这个认知一致。

mock 数据的形状则锚在契约上——下游接口的 JSON Schema 从后端的接口平台导出，fixture 用 schema 校验过再进仓库，避免"mock 和真实接口早就长得不一样了，测试全绿、上线就炸"的经典结局。这也是四年前那个 Express mock 层留下的最大教训：mock 一旦和真实接口脱钩，它提供的所有信心都是假的。

部署与健康检查：这层楼自己扫

部署走公司现成的容器平台。Dockerfile 本身平平无奇，两个细节交代一下：基础镜像用 node:20-slim 而不是 alpine——undici 和一些原生依赖在 musl 下偶有幺蛾子，slim 的体积代价换个省心；进程直接跑 node，不套 pm2，副本数和重启策略是容器平台的职责，容器里再养一个进程管理器属于叠床架屋。

值得多说两句的是健康检查和退出行为。

平台的存活探针定期打 /healthz，这个接口怎么写有讲究：不能只返回 200 表示"进程活着"，也不能激进到把所有下游都探一遍——下游挂了不代表 BFF 该被重启，重启救不了下游，反而把正在生效的降级能力一起杀了。我们的 /healthz 只检查进程自身：事件循环延迟是否失控、Redis 连接是否存活。下游的健康度是监控大盘上的指标，不是存活探针的条件。

优雅退出也要自己管：收到 SIGTERM 先从注册中心摘流量，等在途请求处理完（设 10 秒上限）再退进程，否则每次发布都是一小波 502。Fastify 的 close() 会等在途请求，把它挂到信号处理里就行。

日志用 pino（Fastify 内置），生产环境 level 定在 info，请求级别的调试信息压到 debug、默认不出——BFF 的 QPS 乘上每请求十几条日志，磁盘和采集链路都遭不住。每条请求日志带上从网关透传下来的 traceId，BFF 对下游的每次调用记录目标服务、耗时、状态码。上线一个月，两次排查——一次营销接口偶发 500、一次物流超时率抬升——都是靠 BFF 的日志先圈定下游的，这层楼的可观测性算是立住了。

值班的账也兑现了：BFF 进了前端组的值班表，轮到的人要能看懂它的监控大盘、能执行回滚。这是立项时认下的成本，现在是每周的现实。第一次轮到我值周的那个凌晨没有任何告警，但手机放在枕头边充电的感觉，和只写页面的时候确实不一样。

红线：别长成第二个后端

最后写这条，因为它是 BFF 项目里唯一一个技术之外、却决定这个服务两年后是资产还是包袱的问题。

BFF 的堕落路径非常经典：先是聚合裁剪，然后"顺手"加一点业务规则，然后有人觉得在 BFF 里连个数据库"比推动后端加接口快"，两年后它变成一个由前端团队维护的、没有 DBA 支持、没有领域建模、没有完整测试的第二后端，谁都不敢动，也谁都甩不掉。

我们在立项文档里写死了三条红线。BFF 不直连数据库——所有数据必须来自下游服务的接口。BFF 不落业务状态——Redis 里只允许存缓存和幂等键这类可以随时清空重建的数据，清空 Redis 之后 BFF 必须还能正确工作，只是慢一点。BFF 不写业务规则——"这个字段在什么条件下显示什么文案"是展示逻辑，可以写；"满多少减多少"是业务规则，必须回后端。

评审时拿这三条卡口，已经卡过一次真实的越线：有个需求想在 BFF 里算优惠金额的展示值，理由是"就一个乘法"。被打回去推动后端出了接口——今天是一个乘法，下个月就是叠加规则，优惠算错一分钱都是资损。

判断一段逻辑该不该进 BFF，就问一个问题：这段逻辑出了 bug，是"某个端的展示不对"还是"业务错了"——前者是 BFF 的职责，后者一行都不能碰。

回到开头那笔账。上线一个月：移动端列表接口体积降了六倍；三次端上的接口形状调整都在 BFF 里当天解决，没有走后端排期；代价是前端组多了一个要值班的服务、一套要维护的监控，和三条必须一直守住的红线。账面上这层楼目前是赚的——前提是红线守得住，这也是每次接口评审都要重新交一遍的作业。
