JavaScript 闭包和作用域：问得多，项目里也经常踩坑

2018-01-17
JavaScript前端基础

闭包是前端面试里绕不开的问题。

刚开始听到这个词时，很容易觉得它像一个专门用来考人的概念。可写项目久了会发现，闭包并不只存在于面试题里。事件回调、定时器、模块封装、私有变量、异步请求，很多地方都在用它。

只是我们平时不一定会把它叫作闭包。

我自己就是这么过来的。面试被问闭包，背得滚瓜烂熟，什么“函数加上其引用的词法环境”，可真到项目里写 setTimeout 里引用外层变量、给每个列表项绑事件、用立即执行函数把工具方法包起来——这些天天在写的东西，当时根本没意识到就是闭包。后来踩了几次坑、又面了几次试，才把“课本定义”和“手上的代码”对上号。所以这篇我想尽量从实际写代码的角度来讲，而不是背概念。

先从作用域说起

JavaScript 里函数会创建自己的作用域：

注意是“定义时”，不是“调用时”。

这类题在面试里很常见，目的不是为难人，而是确认你知道 JavaScript 作用域不是动态绑定的。

这里有个特别容易混淆的地方，我专门拎出来说：作用域是“定义时”决定的（词法/静态作用域），但 this 是“调用时”决定的，这俩是两套完全不同的规则。新人最容易在这栽跟头——把变量查找的规律套到 this 上，或者反过来。比如：

什么是闭包

如果一个函数离开了它定义时的作用域，仍然能访问那个作用域里的变量，就形成了闭包。

createCounter 执行完了，但 count 没有被释放，因为返回的函数还在引用它。

这就是闭包最常见的用法：保留一份外部访问不到、但内部函数可以继续使用的状态。

我特别喜欢用闭包做防抖和节流，这是项目里最实在的用法之一。比如搜索框输入联想，不能每敲一个字就发请求：

这里的 timer 就是靠闭包保存下来的。每次返回的那个函数都还引用着同一个 timer，所以它能记住上一次的定时器并清掉。如果没有闭包，timer 要么写成全局变量（多个防抖互相打架），要么每次调用都重置（根本起不到防抖效果）。我早期不懂这个，真就把 timer 提到外面当全局变量，结果页面上两个搜索框一起用的时候互相干扰，查了好久才明白问题出在共享了同一个 timer。闭包在这里的价值就是给每个防抖函数一份独立、私密的状态。

私有变量

在没有 class 私有字段的写法里，闭包经常用来模拟私有变量：

外部不能直接改 score，只能通过方法访问。

这种写法在一些组件库、工具模块里很常见。它比全局变量安全，也让状态边界更清楚。

需要说清楚的是，闭包提供的“私有”是逻辑上的封装，不是安全意义上的加密。score 外部确实拿不到引用，但它存在于内存里，懂行的人通过调试器照样能看到。所以别指望用闭包藏什么敏感数据，它的价值在于约束“正常使用的边界”，避免别人无意中改坏你的内部状态，而不是防黑客。这点我以前没想清楚，还真有同事问过“闭包里的变量是不是就安全了”，得分清楚封装和加密是两回事。

另外提一个 2018 年的现实：ES2015 的 class 虽然有了，但真正的私有字段（#field 语法）还远没普及，浏览器支持也不齐。所以这种闭包模拟私有变量的写法，在当时仍然是工程里最靠谱的选择，而不是“过时写法”。

let 会为每次循环创建新的块级作用域。

let 这里的行为其实挺有意思，它不只是“块级作用域”这么一句话能概括的。在 for (let i ...) 里，规范规定每一轮迭代都会拷贝出一个新的 i 绑定，下一轮的 i 是在上一轮的值基础上重新创建的。所以三个 setTimeout 回调闭包捕获到的，是三个不同的 i，分别是 0、1、2。这也是为什么换成 let 就“神奇地”对了——本质上它帮你做了立即执行函数手动做的那件事：每轮一个独立作用域。

面试时如果能讲到“每次迭代新建绑定”这个层面，而不只是说一句“let 是块级的”，区分度会很明显。我面过不少人，知道答案是 0 1 2，但说不清为什么 let 能做到，往往就是只背了结论没理解机制。

事件回调里的闭包

闭包在事件处理中非常常见：

点击按钮时，回调还能拿到当初传入的 id。这就是闭包。

如果列表很长，并且每一项都绑定独立回调，要注意内存和解绑。页面销毁时，事件引用还在，可能导致 DOM 或数据无法释放。

这也是为什么事件委托很重要。不是所有按钮都需要单独绑定。

事件委托的思路是把监听挂到父容器上，利用事件冒泡统一处理，需要的数据从 DOM 上读，而不是为每一项闭包捕获一份：

这样不管列表有十项还是一万项，都只有一个监听函数，没有成百上千个各自捕获 id 的闭包，内存友好得多，列表动态增删也不用反复绑定解绑。我维护过一个长列表表格，原来给每行每个操作按钮都单独 onclick 绑了闭包，滚动加载几千行之后页面内存蹭蹭涨，改成事件委托后立竿见影。

如果确实有场景必须逐个绑定，那一定要记得在元素移除或组件销毁时 removeEventListener 解绑。闭包会牢牢拽住它引用的东西，只要监听还挂在那、回调闭包没释放，它捕获的变量、甚至关联的 DOM 节点都没法被垃圾回收，这就是很多“DOM 都删了内存还不降”的内存泄漏的来源。

模块封装

以前没有普遍使用 ES Module 时，闭包经常配合立即执行函数做模块：

这种写法现在看起来有点老，但在很多老项目里很常见。理解它，接手老代码会轻松很多。

项目里不要为了“高级”到处写闭包。它应该用在确实需要保存状态、隐藏变量、延迟执行的地方。我的经验是，闭包是顺其自然形成的工具，写防抖、写计数器、做模块封装时它该出现就出现；而不是一个值得专门去“用”的炫技对象。哪天你写代码时压根没意识到自己在用闭包，但用得恰到好处，那才算真懂了。

闭包这东西，真正写多了以后反而不会刻意去“使用”它。

事件回调、定时器、防抖、模块封装里，它经常是顺手出现的。需要留心的是另一面：函数把外层变量带走了，外层函数执行完不代表那些变量马上就能释放。循环变量错乱、大对象被意外留住、异步回调读到旧状态，这些问题都和它有关。能把“保存状态”和“留下引用”同时想到，闭包才算用得踏实。
