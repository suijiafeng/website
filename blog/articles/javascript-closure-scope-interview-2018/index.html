JavaScript 闭包和作用域：从定义到代码现场重新对齐

2018-01-17
JavaScript前端基础

闭包最容易制造一种错觉：定义背熟了，就以为自己懂了。"函数和它引用的词法环境的组合"这句话谁都能脱口而出，但真要说清楚"项目里哪里用到了闭包""为什么 for 循环里会踩坑""闭包为什么有时会带来内存问题"，脑子里冒出来的往往只是一些零散的写法和印象。

这周给组里新来的实习生讲闭包，我原本准备照着定义讲一遍就过去，结果他连着问了几个"为什么"，我才发现自己讲出来的全是背过的结论，没几句是能落回代码里的理解。真正让我不踏实的不是被问住，而是讲完一圈才意识到：自己天天都在写闭包，只是从来没把它当闭包理解过。

下面不从教科书定义讲起，顺着这几个问题，把闭包、作用域链、循环绑定、引用保留这些问题重新对到实际代码上。

第一问：项目里到底哪里用到了闭包

先问自己一个直白的问题：项目代码里，哪一段能理直气壮地说"这就是闭包"？

脑子里飞速翻一遍写过的代码，翻出来的全是 this.$http、v-for、写不完的表单，一时竟找不出一个现成的例子。但回头再翻一遍项目代码就会发现——闭包几乎无处不在，只是平时没有意识到。最典型的就是搜索框的防抖，这段代码我几乎每个项目都抄一遍：

我之所以对这点印象深刻，是因为踩过反面案例：更早的时候我不懂，把 timer 提到外面当全局变量。页面上只有一个搜索框时相安无事，后来加了第二个搜索框，两个框共用同一个 timer，互相清对方的定时器，联想结果时有时无。查了好久，最后发现是两个防抖在打架。

防抖有个孪生兄弟节流，同样是靠闭包记住状态，只是记的东西不一样——防抖记"定时器"，节流记"上次执行的时间"：

last 活在闭包里，每次滚动都拿它和当前时间比。两者的使用场景我是这么记的：防抖是"等你停"（搜索联想、窗口 resize 结束后再算布局），节流是"匀速跑"（滚动加载、拖拽跟随）。这两个函数的实现全靠闭包记状态，是团队 code review 里最常被拎出来讲的一对例子。

原生实现之外，还值得留意一下 lodash 的 debounce/throttle 比手写版本多做了什么。lodash 版本支持 leading/trailing 两个选项，可以控制"第一次触发要不要立即执行"和"最后一次触发要不要补一次执行"；还额外暴露了 cancel() 方法，用来在组件销毁时清掉挂起的定时器，避免组件卸载后回调还在悬空引用旧数据。手写的极简版只覆盖了最常见的"尾部执行"场景，真要接手一个成熟项目，直接上 lodash 更省心，但理解手写版本里 timer 靠闭包存活这件事，是看懂 lodash 源码的前提。

答案是 3、3、3。改成 let 就是 0、1、2。这题很多人刷过，闭着眼都能说出结果，但追一句"为什么 let 就行"，很多人会答"因为 let 是块级作用域"——这个答案经不起再追一层：块级作用域怎么就让三个回调拿到三个不同的值了？循环体不是同一块吗？

查规范才能讲透：for (let i ...) 里，每一轮迭代都会新建一个 i 的绑定，新一轮的 i 用上一轮的值初始化。所以三个 setTimeout 回调各自捕获的是三个不同的 i，值分别是 0、1、2。它本质上就是引擎帮你做了老写法里立即执行函数手动做的事：

每轮手动开一个新作用域，把当时的 i 拷贝进去。

同样输出 0、1、2。原理和 IIFE 一个意思：把值在当下拷贝一份交出去，而不是让回调将来去闭包里找那个早就变成 3 的 i。这个写法要注意 IE9 及以下不支持传参，兼容差的项目慎用，但作为跟 IIFE 并列的第三种解法，理解起来能帮着把"当下拷贝值"这个思路吃得更透。

顺着这道题还能反问一个问题：为什么 setTimeout(fn, 0) 也要等循环全部跑完才执行？这就牵出事件循环了——同步代码是主线程上的当前任务，定时器回调进的是任务队列，必须等当前任务执行完才有机会上场。闭包和事件循环这两块知识本来就是咬合的：闭包决定回调能拿到什么变量，事件循环决定回调什么时候执行。

知道答案是 0、1、2 的人很多，说得清"每轮迭代新建绑定"的人不多，区别就在这一层。

第三问：闭包会内存泄漏吗，怎么证明

"闭包会导致内存泄漏"这句话背下来很容易，但给一个内存一直涨的页面，从哪里查起，是完全不同的另一件事。

自己维护的一个后台项目里，真遇到过这个问题：一个长列表表格，滚动加载几千行后内存蹭蹭涨，页面越用越卡。借着这次机会把 Chrome DevTools 的 Memory 面板学了一遍——拍一张 heap snapshot，操作几下，再拍一张，对比着搜那些本该释放的对象还在不在。

最后定位到两个元凶，都和闭包有关。

第一个：每行的操作按钮都单独绑了 onclick，每个回调闭包捕获一份行数据。几千行就是几千个闭包，行删了监听还挂着，DOM 和数据都释放不掉。改成事件委托后立竿见影：

一万行也只有一个监听函数，数据从 DOM 上现读，没有闭包替每行拽着一份。

第二个更隐蔽：一个回调把整个大配置对象捕获进了闭包，而它只用其中一个字段。

修法是把需要的值提前取出来，让大对象能被回收：

改完那个字段，内存曲线立马平了。

闭包"保存状态"和"留下引用"是同一件事的两面，享受前者的时候，得记得后者的账单。这条经验后来还帮着抓到过第三个坑：一个轮询函数每次都在回调里 new 一个大对象做临时计算，回调本身又被外层的定时器句柄一直引用着，导致每一轮产生的临时对象迟迟不被回收，内存曲线呈锯齿形缓慢爬升。修法也简单，把不需要跨轮次保留的临时变量在回调末尾主动置为 null，或者干脆把大计算挪出闭包，用参数传进去而不是捕获进去。闭包本身不是内存泄漏的原因，忘记闭包正拽着什么东西才是。

答案是：这是两套完全独立的规则。

变量查找走词法作用域——看函数定义在哪，定义时外面有什么，闭包就能拿到什么，跟谁调用无关：

printName 定义在全局，它这辈子访问的就是全局的 name，哪怕它在 run 里被调用。

而 this 走的是调用规则——看函数怎么被调，obj.greet() 和 fn() 是两种调法，this 就是两个东西。

一句话记：作用域看定义，this 看调用。新人最容易把两套规则搅在一起，用变量查找的直觉去猜 this，或者反过来。给别人讲代码时如果先把这句话立住，后面遇到的绝大多数"this 为什么不对"都能顺着推下去。

闭包模拟私有变量

这几个问题背后还有一个常被漏掉的用法：闭包模拟私有变量——

class 的私有字段（#field 语法）眼下还只是个提案，哪家浏览器都没实现，所以闭包封装仍然是工程里最靠谱的私有化手段，一点都不过时。但要分清：这是逻辑上的封装，不是安全意义上的加密。score 就在内存里躺着，调试器照样看得见。它防的是同事无意改坏你的内部状态，不是防黑客。

把前面这几个问题背后的机制串成一条线：

函数被调用时，引擎会创建一个执行上下文，里面挂着这个函数自己的变量对象，以及一条作用域链——由它定义时所处的外层作用域一层层串起来。查找变量就是沿着这条链从内向外找，找到为止。所谓闭包，就是内层函数的作用域链上，串着一个已经执行完毕的外层函数的变量对象。

垃圾回收器的规则很朴素：一个对象只要还被引用着，就不回收。正常情况下函数执行完，它的变量对象没人引用了，很快被回收；但闭包让"返回的函数"攥着那条作用域链，链上的变量对象就一直活着。这一条链同时解释了前面几个问题——

  • 为什么防抖函数里的 timer 记得住上一次的定时器句柄：变量对象被链着，没死。
  • 为什么 var 循环全输出 3：三个回调的链指向同一个变量对象，里面只有一个 i。
  • 为什么闭包会"泄漏"：链上挂着大对象，回收器就动不了它。
  • 为什么作用域看定义：链是函数定义时就确定的，跟谁调用无关；this 不在这条链上，它是调用时才注入的另一套东西。

一条链讲清所有问题，比孤立地背几个结论痛快多了。

闭包不必刻意"使用"，写防抖的时候它在，绑事件的时候它在，包模块的时候它也在，是顺手出现的东西。哪天写代码时压根没意识到自己在用闭包，但用得恰到好处，那才算真懂了。

只是别忘了内存那一问：函数把外层变量带走的那一刻，也把释放它们的责任带走了。
