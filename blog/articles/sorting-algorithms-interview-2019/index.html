排序算法基础：冒泡、选择、插入和快排到底差在哪

2019-12-10
JavaScript

排序算法是面试里最经典的基础题之一。我前几年面试，十次里有七八次都被要求手写一个排序，最常见的就是「白板上写个快排」。那时候我背得滚瓜烂熟，能默写出来，但被追问一句「你这版为什么会退化、稳不稳定、原地不原地」就卡壳了。后来真在项目里踩过几次和排序相关的坑，才回过头明白：面试官要的从来不是那段代码本身，而是你对复杂度、数据规模、稳定性的体感。

业务里绝大多数排序直接用 Array.prototype.sort 就够了，几百上千条数据，V8 引擎那套高度优化的实现比我手写的任何东西都快。但理解几种基础排序，能帮你在「这数据量到底该不该排在前端」「为什么同样的列表换个浏览器顺序就变了」这类问题上有判断力。下面这几种我都按「思路 — 代码 — 什么时候用 — 坑」的方式过一遍，代码都是我当年准备面试时反复写顺手的版本。

先约定一个习惯：下面所有实现我都用 arr.slice() 拷一份再排，绝不原地改入参。这是我吃过亏才养成的——早期写了个原地排序的工具函数，调用方传进来的数组被我就地打乱了，导致它后面依赖原始顺序的逻辑全错，排查了一下午。纯函数式的排序，调用方永远不用担心副作用。

冒泡排序

冒泡排序每次比较相邻元素，把大的往后冒到末尾，跑完一轮最大值就「浮」到了最后。

时间复杂度通常是 O(n²)：外层 n 轮，内层每轮平均比较 n/2 次。它的好处只有一个——直观，谁都能看懂相邻交换这件事。

面试里这道题真正能拉开差距的是一个优化：如果某一轮一次交换都没发生，说明数组已经有序了，可以直接收工，没必要把剩下的轮次跑完。

加了这个 swapped 标志后，最好情况（数组本来就有序）的复杂度从 O(n²) 降到 O(n)，只扫一遍就退出。我当年面试被问「冒泡最好情况是多少」，就是靠这个细节答上来的——很多人下意识答 O(n²)，其实带优化的版本能到 O(n)。

冒泡是稳定排序：相等元素只在 > 时才交换，== 不动，相对顺序保得住。但说实话，工程里我从没真用过它，它的存在价值基本就是教学和面试。

选择排序最大的特点是交换次数少：不管数组什么样，最多只交换 n-1 次（每轮一次）。比较次数则雷打不动是 O(n²)，因为它每轮都要把剩下的全扫一遍找最小值，没法像冒泡那样提前退出——哪怕数组已经有序，它也得老老实实扫完。

这个「交换少」的性质在某些场景有意义：如果你的元素「比较很便宜、但移动/交换很贵」（比如每个元素是一大块数据，搬一次成本高），选择排序的少交换反而划算。但这种场景实际工程里很少，知道有这么个权衡就行。

还有个容易被忽略的点：选择排序是不稳定的。举个例子，[5a, 5b, 2]（用 a/b 区分两个相等的 5），第一轮会把 2 和第一个 5a 交换，变成 [2, 5b, 5a]，两个 5 的相对顺序被打乱了。面试问「哪些 O(n²) 排序不稳定」，选择排序就是标准答案。

插入排序

插入排序像整理扑克牌：左手里的牌已经排好序，每摸一张新牌，就从右往左找到它该插的位置塞进去。

数据基本有序时，插入排序表现非常好——内层 while 几乎一进去就退出，整体接近 O(n)。这不是纸面优势：很多语言和库的内置排序，在小数组或近乎有序的子段上会退化成插入排序，正是看中它在「小规模 + 近似有序」下常数小、又稳定的特性。V8 早期的 Array.sort 对短数组（长度小于等于 10）就直接用插入排序，大数组才上更复杂的算法。

插入排序也是稳定的：内层条件是 list[j] > current，严格大于才往后挪，相等时停下，所以相等元素不会被换到前面去。三种 O(n²) 排序里，冒泡和插入稳定、选择不稳定，这个我专门记过。

我自己写业务代码时，唯一真用过插入排序思路的场景是「往一个已经有序的小数组里插入一个新元素并保持有序」——比如维护一个排行榜的 Top 10，新成绩进来时找位置插进去，比整个重排划算。

快速排序

快排是这几种里唯一平均 O(n log n) 的，也是面试白板的常客。思路是分治：选一个基准（pivot），把比它小的甩左边、比它大的甩右边，然后对左右两半递归。

平均时间复杂度 O(n log n)，但基准选择不好时可能退化到 O(n²)。

这个版本好理解，但有两个明显问题，面试官多半会顺着追问：

第一，它会创建大量新数组。每层递归都 new 出 left、right 两个数组，再 concat 拼回去，空间开销和 GC 压力都很大，不是「原地」排序。真正生产级的快排是原地分区（in-place partition），只在原数组上交换，空间复杂度降到 O(log n)（递归栈）。下面是我后来练熟的原地版本，用经典的双指针 Lomuto 分区：

第二，固定取 arr[0]（或末位）做基准会退化。如果输入本来就有序（升序或降序），每次分区都只能分出一个空的一边和一个 n-1 的一边，递归深度退化成 n，复杂度从 O(n log n) 掉到 O(n²)，还可能爆栈。我真在一次处理「已经按时间排好序、只想再校验一遍顺序」的数据时撞上过这个——一段平时跑得飞快的快排，遇到有序输入突然慢到卡死。

还有一点：朴素快排不稳定。分区过程中的远距离交换会打乱相等元素的相对次序。需要稳定的 O(n log n)，得用归并排序——它稳定，但要额外 O(n) 空间。这也是 V8 后来把 Array.sort 的实现从快排换成 TimSort（归并的变体）的原因之一：ES2019 起规范要求 sort 必须稳定，快排满足不了。

这是项目里我见过最频繁的坑，没有之一。比较函数的约定是：返回负数表示 a 排前面，正数表示 b 排前面，0 表示不变。记住 a - b 是升序、b - a 是降序就行。

还有几个相关的坑我也栽过：

比较函数返回布尔值是错的。我见过有人写 (a, b) => a > b，返回 true/false，而 sort 期待的是数字。true 被当成 1、false 当成 0，永远不会返回负数，结果在不同引擎下行为不一致，排出来的顺序莫名其妙。一定要返回数字差。

大整数相减会溢出/精度问题。如果是时间戳这种大数，a - b 一般没事；但要排的是可能超出安全整数范围的值，稳妥写法是 (a, b) => a < b ? -1 : a > b ? 1 : 0。

稳定性

稳定排序指的是：两个比较起来相等的元素，排序后相对顺序保持不变。

举个我真实碰到的场景。后台有个表格，用户先点「按部门排序」，再点「按入职时间排序」，期望是「同一入职时间内还按部门保持着上次的顺序」。这种「多级排序」依赖的就是排序稳定性——如果底层排序不稳定，第二次排序会把第一次排好的同值次序打乱，用户就会觉得「排序乱跳」。

在 ES2019 之前，Array.sort 的稳定性是不保证的：V8 对长数组用快排，结果不稳定；当年同一份代码在 Chrome 和 Firefox 里排出来的相等元素顺序可能不同，我就被这个坑过——本地 Chrome 一切正常，测试同学的某个浏览器上顺序就是不对。ES2019 之后规范强制要求稳定，各大引擎也都换成了稳定算法，这个历史坑才算填上。但如果你还要兼容老环境，多字段排序最好自己保证稳定：把多个排序维度合并进一个比较函数，而不是排序好几次。

|| 这个写法很顺手：前一个维度比出胜负（非 0）就用它，否则落到下一个维度。

我对这张表的记忆方式不是死背，而是理解每一格背后的原因：选择排序最好情况也是 O(n²)，因为它每轮必须扫完才知道最小值；归并空间是 O(n)，因为合并要开辅助数组；快排不稳定，因为分区有远距离交换。能把「为什么」讲出来，比报数字管用得多。

小结

冒泡、选择、插入是 O(n²) 的基础三件套，理解它们主要是为了建立对复杂度和稳定性的直觉；快排和归并才是 O(n log n) 这一档，也是面试真正想考的分治与递归。

落到工程上，结论其实很朴素：业务里用内置 sort，记得传比较函数，知道它现在是稳定的。数据量大到内置排序都扛不住时，第一反应应该是「这排序是不是该挪到后端、挪到数据库的 ORDER BY」，而不是自己手写一个更快的排序——前端排几万条数据本身就是个信号，说明数据该分页或该在服务端处理了。

面试问排序，从来不只是要你默写代码，而是看你能不能把复杂度、稳定性、数据规模和适用场景串起来讲清楚。代码网上一搜一大把，这份判断力才是值钱的东西。
