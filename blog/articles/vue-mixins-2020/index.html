Vue Mixins 用久了为什么容易乱：复用逻辑不等于把代码拼在一起

2020-10-17
Vue组件与状态

Vue 里做逻辑复用时，Mixins 是很自然会接触到的一种方式。

刚开始用时它很顺手：提一段公共逻辑，多个组件混进来就能复用。可一旦项目做久，很多团队都会感受到同一个问题：Mixin 好写，但不太好管。

Mixin 最大的问题是“隐式”

组件引入一个 Mixin 后，表面上只是多了一行配置，实际上它可能带来：

  • data
  • methods
  • computed
  • 生命周期

这些能力会直接混进当前组件里。

功能上当然成立，但阅读代码的人很容易看不出来某个字段到底来自哪里。

一开始省事，后面成本会上来

Mixin 常常在项目前期特别讨喜，因为它能很快解决：

  • 表单通用逻辑
  • 列表加载逻辑
  • 权限判断逻辑

可随着 Mixin 越来越多，组件就开始出现两个典型问题：

  • 命名冲突
  • 来源不清

这时调试体验会明显变差。

命名冲突尤其隐蔽：

不同选项的合并策略不完全一样。生命周期会合并执行，方法同名可能被覆盖，数据也会合并。项目里 Mixin 多了以后，行为来源会越来越难判断。

把合并规则说细一点，因为冲突时全靠它：

  • 生命周期钩子：不会覆盖，会合并成数组依次执行，Mixin 的先跑，组件自己的后跑。所以一个组件可能有好几个 created 在排队跑，调试时打断点会反复进。
  • data：递归合并，键冲突时以组件自身的为准（上面例子里 page 最终是 10）。
  • methods / computed / components：合并成对象，键冲突时组件自身覆盖 Mixin。
  • watch：和钩子一样合并成数组都执行。

最坑的是「组件覆盖 Mixin」这条规则的隐蔽性。我遇到过：一个 Mixin 提供了 reset 方法做完整重置，某个组件里碰巧也写了个 reset 只重置一半，于是这个组件的重置「看着对、其实漏了」，而别的组件没事。排查时根本不会怀疑 Mixin，因为代码里压根看不到那行被覆盖的方法。最后是全局搜 reset 才发现撞名。多个 Mixin 之间同名方法的合并顺序按数组先后,后面的覆盖前面的,这又给「为什么是这个行为」加了一层迷雾。

复用逻辑不能只看“抽没抽出来”

真正稳定的复用，不只是把代码搬到另一个文件，而是要让依赖关系仍然清楚。

如果一个组件用了多个 Mixin，后面想知道：

  • 哪个方法是谁提供的
  • 哪个生命周期里做了什么
  • 为什么这个字段会突然存在

这些问题都会变得不那么直观。

所以判断一个 Mixin 是否合适，可以看几个问题：

  • 它暴露了哪些字段和方法
  • 是否依赖组件必须实现某些方法
  • 是否会改组件已有状态
  • 是否包含异步请求或副作用
  • 多个 Mixin 一起用时是否会冲突

如果这些问题需要靠口头约定才能说清楚，说明抽象已经不够透明。

把逻辑拆成普通函数

很多时候，普通函数比 Mixin 更清楚。

这样依赖关系很直观：请求函数来自哪里、返回什么结构、组件自己维护哪些状态，都能看见。

跟 Mixin 比，差别就在「显式」两个字。requestJson 是从一个明确的路径 import 进来的，鼠标点过去就能跳到定义；返回值结构 { ok, data, message } 写在那一目了然；组件自己的 list、errorMessage 也实打实声明在 data 里。这三件事 Mixin 全是隐式的——你得知道有这么个 Mixin、得去翻它内部、还得脑补合并后的结果。普通函数把这些都摆到了明面上。

代价是普通函数没法帮你管组件的状态（loading、list 这些响应式数据还得组件自己声明），也接不进生命周期。这恰恰是它的边界：纯逻辑、纯计算、纯请求，普通函数最合适；一旦涉及「要往组件实例上挂响应式状态」或「要挂生命周期」，普通函数就力不从心了，这也是为什么后面会聊到组件组合和组合式函数。

用组件组合替代一部分 Mixin

有些 Mixin 其实是在复用 UI 行为，比如加载、空状态、错误状态。它们更适合抽成组件。

StateView 负责展示状态，页面负责拿数据。这样比把 loading、errorMessage、fetchList 全部混进组件更清楚。

我以前真有过一个 listMixin，里面塞了 loading 状态、空状态判断、错误文案、重试按钮逻辑，混进十几个列表页。一开始爽，后来要改空状态的样式，得确认这十几个页面都能接受同一套改动，改完还得一个个验。后来把展示层抽成 StateView 组件，状态长什么样集中在一个组件里维护，改一处全生效，页面只管把 loading/error/list 当 props/slot 传进去。这就是「UI 复用用组件，逻辑复用用函数」的分工——Mixin 的问题恰恰是它把这两类东西糊在一起,既改不动状态展示，又看不清逻辑来源。

判断一段 Mixin 该往哪拆，我的简单标准是：它主要在复用「长什么样」就抽组件，主要在复用「怎么算、怎么请求」就抽函数。两样都占的，先拆成这两半再说。

Mixin 仍然可以用，但要小

Mixin 不是完全不能用。适合它的通常是短小、稳定、没有太多隐式依赖的逻辑。

比如统一页面标题、简单埋点、极少量生命周期增强，可以保留。但如果一个 Mixin 同时带来数据、请求、校验、权限、跳转，就应该拆开。

更务实的治理方式是：

  • 新逻辑少写 Mixin
  • 老 Mixin 不急着全量重构
  • 修改某个组件时顺手显式化依赖
  • 把通用请求和格式化先移到普通函数
  • 把 UI 状态抽成组件

不要为了“去 Mixin”做大范围重写，风险通常不值得。

Mixin 当然能用，但它更适合短期、简单、边界清楚的逻辑复用。

一旦项目越来越复杂，光“能复用”已经不够，来源和边界同样重要。代码复用如果把可读性搭进去，后面通常会还回来更多维护成本。

复用逻辑的目标不是少写几行，而是让变化更好管理。能用普通函数说清楚的，就不要先交给 Mixin 隐式合并。
