前端安全基线：日常项目先守住这些底线

2023-09-15
前端基础构建与模块化

前端安全不是只有大公司才需要。

后台系统、营销页、小程序 H5、个人 SaaS，只要处理用户数据、登录态、表单提交，就有安全边界。很多问题不需要高深攻击技巧，往往是一个未过滤的富文本、一个开放跳转、一个过期依赖。

我对安全基线的理解是：不追求一开始做到极致，但项目里不能踩明显的底线。

用户输入默认不可信

任何来自用户、URL、接口、第三方系统的数据，都不要直接当 HTML。

React 文本插值默认会转义：

这通常安全。

危险的是：

如果必须渲染富文本，要使用白名单清洗。不要自己写正则过滤 <script>，XSS 入口远不止 script 标签。

Markdown 也一样。允许内嵌 HTML 的 Markdown 渲染器，要么禁用 HTML，要么渲染后再清洗。

接口错误不要原样展示

后端返回的错误信息也可能包含不可信内容。

如果你只作为文本显示，问题不大；如果拼进 HTML，就有风险。

错误处理应该有安全兜底：

详细错误、堆栈、SQL 信息不要展示给用户。它们应该进日志系统。

Cookie 和 token 要按风险选择

把 token 存 localStorage 很方便，但 XSS 一旦发生，脚本可以直接读走。

高风险后台、资金、隐私数据场景，更建议使用 HttpOnly Cookie：

HttpOnly 能防止 JS 直接读取 Cookie，但不能让 XSS 完全失效。攻击脚本仍然可以在当前页面上下文里发请求。所以 XSS 防护仍然是第一位。

如果使用 Cookie 鉴权，要评估 CSRF。SameSite 能挡住不少场景，但复杂跨站业务可能还需要 CSRF token。

文件上传要前后端都校验

前端可以限制文件类型和大小：

但这只是体验优化，不是安全防线。文件类型、大小、内容、病毒扫描、存储权限都必须后端校验。

上传后的文件访问也要注意。用户上传的 HTML、SVG、PDF 都可能带脚本或钓鱼内容。不要随便把用户文件放在主站同域下直接打开，必要时使用独立域名和下载响应头。

依赖安全要持续看

前端依赖很多，漏洞也常见。

至少要做：

  • 锁定 lockfile
  • 定期跑依赖审计
  • 关注构建插件和脚手架依赖
  • 不随便安装没人维护的小包
  • 删除不用的依赖

依赖安全不只是运行时代码。构建时依赖也有风险，因为它们能在安装和构建阶段执行脚本。

引入新依赖前，要问：

  • 是否真的需要
  • 是否维护活跃
  • 是否有替代方案
  • 是否会进入客户端包
  • 是否处理敏感数据

我的安全基线清单

日常项目至少检查：

  • 用户输入是否默认按文本处理
  • 富文本和 Markdown 是否清洗
  • API 错误是否有安全兜底
  • token 存储方式是否符合风险等级
  • Cookie 是否设置 HttpOnly、Secure、SameSite
  • redirect 参数是否限制站内或白名单
  • 文件上传是否前后端都校验
  • 依赖是否定期审计
  • 是否有基本安全响应头

安全不是靠某一个库解决的。它更像一组底线：输入不可信、权限在后端、错误不泄露、依赖要克制、边界要明确。先守住这些，项目的风险就能降很多。
