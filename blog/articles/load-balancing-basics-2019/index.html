负载均衡基础：为什么线上服务不是只放一台机器

2019-11-09
杂项

我第一次真正意识到“负载均衡”这四个字的分量，是在一次大促前的压测。那时我们的接口测试环境只有一台机器，QPS 一上去就开始超时，运维淡淡地说了句“线上是四台，前面挂了 Nginx”。我当时还以为 Nginx 只是个静态文件服务器，后来排查了几次诡异的线上问题，才慢慢把这套东西摸明白。

线上服务几乎不会只跑在一台机器上。一台机器有它的天花板：CPU、内存、连接数、带宽，任何一项被打满，整个服务就开始抖。更要命的是单点故障——这台机器一重启、一 OOM、网卡一抽风，全站就挂了。所以正经的做法是放好几台一模一样的服务实例，前面摆一个入口，把进来的请求分发到后面去。这个分发请求的家伙，就是负载均衡。

作为前端，我们平时确实不直接去配负载均衡。但我后来发现，很多让人摸不着头脑的线上现象，根子都在这一层：接口十次里偶尔失败一两次、某个页面在一部分用户那里数据是旧的、某个同事电脑上死活登录态会掉、灰度发布时一半人看到新功能一半人看到老的。这些都不是浏览器的锅，而是请求被分到了不同的后端机器上。理解这一层，排查问题时心里会踏实很多。

它按照某种策略挑一台，把请求转过去，拿到响应再原路返回给用户。对用户来说，他自始至终只看到 api.example.com 这一个地址，根本感知不到后面有几台机器，也不知道这次是谁服务的。这种“对外一个口、对内一群机器”的结构，就是水平扩展的基础——扛不住了，加机器就行，理论上能一直加下去。

这里有个概念上的分层值得记一下。负载均衡大致分两类：四层（L4）和七层（L7）。四层工作在 TCP/UDP 层面，只看 IP 和端口，转发快、消耗低，但它不懂 HTTP，没法按 URL、按 Header 做路由，典型代表是 LVS、F5、云上的 NLB。七层工作在 HTTP 层面，能看到完整的请求，可以按路径分流、改请求头、做 SSL 卸载，Nginx 就是干这个的。我们前端打交道最多的就是七层，因为它直接和 URL、Header、Cookie 打交道，问题也大多出在这一层。

几种分发策略，以及我踩过的坑

负载均衡器怎么决定“这次请求给谁”，靠的就是调度策略。Nginx 自带这么几种。

实现简单、绝对公平，前提是几台机器配置差不多。我吃过的第一个亏就是机器不对等：有两台是新采购的高配，一台是临时拉来顶班的老机器，轮询照样三家平摊，结果老机器先被打趴下，整体表现被那台最弱的拖着走。

性能强的多分，老弱的少分。上面这个配置里，每 11 个请求大概有 5 个给 server-1、5 个给 server-2、1 个给 server-3。灰度发布也常用这招：新版本先给 1 的权重，观察没问题再慢慢加上去。

最少连接（least_conn） 不按次数轮，而是看谁手上当前未完成的连接最少就给谁：

这个策略特别适合请求耗时差异大的场景。我们有个导出报表的接口，有的请求几十毫秒就回来了，有的要跑十几秒。用轮询的话，某台机器可能连续接了好几个慢请求，连接全堵在那儿，新来的快请求还硬往里塞。换成 least_conn 之后，慢请求多的机器会自然少分一点，明显平顺了。

IP hash 按客户端 IP 算个哈希，让同一个 IP 尽量固定打到同一台机器：

它解决的是会话粘连问题（后面会专门说），但它有个我后来才意识到的坑：很多用户走的是同一个公司出口 IP 或者运营商 NAT，对负载均衡来说他们就是“一个 IP”，结果一大票人全被压到同一台机器上，流量根本不均。所以 ip_hash 我现在基本不用，宁可去把会话做成无状态。

策略没有银弹。机器对等、请求都很短，轮询就够了；机器不对等用加权；请求耗时方差大用最少连接；万不得已要粘连再考虑 ip_hash。

健康检查：那些“刷新几次时好时坏”的元凶

负载均衡最怕的事情，是它不知道后端已经挂了，还在傻乎乎地往一台死机器上转请求。用户的体感就是：刷新十次，七八次正常，两三次报错或者转圈，毫无规律。这种间歇性故障最折磨人，因为它不稳定复现，前端查半天发现自己代码没问题。

开源版 Nginx 的健康检查是“被动”的，靠的就是上面配的 max_fails 和 fail_timeout：当某台机器在 fail_timeout 时间内失败次数达到 max_fails，Nginx 就把它标记为不可用，暂时不往那儿发请求，过一会儿再试探性地放点流量看看活没活过来。这种方式的缺点是“事后诸葛亮”——总得先有几个真实请求倒霉撞上死机器、失败了，才能触发摘除。

更稳妥的是“主动”健康检查：负载均衡定期主动去探一个专门的接口，确认活着才给它发流量。这个能力在 Nginx Plus（商业版）里直接支持，开源版当年我们是用 Tengine 或者 nginx_upstream_check_module 来补的：

会话保持：登录态为什么会“随机”丢

这是我职业生涯里查得最久的一个“前端 bug”，最后发现完全不是前端的问题。现象是：测试同学说登录之后点几下就被踢回登录页，但不是每次都发生，换台电脑又好了。

根因是后端把登录态（session）存在了进程内存里。请求第一次落到 server-1，session 建在 server-1 的内存里；下一个请求被轮询分到了 server-2，server-2 内存里根本没有这个 session，于是它认为你没登录，返回 401。在多机环境下，只要会话状态是“本地的”，就一定会出这种问题。

解决思路有三条，优劣很清楚：

  • 会话粘连（ip_hash / sticky）：让同一个用户固定打到同一台机器。最省事，但前面说过 ip_hash 在 NAT 环境下会失衡；而且这台机器一旦重启，上面所有人的 session 全没了，照样掉登录。属于治标。
  • session 集中存储（Redis）：把 session 从进程内存挪到外部的 Redis，所有机器共享。无论请求落到哪台，都能读到同一份会话。这是当年最主流的做法，我们最后就是这么改的。
  • 无状态 Token（JWT）：干脆不在服务端存会话，登录态全塞进客户端持有的 token 里，每台机器自己验签就行，谁都不用存。扩展性最好，代价是 token 没法轻易主动失效，得配合短有效期或额外的吊销列表。

把 session 挪到 Redis 之后那个“随机掉登录”的问题当场消失。从那以后我形成一个判断习惯：前端碰到“时好时坏、和机器有关”的问题，先怀疑后端是不是有本地状态没共享，而不是埋头改自己的代码。

小结

负载均衡的本质，是把“对外的一个服务”和“对内的一群机器”解耦：对外稳定一个入口，对内随便加减机器，从而同时换来高可用和水平扩展能力。

对前端来说，真正的价值不在于会不会写 upstream，而在于理解了这套结构之后，碰到“偶发失败、数据不一致、登录态随机丢失、灰度只对一部分人生效”这些线上现象时，能立刻反应过来——这很可能是请求被分到了不同机器，问题在负载均衡这一层，而不是我的浏览器代码。轮询、加权、最少连接、ip_hash、健康检查、会话保持，这几个词背后都对应着我实实在在踩过的坑。面试会问，线上更会遇到，早点搞懂不亏。
