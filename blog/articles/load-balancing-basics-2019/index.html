负载均衡基础：为什么线上服务不是只放一台机器

2019-11-09
杂项

线上服务通常不会只跑在一台机器上。

一台机器扛不住流量，也容易成为单点故障。多台机器一起提供服务时，就需要一个入口把请求分发出去，这就是负载均衡。

前端平时不直接配置很多负载均衡，但接口偶发失败、某台机器返回旧数据、某个用户总是异常，这些问题都可能和负载均衡有关。

常见策略

轮询：

简单平均分配。

权重：

性能更好的机器分更多请求。

最少连接：把请求转给当前连接数较少的机器。

IP hash：同一个 IP 尽量分到同一台机器。

不同策略适合不同场景。

健康检查

如果某台机器挂了，负载均衡还继续转发请求，用户就会随机失败。

所以需要健康检查。

没有健康检查时，问题会很隐蔽：你刷新几次，有时成功，有时失败。

会话保持

如果登录状态存在某台服务器内存里，请求被转到另一台服务器，就可能丢登录。

解决方式：

  • session 存 Redis
  • 使用 token
  • 开启会话保持

前端看到“有时登录态丢失”，不一定是浏览器问题，也可能是服务端会话没有共享。

如果失败总来自某台机器，问题就很明确。

前端错误上报时也可以记录接口状态、请求 ID、响应头里的 trace id，方便后端排查。

小结

负载均衡让多台机器共同对外提供服务，提升可用性和扩展能力。

面试问它，项目里也能遇到相关问题。轮询、权重、健康检查、会话保持这些概念，能帮助前端更好理解接口偶发错误和线上部署结构。
