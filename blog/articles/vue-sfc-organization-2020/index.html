Vue 单文件组件写久了以后，真正拉开差距的是组织方式

2020-03-21
Vue组件与状态

Vue 的单文件组件很舒服，这点几乎不用争。

可写得舒服，并不代表天然就能一直保持清晰。很多 .vue 文件一开始只有几十行，后面慢慢加请求、加校验、加交互、加样式，最后变成几百行的“大组件”。

真正有经验的差别，不是能不能写出 .vue 文件，而是能不能让组件在需求持续增长后仍然保持可读。

真正的问题不在文件后缀

.vue 文件只是容器，问题还是回到组织方式。

一个组件如果同时承担：

  • 数据请求
  • 状态处理
  • 页面布局
  • 表单逻辑
  • 弹窗控制

那无论是不是单文件组件，后面都会变重。

一个大组件通常不是突然变大的，而是一点点被“顺手加逻辑”撑大的：

  • 页面多一个接口，直接写在当前组件
  • 多一个弹窗，直接加 dialogVisible
  • 多一个字段校验，直接补一个方法
  • 多一个状态展示，直接在模板里加分支
  • 多一个特殊样式，直接写进当前 style

每一步都合理，但累积起来就会让组件失去边界。

先判断组件职责

可以先把组件分成几类：

  • 页面组件：负责拉数据、组织布局、协调子组件
  • 业务组件：负责一个明确业务块，例如用户信息卡片、订单列表
  • 基础组件：负责稳定 UI 能力，例如按钮、输入框、弹窗
  • 状态组件：负责 loading、empty、error 等通用状态展示

页面组件不应该同时承担所有细节。它更像编排者，而不是所有逻辑的容器。

样式也要有边界

<style scoped> 能降低样式串扰，但它不是命名随意的理由。

比较稳的习惯是：

  • 组件根节点有稳定类名
  • 子元素类名表达结构
  • 页面布局样式留在页面组件
  • 基础组件只处理自身尺寸和状态
  • 不轻易用深度选择器改第三方组件内部结构

当样式开始需要跨组件影响很多内部元素时，通常说明组件边界或设计系统边界需要重新看一遍。

大组件怎么治理

已经变大的 .vue 文件，不建议一次性重写。更稳的顺序是：

  1. 先把请求和格式化移到独立文件
  2. 再把模板里明显独立的区域拆成子组件
  3. 然后把弹窗、表单、列表等交互块拆开
  4. 最后再收敛样式和状态命名

每一步都应该保持行为不变。大组件治理最怕一边重构一边改业务，风险会迅速变高。

写在最后

Vue 单文件组件最大的优势，是让组件边界更完整；但如果把太多职责硬塞进一个文件，这个优势也会被自己抵消掉。

组件写久了以后，真正拉开差距的不是格式，而是组织节奏。

专业的 SFC 组织方式，应该让人能快速回答：这个组件负责什么、数据从哪里来、状态在哪里变、样式影响到哪里、哪些部分可以独立测试和复用。能回答这些问题，组件才算真的稳。
