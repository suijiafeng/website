Vue 生命周期别背顺序了：先弄清楚每个阶段该做什么

2019-11-23
Vue组件与状态

学 Vue 时，生命周期几乎是绕不过去的一章。

很多人一开始会背：

  • created
  • mounted
  • updated
  • destroyed

顺序当然要知道，但真正写项目时，更重要的问题其实是：哪些逻辑该放在哪个阶段。

生命周期不是为了背名词

生命周期存在的意义，是让你知道组件此刻处于什么状态。

数据是不是已经初始化了，DOM 是不是已经挂载了，页面是不是刚更新完，这些信息会直接决定你在这个阶段能做什么。

可以把生命周期理解成组件运行过程中的几个检查点。每个检查点能做的事不同，能拿到的资源也不同。

先建立阶段感

一个常见的 Vue 2 组件，大致会经历：

  • beforeCreate：实例刚开始初始化，数据和方法还没准备好
  • created：数据、方法、计算属性已经准备好，DOM 还没挂载
  • mounted：DOM 已经进入页面，可以访问真实节点
  • updated：响应式数据导致 DOM 更新完成
  • beforeDestroy / destroyed：组件准备销毁或已经销毁

如果使用 keep-alive，还会遇到：

  • activated：缓存组件重新激活
  • deactivated：缓存组件被切走

记顺序只是开始，关键是知道每个阶段的能力边界。

created 更适合处理数据准备

到了 created，组件的数据和方法已经准备好了，但真实 DOM 还没挂到页面上。

所以这个阶段更适合：

  • 初始化数据
  • 发起请求
  • 做纯逻辑处理

如果你要做的是：

  • 操作第三方 DOM 库
  • 依赖页面真实节点

updated 不是补丁桶

很多人一发现界面更新后要再做点事，就会想到 updated。它当然能用，但也最容易被滥用。

因为一旦组件更新频繁，这个钩子也会跟着频繁触发。

所以如果你只是想在某个字段变化后做动作，很多时候用 watch 会更明确，而不是把逻辑一股脑塞进 updated。

destroyed 别只想着“组件被删了”

这个阶段真正要关注的是清理。

例如：

  • 解绑事件
  • 清理定时器
  • 销毁第三方实例

被 keep-alive 包住的组件不会每次切换都销毁，所以 created 和 mounted 不会反复执行。

生命周期不是业务架构

生命周期只是时机，不应该成为业务逻辑的唯一组织方式。

如果 created 里有几十行请求、权限、格式化和状态拼装，问题不在生命周期，而在逻辑没有拆分。可以把请求放到 service，把格式化放到工具函数，把复杂状态拆到子组件或组合函数。

生命周期里最好只做调度：

它告诉读代码的人“什么时候开始”，而不是把所有细节都塞在钩子里。

写在最后

Vue 生命周期真正难的地方，不是顺序，而是时机感。

什么时候该拿数据，什么时候该碰 DOM，什么时候该做清理，只要这些边界分清楚，生命周期就不再是一串需要背诵的名字，而是你组织组件逻辑的坐标点。

专业一点的写法是：created 准备数据，mounted 处理真实 DOM，watch 响应具体状态，updated 谨慎使用，销毁阶段彻底清理资源，keep-alive 单独考虑激活和停用。
