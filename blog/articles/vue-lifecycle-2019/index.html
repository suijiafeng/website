Vue 生命周期别背顺序了：先弄清楚每个阶段该做什么

2019-11-23
Vue组件与状态

学 Vue 时，生命周期几乎是绕不过去的一章。

很多人一开始会背：

  • created
  • mounted
  • updated
  • destroyed

顺序当然要知道，但真正写项目时，更重要的问题其实是：哪些逻辑该放在哪个阶段。

生命周期不是为了背名词

生命周期存在的意义，是让你知道组件此刻处于什么状态。

数据是不是已经初始化了，DOM 是不是已经挂载了，页面是不是刚更新完，这些信息会直接决定你在这个阶段能做什么。

可以把生命周期理解成组件运行过程中的几个检查点。每个检查点能做的事不同，能拿到的资源也不同。

先建立阶段感

一个常见的 Vue 2 组件，大致会经历：

  • beforeCreate：实例刚开始初始化，数据和方法还没准备好
  • created：数据、方法、计算属性已经准备好，DOM 还没挂载
  • mounted：DOM 已经进入页面，可以访问真实节点
  • updated：响应式数据导致 DOM 更新完成
  • beforeDestroy / destroyed：组件准备销毁或已经销毁

如果使用 keep-alive，还会遇到：

  • activated：缓存组件重新激活
  • deactivated：缓存组件被切走

记顺序只是开始，关键是知道每个阶段的能力边界。不过顺序本身也不用死背，写个最小组件在每个钩子里打日志，跑一遍就清清楚楚：

挂载阶段控制台会按这个顺序打印：beforeCreate → created → beforeMount → mounted。之后每次改 msg 触发的是 beforeUpdate → updated；组件销毁时是 beforeDestroy → destroyed（据说正在路上的 Vue 3 会把这两个钩子改名成 beforeUnmount → unmounted，语义更准，但眼下我们用的还是 Vue 2 这套）。

更值得注意的是 this.$el：beforeCreate 和 created 里打印它是 undefined，到了 mounted 才是真实的 <p> 节点。这就直接验证了下面要说的——created 阶段拿不到 DOM，mounted 才能碰。

还有一组容易被忽略的：beforeMount（挂载前，模板已编译但还没插入 DOM）和 beforeUpdate（数据变了、DOM 还没更新）。这俩平时用得少，但 beforeUpdate 偶尔有用——比如更新前想记录一下滚动位置，等 updated 再恢复，做「内容刷新但视口不跳」的效果。父子组件的钩子触发顺序也常被问：挂载时是父 beforeCreate/created/beforeMount → 子完整挂载 → 父 mounted，也就是「父先开始，子先完成，父后 mounted」。我调试嵌套组件初始化时序时，脑子里就靠这条顺序定位「为什么父组件 mounted 里拿子组件 ref 是有值的」。

created 更适合处理数据准备

到了 created，组件的数据和方法已经准备好了，但真实 DOM 还没挂到页面上。

所以这个阶段更适合：

  • 初始化数据
  • 发起请求
  • 做纯逻辑处理

如果你只是要拿数据、准备状态，很多时候放在这里就够了。

这个 destroyed 标记不是多余的防御。我真踩过：列表页发请求还没回来，用户手快切走了组件，请求回来时 this.list = ... 往一个已销毁的实例上写，控制台报一串看不懂的警告，偶现还难复现。加了销毁标记直接 return 就干净了。更狠一点的做法是在 beforeDestroy 里 cancelToken 取消请求（用 axios 的话），从源头掐断。

关于「请求放 created 还是 mounted」这个老问题，我的结论是：纯数据请求放 created 就行，能早一点发出去，不用等 DOM。网上有说放 mounted 的，理由是服务端渲染时 created 在服务端也会跑可能重复请求——但纯客户端项目没这顾虑，created 更早。如果请求结果要立刻操作 DOM（比如拿到数据后要算某个元素高度），那才需要等到 mounted 之后、甚至 $nextTick 之后。

mounted 才适合碰 DOM

如果你要做的是：

  • 获取元素尺寸
  • 操作第三方 DOM 库
  • 依赖页面真实节点

那就更适合放在 mounted。

因为只有到了这个阶段，组件的 DOM 才真正进了页面。

mounted 代表初次挂载完成，nextTick 代表这次响应式更新对应的 DOM 已经刷新。两者解决的问题不同。

这里要提醒一个经典误区：mounted 并不保证子组件全部挂载完。Vue 父组件的 mounted 触发时，它自己的 DOM 是好的，子组件通常也挂好了（因为子先 mounted），但如果子组件内部还有异步渲染（比如 v-if 依赖一个异步数据），那部分 DOM 在父的 mounted 里还拿不到。我吃过的亏是：在父 mounted 里直接量一个依赖异步数据撑开的容器高度，量到的是 0。解法就是把测量挪到数据回来后的 $nextTick 里，而不是赖在 mounted。

$nextTick 还有个细节：它既能 await，也能传回调。我现在统一用 await this.$nextTick()，配合 async 方法读起来顺，避免回调嵌套。

updated 不是补丁桶

很多人一发现界面更新后要再做点事，就会想到 updated。它当然能用，但也最容易被滥用。

因为一旦组件更新频繁，这个钩子也会跟着频繁触发。

所以如果你只是想在某个字段变化后做动作，很多时候用 watch 会更明确，而不是把逻辑一股脑塞进 updated。

destroyed 别只想着“组件被删了”

这个阶段真正要关注的是清理。

例如：

  • 解绑事件
  • 清理定时器
  • 销毁第三方实例

这些事情如果不做，页面看起来可能没马上出问题，但后面很容易留下隐患。

keep-alive 下要注意激活和停用

被 keep-alive 包住的组件不会每次切换都销毁，所以 created 和 mounted 不会反复执行。

如果你希望页面每次回到前台都刷新，可以用 activated：

这类页面最容易出问题的地方是：你以为组件重新创建了，实际上它只是从缓存里恢复。列表滚动位置、筛选条件、定时器状态，都要根据业务决定是保留还是重置。

我在带 keep-alive 的列表-详情场景里踩过一个很典型的坑：从列表点进详情，改了某条数据状态，返回列表，列表还是旧的，因为列表组件被缓存了、created 不再执行。当时第一反应是「数据没刷新是不是接口缓存了」，查了半天才想起来是 keep-alive。解法就是把刷新逻辑从 created 挪到 activated，每次激活时按需拉一下。

但又不能无脑每次 activated 都重新请求，否则用户只是切个 tab 看一眼又回来，列表整个重刷、滚动位置丢了，体验更差。所以我一般加个「脏标记」：详情页改了数据就往一个共享状态里打个标，列表 activated 时看到标记才刷新，没标记就用缓存。activated/deactivated 配合定时器也要小心——deactivated 时该暂停轮询，否则后台缓存的页面还在偷偷发请求，用户根本看不到。这些都是 keep-alive 把「销毁/重建」换成「停用/激活」之后必须重新审视的点。

生命周期不是业务架构

生命周期只是时机，不应该成为业务逻辑的唯一组织方式。

如果 created 里有几十行请求、权限、格式化和状态拼装，问题不在生命周期，而在逻辑没有拆分。可以把请求放到 service，把格式化放到工具函数，把复杂状态拆到子组件或组合函数。

生命周期里最好只做调度：

它告诉读代码的人“什么时候开始”，而不是把所有细节都塞在钩子里。

Vue 生命周期真正难的地方，不是顺序，而是时机感。

什么时候该拿数据，什么时候该碰 DOM，什么时候该做清理，只要这些边界分清楚，生命周期就不再是一串需要背诵的名字，而是你组织组件逻辑的坐标点。

专业一点的写法是：created 准备数据，mounted 处理真实 DOM，watch 响应具体状态，updated 谨慎使用，销毁阶段彻底清理资源，keep-alive 单独考虑激活和停用。
