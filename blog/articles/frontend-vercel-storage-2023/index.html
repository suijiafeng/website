Vercel 推出存储能力后，前端部署不只是静态页面了

2023-05-05
前端基础数据可视化与存储

以前我对 Vercel 的印象也很简单：部署前端页面很方便。

把 Next.js、React 或静态站点推到 GitHub，再连到 Vercel，几分钟就能上线。直到我做一个内部小工具，页面本身很快写完，麻烦反而卡在后面：用户提交的数据放哪，上传的附件放哪，首页列表要不要缓存，测试环境和线上数据怎么隔离。那一刻才发现，一个真正能用的 Web 应用通常不只需要页面，还需要数据。

用户信息、文章内容、订单记录、图片文件、缓存数据，这些都离不开数据库或存储服务。Vercel 推出 Postgres、Blob、KV 等能力后，前端部署平台开始更像一个轻量应用平台，而不只是静态页面托管。

前端应用为什么需要存储

静态页面只负责展示，动态应用需要读写数据。

常见需求包括：

  • 博客文章从数据库读取
  • 用户上传头像或附件
  • 商品列表需要分页查询
  • 表单提交后要保存
  • 页面需要缓存热点数据
  • 用户行为需要记录

如果部署平台只负责页面，开发者就要额外找数据库、对象存储、缓存服务，再手动配置连接、权限和环境变量。这会让小项目变复杂，也会让前端开发者在部署阶段频繁切换平台。

Vercel 的存储能力解决的不是“数据库技术本身”，而是降低全栈小应用的集成成本。

我对这类平台能力的态度是：它很适合把个人项目、内部工具和早期 SaaS 快速跑起来，但不要因为接入方便就忽略数据模型。页面部署可以重来，数据迁移和权限设计一旦做错，后面成本会大很多。

Vercel Postgres 是什么

Vercel Postgres 可以理解为 Vercel 提供的 PostgreSQL 数据库方案。

PostgreSQL 是常见的关系型数据库，适合保存结构化数据，比如用户、文章、商品、订单。

还要注意连接数量和运行环境。Serverless 场景下函数会频繁启动，如果每次都新建连接，数据库连接数很容易被打满。平台通常会提供连接池或推荐用法，接入时要按官方方式处理，不要把传统长驻服务的连接习惯直接搬过来。

数据库适合结构化数据

Postgres 适合处理有明确关系的数据。比如文章和作者、订单和商品、用户和角色。

但不要把所有东西都塞进数据库。图片、视频、PDF 这类大文件直接存数据库通常不是好选择，数据库里保存文件地址和元信息会更清晰。

Vercel Blob 适合存文件

数据库适合保存结构化数据，但不适合直接存大文件。

图片、PDF、音频、视频这类内容，更适合放在对象存储里。Vercel Blob 就是面向文件存储的能力，适合：

  • 用户头像
  • 文章封面
  • 上传附件
  • 富文本图片
  • 导出的报表文件

通常做法是：文件放到 Blob，数据库里只保存文件地址、文件类型、大小、所属用户和创建时间。

文件上传还要处理权限。头像、附件、导出报表不一定都是公开资源。公开 Blob 地址很方便，但如果业务要求私有访问，就要考虑签名 URL、过期时间和服务端鉴权。文件存储不是把图片传上去就结束，还要想清楚谁能看、看多久、能不能删除。

KV 适合做轻量缓存

有些数据不一定要放进关系型数据库。例如：

  • 验证码
  • 临时状态
  • 页面访问计数
  • 热门列表缓存
  • 用户会话信息
  • 接口限流计数

这类数据通常结构简单、读写频繁、生命周期较短，适合放在 KV 这类键值存储里。

存储选型要看数据特征

Postgres、Blob、KV 不是互相替代的关系。

可以用一个简单规则判断：

  • 需要关系查询、排序、事务：用 Postgres
  • 需要保存图片、附件、大文件：用 Blob
  • 需要临时状态、缓存、计数：用 KV

比如一个博客系统，文章标题、正文、作者放 Postgres；文章封面放 Blob；首页热门文章列表缓存放 KV。三者组合起来，才是一个比较完整的应用结构。

边界和成本也要考虑

平台提供存储能力会降低集成成本，但不代表所有项目都应该绑定在一个平台上。

选型前至少要考虑：

  • 数据备份和迁移是否方便
  • 本地开发环境怎么模拟
  • 费用随访问量如何增长
  • 是否有区域和延迟要求
  • 是否会被平台能力限制
  • 团队是否熟悉对应数据库

如果是个人项目、活动页、小型 SaaS、内部工具，使用平台内置存储非常高效。如果是强合规、大数据量、多云部署或复杂数据库运维场景，就需要更谨慎地评估。

本地开发也要提前设计。团队成员不能每个人都连生产数据库调试，至少要有本地或测试环境的连接配置、种子数据和迁移脚本。平台降低了部署门槛，但不会自动解决环境隔离。

数据迁移要从第一天考虑

只要用了数据库，就会遇到 schema 变化。哪怕是小项目，也不要只在控制台手改表结构。至少要把建表 SQL、迁移脚本或 ORM schema 放进版本库。

这样做有两个好处：一是新环境能复现，二是出问题时知道数据结构是怎么变过来的。平台越方便，越容易让人跳过这些基本功，但数据层最怕“只有线上知道真实结构”。

我现在会把这类平台能力当成“快速起步的好工具”，但不会把它当成不用设计数据层的理由。

结构化数据进数据库，文件进对象存储，临时热点数据进 KV，这些边界一开始就要想清楚。平台能帮你省掉部署和集成成本，却不会替你设计表结构、权限、备份、迁移和错误处理。

个人项目、内部工具、早期 SaaS 用它会很舒服；但只要数据开始变重要，就要提前留好迁移脚本、环境隔离和备份方案。页面部署可以推倒重来，数据很少有这么轻松。
