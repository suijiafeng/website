Vercel 推出存储能力后，前端部署不只是静态页面了

2023-05-05
前端基础数据可视化与存储

以前很多人对 Vercel 的印象是：部署前端页面很方便。

把 Next.js、React 或静态站点推到 GitHub，再连到 Vercel，几分钟就能上线。但一个真正的 Web 应用通常不只需要页面，还需要数据。

比如用户信息、文章内容、订单记录、图片文件、缓存数据，这些都离不开数据库或存储服务。Vercel 推出 Postgres、Blob、KV 等能力后，前端部署平台开始更像一个轻量应用平台，而不只是静态页面托管。

前端应用为什么需要存储

静态页面只负责展示，动态应用需要读写数据。

常见需求包括：

  • 博客文章从数据库读取
  • 用户上传头像或附件
  • 商品列表需要分页查询
  • 表单提交后要保存
  • 页面需要缓存热点数据
  • 用户行为需要记录

如果部署平台只负责页面，开发者就要额外找数据库、对象存储、缓存服务，再手动配置连接、权限和环境变量。这会让小项目变复杂，也会让前端开发者在部署阶段频繁切换平台。

Vercel 的存储能力解决的不是“数据库技术本身”，而是降低全栈小应用的集成成本。

Vercel Postgres 是什么

Vercel Postgres 可以理解为 Vercel 提供的 PostgreSQL 数据库方案。

PostgreSQL 是常见的关系型数据库，适合保存结构化数据，比如用户、文章、商品、订单。

数据库适合结构化数据

Postgres 适合处理有明确关系的数据。比如文章和作者、订单和商品、用户和角色。

但不要把所有东西都塞进数据库。图片、视频、PDF 这类大文件直接存数据库通常不是好选择，数据库里保存文件地址和元信息会更清晰。

Vercel Blob 适合存文件

数据库适合保存结构化数据，但不适合直接存大文件。

图片、PDF、音频、视频这类内容，更适合放在对象存储里。Vercel Blob 就是面向文件存储的能力，适合：

  • 用户头像
  • 文章封面
  • 上传附件
  • 富文本图片
  • 导出的报表文件

通常做法是：文件放到 Blob，数据库里只保存文件地址、文件类型、大小、所属用户和创建时间。

KV 适合做轻量缓存

有些数据不一定要放进关系型数据库。例如：

  • 验证码
  • 临时状态
  • 页面访问计数
  • 热门列表缓存
  • 用户会话信息
  • 接口限流计数

这类数据通常结构简单、读写频繁、生命周期较短，适合放在 KV 这类键值存储里。

存储选型要看数据特征

Postgres、Blob、KV 不是互相替代的关系。

可以用一个简单规则判断：

  • 需要关系查询、排序、事务：用 Postgres
  • 需要保存图片、附件、大文件：用 Blob
  • 需要临时状态、缓存、计数：用 KV

比如一个博客系统，文章标题、正文、作者放 Postgres；文章封面放 Blob；首页热门文章列表缓存放 KV。三者组合起来，才是一个比较完整的应用结构。

边界和成本也要考虑

平台提供存储能力会降低集成成本，但不代表所有项目都应该绑定在一个平台上。

选型前至少要考虑：

  • 数据备份和迁移是否方便
  • 本地开发环境怎么模拟
  • 费用随访问量如何增长
  • 是否有区域和延迟要求
  • 是否会被平台能力限制
  • 团队是否熟悉对应数据库

如果是个人项目、活动页、小型 SaaS、内部工具，使用平台内置存储非常高效。如果是强合规、大数据量、多云部署或复杂数据库运维场景，就需要更谨慎地评估。

小结

Vercel 推出存储能力后，前端部署的边界变宽了。开发者可以在同一个平台上完成页面、接口、数据库、文件和缓存的组合。

但存储能力越方便，越要把数据边界想清楚：结构化数据进数据库，文件进对象存储，临时热点数据进 KV。平台能力能降低启动成本，真正决定项目稳定性的仍然是清晰的数据模型、统一的错误处理和可迁移的架构设计。
