移动端 rem 适配实践：设计稿到页面，中间别只靠比例

2018-07-03
移动与小程序CSS

这半年我接连做了三个移动 H5 项目：一个营销活动页、一个内嵌在 App WebView 里的订单详情、一个对外的 H5 商城。三个项目用的都是 rem 适配，但每个都踩了不一样的坑。今年把这套东西彻底捋顺之后，我决定把经验记下来，省得下次又从头摸索。

先把结论摆在前面：rem 解决的是「设计稿到屏幕的等比缩放」，它只解决比例问题。如果你以为套上一个 flexible.js 就万事大吉，那 1px 边框、字体可读性、横屏、图片跳动这些坑会一个不落地等着你。

为什么是 rem，而不是别的

2018 年这个时间点，移动端适配主流就那么几条路：百分比 + flex 弹性布局、rem 等比缩放、vw/vh 视口单位。

百分比布局的问题是它只对宽度生效，高度、字号、圆角这些没法跟着等比走，设计稿一旦有大量「正方形卡片」「固定间距」就很难还原。vw 其实是最优雅的方案——1vw 就是视口宽度的 1%，设计稿 750 宽时 100px 直接写成 13.333vw，连 JS 都不用。但 2018 年我手上还有不少要兼容 iOS 8 和 Android 4.4 的 WebView，vw 在这些老机器上要么不支持要么有 bug，最后只能退回 rem。

rem 是相对根元素 <html> 的 font-size 计算的。思路很简单：用 JS 监听屏幕宽度，动态改 html 的 font-size，所有用 rem 写的尺寸就自动等比缩放了。兼容性好，这是它在那两年能成为主流的根本原因。

第一，用的是 getBoundingClientRect().width 而不是 clientWidth。在某些安卓 WebView 上，页面初始化时 clientWidth 会拿到 0 或者一个错误值，getBoundingClientRect 更稳。

第二，pageshow 的 persisted 判断很关键。iOS Safari 有 bfcache（往返缓存），用户点了返回再进来，页面是从缓存恢复的，不会触发 resize，根字号可能是上一个状态。我那个商城项目就出过这个 bug：用户横屏看了下别的页面，返回时页面布局全乱了，排查半天才定位到这。

第三，data-dpr 是 lib-flexible 的一个历史包袱。它当年还会动态改 viewport 的 initial-scale（1/dpr），让 retina 屏能画出真正的物理 1px。但这套缩放 viewport 的玩法在后期 amfe-flexible 里被砍掉了——因为它和 vw、和很多三方组件冲突太多。如果你现在还在维护老项目看到 data-dpr，知道它是干嘛的就行，不建议沿用。

注意 rootValue 和上面 JS 里的换算要对得上。我用 width / 10 当根字号时，rootValue 就是 75（750÷10）；如果用 width / 7.5 让 1rem=100px，那 rootValue 写 100。这俩一旦对不上，整个页面尺寸会整体偏大或偏小，是新人最常见的「为什么我的页面比设计稿大了一圈」的原因。

minPixelValue: 2 这个配置救过我的命。1px 的边框你是绝对不想让它被转成 rem 的——转了之后在不同屏幕上会被缩放成 0.99px、1.2px 这种值，渲染出来时粗时细还时有时无。这块下面专门讲。

字体：最不该无脑跟着 rem 走的东西

布局尺寸用 rem 等比缩放，没问题。但字体跟着等比缩放，是我交过学费才明白不该做的事。

道理是这样的：iPhone 5 宽 320，iPhone 6 Plus 宽 414，差不多 1.3 倍。如果正文字号也等比走，小屏上 14px 的字会缩到 10px 多，老花眼用户根本看不清；大屏上又会胖到 18px，一行没几个字、显得很蠢。字体先要保证「能不能看清」，而不是「占屏幕多大比例」，这俩诉求经常是矛盾的。

我后来的做法是：布局、间距、圆角、图标尺寸用 rem；正文字号、按钮文字、输入框文字用固定 px，最多分几档断点。

实操里有个偷懒技巧：postcss-pxtorem 默认不转大写的 PX。也就是说，凡是我不想被转成 rem 的，直接在 CSS 里写 font-size: 14PX（大写），构建时它就原样保留。团队约定俗成「大写 PX = 我故意不让你缩放」，比维护一长串 selectorBlackList 清爽多了。

图片：加载前后高度别变，否则页面会跳

图片是移动端页面跳动（CLS，虽然这词那会儿还没火）的头号元凶。图没加载完时高度是 0，加载完撑开高度，整个页面往下顿一下，用户正在点的按钮就跑位了。

解决思路是：在图片加载之前，就用 padding 撑出它应有的比例占位。

padding-bottom 的百分比是相对父元素「宽度」算的，这是个很多人不知道的 CSS 特性，刚好被我们拿来锁高宽比。750×300 的图，比例是 300/750=40%。

二倍图、三倍图的资源选择也别忘了。能用 CSS 的 image-set 或者 srcset 就用，实在不行让后端按 dpr 返回不同尺寸的图——给 dpr=1 的机器推三倍图，纯属浪费用户流量，那年代很多人还按 M 计费。

横屏和异常宽度：保证「不崩」就是胜利

移动 H5 几乎都只按竖屏设计，但用户横屏、平板、PC 分享打开都会发生。横屏要做到像素级完美不现实，目标降一档：别崩、别难看。

这里有个坑：.page 的 max-width 千万别写成 rem。因为锁宽之后根字号也被锁死了，rem 和 px 在那一刻是恒定换算关系，写 7.5rem 看似等于 750px，但万一以后改了根字号基准，这里会跟着错位。直接写死 750px 最稳。

横屏还有个高频问题：iOS 上输入框聚焦弹出键盘，横屏时键盘占掉大半屏，position: fixed 的底部按钮会被顶飞或者错位。我的处理是横屏时干脆隐藏 fixed 底栏，或者监听 orientationchange 重新计算位置。能引导用户「请用竖屏访问」当然最省事，但很多甲方不让加这种提示，只能硬扛。

那个 300ms 延时是经验值。安卓某些机型旋转后立刻读 clientWidth 拿到的还是旋转前的值，延时一下才稳，这个我至今没找到比延时更优雅的解法。

WebView 字体被系统放大。 安卓有些机型、还有 App 自己的「字体大小」设置，会强行放大网页字体，把你精心调好的布局撑爆。可以在根元素上锁 -webkit-text-size-adjust: 100%;，能挡住一部分，但挡不住所有，这是移动端永远的痛点之一。

rem 只是把设计稿按比例还原的工具，关键在于边界处理：锁定根字号上限、提前设置占位、区分字号与布局、处理 1px 线与安全区等。换技术（如 vw）并不免掉这些细节。适配要把边界补齐，用户体验才稳。
