Vue 项目里的 axios 封装：别让每个页面自己处理接口错误

2018-02-24
VueJavaScript前端基础

Vue 项目刚开始写接口时，页面里直接 axios.get 最快。

页面少的时候没问题。等接口多了以后，请求头、token、错误提示、登录失效、loading、重复提交都会散在各个组件里。最后每个页面都有一套相似但不完全一样的处理逻辑。

请求封装不是为了显得高级，而是为了把这些重复的边界收起来。

我对这件事印象最深的一次，是接手一个别人写了一年的项目。全局搜 axios. 搜出来一百多处，每处的错误处理都长得不太一样：有的 .catch 弹 alert，有的弹 this.$message，有的干脆吞掉不管，还有的把后端的 code 判断写成 res.data.code == 0、res.code === '0'、res.errcode 各种版本。后来后端改了一次错误码结构，我们花了整整两天在全项目里捞这些散落的判断。那次之后我才真正理解，请求封装的本质不是“写得漂亮”，而是“把可能集体出错的地方收到一个文件里，改的时候只改一处”。

下面这套封装是我在好几个 Vue 2 项目里反复打磨出来的，基于 axios 0.18 那个版本，思路到现在也没太大变化。

请求拦截器处理 token

这里要注意，token 放 localStorage 有 XSS 风险。很多项目为了开发方便会这么做，但至少要知道这是权衡，不是绝对安全。

如果项目对安全要求高，应该配合 HttpOnly Cookie、CSRF 防护和后端策略。

请求拦截器还有个常被忽略的用途：在这里统一加一些和接口无关的公共参数。比如多语言项目要带 Accept-Language，灰度环境要带版本标识，或者埋点要带个请求追踪 ID。这些东西如果让每个接口自己传，迟早会有人漏掉：

不过也别把拦截器塞太满。我见过有人把业务逻辑判断也写进请求拦截器，结果某个接口因为公共逻辑被意外改了参数，排查时根本想不到问题出在拦截器里。拦截器里只放“所有请求都该做、且和具体业务无关”的事，这条边界要守住。

这里我栽过一个很典型的跟头：登录失效时如果同一个页面并发发了五个请求，五个请求会各自触发一次 router.replace 加一次错误提示，用户屏幕上瞬间弹五个“登录已过期”，URL 也被反复跳。解决办法是加个标志位，确保跳转和清理只发生一次：

跳转时带上 redirect 这个 query 也很重要，登录成功后能回到用户原来想去的页面，而不是粗暴地甩回首页。这是个不写就没人投诉、写了体验明显更好的细节。

顺便说个登录态相关的坑：localStorage 是跨标签页共享的，但内存里的 token 不是。如果用户在 A 标签退了登录，B 标签的内存状态还以为登着，下一个请求才会发现 401。对体验要求高的项目可以监听 storage 事件做多标签同步，不过大多数后台项目不至于做到这一步。

重复提交和 loading 也值得收一收

前面提的“重复提交”这个坑，我单独拎出来说。最常见的就是表单提交按钮，网络一慢用户连点几下，后端就收到几条一样的订单。靠每个页面自己加 submitting 标志位当然可以，但容易漏。可以在封装里做一层请求去重，对相同的请求挂起后续的重复调用：

不过这套去重我不会默认对所有请求开，因为有些场景确实需要短时间内发多次相同请求。更实用的做法往往是给关键操作按钮配一个简单的“锁”，封装里只提供能力、不强制启用。工具应该可选，不该替业务做太多决定。

loading 同理。全局 loading 可以在拦截器里维护一个计数器，请求数从 0 变 1 时显示、归 0 时隐藏；但局部 loading（某个表格自己转圈）还是交给页面自己控制更合适。我吃过的亏是早期把所有请求都挂全局 loading，结果后台轮询接口每隔几秒就让全屏蒙层闪一下，用户以为页面卡了。后来改成轮询、预加载这类“静默请求”默认不触发全局 loading，体验才正常。给请求加个 silent 选项区分就行：

封装请求的意义不在炫技，而在于把那些分散在各处的边界收拢：请求头、超时、错误结构和登录失效等都交给统一的层来处理。这样页面只需要关注展示和业务，改接口时也只需改一处，项目能少走很多弯路。
