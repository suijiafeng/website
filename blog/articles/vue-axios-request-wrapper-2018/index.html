Vue 项目里的 axios 封装：全局搜出一百多处 axios. 之后，我干了什么

2018-06-21
Vue构建与模块化

请求层失控最直观的信号，不是项目里有没有封装，而是你一搜 axios.，结果能滚满好几屏。到这一步，问题已经不是“调用有点多”，而是错误处理、loading、鉴权和兜底逻辑全都在四处重复生长。

我接手这个 Vue 2 项目时，第一件事就是做了这次搜索。结果一百多处。越往下翻，心越凉：有的页面自己弹 alert，有的页面手写 loading，有的地方直接吞错，有的地方又把后端字段当场写死。还没改功能，请求层已经先把维护成本摆在脸上了。

同一个项目里，code == 0、code === '0'、res.errcode 三种判法并存；错误处理有弹 alert 的、弹 $message 的、还有 .catch(() => {}) 直接吞的；token 有的地方拦截器加，有的地方手动拼。它们不是谁写错了——每一段单独看都能跑——它们只是各自为政。

我当时想，只要后端别动返回结构，这堆代码还能这么苟着。

后端动了。

事故：后端改了一次错误码结构

四月的一次迭代，后端把返回结构统一成了新版：错误码从 code 挪到 errcode，部分接口的 0 从数字变成字符串。后端群里发了通知，说"前端同步改一下"。

改哪里？改一百多个地方。

我和同事捞了整整两天。全局搜出来一处处看：这里是 res.data.code，要改；那里是 res.code，前任自己包过一层，也要改，但改法不一样；还有几处判断写在三元表达式里，搜索根本搜不直观。上线后还是漏了两处，一个藏在很少有人点的导出功能里，被用户报上来的。

那两天让我彻底想明白一件事：请求封装的本质不是写得漂亮，而是把"可能集体出错的地方"收进一个文件，出事时只改一处。

事故收尾后我申请了一周，把整个请求层重写了。下面是我收敛的全过程，基于 axios 0.18（写这篇时的最新版），每一步都是被真实的坑逼出来的。

第一步：所有请求走同一个实例

先把散装的 axios.get 收进统一实例，baseURL、超时不再各写各的：

这一步看着平平无奇，但它是后面所有统一处理的地基——拦截器只有挂在同一个实例上才管得住所有请求。

第二步：token 进请求拦截器，手动贴头的全删掉

那些手动拼 headers 的代码全部删掉。顺手把公共参数也收进来：多语言的 Accept-Language、灰度环境的版本标识，这类"每个请求都该带、但和具体业务无关"的东西，让每个接口自己传，迟早有人漏。

两个提醒。一是 token 放 localStorage 有 XSS 风险，我们权衡后接受了，但要知道这是权衡，不是绝对安全。二是拦截器别塞太满——我后来见过有人把业务判断也写进请求拦截器，某个接口的参数被公共逻辑悄悄改了，排查的人想破头也想不到问题在拦截器里。拦截器里只放所有请求都该做、且和业务无关的事，这条边界要守住。

这里有个我反复纠结过的设计点：拦截器里 return result.data 直接把外层的 code/message 剥掉了，页面拿到纯业务数据。好处是页面干净，坏处是个别页面想拿 message 做特殊提示就拿不到了。我的取舍是：主路径服务 80% 的常规场景，剩下 20% 留一个不剥壳的逃生方法。别为了 20% 把主路径搞复杂。

页面按 error.isBizError 决定弹全局提示还是做局部处理。这种细节是项目做大以后才会暴露的，一开始想不到很正常，但封装的结构要留得下这种扩展。

第四步：登录失效，从"各页面自理"到"只跳一次"

旧代码里登录过期的表现堪称行为艺术：有的页面跳登录，有的弹错误，有的什么都不做。统一成 401 就跳：

上线第一天就翻车了。有个页面进来并发五个请求，token 一过期，五个请求各触发一次跳转加一次报错，用户屏幕上瞬间弹五个"登录已过期"，URL 反复横跳。加个标志位，保证跳转只发生一次：

跳转带上 redirect 这个 query 也是那次重写里我坚持加的：登录成功后回到用户原本想去的页面，而不是粗暴甩回首页。这是个不写没人投诉、写了体验明显变好的细节。

顺带一个坑：localStorage 跨标签页共享，内存状态不共享。用户在 A 标签退了登录，B 标签还以为登着，下个请求才发现 401。讲究的项目可以监听 storage 事件做多标签同步，大多数后台项目不至于。

第五步：接口函数进 api 目录，组件不再拼 URL

组件只调业务函数，不碰 URL。下次后端再改接口路径，我不用再全局搜索了。

按业务拆还有个隐性好处：函数名本身就是文档。新人看一眼 api/order.js 里的 createOrder、cancelOrder、getOrderDetail，就知道这个模块有什么能力，比翻散落在组件里的 axios.post('/order/xxx') 直观太多。我还会要求参数结构化：

但这套去重我没有默认全开——有些场景就是需要短时间发多次相同请求。封装只提供能力，开不开由业务定。工具应该可选，不该替业务做太多决定。

一周之后

重写完，全局再搜 axios.，除了 request.js 里那几处，一个都没有了。

又过了两个月，后端第二次调整返回结构。这次我改了一个文件，十分钟，上线，没漏。同事在群里问"前端不用大动吗"，我把 request.js 的 diff 截图发了过去。

那一刻我确信这一周花得值。请求封装的意义从来不在炫技，而在于把请求头、超时、错误结构、登录失效这些"会集体出错的边界"收拢到一处。页面只管展示和业务，出事只改一个文件——接手过烂摊子的人，都懂这有多值钱。
