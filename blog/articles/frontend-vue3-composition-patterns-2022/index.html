Vue3 Composition API 组织方式：别把 setup 写成新的杂物间

2022-01-14
Vue前端基础组件与状态

Vue3 的 Composition API 很好用，但也很容易写乱。

Options API 时代，data、computed、methods、watch 至少天然分区。到了 setup 里，所有东西都能写在一起：状态、请求、事件、监听、表单、弹窗、权限。组件小的时候很顺，组件一大，setup 就变成新的杂物间。

我刚开始写 Vue3 时也踩过这个坑。一个列表页里，搜索表单、分页、详情弹窗、删除确认、字典请求全塞在一个 setup。功能都能跑，但两个月后再改，得从上往下翻半天才能找到某个字段在哪里被改了。

Composition API 的关键不是“都写在 setup”，而是按业务能力组织逻辑。

先按功能块组织

我判断是否值得抽 composable，主要看两点：

  • 这段逻辑是否能独立命名
  • 是否会被复用，或者抽出去能明显降低组件复杂度

不是所有代码都要抽。只被一个组件用、且和组件 UI 强绑定的逻辑，留在组件里反而更清楚。

我的组织习惯

写 Vue3 组件时，我一般按这个顺序：

  1. 简单组件直接在 setup 里按功能块组织
  2. 逻辑超过一屏后，先按业务能力分组
  3. 能独立命名且可复用的逻辑抽 composable
  4. 请求函数统一处理 loading 和错误
  5. watch 只处理必要副作用
  6. 所有事件监听、定时器、订阅都要清理

Composition API 给了更自由的组织方式，但自由不是随便写。代码应该围绕业务能力聚合，而不是围绕 API 名称堆放。
