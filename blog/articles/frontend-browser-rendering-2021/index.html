浏览器拿到页面后发生了什么：前端为什么要理解渲染过程

2021-07-09
前端基础

很多前端问题看起来像“样式没对”“页面卡顿”“脚本执行慢”，往下追其实都和浏览器渲染过程有关。

浏览器不是拿到 HTML 就瞬间把页面变出来，它中间要经历解析、构建、计算、布局、绘制等多个阶段。理解这条链路，不是为了记底层术语，而是为了更清楚哪些写法会影响页面表现。

我自己是吃过亏才认真去补这块的。早几年做一个商品列表页，产品反馈“滚动一卡一卡的”，我第一反应是数据太多，去做了分页和虚拟列表，结果只好了一点点。后来打开 Performance 面板录了一段，才发现真正的元凶是滚动回调里有一行 el.offsetTop，每次滚动都强制浏览器同步算了一次布局。那一刻我才意识到，不懂渲染流程，优化基本靠猜。

这里先把我这几年攒下来的理解和踩过的坑放在一起。链路大致是：解析 HTML 得到 DOM，解析 CSS 得到 CSSOM，两者合成渲染树（Render Tree），然后 Layout（布局/回流）算出每个节点的几何位置，Paint（绘制）把内容画成一个个图层，最后 Composite（合成）把图层拼起来交给 GPU 显示。记住这五步，后面很多现象都能对上号。

HTML、CSS、JavaScript 不是同时等价处理的

浏览器拿到页面资源后，会先解析 HTML，识别出结构内容；遇到样式和脚本时，又会根据它们的类型决定后续处理顺序。

这也是为什么页面首屏速度常常会受到以下因素影响：

  • HTML 结构是否清晰
  • CSS 是否阻塞关键渲染
  • JavaScript 是否在不合适的时机执行了过多工作

这里有几个细节是我后来才搞清楚的。HTML 解析器在遇到一个普通的 <script> 时会直接停下来——它得等脚本下载完、执行完，才敢继续往下解析，因为脚本里可能有 document.write 改变后面的结构。这就是“脚本阻塞解析”。解决办法是 defer 和 async：

我现在的默认习惯是业务脚本一律 defer，埋点、监控这种和 DOM 无关、也不在乎执行顺序的才用 async。把 <script> 一股脑塞在 <head> 里又不加这俩属性，是我见过最常见的首屏拖慢原因。

CSS 更隐蔽一点。CSS 本身不阻塞 HTML 解析，但它会阻塞渲染——浏览器不会用一半的样式去画页面，所以在 CSSOM 构建完之前不会有首屏。更坑的是，CSS 还会间接阻塞它后面的脚本执行：因为脚本可能要读样式（比如 getComputedStyle），浏览器会保险地等 CSSOM 就绪。所以把一个巨大的全站 CSS 顶在前面，等于给首屏判了缓刑。我后来都会把关键的首屏样式内联进 <head>，其余的异步加载。

CSS 会影响元素最终长什么样

HTML 定义了页面结构，但如果没有 CSS，页面只是默认样式下的内容堆叠。

浏览器在解析样式后，需要把规则和 DOM 元素对应起来，计算出每个元素最终使用哪些样式。这就是为什么复杂选择器、大量覆盖和动态样式切换都会影响渲染成本。

有个反直觉的点我提一下：CSS 选择器是从右往左匹配的。.list li a 这种写法，浏览器是先找到所有 a，再往上回溯祖先判断符不符合，而不是先找 .list。所以越靠右的“关键选择器”越泛（比如直接用标签名），匹配代价越高。绝大多数业务里这点开销可以忽略，但在节点成千上万的大表格、富文本场景里，我确实见过因为一条 * { box-sizing: border-box } 配合深层后代选择器导致样式计算明显变慢的情况。后来用 BEM 那种扁平 class（.card__title 一个 class 搞定）反而又快又好维护。

当然，大多数业务页面不需要你天天盯着渲染细节算成本，但至少要知道样式不是“写了就静止不动”，浏览器需要为它做很多计算。

布局和绘制不是一回事

很多人会把页面渲染理解成一个整体动作，其实布局和绘制关注点不一样。

布局更关心元素应该出现在什么位置，占多大空间；绘制则更偏向“把这些结果真正画出来”。

所以当你修改：

  • 宽高
  • 位置
  • 盒模型
  • 文档流结构

这类属性时，浏览器通常需要重新考虑布局。

而一些纯视觉属性，比如颜色变化，可能更多影响绘制阶段。

这里可以把改样式分成三档成本：

  • 改 width、height、top、margin、display 这类影响几何或文档流的，触发 Layout（回流）→ Paint → Composite，最贵；
  • 改 color、background、box-shadow、border-radius 这类不改几何的，跳过 Layout，只 Paint → Composite；
  • 改 transform 和 opacity，如果该元素已经被提升成独立合成层，可以只走 Composite，连重绘都省了，直接交给 GPU。

will-change 是用来提前告诉浏览器“这个元素要动，先给它单独开一层”的，但别滥用——每个合成层都吃显存，我有次给列表里几百个 item 全加了 will-change，结果内存暴涨页面更卡了。原则是只给真正会动的少量元素加，动画结束还可以手动撤掉。

这也是为什么前端性能优化里经常会提到：不同类型的样式变更，成本并不一样。

JavaScript 也会影响渲染节奏

前端代码并不是独立于渲染之外的。

如果脚本在不合适的时候频繁读取布局信息、频繁改 DOM、频繁切换样式，就可能让浏览器不断重复计算，页面就更容易卡。

最经典的坑叫“强制同步布局”（Forced Synchronous Layout，也叫 layout thrashing）。浏览器其实很聪明，它会把你的样式改动攒着，等空闲了再一次性算布局。但只要你在改完之后立刻去读一个需要最新布局才能算出来的值（offsetTop、offsetWidth、scrollHeight、getBoundingClientRect() 这些），它就被迫当场把布局算出来给你。读一改一读一改放在循环里，就是反复强制回流：

为什么理解渲染过程很有用

它带来的最大价值，不是让你可以炫耀术语，而是帮你形成更稳定的判断：

  • 为什么某些资源会阻塞首屏
  • 为什么某些样式改动更容易导致页面抖动
  • 为什么频繁操作 DOM 容易拖慢渲染
  • 为什么组件拆分和资源加载策略会影响体验

很多优化建议如果脱离渲染过程，只会变成口诀。理解了流程以后，很多优化习惯才会真正有因有果。

浏览器渲染不是面试知识，而是页面表现的底层背景

前端做得越久越会发现，很多问题不能只从框架层看。

框架帮你组织组件、管理状态、更新 UI，但最终页面还是要落到浏览器渲染这条链路上。所以只要你还在写网页，就很难完全绕开它。

理解渲染过程并不要求你每天都拿开发者工具盯着性能面板，而是让你知道页面为什么会那样表现。对前端来说，这种底层感知非常值钱。

页面明明逻辑不复杂，为什么还是会卡

这类问题在业务项目里很常见。一个页面可能只是列表、筛选和少量交互，看起来没有什么重逻辑，但实际运行时却要做很多事情：

  • 解析和执行首屏脚本
  • 挂载组件并初始化状态
  • 计算样式和布局
  • 绑定滚动、输入、缩放等事件

这些动作单独看都不算特别重，可一旦它们在页面初始阶段同时发生，浏览器就会很忙。用户感知到的结果就是：页面不是完全打不开，而是“已经出来了，但还不够顺”。

遇到这种说不清道不明的卡，我的做法是别瞎猜，直接上工具。Performance 面板录一段操作，重点看主线程那条 Main 轨道：黄色是 Scripting（JS 执行），紫色是 Rendering（样式计算和布局），绿色是 Painting。哪段最长就先治哪段。如果看到右上角有红色三角的“Long Task”（超过 50ms 的任务），那基本就是卡顿来源。另外右键某个 Layout 事件，它会标红提示是不是 forced reflow，并直接指到触发它的那行代码——我前面那个 offsetTop 的坑就是这么定位出来的。

平时还可以打开 Rendering 面板里的 “Paint flashing”，凡是重绘的区域会闪绿色。有时候你以为只改了一个小角标，结果半屏都在闪，那说明重绘范围被无意中放大了，通常是合成层没分好。

理解渲染流程后，很多优化建议才不再像口诀

比如我们经常听到这些说法：

  • 减少不必要的 DOM 读写
  • 避免一次性渲染过多内容
  • 控制首屏脚本体积
  • 关键内容优先展示

如果不知道浏览器中间经历了什么，这些话很容易停留在口号层。可一旦知道页面从解析到绘制并不是一步完成，你就更容易明白：为什么某些代码会拖慢首屏，为什么某些滚动交互会引起卡顿，为什么一些看似很小的组件初始化叠在一起也会产生明显成本。

框架帮你管理更新，但不会绕开浏览器成本

很多人学了框架以后，会自然把注意力集中在组件、状态和路由层。可无论你用什么框架，最后页面还是要落回浏览器去解析、布局和绘制。

也就是说，框架可以帮你组织更新，但不能凭空消除这些问题：

  • 一次渲染内容太多
  • 页面加载后同步执行太多工作
  • 动态样式和布局反复变动
  • 高频交互下主线程过忙

所以前端理解渲染过程，不是为了和框架对立，而是为了知道框架之外还有一层更底的现实约束。

真正稳定的页面，通常是“先保证内容出来，再逐步增强”

这也是我后来越来越认可的一个方向。对很多内容页、后台页和信息展示页来说，用户最先需要的是看见主要内容，而不是所有交互立即全部到位。

如果能先把关键结构和主要数据稳定展示出来，再逐步挂载不那么关键的能力，页面体验通常会更稳。这种思路说到底，就是在顺着浏览器渲染的节奏做取舍，而不是一上来就要求所有东西同时完成。
