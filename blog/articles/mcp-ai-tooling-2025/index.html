MCP 与 AI 工具生态：给 AI 助手接内部系统，胶水代码写到第三套之前

2025-07-26
AI构建与模块化

给内部 AI 助手接第三个系统之前，我先把前两个系统的胶水代码翻出来数了数行数：订单查询接入用了四百多行，库存查询用了三百多行。

这次要接的是售后工单系统，照这个节奏又是小四百行。而这些代码除了"把一个内部接口包装成模型能调的工具"，没有任何业务价值。

更麻烦的是乘法。上半年团队里冒出了第二个要用工具的 AI 场景：除了运营侧的问答助手，值班同学希望在排查工具里也能让 AI 直接查订单状态。同一个订单查询，两个 AI 应用各接一遍，胶水代码翻倍。

三个系统乘两个应用，六份胶水。每次接口改字段，六个地方都要跟着动，漏一个就是一处不一致。这笔账摆在面前，第三套胶水我不太想再照原样写了。

接入成本随"系统数 × AI 应用数"增长的时候，缺的不是更快的写胶水速度，是一个标准接口。

这也是我这两个月认真看 MCP（Model Context Protocol）的原因。它是 Anthropic 去年十一月发布的协议，到现在大半年，生态肉眼可见地在快速长。

这篇记一下我们拿售后工单系统做的试点：写一个最小的只读 MCP server，权限和审计怎么做，以及过程里想明白的几个取舍。

此前的做法：每接一个系统，写一套 function calling

先交代一下"胶水代码"具体指什么，不然四百行听起来像是我写得啰嗦。

模型本身只会输出文本。所谓工具调用（function calling），是你在请求里声明一批工具的名字、用途和参数 schema，模型决定要调哪个、给什么参数，把这个意图以结构化形式吐回来，真正执行的是你的代码。

参数校验：模型给的参数不能直接信，格式、范围、注入都要防。

返回结果的裁剪：订单接口吐八十多个字段，全塞给模型又贵又乱，要挑十来个有用的。

错误映射：接口超时、订单不存在、无权限，各自要变成模型能理解的文本，不能把一个裸的 500 扔回去。

四百行就是这么来的。单独看每一层都不难，问题在于这套东西和具体的 AI 应用绑死了。运营助手用的是我们自己封装的对话服务，工具声明的格式、分发的写法都长在那个服务里；值班排查工具是另一个代码库，接同一个订单查询，上面这些只能再抄一遍改一遍。

抄的时候两边的 schema 还会慢慢漂移。六月就出过一次：订单接口加了"逆向状态"字段，运营助手这边同步了，排查工具那边忘了，值班同学查出来的信息就比运营的少一截，还以为是接口有问题，白排查了半小时。

MCP 解决的是哪一层问题

MCP 做的事情说穿了很朴素：把"AI 应用"和"工具提供方"之间的连接标准化。

工具提供方写一个 MCP server，声明自己有哪些工具；AI 应用侧只要实现了 MCP client，就能连上任何一个 server，列出工具、发起调用。协议底层是 JSON-RPC，传输方式本地进程用 stdio，远程服务用 HTTP。

类比一下，以前是每个显示器配自己的专用接口，现在大家统一 HDMI——server 写一次，接多少个 AI 应用都是这一份。

对我们的场景，这意味着乘法变加法：三个系统写三个 MCP server，两个 AI 应用各接一次 client（而且 client 侧多数框架和产品已经内置了），六份胶水变成三份，schema 只有一个权威来源，不存在两边漂移。

值得说清楚的是，MCP 没有改变模型调工具的方式。模型看到的还是工具名、描述、参数 schema 那一套，function calling 的机制原样还在。MCP 标准化的是工具怎么被发现、被描述、被接入，是接入层的协议，不是模型能力的变化。理解成"给 function calling 修了条标准公路"，比理解成"新的 AI 能力"更准确。

顺带把协议里的几类原语交代一下，读文档时容易被名词绕住。MCP server 能暴露三种东西：tools（模型可以主动调用的操作）、resources（应用可以读取的数据，比如一份文档、一条配置）、prompts（预置的提示词模板）。我们的试点只用了 tools——对"让模型查订单"这个场景，另外两类暂时用不上，但知道它们存在，看别人的 server 代码时不至于迷路。

顺手还在 CI 里加了个冒烟测试：用 SDK 的 client 把 server 拉起来，listTools 的结果和仓库里的快照比对，工具名、参数 schema 有变化就挂掉，逼着改动的人显式更新快照。工具声明现在是跨应用的契约，契约变更就该有这种最起码的守门。

server 侧的测试反而是最常规的部分——handler 就是普通的异步函数，单测直接调，不需要真起协议层。这也是 MCP 让我觉得舒服的地方之一：协议归协议，业务归业务，两层能分开验证。

我们自己的对话服务里则是用 SDK 的 client 连上去，启动时 listTools 拿到工具列表拼进模型请求，模型要调用时转发给 server。这部分是一次性的基础设施，写完之后接第 N 个 server 都不用再动。

部署方式我们分了两档。开发调试用 stdio，server 就是个本地子进程，改完代码重启就生效；正式环境把 server 用 streamable HTTP 起在内网，挂到网关后面，两个 AI 应用远程连——工具提供方（比如售后工单是别的组维护的）只需要维护这一个服务，不需要把代码分发给每个消费方。

有两个实现细节是从 function calling 时代原样搬过来的经验，换了协议也一样成立。

一是参数校验不能省。模型生成的参数要当用户输入对待，zod 的 schema 在这里同时干两件事：给模型看（SDK 会把它转成 JSON Schema 放进工具声明）和在执行前真的校验一遍。订单号那个正则不是摆设，试点第一天模型就试图拿一个带横杠的工单号来查订单。

二是返回内容要裁剪。工具返回的每个字节都会进模型的上下文，又占窗口又花钱，而且敏感字段一旦进了上下文，你就没法控制模型会不会把它复述给用户。收货人手机号、身份证这类字段，在 pickOrderSummary 里直接脱敏或者剔除，不要指望在 prompt 里叮嘱模型"不要透露"。

工具描述是写给模型看的接口文档

还有一件事，做的时候才体会到分量：工具的 description 不是注释，是模型决定"调不调、怎么调"的唯一依据，值得像写接口文档一样认真。

试点初版的描述就一句"查询订单"。跑起来发现两个问题：用户拿售后单号来问，模型也拿去调这个工具（参数校验挡住了，但白白多了一轮失败调用）；用户问"我的订单怎么还没发货"，模型有时不调工具，直接凭空安抚一句"请耐心等待"。

两类坏案例都明显收敛。模型选工具选得准不准，一半取决于描述写得清不清楚——什么时候该用、什么时候不该用、参数长什么样，都要明说。这个经验在 function calling 时代就成立，MCP 把工具声明变成跨应用共享之后，描述的质量影响的就不止一个应用了，更值得花功夫。

工具多起来之后还有个隐性成本：每个工具的声明都会占用模型请求的 token，接的 server 多了，光工具列表就是几千 token 的固定开销，而且工具越多模型选错的概率越高。所以 client 侧接 server 不是越多越好，按场景挑着接——排查工具只连 order-query 和日志查询，运营助手多连一个库存，各取所需。

权限与安全边界：只读起步，全量审计

把内部系统的入口交给一个由模型决定怎么调的通道，安全上要保守。我们给试点定的几条边界，写出来供参考。

第一，只暴露只读操作。查询可以，改地址、退款、关闭工单这类写操作一概不上。不是协议做不到，是现阶段我们没法给"模型误操作"兜底——查错了顶多答错一句话，改错了就是资损。写操作要上，也得等只读跑稳、并且设计好人工确认环节之后再说。

第二，server 用独立的服务账号，权限最小化。给 order-query 这个 server 申请的账号只有订单读接口的权限，拿不到用户中心、拿不到营销系统。哪怕哪天 server 本身被打穿，爆炸半径也就这么大。

第三，每一次调用都落审计日志：哪个 AI 应用、代表哪个用户、什么时间、调了什么工具、参数是什么、返回摘要是什么。实现上就是给所有工具的 handler 包一层：

这份日志上线两周已经派上用场。运营反馈某个答案不对，顺着日志能直接看到那次会话查了哪个订单、拿到了什么，是查错了还是答错了，一目了然。这和我做 RAG 时"把召回结果落日志"是同一个道理：AI 链路上每个环节的输入输出都要可回放，不然出了问题只能靠猜。

第四，加速率限制。模型偶尔会抽风式地连环调用同一个工具——一次会话里连查十几个订单号挨个试。给 server 按"每会话每分钟"设了个很宽松的上限，正常使用碰不到，异常行为能兜住，也顺便保护了背后的订单接口不被 AI 流量打出毛病。

第五，工具描述本身也是攻击面。MCP 生态里已经有人在讨论"工具投毒"：一个恶意 server 可以在工具描述里夹带指令，诱导模型做不该做的事。内部自己写的 server 没这个问题，但如果引入社区的第三方 server，描述文本要当不可信输入审一遍，来源不明的直接不用。

和直接 function calling 的取舍

试点做完，我的结论不是"以后都上 MCP"，这笔账要按场景算。

如果你只有一个 AI 应用、接两三个工具，而且可预见的未来不会有第二个应用来复用，直接 function calling 更简单：没有额外的进程或服务要部署，没有一层协议要理解，调试链路短。MCP 在单应用少工具的场景下是纯开销，标准化的收益要有复数个消费方才能兑现。

反过来，出现下面任何一个信号，就值得切。

同一个工具要被第二个 AI 应用使用——这是最直接的信号，我们就是被它推过来的。

工具的维护方和 AI 应用的维护方不是同一拨人。售后工单系统是别的组维护的，让他们自己维护一个 MCP server、按自己的节奏发版，比教他们改我们对话服务的代码合理得多。接口的字段口径也顺势变成了 server 维护方的责任，出了歧义找一个人，不用三方扯皮。

想直接复用社区已有的 server。GitHub、PostgreSQL、浏览器自动化这些常用能力都已经有现成实现，配置一段就能用，这部分是白捡的。

另外有一点降低了决策压力：从 function calling 迁到 MCP，业务逻辑几乎原样搬家。server 的 handler 里面装的就是原来 queryOrder 那套鉴权、校验、裁剪、错误映射，变的只是外面那层壳——工具声明从对话服务的私有格式换成 MCP 的标准格式。所以先用 function calling 起步、等出现复用需求再切 MCP，不算走弯路，前期投入基本都能带走。

也要说一句代价。多一跳进程间通信，本地 stdio 的开销可以忽略，远程 HTTP 的就要算进延迟预算；排查问题时链路多了一段，client 和 server 各有各的日志，得把 trace 串起来。另外工具调用本身的错误处理——超时重试、模型拿到错误之后的行为、失败降级——不管走不走 MCP 都躲不掉，这个话题水很深，值得单独写一篇，这里不展开。

生态现状：长得很快，但还在长

最后记一下 2025 年 7 月这个时间点的观察，半年后再看大概会变样。

client 侧的支持已经不是问题。Claude 的桌面端、主流的 AI 编辑器、各家 agent 框架基本都内置了 MCP client，连隔壁几家大厂的产品线今年也陆续宣布了兼容。协议能不能成事，关键看消费方数量，这一点上它已经过了最悬的阶段。

server 侧是另一番景象：数量爆炸，质量参差。社区列表里 server 几千个，但很多是练手作品，参数校验、错误处理、权限设计一概没有。

挑第三方 server 的标准，我现在看三样：官方或者知名组织维护、有真实的版本迭代记录、README 里认真写了权限说明。三样占不齐的，宁可自己写——反正如这篇所示，写一个也就百来行。

协议本身也在补课。今年上半年规范把远程传输从原来的 SSE 方案换成了 streamable HTTP，远程鉴权的 OAuth 规范也在今年的版本里补了进来。这些动作说明远程部署、跨组织共享 server 这条路是官方认真在铺的，但也说明现在入场要有"规范还会动"的心理预期——我们试点期间就升过一次 SDK，改了几处 API 调用。

发现机制也还是个空白。现在找社区 server 靠的是几个人肉维护的 awesome 列表，官方的 registry 还在酝酿中。这对内部使用反而不算问题——我们在内部 wiki 上开了一页表格，登记每个 server 的地址、维护人、暴露的工具和权限级别，土办法，但对三五个 server 的规模绰绰有余。真长到几十个的时候，再考虑要不要做个像样的内部注册中心。

版本管理值得提前想。server 是独立发版的，工具的参数 schema 改了，正在运行的 client 那边不会自动知道。我们目前的约定很保守：工具只加可选参数、只加返回字段，不改名不删字段，破坏性变更就发一个新工具名（比如 query_order_v2），旧的留一个过渡期。听起来和管 REST 接口一模一样——本来也就是同一件事。

内部生态倒是先热起来了。order-query 跑通之后，隔壁组看了审计日志的演示，主动来问库存系统能不能也包一个 server。这大概是标准化最舒服的时刻：不用推销，别人看见收益自己就来了。

回到开头那笔账。售后工单的接入最后花了两天：server 一天（大半时间在和维护方对字段口径），两个 AI 应用接入合计半天，剩下半天写审计日志和冒烟测试。

四百行胶水的预算，实际付掉的是一份百来行的 server 加一套一次性的基础设施。第四个系统再来的时候，连基础设施这部分都省了——那六份胶水的乘法，总算改写成了加法。
