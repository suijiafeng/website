INP 成为核心指标之后，前端性能优化不能只盯首屏了

2025-05-27
前端基础性能与缓存

前端性能过去很长一段时间都喜欢盯首屏。

页面多久能看到内容，图片是不是懒加载，JS 包体积是不是太大，LCP 有没有优化。这些当然重要，但用户真正使用一个页面时，不只是“看到”，还要“操作”。

按钮点下去没反应。

输入框打字卡顿。

筛选条件切换后页面像停住一样。

菜单打开慢半拍。

这些体验不一定会反映在传统首屏指标里，却非常影响用户对系统的判断。INP 被纳入核心性能指标之后，前端性能优化的重点也被迫往交互阶段移动。

INP 关心的是什么

INP 可以粗略理解为：用户和页面交互时，页面响应得够不够快。

它关注点击、键盘输入、触摸等交互，从用户触发事件，到浏览器有机会绘制下一帧之间的延迟。这个指标背后真正想衡量的是：页面是不是忙到没空回应用户。

一个页面首屏很快，不代表 INP 好。比如后台系统首屏秒开，但表格一筛选就卡 800ms，用户仍然会觉得难用。

INP 让我们重新面对一个事实：性能不是加载完成就结束了，交互过程也是性能的一部分。

最常见的问题：主线程太忙

浏览器里很多事情都要占用主线程：

  • 执行 JavaScript
  • 处理事件回调
  • 计算样式
  • 布局
  • 绘制前准备

如果用户点击按钮时，主线程正在跑一段很重的 JS，交互就会延迟。

React 项目里的交互卡顿

React 项目里，INP 差经常和不必要的重渲染有关。

如果 filterLargeList 很重，BigTable 渲染也重，用户每输入一个字都会卡。

可以先做几件朴素的事：

  • 把输入框状态和重列表状态解耦
  • 给昂贵计算加 useMemo
  • 给低优先级更新加过渡
  • 避免无关组件跟着重渲染

这类优化不是为了让代码显得高级，而是为了把“用户正在输入”这件事和“列表慢慢更新”这件事分开。用户输入应该优先被响应，列表更新可以稍微晚一点。

第三方脚本也会拖慢交互

很多页面 INP 差，不完全是业务代码造成的。

埋点、客服插件、广告、A/B 测试、监控 SDK，都可能在用户交互时占用主线程。尤其是一些脚本会在页面加载后继续做初始化、扫描 DOM、绑定事件，用户刚开始操作时正好撞上。

排查时不要只看自己的 bundle。Chrome Performance 面板里如果看到长任务来自第三方脚本，就要评估：

  • 是否必须首屏加载
  • 能否延迟到用户空闲时加载
  • 是否只在特定页面启用
  • 是否有更轻量的配置

性能优化不是只优化业务代码，也要管理页面上所有会执行的代码。

测量不要只靠本地感觉

本地开发机通常很快，网络也稳定。你觉得“点起来挺顺”，不代表真实用户顺。

INP 更需要真实用户监控。实验室工具能帮你发现明显长任务，但真实用户的设备、浏览器、数据量和操作路径差异很大。

平均值最容易骗人。少数用户在低端设备上卡得很严重，平均值可能仍然看起来不错。性能指标要看分位数，尤其是较差用户的体验。

优化顺序

我现在排查交互性能，一般按这个顺序：

  1. 找出最差的页面和交互
  2. 用 Performance 面板看长任务
  3. 区分 JS 计算、渲染、布局和第三方脚本
  4. 先处理高频交互，再处理低频场景
  5. 优化后用真实数据验证

不要一上来就全站做微优化。INP 关注用户交互，最重要的是找到用户真的会频繁触发、并且确实慢的操作。

比如后台系统里，筛选、搜索、分页、展开详情、保存表单，通常比某个隐藏设置页的动画更值得优先优化。

我自己的感受

INP 让前端性能讨论变得更接近真实使用。

以前我们很容易把页面优化成“打开很快”，但打开之后操作重不重，常常缺少统一指标。现在交互延迟被放到核心位置，很多以前被忽略的代码习惯都会暴露出来：事件里做大计算、列表无脑全量渲染、状态提升过度、第三方脚本随便堆。

这对前端开发是好事。因为真正的体验不是 Lighthouse 分数，而是用户每一次点击和输入有没有被认真对待。

延伸阅读

推荐看 web.dev 关于 INP 的系列文章、Chrome Developers 的性能调试指南，以及 React 官方文档里关于 useTransition、memo 和渲染优化的内容。把浏览器性能和框架渲染放在一起看，才能真正理解交互卡顿来自哪里。

写在最后

INP 提醒我们，性能优化不能只停在首屏。

一个页面加载很快，但用户点不动、输不顺、筛选卡，它仍然不是一个性能好的页面。2025 年之后，我会更倾向于把性能分成两段看：加载阶段让用户尽快看到内容，交互阶段让用户每一步操作都得到及时回应。前者决定第一印象，后者决定用户愿不愿意继续用。
