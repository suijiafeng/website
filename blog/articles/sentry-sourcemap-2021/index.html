SourceMap 还原线上报错：从压缩堆栈到可读源码的完整链路

2021-02-20
前端基础构建与模块化

去年团队把前端错误监控搭起来之后，Sentry 后台每天都能收到几十条报错，采集这一层算是跑通了。但真正拿着报错去修 bug 的时候，才发现事情只做了一半：点开一条 TypeError，堆栈长这样——

TypeError: Cannot read property 'id' of undefined
  at r (https://cdn.example.com/js/app.8f3c2d.js:1:183940)
  at Object.n [as handler] (https://cdn.example.com/js/app.8f3c2d.js:1:97335)
  at HTMLButtonElement.<anonymous> (https://cdn.example.com/js/chunk-vendors.4a1be0.js:1:412208)

函数名叫 r，文件只有一行，列号十八万。这条报错等于没报。要把它还原成“src/views/order/detail.vue 第 142 行”，中间横着一整条链路：构建时生成 SourceMap、选对 devtool、把 map 文件安全地送到 Sentry、保证版本对齐、再把 map 从公网撤下来。

**采集是一次性接入，还原是每次发布都要走的流程，成本全在后面这一段。**这两周我把这条链路完整趟了一遍，把每一步的取舍和踩过的坑都记下来。

压缩堆栈为什么读不了

先把问题本身说清楚。我们生产构建走的是 webpack 4 + terser，压缩做了三件事：变量和函数改成单字母短名、多个模块合并进一个文件、删掉所有换行把代码压成一行。

浏览器抛错误时，堆栈里的位置信息是“压缩后文件的行列号”，所以你看到的永远是 xxx.js:1:183940——第 1 行没有意义，因为整个文件就一行；列号 183940 也没法直接对回源码，因为压缩后的第 183940 列可能对应源码里任何一个位置。

SourceMap 就是这个映射表。它是一个 JSON 文件，核心字段有这么几个：

sources 是参与打包的源文件列表，sourcesContent 是这些源文件的完整内容（可选，但对错误监控很关键，后面会提），names 是被压缩掉的原始标识符，mappings 是一串 Base64 VLQ 编码的位置映射——人读不了，工具能读。构建时 terser 每做一次改名、每合并一行，都把“压缩后位置 → 源文件位置 → 原始变量名”的对应关系记进去。

拿到 map 文件，app.8f3c2d.js:1:183940 就能翻译回 src/utils/request.js:57:12，连函数原名都能还原出来。整条链路后面所有的环节，本质上都是在回答一个问题：怎么让 Sentry 在收到报错的那一刻，手里正好有正确的那份 map。

本地开发时我们感受不到这个问题，因为 Chrome DevTools 会自动加载 devtool 生成的 SourceMap，断点和报错都直接显示源码。

线上的区别在于：map 文件不能随手扔在 CDN 上让浏览器加载，但错误监控平台又必须拿到它——矛盾就在这里，整条链路都是围绕这个矛盾展开的。

devtool 的取舍：为什么是 hidden-source-map

webpack 的 devtool 选项有十几个值，名字是由 eval、cheap、module、inline、hidden、nosources 这几个词组合出来的。

之前我一直是开发环境 cheap-module-eval-source-map、生产环境干脆不开，这次趁机把这几个词的语义理了一遍。

eval 指模块用 eval() 包裹执行、map 以 DataURL 附在 eval 内容后面，重新构建快，只适合开发。cheap 指映射只精确到行、不精确到列，体积小、生成快，代价是列号信息丢失。

module 指映射穿透 loader，直接对到 babel 处理之前的手写源码——没有这个词，你还原出来的是 babel 编译后的中间代码。inline 指 map 以 DataURL 内联进 bundle 本身，产物体积暴涨，生产环境绝对不能用。这几个词是可以组合的，理解了单词的含义，十几个选项就不用死记了。

这里有一层容易忽略的连带关系：错误监控要求的映射质量是最高档的。cheap 系列丢掉列号，而压缩产物只有一行，全靠列号区分位置，丢了列号等于什么都没还原；不带 module 的档位还原到的是 babel 中间产物，.vue 文件里的模板和 script 对不回去。所以给 Sentry 用的 map 必须是完整档——精确到列、穿透 loader，能砍的只有“要不要带 sourcesContent”和“要不要暴露给浏览器”这两个维度。

按这套语义过滤，生产环境的候选其实只剩三个。第一个是 source-map：生成独立的 .map 文件，映射精确到列、穿透 loader，并且在 bundle 末尾追加一行 //# sourceMappingURL=app.8f3c2d.js.map 注释。浏览器 DevTools 看到这行注释就会去同目录下请求 map 文件。问题也在这行注释——只要 map 文件还在服务器上，任何人打开 DevTools 都能看到完整源码，等于把 src 目录公开了。

第二个是 hidden-source-map：生成的 map 文件和 source-map 完全一样，唯一区别是 bundle 末尾不加那行注释。浏览器不知道 map 的存在，不会主动请求；但 map 文件本身是完整的，交给 Sentry 照样能还原。这正是“我要 map，但不想让浏览器要 map”这个需求的精确解。

第三个是 nosources-source-map：map 里保留行列映射和文件名，但去掉 sourcesContent。堆栈能还原出文件名和行号，但 Sentry 界面上看不到出错那一行的代码上下文。如果团队对源码泄露极度敏感、连错误监控平台上都不想存源码，可以用它，代价是排查时只能对着行号回本地代码库翻，还得先 checkout 到对应版本的 commit。

我们内部讨论后觉得没必要——Sentry 是私有部署在内网的，源码存在上面和存在 GitLab 上风险等级一样，最终选了 hidden-source-map：

顺带纠正一个我自己之前的误区：有人担心生产开 SourceMap 会拖慢页面。实际上 map 文件只有在 DevTools 打开且需要还原时才会被浏览器请求，正常用户访问根本不会下载它，对运行时性能是零影响。开销只在构建时间和产物体积上——我们项目全量构建从两分半涨到三分十秒，map 文件加起来 40 多 MB，这是要付的成本。

40 MB 听起来吓人，其中 30 MB 是 chunk-vendors 的，业务代码的 map 只占零头。有同事提议只给业务 chunk 生成 map 省时间，但 vendor 里的报错（尤其是 Element UI 内部和 axios 拦截器里抛出来的）恰恰是最难裸眼定位的，这个成本我们认了。

开发环境顺带也重新定了：eval-cheap-module-source-map。开发时报错和断点主要看行，列号可以牺牲换构建速度，module 保住 loader 穿透（不然 .vue 文件断点会对不上位），eval 让增量重建足够快。开发和生产各取所需，两个档位从此写死在配置里，不再每个项目各拍各的。

把 map 交给 Sentry，而不是交给公网

链路的核心一步：构建完成后，用 sentry-cli 把 map 文件上传到 Sentry 服务端。Sentry 收到报错事件时，用事件里携带的 release 版本号找到对应那批 map 文件，在服务端完成还原，前端页面上不需要任何 map 的存在。

还原发生在 Sentry 服务器上，不发生在用户浏览器里，这是整个安全模型成立的基础。

我最初用的就是插件，跑了两周还是换回了 CLI 脚本。插件把“构建”和“上传”绑死在一个进程里，Sentry 服务偶尔抖一下整个构建就失败，构建机上重跑一次是十分钟；拆成 CI 里的独立步骤后，上传失败可以单独重试那一步，构建产物还在。

另外插件在本地开发者手动执行生产构建时也会尝试上传（除非小心地用环境变量圈住），我就误传过一次本地构建的 map，污染了一个正式 release 的 artifacts。CLI 脚本天然只存在于 CI 流程里，不会误触发。这不是说插件不能用，而是它适合“构建即发布”的简单流水线；我们的发布有审批和灰度环节，构建和发布本来就是分开的两步，上传跟着发布走更贴合。

release 和 dist：版本对齐是还原的前提

Sentry 还原堆栈的匹配逻辑是：事件里的 release 字段 + 堆栈里的文件 URL，去找同 release 下同名的 artifact。所以 SDK 初始化时上报的 release，必须和 sentry-cli 上传时的 release 一字不差：

VUE_APP_VERSION 在构建时从 package.json 注入，CI 脚本里的 RELEASE 变量也从 package.json 读，保证两边是同一个源头。一开始我在 SDK 里写的是 git commit hash、CI 脚本里用的是 package 版本号，两边对不上，上传得再勤快也白搭——Sentry 界面上 map 明明在，堆栈就是不还原，查了半天才发现是这个低级错位。

release 的命名里加了项目名前缀（admin-console@），因为 Sentry 的 release 在 org 层面是共享命名空间的，光写 1.4.2 会和别的项目撞名。这个前缀约定后来推给了所有接入 Sentry 的项目。

release 之下还有一层 dist。如果同一个 release 会产出多份不同的构建产物——比如同一版本号分别打了国内版和海外版，文件名还相同——就需要用 dist 区分开，SDK 的 dist 字段和 upload-sourcemaps --dist 参数对应，匹配 artifact 时两个字段都要命中。

我们目前一个版本只有一份产物，这个字段暂时用不上，但多渠道打包的项目绕不开它。知道这一层的存在，将来排查“map 明明传了却匹配不上”时能少排除一个变量。

**版本对齐还有一个隐蔽的时间维度：上传必须发生在部署之前。**如果先把新 bundle 推上 CDN、用户已经开始触发报错，map 却还在上传队列里，这段窗口期的报错永远还原不了——事件进来时 Sentry 找不到 artifact，是不会等 map 到了再回头重新处理的。所以发布脚本的顺序固定为：构建 → 上传 SourceMap → 部署静态资源 → 切流量。这个顺序写进了发布文档，谁也不许调。

release 建好之后还有一个不花钱的增值项：把这个版本包含的 git 提交也关联上去。

--auto 会从当前仓库读取上一个 release 到现在的提交范围。关联之后，Sentry 在展示一条新报错时会顺带列出“这个版本里改动过出错文件的提交”，谁的提交嫌疑最大一目了然。这功能的前提恰恰是堆栈已经还原到了源文件路径——没有 SourceMap，它连出错文件是哪个都不知道，又是一个链路环环相扣的例子。

上传之后：把 map 从发布目录删掉

hidden-source-map 只是不让浏览器主动请求 map，文件本身还是跟着 dist 目录一起生成的。如果发布脚本无脑把整个 dist 推上 CDN，那么知道文件名规律的人手动拼 app.8f3c2d.js.map 照样能下载到完整源码——hidden 挡的是“自动发现”，挡不住“主动猜测”。文件名里的 hash 也不构成保护，bundle 的 URL 在页面源码里是公开的，加个 .map 后缀就是 map 的地址。

权衡之后还是选了最笨也最可靠的做法：**map 只存在于两个地方——CI 的构建产物（发布后即焚）和 Sentry 的 artifact 存储，公网上一个字节都不留。**真需要本地对着线上产物调试时，从 CI 的构建归档里把对应版本的 map 下载下来，用 DevTools 的“Add source map”手动挂载，麻烦一点，但一年用不了几次。

岔出去一步：堆栈本身进不来的情况

排查还原问题的过程中还捞出来一个前置问题，跟 SourceMap 无关但顺手记上。Sentry 里长期有一类报错只有一句 Script error.，没有堆栈、没有行列号，map 传得再对也没用——因为浏览器压根没把错误信息给出来。

这是浏览器的跨域保护：脚本从 CDN 域名加载、页面在业务域名上，跨域脚本抛出的错误默认只暴露 Script error. 这一句，防止页面探测第三方脚本的内部信息。

解法是两边配合——script 标签加 crossorigin="anonymous"，CDN 对 js 文件返回 Access-Control-Allow-Origin 响应头，两个条件都满足，完整的错误消息和堆栈才会交给页面：

Vue CLI 有现成的 crossorigin 配置项可以给注入的 script 统一加上，CDN 那边的响应头找运维加了一条规则。**还原链路的第零环是让堆栈完整地进来，crossorigin 没配对，后面所有环节都是空转。**这批 Script error. 处理完之后，Sentry 里可还原的事件比例明显上了一截。

还原失败的排查清单

链路搭好之后并不是一劳永逸，这两周实际跑下来，遇到过三次“map 传了但堆栈还是压缩态”，原因各不相同，值得逐个记下来。

第一类是 release 错位。前面提过一次 SDK 和 CLI 版本号来源不一致的坑，还有一个变体更阴险：热修复。有次线上出问题，同事改了两行代码直接重新构建部署，版本号没动——于是 CDN 上的 bundle 换了，Sentry 里存的还是上一次构建的 map。文件名里的 hash 倒是变了，按说匹配不上会直接放弃还原，但坏就坏在那次改动没影响到某个 chunk，那个 chunk 的 hash 没变、内容行列却因为公共模块的变化而移位了——还原“成功”了，但指向的源码位置是错的，比不还原更有误导性。

**堆栈还原出来的位置驴唇不对马嘴时，第一反应应该是怀疑线上产物和 map 不是同一次构建出来的。**后来我们约定任何重新构建都必须递增版本号，哪怕只是 patch 位，release 数量多一点无所谓，错位一次就够查一下午。

第二类是路径不匹配。Sentry 匹配 artifact 用的是堆栈里的文件 URL，--url-prefix '~/js' 里的 ~ 是通配协议和域名的意思，也就是说上传后 artifact 的键是 ~/js/app.8f3c2d.js.map。如果实际页面加载的是 https://cdn.example.com/static/js/app.8f3c2d.js，中间多了一层 /static，键就对不上，Sentry 直接放弃还原，界面上连个报错都没有。

排查办法是在 Sentry 的 release 页面看 artifacts 列表，把里面的路径和报错事件里堆栈的 URL 逐段比对——我们第二次翻车就是运维调整了 CDN 目录结构，前端这边没人知道，直到某天的新报错全部变回了压缩态才发现。这之后我在 CI 里加了一步冒烟检查：部署完成后拉一次线上页面，grep 出实际的 js 路径前缀，和上传脚本里的 url-prefix 做一次断言，对不上直接让流水线红掉。

第三类是 map 本身残缺。terser-webpack-plugin 如果没开 sourceMap: true，devtool 生成的映射会在压缩阶段断链——map 文件是有的，但映射到的是压缩前的中间产物，不是手写源码。Vue CLI 的默认配置已经处理好了这一环，但我们有个老项目是手写的 webpack 配置，自己加 terser 时就漏了这个参数，还原出来的“源码”是 babel 编译后的样子，var 和 _interopRequireDefault 满天飞。

这类问题的通用检查方法很直接：本地拿 source-map 这个 npm 包写个小脚本，输入压缩产物的行列号，看能不能吐出正确的原始位置：

先在本地验证 map 的质量，再去怀疑 Sentry 的配置，这个顺序能省掉大量在平台界面上瞎点的时间。如果这个脚本吐出来的位置就是错的，那问题在构建链路；位置对而 Sentry 上不对，问题才在上传和匹配环节。这个十几行的小脚本后来被我放进了脚手架仓库，配合一份“还原失败先查这四条”的排查笔记。

第四类严格说不算失败，但容易被当成失败：sourcesContent 缺失。有些构建配置生成的 map 里 sources 只有路径没有内容，Sentry 能还原出文件名和行号，但代码上下文那一栏是空的，看起来像是“还原了一半”。--rewrite 参数大部分时候能自动补全，补不全的检查 webpack 配置里是不是有 loader 把 sourcesContent 剥掉了。

链路跑通之后

昨天下午又进来一条报错，这次点开是这样的：

TypeError: Cannot read property 'id' of undefined
  at getOrderOwner (src/views/order/detail.vue:142:31)
  at VueComponent.handleAssign (src/views/order/detail.vue:98:24)

第 142 行，order.buyer.id，buyer 在订单被后台作废后是 null，Sentry 界面上连出错行前后五行的代码都直接展示出来了，set-commits 关联的提交列表里，引入这行代码的提交排在第一个。从看到报错到定位原因不到两分钟，修复加发布半小时。

同一类问题在一月份出现过一次，当时对着 app.js:1:183940 猜了一下午没猜出来，最后是靠找到那个用户要了操作录屏才复现的。前后对比就是这条链路的价值。

这条链路上没有任何一步是难的——devtool 一行配置、sentry-cli 几条命令、CI 里一段脚本——难的是把每一环的对齐关系想清楚：release 两端一致、上传先于部署、路径前缀和线上 URL 吻合、map 不落公网、产物和 map 出自同一次构建。开头说采集只是做了一半，现在这另一半算是补上了：报错不但能进来，进来了还能读。
