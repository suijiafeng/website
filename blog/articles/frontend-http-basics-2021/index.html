前端为什么也要懂 HTTP：请求能发出去，不代表你真的理解通信

2021-06-21
前端基础

做前端久了会发现，很多问题表面看像页面 bug，实际往下挖都和 HTTP 通信细节有关。

接口为什么返回 304，为什么跨域失败，为什么表单提交和 JSON 请求表现不同，为什么缓存策略会影响页面更新，这些都说明前端并不只是“把请求发出去”就够了。

理解 HTTP，不是为了转行后端，而是为了更稳地处理前后端协作边界。

先看清一条请求长什么样

在讲方法和状态码之前，得先知道一个 HTTP 请求/响应到底由哪几块组成，否则 DevTools 里那一堆字段你不知道在看什么。一个请求报文就三部分：请求行（方法 + 路径 + 协议版本，比如 GET /api/list?page=1 HTTP/1.1）、若干请求头、一个空行、然后是可选的请求体。响应也对称：状态行（HTTP/1.1 200 OK）、响应头、空行、响应体。头和体之间那个空行是强制的分界符，GET 通常没有 body，POST/PUT 才把数据放在 body 里。

理解这个结构有个实际好处：你就明白为什么 Content-Type、Content-Length 这些都在头里，而真正的数据在体里——头是“元信息”，描述这次传输该怎么解析；体才是 payload。后面所有关于缓存、跨域、上传的坑，本质都是头没配对。

请求方法不只是名字不同

最常见的请求方法当然是 GET 和 POST。

很多项目里大家会形成一种朴素印象：

  • GET 用来拿数据
  • POST 用来提交数据

这个理解没错，但如果只停在这一步，很多接口设计和调试细节就会看不清。

我自己印象最深的一次坑，是做一个商品搜索页。当时把筛选参数都拼在 GET 的 URL 里，本地测试一切正常，上线后却时不时出现“筛选条件变了但列表没变”的反馈。查了半天才发现是 CDN 和浏览器把这个 GET 请求缓存了——因为 GET 在语义上被认为是安全且幂等的，中间任何一层代理都有理由把它缓存起来。后来我们要么给 URL 带上时间戳打破缓存，要么对真正不该缓存的查询改用 POST。这件事让我第一次意识到：方法的选择不是个人偏好，它会被整条链路上的缓存、代理、日志系统按照语义去“理解”。

幂等性这个概念也是后来才真正体会到的。GET、PUT、DELETE 在规范里都是幂等的——同样的请求发一次和发十次，服务端最终状态应该一样。而 POST 不是。这意味着如果一个“创建订单”的接口用 POST，那网络抖动时的自动重试就很危险，可能创建出两个订单；如果改成 PUT 并由前端生成一个唯一 id 作为资源标识，重试就安全得多。所以我现在看到一个“更新”接口，会先问后端到底是整体替换（PUT）还是局部修改（PATCH），这直接决定我前端要不要把整个对象都传上去。

至于参数放 URL 还是放请求体，也有现实约束。URL 长度在很多服务器和浏览器里有几 KB 的隐性上限，参数一多（比如批量选了几百个 id）GET 就会直接 414。这种场景哪怕语义上是“查询”，我也会和后端商量改成 POST 传 body。语义和工程现实之间，需要权衡。

状态码是接口沟通里最直接的信号

前端最常见的几类状态码，大致可以这样理解：

  • 2xx：请求成功
  • 3xx：资源位置或缓存状态发生了某种重定向/协商
  • 4xx：请求本身有问题或权限不满足
  • 5xx：服务端处理失败

很多页面错误处理不清晰，就是因为把所有失败都粗暴地归成“网络错误”。

实际上：

  • 401 和 403 往往意味着认证授权问题
  • 404 更像资源不存在
  • 500 通常是服务端异常

如果前端不区分这些类型，用户看到的反馈就会非常模糊，排障成本也会更高。

401 和 403 的区别尤其值得说一句。我见过太多项目把两者混在一起处理，结果一个明明只是“没权限看这个页面”的用户，被反复踢去重新登录，登完回来还是看不了，体验非常糟。401 是“你是谁我不知道”，403 是“我知道你是谁，但你不能进”，这两种该给用户的引导完全不同。

3xx 里几个重定向码的区别也值得分清，它们不是一回事：301 是永久重定向，浏览器和搜索引擎会把它记下来、以后直接走新地址，所以域名搬迁、URL 改版用 301；302 是临时重定向，下次还来问原地址。但 301/302 有个历史包袱——很多浏览器会在重定向时把原来的 POST 悄悄改成 GET，这在表单提交场景能坑死人。307 和 308 就是来修这个的：它们语义和 302/301 一样（临时/永久），但严格保证方法和 body 不变，POST 重定向后还是 POST。所以现在要做“保持方法的重定向”，该用 307/308。

前端发 fetch 时浏览器默认会自动跟随重定向，所以 res.status 你通常根本看不到 302，拿到的是最终那一跳的状态。如果某个接口靠重定向来做跳转逻辑，得在 fetch 里设置 redirect: 'manual' 才能拿到原始的 3xx，这个我也是踩过坑才知道的。

5xx 内部也别一概而论。500 是服务端代码自己抛了异常；502（Bad Gateway）和 504（Gateway Timeout）则是网关/反向代理层的问题——502 是 Nginx 这类前置把请求转给后端、后端却返回了无效响应或直接挂了（进程崩溃、端口没起），504 是后端在超时时间内压根没回话（接口太慢、卡死）。线上看到 502，我一般先怀疑后端服务挂没挂；看到 504，先去查那个接口是不是慢查询超时了。这两个区分清楚，定位方向完全不同。

请求成功不等于业务成功

这是前端特别容易忽略的一点。

浏览器层面拿到 200，不代表业务逻辑一定成功。很多接口会在响应体里再表达一次业务状态。

例如：

  • HTTP 是 200，但业务码提示参数不合法
  • HTTP 是 200，但数据为空且有特殊提示
  • HTTP 是 200，但需要前端跳转登录

这说明请求层和业务层要分开处理。只看浏览器 Network 面板里是不是 200，往往不够。

还有个更容易栽的点，是 fetch 对失败状态码的态度。很多人以为请求返回 404、500 会进 catch，其实不会。fetch 只在网络层面真出错（断网、DNS 失败、CORS 拦截）时才 reject，HTTP 拿到响应——哪怕是 404、500——Promise 都是 fulfilled。在控制台贴一段验证：

请求层最好把错误形态收拢起来

如果项目里每个页面都自己 try/catch、自己判断 res.status、自己弹 Toast，后面一定会乱。最常见的结果是：同一个 401，有的页面跳登录，有的页面弹“请求失败”；同一个业务错误，有的页面展示后端 message，有的页面吞掉；监控里也分不清到底是网络断了、HTTP 失败，还是业务码失败。

我后来写请求封装，会先把错误分成三层：

  • 网络错误：断网、DNS、CORS、请求被取消，连 HTTP 响应都没拿到
  • HTTP 错误：拿到了响应，但状态码不是 2xx
  • 业务错误：HTTP 是 200，但响应体里的 code 不是成功码

Header 不是附属信息，它经常决定行为

请求头和响应头里有很多看起来不显眼的字段，但它们实际影响非常大。

例如：

  • Content-Type 决定数据怎么解析
  • 缓存相关头决定资源是否复用
  • 认证头决定用户是否有权限

很多“前端明明发出去了，后端却说收不到”的问题，最后都落在请求头设置不对上。

有一次我把数据 JSON.stringify 之后发出去，后端却说参数全是空的——原因就是后端那个接口按表单格式接收，而我发的是 application/json，body 它根本没去解析。光看前端 Network，请求体明明白白带着数据，但语义对不上，就是收不到。

还有文件上传更要小心：用 FormData 时千万别自己手动设 Content-Type。浏览器需要自动生成一个带 boundary 分隔符的 multipart/form-data，你一旦手写覆盖了，boundary 就丢了，后端会直接解析失败。这个反直觉的点也是我调了很久才反应过来的。

连接和缓存：那些藏在头里的行为

Connection: keep-alive 是 HTTP/1.1 默认开的：一条 TCP 连接发完一个请求不立刻关，留着给后续请求复用，省掉反复三次握手的开销。没有它，每个请求都要新建连接，首屏几十个资源会慢得肉眼可见。但 HTTP/1.1 有个绕不开的硬伤——队头阻塞（head-of-line blocking）：同一条连接上请求得排队，前一个响应没回来，后面的就算服务端早处理好了也只能干等。浏览器的对策是对同一域名开 6 个左右的并发连接，早年“域名分片”（把资源拆到多个子域名）就是为了多偷几条连接绕开这个限制。HTTP/2 用多路复用在一条连接上并行收发多个流，才算从协议层把它解掉。

缓存也是头说了算，得分清强缓存和协商缓存。强缓存是 Cache-Control: max-age=300 这种，浏览器在有效期内压根不发请求，直接读本地；协商缓存带 ETag 或 Last-Modified，浏览器会发一个请求问服务端“变了没”，没变就返回 304、body 为空，省的是传输流量而不是请求本身。我那次“列表刷新还是旧数据”就是命中了强缓存，Network 里都看不到新请求（显示 from disk cache），自然怎么刷都是旧的。

# 协商缓存的一来一回
请求:  If-None-Match: "abc123"
响应:  304 Not Modified        （body 为空，用本地缓存）

# 或者
请求:  If-None-Match: "abc123"
响应:  200 OK + ETag: "def456"  （内容变了，返回新数据）

对真实接口数据，我现在倾向让后端明确返回 Cache-Control: no-cache 或 no-store，把控制权握在手里，而不是依赖浏览器和 CDN 的默认行为去猜。

HTTPS 握手大致在做什么

顺带说下 HTTPS，知道个大概轮廓就够用。TCP 三次握手建好连接后，会再走一次 TLS 握手：客户端发 ClientHello（带自己支持的加密套件、随机数），服务端回 ServerHello 选定套件、并把证书发过来；客户端验证证书是不是可信 CA 签发、域名对不对、有没有过期，验过之后双方通过非对称加密协商出一个对称密钥，之后的应用数据全用这个对称密钥加密传输。所以 HTTPS 是“非对称加密协商密钥、对称加密传数据”——非对称慢但安全用来交换钥匙，对称快用来跑正文。前端最常踩的是证书问题：自签证书、证书过期、域名不匹配，浏览器会直接拦在握手阶段，请求根本到不了业务逻辑。

跨域不是“发不出去”，是响应被浏览器拦了

跨域和缓存同理，是浏览器的安全策略，不是网络故障。请求其实发出去了、服务端也处理了，是浏览器拿到响应后发现没有合规的 Access-Control-Allow-Origin 头，就把结果拦在 JS 之外。更隐蔽的是预检请求（preflight）：当你带了自定义头、或用了 PUT/DELETE 这类方法时，浏览器会先自动发一个 OPTIONS 去问服务端允不允许，这个 OPTIONS 挂了，真正的请求根本不会发。我见过有人对着 Network 里那个莫名其妙的 OPTIONS 一脸懵，其实它就是 CORS 预检。

把这些沉到请求层，排障成本会降很多

把前面这些串起来，懂 HTTP 对前端最实际的价值就出来了：你能把状态码语义、头的行为、缓存和跨域约束、请求成功与业务成功的区别识别出来，沉到一个统一请求层里——统一错误处理、登录失效兜底、按状态码分流、按业务码再判一次——而不是每个页面自己猜一遍。排查问题时也能说得具体：请求方法和参数是什么、返回状态码是什么、响应体里有没有业务错误信息、问题在本地还是线上。比起“接口挂了”这种模糊描述，这种精确度能让前后端协作快很多。

下面这些典型场景，往下拆几乎都落在请求方法、请求头、缓存、认证或响应语义上：

  • 列表数据为什么明明刷新了却还是旧的
  • 登录态为什么突然失效
  • 文件上传为什么后端说格式不对
  • 某个接口为什么本地能调、线上却失败

拿“列表刷新了还是旧数据”举例，往下拆基本就是缓存命中了——这正是前面那一节讲过的强缓存。这些问题表面看像业务 bug，但只要你能在 Network 面板里把请求是否发出、方法和参数、状态码、响应头和响应体连起来看，绝大多数都能定位到具体哪一环。页面展示只是结果，通信过程同样是前端工程质量的一部分，理解 HTTP 本质上是在补齐这块基础。
