前端为什么也要懂 HTTP：请求能发出去，不代表你真的理解通信

2021-06-21
前端基础

做前端久了会发现，很多问题表面看像页面 bug，实际往下挖都和 HTTP 通信细节有关。

接口为什么返回 304，为什么跨域失败，为什么表单提交和 JSON 请求表现不同，为什么缓存策略会影响页面更新，这些都说明前端并不只是“把请求发出去”就够了。

理解 HTTP，不是为了转行后端，而是为了更稳地处理前后端协作边界。

请求方法不只是名字不同

最常见的请求方法当然是 GET 和 POST。

很多项目里大家会形成一种朴素印象：

  • GET 用来拿数据
  • POST 用来提交数据

这个理解没错，但如果只停在这一步，很多接口设计和调试细节就会看不清。

我自己印象最深的一次坑，是做一个商品搜索页。当时把筛选参数都拼在 GET 的 URL 里，本地测试一切正常，上线后却时不时出现“筛选条件变了但列表没变”的反馈。查了半天才发现是 CDN 和浏览器把这个 GET 请求缓存了——因为 GET 在语义上被认为是安全且幂等的，中间任何一层代理都有理由把它缓存起来。后来我们要么给 URL 带上时间戳打破缓存，要么对真正不该缓存的查询改用 POST。这件事让我第一次意识到：方法的选择不是个人偏好，它会被整条链路上的缓存、代理、日志系统按照语义去“理解”。

幂等性这个概念也是后来才真正体会到的。GET、PUT、DELETE 在规范里都是幂等的——同样的请求发一次和发十次，服务端最终状态应该一样。而 POST 不是。这意味着如果一个“创建订单”的接口用 POST，那网络抖动时的自动重试就很危险，可能创建出两个订单；如果改成 PUT 并由前端生成一个唯一 id 作为资源标识，重试就安全得多。所以我现在看到一个“更新”接口，会先问后端到底是整体替换（PUT）还是局部修改（PATCH），这直接决定我前端要不要把整个对象都传上去。

至于参数放 URL 还是放请求体，也有现实约束。URL 长度在很多服务器和浏览器里有几 KB 的隐性上限，参数一多（比如批量选了几百个 id）GET 就会直接 414。这种场景哪怕语义上是“查询”，我也会和后端商量改成 POST 传 body。语义和工程现实之间，需要权衡。

状态码是接口沟通里最直接的信号

前端最常见的几类状态码，大致可以这样理解：

  • 2xx：请求成功
  • 3xx：资源位置或缓存状态发生了某种重定向/协商
  • 4xx：请求本身有问题或权限不满足
  • 5xx：服务端处理失败

很多页面错误处理不清晰，就是因为把所有失败都粗暴地归成“网络错误”。

实际上：

  • 401 和 403 往往意味着认证授权问题
  • 404 更像资源不存在
  • 500 通常是服务端异常

如果前端不区分这些类型，用户看到的反馈就会非常模糊，排障成本也会更高。

还有一个容易忽略的是 3xx。前端发 fetch 时浏览器默认会自动跟随重定向，所以 res.status 你通常根本看不到 302，拿到的是最终那一跳的状态。如果某个接口靠重定向来做跳转逻辑，得在 fetch 里设置 redirect: 'manual' 才能拿到原始的 3xx，这个我也是踩过坑才知道的。

请求成功不等于业务成功

这是前端特别容易忽略的一点。

浏览器层面拿到 200，不代表业务逻辑一定成功。很多接口会在响应体里再表达一次业务状态。

例如：

  • HTTP 是 200，但业务码提示参数不合法
  • HTTP 是 200，但数据为空且有特殊提示
  • HTTP 是 200，但需要前端跳转登录

这说明请求层和业务层要分开处理。只看浏览器 Network 面板里是不是 200，往往不够。

Header 不是附属信息，它经常决定行为

请求头和响应头里有很多看起来不显眼的字段，但它们实际影响非常大。

例如：

  • Content-Type 决定数据怎么解析
  • 缓存相关头决定资源是否复用
  • 认证头决定用户是否有权限

很多“前端明明发出去了，后端却说收不到”的问题，最后都落在请求头设置不对上。

有一次我把数据 JSON.stringify 之后发出去，后端却说参数全是空的——原因就是后端那个接口按表单格式接收，而我发的是 application/json，body 它根本没去解析。光看前端 Network，请求体明明白白带着数据，但语义对不上，就是收不到。

还有文件上传更要小心：用 FormData 时千万别自己手动设 Content-Type。浏览器需要自动生成一个带 boundary 分隔符的 multipart/form-data，你一旦手写覆盖了，boundary 就丢了，后端会直接解析失败。这个反直觉的点也是我调了很久才反应过来的。

前端懂 HTTP，才能写出更像样的请求封装

如果只把请求当成 fetch(url)，那封装层通常只能停留在“发一下，拿一下”。

但一旦你理解了：

  • 不同状态码的意义
  • 请求头和响应头的作用
  • 浏览器缓存和跨域约束
  • 请求成功与业务成功的区别

那你的封装才更容易做到统一错误处理、重试策略、登录失效兜底和更明确的异常提示。

它不是额外知识，而是前端工程的一部分

前端和服务端边界越来越紧密的今天，懂 HTTP 已经不是“懂一些底层原理”那么简单。

它直接影响你：

  • 能不能准确描述问题
  • 能不能看懂请求失败原因
  • 能不能和后端顺畅协作
  • 能不能设计出稳定的请求层

页面展示只是结果，通信过程同样是前端工程质量的一部分。理解 HTTP，本质上是在补齐这部分基础。

前端真正离不开 HTTP 的地方，是很多产品问题最后都会回到它

比如这些场景都很典型：

  • 列表数据为什么明明刷新了却还是旧的
  • 登录态为什么突然失效
  • 文件上传为什么后端说格式不对
  • 某个接口为什么本地能调、线上却失败

这些问题表面看像业务 bug，往下拆却几乎都和请求方法、请求头、缓存、认证或者响应语义有关。前端如果完全不理解这些基础，只能停留在“接口不通”这种很模糊的描述上，协作效率会明显受限。

拿“列表刷新了还是旧数据”举例，往下拆基本就是缓存命中了。这里值得分清两种缓存：强缓存和协商缓存。强缓存是 Cache-Control: max-age=300 这种，浏览器在有效期内压根不发请求，直接读本地；协商缓存是带 ETag 或 Last-Modified，浏览器会发一个请求问服务端“变了没”，没变就返回 304，body 是空的，省的是传输流量而不是请求本身。我那次列表不刷新就是命中了强缓存，Network 里都看不到新请求（或者显示 from disk cache），自然怎么刷都是旧的。

# 协商缓存的一来一回
请求:  If-None-Match: "abc123"
响应:  304 Not Modified        （body 为空，用本地缓存）

# 或者
请求:  If-None-Match: "abc123"
响应:  200 OK + ETag: "def456"  （内容变了，返回新数据）

对于真实接口数据，我现在倾向于让后端明确返回 Cache-Control: no-cache 或 no-store，把缓存的控制权握在手里，而不是依赖浏览器和 CDN 的默认行为去猜。

跨域那一类也是同理。跨域不是“前端发不出去”，请求其实发出去了，是浏览器拿到响应后因为没有合规的 Access-Control-Allow-Origin 头而把结果拦在了 JS 之外。更隐蔽的是预检请求（preflight）：当你带了自定义头或用了 PUT/DELETE 这类方法时，浏览器会先自动发一个 OPTIONS 去问服务端允不允许，这个 OPTIONS 挂了，真正的请求根本不会发。我见过有人对着 Network 里那个莫名其妙的 OPTIONS 一脸懵，其实它就是 CORS 预检。

会看 Network 面板，本质上是在读通信现场

很多前端调试能力的分水岭，不是会不会写请求，而是会不会看请求。

打开浏览器 Network 面板后，真正应该关心的通常包括：

  • 请求有没有发出去
  • 参数和方法是不是预期的
  • 返回状态码是什么
  • 响应头和响应体分别在表达什么

这些信息一旦能连起来看，很多问题就不再只是“前后端互相怀疑”。理解 HTTP 对前端最大的现实价值，正是在于它能让你更准确地描述问题边界，也更容易把请求层做成真正可靠的基础设施。

请求层稳定，前端排障成本会下降很多

一个成熟一点的前端项目，通常不会让页面层自己散着处理各种协议细节。因为只要接口数量一多，登录失效、错误提示、重试策略、超时处理这些逻辑就会迅速重复。

这时候懂 HTTP 的价值就会体现出来：你更容易把公共问题识别出来，并沉到统一请求层里，而不是每个页面都自己猜一遍该怎么处理。

前后端协作顺不顺，很大程度取决于沟通是否足够具体

比如只说“接口挂了”，信息其实很少。可如果你能说清：

  • 请求方法和参数是什么
  • 返回状态码是什么
  • 响应体里有没有业务错误信息
  • 问题发生在本地、测试还是线上

那整个排查过程会快很多。理解 HTTP 对前端来说，最终不是为了懂术语，而是为了把问题说得更精确，把系统做得更稳。
