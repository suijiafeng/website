Vue CLI 3 项目体验：脚手架变轻以后，配置反而要更清楚

2018-01-12
Vue构建与模块化

刚开始用 Vue CLI 3 时，最明显的感觉是项目根目录安静了很多。

以前用 webpack 模板生成项目，build、config、各种 loader 配置都摆在眼前。好处是透明，坏处是新人一打开项目就被一堆配置劝退。CLI 3 把很多默认配置收起来，通过插件和 vue.config.js 暴露扩展点，体验更像“先把项目跑起来，再按需要改”。

这件事对团队很友好，但也带来一个新问题：配置藏起来以后，大家更容易忽略它的边界。

默认配置不是没有配置

CLI 3 默认已经处理了很多事情：

  • 开发服务器
  • Babel 转译
  • CSS 预处理
  • 静态资源处理
  • 生产构建
  • HMR
  • 代码分割

这些能力开箱即用，很容易让人产生错觉：项目不需要理解构建配置了。

但真到业务里，还是会遇到路径、代理、source map、CDN、环境变量、打包目录这些问题。只是这些问题从 webpack.config.js 转移到了 vue.config.js。

很多项目喜欢把所有环境差异都堆到 .env.production 里，但前端构建产物最终是给浏览器的。凡是进了浏览器，就要默认用户能看到。

插件化的好处和风险

CLI 3 的插件机制很舒服：

这让项目能力可以渐进添加，不必一开始就选全家桶。

但插件也要克制。每加一个插件，项目就多一个维护点。尤其是 PWA、单元测试、E2E、TypeScript 这类能力，最好先确认团队会不会真的用。为了“看起来完整”把所有选项都勾上，最后常常变成无人维护的配置噪音。

chainWebpack 不是万能入口

CLI 3 提供 chainWebpack，可以细粒度改 webpack 配置：

这很强，但不要滥用。

如果只是改别名、加 loader、调插件顺序，chainWebpack 很合适。可如果整个项目都靠 chainWebpack 重写默认行为，那 CLI 的升级优势就被抵消了。

我的习惯是先问：这个改动是业务必须，还是因为我想按以前的 webpack 写法控制一切？如果只是后者，最好先忍住。

小结

Vue CLI 3 的价值是把默认工程体验做好，让团队少花时间搭脚手架。但配置被收起来，不代表配置不重要。

真正用好它，关键是保持 vue.config.js 简洁、环境变量边界清楚、插件按需添加、webpack 扩展有明确理由。脚手架越智能，团队越应该知道自己改了什么，以及为什么要改。
