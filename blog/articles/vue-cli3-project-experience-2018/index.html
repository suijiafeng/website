Vue CLI 3 项目体验：脚手架变轻以后，配置反而要更清楚

2018-08-20
Vue构建与模块化

Vue CLI 3 正式版出来后，我第一时间拿一个后台项目试了一轮，最明显的感觉是项目根目录安静了很多。

以前用 webpack 模板生成项目，build、config、各种 loader 配置都摆在眼前。好处是透明，坏处是新人一打开项目就被一堆配置劝退。CLI 3 把很多默认配置收起来，通过插件和 vue.config.js 暴露扩展点，体验更像“先把项目跑起来，再按需要改”。

这件事对团队很友好，但也带来一个新问题：配置藏起来以后，大家更容易忽略它的边界。

我是从 vue-cli@2 的 webpack 模板一路用过来的。那个时代新建项目，build/webpack.base.conf.js、build/webpack.prod.conf.js、config/index.js 一打开就是上千行，里面 loader、plugin、devtool、assetsPublicPath 全堆在一起。好处是真出问题你能顺着配置一行行查；坏处是绝大多数人根本不敢动，改一个 publicPath 都怕牵一发动全身。CLI 3 把这套东西抽进了 @vue/cli-service，根目录一下清爽了，但我第一次升级时心里其实是发虚的——配置我看不见了，出问题怎么办？后来才慢慢摸清它的脾气。

默认配置不是没有配置

CLI 3 默认已经处理了很多事情：

  • 开发服务器
  • Babel 转译
  • CSS 预处理
  • 静态资源处理
  • 生产构建
  • HMR
  • 代码分割

这些能力开箱即用，很容易让人产生错觉：项目不需要理解构建配置了。

但真到业务里，还是会遇到路径、代理、source map、CDN、环境变量、打包目录这些问题。只是这些问题从 webpack.config.js 转移到了 vue.config.js。

我不建议一开始就把各种配置都写进去。配置越多，后面升级越麻烦。

更好的做法是只写项目确实需要覆盖的部分，并在旁边留一点注释说明原因。比如 publicPath 是因为部署在二级目录，proxy 是因为本地联调后端接口。

proxy 这块我想多说两句，因为踩坑的人特别多。changeOrigin: true 不写，很多后端会因为 Host 头不对直接拒掉请求，这是新人最常见的“代理配了但 404”的原因。另外如果后端接口本身不带 /api 前缀，而你前端为了走代理统一加了前缀，就还得 pathRewrite 把前缀去掉：

我自己定的习惯是：能用 proxy 解决的本地跨域，就绝不让后端临时给我开 CORS。因为 CORS 是后端配置，临时开的口子上线前经常忘了关，反而留下安全隐患；proxy 只在 vue-cli-service serve 的开发服务器生效，打包产物里压根没有它，天然不会带到生产。这个边界很干净，值得坚持。

publicPath（CLI 2 时代叫 baseUrl）是另一个反复让人翻车的点。部署在二级目录却没改它，结果就是首页能打开、但所有 JS/CSS 静态资源 404，控制台一片红。这个错误我帮人排查过不下五次，现象都一样：白屏 + 资源路径少了一层目录。记住一句话——只要不是部署在域名根目录，就得改 publicPath。

这里要注意，只有 VUE_APP_ 开头的变量会注入客户端代码。也就是说，它不是秘密。接口地址、站点名称可以放，密码、token、私钥不能放。

很多项目喜欢把所有环境差异都堆到 .env.production 里，但前端构建产物最终是给浏览器的。凡是进了浏览器，就要默认用户能看到。

我见过最离谱的一次，是有人把对接第三方支付的私钥 base64 一下塞进了 VUE_APP_PAY_SECRET，理由是“反正打包压缩混淆过了，看不出来”。可只要在浏览器里打开打包后的 JS、搜一下关键字，那串密钥明晃晃地躺在那。webpack 的 DefinePlugin 是把这些变量在编译期直接字符串替换进代码的，压缩混淆只是改变量名，常量字符串原样保留。这事让我彻底记住一条铁律：前端 .env 里只能放“公开也无所谓”的东西，任何带 secret、token、password 的，都该在后端处理。

CLI 3 的 .env 还有加载优先级，容易绕晕。简单记：.env.production 这种带模式后缀的优先级高于通用的 .env，.env.local 优先级又更高且默认不进版本库。我一般把通用配置放 .env，环境差异放 .env.development / .env.production，本地个人调试用的临时覆盖放 .env.local，这样既不污染团队配置，也不会误把自己的本地地址提交上去。

CLI 3 的插件机制很舒服：

但插件也要克制。每加一个插件，项目就多一个维护点。尤其是 PWA、单元测试、E2E、TypeScript 这类能力，最好先确认团队会不会真的用。为了“看起来完整”把所有选项都勾上，最后常常变成无人维护的配置噪音。

chainWebpack 不是万能入口

CLI 3 提供 chainWebpack，可以细粒度改 webpack 配置：

这很强，但不要滥用。

如果只是改别名、加 loader、调插件顺序，chainWebpack 很合适。可如果整个项目都靠 chainWebpack 重写默认行为，那 CLI 的升级优势就被抵消了。

我的习惯是先问：这个改动是业务必须，还是因为我想按以前的 webpack 写法控制一切？如果只是后者，最好先忍住。

注意 build:test 那行的 --mode test，它会去加载 .env.test，这是我们做“测试环境单独打包”的常用手法。很多人不知道 --mode 能指定自定义模式，以为只有 dev/prod 两种，结果为了测试环境去硬改 NODE_ENV，把生产优化也一起关了。把这些命令在 README 里列清楚、写明各自打的是哪个环境，能省掉大量“为什么我打出来的包连的是生产接口”的来回沟通。

CLI 把复杂藏起来是好事，但团队必须知道改动的原因。保持 vue.config.js 简洁、环境变量边界清楚、按需添插件，遇问题时用 vue inspect 看默认配置。工具省力，理解才可靠。
