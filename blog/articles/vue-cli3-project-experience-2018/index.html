Vue CLI 3 升级初体验：根目录安静得让我发虚的那个周末

2018-08-20
Vue构建与模块化

Vue CLI 3 最先制造的不适感，不是功能变化，而是“那些我习惯看到的配置文件突然都不见了”。对长期写 CLI 2 项目的人来说，build/、config/、成堆 webpack 配置是麻烦，但也是一种心理依赖：出了问题，至少知道该去哪翻。

升级实验真正让我发虚的，就是根目录忽然变得太干净了。build 没了，config 没了，webpack.config.js 也没有。舒服当然是舒服，问题也随之冒出来：配置我看不见了，出了问题我去哪查？

这个周末剩下的时间，就是我从发虚到踏实的过程。后面按遇到问题的顺序往下讲。

第一步祛魅：配置没有消失，只是被接管了

我最先干的事，是去 node_modules 里找答案。默认配置全被收进了 @vue/cli-service，翻源码当然能看，但官方给了个体面得多的入口：

它把内部的 webpack 配置完整 dump 出来。我跑完打开一看，心里那块石头落了地：那些"消失"的配置一个没少——loader 链、plugin、代码分割、HMR，全在，只是从"摆在你脸上"变成了"需要时再看"。

这个命令后来在排查问题时帮了大忙。某个 loader 好像没生效、某个文件没被处理，dump 出来对着看默认链路，再决定要不要动手，比瞎猜强太多。我的建议是每个升级 CLI 3 的人都先跑一次，对黑盒祛魅之后，用起来心态完全不一样。

vue inspect 还能带参数只看某一段，不用每次都 dump 一整个文件。想确认某条规则里挂了哪些 loader、顺序对不对，直接：

--rule scss 只打印处理 .scss 的那条规则链，--rules、--plugins 分别列出所有规则名和插件名。我排查样式问题时最常用 --rule：先 --rules 拿到规则名，再 --rule 名字 看那条链上 sass-loader、css-loader、vue-style-loader 的挂载顺序对不对——loader 是从右到左（从下到上）执行的，顺序错了样式就不生效。有了这个，我基本不用再钻进 node_modules 翻 @vue/cli-service 的源码了。

对了，CLI 3 还带了个 vue ui，图形界面里建项目、装插件、看构建分析都行。我试了一圈，图新鲜可以，日常还是回了命令行——但给团队里不爱碰终端的同事演示项目结构时，它意外地好用。

顺便把 CLI 2 和 CLI 3 的世界观差别记一下，因为这直接决定了我升级时该带哪种预期。CLI 2 是"模板拉取器"：vue init webpack my-app 干的事，是去 vuejs-templates/webpack 那个仓库把一整套模板 clone 下来，build/、config/ 里那些 webpack 配置就是模板的一部分，直接躺进你的项目，从此归你所有、也归你维护。模板作者更新了，你已经生成的项目是不会跟着变的，配置和框架彻底解耦——好处是透明，坏处是每个项目都各自长歪，五个项目五套 webpack 配置，改一处公共逻辑要改五遍。CLI 3 反过来，配置不再复制进项目，而是收进 @vue/cli-service 这个 runtime 依赖里，跟着 npm 版本走。这就是为什么根目录空了：配置从"你项目里的文件"变成了"一个 npm 包的实现细节"。理解了这层，vue inspect 的意义才立得住——它不是什么调试彩蛋，而是你唯一还能看见那套被收走的配置的窗口。

官方文档里 baseUrl 这个配置项，具体这么用：它决定的是应用被部署在哪个基础路径下，打包时所有资源引用都会带上这个前缀。这个点必须展开说，因为我帮人排查过不下五次同一种翻车：部署在二级目录、没改它，结果首页能打开，JS/CSS 全部 404，控制台一片红，白屏。现象一模一样，病根一模一样。一句话记住：只要不是部署在域名根目录，就得改 baseUrl。

proxy 是另一个坑位密集区。changeOrigin: true 不写，不少后端会因为 Host 头不对直接拒掉请求——这是"代理配了但 404"的头号原因。后端接口不带 /api 前缀的话，还得 pathRewrite 把前端加的前缀剥掉：

顺便说一条我给自己定的纪律：本地跨域能用 proxy 解决的，绝不找后端临时开 CORS。CORS 是后端配置，临时开的口子上线前经常忘了关；proxy 只活在 vue-cli-service serve 的开发服务器里，打包产物压根不带它，边界天然干净。

proxy 还有个进阶用法是我们这种中后台项目常用的：一个前端要同时联调好几个后端服务，网关服务、订单服务、用户中心各在不同端口。proxy 支持写成对象，按路径前缀分别转发：

环境变量：.env 不是保险箱

CLI 3 原生支持 .env 文件，这是我这次升级最喜欢的改进之一。2.x 时代我们是自己在 config/dev.env.js、prod.env.js 里维护的，现在一个文件搞定：

规则是只有 VUE_APP_ 开头的变量会注入客户端代码。而"注入客户端代码"这六个字，意味着它不是秘密。

这里我要讲一个真事。上个月我们隔壁组有人把对接第三方支付的私钥 base64 了一下，塞进 VUE_APP_PAY_SECRET，理由是"反正打包压缩混淆过了，看不出来"。我当场打开他们线上的 JS 文件搜关键字——那串密钥明晃晃躺在里面。webpack 的 DefinePlugin 是在编译期把变量字符串替换进代码的，压缩混淆只改变量名，常量字符串原样保留。

那天之后这条铁律在我们组挂在了 wiki 首页：前端 .env 里只放"公开了也无所谓"的东西；带 secret、token、password 字样的，一律后端处理。

.env 的加载优先级也容易绕晕，我的分法是：通用配置进 .env，环境差异进 .env.development / .env.production，本地个人调试的临时覆盖进 .env.local——它优先级最高且默认不进版本库，既不污染团队配置，也不会把自己的本地地址误提交上去。

还有一个我第一次没搞明白的点：NODE_ENV 到底是谁定的。CLI 3 里 NODE_ENV 不是你在 .env 里想写就能覆盖的，它由 --mode 决定——serve 默认 --mode development，build 默认 --mode production，各自去加载对应的 .env.development / .env.production。真正灵活的是"模式"这个维度：--mode 的值可以是任意字符串，它决定加载哪个 .env.[mode] 文件，但 NODE_ENV 只认 development / production / test 这几个标准值。我们后来加了个 staging 环境，做法是建 .env.staging 文件，在里面显式写一行：

这样 vue-cli-service build --mode staging 会走生产级的构建优化（压缩、tree-shaking 全开），但接口指向 staging。"模式"和 NODE_ENV 是两个正交的东西，前者决定读哪个配置文件，后者决定构建产物的优化档位，混为一谈就会写出"staging 包体积异常大"这种莫名其妙的 bug——那多半是有人把 NODE_ENV 留成了 development，把生产优化整个关掉了。

插件：vue add 很爽，但每个插件都是维护点

CLI 3 的插件机制是这次架构变化的核心，能力可以渐进添加：

不用一开始就选全家桶，这对"先跑起来再说"的项目太友好了。但升级完实验项目后我又建了个测试项目，把 PWA、单元测试、E2E、TypeScript 全勾上体验了一圈，然后得出一个很朴素的结论：为了"看起来完整"把选项全勾上，最后都会变成无人维护的配置噪音。每加一个插件，项目就多一个维护点。团队会不会真的写 E2E？不确定的话就先别加，vue add 随时可以补。

我特意去看了 vue add 到底做了什么，因为一个命令能自动改一堆文件，不搞清楚机制我用着心虚。CLI 3 的插件其实是两部分：一个 Service Plugin，在构建时往内部 webpack 配置里注入规则（这就是为什么装个 @vue/cli-plugin-eslint 就自动有了 lint 能力，你不用自己配 loader）；一个 Generator，负责在安装那一刻改写你的项目文件——往 package.json 加依赖和脚本、生成配置文件、甚至改 main.js 插入初始化代码。也就是说 vue add router 不只是装个包，它会真的动手改你的 src/router.js 和 main.js。理解这一点之后我给自己立了条规矩：vue add 之前先 commit 一次，让它的改动单独成一个干净的 diff，这样万一它改坏了、或者改的地方不合心意，git checkout 一键还原，不至于和自己手写的代码搅在一起分不清。插件体系省事是真省事，但"一个命令改多个文件"这件事本身就该被 Git 盯着。

transpileDependencies：IE11 白屏的那半天

有一个坑不是升级当天踩的，是升级后第一次拉 IE11 测才炸出来的，值得单独记：页面在 Chrome、Firefox 一切正常，一到 IE11 直接白屏，控制台一句 语法错误。

病根在 CLI 3 的默认 Babel 策略。为了构建速度，@vue/cli-service 默认只转译 src 里的代码、不动 node_modules——它假设发到 npm 上的包都已经编译成 ES5 了。这个假设 2018 年越来越站不住：有些库（尤其是一些 Vue 组件库、以及本身就用 ES6 语法发布的工具库）为了体积，直接把没转译的源码发上来，箭头函数、const 原样保留。这些语法 Chrome 认，IE11 不认，一执行就报语法错误，整个应用挂掉。

排查手段是老实的：白屏但没有 JS 报错时先看 Network，JS 都加载成功了，那问题就在解析/执行阶段；IE11 的开发者工具会把报错定位到某个 chunk 的具体行，扒开一看果然是某个第三方库里的箭头函数。定位到之后，vue.config.js 里一行配置就能救：

transpileDependencies 告诉 CLI："这几个 node_modules 里的包也要过一遍 Babel"。它接受包名或正则。别图省事写成 transpileDependencies: true 去转译全部依赖——那等于把 node_modules 整个塞进 Babel，构建时间会难看地翻上去，我们那个项目试过，dev 启动从十几秒拖到快一分钟。精确列出真正需要转译的那几个包，才是这个配置的正确用法。这件事也提醒我：CLI 3 把 Babel 配置藏起来了，但"哪些代码被转译"这个决策还是得由人来兜底，尤其还背着 IE11 兼容压力的项目。

两个差点被我忽略的新东西

收尾前记两个这次升级捡到的宝。

一是 --report。构建时加上它会生成 bundle 分析报告，哪个依赖占了多大体积一目了然：

moment 默认会把 locale 目录下几十个语言包全打进来，光这一项就是两三百 KB。IgnorePlugin 匹配到 moment 引入的 ./locale 请求就直接忽略，需要哪个语言再手动 import 'moment/locale/zh-cn' 引回来。这类"某个依赖悄悄胖了一圈"的问题，靠肉眼是发现不了的，--report 把它可视化出来才有的救——升级顺手把这条排查手段接进日常，比发现某个具体的胖依赖更值。

二是 modern mode：

它会打两份产物，新浏览器走 <script type="module"> 加载几乎不用转译的现代包，老浏览器走 nomodule 的兼容包。原理是浏览器对 type="module" 和 nomodule 这两个属性的取舍互斥：支持 ES module 的新浏览器只认前者、忽略带 nomodule 的那份，老浏览器不认识 type="module" 干脆跳过、只加载 nomodule 那份。于是同一个页面，新浏览器拿到体积更小、几乎没有 Babel polyfill 冗余的现代包，老浏览器拿到全量兼容包，各取所需。

我在测试项目上试了一下，现代包比兼容包小了百分之十几，async/箭头函数这些在现代包里原样保留，省掉了转译后那一堆 _regeneratorRuntime、Object.assign 垫片。听起来很美，但我还没敢直接上生产，顾虑有两条：一是双份产物对 CDN 和缓存策略有要求，得确认 CDN 不会把两份 JS 的缓存搞混；二是有些老代理、老 CDN 会因为不认识 nomodule 属性把两份脚本都塞给用户，反而下载两遍。这类边界只能在真实网络环境里试，所以先在内部项目挂着观察，等踩明白了再往主站推。新特性带来的收益很实在，但它对基础设施的隐性要求，往往比配置本身更难评估。

index.html 从 dist 里的产物变成了 public 下的模板

还有一处 CLI 2 老用户容易愣一下的变化：index.html 挪到了 public/ 目录，而且里面开始出现 <%= %> 这样的插值语法。CLI 2 时代很多人习惯直接改 dist/index.html，改完发现下次构建又被覆盖——因为那本来就是产物，不是源文件。CLI 3 把源模板放在 public/index.html，构建时由 html-webpack-plugin 处理，注入打包好的 script 标签，再输出到 dist。

周末结束时的判断

周日晚上，实验项目升级完毕，构建通过，页面正常。我关电脑前在笔记里写了三句话，作为这次初体验的结论：

CLI 3 把复杂藏起来是好事，但藏起来不等于不存在——vue inspect 随时能把它请出来，发虚的时候就去看。

vue.config.js 保持少而有据，环境变量守住"公开无所谓"的边界，插件按需加，chainWebpack 只动必要的一刀。

至于团队里那些从 2.x 过来的同事，我在 package.json 里悄悄干了件事：

把 dev 保留成 serve 的别名——CLI 3 默认命令从 dev 改成了 serve，总有人 npm run dev 跑出一句 missing script 然后怀疑自己环境装坏了。build:test 里的 --mode test 会加载 .env.test，这是给测试环境单独打包的手法，很多人以为 --mode 只有 dev/prod 两种，为了测试环境硬改 NODE_ENV，把生产优化也一起关了。

这些都写进了 README。工具把复杂收走了，但改动的原因得留给人。工具省力，理解才可靠——这句话我打算作为这次升级笔记的落款。
