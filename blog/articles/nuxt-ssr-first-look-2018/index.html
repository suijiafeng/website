Nuxt SSR：内容页不收录时，问题不在 SEO 术语而在渲染时机

2018-04-03
Vue组件与状态

内容页不收录、分享卡片抓不到标题和摘要，这类问题看起来像“SEO 没做好”，真正往下查，往往会直接撞到单页应用的渲染时机。页面内容如果只有等浏览器把 JS 跑起来之后才出现，那么爬虫和分享机器人在更前面那一步就已经什么都拿不到了。

我第一次把这件事看透，是点开线上站点“查看源代码”的那一刻：整个 <body> 里只有一个空的 <div id="app"></div>，剩下全是脚本引用。对爬虫来说，这不是“收录慢”，而是根本没内容；对微信这类抓 <head> 的分享卡片来说，标题和摘要也同样抓不到。

所以后面研究 SSR，不是为了追一个新技术名词，而是为了解决一个很具体的事实：浏览器能补出来的内容，不代表爬虫和分享机器人也看得到。

手搓 vue-server-renderer 的两天

我不是一上来就用 Nuxt 的。先照着 Vue 官方的 SSR 指南，用 vue-server-renderer 自己搭：要维护一份 entry-client.js、一份 entry-server.js，webpack 得打两份包（客户端 bundle 和服务端 bundle），还要处理 clientManifest、bundleRenderer、状态注水（hydration）……配置文件加起来好几百行，光是把"开发时热更新还能用"这一件事调通，就实打实花了两天。

第三天停下来问自己：这些工程配置跟业务有一毛钱关系吗？没有。它们是每个 SSR 项目都要重复一遍的通用脚手架。而 Nuxt——今年一月刚发了 1.0 正式版——干的就是把这套东西约定好、封装好。手搓的分支先封存，vue init nuxt-community/starter-template 重来。

所以我对 Nuxt 的第一印象很清醒：**它省掉的不是 SSR 的复杂度，而是搭 SSR 脚手架的复杂度——复杂度还在，只是挪进了框架里。**后面每一节都是这句话的注脚。

不用手写 Vue Router 配置。Nuxt 扫描 pages 目录，按文件名和层级自动生成一份 router.js（藏在 .nuxt 目录里，想看可以翻出来）。index.vue 对应该层级的根路径，下划线开头的 _id.vue 是动态路由参数，对应 :id。

第一周我犯了两个典型的新手错。一是嵌套路由：想做 /posts/:id 下面再挂个 /posts/:id/comments，我把两个文件平铺放进 posts 目录，结果父页面内容直接没了。翻文档才明白，嵌套要有一个和动态目录同名的父组件，里面放 <nuxt-child /> 占位：

二是我顺手把一个公共的弹窗组件丢进了 pages——pages 里的每个 .vue 都会被当成路由页面，Nuxt 真给它生成了一条路由，访问那个 URL 能打开一个光秃秃的弹窗，被同事发现后笑了一天。不对应路由的组件老老实实放 components。

约定式路由的好处是路由结构和目录结构永远一致，新人翻一眼目录就知道站点有哪些页面。坏处是它"太约定"了——文件名就是 URL，重命名文件等于改线上地址，哪天手贱把 about.vue 改成 about-us.vue，线上 /about 直接 404，外链全废。这条我写进了项目 README 第一行。

第二周：asyncData，同构代码给我上的第一课

Nuxt 页面取数的核心是 asyncData：

它在组件创建前执行，返回值直接合并进组件实例。关键特性是：首屏由服务端跑，站内跳转由客户端跑。用户直接访问或刷新 /posts/123 时，asyncData 在 Node 端执行，服务端把带内容的 HTML 整个吐出来——这正是爬虫要的；用户在站内从 / 点进 /posts/123 时，它又在浏览器里执行，体验跟普通 SPA 一样。同一段代码，跑在哪端不确定，这直接决定了里面能写什么。

我踩的第一个坑：asyncData 里没有 this。它在实例创建之前执行，this 还不存在，参数、store、重定向都得从入参 context 里解构（{ params, query, store, redirect, error, req, res }）。我下意识写了 this.$store.dispatch(...)，本地点链接进去没事（客户端跳转时机不同），一刷新就 500——服务端那次根本没有 this。

第二个坑更狠：同构代码里不能碰只有浏览器才有的东西。window、document、localStorage 在 Node 端统统不存在。我们有段取 token 的逻辑写了 localStorage.getItem('token')，本地开发点着玩毫无问题，一上线、用户一刷新就白屏，服务端日志里躺着 localStorage is not defined。排查明白之后立了规矩：凡是读浏览器环境的，要么挪进 mounted（只在客户端跑），要么用 Nuxt 注入的 process.client / process.server 标志位判断：

第三方库同理：只要在模块顶层碰了浏览器 API，引进来就能让服务端构建直接崩。Nuxt 的解法是在 plugins 里声明 { src: '~/plugins/xxx', ssr: false }，让它只在客户端加载。我们的图表库就是这么处理的。

第三个坑是性能：asyncData 阻塞首屏——服务端要等它 resolve 才开始渲染。我最初在文章页里串行 await 了正文、相关推荐、评论数三个接口，后端哪个慢一点，整页 TTFB 就被拖垮，用户对着白屏干等。改法两条：互不依赖的接口 Promise.all 并起来；非首屏必需的数据（相关推荐这种）干脆不放 asyncData，挪到 mounted 异步补，先把正文秒出去。

顺带记一个区分：Nuxt 还有个 fetch 方法（和浏览器的 fetch API 重名但不是一回事），它不合并数据到组件，专门用来往 Vuex store 里灌数据；页面级的取数用 asyncData，要进 store 的公共数据用 fetch 或者 nuxtServerInit。刚上手容易混，各干各的活就清楚了。

第三周：head，这次运营验收的重点

SEO 和分享卡片，最后都落在 <head> 上。每个内容页要有自己的标题和描述：

几个真出过事才记住的细节。

一是别偷懒只在 nuxt.config.js 配一个全局 title。我们第一版就是这样，站内几十个页面标题全一样，搜索结果里一排相同的标题，点击率没法看。每个内容页都要有动态 head()，标题带文章名，描述截正文前 100 来字。

二是 hid 千万别漏。它是 Nuxt 给 meta 标签去重的唯一标识——我一开始没写，页面级 description 和全局 description 同时输出，HTML 里出现两个 <meta name="description">，搜索引擎信哪个全看运气。加上 hid: 'description'，页面级覆盖全局，干净了。

三是社交分享要的是 Open Graph 那套 og: 标签，得单独补，不是写了 description 就万事大吉。运营验收标准很直接：链接丢微信群里，卡片得有标题、摘要、缩略图。

四是 head 必须写成函数才能用 this——这时组件实例已建好，能拿到 asyncData 注进来的 this.post，所以 head 依赖的数据必须先在 asyncData 里取到，顺序不能乱。

五是验证方式：改完 head 别只在浏览器里看 document.title，那是客户端渲染后的结果；一定要 curl 一下页面或查看源代码，确认服务端吐出的原始 HTML 里 title 和 meta 就是对的——爬虫看的就是这份未经 JS 执行的源码。这个习惯我现在每次改 head 都保留。

错误不能再"前端自己兜着"了

SSR 给我扭转的另一个观念是错误处理。纯 SPA 时代接口挂了，页面壳子早渲染出来了，内容区显示个"加载失败"，HTTP 响应永远是 200，天塌不下来。SSR 里不一样：asyncData 抛错或调 error()，影响的是服务端这次响应的真实 HTTP 状态码。

文章不存在就该实打实返回 404，搜索引擎才知道这是死页面、不去收录；服务挂了就该返 500，前面的 Nginx 和监控才能据此告警。

我在这上面栽过一个很隐蔽的跟头：接口返回 null 时我没调 error()，而是 return { post: null }，页面照常渲染出一个空模板，HTTP 还是 200。结果爬虫把一堆"内容为空但状态 200"的页面全收录了，运营那边反馈搜索结果里出现空白页。从那以后，"取不到数据"和"展示空内容"在我这是两件事，前者必须落到正确的状态码上。

配套的活儿：调 error() 后 Nuxt 渲染 layouts/error.vue，记得自己写一个，默认那个太素；生产环境要关掉详细错误输出，别把堆栈吐给用户。我们还和后端约定了统一错误壳子 { code, data, message }，在请求库拦截器里把业务失败转成统一形状，asyncData 里只管据此决定 error(404) 还是 error(500)。另外权限类的拦截别放 asyncData 里东一块西一块，Nuxt 有 middleware，路由级统一做重定向和鉴权，干净得多。

部署：从"扔 CDN"到"养一个 Node 进程"

这块是我交学费最多的地方。SPA 部署就是把 dist 扔到静态服务器；Nuxt SSR 项目是一个要长期运行的 Node 服务：

命令就两行，但"养一个服务"意味着一整套以前不用操心的事：

  • Node 进程管理（谁来拉起、崩了怎么办）；
  • 环境变量（哪些进服务端、哪些进浏览器）；
  • 日志（SSR 报错在服务端，用户控制台里看不到）；
  • 异常重启和开机自启；
  • 反向代理和静态资源缓存。

这几条我几乎每条都交过学费。第一版上线我天真地在 SSH 终端里直接 npm run start，断开连接进程就没了；换 nohup 挂后台，进程崩了没人拉起，半夜挂掉第二天上班才发现。最后老实上了 PM2：pm2 start npm --name web -- run start，崩溃自动重启、开机自启、pm2 logs 看日志。SSR 是 CPU 密集活——每个首屏请求都要在服务端跑一遍 Vue 渲染——Node 单进程吃不满多核，机器内存够就开 PM2 的 cluster 模式跑多个实例。

环境变量是另一个坑。SSR 项目的环境变量分两种命运：只在服务端用的（内部接口域名之类）放心从 process.env 读；要带到浏览器里的，必须在 nuxt.config.js 的 env 字段显式声明，构建时把值"烤"进客户端 bundle：

有次在组件里直接用了 process.env.INTERNAL_API，服务端好好的，客户端拿到 undefined——它压根没被打进前端包。反过来也要警惕：别把密钥丢进 env 字段，那等于明文写进用户能下载到的 JS 里。

Nginx 挡在最前面：/_nuxt/ 下那些带 hash 的打包产物由 Nginx 直接伺候，配长缓存；其余请求才转给 Node：

Node 只干 SSR 这件重活，静态文件交给更擅长的 Nginx，压测下来 QPS 明显上去了。文件名带 hash 所以敢配一年缓存——内容一变 hash 就变，天然不怕缓存穿帮。

还有一条路值得记着：nuxt generate。它把每个路由预渲染成一个个 .html 文件，直接丢任何静态托管上，连 Node 进程都不用养。前提是路由能在构建时枚举——动态路由 /posts/:id 得通过 generate.routes 喂一份 id 列表给它，它不会自己猜。我们的文章更新频率如果降下来，我打算把站点切到 generate + 定时重新生成的方案上，运维成本能陡降；但只要内容依赖请求时动态渲染（随登录用户变、实时性要求高），就得按服务端应用老实养进程。

上线一周，账要怎么算

站点用 Nuxt 重构上线一周了。curl 文章页，HTML 里正文、title、meta 全在；微信分享卡片有图有摘要；收录得等搜索引擎慢慢爬，但至少这次爬虫能看见内容了。

SSR 把"渲染"从用户的浏览器搬到了服务器上，好处是首屏、SEO、分享，代价是服务器实打实地扛活。SPA 时代前端是一堆静态文件，CDN 几乎零成本扛并发；SSR 之后每个首屏请求都烧服务端 CPU，流量一大就得加机器——这笔账要在上线前算，别等压测才发现。开发期的成本也不小：同构的心智负担（window 只是冰山一角）、两端日志一起盯的调试成本、还有 hydration 不匹配时满屏的黄色警告——服务端渲染的 HTML 和客户端首次渲染必须一致，渲染里用了 Date.now()、随机数这种两端必然不同的东西就会炸出来。

判断标准很朴素：**这个页面需不需要被搜索引擎收录、需不需要像样的分享卡片、首屏速度是不是关键体验。**三条中两条沾边，值得上；一条不沾——典型如登录后才能看的后台系统——纯 SPA 又省心又便宜，没必要多绕一层。这个内容站三条全中，选 Nuxt 是划算的。
