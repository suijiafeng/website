Nuxt 初体验：Vue 项目需要 SEO 时，SSR 不是一句配置

2018-04-03
Vue组件与状态

普通 Vue 单页应用开发体验很好，但遇到内容站、官网、营销页时，SEO 和首屏就会变成问题。

事情的起因是我们做了个面向 C 端的内容站，上线两周后运营找过来问：为什么百度搜公司名能搜到首页，但具体的文章页一篇都收不到？我打开线上页面右键"查看源代码"，那一刻就明白了——整个 <body> 里就一个空的 <div id="app"></div>，剩下全是打包出来的 JS。内容是 Vue 在浏览器里跑起来之后才填进去的，可搜索引擎的爬虫（2018 年那会儿百度对 JS 的执行支持还很差）抓到的就是那个空壳。运营要的收录，纯 SPA 给不了。

搜索引擎能不能抓到内容，用户打开页面前几秒看到什么，分享出去有没有标题和描述，这些都不是纯 SPA 最擅长的场景。微信里把链接分享出去，缩略图、标题、摘要全靠 <head> 里的 meta 标签，而 SPA 首屏的 meta 是空的——分享出去一片灰，运营那边也不乐意。Nuxt 的吸引力就在这里：它把 Vue、路由、服务端渲染和项目约定放到了一起，让"服务端先把 HTML 渲染好再吐给浏览器"这件事，不用我从零搭一套 SSR 工程。

要说清楚的是，SSR 这条路我不是没自己趟过。在用 Nuxt 之前，我试过照着 vue-server-renderer 的官方指南手搓一套：要维护一份 entry-client.js、一份 entry-server.js，webpack 得打两份包（客户端 bundle 和服务端 bundle），还要处理 clientManifest、bundleRenderer、状态注水（hydration）……配置文件加起来好几百行，光是把"开发时热更新还能用"这件事调通就花了我两天。Nuxt 本质上就是把这一整套工程约定好、封装好了，我只管写页面。所以我对它的第一印象是：它省掉的不是 SSR 的复杂度，而是搭 SSR 脚手架的复杂度——复杂度还在，只是被挪到了框架里。

不用手写 Vue Router 配置，页面结构会更清楚。Nuxt 会扫描 pages 目录，按文件名和层级自动生成一份 router.js（默认藏在 .nuxt 目录里，想看可以翻出来）。index.vue 对应该层级的根路径，_id.vue 这种下划线开头的就是动态路由参数，对应 :id。

刚上手时我犯过两个有点蠢但很典型的错。第一个是把动态路由写成了 [id].vue——那是后来的写法，2018 年的 Nuxt 用的是下划线 _id.vue，写成方括号直接不识别，路由根本没生成。第二个是嵌套路由：我想做 /posts/:id 下面再带个 /posts/:id/comments，一开始把两个文件平铺放在 posts 目录里，发现父页面的内容没了。后来才搞明白，要嵌套就得有一个和动态目录同名的父组件，再配 <nuxt-child /> 占位：

这套约定的好处是路由结构和目录结构永远一致，新人翻一眼目录就知道站点有哪些页面，不用去对着几百行 router 配置数。坏处是它"太约定"了——文件名就是路由，重命名文件等于改 URL，这事得记在心里，不然哪天手贱把 about.vue 改成 about-us.vue，线上 /about 直接 404，外链全废。

但这也要求团队控制目录层级。页面多了以后，不能什么都扔进 pages 根目录，最好按业务模块组织。真正复杂的交互组件、不对应路由的东西，要放到 components 目录里——pages 目录里的每个 .vue 都会被当成一个路由页面，我有次顺手把一个公共的弹窗组件丢进了 pages，结果 Nuxt 真给它生成了一条路由出来，访问那个 URL 还真能打开个光秃秃的弹窗，闹了笑话。

asyncData 适合服务端取数

Nuxt 里常用 asyncData：

asyncData 在组件创建前执行，可以把数据直接合并到组件实例里。它的关键特性是：首屏由服务端跑，路由跳转由客户端跑。也就是说，用户直接访问 /posts/123（或者刷新这个页面）时，asyncData 在 Node 服务端执行，取到数据后服务端把带内容的 HTML 整个吐出来——这正是 SEO 想要的；而用户在站内点链接从 / 跳到 /posts/123 时，asyncData 改在浏览器里执行，体验就跟普通 SPA 一样。同一段代码，跑在哪一端是不确定的，这件事直接决定了你能在里面写什么、不能写什么。

要注意的是，asyncData 里没有 this。很多刚从 Vue 组件写法切过来的人会踩这个坑——它在组件实例创建之前就执行了，this 自然还不存在。要拿参数、store、重定向这些能力，得从它的入参 context 里解构（{ params, query, store, redirect, error, req, res }），而不是 this.$route、this.$store。我一开始下意识写了 this.$store.dispatch(...)，本地点链接进去没事（客户端有 this），一刷新就 500，因为服务端那次根本没有 this。

由此引出的更深的坑：asyncData 是同构代码，别在里面碰只有浏览器才有的东西。window、document、localStorage 在 Node 端统统不存在，写了就是首屏直接报 window is not defined。我们当时有个取 token 的逻辑顺手写了 localStorage.getItem('token')，本地点进去毫无问题，一上线、用户一刷新就白屏，排查了好一阵才意识到是服务端没有 localStorage。后来的规矩是：凡是要读浏览器环境的，要么挪到 mounted（mounted 只在客户端跑），要么用 process.client / process.server 这两个 Nuxt 注入的标志位做判断。

还有个性能上的隐患我也踩过：asyncData 是阻塞首屏的——服务端会等它 resolve 了才开始渲染。如果里面串行 await 了三四个接口，其中一个后端慢一点，整个页面的 TTFB（首字节时间）就被拖垮，用户对着白屏干等。能并发的接口我一律用 Promise.all 并起来，非首屏必需的数据（比如"相关推荐"）干脆不放 asyncData，挪到 mounted 里异步补，先把主体内容秒出去再说。

head 影响分享和搜索

内容页应该动态设置标题和描述：

如果每个页面都是同一个 title，SEO 和分享体验都会差。我们最初偷懒只在 nuxt.config.js 里配了一个全局默认 title，结果搜索结果里几十个文章页标题全一样，点击率惨不忍睹。后来老老实实给每个内容页都写了动态 head()，标题带上文章名和站点名，描述截取正文前 100 来字。

这里有几个细节是真出过事才记住的。meta 项里那个 hid 千万别漏——它是 Nuxt 用来给 meta 标签去重的唯一标识。我一开始没写 hid，页面级的 description 和 nuxt.config.js 里的全局 description 同时输出，HTML 里就出现了两个 <meta name="description">，搜索引擎到底信哪个全看运气。加上 hid: 'description' 之后，页面级的会覆盖全局的，干净了。

社交分享要的是 Open Graph 那套 og: 标签，得单独补，不是写了 description 就万事大吉：

head() 写成函数（而不是对象）才能用 this，因为这时候组件实例已经建好了，能拿到 asyncData 注进来的 this.post。这也意味着 head 依赖的数据必须先在 asyncData 里取到——顺序不能乱。还有个验证习惯我一直保留着：改完 head 别只在浏览器里看 document.title 对不对，那是客户端渲染后的结果；一定要 curl 一下页面或者"查看源代码"，确认服务端吐出来的原始 HTML 里 title 和 meta 就是对的，因为爬虫看的就是这份未经 JS 执行的源码。

SSR 的接口错误要区分

服务端渲染时接口失败，不能只在浏览器控制台报错。要区分 404 和 500。

如果是服务异常，应该返回 500 或展示错误页，而不是当成空内容渲染。这点在 SSR 里比在 SPA 里严重得多。纯 SPA 接口挂了，页面壳子早就渲染出来了，大不了内容区域显示个"加载失败"，HTTP 响应本身永远是 200。但在 SSR 里，asyncData 抛错、或者你调了 error({ statusCode: 404 })，影响的是服务端这次响应的真实 HTTP 状态码——文章不存在就该让服务端实打实返回 404，搜索引擎才会知道这是个死页面、不去收录；服务挂了就该返 500，前面的 Nginx 和监控才能据此告警。

我踩过最隐蔽的一个坑，就是把"文章不存在"当成了空数据渲染：接口返回 null，我没调 error()，而是 return { post: null }，页面照常渲染了一个空模板，HTTP 还是 200。结果搜索引擎把一堆"内容为空但状态 200"的页面全收录了，过段时间被判定为低质量页面，连累整站权重。从那以后，"取不到数据"和"展示空内容"在我这是两件事，前者必须落到正确的状态码上。

调 error() 之后页面会渲染 layouts/error.vue 这个错误布局，记得自己写一个，别用默认那个丑兮兮的。另外服务端真正崩了（代码抛异常没被 catch）时，Nuxt 默认会渲染一个 500 页，但生产环境别把错误堆栈直接吐给用户看，得在配置里关掉详细错误。

统一 API 错误结构在 SSR 项目里尤其重要，因为错误会影响服务端响应状态。我们当时和后端约定了统一的错误壳子（{ code, data, message }），在请求库的拦截器里把业务失败统一转成约定的形状，asyncData 里只管根据这个形状决定是 error(404) 还是 error(500)，逻辑就清爽了——这套约定值得单独拉出来讲，这里不展开。

部署不是静态文件上传

Nuxt SSR 项目需要 Node 服务运行。它和普通 dist 静态部署不一样。

常见命令：

部署时要考虑：

  • Node 进程管理
  • 环境变量
  • 日志
  • 异常重启
  • 反向代理
  • 静态资源缓存

这块是我交学费最多的地方。第一版上线我天真地 npm run start 直接跑在终端里，SSH 一断进程就没了；后来用 nohup 挂后台，进程崩了也不会重启，半夜挂掉第二天才发现。最后老老实实上了 PM2：pm2 start npm --name web -- run start，它负责崩溃自动拉起、开机自启、还能 pm2 logs 看日志。内存够的话我会开 cluster 模式跑多个实例，把多核利用起来——Node 单进程是吃不满 CPU 的，SSR 又是个 CPU 密集活，每次请求都要在服务端跑一遍 Vue 渲染。

环境变量是另一个坑。SSR 项目的环境变量分两种命运完全不同：只在服务端用的（数据库地址、内部接口域名）可以放心从 process.env 读；要带到浏览器里的，必须通过 nuxt.config.js 的 env 字段显式声明，它会在构建时把值"烤"进客户端 bundle。我有次把一个内部接口地址直接 process.env.INTERNAL_API 在组件里用，服务端好好的，客户端拿到的是 undefined，因为它压根没被打进前端包。还要警惕别把密钥之类的敏感信息丢进 env 字段——那等于明文写进了浏览器能下载到的 JS 里。

反向代理我用 Nginx 挡在前面：静态资源（/_nuxt/ 下那些带 hash 的打包产物）直接由 Nginx 配长缓存（Cache-Control: max-age=31536000），其余请求才 proxy_pass 给后面的 Node。这样 Node 进程只干 SSR 这一件重活，静态文件交给更擅长的 Nginx，QPS 一下就上去了。

如果只是纯静态内容，也可以考虑生成静态站点。Nuxt 提供了 nuxt generate，会把每个路由预渲染成一个个 .html 文件，直接丢到任何静态托管上就行，连 Node 服务都不用养。我们那个内容站后来文章更新没那么频繁，就改成了 generate + 定时重新生成的方案，运维成本陡降。但 generate 的前提是路由能在构建时枚举出来——动态路由 /posts/:id 得在配置里通过 generate.routes 喂给它一份 id 列表，它不会自己去猜有哪些 id。但只要依赖请求时动态渲染（比如内容随登录用户变、或者数据实时性要求高），就要按服务端应用对待，老老实实养 Node 进程。

SSR 不是免费的，要算清这笔账

用了一段时间，我对 SSR 最大的体会是：它把"渲染"这件事从用户的浏览器搬到了你的服务器上，好处是用户体验和 SEO，代价是服务器要扛活。SPA 时代前端是一堆静态文件，扔 CDN 上几乎零成本扛海量并发；SSR 之后每个首屏请求都要在 Node 里跑一次组件渲染，CPU 是会被吃掉的，流量一大就得加机器。这笔账上线前要算清楚，别等被压测打脸。

还有几个开发期的体感变化也得提前有心理准备。一是同构带来的心智负担——前面说的 window 问题只是冰山一角，任何第三方库只要在模块顶层碰了浏览器 API，引进来就可能让服务端构建直接崩，得用 Nuxt 的 plugins 配 { src, mode: 'client' } 让它只在客户端加载。二是调试变难了，报错可能在 Node 端、也可能在浏览器端，得同时盯两边的日志。三是状态注水（hydration）不匹配的警告：服务端渲染的 HTML 和客户端首次渲染的结果必须一致，否则控制台一片黄色警告，最常见的诱因就是渲染里用了 Date.now()、随机数这种两端必然不同的东西。

所以要不要上 Nuxt，我的判断标准很朴素：这个页面需不需要被搜索引擎收录、需不需要好看的分享卡片、首屏快不快是不是关键体验。三个里中两个，就值得上 SSR；一个都不沾（典型就是登录后才能看的后台系统），那纯 SPA 又省心又便宜，没必要给自己找罪受。

Nuxt 确实省掉了很多手搭 SSR 工程的力气，但它没有把 SSR 这件事变便宜。

用它之后，数据获取、错误状态、head、部署和监控都会跟着变。以前只要把静态文件丢到 CDN，现在首屏请求要经过 Node 渲染；以前一个接口错了页面还能自己兜，现在错误最好能落到真实的 HTTP 状态码；以前浏览器 API 随便写，现在同构代码里碰一下 window 都可能让服务端炸掉。

所以我后来判断要不要上 Nuxt，基本先看页面是不是内容站、官网、营销页、分享页这类需要搜索收录和首屏体验的东西。如果只是登录后才看的后台系统，SPA 往往更稳、更便宜，也少很多运维上的账。
