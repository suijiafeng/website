XSS 和 CSRF：前端安全面试题，也是真实项目的底线

2019-08-28
前端基础

前端安全看起来离业务开发很远，但其实很多漏洞都来自普通页面。

评论区显示用户输入、后台富文本、活动页 URL 参数、登录态 Cookie，这些都是安全问题容易出现的地方。面试问 XSS 和 CSRF，不是为了背缩写，而是确认你有没有基本的安全边界意识。

我第一次真正重视前端安全，是公司内部一次安全扫描。一个做了两年的运营活动页被扫出存储型 XSS，原因特别朴素：活动页有个昵称展示，直接 innerHTML 把用户填的昵称塞进去，有人把昵称改成了一段 <img onerror>，于是每个打开活动页的人都执行了那段脚本。那次之后我才明白，XSS 不是什么高深的黑客手段，就是“你信了你不该信的输入”。这篇就按我踩过的坑，把 XSS 和 CSRF 这两块讲清楚。

onerror、onload 这些事件处理器是会触发的，javascript: 伪协议也会。所以别以为“我过滤了 <script> 就安全了”，攻击面比想象的大得多。这也是为什么自己写黑名单过滤基本拦不住——你永远想不全所有能执行 JS 的写法。

XSS 一般分三类，记一下方便定位问题：存储型（恶意内容存进了数据库，比如评论、昵称，影响所有访问者，危害最大）、反射型（恶意内容在 URL 里，需要诱导用户点链接）、DOM 型（漏洞完全在前端 JS 里，比如拿 location.hash 直接塞进 innerHTML，后端都看不到）。前端最该警惕的其实是 DOM 型，因为它绕过了后端的所有过滤，纯粹是前端自己作的。

输出要转义

普通文本应该当文本显示，不要当 HTML：

“白名单过滤”不要自己手写。我见过有人用正则去删 <script>，攻击者一个 <scr<script>ipt> 就绕过去了，删完中间那段反而拼成了完整的 script。正经做法是用成熟的库，2019 年前端这边一般用 DOMPurify：

它会基于白名单解析 DOM 树，把不允许的标签、onxxx 事件、javascript: 协议全清掉，比正则可靠得多。富文本场景我现在一律走 DOMPurify，不自己造轮子。

Vue 用户特别注意 v-html。{{ }} 插值默认是转义的，安全；但 v-html 等价于 innerHTML，直接渲染原始 HTML：

v-html 的内容必须是可信的，或者过滤后的。我们团队约定 code review 看到 v-html 必须问一句“这数据哪来的、过滤了没”。React 那边对应的是 dangerouslySetInnerHTML，名字起得好，dangerously 就是提醒你。

不要相信“后台已经处理过”。前端显示用户输入时，也要知道当前内容是否可信。后端的过滤策略可能跟前端的渲染方式对不上——后端按入库时的规则过滤，前端可能换了种渲染方式，老数据里的脏内容照样能触发。安全要做纵深防御，输入做校验、输出做转义，两边都做，别指望一道关卡兜底。

用 CSP 兜底

光靠转义，难免有遗漏。我后来给重要页面加了一层 CSP（内容安全策略），它是浏览器层面的兜底——就算有一处 XSS 漏过去了，CSP 也能拦住脚本执行。可以用响应头下发：

这条策略的意思是：脚本只允许加载同源的，禁止内联脚本（onerror、<script>alert(1)</script> 这种全废了），禁止 object/embed。配上之后，攻击者注入的内联事件处理器根本跑不起来。

代价是项目里原有的内联脚本、内联事件、eval 都得改掉，老项目接入有改造成本，得逐步收紧。我的做法是先用 Content-Security-Policy-Report-Only 模式跑一段时间，只上报不拦截，看看会误伤哪些东西，确认没问题再切成强制模式。这是个把安全往前端外围再加一道墙的好东西，值得花时间上。

Cookie 和 HttpOnly

如果 token 存在普通 JavaScript 可读的位置，一旦 XSS 成功，就可能被拿走。

Cookie 可以设置：

HttpOnly 能防止 JavaScript 读取 Cookie。它不能阻止所有攻击，但能减少 token 被脚本直接偷走的风险。

这三个属性各管一摊，分清楚：

  • HttpOnly：document.cookie 读不到它，XSS 拿不到这个 cookie。
  • Secure：只在 HTTPS 下发送，防止明文 HTTP 传输时被中间人嗅探。
  • SameSite：限制跨站请求时是否带上 cookie，这是防 CSRF 的关键，下面会展开。

这里有个绕不开的权衡：token 到底存哪。一种是存 HttpOnly Cookie，好处是抗 XSS（脚本读不到），坏处是天然会被浏览器自动带上，所以怕 CSRF，得另配 SameSite 或 CSRF Token。另一种是存 localStorage，前端读写方便、不会自动发送（不怕 CSRF），但 localStorage 任何 JS 都能读，一旦 XSS 整个 token 直接被偷走。

我现在的倾向是：登录态走 HttpOnly Cookie + SameSite，安全性更高；如果架构上必须前端拿 token（比如纯前后端分离、跨域多端），那就要格外重视 XSS 防护，因为这时候 XSS 等于直接交出登录态。没有银弹，关键是想清楚自己堵的是哪个攻击面。

前端不要把敏感 token 随便放到页面变量里。打印日志、上报错误时也要小心，别把 Authorization 头、cookie 内容一股脑塞进监控平台，那等于换了个地方泄露。

CSRF 是什么

CSRF 是利用用户登录态，诱导浏览器向目标网站发送请求。

比如用户已经登录了某后台，攻击页面放一个表单自动提交：

如果目标网站只靠 Cookie 判断登录，浏览器会自动带上 Cookie，危险操作可能被执行。

CSRF 的核心要害就一句话：浏览器在发跨站请求时，会自动带上目标站点的 Cookie。攻击者不需要知道你的 cookie 是什么，他只是借你浏览器的手发了个请求，cookie 是浏览器自动贴上去的。所以 CSRF 偷不走你的登录态，但能冒用你的登录态干事。

理解这点就明白为什么纯 Cookie 鉴权最怕 CSRF，而把 token 放在请求头里手动带的方案天然抗 CSRF——攻击者的页面没法读到你的 token，也就没法在伪造请求里带上正确的头，跨站发的请求缺了那个头，服务端一看就拒了。

CSRF 防护

常见方式：

  • CSRF Token
  • SameSite Cookie
  • 校验 Referer 或 Origin
  • 重要操作二次确认

服务端校验 token 是否匹配。

这几种防护我都用过，简单说下体感。CSRF Token 最经典，服务端下发一个随机 token，前端每次提交带上，服务端比对。它的可靠性来自“攻击者跨站读不到这个 token”。实际接入时要注意 token 怎么传给前端——常见做法是后端塞进页面或者放一个非 HttpOnly 的 cookie 里，前端读出来再放进请求头（这就是 axios 默认支持的 xsrfCookieName / xsrfHeaderName 机制）：

SameSite Cookie 是这两年（2019 前后）我更推荐的方案，因为它在浏览器层面直接挡住跨站带 cookie，几乎零业务改造。设 SameSite=Lax 能挡住大部分跨站 POST，Strict 更严但会影响从外站链接跳进来时的登录态（比如别人发你站点链接，点进去发现没登录）。我一般默认 Lax，体验和安全比较平衡：

校验 Referer/Origin 是补充手段，但 Referer 可能因为隐私设置被浏览器删掉，不能当唯一依据。重要操作二次确认（比如转账要输密码、删除要弹确认）属于业务层兜底，挡不住自动化请求但能拦住一部分。

我现在的标配是 SameSite=Lax 打底，重要写操作再叠一层 CSRF Token，双保险。

GET 不要做危险操作

删除、修改、支付这类操作不要用 GET。

这很危险，因为图片、链接、爬虫都可能触发 GET。

危险操作应该使用 POST、PUT、DELETE，并配合权限和 CSRF 防护。

为什么 GET 特别危险？因为 GET 能被各种东西无声触发：页面里一个 <img src>、一段 <link>、预加载、爬虫、甚至 IM 软件抓取链接缩略图，都会发 GET。攻击者在论坛贴一张图 <img src="https://admin.example.com/delete?id=1">，任何登录态还在的管理员浏览那个帖子，删除就执行了，全程不用点任何东西。GET 应该是“安全且幂等”的——只读、不改状态，这是 HTTP 语义的基本约定，不只是安全要求。

反过来说，把危险操作改成 POST 不等于就安全了，POST 照样能被自动提交的表单触发（前面那个例子就是），所以 POST + CSRF 防护才是完整的。换方法只是第一步。

前端能做什么

前端不能单独解决安全问题，但能做好这些：

  • 不直接渲染不可信 HTML
  • 对用户输入做必要限制
  • 不把敏感信息暴露在页面上
  • 请求层统一带安全 token
  • 对危险操作做确认
  • 接口错误统一处理，不泄露内部信息

安全一定是前后端协作。

XSS 关注脚本注入，CSRF 关注利用登录态发请求。

面试问这两个，是因为它们是 Web 安全基础。项目里最重要的是：外部输入默认不可信，危险操作必须有服务端校验，前端不要把安全当成“后端的事”。

我把这几年的经验压成几条放在心里：渲染任何用户内容默认用 textContent，要 HTML 就过 DOMPurify；v-html / dangerouslySetInnerHTML 一律重点 review；登录态优先 HttpOnly Cookie 配 SameSite；重要页面加 CSP 兜底；写操作不用 GET，并叠 CSRF 防护。这些不是为了应付面试，而是真出过事之后留下的肌肉记忆。安全这事不怕麻烦，怕的是侥幸。
