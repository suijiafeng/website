TCP、HTTP 和三次握手：前端也要懂一点网络基础

2019-10-29
请求与异步前端基础

前端平时写的是页面和请求，但请求为什么慢、为什么会超时、为什么 HTTPS 第一次连接更贵，这些都离不开网络基础。

我一开始也觉得这些是后端和运维的事，直到有一次线上反馈「页面偶尔加载特别慢」，我对着代码看了半天找不出毛病，最后是打开 Network 面板的瀑布图，发现慢的根本不是 JS 执行，而是请求在「Stalled」和「Initial connection」上耗了一两秒。那次之后我才认真补了点网络基础——前端不需要会写协议栈，但你得能看懂浏览器发一个请求背后到底发生了什么，否则面板上那些时间段对你就是天书。

面试里问 TCP 三次握手、HTTP 状态码、HTTPS，也是同一个道理：不是要前端去实现网络协议，而是看你有没有「请求不是瞬间发生」的体感，能不能据此做优化和排错。

一个请求大致经历什么

用户打开页面时，浏览器可能会经历：

  1. DNS 解析域名
  2. 建立 TCP 连接
  3. 如果是 HTTPS，进行 TLS 握手
  4. 发送 HTTP 请求
  5. 服务端处理并返回响应
  6. 浏览器接收响应并渲染

任何一步慢，页面都会慢。这几步在 Chrome 的 Network 面板里其实是能一一对上号的，把请求点开看 Timing：

学会看这张图，比背任何协议都实用。我排查性能问题第一件事就是看 TTFB（Time To First Byte）高不高：TTFB 高，问题在后端或网络链路，再怎么优化前端代码都没用；TTFB 低但 Content Download 长，那是响应体太大，该考虑压缩、分页、懒加载。把锅甩对地方，能省下大量瞎忙的时间。

TCP 三次握手

建立连接需要三次握手：

简单理解：

  • 客户端告诉服务端：我要建立连接
  • 服务端告诉客户端：我收到了，也准备好了
  • 客户端再确认：我也知道你准备好了

这样双方都确认了对方的「发送」和「接收」能力都正常。经常有人问「为什么是三次不是两次」，关键在这里：两次握手的话，服务端无法确认客户端的接收能力，也无法防止历史延迟的重复连接请求把服务端带歪——比如一个早就超时的 SYN 在网络里兜了一圈才到，服务端如果两次握手就建连，会白白维护一个客户端根本不想要的连接。第三次的 ACK 就是客户端在说「这次连接确实是我现在想要的」。

对前端真正有体感的一点是：握手是要花时间的，而且这个时间和物理距离（RTT，往返时延）成正比。一次握手至少一个 RTT。如果用户在国内、服务器在美国，一个 RTT 可能就两三百毫秒，光建连就先耗掉这么多，请求还没发呢。这就是为什么 CDN 把节点铺到离用户近的地方那么重要——它是在缩短 RTT，让握手和传输都快起来。我接过一个面向东南亚用户的项目，接了 CDN 之后首屏直接快了将近一秒，省下的几乎全是连接和传输的往返时间。

四次挥手

关闭连接通常需要四次挥手：

因为 TCP 是全双工的，一方说「我不发了」（FIN），另一方可能还有数据没发完，所以不能立刻跟着关，得先 ACK 确认，等自己也发完了再单独发 FIN。这就比握手多了一步，凑成四次。

挥手里有个细节会实实在在影响服务端：主动关闭的一方会进入 TIME_WAIT 状态，要等 2 倍报文最大生存时间（2MSL，通常几十秒到两分钟）才真正释放。这个设计是为了确保最后那个 ACK 对方能收到、以及让旧连接的残留报文在网络里自然消亡。我见过一台高并发的网关服务器，因为短连接太多，TIME_WAIT 堆积到几万个，把端口耗尽，新连接建不出来——运维当时是靠调内核参数（tcp_tw_reuse 之类）和改用长连接才压下去的。这件事让我直观理解了那句话：连接不是免费的，建和拆都有代价。

Keep-Alive

如果每个请求都重新走一遍「三次握手 + 四次挥手」，成本高得离谱，尤其在 RTT 大的时候。HTTP/1.1 默认就开了 Keep-Alive，让一条 TCP 连接发完一个请求后不立刻关，留着给后续请求复用：

timeout 是空闲多久就关，max 是这条连接最多服务多少个请求。浏览器在这条连接上一个接一个地发请求，省掉了反复握手的开销。在 Network 面板里，复用到已有连接的请求，Timing 里的 Initial connection 和 SSL 是空的——这就是 Keep-Alive 在帮你省钱。

但 HTTP/1.1 的复用有个硬伤：队头阻塞（head-of-line blocking）。同一条连接上的请求是排队的，前一个响应没回来，后面的得等着。所以浏览器对同一个域名会开多条并行连接（一般 6 条）来缓解。这也催生了两类相反的优化套路：

  • HTTP/1.1 时代：合并资源（雪碧图、打包 JS/CSS）、域名分片（把静态资源拆到多个域名，绕开「6 条连接」上限），尽量减少请求数。
  • 2019 年我手上新项目基本都上了 HTTP/2：它在一条连接上做多路复用，多个请求真正并行，队头阻塞在 HTTP 层被解决了。这时候域名分片、过度合并反而是反优化——分片会破坏 HTTP/2 的连接复用。我当年迁到 HTTP/2 后，特地把之前为了 HTTP/1.1 做的雪碧图和域名分片撤了一部分，整体反而更快。

所以「资源要不要合并」这种问题，没有标准答案，得看你跑在 HTTP/1.1 还是 HTTP/2 上——这正是理解底层带来的判断力。

实战里几个容易混的我专门掰扯过：401 和 403 不一样，401 是「你没证明你是谁」（该去登录/刷 token），403 是「我知道你是谁，但你没这权限」——前端拦截器对这俩的处理逻辑完全不同，401 跳登录、403 提示无权限，写错了用户体验就很怪。还有 502 和 504，502 通常是后端服务挂了或返回了非法响应，504 是后端太慢网关等不及超时了，甩锅给后端时说清楚是哪个，能帮他们快速定位。

另外有个新人常踩的坑：HTTP 状态码 200 不代表业务成功。很多后端把业务错误也包在 200 响应里，body 里再带个 { code: -1, msg: '余额不足' }。所以前端的错误处理得分两层——先看 HTTP 状态，再看业务 code，两层都得判。

HTTPS 多了什么

HTTPS 在 HTTP 和 TCP 之间加了 TLS。

它解决三件事：

  • 加密传输：用对称密钥加密内容，链路上抓包看到的是密文；
  • 身份认证：通过证书确认「你连的确实是这个域名的服务器」，不是冒充的；
  • 防篡改：传输内容带校验，中间人改了你能发现。

握手过程简单说是这样：TCP 三次握手建好连接后，再做 TLS 握手——服务端把证书发给客户端，客户端校验证书是不是可信 CA 签发的、域名对不对、有没有过期，校验通过后双方协商出一个对称密钥，之后的通信都用这个密钥加密。这里的代价是 TLS 握手又多了一到两个 RTT，这就是「HTTPS 第一次连接更贵」的来源。

不过这个代价是可以摊薄的：

  • 连接复用：握手只在建连时做一次，后续请求复用同一条 TLS 连接，不再重复握手；
  • 会话恢复（Session Resumption / Session Ticket）：断开后重连，可以带上之前的会话信息跳过完整握手，省掉一个 RTT；
  • HTTP/2 几乎都跑在 HTTPS 上，多路复用 + 一次握手，整体反而比 HTTP/1.1 多条明文连接还快。

所以「HTTPS 慢」这个刻板印象，在做了连接复用和会话恢复之后基本不成立。我经手的项目从全站 HTTP 切到 HTTPS + HTTP/2，性能不降反升。

实际配置里我还踩过两个坑：一是混合内容（mixed content）——HTTPS 页面里引了一个 http:// 的图片或脚本，浏览器会拦截或警告，整个安全锁标识就没了，得把所有外链资源都换成 https 或协议相对的 //；二是证书过期没人管，半夜证书到期全站报 NET::ERR_CERT_DATE_INVALID，用户一片白屏。后来我们上了证书到期监控告警，再没出过这事。

涉及登录、支付、后台系统，HTTPS 是底线，2019 年 Chrome 已经开始把纯 HTTP 页面标「不安全」了。绝对不要在 HTTP 页面里传密码、token 这类敏感信息——明文链路上谁都能抓到。

前端能做什么优化

前端不能控制所有网络细节，但能做一些事：

  • 减少不必要请求：能合并的接口合并，能懒加载的延后，首屏不需要的别在加载时就拉；
  • 静态资源用缓存：强缓存（Cache-Control: max-age）让浏览器压根不发请求，协商缓存（ETag/Last-Modified）让命中时只回个 304，省掉响应体下载；
  • 合理用 CDN：前面说过，重点是缩短 RTT，让握手和传输都快；
  • 接口并行而不是无意义串行：很多人习惯 await a(); await b(); 一个个等，其实没有依赖关系就该 Promise.all([a(), b()]) 并发，省掉一串串行的等待；
  • 控制资源大小：开 gzip/br 压缩、图片选对格式（2019 年 WebP 已经能在大部分场景用了）、按需加载;
  • 超时和错误统一处理：默认 fetch 是不带超时的，得自己用 AbortController 或 Promise.race 包一层，否则后端卡死前端就一直转圈。

错误处理这块我专门封装过一个请求层，把失败分成几类区别对待：

把「网络错误、超时、HTTP 错误、业务错误」分清楚，前端的提示和重试策略才做得对：超时可以自动重试，业务错误（余额不足）重试没意义、该直接提示，401 该跳登录而不是弹个红框。这套分层我在好几个项目里复用，排错效率高了很多。

TCP 负责可靠连接，HTTP 负责应用层的请求响应，HTTPS 在中间塞了一层 TLS 负责安全传输。这几层叠起来，就是浏览器地址栏敲下回车到页面出来之间发生的事。

面试问三次握手和 HTTP，不是让前端去背网络课本，而是让你理解请求不是「瞬间发生」的——它要经过 DNS、握手、传输、服务端处理，每一段都有时间成本，每一段都可能是性能瓶颈或出错点。理解了这条链路，你才知道 Network 面板那张瀑布图在说什么，才知道一个「慢」该往 DNS、连接、TTFB 还是下载哪个方向查，也才明白 CDN、缓存、HTTP/2、连接复用这些优化手段各自在省哪一段的钱。

对我自己来说，补这点网络基础最大的收获不是面试能多答几道题，而是再遇到「页面偶尔很慢」「接口时好时坏」这类模糊问题时，我不再瞎猜，而是能顺着这条链路一段段往下查，把问题精准定位到该负责的那一层。这种排错的笃定感，是值得花时间打的底子。
