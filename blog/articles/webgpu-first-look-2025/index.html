WebGPU 初探：十万点散点图卡死 Canvas 之后的渲染能力预研

2025-08-09
前端基础JavaScript性能与缓存

数据组新给的用户行为散点图，点数从一万涨到了十万。我们后台里那个 Canvas 2D 实现的图表，一万点的时候还算流畅，十万点直接把页面拖到了幻灯片状态：每次缩放重绘要接近一秒，拖拽平移的时候帧率掉到个位数。

这个瓶颈把我推去做了一轮渲染能力的预研。先说结论：这次预研的产出不是一个上线方案，是一份能力边界的笔记——WebGPU 在 Chrome 里已经成熟，能轻松把十万点画到 60fps，但 Safari 的支持今年才刚跟上、还在 beta，生产要用必须带完整降级；而我们眼下这个散点图，最后用一个便宜得多的办法顶住了。过程记下来，等一个真正需要它的场景。

先把 Canvas 2D 的极限摸清楚

优化之前先测量。十万个点，最朴素的画法：

我机器上（M 系列的 MacBook，不算差）一帧 900ms 上下。性能面板里看得很清楚，时间全花在十万次 beginPath + arc + fill 的调用上——Canvas 2D 的每个绘制调用都要走一遍状态检查和路径构建，十万次系统调用级别的开销叠起来就是这个数。

常规优化手段挨个上了一遍。圆点换成 fillRect（矩形不用构建路径），降到 300ms 左右；按颜色分组、每组只设一次 fillStyle、拼成一条大路径再一次 fill，降到 120ms；再把绘制挪进 OffscreenCanvas + Worker，主线程不卡了，但重绘本身还是 100ms 级别——拖拽平移时每帧重绘，交互还是黏。

Canvas 2D 的瓶颈不在画布，在"逐个提交绘制命令"这个模型本身。它是为几百上千个图形设计的即时模式 API，十万个图形就是在错误的抽象层级上干活。要往上走，就得把数据一次性交给 GPU，让 GPU 并行处理每个点——这正是 WebGL 和 WebGPU 的地盘。

WebGL：能解决，但门槛是历史遗留的

WebGL 不是新东西，它能不能解决这个问题？能。事实上图表库早就替大家蹚过这条路，ECharts 有 GL 版本，deck.gl 专门做大数据量可视化，拿来就能用。如果只是"把这张散点图救活"，接一个库是最短路径。

但这次预研我想搞清楚的是自定义渲染的能力储备——图表库覆盖标准图形，真到了要画自定义的密度图、订单流向这类东西，还是得自己碰底层 API。而 WebGL 的底层开发体验，是我几年前试过一次就放下的：它是 2011 年从 OpenGL ES 搬过来的 API，全局状态机设计，bindBuffer、enableVertexAttribArray 这类调用顺序稍微错一点就是黑屏，没有报错，只能靠猜。团队里没人有 GL 背景，维护这种代码的成本我们担不起。

WebGPU 是这条线上的新答案：不背 OpenGL 的历史包袱，按现代 GPU 的实际工作方式设计（对标的是 Vulkan/Metal/D3D12 这代原生 API），错误信息是人话，还带了 compute shader 这个 WebGL 里没有的能力。代价是概念比 WebGL 更多，上手要先啃一遍它的心智模型。

adapter、device、pipeline：概念多，但每个都有用

WebGPU 的初始化是一条链，每一环都是显式的：

adapter 是物理 GPU 的抽象——一台机器可能有集显和独显两块，adapter 就是"选哪块卡"这一层。device 是拿到卡之后开出来的逻辑设备，后续所有资源（buffer、纹理、管线）都从它创建，它也是错误的边界：设备丢了（驱动崩溃、后台回收）会收到通知，可以重建。这两层在 Canvas 2D 里根本不存在，在 WebGL 里被藏在 context 背后，WebGPU 把它们摆到明面上，换来的是对"GPU 什么时候会没了"这件事的显式控制。

真正的核心概念是 pipeline（管线）。它把一次绘制要用的所有配置——顶点怎么读、跑哪个 shader、输出什么格式——提前打包成一个不可变对象，创建时就完成编译和校验：

shader 用的是 WGSL，WebGPU 自己的着色器语言，语法介于 Rust 和 TypeScript 之间，比 GLSL 可读。point-list 拓扑意味着每个顶点就是一个点，正好对散点图。

对比一下 Canvas 2D 的账：那边是十万次 API 调用，这边是数据上传一次、每帧一个 draw call，十万个点在 GPU 上并行处理。实测这一版稳定 60fps，缩放平移只是改一个 uniform 里的 scale/offset，数据 buffer 动都不动。同一份数据，换一个和硬件工作方式对齐的抽象层级，性能差出两个数量级。

代码量也要老实说：Canvas 2D 版本三十行的事，WebGPU 版本连初始化带降级检测写了两百多行。这些概念（adapter/device/pipeline/encoder/pass/bind group）每一个都有存在的理由，但学习曲线确实比"拿起画笔就画"陡得多。

调试体验：比 WebGL 强，比 DevTools 差

写 demo 的过程里专门留意了一下出错时的体验，这是当年劝退我碰 WebGL 的主要原因。

WebGPU 这方面确实进步明显。管线创建时就做完整校验，顶点布局和 shader 入参对不上、格式声明错了，控制台直接告诉你哪个字段、期望什么、实际是什么，行号都给到 WGSL 源码里。我把 float32x4 写成 float32x2 的那次，报错信息读一遍就定位了——同样的错在 WebGL 里大概率是一块安静的黑屏。

需要主动处理的错误有两类。一类走 error scope，包住一段命令，异步收集校验错误；另一类是设备级的意外丢失：

device.lost 这个设计值得点名表扬：GPU 设备本来就可能没了（驱动崩溃、标签页在后台被回收），WebGL 时代这是个容易被忽略的边缘事件，WebGPU 把它做成了必须面对的一等公民。

短板在工具链。Chrome DevTools 对 WebGPU 的支持还很基础，没有像样的帧调试器，想看某一帧 GPU 到底画了什么，得靠平台原生工具（Mac 上是 Xcode 的 GPU 捕获）或者在 shader 里把中间值写进 buffer 读回来——回到了 printf 调试的年代。对习惯了 Elements 面板的前端来说，这个落差要有心理准备。

compute shader：预研里最让我心动的部分

WebGPU 相比 WebGL 真正的新能力是 compute shader——不画任何东西，纯拿 GPU 做并行计算。

计算侧的另一条线是 WebAssembly，适合逻辑复杂但并行度一般的计算，和 compute shader 各管一段，这里不展开。

我只写了个把点做网格聚合的小 demo 验证了一下可行性，没有深入。但这个能力值得记在小本子上：以后遇到"前端要对大数据集做重计算"的需求，选项不止 Worker 和 WASM，还有 GPU。

支持现状与降级：2025 年 8 月这个时间点

预研最后一定要回答"能不能上生产"。现状是这样的：

Chrome 从 113（2023 年 5 月）开始正式支持，到现在两年多，Windows/Mac 上都算成熟，Edge 跟随。我们中后台用户九成以上是 Chrome 内核，这部分没问题。

Safari 今年 WWDC 上宣布了 WebGPU 支持，跟着 Safari 26 走，现在还在 beta，正式版要等秋天的系统更新，而且用户更新系统还得再等一波。也就是说今天面向全量用户的功能，还不能假设 WebGPU 存在。

Firefox 上个月刚在 Windows 版的 141 里启用，Mac/Linux 还在路上。好在它在我们的用户占比里可以忽略。

所以生产可用的姿势只有一种：特性检测加降级。

注意中间那行注释：navigator.gpu 存在不代表能用，虚拟机里、被驱动黑名单命中的老机器上，requestAdapter() 会返回 null，检测要做到 adapter 这一层。这意味着降级路径不是可选项，是必选项——上 WebGPU 等于同时维护两套渲染代码，这笔维护成本要在决定引入之前想清楚。

什么业务根本不需要它

预研写到最后，反而要泼自己一盆冷水。

我们这个中后台，九成九的页面是表格、表单、几千个点以内的常规图表。这些场景 DOM、SVG、Canvas 2D 绰绰有余，图表库开箱即用，可访问性和调试工具链全是现成的。给这些页面上 WebGPU，等于用集装箱货轮送外卖。

就连开头那个十万点散点图，最后的解法也不是 WebGPU。和数据组的同事聊了一轮之后我们想明白一件事：十万个点挤在一块 1200×600 的画布上，每个像素平均摊到零点几个点，人眼根本分辨不出十万个点和"按网格聚合后的两万个带权重的点"的区别。于是先上了服务端聚合加前端抽样，Canvas 2D 版本改都没大改，重绘回到了 30ms 以内，交互顺滑，用户毫无感知。

渲染性能问题的第一解法永远是少画点东西，换渲染技术是第二解法。WebGPU 真正的用武之地，是"数据一个都不能少、交互还要实时"的场景：实时更新的监控大屏、需要逐点交互的分析工具、自定义的密度图和流向图，或者哪天真要做 3D 的仓储可视化。

这些场景我们目前一个都没有。所以这轮预研的结论就是开头那句：Chrome 里它已经好用，Safari 今年刚跟上，能力边界记下了——两百行的 demo 代码放在内部仓库里，等哪天真正的场景找上门，再把它拿出来。
