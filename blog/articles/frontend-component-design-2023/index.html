前端组件设计实践：从能复用到真好用，中间差了什么

2023-11-09
前端基础React组件与状态

前端项目里经常会强调组件化。

按钮做成组件，弹窗做成组件，表单项做成组件，最后看起来页面被拆得很细，代码也“似乎”更复用了。但实际开发几年后，不少团队都会发现一个尴尬的问题：组件确实越来越多，可真正好用、敢复用、改起来不痛苦的组件却没有同步增加。

说到底，组件化不等于组件设计。把页面切成很多文件，只是组织形式变化；组件能不能长期维护，取决于职责边界、数据入口、扩展方式和业务耦合程度。

我踩过最典型的坑，是把一个业务表格越抽越“大”。最开始只是复用分页和 loading，后来加筛选、导出、批量操作、权限按钮、空态文案、固定列、接口请求，最后组件 props 多到没人敢改。它确实复用了很多页面，但每个页面都在被它的抽象限制。那次之后我对“通用组件”这几个字会更谨慎。

组件“能用”不代表“可维护”

很多组件第一次写出来时都很好用，因为它们只服务一个页面、一个场景、一个需求。

问题往往出在第二次、第三次复用时。

这时常见情况是：

  • 新场景需要一个额外参数
  • 旧交互要兼容新的样式
  • 一个组件同时承担多个职责
  • props 越加越多
  • 内部状态越来越难预测

组件没有坏，但它开始变重。更麻烦的是，很多重组件仍然打着“通用组件”的名字，后续业务不得不继续往里面塞参数。

最常见的误区：为了复用而过度抽象

前端开发里一个很常见的问题是过早抽象。

例如一个项目刚做了两个列表页，就急着提炼一个“超级列表组件”，希望分页、筛选、空态、加载态、表头、操作栏全部统一。

参数越来越多，说到底是在用 props 模拟不同页面。这不是复用，而是在制造另一个配置系统。

更稳的做法是先让重复出现三次以上、边界稳定的部分沉淀为组件。只有两个场景时，先保留一点重复，往往比抽象一个不成熟的组件更便宜。

我现在更愿意先抽“能力小组件”，而不是一上来抽“业务大组件”。比如先沉淀 EmptyState、ConfirmDialog、ToolbarButton、Pagination，等多个页面的组合方式稳定了，再考虑更高层组件。小组件失败了也好替换，大组件失败了通常会绑住一堆页面。

好组件通常只解决一个明确问题

稳定的组件往往有一个共同特点：边界清楚。

例如：

  • Button 只负责按钮语义和样式
  • Modal 只负责弹层显示与关闭
  • Table 只负责表格展示，不负责业务筛选逻辑
  • Upload 只负责选择和上传文件，不决定业务归属

组件边界越清楚，后面就越容易判断：这个需求该不该进组件，这个参数是不是越界了，这段逻辑应该放在外层还是内层。

如果一个组件名字叫 CommonButton，但里面判断了订单、文章、客户三种业务状态，它就已经不是通用组件了。组件是否通用，不看文件名，看它是否依赖具体业务概念。

展示组件和业务组件最好分开

很多组件难复用，是因为它既负责 UI，又负责业务。

例如一个“用户列表组件”里同时做了：

  • 请求用户列表
  • 处理分页
  • 判断权限
  • 渲染表格
  • 控制删除弹窗
  • 调用删除接口

这样的组件在当前页面可能很好用，但换一个页面想复用表格展示时，就会被接口、权限和弹窗逻辑绑住。

这个拆法还有一个好处：测试更容易写。展示组件可以用固定 props 做快照或交互测试，容器组件则关注请求、权限和状态流转。把两类逻辑揉在一起，测试往往也会变得又慢又脆。

组件内部状态要谨慎

组件可以有内部状态，但要分清哪些状态应该由外部控制。

适合放在组件内部的状态通常是纯 UI 细节，比如 hover、临时动画、内部输入组合状态。涉及业务流程、数据提交、跨组件同步的状态，最好不要藏在组件内部。

有些组件可以同时支持受控和非受控，但要设计清楚。比如 Tabs 可以内部维护当前 tab，也可以由外部传 value 控制：

这种模式灵活，但实现时要避免“双源状态”。如果外部传了 value，组件内部就不应该再自作主张改最终状态，只能通过回调通知外部。否则父组件和子组件各维护一份当前值，迟早会不同步。

然后 Tabs、Switch、Accordion 都走同一套规则：传了 value 就是受控，组件只发 onChange；没传 value 才用内部状态。这样可以避免每个组件都重新写一遍半受控逻辑，也能减少“外部传了 value 但内部又 setState”的同步 bug。

还有一个容易漏的边界：defaultValue 只在初始化时生效，不应该在每次 props 变化时重置内部状态。很多用户会以为改 defaultValue 能改变当前值，但在 React 组件语义里，真正想控制当前值就应该传 value。

设计系统不是组件仓库

很多团队做组件库时，会把所有组件都扔进去，最后组件库变成另一个业务仓库。真正有价值的设计系统，应该先沉淀稳定的设计 token、基础组件和交互约定。

我会把组件分成几类：

  • 基础组件：按钮、输入框、弹窗、提示
  • 业务组件：用户选择器、组织树、权限面板
  • 页面片段：某个页面专用的卡片、筛选区

只有基础组件适合放进真正的公共层。业务组件可以共享，但要承认它有业务语义；页面片段就留在页面附近，不要强行包装成通用能力。

我现在看到“要不要抽个通用组件”这种需求，会先让它多等一等。

一个组件只在两个页面相似，不代表它已经有稳定抽象；三个页面都在用，也不代表它就应该继续加参数。真正值得抽出来的，是那些职责清楚、变化方向稳定、调用方不需要理解内部业务流程的东西。

好组件不是“参数最多”，也不是“复用次数最多”，而是边界清楚、行为稳定、扩展方式自然。组件设计最难的是克制：不要过早抽象，不要用 props 模拟整个业务系统，不要让展示组件背上业务流程。真正好用的组件，往往只解决一个明确问题，再通过组合去适应变化。
