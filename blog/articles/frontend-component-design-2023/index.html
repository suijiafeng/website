前端组件设计实践：从能复用到真好用，中间差了什么

2023-11-09
前端基础React组件与状态

前端项目里经常会强调组件化。

按钮做成组件，弹窗做成组件，表单项做成组件，最后看起来页面被拆得很细，代码也“似乎”更复用了。但实际开发几年后，不少团队都会发现一个尴尬的问题：组件确实越来越多，可真正好用、敢复用、改起来不痛苦的组件却没有同步增加。

说到底，组件化不等于组件设计。把页面切成很多文件，只是组织形式变化；组件能不能长期维护，取决于职责边界、数据入口、扩展方式和业务耦合程度。

组件“能用”不代表“可维护”

很多组件第一次写出来时都很好用，因为它们只服务一个页面、一个场景、一个需求。

问题往往出在第二次、第三次复用时。

这时常见情况是：

  • 新场景需要一个额外参数
  • 旧交互要兼容新的样式
  • 一个组件同时承担多个职责
  • props 越加越多
  • 内部状态越来越难预测

组件没有坏，但它开始变重。更麻烦的是，很多重组件仍然打着“通用组件”的名字，后续业务不得不继续往里面塞参数。

最常见的误区：为了复用而过度抽象

前端开发里一个很常见的问题是过早抽象。

例如一个项目刚做了两个列表页，就急着提炼一个“超级列表组件”，希望分页、筛选、空态、加载态、表头、操作栏全部统一。

参数越来越多，说到底是在用 props 模拟不同页面。这不是复用，而是在制造另一个配置系统。

更稳的做法是先让重复出现三次以上、边界稳定的部分沉淀为组件。只有两个场景时，先保留一点重复，往往比抽象一个不成熟的组件更便宜。

好组件通常只解决一个明确问题

稳定的组件往往有一个共同特点：边界清楚。

例如：

  • Button 只负责按钮语义和样式
  • Modal 只负责弹层显示与关闭
  • Table 只负责表格展示，不负责业务筛选逻辑
  • Upload 只负责选择和上传文件，不决定业务归属

组件边界越清楚，后面就越容易判断：这个需求该不该进组件，这个参数是不是越界了，这段逻辑应该放在外层还是内层。

展示组件和业务组件最好分开

很多组件难复用，是因为它既负责 UI，又负责业务。

例如一个“用户列表组件”里同时做了：

  • 请求用户列表
  • 处理分页
  • 判断权限
  • 渲染表格
  • 控制删除弹窗
  • 调用删除接口

这样的组件在当前页面可能很好用，但换一个页面想复用表格展示时，就会被接口、权限和弹窗逻辑绑住。

组件可以有内部状态，但要分清哪些状态应该由外部控制。

适合放在组件内部的状态通常是纯 UI 细节，比如 hover、临时动画、内部输入组合状态。涉及业务流程、数据提交、跨组件同步的状态，最好不要藏在组件内部。

小结

好组件不是“参数最多”，也不是“复用次数最多”，而是边界清楚、行为稳定、扩展方式自然。

组件设计的重点是克制：不要过早抽象，不要用 props 模拟整个业务系统，不要让展示组件背上业务流程。真正好用的组件，往往只解决一个明确问题，并通过组合而不是堆参数来适应变化。
