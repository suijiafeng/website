Vue 里 computed 和 watch 怎么选：一次 code review 现场记

2018-11-16
Vue前端基础

computed 和 watch 最容易混掉的时候，是表单联动一多，大家就会本能地用 watch 去把一个字段改出另外三个字段。功能也许能跑，但依赖链一旦长起来，组件很快就会变成没人敢动的多米诺骨牌。

这次 review 我最先警觉的就是这个味道：一个表单页里堆了九个 watch，互相改对方监听的字段，A 触发 B、B 触发 C。代码没有立刻报错，真正的问题是这种结构一旦继续长下去，后面的维护者连改哪里都会先心虚。

我之所以反应这么大，是因为坑我自己踩过。年初做另一个表单页，联动字段也是全用 watch 写，一个字段变了就在 handler 里手动去改另外几个字段。一开始还行，需求加到第五版时，那个组件的 watch 已经互相触发、彼此依赖，改一个地方另一个地方就莫名其妙地不更新或者更新两次。最后调一个"金额偶尔差一分钱"的 bug 调了一下午，根因是几个 watch 的触发顺序在某种操作下变了。那次重构我把所有"派生值"全挪进 computed，组件代码直接少了三分之一，bug 也没了。所以看到新同事这份代码里的九个 watch，我像看到了年初的自己。

开场先把结论放桌上

坐下来我先说了最短的版本，后面所有讨论都围着它转：

如果你只是想基于已有状态推导出一个新值，用 computed。如果你是想在某个值变化后执行副作用——发请求、写本地存储、调第三方接口——用 watch。

更直接一点：computed 应该像一个值，watch 应该像一个动作。值要稳定、可预测；动作可以处理副作用，但要控制边界。这个边界一旦立住，很多代码会立刻顺起来。

他点头说懂了，我说别急，懂概念和认得出现场是两回事，咱们一处一处看代码。

我问他：怎么判断一个值该不该存在 data 里？他答不上来，我给了他一句我自己用的口诀：如果刷新或重新计算，这个值能不能从其他状态恢复出来？能恢复出来的，多半就是派生状态。派生状态进 data 再用 watch 同步，除了啰嗦，还有个隐患：你必须监听所有相关字段，漏一个就出 bug。上面那段如果只 watch 了 firstName 忘了 lastName，改姓不改名时 fullName 就是错的——而且这种 bug 不报错、不抛异常，只是数据悄悄不对，特别难发现。

computed 从机制上杜绝了"漏监听"，因为依赖是 Vue 自动收集的，你用到了哪个值它就追踪哪个，根本不存在"忘了写"的可能。它把"别漏掉依赖"这件事从人脑转移给了框架，这是我更倾向 computed 的底层原因。

他这时候问了个好问题：那我写个 method 在模板里调，{{ getTotalPrice() }}，不也一样？不一样，差在缓存。computed 是带依赖缓存的，只要 items 没变，无论模板里读多少次 selectedTotalPrice，那个 reduce 都只算一遍；methods 则是每次重渲染都重新执行。我之前在一个列表页里把一段稍复杂的过滤逻辑写成 methods，模板里调了好几处，结果每次重渲染过滤都跑很多遍，列表一长就明显卡，换成 computed 立刻顺了。模板里要反复读、且依赖不常变的派生值，优先 computed，除了语义，性能也是实打实的理由。

不过缓存也有个反直觉的坑，我顺手在白板上写给他：computed 只追踪它的"响应式依赖"。如果你在 computed 里读了 Date.now() 或者某个非响应式的外部变量，它不会因为时间流逝而重算，因为 Vue 根本不知道那个东西变了。"为什么我的 computed 不更新"这类问题，十有八九是依赖里混进了 Vue 追踪不到的值。同族的还有数组的坑：this.items[0] = newItem 这种按索引赋值，Vue 2 检测不到，依赖它的 computed 也不会动，得用 this.$set(this.items, 0, newItem) 或者 splice。他说上周正好遇到过一次"改了数据页面不动"，对上了。

第四处：v-model 绑 Vuex，computed 的 setter 出场

表单里还有几个字段存在 Vuex 里，他的写法是模板绑本地 data、再用 watch 同步进 store，绕了一圈。我给他看了 computed 少有人用的另一半：它支持 get 和 set 两种形态，最典型的用处就是给 Vuex 的状态做 v-model 双向绑定——模板要双向绑，但 Vuex 不允许直接改 state，带 setter 的 computed 正好当中间层：

模板里 <input v-model="keyword"> 就能正常用，读走 getter、写触发 commit。但要提醒一句：setter 里只该做"把值写回源头"这一件事，别在里面顺手发请求、做校验。一旦 setter 里塞了副作用，它就又变成了一个伪装成 computed 的 watch，前面说的边界问题会原样回来。读归读、写归写、副作用归 watch，这条线在 computed 内部也得守。

第五处：那个 deep watch 补丁桶

最后过到整个 MR 里最吓人的一个 watch：监听整个 filters 对象，deep: true，handler 四十多行，里面有条件分支、有节流、有两个请求。我问他这是怎么长成这样的，他挠头说：一开始只监听一个字段，后来需求一个个加，就都塞进来了。

这不是他的错，是 watch 太容易被拿来打补丁——每来一个需求就往 handler 里加一段，最后一个 watch 变成了功能中心。**写 watch 要克制，只让它做"变化后的动作"，不要拿它承担状态建模。**复杂 watch 至少要拆出方法：

handler 长到几十行，通常说明它承担了太多职责。

然后是 deep 和 immediate 这两个选项本身。它们都合法，但都要慎用：

immediate 适合组件初始化时就执行一次副作用。我的判断口诀是：如果写完一个 watch，发现 created 或 mounted 里还得手动再调一次同样的逻辑做初始化，那这个 watch 多半就该加 immediate: true——省掉重复调用，也避免初始化逻辑和监听逻辑哪天改得不一致。

deep 的代价要说清楚。它会递归遍历整个对象建立依赖，对象层级深、字段多的时候，每次比对都有开销；更坑的是 handler 拿到的 newVal 和 oldVal 往往是同一个引用——深度监听的是同一个对象的内部变化，对象本身没换，新旧值指向同一处。我被这个坑过：想在 handler 里对比改动前后的差异，结果 newVal === oldVal 永远成立，根本拿不到旧值；要保留旧值得自己提前深拷贝一份，成本就更高了。

散会前的一句话

那个 MR 最后改成什么样：九个 watch 剩下三个（搜索、路由参数、写本地存储），其余全部变成了 computed 链，组件短了一百多行，联动逻辑一眼能看到头。他自己 diff 完说了句"这也太清爽了"。

我让他把判断标准记在便签上，就一句话："这个值是要算出来，还是要顺手做点别的？"算出来的，computed；要顺手去做请求、写缓存、触发外部逻辑的，watch。再配几个例子对照：

  • 表单里 firstName + lastName 得到 fullName：用 computed
  • 购物车商品列表得到总价：用 computed
  • 搜索条件变化后请求接口：用 watch
  • 主题切换后写入本地存储：用 watch
  • 路由参数变化后重新加载详情：用 watch

computed 和 watch 都很重要，但它们处理的问题不是一类：一个是"结果"，一个是"反应"。优先用 computed 表达派生关系，用 watch 处理副作用，这个边界守住了，组件里的状态流就不会变成一团线。下次 review，我希望在他的代码里数 watch 的时候，一只手就够用。
