Vue 里 computed 和 watch 到底怎么选：别把两种能力写成一回事

2018-11-16
Vue前端基础

刚开始用 Vue 时，很多人都会把 computed 和 watch 混着用。

表面上看，它们都能“跟着数据变化做点事”，写起来也都不难。可项目一大，差别就会越来越明显。该放在 computed 里的逻辑写进了 watch，后面会越来越绕；反过来，把副作用塞进 computed，代码也会慢慢变得不好维护。

这两个能力看着相近，职责其实完全不同。

我自己也是踩过坑才把这件事想明白的。早些时候做一个表单页，里面有一堆联动字段：选了省份要联动市、选了套餐要联动价格、勾了优惠券要重算实付金额。我当时全用 watch 写，一个字段变了就在 handler 里手动去改另外几个字段。一开始还行，等需求加到第五版，那个组件的 watch 块已经互相触发、彼此依赖，改一个地方另一个地方就莫名其妙地不更新或者更新两次。最后调一个“金额偶尔差一分钱”的 bug 调了一下午，根因就是几个 watch 的触发顺序在某种操作下变了。那次重构我把所有“派生值”全挪进 computed，组件代码直接少了三分之一，bug 也没了。从那以后我对这条边界特别敏感。

先说最短的结论

如果你只是想基于已有状态推导出一个新值，用 computed。

如果你是想在某个值变化后执行副作用，比如发请求、写本地存储、调第三方接口，用 watch。

这个边界一旦立住，很多代码会立刻顺起来。

更直接一点：computed 应该像一个值，watch 应该像一个动作。值要稳定、可预测；动作可以处理副作用，但要控制边界。

computed 更像“结果”

computed 最适合表达派生状态。

例如购物车里你已经有：

  • 商品列表
  • 数量
  • 单价

那总价就很适合放进 computed。

这个值不需要手动维护，也不需要额外存一份。只要原始数据变了，结果自然就变。

这就是 computed 最舒服的地方：它让状态表达更完整，而不是让你再多维护一份变量。

这些值都不应该手动存在 data 里。它们只是由 items 推导出来的结果。

这里还藏着一个 computed 容易被忽略的好处：缓存。computed 是带依赖缓存的，只要 items 没变，无论模板里读多少次 selectedTotalPrice，那个 reduce 都只算一遍。我之前在一个列表页里把一段稍微复杂的过滤逻辑写成了 methods 里的函数，模板里 {{ filterRows() }} 调了好几处，结果每次重渲染那个过滤都跑很多遍，列表一长就明显卡。换成 computed 之后立刻顺了。所以判断该用 computed 还是 methods，除了语义，性能也是个实打实的理由：模板里要反复读、且依赖不常变的派生值，优先 computed。

不过缓存也有个反直觉的坑：computed 只追踪它“响应式依赖”的东西。如果你在 computed 里读了 Date.now() 或者某个非响应式的外部变量，它不会因为时间流逝而重算，因为 Vue 根本不知道那个东西变了。这种“为什么我的 computed 不更新”的问题，十有八九是依赖里混进了 Vue 追踪不到的值。

watch 更像“反应”

watch 则不是拿来推导结果的，它更像对变化的响应。

请求、日志、埋点、缓存同步，这些都属于 watch 更擅长的范围。

因为 watch 看起来什么都能做。

你完全可以监听某个字段变化，再手动去改另一个字段，于是代码慢慢变成这样：

因为 fullName 并不是独立状态，它只是另外两个值的组合。既然只是组合，就不该手动维护。

这种写法改成 computed 会更自然，也更不容易漏掉边界情况。

判断状态是否应该存在 data 里，可以问一句：如果刷新或重新计算，这个值能不能从其他状态恢复出来？能恢复出来的，多半就是派生状态。

把这种值放进 data 再用 watch 同步，除了啰嗦，还有个隐患：你必须监听所有相关字段，漏一个就出 bug。上面那段如果只 watch 了 firstName 忘了 lastName，改姓不改名时 fullName 就是错的，而且这种 bug 不报错、不抛异常，只是数据悄悄不对，特别难发现。computed 从机制上就杜绝了这种“漏监听”，因为它的依赖是 Vue 自动收集的，你用到了哪个值它就追踪哪个，根本不存在“忘了写”的可能。这是我更倾向 computed 的一个底层原因——它把“别漏掉依赖”这件事从人脑转移给了框架。

一个简单判断办法

可以问自己一句话：

“这个值是要算出来，还是要顺手做点别的？”

如果答案是“算出来”，优先 computed。

如果答案是“要顺手去做请求、写缓存、触发外部逻辑”，那就是 watch。

再补几个例子：

  • 表单里 firstName + lastName 得到 fullName：用 computed
  • 购物车商品列表得到总价：用 computed
  • 搜索条件变化后请求接口：用 watch
  • 主题切换后写入本地存储：用 watch
  • 路由参数变化后重新加载详情：用 watch

别让 watch 变成补丁桶

项目里有个很常见的现象：一开始只是监听一个字段，后面慢慢加条件、加分支、加节流、加异步请求，最后一个 watch 变成了功能中心。

这并不是 watch 的错，而是它太容易被拿来打补丁。

所以在写 watch 时最好克制一点，只让它做“变化后的动作”，不要拿它承担状态建模。

立即执行和深度监听要慎用

watch 支持 immediate 和 deep：

immediate 适合组件初始化时就执行一次副作用。deep 适合监听对象内部变化，但它成本更高，也更容易造成“改一个字段触发一堆逻辑”。

很多时候，把监听对象拆成更明确的字段会更清楚：

不要为了省几行代码，把所有变化都塞进一个深度监听。

deep 的代价具体在哪？它会递归遍历整个对象建立依赖，对象层级深、字段多的时候，每次比对都有开销，而且 handler 拿到的 newVal 和 oldVal 往往是同一个引用——因为深度监听的是同一个对象内部变化，对象本身没换，新旧值指向同一处。我被这个坑过：想在 handler 里对比改动前后的差异，结果 newVal === oldVal 永远成立，拿不到旧值。要保留旧值得自己提前深拷贝一份，成本就更高了。所以能用 string/number 这种基本类型的字段精确监听，就别图省事上 deep。

immediate 也有个我常用的小判断：如果你写完一个 watch，发现 created 或 mounted 里还得手动再调一次同样的逻辑来做初始化，那这个 watch 多半就该加 immediate: true，省掉那次重复调用，也避免初始化逻辑和监听逻辑哪天改得不一致。

computed 和 watch 都很重要，但它们处理的问题不是一类。

一个是“结果”，一个是“反应”。当你不再把它们混着用，Vue 代码会轻很多，状态关系也会更清楚。

优先用 computed 表达派生关系，用 watch 处理副作用。只要这个边界守住，组件里的状态流就不会轻易变成一团线。
