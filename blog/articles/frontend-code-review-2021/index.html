前端代码评审在看什么：不是挑格式，而是提前拦住后续成本

2021-11-22
前端基础

很多团队都有代码评审流程，但大家对它的理解差别挺大。

有人把 review 当成走过场，确认能跑就过；有人把 review 当成语法吹毛求疵，最后搞得大家只敢讨论格式，不敢讨论设计。其实代码评审真正有价值的地方，是在问题还很便宜的时候就把它拦下来。

我自己有过一个很直观的对比。早些年待过一个团队，PR 合并基本靠"看着没问题就 approve"，结果格式不统一、命名风格各异这类东西全靠人眼盯，评审里十条评论有八条在说"这里多了个空格""这个变量名建议改成驼峰"。后来我们做了一件很简单的事——把 ESLint + Prettier 接进 CI，配上 husky 的 pre-commit 钩子，本地提交时自动跑：

格式问题一旦交给机器，评审里那些口水仗瞬间消失了，大家的注意力才真正回到设计和逻辑上。这件事让我彻底想明白一点：凡是机器能管的，就别浪费人的眼睛；人的时间应该花在机器看不出来的地方。

Review 不是在看“你会不会写代码”

评审的重点，不该是证明某个人能力强不强。

它更像一次协作检查，目的包括：

  • 有没有逻辑漏洞
  • 有没有边界没考虑到
  • 有没有不必要的复杂度
  • 有没有破坏现有约定

从这个角度看，review 真正在保护的是项目，而不是在考验某一个人。

我后来给自己定了个习惯：评论里尽量不写"这里不对"，而是写"这里在 xxx 场景下可能会 yyy，要不要确认下"。语气听起来是小事，但它决定了对方是把你当成帮手还是裁判。有一次我评审一段分页逻辑，作者把 pageSize 写死成 20，我没直接说"不该写死"，而是问"如果后端某天要求按 50 拉，这里改起来方便吗"，对方自己就意识到该把它提到配置层。比起我直接下结论，让他自己想通这一步，下次他写别的代码也会带上这个意识。

前端评审尤其要看影响面

前端改动有个特点：很多小改动看起来局部，实际影响面不一定小。

例如：

  • 一个公共组件属性变化，可能影响很多页面
  • 请求层错误处理调整，可能改变全站提示行为
  • 样式类名修改，可能误伤其他模块

所以前端 review 很重要的一件事，就是沿着依赖关系往外看，而不是只盯着当前文件里那几行代码。

我吃过这方面的亏。当时有人改了个基础 Button 组件，把 type 的默认值从 'button' 改成了 'submit'，理由是"大部分场景都在表单里用"。改动本身就一行，看着人畜无害，review 也就过了。结果上线后好几个本来只是装饰用的按钮，放在 <form> 里被点一下就触发了表单提交和页面刷新，线上炸了好几个页面。

从那以后，遇到改公共组件、改请求拦截器、改全局样式这类东西，我都会先把调用方拉出来看一眼到底有多少处在用：

如果一个改动的影响面是几十上百处，那它就不是"一行代码"的评审，而是"一次约定变更"的评审，得用完全不同的谨慎程度对待。判断默认值这种东西，宁可保守——改默认行为永远比加个新参数要危险。

可维护性通常比“这次能跑”更重要

如果只看这次提交能不能工作，很多问题都不会暴露。

但 review 应该多问一步：

  • 下次有人接手能看懂吗
  • 这段封装是不是过度了
  • 错误处理是否统一
  • 状态管理是否清楚

很多技术债不是某次提交直接炸出来的，而是在一次次“先这样也能跑”的放过中积累出来的。

我比较常盯的一个信号，是"过度封装"。前端里很喜欢有人为了一个只用了一次的逻辑，硬抽一个高阶组件或者一个带七八个可选参数的工具函数出来，美其名曰"以后好复用"。但实际情况往往是，这个抽象之后再没被第二处用过，反而让接手的人要先读懂这套抽象才能改一行业务。我现在的判断标准很朴素：抽象至少要有两到三个真实调用点再做，不然就先把重复代码放着——重复是显性的、好改的，错误的抽象才是隐性的、难拆的。

评审时遇到这种，我会直接问一句"现在有几个地方会用它"，答案常常就是"就这一个"。那这层封装的意义就要打个问号了。

测试和验证方式也属于评审范围

前端代码评审不该只看实现，还要看验证。

例如：

  • 这次改动跑了什么测试
  • 手动验证路径是否清楚
  • 是否覆盖了异常情况
  • 构建或兼容性有没有受影响

如果一个改动说不清自己怎么被验证，那就说明它的可靠性还不够扎实。

我们后来在 PR 模板里直接放了一段验证清单，逼大家提交时把这几项填了：

别小看这个清单，光是"异常/边界"那一栏，就逼着作者在提交前自己先想一遍空数据和慢请求的情况。我见过太多 bug 是"正常点一遍没问题就提了"，结果空列表没占位、接口 loading 时按钮能重复点。把这些常见的坑写进模板，等于把团队踩过的雷固化成了每次都要过一遍的检查项。

好的评审不是挑刺，而是让系统更稳

很多人害怕 review，是因为体验停留在“别人专门来挑你错”。但成熟一点的评审，重点其实在于帮提交者把看不见的风险提前暴露出来。

尤其前端页面很多问题并不是作者一眼就能看全，例如：

  • 某个状态在低网速下会不会乱
  • 某个布局在小屏下会不会崩
  • 某个工具函数会不会被其他模块误用

多一双眼睛，不是为了否定，而是为了把系统稳定性再往前推一步。

低网速这一类问题我专门栽过跟头。有个搜索框，作者在本地开发网络飞快，输入即出结果，看着很顺。但线上弱网下，请求返回顺序乱了——先发的请求后到，把后面更新的结果覆盖回了旧的。这种竞态在 review 代码时其实看得出苗头，关键是要养成"看到异步就想一下时序"的习惯：

代码跑起来正不正常，和它在各种真实条件下稳不稳定，是两回事。review 的价值很大一块就在这里——作者沉浸在"我刚写完它能跑"的状态里，往往看不全这些边角，旁边的人反而容易冷静地问出那句"弱网下会怎样"。

Review 最终在培养团队共同的判断标准

代码评审长期最大的价值，不只是每次拦下几个 bug。

更重要的是它会慢慢沉淀出团队对这些问题的共识：

  • 什么算清晰
  • 什么算过度设计
  • 什么边界必须处理
  • 什么验证是最低要求

这些共识一旦形成，后面大家写代码时就会更接近，自然也更容易协作。

所以我一直觉得，前端 code review 不是额外流程，而是项目质量体系的一部分。它真正节省的，往往是后面更贵的返工和维护成本。

真正有价值的 review，通常会多问一句“为什么这样做”

只看结果层面的 review，往往只能发现局部问题，例如某个命名不统一、某个条件判断写得不够简洁。但更影响长期维护的，通常是设计方向：

  • 这段逻辑为什么要放在这一层
  • 有没有复用现有能力，而不是再造一套
  • 这个抽象是真的降低复杂度，还是只是看起来更高级
  • 这次改动是否和现有错误处理、测试方式保持一致

前端项目里很多技术债，不是某一次提交直接写坏了，而是方向一开始就没有被追问清楚，后面大家只能在那个基础上不断补丁。

举个真实的例子。有个需求要在某个页面拿当前登录用户的权限，作者直接在那个页面组件里 fetch 了一遍 /api/permissions，逻辑没毛病，跑得也对。我当时多问了一句"这个权限别的页面是不是也要用，现有有没有地方已经存了"，一查才发现，项目里早就有个 userStore 在登录时就把权限拉好缓存了，只是那位同学不知道。如果当时直接 approve，后面就会有第二个、第三个页面各自重复请求一遍，权限口径还可能不一致。

"为什么放在这一层"和"是不是已经有现成的"这两个问题，单看一次提交都显得有点多余，但正是这两句把方向掰回了正轨。比起事后重构，提交时的一句追问成本低太多了。

Review 最好能沉淀成团队默认写法

如果每次评审都只是临场指出问题，过段时间大家还是会重复踩一样的坑。

所以我更喜欢把高频结论慢慢沉淀成约定，例如：

  • API 层统一错误处理，不在页面里散落判断
  • 改公共组件前先评估兼容影响
  • 每次提交都说明怎么验证
  • 样式类修改要额外关注作用范围

这样做的好处是，review 不只是一次性的把关动作，还会反过来塑造团队的写作方式。长远看，这比单次指出几个 bug 更有价值。

我们的做法是把这些约定写进仓库里的 CONTRIBUTING.md，而不是只留在某次 PR 评论里。评论会被翻篇，文档不会。新人进来先读一遍，评审时如果又遇到同类问题，直接贴文档链接就行，省得每次都重新解释一遍。约定一旦从"某个人的口头偏好"变成"团队写下来的共识"，它的分量和稳定性都完全不一样了。

前端 review 里最该追的，通常是行为变化

很多提交从代码表面看很小，例如改一个 props 默认值、调整一个请求封装返回结构、把一个样式类名换掉。可前端改动的特点就是，局部修改并不一定只影响局部行为。

例如：

  • 一个公共按钮默认类型变化，可能影响多个表单提交逻辑
  • 一个接口错误文案调整，可能改变全站用户提示体验
  • 一个列表组件空状态判断修改，可能导致某些页面直接没有占位内容

所以做前端 review 时，我更在意的不是“这一行写法漂不漂亮”，而是“这次改动会不会让原来稳定的用户路径发生变化”。只要行为变了，就要继续追问验证有没有跟上。

缺少验证说明的提交，风险通常比代码看起来更大

有些提交代码不算复杂，但如果没有清楚说明怎么验证，我通常会更谨慎。因为前端很多问题不是读代码就能完全看出来的，还涉及交互时机、边界状态、不同页面组合和异常路径。

一个比较稳的提交，至少应该说清几件事：

  • 改动影响哪些页面或组件
  • 正常路径怎么验证
  • 异常路径怎么验证
  • 是否跑过 lint、build 或测试

这不是形式主义，而是在帮 review 人更快建立风险地图。说不清验证方式，往往意味着作者自己对影响面也还没有完全看清。
