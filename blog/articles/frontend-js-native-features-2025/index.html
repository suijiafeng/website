容易被忽略的 JavaScript 原生能力：少装库，也能写得更清楚

2025-12-30
前端基础JavaScript

前端项目里，我们很容易习惯性装库。

格式化时间装一个库，处理数组装一个库，深拷贝再装一个库。库当然有价值，但很多需求 JavaScript 原生能力已经能解决。

了解这些能力，可以让代码更轻，也更容易维护。

数组查找和判断

很多数组操作不需要手写循环。

find 用来找第一个符合条件的元素，some 用来判断是否至少有一个符合条件。

如果只是把数组按某个字段分组，2025 年很多运行环境也已经可以考虑 Object.groupBy：

这类 API 的好处是意图非常直白。过去我们可能会用 reduce 写出同样效果，但 reduce 很容易变成“什么都能做，所以读起来要猜”。如果团队的目标运行环境支持，原生语义化 API 往往更适合业务代码。

当然，使用新 API 前要看浏览器和 Node 版本。原生能力不是“新就一定用”，而是要在兼容性、可读性和打包成本之间做判断。

Intl 处理本地化格式

格式化数字、货币、日期时，可以先看看 Intl。

它适合处理多语言、多地区格式，很多时候不需要额外引入大型格式化库。

Intl 不只适合货币，也适合日期、相对时间和列表格式：

我以前在后台系统里见过不少手写格式化函数，刚开始只有中文和人民币，后来要支持英文、美元、日期格式、时区，函数就越补越乱。Intl 的优势不是代码少几行，而是它把本地化这件事交给标准库处理，少了很多“看起来能用，但遇到地区差异就露馅”的边界问题。

URL 和 URLSearchParams

拼接查询参数时，不要手写字符串。

这样可以避免转义、问号、连接符这些细节出错。

手写 query string 最常见的问题不是第一次写错，而是后面需求变多后慢慢出错：数组参数怎么表示、空值要不要保留、中文是否转义、已有参数如何合并。标准 API 至少能把这些细节收束到一套明确行为里。

structuredClone 深拷贝

现代浏览器支持 structuredClone。

它比 JSON.parse(JSON.stringify(data)) 更可靠，能处理更多数据类型。

当然，它也不是万能的。函数、DOM 节点这类内容仍然不适合直接克隆。

我会把 structuredClone 用在“纯数据快照”场景，比如撤销栈、表单草稿、配置副本：

但如果数据里有 class 实例、方法、DOM 引用、响应式代理，就要谨慎。深拷贝并不能替代清晰的数据建模。很多时候真正该做的是把可序列化数据和运行时对象分开，而不是指望一个 clone API 处理所有复杂性。

还有几个值得重新认识的原生能力

Promise.allSettled 适合“多个请求互不影响”的页面。比如仪表盘里有统计、列表、提醒三个接口，某一个失败不应该让整页空白。

这些能力的共同点是：它们不一定炫，但能让代码表达更准确。少装库不是目的，真正的目的其实是少一层不必要的抽象。

延伸阅读

建议常翻 MDN 的 JavaScript reference、TC39 proposals，以及 V8 Blog 对新特性的说明。尤其是 TC39 proposals，能帮你判断一个能力是不是已经稳定，避免在生产项目里过早依赖还在变化的语法。

小结

JavaScript 原生 API 这些年已经补了很多能力。

项目里不是不能用库，而是不要在不了解标准能力的情况下无脑加依赖。先看原生 API 能不能清楚解决问题，再决定是否引入工具库。
