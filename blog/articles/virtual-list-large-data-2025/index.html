虚拟列表与大数据渲染：万行表格卡顿的 DOM 成本账，以及什么时候分页就够了

2025-10-25
前端基础React性能与缓存

先把判断标准放在最前面，因为"上不上虚拟列表"这个决定比实现本身重要。

用户如果不需要在一个连续的滚动容器里浏览全部数据，就不需要虚拟列表，分页或者筛选就够了。中后台的绝大多数表格属于这一类：运营查订单，真实行为是筛选条件缩小范围、翻一两页、找到目标行操作，没有人真的用滚轮从第一行滚到第一万行。给这种场景上虚拟化，收益是零，代价照付。

真正值得虚拟化的场景有明确特征：数据天然连续且用户会长距离滚动（日志流、消息记录）、业务上没法分页（类 Excel 的对账单核对，用户要求"像表格软件一样拖着滚"）、或者列表本身就是交互主体（无限滚动的选品面板）。这次让我把虚拟列表从头到尾做了一遍的，是第三类混合第二类：财务同事的对账页面，一次核对就是八千到一万行，明确拒绝分页——"翻页会打断核对，Excel 里我从来不翻页"。

需求合理，那就得面对 DOM 成本这本账。

万行表格的 DOM 成本账

先量化"卡"。那个对账表格 15 列，每个单元格里还有 span、状态标签、操作按钮之类的结构，平均一行 40 多个 DOM 节点。一万行就是 40 多万个节点，React 组件树的规模同理。

实测下来（测试机是台标配的办公本，用户机器只会更差）：首次渲染 6 秒多，其中 JS 执行两秒出头，剩下大头是 layout 和 paint——40 万节点的首次布局计算浏览器要实打实算一遍。

渲染完之后也不太平。内存占了 1.2GB；随手点一个筛选，style recalculation 就是几百毫秒，INP 直接烂穿。滚动倒是不掉帧（浏览器合成器扛住了），但任何触发重排的交互都是秒级等待。

这几个数字对着看有个规律：DOM 数量是个存量成本，页面上每多一个节点，后续每次布局、每次样式计算、每兆内存都在为它持续付费。这和"某个函数慢"不一样，函数可以优化，存量只能减少。

这里要和另一个话题划清界限：这是 DOM 数量的问题，不是重渲染的问题。去年我写过 React 渲染性能优化，memo、useMemo 那套解决的是"一次交互触发了多少组件重新执行"，而这里就算重渲染优化到零，40 万个节点的首次渲染、布局、内存占用一分都少不了。两个维度各管各的，卡顿排查时先分清是哪一边——打开 Performance 面板，时间花在 commit 之后的 layout/paint 上，就是 DOM 数量的锅。

虚拟列表的思路对症下药：视口高度 800px、行高 40px，一屏其实只能看见 20 行。那就只渲染这 20 行加上下缓冲，滚动时动态替换内容，DOM 里永远只有几十行。一万行的数据，DOM 成本压到常数。

固定行高：三个数就能手写

固定行高的虚拟列表，核心就三个数：scrollTop（滚过去多少）、视口高度（能看见多少）、缓冲区（多渲染几行防白屏）。所有实现都是围绕这三个数做算术：

五十行不到，原理全在这了：外层容器负责滚动，内层用一个总高度为 total * rowHeight 的元素把滚动条撑出正确的长度和比例，真正渲染的那几十行用 translateY 平移到视口对应的位置上。滚动时 scrollTop 变化触发重渲染，slice 出新的窗口。

几个细节值得点一下。

缓冲区（overscan）不是可有可无。滚动事件和渲染之间有延迟，快速滚动时没有缓冲就会看到白屏一闪。缓冲行数也不是越多越好，多一行就多一行的渲染成本，5 到 10 行通常够。

key 必须用数据的稳定 id，不能用数组下标。虚拟列表里同一个下标位置在滚动中会对应完全不同的数据行，用 index 做 key，React 会复用错节点，带内部状态的行（比如展开、输入框）会出现"滚动之后状态串行"的经典 bug。

滚动事件本身不用节流。React 18 之后的自动批处理加上滚动事件的高频触发，实测直接 setState 就够顺滑；真遇到渲染压力，把行组件用 memo 包住（这里重渲染优化又回来了，两个维度在这儿汇合）比给滚动加节流有效得多。

这一版上到对账页面，一万行首次渲染从 6 秒降到 200ms 以内，内存从 1.2GB 回到 200MB 出头，筛选、排序全部回到即点即响。固定行高的虚拟化是性价比极高的手写题，五十行代码换两个数量级的性能。

动态行高：难度陡增的分界线

固定行高的前提是"每行多高是已知的"。一旦行高不定——备注字段会换行、有的行带附件缩略图——难度就不是多写几行代码的事了。

难在两个互相咬合的问题。

第一，总高度和位置都算不准了。第 5000 行的 top 位置是前 4999 行高度的累加，但那些行没渲染过，高度根本不知道。只能先用估计值（比如平均 44px）撑场面，等行真正渲染出来再用 ResizeObserver 量出实际高度，回头修正累加值。

位置计算从一个乘法变成了"估计、测量、修正"的循环，还得维护一套前缀和来做"scrollTop 反查行号"的查询：

二分本身不难，难的是每次测量修正之后，被修正行之后所有的 offset 都要跟着更新。行数大了还得换更讲究的数据结构（区间树、Fenwick 树）来摊薄更新成本。

第二，修正会引发跳动。向上滚动时，上方的行刚被测量出来比估计值高 30px，总高度和当前行的位置跟着变，视口里的内容猛地一跳。要压住跳动，得在修正的同时补偿 scrollTop，这块的边界情况多到写起来怀疑人生——快速拖动滚动条、跳转到某一行、窗口 resize 触发全量重新换行，每一个都能制造新的跳法。

我手写到这一步就停了。固定行高值得手写，动态行高属于"知道原理，然后用库"的领域——这些边界情况是虚拟化库的核心资产，没必要自己再踩一遍。

TanStack Virtual：headless 的取舍

选型没花太多时间。react-window 是老牌选择，组件式封装，固定场景开箱即用，但它对表格结构、动态测量的支持要绕着写；TanStack Virtual v3 是 headless 思路，只提供 hook 和计算结果，DOM 结构完全自己搭，动态测量是一等公民。我们的场景要自定义表格结构，选了后者。

结构和手写版一模一样——撑高、平移、渲染窗口——只是三个数的算术和"估计、测量、修正"那套脏活全部由 useVirtualizer 接管，measureElement 挂上去动态行高就工作了。

headless 的取舍两面都要说。好处是它不碰你的 DOM，表格、固定列、行内展开这些结构上的自定义完全不受库的约束，出了样式问题也好排查，因为每个节点都是自己写的。代价是没有"开箱即用"这回事，滚动容器、定位结构、样式全要自己搭，搭错了（比如忘了 position: relative）库不会报错，只会表现得很怪。

对我们这种本来就要深度自定义表格的场景，这个取舍是划算的；如果只是一个简单的选项列表要虚拟化，react-window 那种十行代码完事的封装反而更合适。

滚动位置：两个容易漏的行为

虚拟化改变了"位置"的含义，有两个行为上线前要专门处理，都是真实被用户报出来的。

一是筛选之后要重置滚动。切换筛选条件，数据从一万行变成三百行，但滚动容器的 scrollTop 还停在原来的位置——超出了新总高度，虚拟列表要么白屏要么定格在最后几行。数据源变化时手动 scrollToOffset(0)，一行代码，漏掉就是灵异现象。

二是从详情返回要恢复位置。财务核对到第 6000 行，点进凭证详情再返回，列表回到了顶部，前面滚的全白费。传统长列表浏览器自己会记 scrollTop，虚拟列表恢复 scrollTop 还不够——数据要先就位，估高要稳定。我们的做法是离开时把当前 range.startIndex 存进路由 state，返回后数据加载完成再 scrollToIndex(savedIndex, { align: 'start' })。虚拟列表里"位置"的唯一可靠货币是数据索引，不是像素，像素在动态行高下每次测量都会漂。

数据侧的配合：一万行 JSON 也要算账

DOM 的账算完，数据的账也不能拉下。一万行对账数据一次性拉回来是 8MB 出头的 JSON，接口要三四秒，解析和 setState 又是一下卡顿。

虚拟化天然适合配合按块加载：virtualizer 暴露当前渲染区间，滚动到哪个区间就取哪一块，配合数据缓存，体验上和全量加载没区别：

没加载到的行渲染成骨架占位，行高按估计值撑住，数据到了原地替换。对账这个场景财务通常从头顺序核对，命中率很高，几乎感觉不到加载。

不过这一步是可选的锦上添花。如果接口本身快、数据在 2MB 以内，全量拉回来放内存里反而简单可靠，排序筛选都能纯前端做。我们最后是折中：默认按月份拉全量（几千行，1MB 级），跨月核对才走按块加载。

表格场景的特殊性

对账页面是表格，虚拟化表格比虚拟化列表多几个坑，单独记一下。

原生 <table> 结构和虚拟化的定位方式基本处不来。行要绝对定位或者 transform 平移，而 <tr> 脱离 <tbody> 的正常流之后，表格自己的列宽分配算法就废了，表头和内容的列对不齐。业界的主流做法干脆放弃 table 布局，用 div 加 CSS Grid：表头和每一行都是同一个 grid 模板，列宽天然对齐，行随便定位。

固定列用 sticky 就能做：某一列 position: sticky; left: 0，配合行内的 grid 布局，横向滚动时冻结列稳稳贴住。倒是横向虚拟化——列多到几百根的时候连列都只渲染可见的——TanStack Virtual 也支持（再起一个横向的 virtualizer），但我们 15 列远没到那个量级，评估之后没上。横向虚拟化的复杂度和纵向不是加法是乘法，列数没上三位数别碰。

表头对齐还有个小坑：纵向滚动条出现后会占掉容器几像素宽度，表头没滚动条、内容有，两边就差一条缝。用 scrollbar-gutter: stable 给两边都预留出滚动条位置，一行 CSS 了事。

中间档：content-visibility 有时能白嫖一半收益

在"什么都不做"和"完整虚拟化"之间，其实还有个便宜的中间档，评估时值得先试一下：CSS 的 content-visibility。

content-visibility: auto 让浏览器跳过视口外元素的渲染工作——布局、绘制都不做，滚近了再算。DOM 节点还在（所以 Ctrl+F 还能搜到，可访问性没有代价），但首次渲染和重排的成本大幅下降。相当于浏览器帮你做了一半虚拟化，代码一行 JS 都不用写。

它的边界也很清楚：节点本身还是全量创建的，React 的组件树、内存占用、首次 commit 的 JS 执行一分没省。我们拿一万行的场景试过，首渲染从 6 秒降到 2 秒多——好了一大截，但离能用还差得远。content-visibility 适合"几百到两三千行"这个中间规模，再往上还是得上真正的虚拟化。对那些没到万行量级、又懒得动结构的存量页面，这一行 CSS 是性价比之王。

可访问性的代价，明码标价

虚拟列表不是免费午餐，它砍掉的 DOM 里有些东西是有用的，上线前最好把这些代价一条条过给使用方听。

最直接的是 Ctrl+F 失效。财务同事第一天就发现了：浏览器的页内查找只能搜到已渲染的几十行，"我搜一个单号说找不到，明明表里有"。这个没有技术解法，只有产品解法——在表格上方做一个搜数据而不是搜 DOM 的查找框，命中后用 virtualizer.scrollToIndex() 跳过去。做完之后财务反馈比 Ctrl+F 还好用（毕竟能按列精确匹配），但这个功能是虚拟化强加给你的必做项，评估工作量时要把它算进去。

屏幕阅读器同理，DOM 里只有几十行，读屏软件就认为表格只有几十行。缓解手段是 ARIA：容器上标 aria-rowcount 声明真实总行数，每行标 aria-rowindex 声明自己的真实序号，读屏用户至少能知道自己在一万行里的第几行。内部系统这条常被跳过，但加上就是几个属性的事。

还有全选、导出这类"作用于全量数据"的操作，实现时必须走数据层而不是 DOM 层——这在虚拟化之后反而是好事，逼着你把"视图上的行"和"数据里的行"分干净。

行内的交互状态也是同一个道理。勾选、展开、行内编辑的草稿，都不能存在行组件自己的 state 里：行滚出视口就被卸载，滚回来是一个全新挂载的组件，state 全丢。财务勾了三十行准备批量确认，往下滚一段再滚回来发现勾选全没了，就是这个原因。虚拟列表里的行组件要当成无状态的渲染函数写，一切状态按行 id 存到上层，勾选集合就是一个 Set<string>，展开状态就是一张 id 到 boolean 的映射。

顺带提一句测试。e2e 测试里"断言第 9000 行的单元格内容"这种用例会直接失败——那行根本不在 DOM 里。用例要先调 scrollToIndex 把目标行滚进视口再断言，或者干脆改成断言数据层。QA 同学第一次跑旧用例集时一片红，这个坑值得提前打招呼。

回到开头的判断

对账页面上线一个月，一万行拖着滚很顺，财务的核对流程没再被打断过。全部投入算下来：核心虚拟化两天（其中手写原型半天，换 TanStack Virtual 加动态行高一天半），表格结构改造一天，查找框、位置恢复、ARIA 这些配套又是两天多——配套的工作量和核心差不多，这个比例报工期时别漏。

但同一个迭代里，另一个页面我们把虚拟化的提案否了。

订单列表页也喊卡，产品最初的诉求同样是"能不能一次全加载出来"。追问两句真实用法就露馅了——运营永远是先筛选再看，单次看的数据没超过三页。那个页面最后只是把默认每页 20 条改成 100 条、加了两个常用筛选的快捷入口，卡顿投诉消失，一行虚拟化代码都没写。

所以还是开头那句话：先看用户是不是真的要在一个滚动容器里浏览全部数据。是，虚拟列表值得做，三个数的算术加一个成熟的库，代价也明码标价；不是，分页就够了——没上虚拟列表的那个页面，和上了的这个，是同一个判断标准的两个答案。
