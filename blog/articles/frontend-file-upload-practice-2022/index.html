前端文件上传实践：进度、取消、重试和错误提示都要设计

2022-06-10
前端基础构建与模块化

文件上传看起来只是一个 input。

真实业务里就没这么简单了。要限制类型和大小，要显示进度，要能取消，要处理失败重试，要支持多文件，有时还要分片、断点续传、秒传。

我做上传组件踩过一个坑：只处理成功路径。测试时文件小、网络好，一切正常。线上用户传大文件，中途网络断了，页面只停在 73%，没有错误提示，也不能重试。用户不知道是失败了还是还在传。

上传功能一定要把状态机设计清楚。

先做前端基础校验

前端可以先校验文件类型、大小、数量：

这能减少无效请求，提升体验。

但前端校验不是安全防线。文件类型可以伪造，大小限制也能绕过。后端必须重新校验。

进度要来自真实上传

如果用 XMLHttpRequest，可以拿到上传进度：

Fetch 在 2022 年做上传进度不如 XHR 方便，所以很多上传组件仍然用 XHR。

进度条不要假进度到 100%。如果服务端还要处理文件，上传完成后可以显示“处理中”，等接口返回最终结果。

取消上传要有入口

用户选错文件时，应该能取消。

XHR 可以 abort：

取消和失败要区分。用户主动取消，不应该提示“上传失败”。

如果是 fetch，可以用 AbortController。无论哪种方式，取消后都要清理当前文件状态。

多文件要控制并发

一次上传几十个文件时，不要全部同时发。

可以限制并发，比如一次 3 个：

上传大文件尤其要克制并发。并发太高会互相抢带宽，每个都慢，失败率还更高。

分片上传要有服务端配合

大文件上传常用分片：

前端切片：

分片上传不是前端单方面能完成的。服务端要提供分片接收、合并、校验、清理过期分片的能力。

如果要断点续传，还需要文件 hash 或服务端 uploadId。前端先问服务端哪些分片已经有，再补传缺失的。

API 错误要能落到文件

多文件上传时，错误不能只弹一个全局 toast。

每个文件都应该有自己的状态：

接口返回错误时，标记到对应文件：

用户才能知道哪一个失败了，是否需要重试。

我的上传清单

做上传功能时，我会检查：

  • 前端是否校验类型、大小、数量
  • 后端是否也做安全校验
  • 是否有真实上传进度
  • 上传完成后服务端处理阶段是否有状态
  • 是否支持取消
  • 多文件是否限制并发
  • 单个文件失败是否能单独重试
  • API 错误是否落到对应文件
  • 大文件是否需要分片和断点续传

上传不是一个按钮，而是一条长链路。用户最需要的是可见状态和可恢复能力：知道传到哪了，失败为什么，下一步能做什么。
