Chrome DevTools 性能排查：别只看感觉，要看主线程在忙什么

2018-09-05
性能与缓存前端基础

页面卡顿的时候，团队里最容易出现的场景是这样的：产品在群里发一段录屏，说"列表滑起来一卡一卡的，体验太差了"，然后大家开始猜。后端说接口已经很快了，做活动页的同学说肯定是那个新加的动画，写组件库的同学说会不会是 Vue 的 watch 太多。猜了半小时，没人去录一段 Performance。

我自己也踩过这个坑。早些年遇到卡顿，第一反应是去翻代码，看哪里写了循环、哪里 setInterval 没清。翻到的"嫌疑犯"一改一大堆，上线之后卡顿照旧，因为真正的瓶颈根本不在那。后来养成习惯：先打开 Chrome DevTools 的 Performance 面板录一段，看主线程那一帧到底在忙什么，再决定动哪行代码。

下面按我这两年用 Performance 面板排查问题的顺序写，包括怎么读火焰图、怎么定位长任务、怎么抓重排、怎么把 Network 和 Performance 对着看，以及几次具体的踩坑。

先把一次"标准录制"做对

很多人打开 Performance 就直接点 Record，操作一通停下来，结果录了 20 秒，火焰图密密麻麻一片，自己都看不懂。录制这件事是有讲究的。

我的固定流程是：

  • 先确定要复现的那个动作。是首屏加载慢，还是滚动卡，还是点击某个按钮后界面冻住？一次只测一个，别又加载又滚动又点击混在一起。
  • 录制前在 DevTools 顶部勾上 Screenshots（截图），这样火焰图下面会有一排页面快照，能直观看到哪一帧画面"卡住没动"。
  • 如果是测加载，用面板左上角那个带圆圈的刷新按钮（Reload）来录制，它会清空再从导航开始记录，比手动 record 再刷新干净得多。
  • 录制时间尽量短，2 到 4 秒足够。卡顿是瞬间的事，录太长只会让你在火焰图里大海捞针。

录完之后，从上到下我会依次看这几条泳道：

  • Main：主线程，最重要的一条。黄色是 Scripting（执行 JS），紫色是 Rendering（样式计算、布局），绿色是 Painting（绘制），灰色是其他系统占用。
  • Frames：每一帧的耗时，绿条越长说明那帧越慢，飘红就是掉帧。
  • Interactions / Timings：用户交互和一些性能打点。
  • Network：这一时间段内的网络请求瀑布。
  • 顶部的 Summary 那条彩色横条，是整段时间各类工作的占比，先看个大概：到底是 Scripting 多还是 Rendering 多。

判断方向就靠颜色比例：主线程被大片黄色填满，说明 JS 执行是大头；紫色一段一段反复出现，多半是频繁触发布局；如果一帧里黄紫绿都不多但帧还是很长，那要怀疑是不是在等网络或者主线程被某个长任务整个占住了。

长任务：那条标着红角的黄块

Performance 里最该警惕的，是主线程上那些右上角带红色三角的灰/黄色块。鼠标移上去会显示 "Long Task"，并标注比如 Task — 320 ms。浏览器把超过 50ms 的任务定义为长任务，因为这期间主线程被独占，用户的点击、滚动、输入全得排队，体感就是"点了没反应"。

我处理长任务一般有几条路，按优先级排：

第一，能不算就不算。 很多时候那几万条数据用户根本看不完，真正要渲染的就首屏那二三十条。先做虚拟列表或分页，数据量降下来，长任务自然没了。这是收益最大、最该先想的。

第二，分片执行。 实在要算完，就把大循环切成小块，每块算一点，把控制权还给浏览器。2018 年我常用的写法是配合 requestIdleCallback（Chrome 已支持，注意 Safari 不支持要降级）：

重排重绘：从火焰图里揪出"读写交错"

主线程里如果出现密集的紫色 Layout（在面板里展开能看到 Layout / Recalculate Style），而且某个 Layout 块上标着红角写着 "Forced reflow is a likely performance bottleneck"，那基本能锁定是强制同步布局（forced synchronous layout，俗称 layout thrashing）。

它的成因是：你刚改了样式，紧接着又去读一个需要最新布局信息的属性（offsetHeight、offsetWidth、getBoundingClientRect、scrollTop 这些），浏览器为了给你准确的值，只能立刻把还没结算的布局算一遍。放在循环里就是灾难：

这里有个我以前没意识到的点：触发布局的不只是显式读 offsetHeight。像在改了 DOM 之后立刻读 getComputedStyle、或者读 scrollWidth，都会触发。排查时我会把 Main 泳道里那段紫色块点开，看下面调用栈定位到具体哪一行 JS，再回代码里找那行附近的读取操作，八九不离十就是它。

还有个容易混的概念：重排（Layout）一定伴随重绘（Paint），但重绘不一定有重排。如果只是改 color、background 这种不影响几何的属性，理论上只 Paint 不 Layout。想确认有没有不必要的绘制，可以用 DevTools 的 Rendering 标签页（在更多工具里打开），勾上 Paint flashing，页面上发生重绘的区域会闪绿色高亮——滚动时如果整屏都在闪绿，那绘制开销就太大了，得考虑用 transform/opacity 配合 will-change 把动画提升到合成层，避开主线程绘制。

Network 和 Performance 要对着看

首屏慢，新手第一反应总是"是不是 JS 太慢"，但很多时候主线程闲得很，是在干等资源。这种情况光看 Performance 的 Main 泳道会一脸懵：怎么前面一两秒主线程几乎是空的？

这时候得把 Network 面板一起拉出来看。我排查首屏的固定动作：

Network 面板里重点看几样：

  • HTML 文档本身的 TTFB（绿色那段，等待服务器响应的时间）长不长，长就是后端或网络问题，前端再优化也没用。
  • 主 JS bundle 多大、下载花了多久。2018 年 webpack 项目动不动打出一个 2MB 的 vendor 包是常事，不做 code splitting 首屏就得干等它下完。
  • 图片有没有压缩、有没有用对格式，首屏大图是不是该懒加载。
  • 字体文件加载时是不是阻塞了文字渲染（FOIT），考虑 font-display: swap。
  • 接口请求是不是串行瀑布——一个请求回来才发下一个，瀑布图里呈阶梯状下滑，那就该并行或合并。

Performance 面板里则看资源到位之后：

  • 解析执行那个大 bundle 花了多久（下载完之后那根长黄柱）。
  • 主线程是不是被 JS 执行阻塞，导致首屏迟迟不绘制。
  • 首次内容绘制（FCP）、DOMContentLoaded 这些标记线落在什么位置，前面那段空白都耗在哪了。

两个面板对齐时间轴一起看，才分得清到底是"东西没下来"还是"下来了处理太慢"。我有次排查一个活动页首屏 5 秒白屏，Performance 上主线程前 3 秒基本是空的——一看 Network，是首页同步加载了一个第三方统计脚本，那个域名当时解析特别慢，把整个文档解析都堵在那。把它改成 async 之后白屏直接降到 1 秒出头。要是只盯着 Performance 的 JS 执行去优化，永远找不到这个原因。

千万别只在自己这台机器上测

这是我觉得最该写进每个前端入职手册的一条。开发机一般是公司配的高性能笔记本，网络是稳定的办公室宽带，你在上面怎么点都流畅。但用户里有相当一部分用的是两三年前的千元安卓机，CPU 弱、内存小，网络是地铁里时断时续的 4G。你这边"丝般顺滑"的页面，在他们手上可能就是一卡一卡。

DevTools 提供了两个限制开关，录制时务必打开：

  • CPU throttling：在 Performance 面板顶部，可以选 4x slowdown 或 6x slowdown，模拟低端 CPU。我默认用 4x 来测，很多在本机看不出问题的长任务，一降速立刻原形毕露。
  • Network throttling：可以选 Fast 3G / Slow 3G，模拟弱网。测首屏加载尤其要开。

这两个模拟当然不完全等于真实设备——真机还有 GPU 差异、系统调度、后台进程抢占等等——但比只在高配电脑上看强太多了。条件允许的话，最靠谱还是拿一台真实的低端安卓机，用 USB 连上电脑做远程调试（chrome://inspect），直接在真机上录 Performance，那才是用户真正的体感。做移动 H5 的话，这一步省不得。

Memory 也得顺手看一眼

有一类卡顿不是单帧慢，而是页面用着用着越来越卡，关掉重开又好了——这八成是内存泄漏，火焰图里看不出来，得换 Memory 面板。

我排查内存的土办法很朴素：打开 Performance，把顶部的 Memory 勾上录一段，操作过程中如果那条 JS Heap 的蓝线只涨不回落、像台阶一样一级级往上，就说明有东西没被回收。常见元凶就那么几个：

  • 绑了 addEventListener 没解绑。组件销毁了，监听还挂在 window 或某个全局对象上，闭包把整个组件实例都拽住不放。
  • setInterval / 定时器没 clear。Vue 里 beforeDestroy 忘了清，路由切走了定时器还在跑，还引用着旧数据。
  • 全局缓存（一个不断 push 的数组、一个只进不出的 Map）越攒越大。

确认到底是什么没回收，用 Memory 面板的 Heap snapshot：操作前打一张快照，操作几轮后再打一张，用 "Comparison" 比对两张之间新增了哪些对象。我有次就是这么揪出一个弹窗组件——每开关一次就多一个 detached DOM 节点（已从页面移除但仍被 JS 引用，回收不掉），开几十次内存就上去了，根源是一个没解绑的 resize 监听。

性能排查别只盯着 CPU，内存这条线漏了，表现出来也是"卡"，但火焰图怎么看都看不出原因。

几个我常用的小习惯

攒一些零碎但好用的点：

  • 火焰图里看到不认识的函数，鼠标悬停能看到它的来源文件和行号，点一下能跳到 Sources。匿名函数和被压缩的代码很难认，本地复现时尽量在开发模式跑，符号清楚。
  • User Timing 很值得用。在关键逻辑前后打 performance.mark() 和 performance.measure()，这些标记会直接显示在 Performance 面板的 Timings 泳道里，比在火焰图里数毫秒精确多了：
  • 怀疑某段时间有问题，但火焰图太长，可以在概览区框选一段时间，下面的明细就只统计这段，Bottom-Up / Call Tree 看起来清爽很多。
  • Bottom-Up 视图按"自身耗时"排序，特别适合找出那个被反复调用、单次不起眼但累计很贵的函数。
  • 三个视图别只用一个：Call Tree 看自顶向下的调用结构（适合理清"这一帧从哪个入口开始忙的"）；Bottom-Up 看谁自身最贵；Event Log 按时间顺序平铺所有事件，适合定位"某个时间点突然插进来一件什么事"。
  • 怀疑是某个第三方脚本拖慢的，可以在 Network 面板右键把它的请求 Block（请求拦截），再录一次对比有没有它的差别。我用这招验证过好几次"到底是不是那个统计 SDK 的锅"，比改代码再发版快多了。
  • 想量化普通用户的体感，不一定每次都开 Performance。线上可以用 PerformanceObserver 采集长任务上报，攒一段时间看真实分布，比你本机偶尔录一段有代表性：

性能问题别凭感觉动手：先用 DevTools 的火焰图看主线程在忙什么，确定是 JS、布局、绘制还是网络瓶颈再着手优化。按“限速复现 → 定位长任务/强制布局 → 对齐网络”这个顺序，问题会更快被击中，也更容易验证修复效果。

Chrome DevTools 给的不是最终答案，它给的是"主线程在忙什么"。知道忙在哪，优化才不会乱打一气。
