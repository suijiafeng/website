Chrome DevTools 性能排查：别只看感觉，要看主线程在忙什么

2018-09-05
性能与缓存前端基础

页面卡顿时，最怕凭感觉优化。

有人说是框架慢，有人说是接口慢，有人说是 CSS 写得不好。猜来猜去，不如打开 Chrome DevTools 看主线程到底在忙什么。

Performance 面板是排查前端性能问题最直接的工具之一。

先录制操作

打开 Performance，点击 record，然后复现问题：页面加载、点击按钮、滚动列表、展开弹窗。

录制结束后重点看：

  • Main 线程
  • Long Task
  • Scripting
  • Rendering
  • Painting
  • Network

如果主线程长时间被黄色脚本占满，说明 JS 执行是重点。如果紫色布局很多，可能是频繁触发布局。

长任务会阻塞交互

一个同步循环：

执行时主线程被占住，用户点击和滚动都要等。

解决方式可能是：

  • 减少计算量
  • 分片执行
  • 使用 Web Worker
  • 延迟非关键任务

不要把所有初始化逻辑都放在页面加载第一时间执行。

重排重绘要找触发点

危险写法：

读布局再写样式，反复交替，容易触发多次 layout。

更好的方式是先读完，再统一写：

Performance 里如果看到大量 Layout，就要检查是否有这种读写交错。

Network 和 Performance 要一起看

首屏慢不一定是 JS 慢，也可能是资源慢。

Network 面板看：

  • HTML 响应是否慢
  • JS 包是否过大
  • 图片是否未压缩
  • 字体是否阻塞
  • 接口是否串行

Performance 面板看：

  • 下载后解析执行是否慢
  • 主线程是否被阻塞
  • 渲染是否频繁

两个面板结合，才能知道瓶颈在哪。

不要只测自己电脑

开发机通常性能很好。用户可能用的是低端安卓机，网络也不稳定。

DevTools 可以做 CPU throttling 和 network throttling。虽然不完全等同真实设备，但比只在高配电脑上看强很多。

移动 H5 尤其要这样测。

小结

性能优化不要从猜开始。先录制，确认是脚本、渲染、绘制、资源还是接口问题，再动手。

Chrome DevTools 给出的不是最终答案，但它能告诉你主线程在忙什么。知道忙在哪里，优化才不会乱打。
