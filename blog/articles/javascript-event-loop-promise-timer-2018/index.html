事件循环、Promise 和 setTimeout：把执行顺序背后的调度图理顺

2018-04-12
JavaScript前端基础

事件循环最坑人的地方，不是概念多，而是概念一离开代码就会变飘。Promise、setTimeout、async/await 平时都在写，链式调用和错误捕获也不难讲；可一旦把它们放进一段输出顺序题里，很多"我懂"会立刻露馅。

组里那次异步分享上，主讲人没有停在 Promise 用法上，而是切到一页空白编辑器前，连续丢了几道执行顺序题让大家现场回答。第一题就有人磕了一下，第二题不少人答错，后面每一道都要被追问一句"为什么"。到第五题的时候，能明显感觉出来，大家手上都有经验，缺的是一张清楚的调度图。

分享结束后我把那几道题默写下来，一道一道重推，把宏任务、微任务、Promise 回调、定时器和 async/await 重新放回同一条时间线上。下面就按那组题的顺序往下拆，重点不是记答案，而是把"为什么它会这么跑"讲明白。

第一题：setTimeout 写 0，为什么还是排在最后

正确输出是 1 3 2，答案本身不难，但只说"setTimeout 是异步的，异步的排后面"，这句话等于没有解释清楚原因。

真正的解释要从"主线程一次只做一件事"讲起。可以用售票窗口打比方：主线程是唯一的窗口，同步代码是直接站在窗口前办事的人；setTimeout 的回调相当于先去旁边领了个号，当前所有同步代码办完、窗口空了，才轮到叫号。号领得再早（哪怕延迟写 0），也插不了正在办事的队。

还有个容易忽略的点：setTimeout 这一行本身是同步执行的——它做的只是"登记一个定时任务"，登记瞬间完成，计时交给浏览器的定时器线程。很多人误以为 setTimeout(fn, 1000) 会卡住一秒，其实它一行就过去了，1 秒只是回调进队列的时机。这一点在写轮询逻辑时特别容易被误判：如果错把它当成阻塞调用，在循环里一口气登记成百上千个定时器，浏览器很容易直接卡死。

这题的关键在于分清宏任务和微任务这两个词，光知道名字不够，还得排出顺序：异步任务分两个队列，Promise.then 属于微任务，setTimeout 属于宏任务；每当同步代码执行完，先把微任务队列整个清空，再执行下一个宏任务。

记这个区别有个简单的办法：分清"谁是 VIP"。微任务是 VIP 通道，每办完一拨同步事情，先把 VIP 队列全部清空，再去叫普通号。归归类：微任务有 Promise.then/catch/finally、MutationObserver（Vue 的 $nextTick 内部优先用的就是它和 Promise，这个后面还会提）；宏任务有 setTimeout、setInterval、setImmediate（Node 专属）、I/O、UI 事件回调。

第三题：new Promise 里的代码什么时候跑

这题容易顺着直觉答成 A D B C，正确输出其实是 A B D C。

坑在这里：new Promise(executor) 里那个 executor 函数是同步执行的，构造的当下就跑，所以 B 紧跟 A；真正异步的是 .then 里的回调，它才是微任务。"构造时同步、then 回调异步"——最容易出错的地方就是把整个 new Promise 都当成了异步。这是这类题里错误率最高的一档，很多写了一两年 Promise 的人都没意识到 executor 是同步执行的这个细节。

容易被忽略的细节是：两个 .then 并不是同时进微任务队列的。实际上第一个 .then 的回调先进队列，等它执行完，第二个 .then 的回调才被放进去。只是这一切都发生在"清空微任务"这同一轮里，所以 promise1、promise2 接连打印，宏任务 timeout 依然要等它们全跑完。

这个细节在推刁钻题的时候极其重要——有一类题会在微任务里塞 setTimeout、又在 setTimeout 里塞 Promise.then，层层嵌套。可以抓住一句铁律：**每跑完一个宏任务，就把当下产生的所有微任务清空，再取下一个宏任务。**再绕的题都能按这条一行行推。比较可靠的做法是拿张纸画两列，左边宏任务队列，右边微任务队列，一边"执行"一边往队列里加、从队列里取，比在脑子里空想稳妥得多。

第五题：setTimeout 0 到底是不是 0

正确顺序是先 done 再 timeout，timeout 要等 while 跑完才有机会执行。setTimeout(fn, 0) 的意思从来不是"马上执行"，而是"尽快排进后续任务"——主线程被占住，它一毫秒都动不了。（顺带一条细节：按 HTML 规范，定时器嵌套超过一定层数后最小延迟会被钳到 4ms，写 0 也拿不到真正的 0。）

这题背后真正要问的是："这跟页面卡顿有什么关系？"这一点在数据看板项目里真切疼过。当时一个表格要把后端返回的几万行数据在前端排序加格式化，全写在一个同步函数里。功能没问题，但点一下排序，整个页面"死"几百毫秒——按钮按下去没反应，loading 转圈动画也定住不动。根源是转圈动画靠浏览器渲染，渲染也排在主线程上，被那次计算挡在后面了。只要主线程在跑长同步任务，页面就不会重绘，再炫的 loading 都是假的。

async/await 只是 Promise 的语法糖，可以把 await x 大致理解成"把后面的代码包进 Promise.resolve(x).then(...)"。所以 await 之前的代码同步跑（打印 1），遇到 await 就让出执行权（run() 返回，外面的 3 打印），await 后面的部分作为微任务稍后执行（打印 2）。写法像同步，执行顺序仍是异步——它糖衣底下还是 then。

这层理解直接解释了组里反复出现过的一个真 bug：有人在 for 循环里 await，本想并发拉列表，结果接口被一个一个排队调，加载慢得要命：

要不要并发得看场景：接口间有依赖、或怕并发把后端打垮，串行反而稳；纯拉一批互不相关的数据就该 Promise.all。review 代码时看到循环里有 await，都值得停下来确认一句：这里到底想不想串行。

Promise.all 还有个常被忽略的行为：只要有一个 promise 被 reject，Promise.all 会立刻整体 reject，其余还没完成的请求结果就都拿不到了。如果想要"不管成功失败，都等所有请求跑完再统一处理"，得用 Promise.allSettled 那类方案——不过这个 API 眼下还在提案阶段，2018 年的项目里更现实的做法是自己包一层，把每个请求都 .catch 掉，让它们统一变成"要么成功要么带着错误信息的对象"，再扔进 Promise.all。

几个容易被漏掉的延伸点

题目本身推完之后，周边几个相关的点也值得顺手挖一下。

**一轮循环只取一个宏任务。**每轮事件循环，从宏任务队列里取一个执行，执行完清空微任务、给浏览器一次渲染机会，再取下一个宏任务。这意味着递归 setTimeout 排任务时，浏览器能在任务之间见缝插针地渲染；但如果微任务递归地产生新微任务（Promise.then 里再 then 自己），微任务队列永远清不空，渲染和下一个宏任务都会被饿死。用递归 Promise 做"重试直到成功"如果不加退避、不设上限，一旦接口持续失败，页面会被微任务彻底卡死，连关都关不掉。微任务优先级高，但它不是免费的安全区。

**Vue 的 $nextTick 就踩在这套机制上。**改了数据想拿更新后的 DOM，要等 Vue 异步批量更新完——$nextTick 的实现就是往微任务队列里排回调（优先 Promise.then/MutationObserver，环境不支持才降级 setTimeout）。它为什么要用微任务而不是宏任务：赶在本轮渲染前、DOM 补丁打完后立刻执行，比 setTimeout 快一拍。框架的"魔法"拆开看，全是事件循环的基本功。

同一批更新会被合并这件事也值得多说一句：同一个 tick 里如果连续改了好几次同一个 data 字段，Vue 不会每改一次就同步跑一次渲染，而是把这些改动去重合并，最后只触发一次异步更新，$nextTick 的回调也只会跑一次。这也是为什么在循环里疯狂改 data 通常不会造成性能问题——真正昂贵的是 DOM 操作，Vue 帮你把它们攒成了一批。

**Node 和浏览器的循环不完全一样。**Node 有 setImmediate 和 process.nextTick，其中 process.nextTick 的优先级比 Promise 微任务还高，setTimeout(fn, 0) 和 setImmediate 的先后在不同阶段还会变化，这跟浏览器里"宏任务、微任务两条队列"的简化模型不完全一样，Node 内部实际上分成 timers、pending callbacks、poll、check、close callbacks 好几个阶段，process.nextTick 和 Promise 微任务在每个阶段之间都会被清空一次。写 Node 脚本时不能直接把浏览器里的直觉搬过去，这块目前只算摸了个大概，值得找时间单独深挖一次。
