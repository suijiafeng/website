事件循环、Promise 和 setTimeout：异步题背后是执行顺序

2018-04-12
JavaScript前端基础

异步执行顺序是面试里很喜欢考的题。

一段代码里有 console.log、setTimeout、Promise.then，问输出顺序是什么。刚开始看这种题会觉得绕，但它其实在考一个很基础的问题：JavaScript 主线程一次只能做一件事，异步回调要排队。

理解事件循环，不只是为了做题，也能帮助我们理解页面为什么会卡。

我第一次被这种题问住，是两年前面一家做电商后台的公司。当时我能把 Promise 用得很熟，链式调用、错误捕获都没问题，但面试官让我手写一段代码的输出顺序，我愣是把 Promise.then 排到了 setTimeout 后面。回去翻了一晚上资料才搞明白：我会用，但根本不知道它为什么这么跑。后来我自己带新人，也发现一个规律：能讲清楚事件循环的人，写异步代码出 bug 的概率明显低，因为他们脑子里有一张"任务什么时候执行"的图，而不是靠感觉。

下面这些题我会从最简单的讲起，每一段都尽量配上"为什么"，而不是只给答案。

同步代码先执行

输出：

setTimeout 不是立刻执行，它只是把回调安排到后面。当前同步代码执行完，主线程空了，回调才有机会执行。

我喜欢用"售票窗口"来理解执行栈：主线程就是那个唯一的窗口，谁排到谁办。同步代码是直接站在窗口前办事的人，setTimeout 的回调相当于先去旁边领了个号，等当前所有人办完才叫号。号领得再早（哪怕延迟写 0），也得等窗口空下来。

这里有个容易被忽略的点：setTimeout 本身这一行是同步执行的，它做的事情只是"登记一个定时任务"，登记这个动作瞬间完成，回调函数则被交给浏览器的定时器线程去计时。这也是为什么很多人误以为 setTimeout(fn, 1000) 会"卡住" 1 秒——其实它一行就过去了，1 秒只是回调进入队列的时机。我早年写轮询就踩过这个坑，以为 setTimeout 会阻塞，结果在循环里一口气登记了上千个定时器，浏览器直接卡死。

Promise.then 更早执行

输出：

Promise.then 属于微任务，setTimeout 属于宏任务。当前同步代码执行完后，会先清空微任务队列，再执行下一个宏任务。

我自己记这个区别的办法是分清"谁是 VIP"。微任务是 VIP 通道，每办完一拨同步事情，会先把 VIP 队列全部清空，再去叫普通号（宏任务）。常见的微任务有 Promise.then/catch/finally、queueMicrotask、MutationObserver；常见的宏任务有 setTimeout、setInterval、setImmediate（Node）、I/O、UI 事件回调。

要注意的是 Promise.resolve().then 里的回调才是微任务，new Promise(executor) 里那个 executor 函数是同步执行的。下面这段我面试时让人写过，错得最多：

经典嵌套题

输出：

顺序可以按三步看：

  1. 先执行同步代码
  2. 执行所有微任务
  3. 执行宏任务

这里的关键细节是：两个 .then 不是一次性全排进队列的。第一个 .then 的回调（打印 promise1）先进微任务队列，等它执行完，才会把第二个 .then 的回调放进队列。但因为这都发生在"清空微任务"这一轮里，所以 promise1、promise2 会接连打印，宏任务 timeout 还得在它们都跑完之后才轮到。

我把这个过程拆细了讲，是因为有一类更刁钻的题，会在微任务里再塞 setTimeout，又在 setTimeout 里塞 Promise.then，层层嵌套。只要抓住"每跑完一个宏任务，就把当下产生的所有微任务清空，再取下一个宏任务"这条铁律，再绕的题都能一行行推出来。我推这种题的习惯是拿张纸画两列，左边宏任务队列，右边微任务队列，一边执行一边往队列里加、从队列里取，比在脑子里空想可靠多了。

setTimeout 0 不是真的 0

setTimeout(fn, 0) 的意思不是马上执行，而是尽快放到后续任务里。

如果主线程被占住，它也执行不了：

输出一定是先 done，再 timeout。

这也是页面卡顿的原因：主线程被长任务占住时，用户点击、定时器、渲染都要等。

我在一个数据看板项目里真切体会过这点。当时有个表格要把后端返回的几万行数据在前端做排序加格式化，全写在一个同步函数里。功能没问题，但点一下排序，整个页面就"死"几百毫秒——按钮按下去没反应，loading 转圈的动画也卡住不动了。后来我才反应过来：转圈动画是靠浏览器渲染的，渲染也排在主线程上，被我的计算挡在后面了。所以才有那句经验之谈：只要主线程在跑长同步任务，页面就不会重绘，再炫的 loading 都是假的。

异步不是多线程

很多人会把异步理解成同时执行。浏览器确实有网络线程、定时器等机制，但 JavaScript 回调最终还是要回到主线程执行。

所以异步能避免等待接口时阻塞主线程，但不能解决大量同步计算的问题。

如果计算本身很重，应该考虑分片、减少计算，或者使用 Web Worker。

async/await 也是 Promise

输出：

await 后面的代码会被安排到后续微任务里。它让写法像同步，但执行顺序仍然是异步。

可以把 await x 大致理解成"把后面的代码包进 Promise.resolve(x).then(...)"。所以 await 之前的代码是同步跑的（上面的 console.log(1)），遇到 await 就让出执行权，后面的部分变成微任务。这一点解释了一个我团队里反复出现的 bug：有人在 for 循环里用 await 串行请求，本想并发，结果接口被一个一个排队调，列表加载慢得要命。

要不要并发得看场景。如果接口之间有依赖、或者怕一次性打太多请求把后端压垮，串行反而更稳；纯粹拉一批互不相关的数据，那就该用 Promise.all。我现在 review 代码看到循环里有 await，都会先停下来问一句：这里到底想不想串行。

一次只能取一个宏任务

还有个细节面试很少考，但对理解卡顿很有帮助：每一轮事件循环，只会从宏任务队列里取一个来执行，执行完先去清空微任务、给浏览器一次渲染的机会，再回头取下一个宏任务。

这意味着如果你用 setInterval 或者递归 setTimeout 不停地排任务，浏览器会在每两个任务之间见缝插针地渲染。但如果某一个宏任务里塞了大量微任务（比如递归地 Promise.then 再产生新的 Promise.then），微任务队列就永远清不空，渲染和下一个宏任务都会被饿死。我见过有人用递归 Promise 做"重试直到成功"，没加退避也没加上限，接口一直失败，页面就被微任务彻底卡死，连关都关不掉。微任务虽然优先级高，但它不是免费的安全区。

事件循环的本质并不神秘：先执行同步代码，随后清空微任务队列，再执行宏任务。把这条顺序记清楚，很多看似怪异的 Promise/setTimeout 行为和页面卡顿都能迎刃而解。异步是排队的规则，不是并行的魔法。
