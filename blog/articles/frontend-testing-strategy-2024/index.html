前端测试策略：别只纠结单测覆盖率

2024-07-05
前端基础构建与模块化

前端测试最容易被覆盖率带偏。

覆盖率 80% 看起来很好，但如果测的都是工具函数，核心下单流程、登录流程、权限流程没人管，线上照样会出事故。反过来，一个项目覆盖率不高，但关键路径有稳定 E2E，核心组件有组件测试，回归风险可能更低。

我以前也追过覆盖率。为了达标，给很多简单函数补测试，断言输入输出，报告很好看。结果一次支付按钮被样式层遮住，单测全绿，线上用户点不了。那次之后我对测试的理解变了：测试不是数字游戏，而是风险控制。

先按风险选测试

前端测试大致有几层：

不同测试解决不同问题。不要指望单元测试发现弹窗被遮挡，也不要用 E2E 穷举一个工具函数的所有边界。

我一般按风险排序：

  • 钱、权限、数据修改优先测
  • 高频用户路径优先测
  • 历史出过事故的地方优先测
  • 复杂条件分支优先测
  • 纯展示低风险页面可以少测

测试资源有限，应该先保护最值钱的路径。

单元测试适合稳定逻辑

单元测试最适合纯逻辑：

这种函数输入输出稳定，边界明确，测试成本低。

复杂表单规则、金额计算、权限判断、数据转换，都值得写单测。

但不要为了覆盖率给所有 getter、简单映射、样式类名都写测试。那类测试很容易和实现细节绑定，改代码时只会增加维护成本。

组件测试关注用户行为

组件测试不要测内部 state，而要测用户能看到和能操作的结果。

比如一个表单：

这里关注的是：用户没填账号就点登录，页面出现错误提示。至于组件内部用了几个 useState，不应该成为测试关心的内容。

好的组件测试通常使用：

  • getByRole
  • getByLabelText
  • getByText
  • userEvent

少用 querySelector('.class-name')。类名是实现细节，角色、标签和文本更接近用户视角，也顺便能推动可访问性。

E2E 只测关键路径

E2E 很有价值，但不要贪多。

真实浏览器测试更接近用户，但也更慢、更脆、更依赖环境。如果把所有边界都塞进 E2E，CI 会变慢，失败也难定位。

我会选少量关键路径：

  • 用户能登录
  • 核心列表能搜索和进入详情
  • 关键表单能提交
  • 权限不足能被拦截
  • 支付或下单流程能跑通

E2E 的断言要抓业务结果，不要抓过细 UI。

如果断言一堆像素位置、动画过程、内部 class，测试会非常脆。

Mock 要有层次

测试里的 Mock 也要谨慎。

单元测试可以 mock 依赖；组件测试可以 mock API；E2E 最好尽量接近真实环境，但可以用稳定测试数据。

前端组件测试里，我更喜欢用 MSW 这类网络层 mock，而不是 mock 掉业务请求函数。因为它保留了真实的请求路径：

组件仍然像真实环境一样发请求，只是响应由测试控制。这样比直接 mock fetchUsers() 更接近实际行为。

Mock 数据也要覆盖异常：

  • 空列表
  • 接口 500
  • 权限 403
  • 字段为 null
  • 超长文本
  • 慢请求

只测成功路径的测试，很容易给人虚假的安全感。

我的测试策略

一个实用的前端测试策略大概是：

  • 纯逻辑和复杂规则写单元测试
  • 关键组件交互写组件测试
  • 核心业务链路写少量 E2E
  • 接口错误和空状态必须覆盖
  • 不追求无意义覆盖率
  • 测用户行为，不测实现细节
  • 把历史 bug 转成回归测试

测试不是为了证明代码没问题，而是为了让重要问题尽早暴露。

覆盖率可以看，但它只能回答“跑到了多少代码”，不能回答“保护了多少业务风险”。真正好的测试，是开发敢改、CI 能拦、线上少炸。
