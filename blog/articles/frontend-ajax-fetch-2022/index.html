从 Ajax 到 Fetch：前端请求方式的演进到底带来了什么

2022-10-06
前端基础

前端开发离不开请求。

页面展示数据、提交表单、刷新列表、加载详情，这些动作几乎都要和服务端通信。

如果把时间往前拉，大家最熟悉的方式可能是 Ajax；再往后，Fetch 逐渐成为更常见的写法。它们都能完成请求，但带来的开发体验并不完全一样。

Ajax 解决了什么问题

Ajax 最重要的价值，是让页面不必整页刷新也能和服务端交换数据。

这在早期前端开发里是一次很大的改变，因为它让页面开始具备更强的交互性和动态性。

大家最熟悉的实现通常是 XMLHttpRequest。

这个写法并不是不能用，但确实比较底层。

它的底层感主要体现在几个地方：

  • 需要关心 readyState
  • 成功和失败判断分散
  • 响应内容需要自己解析
  • 超时、取消、错误提示都要额外处理

光是 readyState 这一个属性，当年就让不少新人栽过跟头。它有 0 到 4 五个状态值，真正能拿到完整响应的只有 4。我刚入行时见过一种很经典的 bug：有人把判断写成 if (xhr.readyState === 4) 却忘了再判断 status，结果接口返回 500 时也照样去解析 responseText，页面直接渲染出一堆 undefined。还有人反过来，只判断 status === 200，把 201、204 这些同样算成功的状态码当成了失败。HTTP 成功的状态码是 2xx 这一整段，写死 200 在文件上传、创建资源的接口上很容易出问题。

responseText 也是个坑。它永远是字符串，你得自己 JSON.parse，而 parse 一旦遇到后端返回的非法 JSON（比如 nginx 直接吐了一个 HTML 错误页）就会抛异常。如果没有 try/catch 包住，整个回调直接中断，连兜底提示都来不及弹。

如果只是一个简单请求，这些代码还能接受。一旦页面里有十几个接口，每个地方都写一遍状态判断，维护成本就会很快上来。我经手过一个老后台项目，光是 xhr.readyState === 4 && xhr.status === 200 这行判断，全局搜出来有三十多处，每处后面跟着的错误处理还都不太一样，改一个全局提示文案要翻遍整个仓库。

Fetch 为什么更容易被接受

Fetch 更贴近现代 JavaScript 的编码方式。

它的 API 更简洁，也更容易和 Promise、async/await 组合。

相比 XMLHttpRequest，这种写法的优势主要体现在：

  • 更容易阅读
  • 更容易封装
  • 更适合现代异步流程

两者的差异不只是“新旧”

不少人会简单理解成“Fetch 就是更现代的 Ajax”，但更准确地说，它们代表了两种不同层级的开发体验。

XMLHttpRequest 更像底层接口，你需要自己处理很多状态变化。

Fetch 则更像一个围绕请求流程设计得更现代的抽象。

不过有意思的是，从能力角度看，Fetch 早期反而不如 XMLHttpRequest 全面。比如上传进度，XMLHttpRequest 有 xhr.upload.onprogress 可以拿到字节级的上传百分比，做大文件上传的进度条很方便；而 Fetch 在很长一段时间里都拿不到上传进度，只能靠流式 reader 去算下载进度，上传那一侧基本没辙。所以当时我们团队有个不成文的约定：普通业务请求一律用 Fetch，唯独带进度条的文件上传还是退回去用 XMLHttpRequest。这也说明所谓"新旧"并不是简单的替代关系，它们各自有适用的边界。

另一个容易被忽略的差异是 cookie。Fetch 早期默认不带同源 cookie，必须显式写 credentials: 'include'（跨域）或 'same-origin'，否则登录态根本传不过去。这个坑我亲手踩过：本地联调一切正常，一上测试环境接口全部 401，排查半天才发现是 cookie 没带上。XMLHttpRequest 默认就会带同源 cookie，习惯了它的人切到 Fetch 很容易在这里翻车。

还有个细节是 parseJson 里我把解析失败直接吞成 null。这样做的前提是上层会先看 response.ok：如果 HTTP 本身失败了，body 是不是合法 JSON 其实无所谓，错误信息走状态码兜底就够了；如果 HTTP 成功但 body 解析不了，那大概率是后端契约出了问题，返回 null 让页面走空数据逻辑，总比整个流程崩掉强。像 204 No Content 这种本来就没有 body 的响应，response.json() 也会抛错，这个 try/catch 顺手就把它兜住了。

请求封装的重要性

无论使用 Ajax 还是 Fetch，真正影响项目维护体验的，往往不是底层 API 本身，而是你有没有做好请求层封装。

例如：

  • base URL
  • 通用 headers
  • 错误处理
  • token 注入
  • 超时控制

如果这些都散落在页面里，请求方式再现代，项目后期也会很难维护。

401 这个状态码尤其值得单独拎出来处理。它通常意味着登录失效，正确的动作往往不是弹个 toast 了事，而是要清掉本地 token、跳回登录页，登录后还得能跳回原来那个页面。这套逻辑只该在请求层写一次。我见过有的项目把跳登录页的代码复制粘贴到几十个页面里，后来要加一个"跳转前记住当前路由"的需求，改起来简直是灾难。我现在的习惯是在请求层拦截 401，统一触发一个全局事件或者调一个 auth 模块的方法，页面完全不感知这件事。

不过这里也要防一个边界情况：如果是登录接口本身返回 401（密码错了），就不该再触发跳登录页的逻辑，否则会陷入死循环。所以拦截时通常还要排除掉登录、刷新 token 这几个特定接口。

这里要分清楚：被取消的请求也会进入异常分支。封装层最好能区分“用户主动取消”和“真正失败”，否则用户每次快速输入都可能看到错误提示。

GET 和 POST 的边界

请求方式不只是后端的事情，前端也应该明确它们的语义。

一般来说：

  • 读取数据用 GET
  • 创建数据用 POST
  • 整体更新用 PUT
  • 局部更新用 PATCH
  • 删除数据用 DELETE

实际项目未必每个接口都严格遵守，但前端代码里至少应该保持清晰的命名和调用边界。比如 loadArticles、createArticle、deleteArticle 比 handleRequest1 这种名字更能表达意图。

如果涉及表单上传，就不能照搬 JSON 请求头，而应该使用 FormData，让浏览器自己处理边界信息。

这里有个反直觉的坑：用 FormData 时绝对不要手动设置 Content-Type。multipart/form-data 后面跟着一段 boundary 分隔符，这个 boundary 是浏览器根据内容随机生成的，只有让浏览器自己写这个头，boundary 才会和实际请求体对上。如果你手贱写了 'Content-Type': 'multipart/form-data'，boundary 就丢了，后端解析直接报错或者拿到空字段。我帮人排查过好几次"上传一直失败"，最后都是因为在通用封装里无脑给所有请求加了 JSON 的 Content-Type，把 FormData 也一起带歪了。所以封装请求层时，如果 body 是 FormData 实例，要专门跳过 Content-Type 的设置。

GET 请求还有个老生常谈但仍然有人忘的点：参数拼到 URL 上时一定要 encodeURIComponent。搜索关键词里出现 &、#、空格、中文这些字符，不编码的话轻则参数被截断，重则被后端当成 SQL 或者其他注入的入口。前面搜索那段代码里我特意写了 encodeURIComponent(keyword)，不是顺手，是真踩过参数里带 & 导致后面的参数全丢的事故。

从工具切换到抽象思维

很多技术演进表面看起来只是 API 更新，实际上还有一个更关键的问题是推动开发者思维变化。

从 Ajax 到 Fetch，更有价值的变化不只是代码少了几行，而是前端异步请求开始更自然地融入整体工程结构。

请求层做好以后，页面代码会轻很多。它不用关心底层用的是 XMLHttpRequest、Fetch，还是第三方库；只要返回的数据结构稳定，业务层就能稳定工作。

这也是我后来对请求代码的一个判断标准：不是看它是否用了最新 API，而是看它能不能让页面少处理协议细节、少重复错误逻辑、少暴露不稳定边界。

从 Ajax 到 Fetch，是前端请求方式一次很自然的演进。前者解决了页面局部更新的问题，后者则让请求代码更容易和现代 JavaScript 编程方式结合。

工具当然会变化，但真正值得沉淀的是请求层的组织方式。只要这层思路清楚，用什么接口都不会太乱。
