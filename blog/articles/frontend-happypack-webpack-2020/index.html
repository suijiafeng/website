HappyPack 提升 Webpack 构建速度的思路

2020-05-10
前端基础构建与模块化性能与缓存

早期 Webpack 项目变大后，构建速度经常会明显变慢。

尤其是 Vue、React 项目里，文件数量多、loader 多、转换链路长，启动和打包都可能让人等很久。我印象最深的一次，是一个跑了一年多的后台管理项目，源码加上一堆业务页面，全量构建一次要等两分多钟。改一行字、保存、等热更新，节奏完全被打断。中午吃完饭回来还得重新 npm run dev 一遍，等它编译完的那二十几秒，足够我把咖啡冲好。

HappyPack 曾经是解决这类问题的一种常见方案。那段时间团队里几乎人手一个，配置抄来抄去，但很多人其实说不清它到底快在哪、为什么有时候加了反而没效果。

今天不一定还会在新项目里主动选择 HappyPack，但它背后的思路仍然值得理解：构建优化不是只靠换工具，而是先找到耗时环节，再判断它能不能并行。我自己后来踩过不少坑才明白，工具是次要的，找瓶颈的方法才是能复用的东西。

Webpack 为什么会慢

Webpack 构建时要做很多事情：

  • 读取文件
  • 解析模块依赖
  • 调用 loader 转换代码
  • 生成依赖图
  • 输出最终资源

其中 loader 处理可能很耗时，例如转译 JavaScript、处理 Vue 单文件组件、编译样式等。

早期 Webpack 的处理流程里，很多任务是在单进程中排队执行的。

文件一多，等待时间就会变长。

构建慢通常不是一个原因造成的。常见瓶颈包括：

  • Babel 转译大量业务文件
  • Vue 或 React 组件编译链路长
  • 样式预处理器耗时
  • 代码压缩耗时
  • source map 生成成本高
  • 缓存没有命中

所以加 HappyPack 前，至少要先知道慢在哪里。否则很可能只是把配置写复杂了，构建时间却没有明显变化。

我当时是用 speed-measure-webpack-plugin 把每个 loader 和 plugin 的耗时打出来看的，用法很简单：

跑一次构建，它会按 loader 和 plugin 列出各自花了多少时间。结果常常出乎意料：我原以为是 Vue 编译慢，打出来一看，babel-loader 处理那一堆业务 JS 才是大头，Vue 的模板编译其实占比不高。后来才知道，是有人把 babel-loader 的 exclude: /node_modules/ 写漏了，结果连第三方库都重新转译了一遍——光这一个疏忽就吃掉了将近一半的时间。

那次教训让我记住一件事：在加任何并行、缓存工具之前，先用数据确认瓶颈。凭感觉优化，十有八九优化错地方。

HappyPack 的思路

HappyPack 的核心思路是：把 loader 的处理任务分发到多个子进程中并行执行。

简单理解：

  • Webpack 主进程负责调度
  • HappyPack 创建 worker
  • 文件转换交给 worker 并发处理
  • 处理完成后结果交回 Webpack

这样可以更充分利用多核 CPU。

它适合的前提是：某些 loader 任务可以相对独立地处理。比如大量 JavaScript 文件经过 Babel 转译，就比较容易从并行中获益。

这里有个容易忽略的点：HappyPack 用的是子进程，进程之间不共享内存。所以主进程把文件内容序列化后通过 IPC 发给 worker，worker 处理完再把结果序列化传回来。这一来一回是有成本的。文件越大、数量越多、单个文件转换越耗时，这部分通信成本相对收益就越划算；反过来，如果每个文件都是几行的小文件，通信开销可能比转换本身还高。

另外要清楚一个限制：HappyPack 对 loader 是有挑剔的。像 style-loader 这种需要往 DOM 注入、依赖运行时上下文的 loader，放进 HappyPack 里就容易出问题。我早期就因为把整条 CSS 链路塞进去，结果样式热更新失灵、sourcemap 错位，排查了半天才发现是 HappyPack 的锅。后来 CSS 这类带副作用、强依赖顺序的 loader 我就老老实实留在主进程，只把纯转换型的 babel-loader、ts-loader 这种交给它。

cacheDirectory: true 这一项我必须单独提一句。它和 HappyPack 是两个层面的优化，但配合起来才舒服。babel-loader 的缓存会把转译结果写到磁盘（默认在 node_modules/.cache/babel-loader），二次构建时没改过的文件直接读缓存，连 worker 都不用派活。我实测下来，真正让二次构建提速最明显的其实是这个缓存，HappyPack 解决的更多是冷启动那一次的全量转译。

还有个坑是关于 id 的：一个 HappyPack 实例只能配一组 loader，多个文件类型必须建多个实例、用不同的 id 区分。我刚开始想偷懒，把 js 和 css 的规则都指向同一个 id，结果 css 文件被 babel-loader 处理，直接报了一堆语法错误。这种错误信息还特别隐晦，因为它发生在子进程里，栈信息传回来已经不全了，对着报错懵了好一会儿。子进程出错时排查难度比单进程高，这也是用 HappyPack 要付出的隐性成本之一。

不是所有项目都适合

HappyPack 适合早期 Webpack 项目中的某些构建瓶颈，但不是万能加速器。

如果项目本身很小，进程调度的成本可能抵消收益。

如果瓶颈不在 loader，而在其他插件、依赖分析或压缩阶段，效果也会有限。

所以优化前最好先测量，而不是盲目加工具。

可以先做几件低成本检查：

  • 记录冷启动和二次构建时间
  • 关闭 source map 对比耗时
  • 观察是否大量编译了 node_modules
  • 检查 Babel 缓存是否开启
  • 区分开发构建慢还是生产打包慢

如果慢在压缩阶段，HappyPack 处理 loader 的收益就不会太明显。如果慢在某个插件，优化方向也应该转向插件配置。

举个真实例子：有个项目我加了 HappyPack，构建时间几乎没动。一查才发现，慢的根本不是 loader，而是 UglifyJsPlugin 在压缩一个巨大的第三方库 bundle。这种情况下，把压缩本身并行化（比如 UglifyJsPlugin 开 parallel: true）才是对的方向，HappyPack 在那儿一点忙都帮不上。

还有一次是 source map。开发环境本来用了 devtool: 'source-map'，生成完整 source map 巨慢。换成 cheap-module-eval-source-map 之后，构建时间直接砍掉一截——这种调整比折腾 loader 并行划算太多，几乎零成本。所以我现在的习惯是：开发环境用便宜的 source map，生产环境才上完整的，且只在需要排错时开。

并行不是越多越好

多进程会带来进程创建、通信和结果合并成本。

机器核心数有限时，worker 开太多反而会抢资源。尤其在 CI 环境里，CPU 资源可能被限制得很死，配置本地跑得快，不代表 CI 也快。

今天怎么看这个方案

现代前端工具链已经发生了很大变化。

Webpack 自身、缓存机制、thread-loader、esbuild、swc、Vite 等方案都让构建优化有了更多选择。

但 HappyPack 的思路仍然值得理解：当任务可以拆分时，并行处理往往能提升效率。

如果维护的是老项目，HappyPack 可能仍然能解释历史配置为什么存在。如果是新项目，通常应该优先看工具链内置缓存、持久化缓存、更快的编译器和更少的编译范围。

一个简单的优化顺序是：

  • 先排除无意义编译
  • 再开启缓存
  • 再考虑并行
  • 最后再考虑换构建工具

构建优化越往后，收益越依赖具体项目，不适合凭经验直接下结论。

关于替代方案我也想多说两句。社区后来更推荐 thread-loader，它是 webpack 官方维护的，定位和 HappyPack 几乎一样，但配置更直接——直接当成一个 loader 放在链路最前面就行，不用单独建 plugin 实例和管 id：

它和 HappyPack 一样有进程通信成本，所以同样不适合小项目。我后来新项目基本不再用 HappyPack，要么 thread-loader，要么直接上 cache-loader 配合 babel 缓存，再后来 swc、esbuild 这类用 Go/Rust 写的编译器出来，单线程都比 Babel 多进程快好几倍，并行这件事的优先级一下就降下来了。换更快的编译器，往往比在慢编译器上堆并行更有效。

并行处理能缓解构建瓶颈，但先要有数据证明瓶颈在哪。HappyPack 曾有用处，但现代工具链（缓存、thread-loader、esbuild/swc）往往更合适。优化顺序是：测瓶颈 → 减少无效工作 → 开启缓存 → 考虑并行。

真正重要的不是 HappyPack 这个工具本身，而是“测量瓶颈、减少无效工作、利用缓存、再考虑并行”的优化路径。
