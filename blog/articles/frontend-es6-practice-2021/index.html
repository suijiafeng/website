ES6 常用特性回顾：真正改变前端开发体验的是哪些能力

2021-03-27
前端基础

前端开发近几年的编码体验变化，很大一部分都来自 JavaScript 语言本身的演进。

ES6 之后，很多过去写起来很别扭的代码，开始变得更自然。它的价值不只是语法更好看，而是让代码表达能力更强了。

我刚开始学 ES6 时，也会把它当成一堆“新语法”来背。后来写业务写多了，才发现真正有价值的不是语法新，而是它们让代码里的意图更容易被看出来。

let 和 const 让变量语义更清楚

以前大家主要使用 var，它在作用域和提升上的行为比较容易引发困惑。

let 和 const 的出现，让变量声明的意图更明确：

  • let 表示后续可能修改
  • const 表示引用不再重新赋值

这能显著减少一些低级错误。

我现在的习惯是能用 const 就先用 const。不是因为它更高级，而是因为它能告诉后来读代码的人：这个绑定不会被重新指向。一段函数里如果满屏都是 const，少数几个 let 反而会跳出来——那几个就是真正在流转、需要重点盯的状态。这种"靠声明方式做视觉降噪"的效果，是当年用 var 时完全体会不到的。

let、const 还顺手解决了一个困扰我很久的经典面试题，也是真实业务里的坑——循环里注册回调：

以前为了让 var 拿到正确的值，得套一层 IIFE 把 i 当参数传进去，写出来很难看。let 的块级作用域直接把这个问题消化掉了。我第一次知道这个差别，是在排查一个表格行操作按钮全部指向最后一行数据的 bug，找了半天才意识到是闭包捕获的是同一个 var i。

还有暂时性死区（TDZ）这个点也值得记一下：let/const 声明之前访问变量会直接抛 ReferenceError，而不是像 var 那样得到 undefined。这看着像是"更严格了不方便"，实际是好事——它逼着你把声明放在使用之前，省掉了一类"看起来有值其实是 undefined"的隐蔽问题。

这里容易误会：const 限制的是变量绑定，不是对象内容。这个细节如果没弄清楚，很容易误以为 const 声明的对象就完全不能变。

模块化能力意义很大

ES6 模块并不只是语法更新，它实际上推动了前端工程结构进一步标准化。

通过 import 和 export，代码之间的依赖关系变得更清楚，也更适合现代构建工具处理。

我以前见过一些工具函数文件越写越大，最后变成 utils.js 大杂烩。模块化本身不能阻止这种事，但它至少给了我们拆边界的能力。

一个模块应该有自己的主题。不是所有东西都值得 export，也不是所有公共函数都应该塞进同一个文件。

我通常会让模块暴露稳定能力，而不是暴露内部过程。比如页面只需要 getUserProfile，就不应该顺手把拼 URL、转换字段、处理缓存的小函数全部导出。导出的东西越多，模块对外承诺越多，后面调整内部实现就越难。

命名导出和默认导出怎么选，我也纠结过一阵。后来形成的习惯是：一个文件就一个核心东西（一个组件、一个类）用默认导出，工具集、常量集这种"一堆并列的东西"用命名导出。命名导出在重构时更友好——改名字 IDE 能帮你全局跟着改，而默认导出在不同文件里可以随便起名，搜索和重命名都更麻烦。

还有一个容易忽略但很重要的特性：ESM 是静态结构，import 在编译期就能确定依赖关系。这正是 tree-shaking 能生效的前提。所以我尽量避免 import * as utils 这种整包导入，而是按需 import { formatDate } from '...'，这样打包时没用到的导出能被摇掉。CommonJS 的 require 是运行时动态的，构建工具没法这么干，体积上吃亏。

另外 ESM 默认开启严格模式，导入的绑定是只读的活引用——你改不了别人 export 的变量，但能拿到它最新的值。这跟早年那种"导出一个对象、大家随便往上挂属性"的脏写法是两个世界，模块边界因此清楚了很多。

Map 比普通对象强在两点。一是键可以是任意类型，对象、DOM 节点都能当键，不会像普通对象那样被强转成字符串。我做过一个"给每个 DOM 元素挂一份关联数据"的需求，用 Map 把元素本身当键，比维护一个自增 id 干净太多。二是 Map 保证插入顺序、能直接拿 size、能直接 for...of 遍历键值对，不用 Object.keys 绕一圈，也不用担心原型链上的 toString 之类的键来捣乱：

当然不是所有地方都该上 Map。需要 JSON 序列化、或者就是个固定结构的配置，普通对象更顺手——Map 不能直接 JSON.stringify 出键值。我的判断标准是：键不固定、会频繁增删、或者键不是字符串，就用 Map；否则普通对象就够了。

新特性的价值不在“高级”，而在“更稳定”

很多人学习 ES6 时会关注“有哪些新语法”，但真正更重要的问题其实是：

这些能力是不是让代码更容易读、写、改和协作。

从这个角度看，不少 ES6 特性之所以重要，不是因为它们炫，而是因为它们让前端开发更成熟了。

我现在判断一个 ES6 写法值不值得用，不看它是不是新，而看它有没有让意图更清楚。如果只是为了显得“现代”，把简单代码写得绕，那就没必要。

ES6 对前端开发的影响，远不只是多了几种新写法。它真正改变的是代码组织方式和表达效率。

当你回头看这些常用能力，会发现它们已经逐渐成为现代前端开发的基础配置。好的语言特性不是让代码显得更高级，而是让日常开发更顺手、更稳定。

对我来说，ES6 最大的价值不是多了几个语法点，而是让 JavaScript 更适合写大型前端项目。变量边界、模块边界、异步边界、数据转换边界，都比以前更容易表达出来了。
