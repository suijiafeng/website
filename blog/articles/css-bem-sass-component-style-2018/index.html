Sass 和 BEM 写组件样式：命名清楚比嵌套更重要

2018-07-15
CSS前端基础

组件化做了一两年之后，我对 CSS 的焦虑彻底变了。早些年写页面，难的是怎么把效果还原出来——浮动塌陷、垂直居中、IE 下的莫名其妙。等到上了 Vue，effect 这一层基本不再是问题，真正折磨人的变成了另一件事：我改一个组件的样式，会不会把另一个八竿子打不着的页面搞坏？

去年接手过一个后台项目，全局有一大坨 common.scss，里面写满了 .title、.btn、.active 这种通用名。新人加个 .title { margin-top: 20px } 想修自己页面，结果三个列表页的标题全往下掉了。回滚、定位、再改，一下午就这么没了。那之后我才真正理解：组件化时代，CSS 的核心矛盾是隔离和可预测，而不是炫技。

Sass 给的是工具——变量、嵌套、mixin、函数；BEM 给的是约束——一套命名约定。工具是放大器，约束是方向盘。只给放大器不给方向盘，嵌套会一层层往里钻，类名会越来越随意，最后又退化成那坨 common.scss。下面这些，是我这两年踩过的坑和后来定下来的规矩。

先说 BEM 到底在解决什么

BEM 是 Block / Element / Modifier 的缩写，命名长这样：block__element--modifier。第一次看觉得又长又丑，post-card__button--primary 谁顶得住。但用过就回不去了，因为它把 CSS 里最隐蔽的两件事显式化了：这个类属于谁，以及它处在什么状态。

&__title 编译出来是 .post-card__title，是一个单层、低权重的选择器，不依赖它在 DOM 里嵌了几层。这点特别关键：类名长换来的是权重平、归属清。我扫一眼 .post-card__button--primary 就知道它是卡片里那个按钮的主要态，不用回头翻 HTML 结构。

我自己定的几条 BEM 红线：

  • Element 不嵌 Element。没有 post-card__footer__button 这种写法，BEM 里 element 永远直接挂在 block 下，是 post-card__button。footer 只是个布局容器，按钮归属的是整个卡片。一旦写了双下划线套娃，说明这块该拆成独立 block 了。
  • Modifier 不单独使用。--primary 永远和基类一起出现：class="post-card__button post-card__button--primary"。单写一个 .post-card__button--primary 是没意义的，它只是在基类上叠加差异。
  • Block 名带业务前缀。是 post-card 不是 card，是 user-panel 不是 panel。前缀就是天然的命名空间，能挡掉一大半全局冲突。

Vue 组件里：scoped 和 BEM 不是二选一

2018 年写 Vue 2，<style scoped> 几乎是默认操作。有人会问：都 scoped 了，加了 data-v-xxx 属性自动隔离，还要 BEM 干嘛？

我的答案是两者管的事不一样。scoped 解决的是跨组件不串味，靠的是编译期给选择器加属性；BEM 解决的是组件内部结构清晰、状态可读，靠的是命名。一个组件内部如果还是 .title .item .active 满天飞，scoped 救不了你——它只保证不污染别人，不保证你自己看得懂。

而且 scoped 有个坑我吃过：它对子组件根节点的样式穿透是受限的，子组件内部更是完全管不到。当年想改 Element UI 的输入框样式，scoped 下直接写 .el-input__inner 没用，得用 /deep/（或 >>>）穿透：

所以我的组合拳是：scoped 负责组件之间的墙，BEM 负责组件内部的秩序。墙之内，类名照样按 BEM 来，这样哪天去掉 scoped（比如改成 CSS Modules 或服务端渲染场景）也不慌。

第一，权重失控。这条选择器特异性高得离谱，哪天想在某个状态下把这个 span 改成蓝色，你得写一条同样长甚至更长的选择器去压它，或者祭出 !important。我见过一个项目 !important 用了两百多处，根源就是早期嵌套太深，后人只能用核武器覆盖。

第二，和 HTML 结构强绑定。设计师说把 span 换成 i 标签，或者中间多包一层 div，样式立刻失效。CSS 本该描述"长什么样"，结果被写成了"在第几层的什么标签里"，脆得很。

变量：抽全局的代价是耦合

抽全局变量是有代价的，这点很多人没意识到：一旦抽出去，所有引用它的组件就和这个变量耦合了。改 $color-primary 是真的全站生效——这正是你想要的；但如果你把某个营销页临时用的渐变色也抽成全局变量 $promo-gradient，活动一结束这变量留也不是删也不是，删了不知道哪还在引。

所以我的判断标准很简单：这个值如果设计师改了，是不是希望全站一起改？ 是，就进全局；只是这一个页面、这一个组件的特例，就让它老老实实待在组件里。变量碎了比没变量更难维护——一屏滚不完的变量清单，找一个颜色还得 Ctrl+F，那不如直接写值。

mixin 好用，但别变成黑盒

mixin 是 Sass 里最容易被滥用的特性。它太方便了，一个 @include 就能复制一堆样式，于是有人开始往里塞业务逻辑。

这些 mixin 的共同点是：调用方一眼能预期它生成什么。flex-center 就是居中，hairline 就是细线，没有惊喜。

被我枪毙过的反面例子，是有人写了个 @mixin card-style 把整个卡片的 padding、border、shadow、hover、内部标题、按钮全塞进去，然后 .post-card { @include card-style; } 一行搞定。看着干净，实则灾难：想微调某个卡片的内边距，你得跳进 mixin 看它到底生成了什么，改 mixin 又怕影响别处。它把"复用"变成了"看不见的复制"。业务样式该直接写就直接写，几行重复远好过一个谁都不敢动的黑盒。

一个判断口诀：mixin 应该是工具，不是模板。 工具是 ellipsis、flex-center 这种通用能力；模板是"某个组件长什么样"，那是组件自己的事，不该藏进 mixin。

把这些规矩拼成一套目录

实践中我会把样式按职责分层，一个中型 Vue 项目大概长这样：

src/styles/
  variables.scss   // 全局变量：颜色、间距、层级
  mixins.scss      // 通用 mixin：ellipsis、hairline、flex
  reset.scss       // 样式重置
  index.scss       // 入口，@import 上面三个

收个尾

回头看，Sass 和 BEM 这套组合解决的从来不是"怎么写出效果"，而是"半年后还改得动"。BEM 让每个类名都有清楚的归属和状态，Sass 让复用和配置有了抓手。

但工具越强，越要克制。我这两年定下的几条，说到底就一句话——让 CSS 可预测：

  • 嵌套压到 3 层以内，样式靠类名归属，不靠 DOM 层级。
  • 变量只抽设计上稳定、真要全站统一的值，宁缺毋滥。
  • 状态写成显式 modifier 类，让 JS 和 CSS 在同一个名字上对话。
  • mixin 只做通用工具，不做组件模板，别让它变成黑盒。

样式写得清楚，永远比写得短重要。当年那个一改标题全站塌的下午，就是没人为"清楚"付过代价——账迟早是要还的。
