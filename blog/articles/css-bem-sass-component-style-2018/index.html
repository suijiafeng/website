一次样式互相覆盖的事故之后：我和同事把 Sass + BEM 组件样式规范谈了下来

2018-07-15
CSS前端基础

样式互相覆盖，表面上看像某一行 CSS 写错了，真正暴露出来的通常是命名和作用域根本没有边界。一个页面里叫 .title 的类，另一个页面里也叫 .title，公共样式里再来一条 .title，谁先谁后全靠运气。

这次 QA 报的问题就很典型：不止一个页面，三个页面的标题一起往下掉了 20px。我盯着自己最近的提交看了十分钟，一行没动过这些页面。最后用 DevTools 一层层翻样式来源，凶手在 common.scss 里：

提交人是组里另一个前端，提交信息写着"修复个人中心标题间距"。他要修的是他自己那个页面的 .title，但这个类名全项目有十一处在用。他修好了一处，砸了三处。

我拿着 blame 记录去找他，他也委屈："我搜过了呀，我以为 .title 就我们个人中心在用。而且上周你改 .card 的 padding，把我营销页的卡片也挤变形了，我还没找你呢。"

我俩对视了几秒，都没再说话。这不是谁的锅，是这个项目的 CSS 里根本没有"归属"这个概念——.title、.btn、.active、.card 满天飞，谁都在用，谁改都可能砸到别人，出了事只能靠全局搜索加祈祷。更糟的是项目里已经有两百多处 !important，那是前人打"覆盖战争"留下的弹坑：你的选择器压不过我，我就加 !important，下一个人再拿更长的选择器来压。

那周的周会，我提议把这事拿出来聊。这一聊就是两个小时，从甩锅现场变成了规范谈判。

谈判第一回合：BEM 太丑，但丑得有用

我开出的第一个方案是 BEM。Block / Element / Modifier，命名长这样：block__element--modifier。

他的第一反应和所有第一次见 BEM 的人一样："post-card__button--primary？这也太丑了，一个类名快赶上一行代码了。"

我没跟他争美丑，我把那天的事故重新推了一遍：如果个人中心的标题叫 user-panel__title，他改它的时候，全项目不可能有第二个地方受影响；如果我的卡片叫 post-card，我改 padding 也砸不到他的营销卡片。BEM 用类名的长度，换回了 CSS 里最值钱的两样东西：这个类属于谁，以及它处在什么状态。

对应的 Sass，用 & 把 BEM 的层级压平，DOM 上其实没有那么深的嵌套：

&__title 编译出来是 .post-card__title，是一个单层、低权重的选择器，不依赖它在 DOM 里嵌了几层。类名长，换来的是权重平、归属清：扫一眼 .post-card__button--primary 就知道它是卡片里那个按钮的主要态，不用回头翻 HTML。权重全是单类，也就没人需要 !important 了——弹坑不会再多。

他松了口，但提了个条件："规则得写死，不然每个人的 BEM 都长得不一样。"这个条件提得好，我们当场敲了三条红线进规范文档：

  • Element 不嵌 Element。没有 post-card__footer__button 这种写法，element 永远直接挂在 block 下，是 post-card__button。footer 只是个布局容器，按钮归属的是整个卡片。一旦写出双下划线套娃，说明这块该拆成独立 block 了。
  • Modifier 不单独使用。--primary 永远和基类一起出现：class="post-card__button post-card__button--primary"。单写一个 .post-card__button--primary 没有意义，它只是在基类上叠加差异。
  • Block 名带业务前缀。是 post-card 不是 card，是 user-panel 不是 panel。前缀就是天然的命名空间，能挡掉一大半全局冲突——那天的事故如果有这条，根本不会发生。

谈判第二回合：都有 scoped 了还要 BEM 干嘛

这是他的第二记反击，也是我预料中的。我们写 Vue 2，<style scoped> 几乎是默认操作，编译期给选择器加 data-v-xxx 属性自动隔离。他的原话："scoped 已经隔离了，类名随便叫不也砸不到别人？"

有一半对。scoped 确实能防住那天的事故——如果 .title 那条规则写在个人中心组件的 scoped 块里，泄漏不出去。但它防不住另外两件事。

第一件，common.scss 这种全局文件天然在 scoped 之外，而项目里总有全局样式；那天的提交恰恰就发生在全局文件里。第二件，scoped 只保证不污染别人，不保证你自己看得懂——组件内部照样可以 .title .item .active 满天飞，三个月后自己都分不清哪个 .active 是哪个状态。scoped 解决的是跨组件不串味，BEM 解决的是组件内部结构清晰、状态可读，两者管的不是同一件事。

而且 scoped 有个坑我当场给他演示了：它对子组件内部完全管不到。我们项目想改 Element UI 的输入框样式，scoped 下直接写 .el-input__inner 没用，得用 /deep/（或 >>>）穿透：

顺带一提，Element UI 自己的类名就是 BEM——el-input__inner 这个名字本身就在告诉你它是 el-input 这个 block 里的 inner 元素。我们天天在用的组件库都靠这套命名活着，这个论据比我讲半小时道理都好使。

会上还有人提了 CSS Modules，vue-loader 也支持，靠编译期把类名 hash 掉来隔离。我们讨论了一下没采用：它对模板里动态拼类名不友好，而且团队里还有两个多页的老项目根本不走 vue-loader，规范得照顾到它们。最后的组合拳定为：scoped 负责组件之间的墙，BEM 负责组件内部的秩序。墙之内类名照样按 BEM 来，哪天某个页面去掉 scoped（比如服务端渲染的场景）也不慌。

谈判第三回合：嵌套层数，从"随意"砍到 3

聊完命名聊嵌套。我把项目里一段真实代码投到了会议室屏幕上（当事人就在场，气氛一度微妙）：

Sass 嵌套写起来太顺了，看着 DOM 结构往里缩进就完事。但它编译出来是 .page .list .item .title span，五层后代选择器。问题有两个，一个比一个隐蔽：

第一，权重失控。这条选择器特异性高得离谱，哪天想在某个状态下把这个 span 改成蓝色，就得写一条同样长甚至更长的选择器去压它，或者祭出 !important。我们项目那两百多处 !important，根源就是早期嵌套太深，后人只能用核武器覆盖。

第二，和 HTML 结构强绑定。设计师说把 span 换成 i 标签，或者中间多包一层 div，样式立刻失效。CSS 本该描述"长什么样"，结果被写成了"在第几层的什么标签里"，脆得很。

mixin 之争：我毙掉了一个 card-style

规范落地两周后，第一次按新规矩做 code review，我和他又讨论了一回。他提交了一个 mixin：

然后 .post-card { @include card-style; } 一行搞定。他很得意："复用啊，三个卡片组件都能用。"

我把它毙了。看着干净，实则灾难：想微调某个卡片的内边距，得跳进 mixin 看它到底生成了什么；改 mixin 又怕影响另外两个卡片。它把"复用"变成了"看不见的复制"，而且是三份绑在一起的复制。业务样式该直接写就直接写，几行重复远好过一个谁都不敢动的黑盒。

这些 mixin 的共同点是：调用方一眼能预期它生成什么。flex-center 就是居中，hairline 就是细线，没有惊喜。最后写进规范的口诀是：mixin 应该是工具，不是模板。工具是 ellipsis、flex-center 这种通用能力；模板是"某个组件长什么样"，那是组件自己的事。

这里再补一个相邻的坑，讨论 mixin 时顺带定的：@extend 和占位符 %placeholder 原则上不用。@extend 会把选择器合并到被继承的位置，编译产物里选择器的顺序和归属变得难以预测，配合媒体查询还会直接报错。真需要复用一段声明，mixin 的输出是"就地展开"，行为可预期得多。gzip 之下 mixin 多出来的那点重复体积，基本可以忽略。

权重计算，顺手在规范里补一段

谈判进行到后半段，有人提了个问题：BEM 类名都是单层选择器，权重理论上一致，那真遇到需要临时压过别人一头的场景（比如覆盖第三方组件库的默认样式），该怎么判断到底要写几层选择器才够。这个问题值得单独在规范里写清楚计算方式，免得又变成"加长选择器"或者" !important"这两条老路。

CSS 选择器的权重按四级来算，从高到低是内联样式、ID、类（包括属性选择器和伪类）、标签（包括伪元素）。BEM 体系下几乎不用 ID 选择器，也很少用标签选择器兜底，所以权重基本只在"类的数量"这一级别里比较。.post-card__button--primary 是两个类（post-card__button 和 post-card__button--primary 分开写在 HTML 里，但作为两条独立规则各自都是单类选择器），要压过它，理论上写一个双类选择器 .post-card__button.is-loading 就够了，完全不需要往上叠祖先节点。真遇到必须覆盖 Element UI 这类第三方组件默认样式的场景，我们内部的约定是宁可多写一层限定它的业务容器类（比如 .order-detail .el-button），也不写 !important——容器类既明确了"这是我们业务场景下的覆盖"，权重也够用，而且未来想撤销这条覆盖，删掉这条规则就行，不会有全局副作用。

落地：目录结构，加一道机器守门

谈下来的规矩，最后拼成了这套目录，一个中型 Vue 项目大概长这样：

src/styles/
  variables.scss   // 全局变量：颜色、间距、层级
  mixins.scss      // 通用 mixin：ellipsis、hairline、flex
  reset.scss       // 样式重置
  index.scss       // 入口，@import 上面三个

variables 和 mixins 因为只是声明、不产出实际 CSS，可以让构建工具全局注入，省得每个组件都 @import。我们有个用 Vue CLI 3 rc 试水的内部项目，配置写在 vue.config.js：

注意只注入变量和 mixin 这类"零产出"的文件，绝不要注入会生成实际样式的文件——否则每个组件都会被塞一份副本，打包体积爆炸。这个坑我替全组踩过了：有次手滑把 reset.scss 也注入进去，几十个组件各带一份 reset，最终 CSS 大了十几 KB，还是查打包分析报告才发现的。

半个月之后

上周他又改了一处 user-panel__title 的间距，提交信息还是"修复个人中心标题间距"。这次没有任何页面陪葬，QA 没有 @ 任何人，这个提交安静得像没发生过。

六月底那个下午，.title 那 20px 的位移砸出来的这场谈判，谈的从来不是"怎么写出效果"，而是"半年后还改不改得动"。BEM 让每个类名都有清楚的归属和状态，Sass 让复用和配置有了抓手，stylelint 让规矩不靠自觉。嵌套压到 3 层以内，样式靠类名归属而不靠 DOM 层级；变量只抽设计上稳定、真要全站统一的值；状态写成显式 modifier 类，让 JS 和 CSS 在同一个名字上对话；mixin 只做通用工具，不做组件模板，@extend 原则上不碰。样式写得清楚，永远比写得短重要——那个一改标题三页齐塌的下午，就是没人为"清楚"付过代价。

这份规范也不是终点。下个季度移动端项目要启动，涉及到跟现有 PC 中后台共享一部分变量和 mixin，到时候 variables.scss 要不要拆成"通用"和"平台专属"两层，是另一场还没开始的谈判。
