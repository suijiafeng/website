前端表单校验和 Zod：类型和运行时规则要对齐

2023-03-03
前端基础TypeScript

表单校验最怕两套规则。

TypeScript 里写一份类型，表单里写一份校验，提交前又手写一份清洗。时间一长，类型说字段必填，校验却允许为空；校验说手机号必须 11 位，接口实际还要求区号。问题不一定立刻暴露，但总会在某个边界数据上炸出来。

Zod 这类 schema 工具的价值，是把运行时校验和 TypeScript 类型尽量放到同一个来源。

表单错误要能落到字段

表单校验不是只返回 true/false。用户需要知道哪个字段错了。

safeParse 比 parse 更适合表单，因为它不会直接 throw，方便把错误回填到 UI。

前后端 schema 共享要谨慎

很多团队会想把 Zod schema 前后端共享。这个方向是好的，但要注意边界。

前端表单 schema 和后端接口 schema 不一定完全一样。前端可能有确认密码、临时上传文件、展示字段；后端可能有权限字段、审计字段、服务端生成字段。

我的使用清单

我会优先在这些地方用 schema：

  • 复杂表单
  • URL 参数解析
  • localStorage 草稿恢复
  • 关键接口响应校验
  • 前后端共享的 DTO 边界

不一定需要的地方：

  • 只有一两个简单字段的小表单
  • 完全静态配置
  • 已经由成熟表单库和后端强校验覆盖的低风险页面

Zod 的价值不是让代码显得更类型化，而是让“这个数据到底应该长什么样”有一个运行时也能执行的答案。
