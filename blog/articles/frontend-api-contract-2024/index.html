前后端接口契约：别让 TypeScript 只保护前端自己

2024-05-10
前端基础TypeScript构建与模块化

TypeScript 能让前端代码更稳，但它保护不了真实接口返回。

你在前端写了一个类型：

这只能说明“前端希望它长这样”。后端实际返回 avatar_url、avatarUrl: null、或者漏了字段，TypeScript 在运行时完全不知道。

我遇到过一个很典型的问题：列表页上线后偶现白屏，本地 mock 从来没复现。最后发现后端某些历史数据 name 是 null，前端类型写的是 string，组件里直接 user.name.trim()。类型没报错，线上直接炸。

所以接口契约的重点不是前端自己写类型，而是让前后端对同一份约定负责。

类型来源要尽量单一

最差的情况是：后端有 DTO，接口文档有一份字段说明，前端再手写一份 TypeScript 类型。

三份东西只要有一份没同步，就会出问题。

更好的方式是从契约生成类型。常见来源有：

  • OpenAPI / Swagger
  • GraphQL schema
  • tRPC / RPC 类型共享
  • 后端导出的 JSON Schema
  • 前后端共享的 schema 包

这样字段改名、必填变可选、枚举新增，都能在类型层被前端感知。

当然，生成类型不是银弹。接口文档必须准确，后端也要把文档当交付物维护。如果 Swagger 只是“看起来有”，实际和返回不一致，那生成出来的类型也是错的。

错误响应也要有契约

很多团队只认真设计成功响应，错误响应随缘。

或者不同接口各写各的：

前端最后只能到处写兼容逻辑。

我更希望错误响应至少稳定包含：

code 给程序判断，message 给默认展示，requestId 给排查日志，fields 给表单错误回填。

前端处理错误时不要只看 HTTP status，也不要只看 message：

API 错误必须有明确处理路径。否则线上只会剩下一堆“接口报错了”的模糊反馈。

运行时校验补上最后一公里

即使有生成类型，我仍然建议在关键边界做运行时校验。

因为类型只在编译期存在，真实数据来自网络、缓存、第三方系统和历史脏数据。关键页面如果不能接受脏数据，就应该在入口校验。

校验失败时也要处理，不要让错误直接白屏：

不是每个接口都要上严格校验。我的原则是：权限、支付、配置、核心详情页、跨团队接口优先校验；普通低风险列表可以先依赖类型和兜底。

Mock 要从契约生成

Mock 数据如果手写，很容易和真实接口分叉。

比如前端 mock 里 status 只有 pending 和 done，线上后端新增了 cancelled，前端没处理就出问题。

如果契约里有枚举，mock 应该覆盖边界值：

测试数据至少要包含每一种状态，而不是只给最顺利的一条。

我更喜欢把 mock 当成契约测试的一部分：字段缺失、空数组、null、超长文本、错误码都要有样本。这样前端在开发阶段就能看到极端情况。

变更要分兼容和不兼容

接口变更不是一句“前端改一下”。

兼容变更包括：

  • 新增可选字段
  • 新增枚举但前端有兜底
  • 新增接口

不兼容变更包括：

  • 删除字段
  • 必填变可选
  • 字段类型变化
  • 枚举值语义变化
  • 错误码变化

不兼容变更要有迁移计划。最稳的方式是后端先双写或兼容一段时间，前端切换后再删除旧字段。

这看起来有点笨，但比前后端同时上线赌时序安全。尤其是多端应用，Web、iOS、Android、小程序发版节奏不一样，后端不能只按 Web 的节奏删字段。

我的接口契约清单

我会重点看这些点：

  • 类型是否来自同一份契约，而不是前端手写猜测
  • 错误响应是否有稳定 code 和 requestId
  • 表单错误是否能回填到字段
  • 关键接口是否做运行时校验
  • Mock 是否覆盖空值、异常值和枚举边界
  • 不兼容变更是否有过渡期
  • 前端是否对未知枚举和未知错误码有兜底

接口契约的目标不是让文档更好看，而是减少“你以为”和“我以为”。前后端共享同一份事实，TypeScript 才能真正保护到系统边界。
