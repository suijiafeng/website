Vue 单文件组件为什么离不开 Webpack：从 .vue 文件说起

2018-06-22
Vue构建与模块化

很多人第一次看到 Vue 的 .vue 文件时，都会觉得这东西很顺手。

模板、脚本、样式放在一个文件里，写组件时非常舒服。可写得顺手，不代表浏览器天生认识它。

浏览器并不理解 .vue 文件，能让这套写法成立的，背后其实是构建工具。

Webpack 和 vue-loader 的价值，就是把适合开发者书写的组件格式，转换成浏览器能够执行的 JavaScript、CSS 和资源引用。

我刚开始写 Vue 的时候完全没想过这层。直到有一次想脱离脚手架、用一个最简单的 HTML 配 CDN 引入 Vue 来跑 .vue 文件，结果浏览器报了一堆看不懂的语法错误，我才意识到：.vue 根本不是浏览器能直接吃的东西，平时之所以"写完就能跑"，全是 webpack 在背后默默干活。搞懂这条链路之后，很多以前觉得玄乎的报错一下子就有头绪了。

单文件组件为什么好用

单文件组件最大的好处，是把一个组件真正聚合在一起。

一个组件通常本来就包含三部分：

  • 结构
  • 逻辑
  • 样式

以前这些内容可能散落在多个文件里，维护起来总要来回切。SFC 的好处就在于，组件边界更完整。

但浏览器并不会直接执行它

.vue 文件不是浏览器原生支持的格式，所以它必须先被处理。

这里 Webpack 的价值就体现出来了。它不是在“帮你写 Vue”，而是在帮你把这些开发阶段的写法转换成浏览器能运行的代码。

如果没有构建工具，浏览器拿到 .vue 文件只会把它当成未知资源。它不会自动理解 <template> 应该编译成 render 函数，也不会知道 <style scoped> 该怎么隔离样式。

vue-loader 的角色

如果说 Webpack 是总调度，那 vue-loader 就是专门处理 .vue 文件的那一层。

它会把：

  • <template>
  • <script>
  • <style>

拆开处理，再交给对应的 loader 去接力。

这也是为什么你在 Vue 项目里明明只写了一个组件文件，最后浏览器却能正常拿到 JS 和 CSS。

这里有个 vue-loader 15 的大坑值得专门提一下。早期 vue-loader 13/14 的时候是不需要单独引 VueLoaderPlugin 的，老教程和老配置里也没有这一行。升级到 vue-loader 15（配合 webpack 4）之后，架构变了：它现在依赖一个插件把你为普通 .js、.css 配的规则"复制"一份应用到 .vue 文件内部对应的语言块上。如果你漏了 new VueLoaderPlugin()，报错信息是这句很迷惑的：

理解这个机制还有个实际好处：你为 .css 配的 style-loader + css-loader，会自动作用到 .vue 文件里的 <style>；你配的 .scss 规则，也会自动应用到 <style lang="scss">。所以处理 SFC 内部的样式，不需要再为它单独写一套 loader 规则，复用普通规则就行——这正是 VueLoaderPlugin 在背后帮你做的事。

模板编译还分两种时机，这点不少人没注意。一种是运行时编译：你引的是完整版 Vue（带 compiler），模板字符串在浏览器里实时编译成 render 函数；另一种是预编译：构建阶段就由 vue-template-compiler 把 <template> 编译好，运行时只需要那个轻量的 runtime-only 版 Vue。Vue CLI 默认走的是后者，所以打包产物更小、首屏也更快。

这就引出一个常见报错：当你直接用 new Vue({ template: '...' }) 或者动态传字符串模板，而项目里装的是 runtime-only 版本时，控制台会甩给你这句——

意思是运行时根本没带编译器，自然编译不了字符串模板。解决办法要么改用 render 函数，要么在配置里把 Vue 的别名指到完整版（vue/dist/vue.esm.js），但后者会让包变大，多数情况下还是老老实实用 .vue 文件 + 预编译更划算。我自己的原则是：能在 .vue 文件里写模板，就绝不在 JS 里拼字符串模板，既避开了这个坑，预编译的性能红利也白拿。

还有个细节是 vue-template-compiler 的版本必须和 vue 主版本严格对齐，差一个小版本都可能编译出问题。它们俩本来就该一起升级，我每次升 Vue 都会顺手 check 一下这个包的版本，别让它掉队。

scoped 样式不是影子 DOM

很多人看到 <style scoped>，会以为它像 Shadow DOM 一样完全隔离。实际上 Vue 的 scoped 样式通常是通过给元素加属性选择器实现的。

类似这样：

它能降低样式串扰，但不是绝对隔离。全局样式、第三方组件样式、深度选择器仍然可能影响组件。

所以 scoped 很有用，但不要把它当成随意命名的理由。组件类名依然要清楚。

scoped 最让人意外的一点，是它对子组件的"穿透"行为。父组件的 scoped 样式，默认只会给子组件的根元素打上那个 data-v-xxx 属性，子组件内部的元素是不带的。也就是说你想在父组件里改子组件深处某个元素的样式，普通写法是不生效的——这个坑我撞过无数次，最典型就是想改 Element UI 某个组件内部的样式，怎么写都不起作用。

另外提一句性能：scoped 给每个元素都加属性选择器，选择器的特异性和数量都会上去，绝大多数项目无所谓，但在超大列表里堆太多 scoped 规则，理论上是有一点点开销的。不过这从来不是我优化的重点，知道有这回事就够了。

Webpack 不只是打包

很多初学者会把 Webpack 理解成“把文件合并一下”。实际上在 Vue 项目里，它做的事情远不止这些。

例如：

  • 处理单文件组件
  • 转换 ES Module
  • 编译样式预处理器
  • 处理图片和字体资源
  • 做代码拆分

说到底，它在替你把开发体验和浏览器运行环境之间的差距补上。

构建时这个资源会被解析、复制、重命名或内联，最终变成浏览器能请求到的地址。你写的是项目路径，用户拿到的是构建产物。

这里"复制"还是"内联"是由 url-loader 的 limit 决定的，这个机制很实用：小于阈值的图片会被转成 base64 直接内联进 CSS/JS，省掉一次 HTTP 请求；超过阈值的才作为独立文件输出。

文件名里那个 [hash:8] 也不是装饰——它是内容指纹，文件内容变了 hash 才变。配合服务端的长缓存策略，没改动的图片浏览器就一直走缓存，改了的因为文件名变了会自动重新拉取。我刚工作时不懂这套，发版后总让用户"清缓存才能看到新图"，后来理解了 hash 命名才知道根本不该有这种操作。

还有一个 .vue 里特别容易踩的点：<template> 里 <img :src="变量"> 这种动态绑定的路径，webpack 是不会去解析的。因为构建时它只是个字符串变量，loader 根本不知道你要引哪个文件。静态的 src="@/assets/x.png" 才会被处理。所以动态图片要么放 public/static 目录走绝对路径，要么在 JS 里显式 require('@/assets/' + name) 让 webpack 介入。这个区别我也是被坑过才记牢的。

理解工具链能帮助排错

当 Vue 项目报错时，错误经常出现在工具链边界上：

  • 模板语法错误
  • loader 配置缺失
  • 样式预处理器没装或版本不匹配
  • 图片路径无法解析
  • Babel 没有处理目标语法

知道 .vue 文件会被拆成几段处理，就能更快定位问题。比如样式报错不一定是 Vue 的问题，可能是 sass-loader 或 CSS 处理链路的问题。

Vue 单文件组件之所以让人觉得自然，是因为 Webpack 把复杂度挡在了后面。

你写 .vue 文件时感受到的是组件化的轻松，但这份轻松本身，就是工具链替你换来的。理解这一点之后，再看 Vue 项目的构建过程就不会那么抽象了。

会写组件只是第一步，知道组件怎样被编译、拆分和加载，才更容易在项目变大后保持稳定。
