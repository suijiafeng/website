Vue 单文件组件为什么能跑：从 `vue-loader` 到最终构建产物

2018-06-22
Vue构建与模块化

浏览器并不认识 .vue 文件，这件事很多人直到第一次脱离脚手架才会真正意识到。平时单文件组件“写完就能跑”，不是浏览器突然学会了新语法，而是构建工具一直在背后替你拆、编、转。

所以理解 .vue 为什么能跑，关键不在 Vue 组件 API 本身，而在 vue-loader 到最终产物这条构建链。模板怎么变成 render，样式怎么带上作用域标记，脚本又是怎么和这些片段重新组装回去，答案都在那里。

组里新来的实习生这周正好在看 SFC 相关的代码，问我”为什么 .vue 文件能被 import”，我干脆把这条链路完整讲了一遍给他听——这事一句话讲不完，但搞懂这条链路之后，很多”玄乎报错”都会一下子有头绪。下面就按他那天的提问顺序，从”浏览器为什么最后能执行它”讲起，不从”组件怎么写”讲起。

先回答”为什么要有 .vue 这种东西”

实习生的第一反应是：既然浏览器不认识，为什么不老老实实分三个文件写？

因为单文件组件（SFC）最大的好处，是把一个组件真正聚合在一起。一个组件本来就天然包含三部分：

  • 结构
  • 逻辑
  • 样式

以前这些内容散落在多个文件里，维护起来总要来回切。SFC 让组件边界更完整。一个典型的单文件组件长这样：

这不是把 HTML、JS、CSS 简单塞进一个文件，而是把组件的结构、行为和局部样式放进同一个边界内。

但浏览器确实不认识它。.vue 不是浏览器原生支持的格式，你直接丢给浏览器，它只会把它当成未知资源——它不会自动理解 <template> 该编译成什么，也不知道 <style scoped> 该怎么隔离样式。所以它必须先被处理。

**Webpack 的价值就在这：它不是在"帮你写 Vue"，而是把这些适合开发者书写的格式，转换成浏览器能执行的 JavaScript、CSS 和资源引用。**你写代码时舒服的那一头，和浏览器运行时苛刻的那一头，中间的差距全是它在补。

拆解第一站：vue-loader

他追问：那 webpack 拿到一个 .vue 文件，具体干了什么？

如果说 webpack 是总调度，vue-loader 就是专门处理 .vue 文件的那一层。它把一个 .vue 文件按块拆开：

  • <template>
  • <script>
  • <style>

拆完再交给对应的 loader 接力处理。这就是为什么你明明只写了一个组件文件，浏览器最后却能正常拿到 JS 和 CSS。

讲到 VueLoaderPlugin 我特意停下来敲了敲黑板，因为这是今年升级里的一个大坑。早期 vue-loader 13/14 是不需要单独引这个插件的，老教程老配置里都没这行。今年配合 webpack 4 升到 vue-loader 15 之后，架构变了：它现在依赖这个插件，把你为普通 .js、.css 配的规则"复制"一份，应用到 .vue 文件内部对应的语言块上。漏了 new VueLoaderPlugin()，报错是这句很迷惑的：

我四月份第一次升级遇到它，盯着 vue-loader 的版本号查了半天，其实答案明明白白写在错误里——少了插件。从那以后我装 vue-loader 必定第一时间把这行加上。

理解这个机制还有个实际好处：你为 .css 配的 style-loader + css-loader，会自动作用到 .vue 文件里的 <style>；你配的 .scss 规则，也自动应用到 <style lang="scss">。所以处理 SFC 内部的样式不需要再单独写一套 loader 规则，复用普通规则就行——这正是 VueLoaderPlugin 在背后做的事。

拆解第二站：template 去哪了

他下一个问题很敏锐："那 <template> 里那些 {{ }}、@click，浏览器也不认识吧？"

模板越薄，编译后的结构越容易理解，组件也更好维护。

模板编译还分两种时机，这点不少写了很久 Vue 的人都没注意。一种是运行时编译：引完整版 Vue（带 compiler），模板字符串在浏览器里实时编译成 render 函数；另一种是预编译：构建阶段由 vue-template-compiler 把 <template> 编译好，运行时只需要轻量的 runtime-only 版 Vue。脚手架的 webpack 模板默认走后者，打包产物更小、首屏更快。

这就引出一个常见报错。当你直接 new Vue({ template: '...' }) 或动态传字符串模板，而项目里用的是 runtime-only 版本时，控制台会甩给你——

意思是运行时根本没带编译器，自然编译不了字符串模板。解决办法要么改用 render 函数，要么在 webpack 里把 Vue 的别名指到完整版（vue/dist/vue.esm.js），但后者会让包变大。多数情况下老老实实用 .vue 文件 + 预编译更划算。我自己的原则是：能在 .vue 文件里写模板，就绝不在 JS 里拼字符串模板，既避开这个坑，预编译的性能红利也白拿。

还有个细节：vue-template-compiler 的版本必须和 vue 主版本严格对齐，差一个小版本都可能编译出问题。它俩本来就该一起升级，我每次升 Vue 都顺手 check 一下这个包，别让它掉队。

拆解第三站：scoped 样式是怎么"隔离"的

他又指着 <style scoped> 问："这个 scoped 是不是像 Shadow DOM 那样完全隔离？"

不是，而且这个误解很普遍。Vue 的 scoped 样式是靠给元素加属性选择器实现的。构建后大概长这样：

它能降低样式串扰，但不是绝对隔离——全局样式、第三方组件样式、深度选择器仍然可能影响组件。所以 scoped 很有用，但别把它当成随意命名的理由，组件类名依然要清楚。

scoped 最让人意外的一点，是它对子组件的行为。父组件的 scoped 样式，默认只会给子组件的根元素打上那个 data-v-xxx 属性，子组件内部的元素是不带的。也就是说你想在父组件里改子组件深处某个元素的样式，普通写法不生效——这个坑我撞过无数次，最典型的就是想改 Element UI 某个组件内部的样式，怎么写都不起作用。

另外提一句性能：scoped 给每条规则都加属性选择器，选择器的数量和复杂度都会上去。绝大多数项目无所谓，但超大列表里堆太多 scoped 规则，理论上有一点点开销。这从来不是我优化的重点，知道有这回事就够。

样式这条链路上还有一层他没注意到：<style> 出去之后，除了 css-loader、vue-style-loader，通常还会经过 postcss-loader。项目里配的 autoprefixer 就是靠这层加上 -webkit-、-ms- 这些前缀的，我们写 display: flex 或者 position: sticky，从来不用自己手动加浏览器前缀，全是构建时插进去的：

这也是为什么同一份 <style scoped>，开发环境和构建产物打开看内容不一样——scoped 加的属性选择器、postcss 加的前缀，全叠在这一层跑完。前缀目标浏览器写在这一份配置里，和前面提过的 browserslist 概念是同一件事，只是 postcss 这边写法略有不同，团队里最好统一到一处维护，不然两边配置一旦不同步，兼容行为就会各说各话。

他还顺带问了 CSS Modules 是不是也走这条链路。我说是同一层 css-loader 在管，但思路和 scoped 完全不同：scoped 是给选择器加属性做隔离，CSS Modules 是把类名编译成哈希过的唯一字符串，.vue 文件里要用 <style module> 才会启用，组件里通过 this.$style.className 取用编译后的真实类名。两条路都能防止样式冲突，我们项目里统一用了 scoped，一是因为 scoped 写法和普通 CSS 几乎没差别，团队上手成本低；二是 CSS Modules 那套 $style 取值方式和惯常的 class 写法不一样，混着用容易让新人犯糊涂。这属于团队约定层面的取舍，没有绝对的对错。

眼见为实：带他看 dist 目录

讲到这，我觉得光说不够，干脆 npm run build，带他把 dist 目录翻了一遍。看一次构建产物，胜过读十篇文章。

他看到的是：没有任何一个 .vue 文件；JS 被合并成了几个带 hash 的 bundle；CSS 被抽成了独立文件；他写的 <template> 在 bundle 里变成了一段 render 函数的压缩代码，搜他写的类名还能搜到旁边跟着 data-v- 开头的属性。"原来我写的东西最后是这样。"他说。

我顺着产物给他讲了资源这条线。比如组件里引用图片：

构建时这个资源会被解析、复制、重命名或内联，最终变成浏览器能请求到的地址。你写的是项目路径，用户拿到的是构建产物。"复制"还是"内联"由 url-loader 的 limit 决定，这个机制很实用：小于阈值的图片转成 base64 直接内联进 CSS/JS，省一次 HTTP 请求；超过阈值的才输出独立文件。

文件名里那个 [hash:8] 也不是装饰——它是内容指纹，文件内容变了 hash 才变。配合服务端的长缓存策略，没改动的资源浏览器一直走缓存，改了的因为文件名变了自动重新拉取。我刚工作时不懂这套，发版后总让用户"清缓存才能看到新图"，理解了 hash 命名才知道根本不该有这种操作。

还有一个 .vue 里特别容易踩的点，我提前打了预防针：<template> 里 <img :src="变量"> 这种动态绑定的路径，webpack 是不会解析的。构建时它只是个字符串变量，loader 根本不知道你要引哪个文件；静态的 src="@/assets/x.png" 才会被处理。所以动态图片要么放 static 目录走绝对路径，要么在 JS 里显式 require('@/assets/' + name) 让 webpack 介入。这个区别我也是被坑过才记牢的。

开发时的两个"魔法"，也是 webpack 给的

他最后问了个日常体验的问题："那我开发的时候改一下样式，页面不刷新就变了，这也是它干的？"

对，这叫热更新（HMR，模块热替换），webpack-dev-server 提供的。它在内存里维护构建结果，文件一改就把变化的模块推给浏览器替换掉，改样式、改模板都不用整页刷新，data 里的状态还能保住——调一个填了一半的表单页时格外幸福。这不是 Vue 的魔法，是 dev server 和 vue-loader 配合出来的开发体验。

另一个是 source map。他调试时在 DevTools 里看到的是自己写的 .vue 源码，能直接在上面打断点——但浏览器实际执行的明明是编译后的 bundle。这靠的是构建时生成的映射文件，webpack 配置里的 devtool 选项管这个。开发环境我们用 cheap-module-eval-source-map，构建快、能定位到源码行；生产环境要么关掉，要么用独立的 .map 文件配合错误上报。报错堆栈指到 bundle 里看不懂的位置时，第一反应该是查 source map 配置，而不是怀疑人生。

顺便说一句，这些能力在 webpack 4 里比以前省心了不少——新加的 mode: 'development' / 'production' 会按环境自动套上一批合理默认值，生产模式自带压缩和作用域提升。我们今年年初从 webpack 3 升上来，构建速度也确实快了一截，就是配套的 loader 和插件版本得跟着捋一遍，vue-loader 15 那个坑就是升级路上捡的。

答疑收尾：这层理解值多少

那天最后我跟他说：知道这条链路，最直接的回报是排错。Vue 项目报错，错误经常出在工具链边界上：

  • 模板语法错误
  • loader 配置缺失
  • 样式预处理器没装或版本不匹配
  • 图片路径无法解析
  • Babel 没有处理目标语法

知道 .vue 文件会被拆成几段、各自走什么链路处理，就能更快定位问题。比如样式报错不一定是 Vue 的问题，可能是 sass-loader 或 CSS 处理链路的问题；import 报语法错误，多半是 babel-loader 的 exclude 把某个需要转译的包排除掉了。

回到他最开始那个问题——.vue 浏览器不认识，为什么能跑？因为 Vue 单文件组件之所以让人觉得自然，是 webpack 把复杂度全挡在了后面。你写 .vue 文件时感受到的组件化的轻松，本身就是工具链替你换来的。理解这一点，再看 Vue 项目的构建过程就不抽象了。

周五他在群里贴了个报错自己解决了——正是那个 runtime-only 的模板编译错误，他一眼认出来，改成了 .vue 文件写法。这次答疑算是值了。会写组件只是第一步，知道组件怎样被编译、拆分和加载，才更容易在项目变大后保持稳定。
