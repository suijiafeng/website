从 Vue CLI 迁到 Vite：真正麻烦的不是改命令

2022-02-18
构建与模块化前端基础

2022 年很多 Vue 项目开始从 Vue CLI 或 Webpack 迁到 Vite。

迁移的直接收益很明显：开发服务器启动快，热更新快，配置更轻。但真正做迁移时，麻烦往往不在把 npm run serve 改成 npm run dev，而在那些项目历史里积累的构建假设。

我迁过一个老后台，第一天就跑起来了，第二天开始补坑：环境变量读不到、别名失效、图片路径错、CommonJS 包不兼容、mock 插件要换、生产构建结果和开发环境不一致。迁移不是换工具，而是重新梳理工程边界。

CommonJS 依赖要重点看

Vite 开发环境基于 ESM，遇到一些老 CommonJS 包可能会有兼容问题。

常见表现：

  • 默认导入不对
  • 包依赖 Node 内置模块
  • 开发环境正常，生产构建失败
  • 生产正常，dev 预构建失败

可以先检查是否有 ESM 版本，或者升级依赖。如果短期不能升级，再考虑配置 optimizeDeps 或替换导入方式。

不要为了一个老包写太多兼容配置。迁移工具链时，顺手清理长期没人维护的依赖，通常更划算。

dev 和 build 都要验证

Vite dev 和 build 不是同一条链路。dev 用 esbuild 预构建依赖，build 用 Rollup 打包。

所以只跑 npm run dev 不够，还要跑生产构建和 preview：

按项目规则，这类验证可以在需要时跑；迁移时我一定会跑。因为很多问题只在生产构建暴露，比如动态导入、资源路径、CSS 顺序。

API 错误处理顺手统一

迁移过程中经常会碰到请求封装。不要只改 baseURL，也可以顺手检查错误处理。

至少要让 API 错误有统一出口。迁移后如果接口地址错了、代理配置错了，页面应该显示明确错误，而不是静默空白。

我的迁移清单

迁 Vite 时，我会逐项看：

  • package scripts、CI、部署脚本是否同步
  • 环境变量是否改成 import.meta.env 且无敏感泄露
  • alias 是否同时配置 Vite 和 tsconfig
  • 静态资源和动态导入是否兼容
  • 老 CommonJS 依赖是否能正常预构建
  • dev、build、preview 是否都验证
  • 代理、mock、接口错误处理是否正常

Vite 迁移本身不难，难的是把旧项目里隐含的构建假设找出来。迁移做得好，项目会变快；迁移做得急，只是把旧问题搬到新工具上。
