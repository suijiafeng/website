JavaScript this 指向：call、apply、bind 不是背 API 就够了

2018-03-14
JavaScript前端基础

this 是 JavaScript 里最容易让人迷糊的点之一。

同一个函数，换一种调用方式，this 就变了。它经常被拿来考察基础，项目里也确实容易因为它出 bug。尤其是事件回调、定时器、Ajax 回调里，this 丢失很常见。

理解 this 的关键不是看函数写在哪里，而是看函数怎么被调用。

我刚工作那会儿，对 this 的理解全靠"经验直觉"，写得多了大概知道哪种情况会出问题，但说不清原因。直到有次接手一个 jQuery 时代的老后台，里面满屏的 var that = this、var _this = this、var self = this，同一个文件里三种命名都有，看得我头疼。我当时就想，这帮人为什么要这么写？后来真正搞懂 this 的绑定规则才反应过来——他们不是闲的，是在用最朴素的办法对抗"回调里 this 丢失"。把规则吃透之后，我再看这些代码就不慌了，也知道哪些能用箭头函数干净地替掉。

普通函数调用

普通函数直接调用时，非严格模式下 this 指向全局对象。严格模式下是 undefined。

所以业务代码里不要依赖普通函数调用时的全局 this。

另外箭头函数没有自己的 this，连带着也没有自己的 arguments，也不能用 call/apply/bind 改它的 this（改了不报错，但没效果），更不能当构造函数 new。这些限制平时不显眼，真撞上了排查起来很费劲。

优先级

大致规则：

  1. new 调用优先级最高
  2. call、apply、bind 显式绑定
  3. 对象方法调用
  4. 普通函数调用

箭头函数单独看，它没有自己的 this，不能用这些规则简单套。

实际判断一个 this 指向哪，我的习惯是从上往下问四个问题：

  1. 是箭头函数吗？是的话直接看它定义时外层的 this，下面三条都不用看了。
  2. 是用 new 调的吗？是的话 this 是新建的实例。
  3. 有没有 call/apply/bind 显式绑定？有的话 this 是绑定的那个对象。
  4. 是不是 obj.fn() 这种带点号调用？是的话 this 是点号左边的对象；都不是，就是光杆调用，落到全局或 undefined。

按这个顺序走一遍，几乎所有 this 的题都能秒判。需要补一句的是：现在写新代码用 strict mode（模块里默认就是严格模式）的越来越多，光杆调用时 this 是 undefined 而不是 window，这反而是好事——以前那种"忘了 new 把属性悄悄挂到全局"的隐蔽 bug，严格模式下会直接抛错，问题暴露得更早。

this 不看函数在哪里写，而看它怎么被调用。

面试问 this，通常会连着问对象方法、回调丢失、call/apply/bind、箭头函数和构造函数。项目里最常见的问题是回调里 this 丢失，以及 bind 后无法解绑事件。

把调用方式看清楚，this 就不再那么玄。
