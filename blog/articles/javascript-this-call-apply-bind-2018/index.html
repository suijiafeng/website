JavaScript this 指向与 call、apply、bind：从一个回调丢 this 的真实 bug 讲清楚

2018-03-14
JavaScript前端基础

组里一个同事遇到一个 bug 来问我：一个对象方法传进 setTimeout，里面的 this 已经不是原来那个对象了，导致取值全部不对。

我瞄了一眼代码，心里想这个坑很熟，张口就来："回调里 this 丢了，加个 bind 就好。"他照做，bug 确实好了。然后他问了一句："为什么传进 setTimeout 之后 this 就丢了？"

我说："因为调用它的不是你的对象了。"他接着问："那调用它的是谁？this 变成什么了？"我说是 window。他又问："那要是严格模式呢？箭头函数为什么就不丢？箭头函数是把 this 绑定到定义时的对象上吗？"

第三问我就开始含糊了。"绑定到定义时的对象"这个说法自己讲出来都觉得不对劲，但一时又说不出哪里不对，讲了两分钟也没讲透。

this 的坑靠"经验直觉"基本都能绕开：看到回调就下意识 bind，看到老代码里的 var self = this 也知道是干嘛的。但"能绕开坑"和"能讲清楚规则"是两回事。当晚把《You Don't Know JS》里 this 那章翻出来重读了一遍，又把手头项目里的相关代码过了一轮，把整个体系重新捋了一遍。下面就按被问住的顺序，把 this、call、apply、bind 和箭头函数重新讲一遍。

第一问：传进 setTimeout 之后，this 为什么变了

先把那段代码简化出来：

这里最容易讲错的地方，就是脱口而出"this 丢了、读 this.name 会是 undefined"。实际验证一下会发现，浏览器里跑出来的是空字符串 ''，不是 undefined。原因要往下拆两层：this 不看函数写在哪里，只看函数怎么被调用，函数体长在 page.init 里面这件事，对 this 毫无意义。

那这个匿名函数是怎么被调用的？它被当作参数交给了 setTimeout，一秒后由浏览器的定时器机制直接调用——一次"光杆调用"，前面没有任何对象。而普通函数光杆调用时，非严格模式下 this 指向全局对象，在浏览器里就是 window：

这个例子里因为外层用 var name = 'global' 声明了一个全局变量，它本质就是 window.name = 'global'，所以 this.name 能读到 'global'。但回到 page.init 那段代码，setTimeout 回调里的 this 同样变成了 window，这次读的 this.name 却不是 page.name（那个 'list' 从头到尾没被回调访问到），而是 window.name——window 对象上天生就有一个 name 属性，默认值是空字符串 ''，而不是 undefined。它是浏览器窗口自带的属性，本来是用来跨页面传字符串数据的（比如 window.name 在同一个标签页跳转之间不会被清空，早年有人拿它做过简易的跨页数据传递），平时业务代码很少特意用到它，但它确确实实存在，不是空的。

严格模式下才是 undefined——严格模式下光杆调用的 this 本身就是 undefined，读 undefined.name 会直接抛 TypeError: Cannot read property 'name' of undefined，报错反而更直接。顺带一提，HTML5 规范里还专门写明：setTimeout 的回调即使在严格模式下，this 也依然会被设成 window，不会是 undefined——这是个容易被忽略的特例，浏览器环境下 setTimeout/setInterval 的回调统一按非严格模式的全局对象处理。

所以第一问的完整答案是：不是"this 丢了"这么玄乎，而是调用方式从 page.init() 变成了光杆调用，this 按规则落回了 window；此时 this.name 读的是 window.name，它默认是空字符串，不是 undefined。"丢失"只是业务视角上的说法，规则视角里它一步都没乱，只是换了一个读取目标而已。

第三问：箭头函数到底把 this 绑到了哪

"箭头函数是把 this 绑定到定义时的对象上吗"——这个说法听着顺耳，但经不起细究，很容易讲得含糊。准确的说法是：箭头函数根本没有自己的 this。它不参与任何绑定规则，函数体里写的 this，就像一个普通变量一样，沿作用域链找到外层函数的 this 来用。

Vue 靠在调用方法时把 this 绑到组件实例上来工作，你写箭头函数等于拒绝了这个绑定。我的经验是一句话：对象和组件的方法本身用普通函数，方法内部的回调用箭头函数——一个要接受调用方的绑定，一个要锁住外层的 this，需求正好相反。

另外箭头函数没有自己的 this，连带着也没有自己的 arguments，不能用 call/apply/bind 改它的 this（改了不报错，但没效果），也不能当构造函数 new。这些限制平时不显眼，真撞上了排查起来很费劲。

显式绑定：call 和 apply

回调丢 this 是"被动"的一面，call/apply/bind 是"主动"的一面——直接指定 this 是谁。

call 和 apply 的差别就一个：传参方式不同，一个铺开传，一个用数组传。我记它俩的口诀是"Apply 对应 Array"，A 开头的用数组，剩下那个就是逐个传。功能完全等价，纯看手头参数是散的还是已经在数组里。

new 调用：this 是新造的对象

用 new 调用时，this 指向新创建的对象。忘了 new 就热闹了：

非严格模式下这等于光杆调用，this.name = name 把 name 悄悄挂到了全局对象上，p 本身是 undefined——两个 bug 一次配齐，而且都不报错。老代码里这类问题不少见。好消息是严格模式（ES6 模块里默认就是）下光杆调用的 this 是 undefined，忘写 new 会直接抛 TypeError，问题暴露得更早。这也是新项目值得全面上严格模式的理由之一：把隐蔽 bug 变成显式报错。

new 还有一个容易被忽略的连带影响：如果构造函数里显式 return 了一个对象，new 会用这个返回的对象顶替掉本该新建的实例；但 return 一个原始值（数字、字符串、布尔值等）会被忽略，照样返回新建的对象。这条规则平时很少被用到，但读到一些刻意利用它做单例模式的老代码时，能少一分困惑：

把四条规则排个序

把所有规则压成一个"从上往下问四个问题"的判断流程：

  1. 是箭头函数吗？是的话直接看它外层函数的 this，下面三条全不用看。
  2. 是用 new 调的吗？是的话 this 是新建的实例。
  3. 有没有 call/apply/bind 显式绑定？有的话 this 是绑定的那个对象。
  4. 是不是 obj.fn() 带点号调用？是的话 this 是点号左边的对象；都不是，就是光杆调用，落到全局或 undefined（事件回调等宿主指定 this 的场合另算）。

优先级也藏在这个顺序里：new 最高，显式绑定次之，点号调用再次，光杆兜底；箭头函数则根本不进这套规则，单独判。

讲清楚之后

隔了两天再和那位同事把这个 bug 重新过了一遍。这次没有从 bind 讲起，而是先立"看调用不看定义"的总纲，再按四个问题往下走，最后让他自己解释最初那个 bug。他讲完"setTimeout 调它的时候是光杆调用，所以 this 落到 window，读 this.name 读到的是 window.name 这个默认空字符串的属性，跟 page.name 完全没关系"，说明这次是真的理解了，比最初那句"加个 bind 就好"清楚得多。

**"会用"和"能讲清楚"之间隔着的，正是那些被追问几层才暴露出来的含糊地带。**下次再遇到 this 相关的问题，不用再靠直觉判断：先问一句"它是怎么被调用的"，四个问题过一遍，答案自己会浮出来。
