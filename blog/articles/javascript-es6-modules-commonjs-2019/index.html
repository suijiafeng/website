我刚开始也是糊里糊涂，反正 webpack/babel 都帮我编译了，写哪种都能跑，能跑就不想了。真正让我开始认真区分的，是有一次给一个公司内部的工具库发 npm 包，库里用的是 ES Module 写法，结果一个用 Node 直接 require 的脚本死活拿不到导出，报 undefined is not a function。查了半天才反应过来：我发上去的是 src 里的 ES Module 源码，对方的 Node 根本不认 import/export。从那以后我才意识到，这俩不只是写法的差别，连"什么时候、由谁来解析"都不一样。

CommonJS 是运行时加载。require 执行时，模块代码会被同步加载并执行一遍，返回 module.exports。这里"同步"很关键——require 是阻塞的，下一行代码要等模块执行完才会跑。所以 Node 里 require 一个大模块会卡住主线程，这在浏览器端是不可接受的（不可能让页面同步去网络上拉一个模块再继续），这也是浏览器原生模块用异步加载的根本原因。

我那会儿写工具函数库总是分不清，一会儿能导出一会儿导不出，后来记死一个规矩：只导单个对象/函数就用 module.exports =，零散挂多个就用 exports.xxx =，两种别混着写。

还有一点容易忽略：CommonJS 模块有缓存。同一个模块被 require 多次，只会执行一次，后面拿到的都是第一次的那个 module.exports：

这个缓存机制很有用（单例配置、数据库连接池都靠它），但也意味着模块里的顶层状态是全局共享的，写的时候得想清楚。

这也是为什么 webpack 配置文件里常用 CommonJS，因为 webpack.config.js 本来就是 webpack 启动时由 Node 直接跑的，还没进到打包流程里，自然得用 Node 认识的语法。

我们当年一个后台项目，首屏白屏时间长到被产品投诉，就是因为几十个页面全打进了一个 app.js，首次进来要下载两三 MB。改成路由级动态 import 之后，主包瘦了一大半，首屏快了好几秒。代价是切换路由时会有一次小小的加载延迟，体验上可以加个 loading，或者对核心几个页面用 prefetch 预拉。

要分清的是：import 静态语句和 import() 动态函数是两回事。前者是声明，必须顶层、被静态分析；后者是个返回 Promise 的运行时操作，可以写在任何地方、可以拼路径（但路径里至少要有一段静态字符串，webpack 才知道该把哪些文件打进候选）。

循环依赖要谨慎

循环依赖不是一定报错，但结果可能和直觉不同。尤其是 CommonJS 里，拿到的可能是未初始化完成的 exports。

项目里如果出现循环依赖，通常说明模块边界不够清楚。常见解决方式是抽出第三个公共模块，让双方都依赖它。

具体说说为什么 CommonJS 的循环依赖最坑。CommonJS 在遇到 require 时同步执行模块，如果执行到一半又 require 回了正在执行的自己，为了不死循环，Node 会直接把"当前已经导出到一半的 module.exports"返回给你。也就是说你可能拿到一个还没填完的对象：

ES Module 因为是"引用绑定"而不是值拷贝，循环依赖的容错性反而好一些——只要你别在模块顶层立刻去用那个还没初始化的值，等到函数真正被调用时绑定已经填好了，就没事。但这也只是"症状轻一点"，根上还是模块设计的问题。

我自己排查循环依赖有个土办法：装 circular-dependency-plugin 这个 webpack 插件，构建时它会直接把环打印出来。真有环的时候，顺着它指的链路去拆，比肉眼盯 import 快多了。

这是因为 ES Module 和 CommonJS 的导出模型不同，打包工具会做兼容处理，但不同工具处理细节可能不一样。

简单说，当你 import foo from 'some-cjs-module' 一个 CommonJS 模块时，Babel 编译后会去找它的 module.exports.default。可 CommonJS 模块根本没有 default 这个概念，它只是 module.exports = 一个函数/对象。Babel 为此引入了一个 __esModule 标记和 interopRequireDefault 的兼容逻辑：如果模块带了 __esModule: true，就取 .default；否则就把整个 module.exports 当默认导出。问题是不同工具、不同 Babel 版本对这个 interop 的处理不完全一致，于是就出现了有时要 .default 有时不要的玄学。

我被它坑得最惨的一次，是从 require 改写成 import 时：

到底该不该带 .default，规律是：看那个包发布的是 ES Module 还是 CommonJS。是 CJS 的，经过 Babel interop 一般 import x from 能正常拿到；但如果你的构建没开 interop、或者用的是不做兼容的 esbuild/rollup，就可能要 import * as x 或者手动 .default。

老项目里遇到 .default 不要慌，先看模块到底是怎么导出的——console.log(require('xxx')) 把它原样打出来，是函数就直接用，是 { default: ... } 就取 default，一目了然，别凭感觉猜。

小结

CommonJS 更常见于 Node 和配置脚本，ES6 Module 更适合前端业务代码和静态分析。

面试问模块化，通常会问 require 和 import 的区别、默认导出和命名导出、循环依赖、动态 import、tree shaking。项目里真正要注意的是：模块边界要清楚，导出方式要统一，不要让循环依赖慢慢长出来。
