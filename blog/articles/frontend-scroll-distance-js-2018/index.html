原生 JavaScript 获取页面滚动距离：一台老安卓机教我的三个问题

2018-04-12
JavaScript前端基础

三月份的一个需求，说起来简单到不值得开评审会：内容页加一个返回顶部按钮，滚过 400px 出现，再加一条顶部阅读进度条。

我半天就写完了，自己的电脑上丝般顺滑，提测。

第二天同事拿着他那台用了三年的安卓机走过来，把手机横在我面前划了一下。页面跟着他的手指一顿一顿地挪，进度条像卡了帧的秒针。他说："你这页面，卡成 PPT 了。"

我接过手机划了两下，脸有点挂不住。代码就这么几行，能有什么问题？

就是这几行。这次排查把我关于滚动的认知重写了一遍，最后沉淀成三个问题——现在我写任何跟滚动沾边的代码，都会先把这三个问题过一遍：读哪里、读多频、读完干了什么。

破案第一步：先看现场，别猜

我最初的反应是猜："是不是老机器就这样？"前辈路过甩了一句："录一段 Performance 再说话。"

Chrome DevTools 的 Performance 面板，连上真机录了三秒滚动。主线程上的景象让我头皮发麻：scroll 回调密密麻麻排成一片——滚动事件一秒能触发上百次，而我的回调每次都在查 DOM、读布局、改样式。平时不在意的小开销，被这个频率放大了一百倍。

在我自己的电脑上，CPU 好、屏幕刷新稳，这些开销被硬件性能掩盖了；老安卓机上无处可藏。

所以第一课：滚动相关的卡顿别靠感觉猜，Performance 录一段最诚实。接下来按三个问题往下查。

问题一：读哪里

先把最基础的事捋清楚：滚动距离到底从哪读。这一步我倒是没写错，但排查过程里我把这块的家底翻了个遍，记下来。

回到案发现场。Performance 里那一片密密麻麻的回调，第一刀要砍的是频率。

两段代码里的 { passive: true } 也是这次排查学到的，值得多讲两句。浏览器在你滚动时本想立刻跟着手指动画面，但只要 scroll（尤其 touchstart/touchmove）上挂了监听，它没法预知你会不会在回调里 preventDefault 把滚动拦下来，只能先等你的回调跑完再动——这就是"滑动不跟手"的一大来源。passive: true 等于提前承诺"我绝不拦截"，浏览器就敢立即滚动，把回调丢到一边异步跑。在那台老安卓机上，加与不加，跟手程度肉眼可见地不同。

代价是承诺要作数：声明了 passive 就真不能再 preventDefault，调了不生效还会收到控制台警告。自己实现下拉刷新、轮播拦截纵向滚动这类真要拦截默认行为的场景，别加。

问题三：读完干了什么

砍完频率，老安卓机上还是有察觉得到的顿挫。Performance 再录一段，这次看到的不是回调太密，而是每次回调里跟着一块紫色的 Layout——强制同步布局，才是真正的病根。

一行 JS 都不用，浏览器自己在合成阶段处理，性能天花板。Chrome 和 Firefox 都已经支持，Safari 要带 -webkit- 前缀，IE 全家不支持。我的策略是渐进增强：支持的浏览器白赚顺滑吸顶，不支持的降级回 JS 方案——而 JS 方案里判断"到没到顶"，读一次 getBoundingClientRect().top 就够，记得进 rAF、读写分离，教训都在前面了。

sticky 有个著名的失效坑先记下：任何一层祖先元素设了 overflow: hidden 或 overflow: auto，sticky 就悄悄失效，不报错、不警告，就是不吸。我在后台项目里遇到过一次，查了半小时，最后发现是外层某个容器为了清浮动加了 overflow: hidden。以后 sticky 不生效，第一件事就是顺着 DOM 树往上翻 overflow。

番外四：移动端的两个小机关

老安卓机排查过程里还捡到两个移动端专属知识点，顺手记下。

一是自定义滚动容器在 iOS 上默认没有惯性——手指一松立刻停，硬得像刮竹片。加一句就能找回原生手感：

但它有代价：iOS 惯性滚动期间 scroll 事件不连续触发，要等滚动完全停下才补一发。所以进度条这类需要实时跟踪的逻辑，在这种容器里会"跳帧"，设计交互时得心里有数。

二是移动端拿 window.innerHeight 算"到底"时，浏览器地址栏的展开收起会让视口高度动态变化，快滑几下数值就对不上。我的土办法是监听 resize 重新取值，再配合前面说的容差判断，别追求像素级精确——移动端视口这潭水，追求绝对精确就是跟自己过不去。

结案陈词

三处修改全部上线后，我又借了那台老安卓机，划了一分钟。顺滑。同事在旁边看着说："这不挺好的吗，上次是不是没用心。"我没反驳，因为他说得对——上次我确实没意识到，滚动回调里的每一行代码都会被一秒执行上百次。

结案后沉淀下来的就是那三个问题，后来成了我写滚动逻辑前的固定自检：

读哪里——滚动主体是 window 还是容器？读 scrollY 还是 scrollTop？目标浏览器需要兜底吗？取不到值先查 compatMode。

读多频——挂进滚动事件了吗？按钮显隐这类低频需求上节流，跟手动画用 rAF，监听记得 passive: true。

读完干了什么——回调里有没有读写混杂？先读后写、批量分离；能用 transform 就别动 width。

API 本身一点都不难，难的是现场每次都不一样。而验证现场的方式只有一个：打开 Performance，录一段，看主线程上有没有密密麻麻的紫色。它比任何感觉都诚实。
