原生 JavaScript 获取页面滚动距离

2018-08-09
前端基础JavaScript

前端开发里，经常需要知道页面滚动到了哪里。

例如：

  • 顶部导航吸顶
  • 返回顶部按钮显示隐藏
  • 阅读进度条
  • 滚动到某个区域后触发动画

这些功能都离不开滚动距离。

滚动距离本身只是一个数字，真正需要注意的是：你读的是页面滚动，还是某个容器滚动；你读取的频率有多高；读取之后会不会触发布局抖动。

我刚做前端那会儿对这块没什么概念，做返回顶部按钮时随手在 scroll 里写了一堆 DOM 操作，自己机器上跑得挺顺，结果同事拿一台老安卓机一划，整个页面卡成 PPT。后来排查才发现，滚动里的每一行代码都可能被一秒钟调用上百次，平时不在意的小开销会被这个频率成倍放大。从那之后我写任何跟滚动相关的逻辑，都会先问自己三个问题：读哪里、读多频、读完干了什么。这篇就按这三个问题来展开。

另外提一句容易被忽略的点：pageYOffset 和 scrollY 这两个值是只读的。想用脚本改变滚动位置不能给它们赋值，得用 window.scrollTo(x, y) 或者 window.scrollBy(dx, dy)。我见过有人写 window.scrollY = 0 想回到顶部，结果毫无反应还查了半天，就是把读和写搞混了。

这里再补一个真实踩过的坑。window.pageXOffset !== undefined 这个判断看起来很稳，但如果你在某些被改造过的环境里（比如把 window 上某些属性 polyfill 过的旧项目），它可能给你一个意料之外的值。所以兜底函数我后来都会写单元测试，至少在目标浏览器里实测一遍，而不是凭感觉觉得它能跑。

为什么有 documentElement 和 body

历史上，不同浏览器和不同渲染模式下，滚动距离可能存在不同位置。

标准模式下通常读取 document.documentElement。

怪异模式下可能需要读取 document.body。

所以兼容函数里会先判断 document.compatMode。

document.compatMode 为 CSS1Compat 时，表示页面运行在标准模式；如果是 BackCompat，通常就是怪异模式。只要页面使用标准的 HTML5 doctype，大多数时候都会走标准模式。

这个细节也说明了基础 HTML 结构会影响 JavaScript 读取行为。我接手过一个上古项目，doctype 写得不规范，整个站跑在怪异模式下，document.documentElement.scrollTop 永远是 0，所有滚动距离都得从 document.body 上读。当时一头雾水，明明代码逻辑没问题就是取不到值，最后是在控制台敲了一句 document.compatMode 看到 BackCompat 才反应过来。把 doctype 补成标准的 <!DOCTYPE html> 之后一切正常。

所以遇到滚动距离取出来是 0、或者跟肉眼看到的不一致，先别怀疑自己的 JS，敲一下 document.compatMode 看看页面处在哪种模式，往往能省下大半天的排查时间。

很多业务页面并不是整个窗口滚动，而是某个内容区域滚动。比如后台系统常见的右侧主内容区。

  • scrollTop：已经向上滚过的距离

为什么 passive 对滚动这么重要，值得多说两句。浏览器在你滚动的时候，本来想立刻跟着手指动画面，但如果你给 scroll（尤其是 touchstart/touchmove）挂了监听，浏览器没法预知你会不会在里面调 preventDefault 把滚动拦下来，于是它只能先等你的回调跑完再决定要不要滚，这就是著名的“滑动延迟”。加上 { passive: true } 等于提前向浏览器承诺“我绝对不拦截”，浏览器就可以放心地立即滚动，把你的回调丢到一边异步执行。移动端这个差别尤其明显，我在一个内容站上加了 passive 之后，低端机的滚动跟手程度肉眼可见地变好了。

唯一要注意的是：一旦声明了 passive，你就真的不能在回调里调 preventDefault 了，调了不光不生效，控制台还会甩一条警告。所以那些确实需要阻止默认滚动的场景（比如自己实现下拉刷新、横向轮播拦截纵向滚动），就别加 passive。

滚动场景里，最忌讳的是一边频繁读取布局，一边频繁写样式。读写混在一起，很容易造成卡顿。

这背后的原理叫强制同步布局（forced synchronous layout，也有人叫 layout thrashing）。浏览器为了省事，会把样式改动攒着批量处理，但你一旦在 JS 里读取像 offsetTop、offsetHeight、getBoundingClientRect() 这类依赖布局的属性，浏览器为了给你一个准确值，不得不立刻把之前攒的改动全部计算一遍。如果你在循环或滚动回调里反复“读一下、改一下、再读一下”，就等于逼着浏览器一帧之内反复重排，性能瞬间崩掉。

小结

获取滚动距离本身不复杂，但要注意浏览器兼容和滚动事件性能。

现代项目里可以优先使用 window.pageYOffset 或 window.scrollY，如果需要兼容旧环境，再封装统一函数。

真正落地时先判断滚动主体：页面用 window，容器用元素自身。再根据交互频率选择 requestAnimationFrame、节流或被动监听。
