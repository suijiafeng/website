Cookie、localStorage 和 sessionStorage：别什么都往本地存

2019-11-18
前端基础JavaScript

浏览器存储是项目里经常用、面试也经常问的基础。

登录 token、主题设置、搜索历史、临时表单、引导状态，好像都能存本地。但能存不代表应该存。Cookie、localStorage、sessionStorage 的生命周期、容量、安全边界都不一样。

Cookie

Cookie 会随请求发送到服务端。

服务端可以设置：

常见属性：

  • HttpOnly：JavaScript 不能通过 document.cookie 读取
  • Secure：只在 HTTPS 下发送
  • SameSite：限制跨站请求携带
  • Expires/Max-Age：过期时间
  • Domain/Path：限定哪些域名、路径会带上这个 Cookie

HttpOnly 这条我特别想强调。登录 token 放 Cookie 且加 HttpOnly，就算页面被 XSS 注入了脚本，攻击者也读不到 token——document.cookie 拿不到它。这是把 token 放 Cookie 而不是 localStorage 的核心理由之一。反过来，很多人把 token 存 localStorage 图取用方便，一旦中招 XSS，token 直接被脚本捞走发到攻击者服务器，连补救机会都没有。

SameSite 是防 CSRF 的关键，2019 年它的存在感越来越强（Chrome 后来还把默认值改成了 Lax）。几个值的实际区别：

我现在登录态默认上 HttpOnly; Secure; SameSite=Lax，需要嵌 iframe 或跨站场景才退到 None。

想取某一项得自己 split 解析，没有现成的按 key 取的 API。而且加 HttpOnly 的那条（比如登录 token）根本不会出现在这个字符串里——这正是 HttpOnly 的意义。

Cookie 适合登录态、服务端需要读取的小数据。不适合存大对象——它有两个硬伤：单个域名的 Cookie 总量通常限制在 4KB 左右，而且每次请求都会自动带上。我见过有人往 Cookie 里塞了一大坨用户配置，结果每个请求头都背着几 K 的 Cookie，连请求图片、CSS 都带，纯属浪费带宽。能不放 Cookie 的数据就别放。

localStorage

localStorage 持久保存，除非手动清除。

有几个用之前最好知道的特性：

  • 只能存字符串。 存对象得自己 JSON.stringify，读出来 JSON.parse。直接 setItem('user', obj) 会被转成字符串 "[object Object]"，新手常踩。控制台跑一遍就现原形：

    顺带一提，存进去的东西在 Chrome DevTools 的 Application 面板 → Local Storage 里能直接看到键值，调试时比反复 getItem 方便。

  • 容量大约 5MB（各浏览器略有差异），比 Cookie 的 4KB 宽裕得多，但也不是无限。塞太多大字符串照样会满，满了 setItem 会抛 QuotaExceededError。

  • 同步阻塞主线程。 读写都是同步 API，存几 MB 的大字符串时 JSON.stringify + 写入会卡一下。高频写入要节流。

  • 按域名隔离。 http:// 和 https://、不同端口算不同源，存的东西互相看不到。本地开发切协议时数据“丢了”，多半是这个原因。

那个 try/catch 不是摆设。Safari 的无痕模式下，localStorage.setItem 会直接抛异常，我就被线上报错炸过——一堆 iOS 用户开了无痕浏览，页面一进来就白屏，最后定位到就是某处裸写 localStorage 没接住异常。

适合存：

  • 主题
  • 语言
  • 非敏感偏好
  • 简单草稿

不适合存：

  • 密码
  • 敏感个人信息
  • 大量列表数据
  • 重要权限数据

一旦发生 XSS，localStorage 里的内容可以被脚本读取。不要因为方便就把敏感 token 随便存进去。

sessionStorage

sessionStorage 在当前标签页会话内有效，关闭标签页后清除。

适合存临时流程状态，比如分步表单当前步骤、某个页面临时筛选。

它不会在不同标签页之间共享，这点和 localStorage 完全相反，是选型的关键依据。我用它的真实场景：一个支付流程分好几步，用 sessionStorage 存当前进度和填过的数据，用户中途刷新页面不丢、能接着填；但他要是另开一个标签页发起一笔新支付，那是独立的会话，两边数据不串——这正是我想要的隔离。要是用 localStorage，两个标签页就会互相覆盖，乱套。

还有个容易混的点：“关闭标签页清除”里的“关闭”指的是这个标签页的生命周期结束。刷新（F5）不算关闭，数据还在；通过链接在同一标签页内跳转也还在；但关掉标签再重开就没了。另外，从一个页面用 target="_blank" 打开的新标签，在某些浏览器里会复制一份 sessionStorage 过去，之后两者各自独立——这个行为我也是查文档才确认的，别想当然。

三者区别

简单对比：

如果服务端需要识别登录态，Cookie 更自然。

如果只是前端偏好设置，localStorage 更合适。

如果只是当前标签页临时状态，sessionStorage 更合适。

存储要考虑版本

本地存储结构可能变化。

读取时检查：

不要假设本地数据永远合法。用户可能手动改，旧版本也可能留下脏数据。

Cookie、localStorage、sessionStorage 都能存数据，但用途不同。

面试问它们，是因为它们关系到登录、安全和状态管理。项目里要记住：敏感信息少存本地，本地数据要做容错，服务端需要的登录态优先考虑 Cookie 和安全属性。
