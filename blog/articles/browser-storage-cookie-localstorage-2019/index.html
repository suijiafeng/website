Cookie、localStorage、sessionStorage：登录态该放哪，边界差在哪

2019-11-18
前端基础JavaScript

登录态问题最烦的地方，是表面症状常常像同一个 bug，真正的根因却散在不同存储里。"登录一会儿就掉"、"明明显示登录了，一操作就过期"、"iPad 上直接白屏" 这三种反馈同时出现时，第一反应很容易是后端会话不稳；这次往下查，问题却几乎都在浏览器这一侧。

更麻烦的是，这三种症状还真不是一个源头。有人踩的是会话级 Cookie，有人踩的是 localStorage 的使用边界，还有人踩中了移动端存储环境的不稳定行为。顺着工单一条条拆下去，我才把 Cookie、localStorage、sessionStorage 这三兄弟的生命周期、容量和安全边界重新捋清楚。

登录态到底存在哪

先交代背景。我们中后台的登录态是 token 放 localStorage、axios 请求拦截器统一往 header 里塞的那一套。但客服同时还要用一个更老的订单查询系统，那套系统走的是 Cookie 登录态。两套系统、两种存储，症状混在一起报上来，第一步就是把它们分开。

浏览器能存东西的地方不止一个，登录 token、主题设置、搜索历史、临时表单、引导状态，好像都能存本地。但能存不代表应该存——三兄弟的生命周期、容量、安全边界都不一样，选错了地方，症状就会像这次一样诡异。

没设过期时间的 Cookie

先查"每天早上必须重新登录"的那位客服。她用的主要是那套老系统，我借她工位打开 DevTools 的 Application 面板一看，登录后的 Cookie 里那条 token，Expires 一栏写着 Session。

问题就在这。Cookie 不设 Expires 或 Max-Age，就是会话级 Cookie，浏览器全部关掉就没了。她每天下班关浏览器，第二天自然要重新登。这不算 bug，是老系统当年就这么设计的，但没人跟客服说过。我提了个单给维护那套系统的同事，把登录态改成带 Max-Age 的持久 Cookie，按需求给了七天。

服务端可以设置：

常见属性：

  • HttpOnly：JavaScript 不能通过 document.cookie 读取
  • Secure：只在 HTTPS 下发送
  • SameSite：限制跨站请求携带
  • Expires/Max-Age：过期时间，不设就是会话级
  • Domain/Path：限定哪些域名、路径会带上这个 Cookie

HttpOnly 这条我特别想强调。登录 token 放 Cookie 且加 HttpOnly，就算页面被 XSS 注入了脚本，攻击者也读不到 token——document.cookie 拿不到它。这是把 token 放 Cookie 而不是 localStorage 的核心理由之一。反过来说，我们新系统把 token 存 localStorage 图取用方便，一旦中招 XSS，token 是可以被脚本直接捞走的。这是当初封装请求层时权衡过的决定，但要清楚这是权衡，不是绝对安全。

SameSite 是防 CSRF 的关键，今年它的存在感明显越来越强，Chrome 那边已经在吹风要把默认值收紧到 Lax。几个值的实际区别：

我现在给登录态的默认配方是 HttpOnly; Secure; SameSite=Lax，需要嵌 iframe 或跨站的场景才退到 None。

排查过程中还翻出一个 Domain 的陈年坑：老系统曾经把 Cookie 的 Domain 写成了 order.example.com，后来加了个 report.example.com 的子系统想共享登录态，死活拿不到——Cookie 只发给设它的那个域。想让子域共享，Domain 要设成 .example.com。这类问题在 Application 面板里对着 Domain 一栏看一眼就明白，比瞪代码快得多。

顺带说 document.cookie 的一个坑：它返回的不是对象，而是把当前域下所有非 HttpOnly 的 Cookie 用 ; 拼成的一整个字符串。比如设了两条：

想取某一项得自己 split 解析，没有现成的按 key 取的 API。而且加了 HttpOnly 的那条（比如登录 token）根本不会出现在这个字符串里——这正是 HttpOnly 的意义。

Cookie 适合登录态、服务端需要读取的小数据，不适合存大对象。它有两个硬伤：单个域名的 Cookie 总量通常限制在 4KB 左右，而且每次请求都会自动带上。我在老系统里就见过有人往 Cookie 里塞了一大坨用户配置，结果每个请求头都背着几 K 的 Cookie，连请求图片、CSS 都带着，纯属浪费带宽。能不放 Cookie 的数据就别放。

iPad 白屏与 localStorage 的脾气

第二个症状——iPad 上白屏——查起来最快，因为我们前端错误监控里躺着一串来自 iOS Safari 的报错。那位同事习惯用无痕模式浏览，而 Safari 的无痕模式下，localStorage.setItem 会直接抛异常。我们有一处埋点代码裸写 localStorage 没接住异常，页面一进来就崩在那儿，白屏。

修法很简单：所有 localStorage 读写都收进一个带 try/catch 的工具。但先把 localStorage 的几个特性摆清楚，这次排查每一条都用上了：

  • 只能存字符串。 存对象得自己 JSON.stringify，读出来 JSON.parse。直接 setItem('user', obj) 会被转成字符串 "[object Object]"，组里上个月刚有人踩过。控制台跑一遍就现原形：

    顺带一提，存进去的东西在 Chrome DevTools 的 Application 面板 → Local Storage 里能直接看到键值，这次排查我基本住在这个面板里，比反复 getItem 方便。

  • 容量大约 5MB（各浏览器略有差异），比 Cookie 的 4KB 宽裕得多，但也不是无限。塞太多大字符串照样会满，满了 setItem 会抛 QuotaExceededError。

  • 同步阻塞主线程。 读写都是同步 API，存几 MB 的大字符串时 JSON.stringify 加写入会卡一下，高频写入要节流。

  • 按域名隔离。 http:// 和 https://、不同端口算不同源，存的东西互相看不到。本地开发切协议时数据"丢了"，多半是这个原因——我们测试环境上 HTTPS 那周，好几个人以为自己的偏好设置被清了。

localStorage 适合存主题、语言、非敏感偏好、简单草稿；不适合存密码、敏感个人信息、大量列表数据、重要权限数据。一旦发生 XSS，localStorage 里的内容可以被脚本读取，不要因为方便就把敏感信息随便存进去。

顺带讲清楚的 sessionStorage

这次排查里 sessionStorage 其实没有问题，但排查时它出过场——我们下单审核有个分步表单，进度存在 sessionStorage 里，客服一度怀疑是它把登录态吃了。趁机把它也讲清楚。

sessionStorage 在当前标签页会话内有效，关闭标签页后清除：

适合存临时流程状态，比如分步表单当前步骤、某个页面的临时筛选。

它不会在不同标签页之间共享，这点和 localStorage 完全相反，是选型的关键依据。我们那个审核流程分好几步，用 sessionStorage 存当前进度和填过的数据，用户中途刷新页面不丢、能接着填；但另开一个标签页处理另一单，那是独立的会话，两边数据不串——这正是想要的隔离。要是用 localStorage，两个标签页就会互相覆盖，乱套。

还有个容易混的点："关闭标签页清除"里的"关闭"指的是这个标签页的生命周期结束。刷新（F5）不算关闭，数据还在；通过链接在同一标签页内跳转也还在；但关掉标签再重开就没了。另外，从一个页面用 target="_blank" 打开的新标签，在某些浏览器里会复制一份 sessionStorage 过去，之后两者各自独立——这个行为我是查了文档才确认的，别想当然。

对照表

三种存储的特性都过了一遍，整理成一张表，以后选型扫一眼就够：

如果服务端需要识别登录态，Cookie 更自然；如果只是前端偏好设置，localStorage 更合适；如果只是当前标签页的临时状态，sessionStorage 更合适。

一句话决策：服务端要读 → Cookie；前端长期留 → localStorage；当前页用完就扔 → sessionStorage。

多标签页的"假登录"

还剩一个症状没查清楚：明明显示登着，一点就弹"登录已过期"。

我去客服工位蹲了一上午才看明白她们的用法：习惯性开五六个标签页，各干各的活。其中一个标签退出登录，token 从 localStorage 里被清掉了——localStorage 是同源标签页共享的，清是全清。但其他标签页的页面还停在退出前的样子，内存里的用户信息、界面上的头像昵称都还在，看起来"登着"。下一个请求发出去，header 里没 token，后端返回 401，前端弹"登录已过期"。用户视角就是：我什么都没干，它突然把我踢了。

上线之后我特地又去客服那边坐了会儿：一个标签退出，其他标签齐刷刷跳到登录页。她们说这下"讲道理了"。

**不要假设本地数据永远合法。**用户可能手动改，旧版本也可能留下脏数据，隐私模式可能根本不让你写。

三个症状，三个根因：会话级 Cookie、无痕模式抛异常、多标签不同步。回头看，每一个都不是什么高深的 bug，全是"没搞清楚这个数据到底存在哪、活多久、谁能看见"。浏览器存储三兄弟长得像，脾气完全不同——登录、安全、状态管理全押在它们身上，把边界摸清楚，比多背十遍对比表有用。
