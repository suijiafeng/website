前端测试实践：Vitest 和 Cypress 分别该测什么

2022-06-09
前端基础构建与模块化

前端测试生态变化很明显。Vite 普及之后，Vitest 开始成为很多 Vite 项目的自然选择；Cypress 也不再只是端到端测试工具，组件测试能力逐渐被更多团队关注。

但测试工具变多以后，另一个问题也变明显：到底该测什么？

很多团队一提测试就想到“覆盖率”，然后试图给所有组件补测试，最后写了一堆脆弱用例。我的经验是，前端测试先不要追求覆盖所有代码，而是优先覆盖最容易出错、最难手工验证、改动风险最高的逻辑。

先分清测试类型

前端测试大致可以分三类：

  • 单元测试：测试纯函数、hooks、工具逻辑
  • 组件测试：测试组件在特定输入下的渲染和交互
  • 端到端测试：模拟用户完整流程

不同测试解决的问题不一样。

单元测试快、稳定、便宜，适合大量覆盖业务规则。端到端测试最接近真实用户，但慢、维护成本高，不适合覆盖所有分支。

所以不要用 Cypress 去测一个金额格式化函数，也不要只靠 Vitest 去证明登录流程完整可用。

请求层一定值得测

很多线上问题来自接口错误处理不一致。请求层如果有统一错误转换，就应该补测试。

这是很典型的低成本高收益测试。一旦错误结构变了，测试会立刻提醒你。

组件测试不要测实现细节

组件测试最容易写错的地方，是过度关注实现。

不要测试“组件内部有没有调用某个函数三次”，而应该测试用户能看到什么、能做什么。

Cypress 适合完整流程

Cypress 适合验证关键业务路径，例如：

  • 登录
  • 下单
  • 发布文章
  • 修改资料
  • 权限拦截
  • 表单提交失败提示

我一般会拆成两类：

  • UI 状态测试：可以 mock 接口
  • 关键集成流程：尽量连测试环境真实接口

这样既保证测试稳定，也保留发现集成问题的能力。

从哪里开始补测试

老项目补测试最怕一上来目标太大。更现实的顺序是：

第一，补工具函数和业务规则测试。它们最容易写，也最稳定。

第二，补请求层错误处理测试。确保 API 错误统一转换。

第三，补核心组件测试。比如表单、弹窗、权限按钮。

第四，补 3 到 5 条关键 E2E 流程。不要追求多，先保证主流程不被破坏。

第五，把测试放进 CI。只有本地偶尔跑的测试，长期价值会打折。

小结

前端测试不是为了把覆盖率堆满，而是为了保护关键行为。Vitest 适合纯逻辑、请求层、hooks 和轻量组件；Cypress 适合关键用户流程和集成验证。

现在给前端项目补测试的成本已经比过去低很多。但真正有价值的测试，仍然来自清楚的分工：单元测试保业务规则，组件测试保交互行为，端到端测试保关键流程。测试写得少但准，比写得多但脆弱更有意义。
