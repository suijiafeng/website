Babel 7 升级记录：语法转换越来越像基础设施

2018-09-03
JavaScript构建与模块化

Babel 在项目里存在感有点奇怪。平时大家不太关心它，只有构建报错、浏览器兼容出问题、语法不能用时才会想起来。

Babel 7 正式发布后，我把一个老项目的转换链路升了一遍。这个过程让我重新意识到：语法转换已经是前端项目的基础设施。它不只是让我们写新语法，还决定了代码会以什么形式跑在用户浏览器里。

我这次升级的契机很被动：项目里要用 async/await 配合一个新依赖，结果那依赖发布的是 ES2017 的代码，老的 babel-preset-es2015 根本不认，构建直接报 Unexpected token。顺藤摸瓜才发现整套 Babel 配置还停在 6 的时代，preset 一堆、polyfill 全量打进、targets 一个没配。借这次机会整个推倒重来，过程里踩的坑比想象中多，记下来。

包名变了，心智也要变

配置也变成：

以前很多项目配置里还留着 babel-preset-es2015、babel-preset-stage-2。迁移时不要机械替换，最好重新看一次项目到底需要支持哪些浏览器。

包名带 scope 这件事不只是改个名字这么简单，几个连带变化会卡住人：

  • 老的 babel-preset-es2015 / es2016 / es2017 这种按年份切的 preset 全部废弃，统一收进 @babel/preset-env，由它根据 targets 决定转哪些。这其实是好事，再也不用自己拼年份了。
  • .babelrc 配置文件依然能用，但 Babel 7 引入了 babel.config.js。两者作用域不同：.babelrc 是就近、按目录生效的，对 node_modules 里的文件默认不生效；babel.config.js 是项目级、全局生效的。要转译某个 node_modules 里的依赖时，配置必须放在 babel.config.js 里才管得到，放 .babelrc 是没用的——这个我卡了一会儿才反应过来。
  • 有个 babel-upgrade 工具可以自动帮你把老配置和依赖升级到 7 的写法，跑一遍能省不少手动改 package.json 的功夫，但跑完一定要逐项核对，它不会帮你想清楚 targets。

还有一个容易忽略的：升级完成后，要把老的 babel-core、babel-preset-* 这些不带 scope 的包从 package.json 里删干净。新老包共存时，有时候 loader 会去读到老的 preset，报一些莫名其妙的错，删掉重装 node_modules 才好。

polyfill 不是语法转换

Babel 能把箭头函数转成普通函数，但不能凭空让老浏览器拥有 Promise、Array.from、Object.assign。

这就涉及 polyfill。

更精细的方式是使用 useBuiltIns：

它会根据代码使用情况注入 polyfill。配置时要确认 core-js 版本，否则构建容易警告或报错。

useBuiltIns 三个取值我都试过，区别说清楚很重要：

  • false（默认）：什么都不注入，你得自己在入口手动 import polyfill。
  • 'entry'：你在入口写一行 import '@babel/polyfill'（或后来的 import 'core-js'），Babel 会把这一行按 targets 展开成实际需要的那些 polyfill。等于全量的子集，比手写全量小，但仍然是按目标环境而不是按你用没用来裁。
  • 'usage'：最省的一种，连入口那行 import 都不用写，Babel 扫每个文件，你用到了 Promise 就注入 Promise 的 polyfill，没用到就不注入。

我最后选了 'usage'，包体积最小，但它有个坑：它只能识别你源码里用到的 API，识别不了第三方依赖里用到的。如果某个 node_modules 依赖内部用了 Array.prototype.includes 而你的代码没用，usage 模式不会给它注入，老浏览器照样炸。所以那些会用到新 API 的依赖，要么自己带 polyfill，要么纳入转译范围让 Babel 也扫它。

@babel/polyfill 在 7 里其实已经被标记为不推荐（它是 core-js + regenerator 的打包），更现代的写法是直接配 corejs 版本，让 preset-env 去引 core-js 的模块。core-js 2 和 3 的差别也不小，2 不支持一些实例方法的按需引入，3 才比较完整，但 2018 年那会儿 3 还没正式稳定，我项目里用的还是 corejs: 2，配置时版本号写错就会一堆 warning。

另外，普通 polyfill 会污染全局原型（给 Array.prototype 挂方法），写应用没问题，但写库别这么干——会把使用者的全局环境也改了。库应该用 @babel/plugin-transform-runtime 配 @babel/runtime-corejs2，它用沙箱化的辅助函数，不动全局：

transform-runtime 还有个附带好处：它会把 Babel 每个文件都要插的那些 helper 函数（_classCallCheck、_extends 之类）抽成公共引用，而不是每个文件各塞一份，对多文件项目能省下可观的体积。这个我是看打包产物时发现一堆重复 helper 才补上的。

Babel 7 干脆把 stage preset 整个移除了，逼着大家显式声明用了哪个提案插件，我觉得这个决定是对的。提案是分阶段的（stage 0 到 4），stage 越低越不稳定，语义甚至可能整个改掉。最典型的反面教材就是装饰器 @decorator 和早期的私有字段——这些语法在不同 Babel 版本之间行为变过，凡是早早把 stage-0 全量开下、大量用上这些语法的项目，后来升级都升得很痛苦。

我现在的原则是：能用已进标准的就不用提案；非用提案不可，就单独装那个 plugin-proposal-* 插件、并在 README 里记一笔为什么用、用在哪。对象展开 {...obj} 这种当时虽然还是提案、但已经 stage 3 很稳了，用是没问题的，但也明确写出来，而不是靠一个 stage-2 把一大片不知道什么的语法都囫囵开着。

和 webpack 的配合

webpack 项目里通常通过 babel-loader 接入：

exclude: /node_modules/ 很常见，但有些 npm 包发布的是较新的语法，老浏览器会报错。遇到这种情况，要么让依赖提供兼容版本，要么把特定包纳入转译。

不要一看到线上白屏就只怪业务代码，依赖包语法也可能是原因。

这个坑我栽得很惨。有个项目上线后在某些安卓机白屏，本机怎么都复现不出来，最后是用真机远程调试连上去，看到 console 里一行 SyntaxError，定位到是某个新引入的 UI 组件库直接发布了 ES2015+ 的代码，里面的箭头函数、const 在那台老 webview 上跑不了。我们的 exclude: /node_modules/ 把它整个跳过了，没转译，于是原样送进了老浏览器。

解决办法就是把这个包从 exclude 里捞出来单独转。但要注意，babel-loader 转 node_modules 会拖慢构建、也可能踩到那个包用了非标准语法（更需要插件）的情况，所以是有选择地放行，而不是把整个 node_modules 都转——那样构建慢到没法用。判断哪些包要转，可以先看它 package.json 的 main 指向的文件是不是已经是 ES5；现在很多包会同时提供 module（ESM、可能含新语法）和 main（CommonJS、通常已降级），webpack 默认优先用 module，所以即便 main 是 ES5 也可能吃到新语法。

还有个 2018 年特别常见的报错值得提一句：regeneratorRuntime is not defined。这是用了 async/await 或 generator、但没引入 regenerator 运行时导致的——语法被 Babel 转成了状态机，但状态机依赖一个全局的 regeneratorRuntime，没 polyfill 它就报这个。配好 useBuiltIns + corejs，或者用 transform-runtime，就不会再见到它。我第一次见这报错完全摸不着头脑，因为它不在我写的代码里，是转换产物里的。

顺手把缓存和 sourcemap 配好

升级时我顺带把 babel-loader 的缓存打开了。Babel 转译是构建里比较吃 CPU 的一环，开了缓存第二次构建能快不少：

还有就是确认 sourcemap 没断。Babel 转换后行号全变了，线上报错栈如果对不回源码，排查基本抓瞎。webpack 的 devtool 和 Babel 默认都会生成 sourcemap，但如果中间又过了 UglifyJS 之类的压缩，要确认每一环都把 sourcemap 串下去，否则最后定位到的就是一行压缩过的天书。我升级后特意上线前在测试环境故意抛个错，看 Sentry 上的栈能不能落回源码，确认这条链路没断才放心。

升完做一次回归

Babel 配置改动影响的是全量产物，不是某个页面，所以不能只点几个页面看看就完事。我那次升完，专门挑了几台覆盖目标范围的真机/低版本浏览器，把核心流程整个走一遍——尤其是用到 async/await、Promise、数组新方法、Object.assign 这些的页面，因为这些正是 polyfill 和转换最容易出岔子的地方。本机 Chrome 全绿不代表用户端没问题，这个教训前面已经付过学费了。

这次升级给我的提醒是：Babel 配置越基础，越不能随手从别的项目复制。

包名改成 @babel/* 只是最表面的部分，后面还得重新确认浏览器目标、语法转换和 polyfill 的边界、提案插件是不是还该继续用，以及 webpack、loader、压缩和 sourcemap 这条链路有没有一起跟上。开发时写的是新语法，用户机器上跑的却是转换后的结果，这中间每一层都值得多看一眼。
