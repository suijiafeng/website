Babel 7 正式版发布一周，我把老项目升了：@babel/ 包名、preset-env 与 polyfill 踩坑记

2018-09-03
JavaScript构建与模块化

Babel 升级真正麻烦的地方，从来不是把包名从旧前缀替换成 @babel/，而是会顺着这次升级，把项目里那些长期没人碰过的转换链路问题一起翻出来。preset 是怎么堆上去的，polyfill 为什么全量打进入口，浏览器目标为什么一直没配，很多老项目都靠"能跑就先别动"拖到了今天。

我手上的这个项目就是典型。为了接一个用了 ES2017 语法的新依赖，构建直接报 Unexpected token。打开 .babelrc 一看，还是 Babel 6 时代的 babel-preset-es2015，preset 堆了一排、polyfill 在入口全量打进、targets 一个没配，完全是那种从别的项目复制过来、两年没人动过的配置。

正式版发布把这笔账提前摆上了桌面：与其继续在 Babel 6 上缝缝补补，不如趁这个机会把整条转换链路重新梳一遍。 上周末两天加这周一，我把整条转换链路升到了 Babel 7。过程里踩的坑比官方那篇轻描淡写的 migration 文章多得多，后面按实际遇到的顺序展开。

第一步：包名全换成 @babel/，旧包要删干净

Babel 7 最显眼的变化是包名开始使用 npm 的 scope：

配置跟着变成：

以前项目配置里那些 babel-preset-es2015、babel-preset-stage-2，迁移时不要机械地一对一替换，最好借机重新想一遍项目到底要支持哪些浏览器——这是我这次升级最大的心得，后面细说。

包名带 scope 不只是改个名字，几个连带变化会卡住人：

  • 老的 babel-preset-es2015 / es2016 / es2017 这种按年份切的 preset 全部废弃，统一收进 @babel/preset-env，由它根据 targets 决定转哪些。我觉得这是好事，再也不用自己拼年份了。
  • 官方出了个 babel-upgrade 工具，可以自动把老配置和 package.json 里的依赖升级成 7 的写法。我跑了一遍，确实省了不少手动改依赖的功夫，但跑完必须逐项核对——它只负责换名字，不会帮你想清楚 targets 该是什么。
  • 升级完成后，要把老的 babel-core、babel-preset-* 这些不带 scope 的包从 package.json 里删干净。我第一次构建时报了一个莫名其妙的 preset 解析错误，查了半天，是 loader 读到了残留的老 preset。新老包共存是隐患，删掉、重装 node_modules，世界清净。

还有一个我周六晚上栽进去的坑：babel-loader 的版本要跟上。babel-loader 8 才配 @babel/core，如果 package.json 里还锁着 babel-loader 7，它会去找老的 babel-core，报 Cannot find module 'babel-core'；反过来装了 babel-loader 8 却没装 @babel/core，报的又是 Cannot find module '@babel/core'。这两个报错在这一周的 GitHub issue 区里刷了屏，我看了一眼提问时间，全是 8 月 28 号之后的——看来大家都是发布当周就冲了。

.babelrc 还是 babel.config.js，这次真的有区别

Babel 7 引入了一个新的项目级配置文件 babel.config.js，老的 .babelrc 依然能用，但两者作用域不同，这个区别我卡了一个多小时才反应过来：

  • .babelrc 是就近、按目录生效的，对 node_modules 里的文件默认不生效；
  • babel.config.js 是项目级、全局生效的。

也就是说，想转译 node_modules 里某个依赖时，配置必须放在 babel.config.js 里才管得到它，放 .babelrc 是没用的。我一开始把转译配置写在 .babelrc，webpack 那边明明把那个依赖从 exclude 里放行了，转出来的代码还是原样——因为 Babel 压根没对它应用任何 preset。换成 babel.config.js，立刻就通了。

顺带一提，Babel 7 对 Node 版本也有要求，0.10、0.12、4、5 这些古董 Node 全部不再支持。我们构建机上还有台跑 Node 4 的老 Jenkins 节点，升级前先把它换掉了，否则装依赖那一步就过不去。

preset-env 的核心是 targets，而 targets 该交给 browserslist

@babel/preset-env 的价值在于按目标环境转换语法。没有明确 targets，转换结果就很难解释——你不知道它为什么转了这个不转那个。

第一次配 targets 时，强烈建议把 preset-env 的 debug 打开：

polyfill 不是语法转换，这条边界必须分清

Babel 能把箭头函数转成普通函数，但不能凭空让老浏览器拥有 Promise、Array.from、Object.assign——语法转换和运行时能力是两回事，这就轮到 polyfill 出场。

全量打进，不管用没用到。能解决问题，但包体积也实打实地背上了。Babel 7 里更精细的方式是 useBuiltIns：

三个取值这两天我挨个试了，区别值得说清楚：

  • false（默认）：什么都不注入，你得自己在入口手动 import polyfill。
  • 'entry'：你在入口写一行 import '@babel/polyfill'，Babel 会把这一行按 targets 展开成实际需要的那些 polyfill。等于全量的子集，比手写全量小，但仍然是按目标环境、而不是按你用没用来裁。
  • 'usage'：最省的一种，连入口那行 import 都不用写，Babel 扫每个文件，你用到了 Promise 就注入 Promise 的 polyfill，没用到就不注入。

我最后选了 'usage'，打出来的包确实小了一圈。但它有个坑要心里有数：它只能识别你源码里用到的 API，识别不了第三方依赖里用到的。如果某个 node_modules 依赖内部用了 Array.prototype.includes 而你的代码没用，usage 模式不会给它注入，老浏览器照样炸。所以那些会用到新 API 的依赖，要么自己带 polyfill，要么纳入转译范围让 Babel 也扫它。

@babel/polyfill 这个包在 7 里其实已经被标记为不推荐了（它就是 core-js 加 regenerator 的打包），更干净的写法是直接配 corejs 版本，让 preset-env 去引 core-js 的模块。core-js 2 和 3 差别也不小，2 不支持一些实例方法的按需引入，3 才比较完整——但 3 现在还没正式稳定，我不敢上，项目里用的是 corejs: 2。版本号写错的话构建会给一堆 warning，别忽略它们。

另外有条原则值得单独一段：普通 polyfill 会污染全局原型（给 Array.prototype 挂方法），写应用没问题，但写库别这么干——你会把使用者的全局环境也改了。库应该用 @babel/plugin-transform-runtime 配 @babel/runtime-corejs2，它用沙箱化的辅助函数，不动全局：

transform-runtime 还有个附带好处：它会把 Babel 每个文件都要插的那些 helper 函数（_classCallCheck、_extends 之类）抽成公共引用，而不是每个文件各塞一份。我是周日翻打包产物时看到一堆重复的 _classCallCheck 才补上它的，对多文件项目能省下可观的体积。

这类配置的问题是边界太宽——你根本说不清项目到底依赖了哪些提案语法。提案是分阶段的（stage 0 到 4），stage 越低越不稳定，语义甚至可能整个改掉。最典型的反面教材就是装饰器 @decorator 和早期的私有字段，这些语法在不同 Babel 版本之间行为变过，凡是早早把 stage-0 全量开下、大量用上的项目，升级的时候都很痛苦——我这次升级最提心吊胆的就是排查项目里有没有偷偷用过 stage-2 里的东西。

我觉得这个决定是对的。我现在的原则是：能用已进标准的就不用提案；非用提案不可，就单独装那个 plugin-proposal-* 插件，并在 README 里记一笔为什么用、用在哪。 对象展开 {...obj} 这种虽然还是提案、但已经 stage 3 很稳了，用没问题，但也要明确写出来，而不是靠一个 stage-2 把一大片不知道什么的语法囫囵开着。

顺带说一个我这次没用上、但很想找机会试的新东西：Babel 7 自带了 @babel/preset-typescript，可以直接把 TypeScript 语法剥掉当 JS 转（不做类型检查）。我们项目没上 TS，但这意味着以后想渐进式引入 TS，不用整条构建链换成 tsc，Babel 一条链就能吃下——这可能是 7 里最被低估的特性。

测试环境和构建环境，配置不该是同一份

升级过程中还顺手解决了一个老早就存在、但一直懒得动的问题：Jest 跑测试用的转换配置，和 webpack 构建用的转换配置，其实需求完全不同。测试跑在 Node 里，不需要转 ES 模块之外的太多东西，targets 甚至可以直接写 node: 'current'，让 preset-env 只做 Node 当前版本不支持的那一小撮转换，跑起来更快；构建给浏览器用的，targets 要按 browserslist 来，两者混用一份配置，要么测试跑得慢，要么构建目标被测试的宽松要求带偏。

Babel 7 的 babel.config.js 支持一个 env 字段，按 BABEL_ENV 或 NODE_ENV 分环境覆盖配置，正好解决这个问题：

Jest 默认会把 BABEL_ENV/NODE_ENV 设成 test，env.test 里的配置会和顶层配置合并覆盖，不用再单独维护一份 .babelrc.test.js。除了 env 按运行环境分支，Babel 7 还新增了 overrides 字段，可以按文件路径给不同目录用不同规则，比如老代码目录暂时不接入某个新插件，同一份配置文件里精确到 glob 匹配的一段就行，不用整条链路为了迁就一个目录的历史包袱而妥协。

webpack 项目里通常通过 babel-loader 接入：

exclude: /node_modules/ 几乎是每个项目的标配，但有些 npm 包发布的是较新的语法，被 exclude 跳过就意味着原样送进老浏览器。

这个坑我上半年栽得很惨，正好借这篇一起记了。当时有个项目上线后在某些安卓机白屏，本机怎么都复现不出来，最后是用真机远程调试连上去，看到 console 里一行 SyntaxError，定位到是某个新引入的 UI 组件库直接发布了 ES2015+ 的代码，里面的箭头函数、const 在那台老 webview 上跑不了。我们的 exclude: /node_modules/ 把它整个跳过了，没转译。

但注意，是有选择地放行，不是把整个 node_modules 都转——那样构建慢到没法用，也可能踩到某个包用了非标准语法、还得补插件的情况。判断哪些包要转，可以先看它 package.json 的 main 指向的文件是不是已经是 ES5；很多包现在会同时提供 module（ESM、可能含新语法）和 main（CommonJS、通常已降级），而 webpack 默认优先用 module，所以即便 main 是 ES5，你吃到的也可能是新语法。不要一看到线上白屏就只怪业务代码，依赖包的语法也可能是原因。

还有个今年特别常见的报错值得单独记一句：regeneratorRuntime is not defined。这是用了 async/await 或 generator、但没引入 regenerator 运行时导致的——语法被 Babel 转成了状态机，但状态机依赖一个全局的 regeneratorRuntime，没 polyfill 它就报这个。配好 useBuiltIns 加 corejs，或者用 transform-runtime，就不会再见到它。我第一次见这报错时完全摸不着头脑，因为它不在我写的任何一行代码里，是转换产物里的。

顺手把缓存和 sourcemap 配好

升级时我顺带把 babel-loader 的缓存打开了。Babel 转译是构建里最吃 CPU 的一环，开了缓存第二次构建能快不少：

还有就是确认 sourcemap 没断。Babel 转换后行号全变了，线上报错栈如果对不回源码，排查基本抓瞎。webpack 的 devtool 和 Babel 默认都会生成 sourcemap，但如果中间又过了 UglifyJS 之类的压缩，要确认每一环都把 sourcemap 串下去，否则最后定位到的就是一行压缩过的天书。这次上线前我特意在测试环境故意抛了个错，看 Sentry 上的栈能不能落回源码，确认这条链路没断才放心。

升完做一次全量回归

Babel 配置改动影响的是全量产物，不是某个页面，所以不能只点几个页面看看就完事。周一合并之前，我专门挑了几台覆盖目标范围的真机和低版本浏览器，把核心流程整个走了一遍——尤其是用到 async/await、Promise、数组新方法、Object.assign 的页面，因为这些正是 polyfill 和转换最容易出岔子的地方。本机 Chrome 全绿不代表用户端没问题，这个学费上半年那次白屏已经交过了。

一周之后，还剩几件没收尾的事

从 8 月 27 日看到发布公告，到今天升级合并上线，正好一周。包名改成 @babel/* 只是最表面的部分，真正的工作量在后面：重新确认浏览器目标、划清语法转换和 polyfill 的边界、把 stage preset 换成显式的提案插件，以及确认 webpack、loader、压缩和 sourcemap 这条链路有没有一起跟上。Babel 的配置越基础，越不能随手从别的项目复制——开发时写的是新语法，用户机器上跑的却是转换后的结果，中间每一层都得对上。

还剩两件事记在下周的任务里。一是 @babel/preset-typescript 想找机会拉个内部小工具试一遍剥类型的效果，为以后渐进式引入 TS 探路；二是 core-js 3 等它转正后要重新评估一遍，看实例方法按需引入是不是真的比 2 更省包体积。正式版才发布一周，社区的 issue 区还在陆续冒新坑，babel-upgrade 工具本身估计也得再出几个小版本才稳，这周先把主力项目的转换链路理顺，其余的边角问题留着后面再逐个啃。
