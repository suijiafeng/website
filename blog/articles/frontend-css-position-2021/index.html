CSS 定位为什么总让人绕晕：relative、absolute、fixed 到底怎么配合

2021-02-03
前端基础

CSS 里的定位一直是前端基础里很典型的一类知识点。

概念看起来不多，属性也不复杂，但一碰到真实布局，就很容易出现两个问题：要么定位不到自己想要的地方，要么定位是对了，结果把周围布局全弄乱了。

很多时候不是属性难，而是没有把“元素原来在哪”“它现在相对谁定位”“它是否还占文档流空间”这三件事分开理解。

我自己刚工作那两年，调定位基本靠手感：top 不对就改 top，改不动就加 !important，再不行就套一层 div。结果就是页面在我电脑上像那么回事，一换分辨率、一加内容就崩。后来真正花时间把包含块、文档流、层叠上下文这几个概念啃明白之后，调定位才从“撞运气”变成“能预判结果”。下面把我踩过的坑串起来讲。

先理解什么叫文档流

页面元素在默认情况下，会按照 HTML 结构顺序依次排布。

块级元素从上到下，行内元素从左到右，这种自然排布方式通常就叫文档流。

如果一个元素还留在文档流里，后面的元素就会参考它原来的位置排布；如果元素脱离了文档流，后面的元素会当它原本不存在。

定位相关问题之所以容易乱，就是因为不同 position 值对文档流的影响不一样。

我后来记这几个值的方式很简单，就看两个问题：它还占不占原来的空间？它的偏移参照谁？static 占空间、不参照；relative 占空间、参照自己原位；absolute 不占空间、参照定位祖先；fixed 不占空间、参照视口；sticky 占空间、在阈值前后切换。把这张表记牢，大部分“为什么跑偏了”的疑惑当场就能消掉一半。

relative 常被低估，但它非常实用

`position: relative`` 的一个特点是：元素仍然保留在文档流中，只是可以相对自己原本的位置偏移。

这里有个容易忽略的细节：relative 的 top/left 偏移只是“视觉上挪”，它不会影响周围元素的排布。也就是说我让 .badge 向下偏 4px，它可能压到下面的内容，但下面的内容不会让位——它眼里这个元素还在原地。这点和外边距 margin 完全不同，margin 是会挤动别人的。我早期就吃过亏，想用 relative 微调间距，结果偏移大了直接和相邻元素重叠，找半天才反应过来该用 margin 才对。

还有个坑是：给 relative 元素同时写 top 和 bottom，只有 top 生效（在默认书写方向下 top 优先，bottom 被忽略），left 和 right 同理。所以别指望靠 top + bottom 把它“拉伸”，relative 做不到这件事，那是 absolute 才有的能力。

很多人以为 relative 只能拿来“自己挪一下”，其实它还有另一个非常重要的作用：为绝对定位子元素提供参照系。这个用法我用得比“自己挪一下”多得多——很多时候我给父元素加 position: relative 但根本不写任何偏移，纯粹是为了给里面的 absolute 子元素“圈一个范围”。

absolute 真正关键的是“相对谁”

`position: absolute`` 的特点是元素脱离文档流，并且相对于某个定位祖先元素进行定位。

如果它的祖先里有最近的非 static 定位元素，就相对那个祖先；如果没有，通常会相对页面初始包含块（差不多就是视口大小那一块）。

注意这里说的是“非 static”，不一定非得是 relative。absolute、fixed、sticky 同样能当参照系。只是 relative 因为不脱流、不影响布局、副作用最小，所以最常被拿来当“锚点”。我在 review 别人代码时，看到一个 position: relative 后面跟着空的声明块，基本就能猜到里面藏着个 absolute 子元素。

还有几个容易让人懵的点。一是百分比：absolute 元素的 width: 50% 是相对“包含块的宽度”算的，不是相对父元素的 content box，padding 也算在内，这点经常和正常流元素的百分比行为对不上。二是 top/right/bottom/left 四个值如果都给了，元素会被“撑开”到这个范围，这时候不写 width 也能确定宽度——我做全屏遮罩层就爱用 inset: 0（等价于四个方向都是 0）：

如果父元素不设参照系，绝对定位元素可能会直接跑到页面别的地方，表现看起来就像“失控了”。我遇到过最典型的一次：列表项里的角标全跑到了页面右上角叠成一团，排查半天发现是有人把卡片的 position: relative 误删了，角标失去锚点直接挂到了 body 上。所以写 absolute 时，我现在的习惯是先确认它的“锚”到底是谁，别等渲染出来再猜。

另外提醒一个老 bug：祖先元素只要设了 transform、filter、perspective 或者 will-change 这类属性，它会意外变成 fixed 子元素的包含块。也就是说一个本该相对视口的 fixed 元素，会突然只相对这个祖先定位。我做吸顶弹层时被这个坑过一次，明明写了 fixed 却跟着某个容器滚走了，最后发现是外层一个动画用了 transform。

fixed 和 absolute 很像，但参照物不一样

`position: fixed`` 也会脱离文档流，但它通常相对浏览器视口定位。

这类元素不会跟着普通页面滚动一起移动，所以很适合：

  • 回到顶部按钮
  • 悬浮客服入口
  • 固定顶部导航

三是前面说的 transform 祖先问题，在移动端轮播、过渡动画里特别常见，写 fixed 之前最好先确认外层没有这些属性。

sticky 像是相对定位和固定定位的结合

现在页面里也越来越常见 position: sticky。

它的行为可以粗略理解成：在没滚到阈值前像普通元素，滚到指定位置后像固定元素。

最典型的场景是：

  • 吸顶目录
  • 表格表头
  • 侧栏筛选区

它并不是任何时候都像 fixed 那样贴在视口上，而是在容器和滚动条件满足时才生效。

sticky 是我用着最爽、也最容易“写了没反应”的一个。新手最常见的三个失效原因，我基本都犯过：

第一，没写阈值。sticky 必须配一个 top/bottom/left/right，光写 position: sticky 它跟普通元素没区别，吸不住。

第二，父容器有 overflow: hidden/auto/scroll。sticky 的生效范围被限制在它的滚动祖先里，一旦某个祖先开了 overflow，吸顶就只在那个容器内部生效，或者干脆失效。我排查这个问题排查到怀疑人生，最后发现是为了去掉一个横向滚动条，外层随手加了个 overflow: hidden。

第三，父容器高度不够。sticky 只能在父元素的高度范围内“吸”，父元素一滚出去它就跟着走了。所以它适合吸表头、吸目录这种“父容器很长”的场景，拿来做全局导航就不合适，那种还是老老实实用 fixed。

为什么绝对定位容易把布局搞乱

绝对定位最大的问题，是它脱离文档流。

这意味着你虽然把它放到了想要的位置，但其他元素不会给它留空间。如果一个区域本来应该依赖内容高度撑开，结果你把核心内容都改成了 absolute，父元素高度可能直接塌掉。

很多新手页面里的重叠、遮挡、留白异常，都是因为过度依赖绝对定位。

不是说 absolute 不能用，而是它更适合：

  • 小范围角标
  • 装饰元素
  • 叠层操作区
  • 需要压在内容上的局部模块

如果一个区域本质上还是正常流式布局，用 Flex、Grid 或普通文档流往往更稳。

定位和层级经常一起出现

只要说到定位，通常也会碰到 z-index。

但 z-index 不是所有元素都能直接生效。最基本的一条：z-index 只对“定位元素”（position 不是 static 的元素）起作用——一个 position: static 的普通块你写 z-index: 9999 完全是无效声明，浏览器直接忽略。给它补一个 position: relative（哪怕不写任何偏移），z-index 才会开始参与层叠。除此之外它还和定位上下文有关。很多时候你给元素加了很大的 z-index 仍然没压住别的层，不是数值不够大，而是层叠上下文不在一层。

所以遇到弹窗、下拉框、浮层被遮住的问题时，不能只盯着 z-index，还要往上看定位祖先和层叠上下文。

说几个真容易制造层叠上下文的属性，因为它们太常见反而最坑：opacity 小于 1、transform、filter、position: fixed/sticky、will-change，还有 flex/grid 容器的子项设了 z-index。这些一旦出现，里面元素的 z-index 就被“关”在这个上下文里了，外面的元素根本比不过去。

我印象很深的一次：一个下拉菜单怎么调 z-index 都被旁边的卡片盖住，加到 9999 也没用。最后发现那张卡片为了做 hover 动画用了 opacity 过渡，hover 时 opacity 变成 0.99，硬生生造出一个新的层叠上下文，把下拉菜单整个压下去了。解决办法不是堆数字，而是把下拉菜单用 portal 渲染到 body 下面，或者干脆挪出那个上下文。从那以后我调层级问题，第一反应是去看“它俩到底在不在同一个层叠上下文”，而不是先改数字。

实战里更重要的是少滥用定位

CSS 定位好用，但它不是通用解法。

早几年我也经常看到一种写法：页面结构一复杂，就开始靠一堆 absolute + top/left 硬摆位置。短期看效果能出来，后期维护会越来越痛苦，响应式一变、内容一变、字体一变，所有坐标都要跟着重调。

所以我现在的判断顺序更简单：

  • 能用正常文档流解决，先不用定位
  • 需要局部覆盖或角标，再考虑 absolute
  • 需要吸顶吸底，再看 sticky 或 fixed
  • 需要子元素相对父元素摆放，先给父元素建立参照系

把定位当作补充工具，而不是默认布局手段，页面会稳定很多。
