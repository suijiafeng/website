微前端边界设计：先想清楚为什么要拆

2024-06-07
前端基础构建与模块化

微前端很容易被当成架构升级。

项目大了、构建慢了、团队多了，就有人提“要不要上微前端”。但微前端不是性能优化工具，也不是万能拆分方案。它解决的核心问题是组织协作和独立交付，同时带来运行时复杂度。

我参与过一个后台系统拆微前端。初衷很合理：多个业务团队共用一个壳子，各自独立发布。但第一版边界没设计好，主应用和子应用互相调用内部方法，样式互相覆盖，登录态刷新逻辑写了三份。拆是拆了，耦合还在，只是从代码仓库耦合变成运行时耦合。

所以微前端第一步不是选 qiankun、Module Federation 还是 iframe，而是先问：我们到底要拆什么边界？

适合微前端的场景

微前端适合这些情况：

  • 多个团队负责不同业务域
  • 各业务需要独立发布
  • 技术栈存在历史差异，短期无法统一
  • 主应用需要统一登录、导航、权限和布局
  • 子应用之间业务耦合不强

不适合这些情况：

  • 只是页面多
  • 只是构建慢
  • 只是想追新架构
  • 所有页面仍然由同一个小团队维护
  • 子应用之间共享大量状态和组件

如果只是构建慢，先看构建缓存、依赖预构建、代码分包、CI 资源。不要把构建问题直接升级成运行时架构问题。

业务域边界比路由边界重要

很多微前端拆分会按路由切：

这只是表象。真正应该按业务域和团队责任切。

一个子应用应该能回答：

  • 它负责哪个业务域
  • 它的数据模型谁维护
  • 它能否独立发布
  • 它和其他子应用通过什么契约通信
  • 它失败时主应用如何降级

如果两个页面频繁共享内部状态、互相调用方法、一起上线，那它们大概率不该拆成两个子应用。

微前端不是越碎越好。拆得太细，用户一次操作可能跨多个子应用，加载、通信、错误边界都会变复杂。

主应用要少管业务

主应用应该负责壳能力：

  • 登录态
  • 全局布局
  • 导航菜单
  • 权限入口
  • 子应用注册和加载
  • 全局错误兜底
  • 公共监控和埋点

主应用不应该理解太多子应用业务细节。

说明边界开始坏了。主应用越懂业务，子应用越难独立。

子应用之间通信也要克制。优先通过 URL、事件、后端数据和明确协议通信，不要直接互相 import 内部模块。

事件也要有命名规范和版本意识。否则全局事件会变成另一个隐形全局 store。

样式隔离要提前设计

微前端最常见的事故之一是样式污染。

子应用 A 写：

子应用 B 的按钮也变红了。

解决方式有几种：

  • CSS Modules
  • CSS-in-JS
  • BEM 命名约束
  • Shadow DOM
  • 框架提供的样式隔离

没有一种是完美的。Shadow DOM 隔离强，但主题、弹窗、字体、组件库适配会复杂；CSS Modules 对局部样式友好，但全局 reset 和第三方组件仍要处理。

我的建议是：子应用禁止写宽泛全局选择器，公共 reset 由主应用提供，业务样式必须有命名空间或模块化。

这不是最优雅，但比裸 .button 安全。

依赖共享不是越多越好

微前端里常见优化是共享 React、组件库、工具库，减少重复加载。

共享依赖确实能降低体积，但也会带来版本耦合。主应用升级 React，子应用是否都兼容？组件库升级后，旧子应用是否会样式错乱？

不要为了省几十 KB，把所有依赖都强行共享。共享越多，独立发布越弱。

错误隔离和降级要做

子应用加载失败时，主应用不能白屏。

至少要有：

  • 加载中状态
  • 加载失败兜底
  • 重试按钮
  • 错误上报
  • 子应用运行时错误边界

错误上报要带上子应用名称、版本、路由、用户环境。否则线上只看到“主应用报错”，根本不知道是谁的问题。

我的判断清单

上微前端前，我会先确认：

  • 是否真的需要多团队独立发布
  • 业务域边界是否清楚
  • 主应用是否只负责壳能力
  • 子应用之间是否有明确通信协议
  • 样式隔离方案是否确定
  • 共享依赖策略是否有版本治理
  • 子应用加载失败是否能降级
  • 监控是否能区分应用和版本

微前端的价值是让组织边界和技术边界对齐。边界清楚，它能提升协作效率；边界不清楚，它只会把单体应用的问题搬到运行时。
