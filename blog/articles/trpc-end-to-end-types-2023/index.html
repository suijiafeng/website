tRPC 端到端类型安全评估：两周试用的收获与约束

2023-04-21
前端基础TypeScript构建与模块化

tRPC 这半年在社区的热度高得有点晃眼，Twitter 上的演示视频都是同一个套路：后端改一个字段名，前端的调用处立刻标红。看多了难免怀疑是不是又一轮营销，但它戳的那个痛点我们是真实在流血的，所以三月底我拿一个正要重写的内部小工具当试验田，认认真真试了两周。这篇把试用的结论整理出来——先说结果：它兑现了演示里的承诺，但兑现的前提条件比演示里显眼得多。

先把痛点说具体。我们主系统是前后端分离的经典形态：Java 后端出 REST 接口，前端在 types/api/ 下手写一堆 interface。这套类型的维护完全靠自觉和 code review，于是漂移是常态——上个月一个线上问题就是典型：后端把订单列表的 deliveryTime 从字符串改成了带时区的对象，改动通知发在群里，前端类型没人同步，TypeScript 全程绿灯，问题在预发环境的页面上才炸出来。手写的接口类型本质上是一份"我相信后端长这样"的注释，它和真实接口之间没有任何机制保证一致。类型体操写得再好，事实来源是错的，一切白搭。

tRPC 的思路：不生成代码，直接共享类型

解决类型漂移，此前我知道的路线是 OpenAPI：后端出 schema，前端用 openapi-typescript 这类工具生成类型，靠 CI 保证生成物新鲜。tRPC 走的是另一条路，激进得多：前后端在同一个 TypeScript 工程里，后端 router 的类型被前端直接 import，中间没有生成步骤，没有 schema 文件，没有任何可能过期的中间产物。

注意 import 的只是类型。tRPC 的口号里"零运行时依赖共享"说的就是这个：前端拿到的是 type AppRouter = typeof appRouter，一个纯类型，后端的实现代码一行都不会进前端的 bundle。类型漂移问题在这个架构下不是"被解决"了，而是不存在了——类型和实现是同一个东西，谈不上漂移。

去年 11 月 tRPC 发了 v10，API 相比 v9 大改，客户端从字符串路径换成了链式代理，类型提示和跳转定义都顺了。现在入手直接从 v10 开始，不用理会旧版资料。

zod 站在哪个位置

上面 input 里的 zod 值得单独说。它在这个架构里同时干两件事：运行时校验请求入参（恶意的或者写错的请求在进业务逻辑之前就被拦下，报错信息还带着 schema 的路径），以及给客户端提供入参的静态类型（通过 z.infer 机制）。

这正好接上我之前形成的判断：类型系统管不着运行时进来的数据，边界上必须有运行时校验。tRPC 的设计把这条实践直接固化进了框架——你没法定义一个不声明 input 的带参 procedure，校验不是可选的最佳实践，是必经之路。相比之下我们主系统的 REST 接口，入参校验写不写、写多细，全看后端同事当天的状态。

输出方向默认是不校验的（只推断类型），需要的话可以加 .output(schema)，会在运行时校验返回值并以 schema 为准收窄类型。内部工具我没加，公网接口值得加——它能防止你不小心把数据库行里的敏感字段整个吐出去。

useQuery 的缓存 key 由路径和入参自动生成，不用再手工维护 queryKey 数组这个 TanStack Query 里最容易写错的东西；mutation 成功后的缓存失效也是类型安全的——utils.activity.list.invalidate() 写错路径会在编译期报错。用过手工管理 queryKey 的人会体会到这里省掉的是哪种心智负担。tRPC 最聪明的设计决定可能就是不做数据层，把缓存、重试、乐观更新这些难题原样交给已经成熟的 TanStack Query。

测试也有个顺手的入口：appRouter.createCaller(ctx) 可以在服务端直接调用 procedure，不走 HTTP。给 procedure 写单测时构造一个假 context 就能测业务逻辑，比起 REST 项目里"起一个测试服务器再发请求"轻了一个量级。

前提条件：这些约束缺一个都玩不转

两周里我一直在留意的其实不是功能，是约束。tRPC 的甜头全部建立在几个前提上，少一个，体验就塌一角。

最硬的一条：前后端必须共享 TypeScript 类型，实际上意味着同仓（或至少同一个 monorepo workspace）且后端就是 TypeScript。我们主系统后端是 Java，这一条直接判了死刑——不存在"把 tRPC 接到 Java 后端"的说法，类型推断的链路要求 typeof appRouter 这个表达式在前端的编译上下文里可解析。试验田能跑起来，正因为它是我自己一个人写的 Node 全栈小项目，pnpm workspace 里 server 和 web 两个包，types 引用直接跨包。

第二条软一些但真实：跨团队协作模型变了。REST + 文档的模式下，接口文档是前后端的谈判桌；tRPC 模式下没有文档这个环节，接口"文档"就是代码本身。两三个人的小项目里这是效率，前后端分属两个团队、要走排期和联调流程的场景里，缺一个中立的契约层反而会让协作没有抓手。还有客户端多样性的问题：哪天这个工具要出小程序端、要给 Python 脚本调用，tRPC 的调用协议虽然是普通 HTTP+JSON，但没有 schema 可以生成其它语言的客户端，那些消费方等于回到裸调接口的状态。

第三条是工程尺度：类型推断的成本随 router 规模增长。试验田十几个 procedure，编辑器响应毫无压力；社区里几百个 procedure 的项目已经有人在抱怨 tsserver 变慢。这个尺度我没验证到，记下来存疑。

和 OpenAPI 代码生成路线的取舍

评估不能只看 tRPC 自己，得放到备选方案旁边比。OpenAPI 路线（后端出 schema，前端生成类型或客户端）解决的是同一个漂移问题，思路是"让中间产物机器化，靠流程保鲜"；tRPC 是"消灭中间产物"。

摆在一起看，取舍其实清晰。OpenAPI 的优势：后端语言无关（Java 后端一样出 schema）、契约文件本身是跨团队协作的抓手、多端客户端可以各自生成、生态工具（mock、网关、测试）都认这个格式。代价：链路长——schema 要写准（或从注解生成）、生成步骤要接进 CI、生成物的新鲜度要有人管，每一环都可能松掉；而且 schema 的表达力有天花板，联合类型、泛型这类 TS 里自然的东西，OpenAPI 表达起来很勉强，生成出来的类型经常比手写的糙。

tRPC 的优势和劣势正好是镜像的：链路为零、类型保真度满格（毕竟就是原始类型），但换来的是技术栈和组织形态的强绑定。这不是"谁更先进"的问题，是适用域几乎不重叠的两个方案——所以社区里"tRPC 会不会取代 REST"的争论我觉得问错了问题。

还有一层容易被忽略的代价是 HTTP 语义的弱化。tRPC 的 query 走 GET、mutation 走 POST，路径全长在 /api/trpc/activity.list 这种形式上，入参在 batch 模式下编码进查询串。这意味着 REST 世界里那些"白捡"的基础设施红利要重新审视：网关按 URL 前缀做的限流和权限规则粒度变粗了，CDN 或反向代理对 GET 的缓存策略要针对 tRPC 的 URL 形态重新配，抓包排查时也没有"看一眼 URL 就知道在干什么"的直观。内部小工具无所谓，但要是一个系统重度依赖网关层的能力，这笔账得提前算。

顺带一提，tRPC 生态里有 trpc-openapi 这种给 procedure 补 REST 出口的插件，看起来像是两头兼得，但我试了半天感觉是给特殊场景兜底用的，把它当主路线等于同时背上两套方案的心智负担，不推荐。

团队结论

两周试用收尾，我在周会上给的结论是三句话。第一，试验田这个工具用 tRPC 重写完成，体验好于预期，保持现状，后续内部的全栈 TS 小工具（一两个人维护、Node 后端、同仓）默认可以选 tRPC，配 TanStack Query 的官方集成（@trpc/react-query，我们试验田的 web 端就是这么接的，缓存失效和 mutation 的配合都是现成的）。第二，主系统不动：Java 后端加跨团队协作，tRPC 的前提一条都不满足，接口契约的改进方向仍然是把 OpenAPI 的生成链路建起来——这件事值得单独立项去做，不在这篇的范围里。第三，半年后回头看一次试验田的维护体验，特别是升级成本和多人协作之后的感受，再决定要不要扩大适用范围。

资深前端在会上问了个好问题：如果它的适用面这么窄，热度为什么这么高？我的理解是，社区里全栈 TS 小团队的数量比我们这种分工明确的中后台团队想象的多得多——Next.js 一把梭的独立开发者、初创公司的三人小队，对他们来说 tRPC 的前提条件不是约束，是默认现状。工具没有好坏，只有前提。我们的前提决定了它在这里是一把好用的小刀，而不是主战武器。

那个上个月炸掉的 deliveryTime 字段，在 tRPC 的世界里根本没有机会活到预发环境。这个事实我记下了——哪怕主系统用不上它，它至少把"类型漂移是可以在架构层面消灭的"这件事演示给了我们看，OpenAPI 链路立项的时候，这就是说服大家的最好论据。
