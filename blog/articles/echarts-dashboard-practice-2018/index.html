ECharts 后台大屏实践：图表好看之前，数据结构要先稳

2018-06-18
前端基础数据可视化与存储

后台系统做数据看板，ECharts 基本绕不开。

我们公司的运营后台、监控大屏、各种统计页，前前后后我用 ECharts 画过几十个图。一开始我也觉得这玩意儿简单：官网 example 那么全，复制一个 option 进来，把 data 换成自己的就行。直到图表越堆越多，页面开始变成一坨——一个 .vue 文件里塞着五六个图的 option，每个 option 里又掺着 data.map、三元判断、单位拼接，接口字段一改，得满文件找哪个 series 引用了它。那会儿我才意识到，ECharts 本身不难，难的是怎么让一屏十几个图还能维护得动。

图表配置很强大，但也很容易写乱。很多项目一开始把 option 直接写在组件里，接口数据回来后到处拼数组。图表多了以后，页面里全是数据转换和配置细节，改一个字段牵一发动全身。

图表要写得稳，第一步不是调颜色，而是整理数据结构。这篇就按我自己踩过的顺序，从 option 组织、接口转换、resize、空状态一路记下来。技术背景是 2018 年：Vue 2 + ECharts 3/4，还没有那么多现成的 Vue 封装库，基本都是自己 echarts.init 手撸。

我的原则是：接口返回的数据进入 option 之前，必须先过一遍 normalize。这一层就是图表的“防火墙”，把后端的脏数据、缺字段、类型不一致全挡在这里，下游的 option 工厂函数永远只面对干净、确定的结构。后来后端字段改名、加字段，我也只需要动 normalize 一个函数，option 和组件都不用碰。

二是 dispose 一定要在 beforeDestroy 里调。这个我栽过——一个页面来回切来切去，内存噌噌往上涨，Chrome 任务管理器里这个 tab 占了几百兆。查了半天是 ECharts 实例没销毁，每次进页面 init 一个新的，老的还挂在 DOM 上下不来。dispose 之后 ECharts 会解绑事件、释放 canvas，内存才回落。组件销毁时既要 removeEventListener 又要 dispose，缺一个都漏。

如果图表在 tab、弹窗、折叠菜单里，初始化时容器宽度可能是 0，画出来要么是一条线要么干脆不显示。要等容器真正显示后再 resize。我的做法是在切到对应 tab、或者弹窗 opened 之后，主动调一次 this.$nextTick(() => this.chart.resize())——nextTick 是为了等 DOM 把容器的宽高真正撑开，太早调 resize 量到的还是 0。el-dialog 这种带过渡动画的更要命，得等动画结束的回调里再 resize，否则量到的是动画中途的尺寸。

空状态不能只显示空图

接口没数据时，ECharts 可能显示一块空白。用户不知道是加载中、没数据，还是接口失败。

组件应该区分：

  • loading
  • empty
  • error
  • success

错误也要统一结构，不要每个图表自己猜接口失败原因。

这四个状态我后来直接封进了一个 ChartCard 组件，里面放一个具名插槽给图表，外面套 loading / empty / error 的壳。这样每个业务图表都不用再各写一遍这套判断，传个 status 进来就行：

封装的另一个好处是 empty 和 error 的视觉能全站统一——以前各人各写，有的显示“暂无数据”，有的显示“无数据”，有的干脆一片空白，看着像没做完。统一成一个组件后，连“点击重试”按钮都能在一个地方加好。

还有个容易忽略的点：图表从有数据切到无数据时，得记得把旧图清掉。ECharts 的 setOption 默认是合并模式，你给个空 series 它可能还留着上一次的线。这种情况我会在切 empty 之前调一次 this.chart.clear()，或者 setOption(option, true) 用 notMerge 强制覆盖，免得用户看到一张“幽灵图”。

数据量大时要谨慎

几百个点没问题，几万个点就要小心。大数据量图表会影响渲染和交互。

可以考虑：

  • 后端聚合
  • 前端抽样
  • 分页或缩放
  • 只展示关键区间

不要为了“数据完整”把所有点都塞进图表。看板是帮助理解趋势，不是数据库导出工具。

我真遇到过一个监控页，后端一次返回近三万个时间点的折线，页面一加载就卡死好几秒，鼠标在图上一动 tooltip 跟不上，CPU 直接拉满。当时几个补救手段：

  • 让后端按分钟/小时聚合，原始秒级数据没人会逐点看，聚合完点数掉到几百，肉眼趋势完全一样；
  • 实在要前端处理，ECharts 的 series 上有个 sampling: 'lttb'（最大三角形三点采样），在不明显改变曲线形状的前提下抽稀点数，对大数据折线很管用；
  • 关掉一些昂贵的视觉效果，比如 symbol: 'none'（不画每个点的小圆点）、hoverAnimation: false，渲染压力小很多；
  • 如果是散点这种海量点，换 ECharts 的 large: true 模式或者直接上 canvas 渲染（ECharts 4 默认就是 canvas，比 SVG 扛点数）。

结论还是那句：能在后端聚合就别让前端硬扛，浏览器画几万个 DOM/canvas 点的代价，远比多写几行聚合 SQL 大。

现在再让我做一个看板页，我反而不会先急着调颜色和动画。

更早要定下来的，是接口数据怎么转成图表能吃的结构，空数据和异常接口怎么兜住，窗口变化时谁负责 resize，页面切走时有没有 dispose 干净。ECharts 本身已经把绘图能力做得很足了，项目里真正容易翻车的，往往是这些看起来不显眼的边界。
