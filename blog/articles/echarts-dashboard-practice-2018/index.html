ECharts 大屏实践：图表能不能稳，先看数据结构和信息层次

2018-06-18
前端基础数据可视化与存储

大屏项目最容易把人带偏的地方，是所有人一上来都在讨论”要不要发光””颜色够不够酷””地图炫不炫”，真正决定它能不能长期维护的，却是底下的数据结构、信息层次和渲染代价。

我一开始也没逃掉这个坑。需求给得很虚，只剩一个”要好看”，于是最顺手的做法就是上官网 example 抄 option，折线、柱状、饼图、地图能堆多快就堆多快。短期当然能看到效果，真正的问题却都藏在图表下面：字段脏、结构乱、窗口一缩就崩、点位一多就卡。

一个月做下来，图我确实画了十几个，但真正让我脱层皮的没有一个是”图不好看”，全是图表底下的东西：接口脏数据、resize、内存泄漏、三万个点卡死页面。下面按这些问题实际暴露出来的顺序往下讲。

第一周：图表堆砌，然后 option 开始失控

第一周我干的事就是字面意义的"堆"。老板说要好看，我就把折线、柱状、饼图、仪表盘全码上去，一个 .vue 文件里塞五六个图的 option，每个 option 里又掺着 data.map、三元判断、单位拼接。

第二周初后端改了一个字段名，我在那个一千多行的文件里搜了二十分钟，找哪几个 series 引用了它。那一刻我意识到，ECharts 本身不难，难的是一屏十几个图还能维护得动。图表要写得稳，第一步不是调颜色，而是整理结构。

这两处全是实打实被坑出来的。一是某天接口异常，返回的不是数组而是个错误对象，不加 Array.isArray 判断，.map 直接抛错，整个大屏白屏——参观演示要是赶上这个就完了；二是后端有个接口把数字用字符串传，yAxis 是数值轴时，字符串 "12" 和 "100" 按字符串排，刻度间距乱七八糟，Number() 转一下就好。

我的原则从此定死：接口返回的数据进入 option 之前，必须先过一遍 normalize。这一层是图表的防火墙，把后端的脏数据、缺字段、类型不一致全挡在这里，下游的 option 工厂函数永远只面对干净、确定的结构。后来后端字段改名、加字段，我只动 normalize 一个函数，option 和组件都不用碰。

第三周：resize、销毁，和那几百兆内存

大屏要投到会议室的电视上，分辨率和办公室显示器不一样，窗口一变图就得跟着变。图表容器变化时要调 resize：

两个细节值得展开。一是 window.resize 事件触发很密集，拖动浏览器窗口一秒能触发几十上百次，每次都 chart.resize() 会卡。我给它套了层节流：

二是 dispose 必须在 beforeDestroy 里调。这个我栽得很惨——大屏页和后台其他页面来回切着调试，切了一下午，浏览器越来越肉，Chrome 任务管理器里这个 tab 占了几百兆。查了半天是 ECharts 实例没销毁：每次进页面 init 一个新的，老的还挂在脱离文档的 DOM 上下不来。dispose 之后 ECharts 会解绑事件、释放 canvas，内存才回落。组件销毁时既要 removeEventListener 又要 dispose，缺一个都漏。

还有个衍生坑：图表放在 tab、弹窗、折叠面板里时，初始化那一刻容器宽度可能是 0，画出来要么是一条线要么干脆不显示。要等容器真正显示后再 resize。我的做法是切到对应 tab、或者弹窗 opened 之后，主动调一次 this.$nextTick(() => this.chart.resize())——nextTick 是为了等 DOM 把容器宽高真正撑开，太早调 resize 量到的还是 0。el-dialog 这种带过渡动画的更要命，得在动画结束的回调里再 resize，否则量到的是动画中途的尺寸。

大屏投电视还牵出一个适配问题：设计稿是按 1920×1080 出的，会议室电视是 4K。我最后用的土办法是整屏按设计稿尺寸布局，外层根据实际视口算一个缩放比，transform: scale() 整体缩放——图表内部不用动，文字和图的比例关系全保住。比挨个图算自适应省事得多，唯一注意的是缩放后要补一次 resize 让 canvas 按新尺寸重绘，不然文字会糊。

第四周上：空状态不能只显示空图

联调到中期，运营的数据没铺全，很多接口返回空。这时 ECharts 显示的是一块空白，用户分不清是加载中、没数据，还是接口挂了。老板巡场看到一块空白问我"这坏了？"——那一刻我意识到空状态不是小事，它直接决定别人觉得你这系统"能不能信"。

组件应该老老实实区分四个状态：

  • loading
  • empty
  • error
  • success

错误也要统一结构，别让每个图表自己猜接口失败原因。

这套判断我后来直接封进一个 ChartCard 组件，里面一个具名插槽放图表，外面套 loading / empty / error 的壳，业务图表传个 status 进来就行：

封装的另一个好处是 empty 和 error 的视觉全屏统一——之前各人各写，有的显示"暂无数据"，有的显示"无数据"，有的干脆一片空白，看着像没做完。统一成一个组件后，连"点击重试"按钮都在一个地方加好了。

还有个容易忽略的点：图表从有数据切到无数据时，得把旧图清掉。ECharts 的 setOption 默认是合并模式，你给个空 series 它可能还留着上一次的线。我会在切 empty 之前调一次 this.chart.clear()，或者 setOption(option, true) 用 notMerge 强制覆盖，免得用户看到一张"幽灵图"。

第四周下：三万个点，和"好看"的真正含义

大屏最中间那块，老板点名要放接口监控的实时曲线。后端图省事，一次把近三万个秒级时间点全甩过来。页面一加载卡死好几秒，鼠标在图上一动 tooltip 跟不上，CPU 直接拉满。

几百个点没问题，几万个点就要小心，补救手段我试了一圈：

  • 让后端按分钟/小时聚合。原始秒级数据没人会逐点看，聚合完点数掉到几百，肉眼趋势完全一样；
  • 实在要前端处理，ECharts 折线的 series 上有 sampling: 'average' 这类降采样配置，按窗口取均值抽稀点数，大数据折线很管用；
  • 关掉昂贵的视觉效果：symbol: 'none'（不画每个点的小圆点）、hoverAnimation: false，渲染压力小很多；
  • 海量散点就换 large: true 模式。渲染器方面 ECharts 4 新加了 SVG 可选，但大数据量还是默认的 canvas 扛造。

真要看细节，别硬塞，给用户一个 dataZoom 让他自己框选区间缩放，比一次画全量点体面得多：

结论是：能在后端聚合就别让前端硬扛，浏览器画几万个点的代价，远比多写几行聚合 SQL 大。看板是帮人理解趋势的，不是数据库导出工具。

收尾：图表数量和"好看"之间没有正比关系

上周五客户来参观，大屏投在会议室电视上，没白屏、没卡顿、没幽灵图。老板很满意，说"就是这个感觉"。

中间还有一次返工值得记一笔。第一版堆了十几个图的大屏其实最难看——每个图都在喊话，没人知道该看哪。改版时我砍掉了一半图表：核心的四个指标做成大数字卡片放最上面，趋势只留两条真正有人看的曲线，剩下的细节图收进二级页。图少了，屏幕反而"高级"了。老板要的好看，从来不是图表多，是一眼能看到重点——这属于信息设计，不属于 ECharts 本身的绘图能力。

支撑这一切的，是那些不显眼的底层活：接口数据怎么转成图表能吃的稳定结构，空数据和异常接口怎么兜住，窗口变化时谁负责 resize，页面切走时有没有 dispose 干净。这几周下来我对大屏项目的判断标准变了：调颜色和动画放最后，图表底下这些边界问题才是决定项目能不能撑住的关键。

还有两个后续遗留的问题记在这里，留给下一阶段处理。一是 ECharts 的 dataZoom 虽然能让用户自己缩放海量点位，但会议室大屏是无人值守的展示场景，没人会去拖动条——真要解决展示场景下的海量点问题，还是得回到后端聚合这条路上，dataZoom 更适合有人操作的后台报表页。二是这版主题色是写死注册的，如果以后要支持"日间/夜间"两套大屏配色，registerTheme 得从一次性调用改成根据一个全局开关动态切换，echarts.init 时重新传主题名、并对已有实例调 dispose 再重建，这块目前还没有真实需求，先记下方案。
