防抖和节流：搜索框、滚动监听和按钮点击里的老问题

2019-07-24
JavaScript性能与缓存

防抖和节流几乎是前端面试必问。

它们不是为了背函数实现，而是为了解决高频触发问题。输入框每打一个字都请求接口，滚动事件每一帧都执行计算，按钮连续点击提交多次，这些都会让页面和接口受不了。

我第一次真正意识到这俩东西的价值，是接手一个商品搜索页。产品要「输入即搜索」，原始实现就是 input 事件里直接 search()。测试同事打字快，敲「连衣裙」三个字眨眼发了六七个请求（拼音输入法还会触发更多中间态），接口被打得返回乱序，最后渲染出来的居然是「连」的搜索结果，因为它最后才回来。那次之后我才老老实实把防抖加上，也顺手把后面这些坑都踩了个遍。

补一句概念上的区分，免得混：防抖关心「停下来」，节流关心「频率」。一个是等你别动了我再干活，一个是不管你多疯狂我固定节奏干活。记住这句话，选型基本不会错。

正确做法是先 var debouncedSearch = debounce(search, 300)，再把 debouncedSearch 绑上去，让闭包里的 timer 在多次触发间共享。这个错误特别隐蔽，因为代码不报错、功能也「能用」，只是防抖完全没生效。

再说说防抖的「延迟感」。300ms 是我的默认值，搜索场景体感刚好；如果接口慢、想更省，可以放到 500ms，但超过 500ms 用户会觉得「我打完字了它怎么还不动」。另外有时候产品希望「第一次输入立刻搜一次，后面再防抖」，那就要支持 leading 模式（首次立即执行），这点 lodash 的 debounce 用 { leading: true, trailing: true } 配置就能做到。能不手写就别手写，2019 年项目里我基本直接 import debounce from 'lodash/debounce'，自己写的留着面试讲原理用。

节流是什么

节流的意思是：高频触发时，每隔一段时间最多执行一次。

上面这个时间戳版本有个特点要知道：它是 leading 的，也就是第一次触发立刻执行，但「最后一次」可能丢。比如用户滚到底停住，最后那次落在了节流间隔之内，回调就不执行了——做「滚动到底加载更多」时，这会导致差一点点没触发到底判断。所以另一种实现是用定时器（trailing 版），保证停下后还会补一次：

时间戳版「首次立即、末次可能丢」，定时器版「首次有延迟、末次会补」。讲究的实现（比如 lodash）会把两者合起来，首尾都顾上。实际项目我会根据场景选：滚动加载更看重「到底了一定要触发」，我倾向定时器版或者干脆 lodash；而像实时改变某个数值显示，首次立即响应体感更好，就用时间戳版。

还有个常被问的细节：滚动监听记得给 addEventListener 加 { passive: true }，告诉浏览器你不会 preventDefault，滚动能走合成线程，配合节流体验更顺。

防抖和节流怎么选

防抖适合“只关心最后一次”的场景：

  • 搜索输入
  • 窗口 resize 后重新布局
  • 表单字段异步校验

节流适合“持续触发，但固定频率响应”的场景：

  • 滚动加载
  • 拖拽移动
  • 鼠标移动
  • 页面滚动进度

如果用户连续输入，搜索只要最后结果，选防抖。

如果用户持续滚动，页面需要定期判断是否到底部，选节流。

举几个我实际拿不准、最后这么定的例子。窗口 resize 重画图表（echarts）我用防抖，因为拖拽改窗口大小的过程中间态没意义，只要松手后的最终尺寸重画一次。但「拖拽元素跟随鼠标」必须用节流不能用防抖——防抖会让元素停在原地、等你松手才瞬移过去，体感像卡顿。表单字段失焦校验我两个都不用，直接 blur 触发就行，没必要硬套。

一句经验：分不清的时候问自己「中间过程的那些次到底要不要响应」。要，且想控制频率，节流；不要，只认最后一锤，防抖。

按钮重复点击

按钮提交更适合加 loading 锁，而不是单纯防抖：

防抖只能减少短时间内触发，不能保证接口期间不重复提交。表单提交应该前后端都处理幂等或重复限制。

这是新人最容易用错防抖的地方。我见过有人给「提交」按钮加 300ms 防抖防重复点击——看着像解决了，但只要接口超过 300ms（很常见），用户在等待期间再点一次，防抖间隔早过了，照样发第二个请求。结果就是慢网络下重复下单。防抖管的是「短时间高频触发」，而提交按钮的问题是「一次请求还没回来又点了」，这俩根本不是一回事。

正确的姿势就是上面那段：一个 submitting 标志位，请求期间锁住按钮（UI 上同步置灰、转圈），finally 里再解锁。但前端这层只是体验优化，真正的兜底必须在后端做幂等——前端拦不住手快、拦不住网络重试、更拦不住有人直接调接口。我们的做法是提交时前端生成一个唯一的 requestId 带上，后端用它去重，同一个 id 只认第一次。前后端各守一道，才算稳。

取消防抖

有些场景需要取消未执行任务：

组件销毁时可以取消，避免页面离开后还执行回调。这个坑很真实：用户在搜索页打了字、还没到 300ms 就点返回离开了，组件已经销毁，结果定时器到点还是触发了回调，回调里 this.$set 一个已经不存在的组件，控制台一片报错，严重的还内存泄漏。我的习惯是在 Vue 的 beforeDestroy（或 React componentWillUnmount）里调一下 cancel：

lodash 的 debounce/throttle 自带 .cancel() 和 .flush()（立即执行挂起的那次），所以又是一个我推荐直接用 lodash 的理由——这些边界它都替你想好了。自己手写时记得把 cancel 补上，尤其是单页应用，组件频繁创建销毁，漏掉清理迟早出问题。

我见过有人 removeEventListener('scroll', throttle(this.handleScroll, 200))，又 new 了一个新函数去解绑，自然解不掉，滚动监听就一直挂在 window 上累积，切几次页面后卡得明显。这类「监听器泄漏」在长生命周期的单页应用里特别容易被忽略。

小结

防抖是等停下来再执行，节流是固定频率执行。

面试喜欢问手写实现，项目里更重要的是选对场景。搜索用防抖，滚动用节流，提交用 loading 锁和后端幂等。不要只背函数，先看问题到底是高频输入、持续触发，还是重复提交。
