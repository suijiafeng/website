路由参数我后来是当成状态来设计的：一个中后台列表页的复盘

2024-09-07
React前端基础

我对路由传参的理解，是被一个中后台列表页逼着升级的。

那个页面是订单管理，顶上一排筛选：状态、时间范围、关键词、分页。我一开始图快，把这些全放在组件的 useState 里。功能跑得好好的，直到运营来找我：他想把“某个时间段里所有失败订单”这个筛选结果发给同事，结果发过去的链接打开是空的——因为筛选条件根本没在 URL 里。

紧接着第二个投诉来了：他在第 3 页点了详情，看完按浏览器返回，回到的是第 1 页、筛选也没了。那一刻我才意识到，列表页的筛选条件其实不是“组件内部状态”，它是页面状态，而页面状态的归宿是 URL。

先想清楚每个参数该放哪

返工的时候我没有急着写代码，而是先把参数分了三类，这个分类后来成了我每个列表页的默认动作：

  • 代表资源身份的，放路径。比如 /orders/123 里的 123，它稳定、可分享、搜索引擎也能理解。
  • 代表“同一个页面的不同视图”的，放 query。筛选、排序、分页都属于这类，比如 /orders?status=failed&page=2。
  • 不适合暴露、或者只在当前交互里有意义的，留在组件状态或服务端。比如弹窗里的临时编辑内容、敏感字段、体积很大的对象。

订单列表的那排筛选，显然全属于第二类。把它们搬进 query 之后，分享、刷新、回退三个问题一起消失了——因为 URL 本身变成了可复现的状态快照。

从 URL 读参数，不能假设它是干净的

把参数交给 URL，也意味着我要开始防着它。URL 是用户能直接改的，page=-1、page=abc、甚至同名参数出现两次，都得当成正常输入来处理。

我吃过一个具体的亏：router.query 里的值可能是字符串，也可能是数组。用户手贱访问 /orders?status=failed&status=paid，status 就成了 ['failed','paid']，我那段按字符串处理的代码直接挂了。后来我固定封两个小函数兜底：

还有一点容易忽略：在客户端首次渲染时，参数不一定立刻就绪（静态优化的页面尤其如此）。依赖参数去请求数据时，我宁愿在服务端阶段就把它读出来、校验完、不合法直接 notFound，也不愿意让用户先看到一个半成品页面再在客户端跳来跳去。

push 还是 replace，决定了用户的返回键

参数搬进 URL 之后，我又遇到一个细节：修正非法参数时该用哪个跳转。

用户访问 /orders?page=-1，我要把它纠正成第一页。如果用 push，这个非法 URL 会进历史记录，用户点返回又回到 page=-1，陷进一个尴尬的循环。这种“补默认值、纠正参数、登录后重定向”的场景，应该用 replace：

判断标准我后来记成一句话：这次跳转用户以后会想“返回”到吗？想，就 push；不想，就 replace。

这事还有个更底层的版本。push/replace 本质上是浏览器 History API 的封装，history.pushState 往会话历史栈里压一条，history.replaceState 原地改当前那条。Next.js 的 router 只是在它上面套了数据预取和组件更新。理解这层之后我才想明白一个一直没搞清的现象：为什么连续改筛选条件、再点返回，有时候要点好几下才退出页面。因为我每改一个筛选项都 push 了一次，历史栈里堆了一长串只差一个参数的 URL。

正确做法是把“同一轮筛选交互”里的连续修改用 replace 合并，只有用户明确切换到一个值得返回的视图时才 push。我现在列表页的筛选基本都这么写：

一次因为编码搞出来的线上事故

有个事故我印象很深，因为排查它花了我大半天，根因却小得可笑。

那阵子运营要按中文关键词搜订单备注，比如“退款 申请”。测试环境一切正常，上线后偶尔有人反馈“搜出来的结果不对，像是搜了别的词”。我盯着监控看了很久——前端发出去的请求参数没问题，后端日志里收到的关键词却时好时坏，有时候空格变成了 +，有时候中文变成了乱码。

把链路拆开看才定位到：前端有两处在拼 URL，一处用了 encodeURIComponent，另一处图省事直接字符串拼接，中间还过了一层带缓存的网关。encodeURIComponent 会把空格编码成 %20，而表单提交那套 application/x-www-form-urlencoded 习惯把空格编码成 +。两种编码混在一起，后端用统一的解码逻辑去解，自然有一半解错。更要命的是网关把 ?keyword=退款+申请 和 ?keyword=退款%20申请 当成两个不同的 key 各缓存了一份，于是“时好时坏”。

URLSearchParams 这个内置对象其实早该用——它 set 时按 application/x-www-form-urlencoded 规则编码，但 toString 出来的是 %20 而非 +（这是规范里一个长期被人混淆的细节），整条链路只要都用它，编码就统一了。从那以后我团队里立了条规矩：代码里禁止出现手写的 ?a= + 变量这种拼接，一律走 URLSearchParams 或框架的对象式 API。一个内置类省掉了一类反复出现的 bug。

解析阶段我也补了一课：URL 长度和重复参数

顺着上面那次事故，我把 URL 本身的边界也摸了一遍，免得再被“偶发”坑到。

URL 长度没有统一规范上限，但现实里各处都有隐形天花板：很多 CDN、Nginx 默认 large_client_header_buffers 大概在 8K 上下，IE 时代的 2083 字符传说虽然过时但代理层仍可能截断。我那个把整个订单 JSON 塞进 query 的黑历史，挂掉的直接原因就是被网关按长度截了一刀，后半段参数没了，JSON.parse 报错。所以现在凡是可能变长的参数（多选筛选、批量 ID），我都会评估一下最坏情况的长度，超了就改成 POST 带 body，或者后端建一个临时查询条件再返回一个短 token。

重复参数的语义也值得定清楚。?id=1&id=2 在不同框架里行为不一致：URLSearchParams.get('id') 只返回第一个 '1'，getAll('id') 才给你 ['1','2']；Next.js 的 router.query.id 则直接给数组。多选场景我现在统一用 getAll 显式表达意图：

顺带一提：参数错了，错误结构也要统一

列表页和它背后的接口是一起的。参数校验不过时，接口返回的错误最好也长一个样，比如统一成 { error: { code, message } }。我维护过一个各接口错误格式各异的项目——有的返回字符串，有的 { message }，有的 { errors: [] }——最后前端那个错误提示组件写得惨不忍睹。入口统一校验、出口统一结构，这两件事配套做，列表页才算真的稳。

现在回头看，路由传参对我来说早就不是“怎么把值拿出来”的语法问题了，它是页面信息架构的一部分。参数设计得清楚，刷新、分享、回退、SEO、埋点都会顺；设计得随意，后面通常会在权限、缓存和错误处理上慢慢还债。那个订单列表页教给我的，其实就一句话：先决定每个参数住在哪里，再决定怎么读它。

上一篇用了几年 Next.js 之后，我对它的态度反而更克制了下一篇异步我是被几个线上 bug 教明白的：竞态、白屏和静默失败
