Next.js路由传参全攻略

2024-09-07
React前端基础

Next.js 的路由传参看起来很简单：路径里放一个 id，页面里读出来就行。但真正做项目时，问题往往不在“怎么拿到参数”，而在“这个参数适合放在哪里”“什么时候能拿到”“拿到以后如何校验”“错误时页面应该怎么处理”。

2024 年的 Next.js 项目里，很多团队同时接触两套路由体系：老项目常见 pages Router，新项目更多使用 app Router。两者都能传参，但读取方式、服务端渲染时机、客户端可用 API 都不完全一样。本文按实际开发场景梳理一次。

先区分三类参数

我通常会先把路由参数分成三类：

  • 路径参数：资源身份，例如 /posts/123 里的 123
  • 查询参数：筛选、排序、分页，例如 /posts?page=2&tag=react
  • 状态参数：不适合暴露在 URL 里的临时状态，例如弹窗内部数据、复杂对象、敏感信息

路径参数应该稳定、可分享、可被搜索引擎理解。查询参数适合表达同一个页面下的不同视图状态。状态参数则更适合放在组件状态、全局 store、服务端 session 或数据库里。

什么时候不要用 URL 传参

不是所有信息都适合通过路由传递。

下面这些情况要谨慎：

  • token、手机号、邮箱等敏感信息
  • 体积很大的对象
  • 只在当前交互流程中有意义的临时状态
  • 用户不能篡改的数据
  • 会频繁变化但不需要分享的状态

实战建议

我的经验是先问三个问题：

第一，这个参数是否代表资源身份？如果是，放路径里，例如 /posts/[id]。

第二，这个参数是否代表可分享的页面视图？如果是，放 query，例如 /posts?tag=react&page=2。

第三，这个参数是否敏感、复杂或不可信？如果是，不要直接放 URL，改用 ID、服务端状态或客户端状态。

然后再做两件事：所有入口统一校验，所有错误统一返回。

路由传参不是语法题，而是应用信息架构的一部分。参数设计得清楚，页面刷新、分享、回退、SEO、日志分析都会顺很多；参数设计得随意，后面通常会在权限、缓存、埋点和错误处理上慢慢还债。

小结

Next.js 提供了丰富而灵活的路由传参方式：动态路由适合资源身份，查询字符串适合筛选和分页，Link 和编程式导航适合不同交互场景，catch-all 路由适合文档和 CMS，App Router 则把 params 与 searchParams 分得更明确。

真正重要的是边界意识：参数来自用户，必须校验；URL 可分享，也可被篡改；API 错误要统一；复杂对象不要轻易塞进 query。把这些基础打牢，路由层会稳定很多。
