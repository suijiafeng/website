DOM 事件机制入门：捕获、冒泡和事件委托到底该怎么理解

2021-11-21
前端基础

前端开发里，事件是最基础也最常见的能力之一。

点击按钮、输入内容、提交表单、滚动页面，这些交互的背后其实都离不开事件机制。

实际开发中大家会直接使用事件，但一旦遇到下面这些情况，就会发现自己其实并没有真正理解它：

  • 为什么点击子元素时父元素的事件也触发了
  • 为什么有些事件监听加在父级上也能生效
  • 为什么 stopPropagation 有时能解决问题，有时又不够

这些问题都和 DOM 事件机制有关。

我自己刚工作那两年，对事件的理解就停留在"绑 click 就能用"的程度。直到有一次做一个表格组件，每行有编辑、删除、查看三个按钮，整行又能点开详情，结果点删除的时候详情弹窗也一起弹出来了。当时我对着代码看了半天，怎么也想不通"我明明只给删除按钮绑了事件"，最后才意识到问题出在冒泡上。从那以后我才认真去补这块的知识。后来发现，事件这套机制看着基础，真正绕不开的坑其实不少，下面这些都是我实际踩过或者帮同事排查过的。

什么是事件传播

当你点击一个页面元素时，浏览器并不是只把这次点击交给当前元素处理。

它会沿着 DOM 树进行一轮传播，这个传播过程通常分成三个阶段：

  1. 捕获阶段
  2. 目标阶段
  3. 冒泡阶段

简单理解就是，事件会先从外往里走，再从里往外走。

假设页面结构是这样：

当点击按钮时，事件路径大致会经过 window、document、html、body、#app、#save，然后再沿着路径往回走。捕获阶段是从外到内，冒泡阶段是从内到外。

大多数时候我们写的监听器都在冒泡阶段执行，因为 addEventListener 默认的 capture 是 false。

这里有个细节我一开始没注意：目标元素本身上面的监听器，无论你写 capture: true 还是默认的冒泡，都会在"目标阶段"被触发，区别只是同一个元素上多个监听器之间的相对顺序。也就是说捕获和冒泡的差异主要体现在祖先元素上，目标节点是个特殊点。这点在调试事件顺序时容易让人困惑，我后来干脆写了个小 demo 把整条路径打印出来，看一遍就清楚了：

点一下保存按钮，控制台输出顺序是：app 捕获 → save 捕获 → save 冒泡 → app 冒泡。可以看到目标节点 save 上两个监听器是按注册顺序走的，跟捕获冒泡没关系，而祖先 app 则严格分两头。这个输出我贴在工位便签上看了很久才真正记住。

冒泡为什么这么重要

在日常开发中，最常遇到的通常是冒泡。

例如：

当点击子元素时，通常会先触发子元素，再触发父元素。这就是冒泡。

理解这一点很重要，因为很多交互问题其实不是“事件绑错了”，而是没有意识到事件还会继续向上传播。

一个很典型的场景是卡片点击：

点击删除按钮时，如果不阻止传播，卡片的 openDetail 也会执行。这不是浏览器异常，而是事件冒泡的正常结果。

我前面提到的那个表格组件，本质就是这个问题。当时我的第一反应是给删除按钮也加 stopPropagation，确实管用，但后来按钮越来越多（编辑、复制、更多菜单……），每个都要记得写一句，漏一个就出 bug。这种"靠每个子元素自觉"的方案在团队里几乎一定会坏掉，因为新来的同事根本不知道这条隐形规则。后面我会讲到我更倾向的做法，是把判断收到父级去。

还有个容易忽略的点：冒泡不只发生在 click 上。focus 和 blur 这两个事件本身是不冒泡的，但浏览器提供了对应的 focusin / focusout，它们是冒泡的。我有次想用事件委托统一处理表单里所有输入框的失焦校验，绑 blur 怎么都不触发，查了文档才知道得用 focusout。这种"看着该冒泡却不冒泡"的事件还有 mouseenter、mouseleave，对应能冒泡的是 mouseover、mouseout，做悬浮交互时要分清楚。

捕获阶段什么时候会用到

捕获阶段在业务开发里不像冒泡那样常见，但它确实存在。

如果你通过第三个参数或配置项启用捕获监听，事件会先在外层元素触发，再到目标元素。

大多数场景下你不一定主动用它，但知道它的存在，能帮助你更好理解事件执行顺序。

捕获阶段适合少数需要更早拦截事件的场景，比如全局点击统计、弹窗外点击判断、某些基础组件的统一拦截。不过它不应该被滥用，因为捕获监听比普通冒泡监听更不容易被业务代码察觉。

我真正用到捕获，是在做一个全局埋点的时候。需求是无论页面上哪个带 data-track 的元素被点了，都要上报一次，而且要保证业务自己的 stopPropagation 不会把埋点吞掉。如果埋点绑在冒泡阶段，业务代码里随便一个 stopPropagation 就会让上报丢失。把埋点放在 document 的捕获阶段就稳了，因为捕获是从最外层先走，业务的冒泡阻断发生在它之后：

什么是事件委托

事件委托是前端里非常实用的一种技巧。

它的思路是：不把事件直接绑定在每个子元素上，而是绑定在它们的父元素上，再通过事件对象判断具体是哪个子元素触发的。

这样做的好处很明显：

  • 减少重复绑定
  • 动态新增元素也能响应
  • 结构更集中

不过真实业务里，点击目标不一定正好是 li。用户可能点到列表项里的文字、图标、按钮，这时 event.target.matches('li') 就不一定成立。

  • 用 closest 向上找真正的列表项
  • 用 contains 确认找到的元素仍然属于当前列表

第二个判断看起来多余，但在嵌套列表、弹层、复杂组件里很有用，可以避免误处理外部元素。

事件委托也不是所有场景都适合。如果每个子元素的交互差异很大，或者需要独立清理资源，直接绑定在子组件上反而更清楚。

我吃过一次委托相关的性能亏，反而让我对它印象更深。那是一个上千行的长列表，最初每行都单独绑了 click、mouseenter、mouseleave，结果滚动起来很卡，DevTools 里能看到内存里挂着几千个监听器。改成在容器上委托之后，监听器从几千个降到三个，滚动流畅了不少，初次渲染也快了。这是事件委托除了"动态元素也能响应"之外，另一个很实在的好处：监听器数量从 O(n) 降到 O(1)。

委托里还有个坑是关于 event.target 的取值。如果列表项里有 SVG 图标，点到 SVG 内部的 path 时，event.target 会是那个 path 元素，而 SVG 元素的 className 是 SVGAnimatedString 而不是普通字符串，用 classList 判断有时会出意外。所以我现在做委托一律走 closest，让它自己往上找到带 data-id 的业务节点，不去纠结到底点中了哪个子标签，省心很多。

如果你不希望事件继续向上传播，可以调用：

这通常用于阻止父级事件误触发。

例如一个卡片整体可点击，卡片内部又有删除按钮，这时删除按钮点击后如果不阻止传播，卡片点击逻辑也可能被触发。

但 stopPropagation 不是万能药。它只阻止事件继续向父级传播，不会阻止当前元素上其他监听器执行。如果你需要阻止同一元素上后续监听器执行，才会用到 stopImmediatePropagation。

日常业务里我会谨慎使用这类方法。很多时候更好的方式是让父级判断点击来源，而不是让子级强行打断所有传播。

这种写法把规则放在父级：如果点到按钮，就不打开详情。相比在每个内部按钮都写 stopPropagation，更容易维护。

回到我那个表格组件，最后我就是用这个思路重构的。父级只认一条规则——点到任意带 data-action 的元素就交给对应处理函数，否则才算"点了整行"，删除复制编辑这些按钮再也不用各自去阻断传播。代码集中在一处，新增按钮只要加个 data-action 属性就行，再没出过误触详情的问题。

另外提醒一个我见过别人踩的坑：stopPropagation 在 React 里和原生不完全是一回事。React 的合成事件是统一委托在根节点上的，你在某个子组件里对合成事件调 e.stopPropagation()，它只能拦住 React 体系内的其他合成监听器，拦不住你另外用 addEventListener 绑在 document 上的原生监听器。要拦那种得用 e.nativeEvent.stopImmediatePropagation()。这种混用原生和框架事件的场景虽然不多，但一旦碰上排查起来特别费劲。

事件对象里最常用的几个属性

日常开发中比较常见的有：

  • target
  • currentTarget
  • preventDefault

其中最容易混的是：

  • event.target 表示实际触发事件的元素
  • event.currentTarget 表示当前正在处理事件的元素

理解这两个区别，对写事件委托特别重要。

我以前最容易忘清理的就是这种绑在 window / document 上的全局监听。组件本身的 DOM 被销毁时，绑在它内部元素上的监听器会跟着一起回收，不用太操心；但绑在全局对象上的不会，组件反复挂载卸载几次，全局上就堆了一串旧回调，旧回调里又闭包引用着已经销毁的组件状态，既漏内存又会触发奇怪的逻辑。我有次做单页应用切路由，回到上一个页面发现滚动逻辑被执行了两遍，就是上一次的 scroll 监听没清掉。

写在最后

DOM 事件机制最重要的，不是死记捕获和冒泡的定义，而是理解事件在页面中的传播路径。

只要把事件传播、事件委托、默认行为和当前目标这几个概念理顺，很多日常交互问题都会更容易分析。事件机制看起来基础，但它几乎贯穿了整个前端交互开发。

我现在写事件逻辑时会习惯性问几个问题：这个监听器应该绑在哪一层？是否需要委托？是否会误触发父级逻辑？是否需要阻止默认行为？组件销毁时是否要清理？这些问题想清楚，事件代码通常就不会太乱。

上一篇前端代码评审在看什么：不是挑格式，而是提前拦住后续成本下一篇为什么前端要关心可访问性：它不是额外需求，而是页面基本质量
