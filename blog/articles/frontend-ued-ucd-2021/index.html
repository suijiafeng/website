UED 和 UCD：前端该在设计稿之外补哪些状态

2021-01-25
前端基础交互与动效

设计师同事给我甩了一版后台详情页的设计稿，评审会上她盯着我改的间距皱眉："按钮和上面的表单区隔太小了，视觉上会显得挤。"我把间距按她原稿的 24px 改回去了，但顺嘴多问了一句："那这个保存按钮点下去之后长什么样，你稿子里没画。"她愣了一下说这个一般前端自己处理就行。

这个反问不是抬杠。间距是视觉问题，设计师负责的边界很清楚；但"点下去之后"这件事，往往落在设计稿画不到、产品需求文档也不会写的地方，最后全靠前端自己拿主意。这也是这一年我对 UED（User Experience Design）和 UCD（User-Centered Design）这两个词的理解方式：不是把它们当成设计部门的专业术语挂在嘴边，而是当成前端实现时的一份检查清单——设计稿之外，哪些状态是我必须自己想清楚的。

从一次按钮防重复点击说起

那次评审之后没几天，这个保存按钮真出了事。用户网络卡顿，点了按钮没反应就又点了四次，后台收到五条重复提交的记录。设计稿上压根没画"提交中"这个状态，我也没主动做，事故就是这么来的。

UED 关心的不只是好不好看

设计同事后来跟我解释过她们内部对 UED 的理解：不是页面好不好看，而是用户在使用过程中的整体感受——操作顺不顺手、出错了知不知道怎么办、信息层级合不合理。这些确实听起来偏视觉和交互设计，但真正执行下去，很大一块要靠前端在实现细节里兜住。

长表单校验失败还有一个体验细节容易被忽略：只在顶部弹一句"有字段填写有误"，用户得自己一个个去找错在哪。更好的做法是校验失败时把焦点移到第一个出错字段：

focus 管理还有一层容易被忽视的地方：弹窗、抽屉这类临时打开的浮层，关闭之后焦点应该还给触发它的那个元素，而不是让焦点悬空回到 <body>。用键盘操作或者读屏软件的用户，关掉一个弹窗后如果焦点丢了，等于要重新从头找一遍页面，体验上是一次断裂。处理方式并不复杂，打开浮层前记住触发元素，关闭时手动 focus 回去：

打开时把焦点放到浮层内第一个可交互元素，关闭时还给触发者，这一来一回构成一个完整的焦点闭环，是很多组件库自己实现弹窗时容易漏掉的细节——尤其是团队里早期直接手写、没依赖组件库封装的那批浮层组件，这个问题在我们项目里就出现过好几次。

UCD 落到具体任务上是什么样子

UCD 讲的是从用户需求出发，而不是照着功能清单实现。这句话听起来有点空，但拿一个具体功能对照就很清楚。

我们后台系统里"导出报表"这个功能，产品需求文档上只有一句话:支持导出。我第一版做得也很直白:点击按钮、调接口、弹个"导出成功"。上线以后数据量一大，接口要跑十几秒，用户在这十几秒里什么反馈都没有，以为没点上就疯狂连点，或者干脆切走页面导致请求被取消，又跑来问导出的文件去哪了。

后来我把这个功能重新设计成一个有生命周期的任务：点击后立刻进入"生成中"状态，明确告诉用户大概要等多久、可以先去做别的事；生成完成后给一个可下载的通知或链接；失败了给出重试入口。功能清单上"支持导出报表"这一句话，落到前端其实拆成了好几个状态。UCD 强调的正是这个——不能只看功能有没有实现，要看用户在真实场景里能不能顺利把这件事办完。

同样的思路放到"用户是谁、在什么场景下用"这个问题上也成立。这套后台系统的使用者是仓库和客服人员，很多人是在仓库里用平板操作，网络环境比办公室差得多、手指点击也没有鼠标精准。这两个前提直接决定了两件事：一是所有异步操作都要假设网络慢，反馈要更保守、更明确；二是可点击区域不能照搬 PC 端的间距。我们后来把移动端和平板端的按钮点击热区统一提到不小于 44×44px 这个标准（这个数字最早是苹果人机界面指南给的经验值，后台系统虽然不是原生 App，但触屏场景下这个尺寸依然适用），这不是凭感觉定的，是先搞清楚使用者的实际操作方式再倒推出来的约束。

除了点击热区，响应式断点这一年也被我们重新梳理过一次。以前团队的做法是照抄一套通用的 768px/1024px 断点，不管这个系统实际给谁用。后来发现仓库场景下常用的平板尺寸相对固定，与其套用通用断点，不如直接针对实际设备的视口宽度调整关键断点：

视觉还原之外，前端要主动补的几类状态

设计同事那次问我"这个前端自己处理就行吧"，其实说出了一个常见的认知：设计稿覆盖的是最顺利的那条路径，剩下的分支状态默认交给前端判断。这些状态通常包括加载中、空数据、出错、禁用、操作成功、弱网环境下的呈现，它们不会全部画在设计稿里，但项目上线后一定会遇到。

我现在接手一个新页面，会主动拿这几类状态去跟设计师和产品对一遍，尤其是空状态和错误状态，十有八九设计稿里没画。比如这次导出功能定稿前，我直接问设计同事："列表没有数据的时候，是不是应该有个引导语，还是就留白？"她想了两秒说确实没考虑过，补了张插图加一句"暂无导出记录，点击上方按钮开始导出"。这种问题问得越早，返工成本越低，比等上线后被用户截图甩到群里再补救要划算得多。

调试这些状态也有个实用方法：不用等真出问题才去看错误态长什么样。开发阶段可以直接把状态临时写死，或者用 Chrome DevTools 的 Network 面板把请求节流到 Slow 3G，甚至直接 block 掉某个接口，弱网和失败态当场就能复现。QA 提测前有个习惯，专门会问一句"空状态和失败态给我看一眼"，这个问题问多了，团队里现在默认所有状态都要肉眼验证过一遍才算开发完成，只跑通顺利路径不算完工。

空状态本身也不是只有一种。列表为空可能是因为用户还没创建过数据，也可能是筛选条件太严格导致查不到结果，这两种情况给用户的引导完全不同。前一种适合引导去创建，后一种适合提示放宽筛选条件：

一类进阶写法：乐观更新和可撤销操作

导出报表这类耗时几秒到十几秒的操作，靠"生成中"状态过渡是合理的;但对于点赞、收藏、拖拽排序这类几乎瞬间就能返回结果的操作，让用户等接口返回再刷新界面，感知上反而显得迟钝。这类场景可以考虑乐观更新——先假设操作会成功，立刻更新界面，接口在背后异步提交，失败了再回滚并提示:

乐观更新的取舍点在于：操作的可逆性和失败概率都要足够高才值得用。像收藏、点赞这类失败率低、且失败了用户重试成本也很低的操作适合;但涉及金额、库存这类操作，失败回滚会让用户产生"我到底操作成功没有"的困惑，还是老实等接口返回更稳妥。这也是这一年我们内部对"什么时候可以乐观、什么时候必须悲观等待"逐渐形成的一条经验线。

与乐观更新配套的还有一种更保守的模式——可撤销操作。比如删除一条记录，与其在删除前弹确认框打断操作节奏，不如直接执行删除，同时在界面上给出一个几秒钟的"撤销"入口，用户点了才真正调用删除接口。这种设计能减少确认框对操作流程的打断，同时把犯错的代价兜住，是不少国外产品邮件客户端惯用的手法，这一年国内后台系统里也开始有团队尝试。

这套写法比乐观更新多了一层缓冲：真正的接口调用被延后到"撤销窗口"关闭之后，用户如果手滑删错了，撤销的成本几乎为零。要不要用这一套，取决于误操作的代价——批量删除、不可逆的业务动作，适合用可撤销缓冲一层；影响范围很小、随时能重新创建的数据，直接乐观更新就够了，没必要每个操作都加一层撤销倒计时，那样反而让界面显得啰嗦。

长列表场景下的另一类体验取舍

后台系统里另一类常见页面是长列表，订单、日志、商品这些数据量动辄几千上万条。这类页面如果一次性把所有行渲染进 DOM，滚动会明显发卡，这是性能问题，但从体验角度看，它同样是一种"用户能不能顺利完成任务"的问题——列表卡顿，用户会怀疑是不是页面崩了。

这一年团队对这类页面的处理方式是只渲染可视区域内及上下各留一屏的行，其余部分用空白占位撑住滚动条高度：

这套思路自己纯手写维护成本不低，边界情况一多就容易出 bug——行高不固定的场景尤其麻烦。真要上生产环境，用现成的虚拟滚动方案更稳妥，自己撸一遍主要是为了搞清楚它到底在解决什么问题：不是单纯地"少渲染几个节点提升帧率"，而是让用户在面对几千条数据时，滚动这个最基础的操作依然是顺畅、可预期的，这本身也是体验的一部分，只是伪装成了一个性能话题。

性能也是体验的一部分，不只是跑分指标

用户不会关心首屏慢是因为接口慢、包体积大还是图片没压缩，他只会觉得这个产品难用。这一年 Google 把 LCP、FID、CLS 这三项指标合称为 Core Web Vitals，5 月起正式成为搜索排名的信号之一，这也是这一年团队重新审视页面性能的一个真实背景——性能不再只是内部跑分好看，还直接和产品能不能被搜索引擎优待挂钩。

其中 CLS（布局偏移）这一项我觉得最值得单独说，因为它特别隐蔽。图片不写尺寸，加载完成那一刻会把下面内容猛地往下挤一截，用户正准备点的按钮突然跑位，手一抖点到别处。解决方式很简单，提前给图片容器占好位：

aspect-ratio 这个写法还比较新，不少浏览器刚支持不久，老项目里更稳妥的做法是用 padding-top 撑出比例的占位方案。无论用哪种，核心都是在图片真正到货之前把那块空间提前留出来，别让布局在加载完成后跳动。这种跳动用户说不清哪里别扭，但会觉得页面"毛躁"，是最容易被忽略、又最容易被 Core Web Vitals 量化出来的一类体验问题。

骨架屏是另一个容易走偏的细节。很多团队做骨架屏图省事，随手拿几个灰色矩形拼一下，形状和真实内容对不上，用户看着骨架屏出现，等真实内容加载完成的瞬间，整个布局又是一次跳动，相当于把 loading 状态和 CLS 问题一起制造出来了。骨架屏的骨架应该尽量贴近真实内容的行高和区块大小，这样加载完成时才是"内容填充"而不是"布局重排"。

还有一点是心理层面的：及时反馈有时候比真的变快更重要。一个操作要花两秒，如果点下去立刻出现 loading，用户是能接受的；但如果点下去半秒没有任何动静，他就会开始怀疑自己是不是没点中。感知速度和真实速度是两回事，前端能优化的很大一部分，其实是感知这一层。

这一点后来我们还专门跟设计同事讨论过 loading 动效的过渡时长。她一开始给的方案是操作触发后立刻显示 loading 图标，我提出了一个折中方案：如果预期操作能在 200 毫秒内完成，不显示任何 loading，避免图标一闪而过反而显得突兀；超过这个阈值再显示，且显示后至少停留几百毫秒，避免因为网络突然变快导致 loading 图标出现又立刻消失、造成视觉闪烁：

这类细节没有放之四海皆准的数值，200 毫秒和最短停留时长都是团队根据实际观察定的经验值，但背后的判断逻辑是一致的：loading 状态本身也需要设计，不是"有没有"这么简单的二元选择。

禁用状态要说清楚原因

disabled 是设计稿里经常出现、但最容易被简化实现的一种状态。设计稿上一个按钮标成灰色、写着"不可用"，前端照着实现无非是加个 disabled 属性，视觉上确实符合稿子，但用户看到一个灰色按钮，第一反应往往是"为什么点不了"，而不是自己去猜。

我们后台系统里有个典型场景：审批流程里，只有当前节点的审批人才能点击"通过"按钮，其他人看到的是禁用状态。早期版本只是简单地灰掉按钮，什么提示都没有，结果客服天天收到"按钮点不动是不是系统坏了"这类工单。后来在禁用按钮上加了一层说明，可以是 title 属性做最基础的兜底，也可以是禁用状态旁边直接放一行文字：

title 属性依赖用户主动悬停才能看到，移动端基本没用，所以关键流程上更建议直接用可见文案说明原因，而不是指望一个悬浮提示兜住所有场景。禁用状态传达的信息应该是"为什么不能操作、什么条件下能操作"，而不只是"现在不能点"。

这条原则往前延伸一步，还能带出一个容易被忽略的判断：有些场景其实不该用 disabled，而应该允许点击、点击后再给出说明。比如一个操作因为库存不足没法执行，禁用按钮会让用户以为这个功能整体坏了；换成允许点击、点击后弹出"当前库存不足，无法发货"这样的提示，用户至少能确认功能本身是正常的，只是当前条件不满足。disabled 和"可点击但会拦截"这两种做法该怎么选，取决于原因对用户来说是不是显而易见——原因足够明显（比如必填项没填），可以直接禁用；原因涉及后台状态、用户无法从界面直接判断（比如库存、权限），更适合让按钮保持可点，点击后再解释。

跟设计师和产品的协作节奏

这几类状态要真正落地，光靠前端自己想清楚还不够，得在评审阶段就有意识地把这些问题摆到桌面上，而不是等开发到一半自己拍板。我们组现在评审设计稿时，除了看视觉还原，还会把 loading、empty、error、disabled 这几项列成几个具体问题当场问出来：数据为空时长什么样、接口失败用户看到什么、这个按钮什么条件下不可点、慢网络下会不会有说明。这几个问题以前是开发中途自己拿主意，现在提前到评审阶段问，好处很直接——设计师和产品当场就能给出方案，不用等我写完代码发现哪里空着，再回去等对方补稿子，中间那段等待和反复沟通的时间基本省掉了。

团队里另一位同事负责的模块之前也踩过反方向的坑：设计师给了非常完整的一套状态设计，包括加载动画的每一帧、错误提示的具体文案，但前端实现的时候图省事只做了默认状态，理由是"反正用户很少遇到"。这类情况提醒我们，前端和设计师之间信息不对称不止一种方向，有时候是设计稿没画全需要前端补，有时候是设计稿画全了、前端偷懒没做全，两种情况都需要在评审或者验收环节被检查出来，不能靠自觉。

文案也是前端要负责的一部分

状态设计里还有一层经常被前端忽略——文案本身的措辞。同样是提示"操作失败"，"提交失败，请重试"和"网络异常，请检查网络连接后重试"传递的信息量完全不同，前者只是告诉用户结果，后者还给出了大致的原因和下一步动作。很多项目里错误文案是前端随手写的，写得潦草，等于把前面做的所有状态设计打了折扣。

移动端输入体验的几个具体细节

后台系统虽然主要在 PC 端使用，但仓库和外勤场景下移动端访问的比例这一年明显上升，输入体验上的几个细节因此被重新检查了一遍。最常见的问题是输入框没有指定合适的 type 和 inputmode，导致用户在手机上输入数字还要切换到符号键盘去找数字，多此一举：

inputmode="numeric" 会让移动端键盘默认展示数字键盘，同时保留 type="text" 不强制浏览器做数字格式校验，比直接用 type="number" 更适合这类"看起来是数字但其实是文本"的字段——比如订单号、验证码这类不需要参与四则运算的数字串，用 type="number" 反而会引入步进箭头这类不必要的界面元素，还可能因为前导零被自动去掉而出错。这个区分很容易被忽略，很多团队图省事所有数字输入框统一用 type="number"，订单号前面的 0 就这么在提交时被吃掉过。

一份可以复用的状态检查清单

把前面这些具体案例往回收一收，其实可以整理成一份不针对特定页面、可以套用到任意新功能上的检查项。我现在接手一个页面时，会按下面这个顺序在心里过一遍，而不是等设计稿评审完就直接开工：

数据还没返回时，用户看到的是什么，这个等待过程要不要告诉用户大概多久；数据为空时，是没有数据还是筛选条件太严格，这两种情况的引导语是不是分开写的；请求失败时，是用户能自己解决的业务错误，还是纯粹的系统故障，文案是不是分层处理过；按钮或操作项不可用时，原因对用户是不是显而易见，不显而易见的话要不要换成可点击、点击后再解释的方式；表单校验不通过时，焦点有没有移动到具体字段，读屏用户能不能听到对应提示；操作完成后，有没有明确的成功反馈，这个反馈是一闪而过还是能让用户确认下来；弱网或者移动端场景下，前面这些状态是不是依然成立，而不是只在办公室的高速网络和大屏幕下测试过一遍。

这份清单没有哪一条是多深的技术难点，难的是养成习惯，在设计稿定稿之前就带着这些问题去问，而不是自己在写代码的时候临时决定，更不是等用户在生产环境里替你发现遗漏。

回到间距那次分歧

那次评审会上关于 24px 间距的分歧后来是这么收的：视觉间距按设计同事的稿子来，但保存按钮这一块我额外加了三种状态的设计——加载中、成功、失败——回头给她看了一眼实现效果，她挑了个更合适的过渡时长。这不是谁让步给谁，而是两边分工本来就不完全重叠：视觉节奏、色彩、间距是设计师的专业判断，前端负责的是把设计稿里没画出来、但用户一定会遇到的那些分支状态想清楚、做完整。

这份判断标准这一年我逐渐固定下来，接手任何一个新页面，先把 loading、empty、error、disabled、success 这几种状态在心里过一遍，再看设计稿里覆盖了哪些、遗漏了哪些，遗漏的部分主动去跟设计师或产品对齐，而不是等上线之后被用户的反馈推着走。

设计同事后来在另一个项目里也开始主动画这几类状态的示意图，倒不是因为她突然多懂了前端实现细节，而是她发现提前把这些分支画出来，返工的次数确实少了。这算是一次分工边界被重新校准的过程：视觉规范该谁定还是谁定，但哪些状态必须存在、该在什么条件下出现，前端和设计师提前对齐一次，比谁都省事。

这套判断习惯放到不同项目里会有不同的取舍权重，电商中后台和面向普通消费者的产品对"分支状态"的容忍度也不一样——中后台用户是内部同事，遇到问题多半会直接反馈甚至当面找过来，容错空间看起来更大，但正因为这样更容易被前端自己忽略掉这些细节，觉得"反正问题会有人来找我"。真正把这些状态当成实现的一部分而不是可选项来做，省下来的不只是用户的等待和困惑，也是自己后续被回头追问、临时补救的那部分时间。

设计同事那句"这个前端自己处理就行"，某种程度上说的没错——很多状态确实不需要设计师逐一画出来，但"不需要画"不等于"不需要设计"，前端在写这部分代码的时候，本质上就是在替这些没画出来的状态做设计决策。这个决策做得细不细致，用户是感受得到的。
