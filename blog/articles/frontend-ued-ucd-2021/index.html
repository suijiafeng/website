UED 和 UCD：前端为什么也要理解用户体验

2021-01-25
前端基础交互与动效

前端开发经常被理解成“把设计稿做出来”。

但真正好的前端工作，不只是还原页面，还包括让用户能顺畅地完成操作。

这就绕不开 UED 和 UCD。

对前端来说，理解用户体验不是越界，而是把实现做完整。用户最终接触的是页面，不是设计稿，也不是接口文档。

我刚工作时也觉得这是设计师该操心的事，自己只要像素级还原就算交差。真正让我转变想法的是一次线上反馈：一个表单提交按钮，用户连点了五次，后台收到五条重复订单。设计稿上压根没画“提交中”这个状态，我也就没做，结果就出了事故。那一刻我才明白，设计稿只是产品的一个切面，真正完整的体验是由前端在实现里一点点补齐的——加载、禁用、重试、空数据，这些设计师不一定画得全，但用户一定会遇到。理解 UED 和 UCD，本质上是帮自己把活干完整，少背锅。

UED 是什么

UED 是 User Experience Design，也就是用户体验设计。

它关注用户在使用产品过程中的整体感受。

比如：

  • 页面是否好理解
  • 操作是否顺手
  • 状态反馈是否清楚
  • 出错时是否知道怎么办
  • 信息层级是否合理

这些都不只是视觉问题，也和交互、文案、性能、前端实现有关。

UCD 是什么

UCD 是 User-Centered Design，也就是以用户为中心的设计。

它强调从用户需求出发，而不是只从功能清单出发。

一个功能做出来，不代表用户真的会用。

UCD 更关心：

  • 用户是谁
  • 用户要完成什么任务
  • 用户在什么场景下使用
  • 哪些步骤会造成困扰
  • 怎样减少用户理解成本

这和前端开发的关系很直接。

举个例子：后台系统里的“导出报表”功能，功能清单可能只有一句话，但用户真正关心的是：

  • 数据量大时要等多久
  • 导出期间能不能离开页面
  • 失败后能不能重试
  • 文件生成后在哪里下载
  • 没有权限时为什么不能导出

这些问题都会落到前端交互和状态呈现上。

我做过一版导出，一开始就是简单地点击按钮、调接口、弹个“导出成功”。结果数据量一大，接口要跑十几秒，用户在这十几秒里啥反馈都没有，以为没点上就疯狂点，要么直接切走页面导致请求被取消。后来才意识到，导出这种耗时操作得当成一个有生命周期的任务来设计：点击后立刻进入“生成中”，明确告诉用户大概要等多久、可以离开；完成后用一个可下载的链接或通知告诉他文件好了；失败了给重试入口。功能清单里那一句“支持导出报表”，落到前端其实是好几个状态的事，这正是 UCD 强调的——别只看功能有没有，要看用户在真实场景里能不能顺利用上。

前端和用户体验的关系

前端是用户真正接触产品的地方。

同一个功能，前端实现不同，体验可能差很多。

例如：

  • 请求慢时有没有 loading
  • 表单错误是否定位到具体字段
  • 按钮点击后是否防止重复提交
  • 移动端点击区域是否足够大
  • 空状态是否告诉用户下一步做什么

这些细节看起来小，但会直接影响用户是否能完成任务。

这里的 aria-describedby 和 role="alert" 不是摆设。role="alert" 会让屏幕阅读器在内容出现时主动念出来，aria-describedby 把错误文案和对应输入框关联起来，用读屏软件的用户聚焦到这个框时就能听到提示。我以前完全不在意无障碍，觉得那是边角需求，直到给一个政务项目做验收，对方明确要求过无障碍检测，临时补一堆 aria 属性补得焦头烂额。后来我养成习惯，表单的错误提示从一开始就带上这两个属性，反正也不费事，还顺手解决了一类未来的麻烦。

另外一个体验细节：错误要尽量定位到具体字段并把焦点移过去。一个长表单提交失败，只在顶部弹一句“有字段填写有误”，用户得自己一个个去找哪儿错了。更好的做法是校验失败时把页面滚动并聚焦到第一个出错的输入框：

少让用户找，就是在降低他完成任务的成本。

不要只盯着视觉还原

视觉还原当然重要，但不是全部。

一个页面像素级还原设计稿，但如果接口慢、表单难填、错误提示模糊、移动端点不到按钮，用户体验仍然不好。

前端需要在实现时主动关注：

  • 交互状态
  • 加载状态
  • 空状态
  • 错误状态
  • 禁用状态
  • 响应式表现

这些状态通常不会全部画在设计稿里，但项目上线后一定会出现。

可以把它们整理成前端实现检查清单：

  • loading：用户是否知道正在处理
  • empty：没有数据时是否知道下一步
  • error：失败原因和恢复动作是否明确
  • disabled：不能操作的原因是否清楚
  • success：操作完成后是否有反馈
  • mobile：移动端点击区域和输入体验是否可用
  • slow network：慢网络下是否还能理解当前状态

这份清单比单纯对照静态设计稿更接近真实使用场景。

我现在每接一个页面，都会拿这份清单跟设计师和产品对一遍，尤其是 empty 和 error 这两项，十有八九设计稿里是没有的。早点问出来，要么对方补个稿，要么口头约定个简单方案，总比上线后用户截图甩到群里再返工强。提需求的时候多问一句“没有数据时长什么样”“接口挂了显示什么”，往往能省掉后面一轮加急。

调试这些状态也有个实用的小技巧：别等真出错才去看错误态长什么样，开发时直接在代码里临时把状态写死，或者用 Chrome DevTools 的 Network 面板把请求节流到 Slow 3G、甚至直接 block 掉某个接口，慢加载和失败态当场就能复现出来。我团队里要求所有状态都得肉眼验过一遍才算开发完成，不能只跑通 happy path 就提测。

统一错误处理的意义不是让代码看起来整齐，而是让用户在不同页面遇到失败时，得到一致、可理解的反馈。

不过有一类错误得单独拎出来，不能一律糊一句“服务暂时不可用”——那就是后端返回的、对用户有指导意义的业务错误。比如“余额不足”“验证码已过期”“该手机号已注册”，这些是用户能自己解决的，含糊成“系统繁忙”反而坑人。我后来的做法是分层：网络层、5xx 这种用户管不了的，统一兜底文案；4xx 里后端带了明确 message 的业务错误，原样透传给用户：

这套约定能成立的前提是和后端谈好错误结构，至少有个稳定的 message 字段。我吃过亏的项目就是各个接口错误格式五花八门，前端只能各写各的兜底，最后用户看到的提示也乱七八糟。错误契约这种事，越早跟后端拉齐越省心。

性能也属于体验

页面慢不是单纯的技术指标问题。用户不会关心首屏慢是因为接口慢、包太大还是图片没压缩，他只会觉得产品难用。

前端至少要关注这些体验层面的性能细节：

  • 首屏是否尽快出现有意义内容
  • 骨架屏是否和真实布局接近
  • 图片是否有尺寸，避免布局跳动
  • 点击后是否及时给反馈
  • 长列表是否避免一次渲染过多节点

性能优化最终不是为了跑分，而是为了让用户少等、少误解、少重复操作。

其中“图片有尺寸、避免布局跳动”这条我想多说一句，因为它特别隐蔽。图片不写宽高，加载完成那一刻会把下面的内容猛地往下挤一截，用户正要点的按钮就跑了，手一抖点到别处。解决很简单，给图片容器提前占好位：

aspect-ratio 是比较新的写法，老项目里更稳妥的是用 padding 撑出比例的那套占位方案。无论哪种，核心都是在图片到货前就把那块空间留出来，别让布局事后跳动。这种跳动用户说不清哪里别扭，但就是觉得页面“毛躁”，而它恰恰是最容易被忽略的体验杀手。

还有一个心理层面的点：及时反馈有时候比真的变快更重要。一个操作要花两秒，如果点下去立刻出现 loading，用户是能接受的；但如果点下去半秒没动静，他就开始怀疑是不是没点上。感知速度和真实速度是两回事，前端能优化的，很大一部分其实是感知。

做久了以后我越来越觉得，设计稿只覆盖了最顺利的那一刻。

前端真正要补的是那些不顺利的状态：接口慢了有没有反馈，数据空了是不是还说得通，按钮禁用时用户知不知道原因，图片没回来前布局会不会跳，手机屏幕窄一点内容会不会挤坏。页面“出来了”只是第一步，用户能不能少猜、少等、少误触，才是这些细节最后要解决的问题。
