Next.js 14 重点更新：更快的开发体验和更自然的数据变更

2023-10-30
前端基础React

我看 Next.js 14 时，第一反应不是“又有哪些新 API”，而是它会不会影响现有项目的升级节奏。

当时手上有个 Next 项目，本地开发已经开始变慢，表单提交还绕着一层 API Route，页面又同时有静态内容和登录后动态数据。Next.js 14 里几个变化刚好都戳在这些点上：Turbopack 解决开发体验，Server Actions 让数据变更更靠近服务端，部分预渲染继续模糊静态和动态的边界。

如果项目已经使用 App Router，Next.js 14 会更贴近它的完整设计方向；如果还在 Pages Router，我不会建议为了追版本立刻迁，但这些能力背后的方向值得提前理解。

这篇是 2023 年底写下来的记录。回头看，Next.js 的变化速度很快，所以我更愿意把它当成一次“方向观察”，而不是固定版本教程。具体 API 是否稳定，要以当前官方文档和项目版本为准；但它背后的几个趋势很明确：服务端边界更重要，数据变更更靠近服务端，静态和动态渲染开始混合。

Turbopack 继续推进

Next.js 14 继续推进基于 Rust 的 Turbopack。它的目标是改善大型项目的本地开发速度，包括启动速度和热更新速度。

对日常开发来说，这类优化很直接：项目越大，等待构建和刷新带来的损耗越明显。一个页面改完样式后等几秒才看到结果，单次看似不多，一天累积下来就是明显的效率损耗。

不过 Turbopack 不是魔法。项目里如果存在大量动态导入、复杂 Babel 插件、自定义 Webpack 配置或非标准资源处理，仍然需要验证兼容性。

升级时建议先在本地和测试分支开启，重点检查：

  • 热更新是否正常
  • CSS 和 CSS Modules 是否正常
  • SVG、图片、字体等资源是否正常
  • 自定义构建配置是否仍然生效
  • 开发环境和生产构建结果是否一致

不要只看启动速度变快就直接合并。构建工具变化影响的是整个工程链路。

我在升级构建工具时会先跑两个维度：本地开发体验和生产产物一致性。前者看 HMR、CSS、资源处理，后者看 next build、核心页面、部署平台。开发快是好事，但如果生产构建和开发表现不一致，问题会更难排查。

Server Actions 更稳定

Server Actions 让数据变更可以写得更自然。

以前提交表单常见做法是：

  • 前端监听 submit
  • 调用 API Route
  • 服务端处理数据
  • 客户端再刷新状态

这让简单表单和数据变更少写很多胶水代码，尤其适合创建、更新、删除这类直接动作。

但 Server Actions 不是让你把所有业务都塞进组件文件。复杂业务仍然应该放在清晰的 service 或 domain 层里，Server Action 只作为入口，负责拿表单数据、调用业务函数、处理跳转或刷新。

我更愿意把 Server Action 看成“服务端入口函数”，不是业务层本身。比如创建文章，Action 负责读取 FormData、校验权限、调用 createPostService，而不是把数据库写入、日志、通知、缓存刷新全塞在组件文件里。入口可以靠近页面，业务规则还是要有自己的边界。

Server Action 做完数据变更后，还要处理缓存失效。很多“提交成功但页面还是旧数据”的问题，不是写库失败，而是服务端缓存或路由缓存没有刷新。我的习惯是把数据读取和失效点成对设计：哪里读了列表，哪里就要知道变更后该刷新列表还是详情。

这里不要为了省事全站刷新。列表、详情、用户信息这些数据最好有清楚的 tag 或路径边界，否则一次小提交会让太多页面缓存失效，最后性能收益又被自己打掉。

错误处理不能省

Server Actions 写起来像直接调用函数，但它仍然跨越了客户端和服务端边界。权限、参数校验、数据库错误、重复提交都要处理。

部分预渲染值得关注

先说清楚状态：部分预渲染（Partial Prerendering）在 14 这个版本还是 preview，要手动打开 experimental.ppr 才能试，官方明确说了别上生产。所以下面这些更多是"它想解决什么、值不值得提前关注"，不是让你现在就拿它重构页面。

它的思路是：先把页面中稳定的部分尽快返回，再把动态内容流式补上。

它试图在静态页面速度和动态页面能力之间取得平衡。这对电商、内容站、SaaS 首页这类页面很有价值，因为它们往往同时包含静态结构和个性化内容。

比如一个文章详情页，标题、正文、作者信息可以静态生成；阅读数、推荐内容、登录用户状态可以动态加载。用户不应该因为一个个性化模块慢，就一直看不到主体内容。

这种思路要求开发者更认真地区分页面里的稳定部分和动态部分。不是所有内容都要放在同一个请求里，也不是所有组件都要用同一种渲染策略。

这其实是对页面结构的重新拆分。以前很多页面习惯一个顶层请求拿齐所有数据，现在要想清楚哪些内容可以先回来，哪些内容可以挂 Suspense，哪些内容失败了不影响主体。渲染策略不只是框架配置，也会倒逼你整理业务模块的依赖关系。

App Router 的心智变化

Next.js 14 继续强化 App Router 的方向。它不仅是目录结构变化，还改变了数据获取和组件边界的心智。

Server Component 更适合读取数据和渲染稳定内容；Client Component 更适合处理交互、状态和浏览器 API。一个常见误区是为了方便，在顶层加 "use client"，结果整棵组件树都变成客户端渲染，失去了 Server Component 的价值。

更稳的方式是把客户端边界压到真正需要交互的位置：

LikeButton 可以是 Client Component，但文章主体不需要为了一个点赞按钮一起变成客户端组件。

我见过最常见的迁移问题，是为了用一个浏览器 API，就把很大的 layout 标成 "use client"。这样做短期省事，长期会把很多本来可以服务端渲染的内容推到客户端。更好的办法是把交互组件往下沉，把纯展示和数据读取留在 Server Component。

判断一个组件该不该 "use client"，我会按这几项过一遍：

  • 是否使用 useState、useEffect、事件处理函数
  • 是否依赖 window、document、localStorage
  • 是否依赖只能在浏览器运行的第三方库
  • 是否真的需要把父组件也变成客户端组件

如果只是一个小按钮需要交互，就把按钮单独拆成 Client Component；如果整个页面都要读浏览器宽度或订阅事件，再考虑更大的客户端边界。这个边界越小，发给浏览器的 JS 越少，服务端组件的价值也越能保住。

升级前要看运行环境

Next.js 14 对 Node.js 版本有要求，也有一些弃用和行为变化。

升级前建议检查：

  • Node.js 版本
  • next/font 使用方式
  • next/image 配置
  • 自定义 webpack 配置
  • App Router 和 Pages Router 的混用情况
  • 中间件和运行时配置
  • 部署平台是否支持目标版本

不要只改版本号就上线，至少要跑完整构建和核心页面回归。对于使用 SSR、鉴权、支付回调、后台管理的项目，还要重点验证服务端行为。

升级前我还会查一遍第三方库是否支持 App Router 和 Server Component。很多组件库、富文本、图表、埋点 SDK 默认依赖 window，只能放在 Client Component 里。不是不能用，而是要明确客户端边界，避免在服务端组件里直接 import 导致构建或运行时报错。

我现在评估 Next 升级，会把“能不能用新特性”放在后面。

先看项目有没有清楚的服务端/客户端边界，第三方库是不是依赖 window，构建产物和开发环境表现是否一致，部署平台是否支持目标版本。Turbopack、Server Actions、部分预渲染都很吸引人，但它们一旦进项目，影响的是工程链路，不是某个页面的小改动。

Next.js 14 的方向很清楚：开发体验、数据变更和渲染性能在继续收拢。跟上这条线没问题，但升级最好一步一步来，先验证基础，再引入能力。
