Playwright 做 E2E：关键路径比覆盖率更重要

2023-03-24
前端基础构建与模块化

E2E 测试最容易写成两种极端。

一种是完全没有，所有回归都靠人工点；另一种是想用 E2E 覆盖所有细节，结果测试又慢又脆，CI 一天红几次，大家最后选择忽略。

Playwright 很好用，但它不能替你决定测什么。E2E 的目标不是追覆盖率，而是保护关键路径。

先选关键路径

我一般只把这些放进 E2E：

  • 登录能成功
  • 核心列表能搜索并进入详情
  • 关键表单能提交
  • 权限不足能被拦截
  • 支付、审批、发布这类高风险流程

不要用 E2E 测每个按钮颜色、每个工具函数、每个弹窗边界。这些更适合组件测试或单元测试。

E2E 越少越要准。它应该像上线前的自动巡检，保证主干流程没断。

测试数据要可控

E2E 很怕依赖脏数据。

比如测试“删除订单”，如果环境里刚好没有订单就失败；如果删除了别人正在用的数据，也会影响别的测试。

更稳的方式是每个测试准备自己的数据：

测试结束后清理，或者使用专门测试租户。没有稳定数据，E2E 会变成随机数。

如果不能直接调后端准备数据，也至少要有固定测试账号和固定样本，避免依赖生产式的自然数据。

CI 失败要能定位

E2E 在 CI 上失败时，要留下证据：

  • screenshot
  • trace
  • video
  • console log
  • network log

Playwright trace 很有用，能回放每一步操作。没有 trace 的 E2E 失败，经常只能靠猜。

测试命名也要清楚：

不要写 test('case1')。失败报告应该让人一眼知道哪个业务路径断了。

我的 E2E 原则

我会遵守这些规则：

  • 只测关键路径
  • 用用户视角选择器
  • 不用固定 sleep
  • 登录态复用
  • 测试数据可控
  • 至少覆盖关键错误状态
  • CI 保留 trace 和截图
  • 失败用例要能快速定位

Playwright 能让 E2E 写起来很顺，但真正决定质量的是测试策略。少而稳的关键路径测试，比一大堆脆弱用例更有价值。
