Vuex 什么时候该上：一个购物车金额对不上的 bug 教我的状态分层

2018-08-11
Vue组件与状态

月底测试同学提了个 P1 的 bug：购物车里删掉一件商品，底部的合计金额纹丝不动。用户要是没细看直接下单，结账金额就对不上——这在电商项目里是能出资损的级别，组长直接把它钉在了白板上。

我接手排查。删除商品的逻辑看起来没毛病，cartItems 数组里那一项确实被删掉了，Vue devtools 里看得清清楚楚。但 totalPrice 还是老数字。顺着 totalPrice 往回找，我发现它是一个单独的 state，加商品的 mutation 里手动 state.totalPrice += item.price，而删商品的 mutation 是另一个同事后来加的——他只删了数组项，忘了同步减总价。

**两份本该一致的数据，各改各的，就一定有对不上的一天。**这是这个 bug 的直接成因。但往下挖，我发现这个 store 里的问题远不止这一处，排查最后变成了一场对整个项目状态放置方式的清算。项目的技术栈是 Vue 2.5 加 Vuex 3.x，下面的判断都是从这个项目里一条条摸出来的。

一个八百多行的 store

修 totalPrice 本身只要十分钟，但我打开 store/index.js 的时候愣住了：八百多行，一个文件。里面躺着什么呢——当前登录用户、权限列表、购物车，这些没毛病；但还有某个页面的 tab 当前页码、某个确认弹窗的开关、某个搜索框的输入内容、某个列表的 loading。

问了下组里的老人，说是年初定过一个风气：「能放 store 就放 store，共享方便」。于是所有人写新状态的第一反应都是往 store 里塞。结果就是改一个小交互要在 state、mutation、action 三个地方来回跳；两个人同时开发不同页面，merge 时 store 天天冲突；新人接手第一周基本处于懵的状态，分不清哪个 state 是全局真在用的、哪个只是某个页面的私产。

totalPrice 那个 bug 之所以能发生，土壤就是这个：store 太大太乱，没人能对它建立完整的心智模型，加删除功能的同事根本不知道还有个 totalPrice 需要同步维护。

这篇想记的不是"Vuex 怎么用"，而是排查之后想清楚的那个问题：状态管理的关键不是"有没有 store"，而是状态放在哪个层级最合适。层级放高了，简单交互会变重；层级放低了，跨组件同步又会变乱。

能算出来的就别存

先把案子本身结了。totalPrice 是从 cartItems 派生出来的数据，派生数据存成独立 state，就注定要靠人肉在每个改动点同步维护，而人肉一定会漏。正确的做法是让它变成 getter，永远从源头实时算：

改成 getter 之后，总价永远是 cartItems 实时算出来的，数据只有一份源头，根本不可能不一致。删商品的 mutation 只管删商品，谁也不用记得"还有个总价要同步"。

getter 还有个好处是带缓存——只要依赖的 state 没变，多次访问 cartTotal 不会重复计算，跟组件里的 computed 一个道理。所以放心把复杂派生逻辑写进 getter，性能上不亏。能算出来的就别存，这是我从这个 bug 里带走的第一条铁律。

这个 bug 修完只花了十分钟，但真正的病根还没动：那八百行的 store。接下来是清算。

把不该进 store 的请出去

我把 store 里的 state 一条条过，先问一个问题：这个状态的「生命」是不是和某个组件绑死的？

弹窗关了就没意义、输入框组件销毁了内容就该清空、tab 切走了页码就该重置——这些状态跟着组件生灭，天然属于组件。它们进了 store 之后是什么样呢：

  • mutation 要写
  • action 要写
  • getter 要写
  • 最后只是改一个布尔值

调用链变长了，业务价值一点没增加，还留下一堆"组件已经死了、state 还残留着上次的值"的隐患——我们那个确认弹窗就出过这种事，A 页面开过弹窗没重置，B 页面一进来弹窗自己弹出来了，当时也是查了半天。

这类状态搬回组件里，就是最朴素的写法：

组件销毁，状态跟着销毁，干干净净，不需要任何"记得重置"的纪律。

而登录用户、权限、购物车这种，组件来来去去它都得活着，多个页面都要读、修改入口不止一个、还希望改动路径可追踪——这才是 store 该管的。清算完，store 的 state 砍掉了一半还多。

中间地带用状态提升，别急着全局化

最纠结的是中间那类：同一页面里几个兄弟组件共享一个东西，比如列表组件和筛选栏组件共用一份筛选条件。原来的做法也是进 store，理由是"兄弟组件没法直接通信"。

其实不用惊动全局。先用「状态提升」——把它放到这俩组件共同的父组件里，props 往下传、事件往上抛。Vue 2 里 .sync 修饰符处理这种父子双向同步很顺手：

子组件里 this.$emit('update:keyword', value)，父组件的 keyword 就更新了，另一个兄弟组件自然拿到新值。只有当这份筛选条件还要被别的页面、别的模块复用时，才值得提到 store。

还有人提议兄弟通信用 event bus（new Vue() 当总线）。小场景能用，但我在这个项目里见到了它失控的样子：十几个组件在总线上 $emit、$on，事件名散落各处，谁发的、谁收的、收了干什么，全靠全文搜索。event bus 超过三五个事件就开始变成暗网，这种复杂度反而是 Vuex 的主场——它把改动路径逼到明面上。

清算完这一步，我给自己定了个判断阶梯：

  • 只被当前组件使用：放组件内
  • 父子组件共享：优先 props 和事件（.sync 很顺手）
  • 同一页面多个兄弟组件共享：提升到页面级父组件
  • 跨页面、跨模块共享：再考虑 Vuex

状态层级应该随着真实需求上移，而不是一开始就放到最高处。「会被复用」不等于「应该全局」——有些数据确实有机会在别处再用，但眼下只是局部交互，就不必提前进 store，越早全局化，后面越容易产生多余耦合。

留在 store 里的，要配得上 store 的规矩

清算完剩下的才是正主。以当前登录用户为例，多个页面都依赖 currentUser，放 store 里很自然，否则每个页面都请求一遍 /api/me，或者靠父子组件层层透传——中间隔三四层组件，每层都得声明一遍 prop 再往下递，加一个字段要改一串文件，烦得很。

action 开头那行幂等判断是排查这个项目时顺手抓出的另一个案子：路由守卫里、布局组件里、某个页面里各 dispatch 了一次 fetchCurrentUser，首屏并发打了三个一模一样的 /api/me，接口被刷不说，还可能因为竞态，后到的响应覆盖先到的。拉全局数据的 action 要做幂等，已有就别再打接口，加一行判断省很多事。

另外提醒一句，Vuex 的 state 存在内存里，刷新页面就清空。currentUser 这种不能光靠 store 持久化，得配合 token 在刷新后重新拉，或者用 vuex-persistedstate 之类的插件把它同步到 localStorage。我们项目早期就有人以为放进 store 就万事大吉，结果用户一刷新登录态没了，也是查了半天。用插件的话记得用 paths 圈定范围，只持久化真正需要落盘的那几项，别把整棵状态树往 localStorage 里塞：

整棵树都存的话，那些本该随会话消失的临时状态（比如上次没走完的下单流程）也会在刷新后诈尸，又是一类新 bug 的来源。

留下来的状态还要守 Vuex 的分工约定：

  • state 放状态
  • getter 放派生数据
  • mutation 做同步修改
  • action 处理异步流程

其中有条硬规矩今年踩过的人不少：mutation 必须是同步的。你在 mutation 里写 setTimeout 或者发请求再改 state，Vuex devtools 的时间旅行就废了，状态变更追踪不到。异步一律走 action，action 里 await 完再 commit 同步的 mutation。这不是洁癖，是 Vuex 设计的硬约束，违反了调试体验直接崩。

顺带一个 Vue 2 响应式的坑也在这个 store 里出现过：直接给 state 上的对象加新属性，视图不更新。我们有个按 id 缓存用户详情的 mutation 就是这么写的：

state.userMap[id] = user 这种写法 Vue 的响应式系统追踪不到，得用 Vue.set，或者整个对象换新引用：

数组下标赋值 state.list[0] = xxx 同理，要用 splice 或 Vue.set。这坑在组件 data 里大家都知道防，进了 store 反而容易忘——store 里的 state 一样是 Vue 的响应式系统在管，规则一条不少。

拆 module：别等 store 长成一坨再动手

八百行单文件 store 的最后一步治理是拆 module。这时候最痛的不是拆的技术难度，而是各处调用已经耦合缠死，拆一次像拆炸弹——所以这件事应该在项目早期就做，别等胖了再回头治理。

两个细节别偷懒。一是 module 的 state 写成工厂函数 state: () => ({...}) 而不是对象字面量：直接写对象的话，module 被多处复用时会共享同一份 state 引用，互相串改；写成函数每次返回新对象就没这问题——组件的 data 必须是函数，同一个道理。

二是 namespaced: true 每个 module 都开。不开的话，所有 module 的 mutation/action 名字平铺在全局，两个 module 各有一个 setLoading 就冲突了，commit 一下两个一起触发，诡异得很。我们拆的时候就撞上了：user 和 order 各有一个 setList，没开命名空间前一直在互相触发，没人发现——因为现象只是"多渲染了一次"。

异步错误也要有统一的出口

清算过程里还发现一类乱象：每个 action 的错误处理各自为政。有的 throw、有的返回 null、有的 console.log 一下吞掉，组件根本不知道该怎么接，于是很多组件干脆不处理失败，页面停在永远转圈的 loading 上。

组件拿到的是统一结构，用同一套提示逻辑处理失败。选「结果对象」而不是「抛异常」，是因为后台里大量失败是预期内的（没权限、数据不存在），组件想要的是拿到失败信息做个 toast，而不是被一个 throw 打断流程还得到处包 try/catch。当然这看团队约定，统一了就行，最忌讳的是各写各的。

顺带说说 loading 状态放哪，这又回到全文的核心判断。列表请求的 loading 只有当前页用，放组件 data 就够了；但「全局接口请求计数、控制顶部进度条」这种跨组件的，就适合放 store，action 里 commit('SET_LOADING', true) 开始、finally 里关掉。状态用在哪个范围，就放在哪个层级。

状态该放哪，先想清楚再动手

totalPrice 的 bug 修掉了，store 从八百多行拆成了五个各一百行上下的 module，砍掉了一半不该在里面的 state。测试回归通过那天，我在白板上把那条 P1 划掉，顺手写了一行字：先想归属，再进 store。

Vuex 不该被神化，也不该被滥用。它适合那些真正跨组件、跨页面、需要清晰流转的状态；局部交互交给组件自己反而更自然。「能放 store 就放 store」的风气，恰恰是让 store 失去可维护性的开始——所有东西都全局，等于没有东西是清晰的。

状态管理做得好不好，关键不是上没上 Vuex，而是状态层级是不是放对了。先把状态归属想清楚，再决定是否进 store，Vuex 才会帮你降低复杂度，而不是把简单问题变成流程问题。
