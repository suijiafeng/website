浏览器缓存为什么重要：前端性能优化里最容易被忽略的一环

2021-03-04
前端基础

做前端性能优化时，很多人先想到的是图片压缩、代码拆包、接口并发控制。

这些当然都重要，但浏览器缓存其实是一个更基础的性能杠杆。因为只要缓存策略合理，很多资源根本不需要重复下载。

用户第二次打开页面快不快，很大程度上就看缓存有没有配好。

我自己印象最深的一次，是接手一个老项目时翻 Network 面板，发现首页一次性发了 80 多个请求，其中一半 vendor 脚本每次刷新都重新走网络，总共一两兆。当时第一反应是想着拆包、按需加载，折腾了两天体积只压下来一点点。后来才意识到，问题根本不在体积，而在于这些根本不怎么变的库每次都在重新下载——给它们配上一年的强缓存，二次访问的资源加载时间直接从一千多毫秒掉到几十毫秒。那次之后我才真正把缓存当成性能优化的第一优先级，而不是收尾时顺手做的小事。

缓存在解决什么问题

浏览器访问一个页面时，要下载 HTML、CSS、JavaScript、图片、字体等资源。

如果每次进入页面都把这些内容重新拉一遍，不仅浪费带宽，也会让首屏时间明显变长。

缓存的意义很直接：

  • 减少重复请求
  • 降低资源下载时间
  • 提升二次访问体验
  • 减轻服务端压力

尤其是静态资源体积较大时，缓存带来的收益会非常明显。

前端最常接触的是强缓存和协商缓存

虽然缓存细节涉及 HTTP 协议，但从前端视角看，最常碰到的还是两类：

  • 强缓存
  • 协商缓存

强缓存的特点是浏览器直接使用本地副本，不再向服务端发起完整资源请求。只要缓存还没过期，就不用走网络。它由响应头里的 Cache-Control 和 Expires 控制，现在基本都用前者：

max-age 是相对时间，单位秒，比 Expires 那种绝对时间戳靠谱（Expires 依赖客户端本地时钟，用户电脑时间不准就会失效）。immutable 是我后来才补上的一个属性，意思是告诉浏览器"这文件在有效期内绝对不会变，连刷新时的条件请求都别发"。没加它之前，用户按 F5 刷新，Chrome 还是会对强缓存资源发一轮 304 校验，加了之后这一轮请求也省掉了——对带 hash 的静态资源特别合适。

协商缓存则是浏览器先问服务端："我本地这个资源还能不能继续用？"如果服务端确认没变，就返回一个 304 Not Modified，body 是空的，告诉浏览器继续用旧副本。它靠两组头配合：

  • Last-Modified / If-Modified-Since：基于文件修改时间，精度只到秒
  • ETag / If-None-Match：基于内容指纹，更准

我踩过一个坑：只靠 Last-Modified 时，有个文件被重新部署但内容没变，修改时间却更新了，结果明明可以复用却被判定成"变了"，全量重下。后来发现同时存在 ETag 时浏览器会优先用 ETag，这种"内容没变但时间戳变了"的场景就稳了。所以多数 web server（Nginx、Apache）默认两个一起发，是有道理的。

开发中最重要的不是背术语，而是知道两者带来的实际差别：强缓存命中时 Network 里状态是灰色的 200 (from disk cache / from memory cache)，根本不发请求；协商缓存命中时是 304，请求还是发了，只是省掉了 body 的传输。前者更省网络，后者更适合确认资源是否更新。

为什么静态资源特别适合做缓存

静态资源有一个天然优势：很多时候它们不会频繁变化。

例如：

  • logo 图片
  • 打包后的 JS 文件
  • 样式文件
  • 字体文件

如果这些资源每次都重新下载，用户体验会非常浪费。

所以前端工程化里常见做法是给资源文件名加 hash。这样一旦内容变化，文件名也会变化；内容没变时，文件名保持不变，就可以大胆使用更长时间的缓存策略。

还有一个容易忽略的细节：webpack 默认会把模块 id 算进 chunk 内容，导致你加一个无关的新模块时，老 chunk 的 contenthash 也跟着变。生产构建里我一般会显式固定 runtime 和模块 id 的生成方式（比如 optimization.moduleIds: 'deterministic'、把 runtime 单独抽成一个 chunk），让"内容没动的文件 hash 也别动"这件事真正可控，否则发一次版用户缓存哗啦啦失效一大片，缓存配得再长也没用。

仅仅“开缓存”还不够，关键是更新机制要可靠

很多缓存问题不是因为没缓存，而是因为缓存更新失控。

最典型的是：

  • 资源已经发布了新版本，但用户还在用旧文件
  • HTML 更新了，引用的静态资源还是老地址
  • 强缓存太久，线上修复无法及时生效

这就是为什么缓存策略必须和构建产物命名、发布流程一起考虑。

如果资源文件名不变，又给了很长缓存时间，后面想让用户拿到新版本就会变得麻烦。反过来，如果资源名带内容 hash，就能兼顾"缓存时间长"和"版本更新准"这两个目标。

我们线上真出过一次"缓存太久压不下来"的事故。某个公共配置 JS 当时没加 hash，文件名固定，又被配了 max-age=86400（一天）。结果上线一个紧急修复，老用户因为强缓存还没过期，整整一天都拿的是旧文件，客服那边投诉一直没断。强缓存命中期间浏览器压根不发请求，你在服务端怎么改都没用，唯一能"召回"用户的办法就是换 URL。从那以后我定的规矩很简单：

  • 带 contenthash 的文件：Cache-Control: max-age=31536000, immutable，放心缓一年
  • 没法加 hash、但又需要随时能改的文件：宁可 no-cache 走协商缓存，也不要配较长的 max-age

no-cache 这个名字特别有迷惑性，它不是"不缓存"，而是"每次都要先找服务端校验一下再用"，真正完全不存的是 no-store。我面试时也常拿这个问，能分清这俩的人其实没想象中多。

开发环境和生产环境看缓存的方式不一样

开发阶段经常会看到浏览器里资源不断重新加载，于是有人会误以为缓存策略没生效。

其实开发环境往往有热更新、禁用缓存或本地代理等因素，行为和线上并不一样。

真正需要关心的是生产环境：

  • 页面 HTML 怎么缓存
  • 打包出来的 JS / CSS 怎么缓存
  • 图片和字体怎么缓存

通常 HTML 不会缓存太激进，因为它要负责把最新资源入口给到浏览器；而带 hash 的静态资源可以更大胆地长期缓存。

补充一个开发环境的真实困惑：本地用 webpack-dev-server 时所有资源都是内存里实时编译、强制不缓存的，所以你在本地永远复现不出线上的缓存问题。要验证缓存策略，最靠谱的办法是 npm run build 出产物，用一个真正的静态服务器（比如 npx serve 或本地起个 Nginx）配上对应的响应头跑一遍，再去 Network 面板看状态码。光在 dev 环境点点点是看不出门道的。

缓存不是万能的，但它非常划算

缓存不能解决所有性能问题。首访用户仍然需要第一次下载资源，体积过大的脚本也不会因为缓存就消失。

但缓存的好处是性价比很高。一套合理的缓存策略，不一定需要改很多业务代码，却能显著改善重复访问体验。

这也是为什么我一直觉得，前端做性能优化不能只盯着打包体积和接口时间。资源被怎么使用、有没有重复下载、版本更新是否稳，也同样重要。

真正要形成的是资源生命周期意识

浏览器缓存看起来像后端或运维的事情，但前端其实和它关系很近。

因为前端决定了：

  • 资源是否可被长期复用
  • 文件名是否稳定可控
  • 页面是否引用了正确版本
  • 发布后用户多久能拿到最新资源

理解缓存的价值，本质上是在理解资源生命周期。一个成熟的前端项目，不只是把页面写出来，还要让资源在用户浏览器里以更合理的方式被复用。

HTML 和静态资源，通常不该用同一套缓存策略

前端项目里很容易混淆的一点，是把入口 HTML 和打包产物当成同一类资源对待。

实际上它们的职责并不一样。HTML 更像资源索引，它负责把当前页面应该加载哪些脚本和样式告诉浏览器；而打包后的 JS、CSS、图片则是相对稳定的具体文件，只要内容不变，就应该尽量被长期复用。

如果 HTML 缓存过重，用户可能迟迟拿不到新版本入口；如果静态资源缓存过轻，用户又会反复下载本来没变化的文件。很多“已经发版了，为什么用户还是旧页面”的问题，往下看几乎都和这两类资源没有分开处理有关。

真正排查缓存问题时，要连发布链路一起看

缓存之所以让人头疼，是因为它表现出来的现象往往不只发生在浏览器这一层。

例如：

  • 资源文件名有没有随着内容变化而变化
  • HTML 引用的是不是最新打包产物
  • CDN 节点是否还在分发旧文件
  • 用户本地是否命中了老入口页

只盯着浏览器有没有重新请求，并不足以解释很多线上现象。前端理解缓存的真正价值，不是会背几个响应头，而是能在资源复用、版本更新和发布稳定性之间做出更清楚的判断。

我自己排查这类问题有个固定顺序，基本能少走很多弯路：

  1. 先在浏览器无痕窗口里复现，排除是不是本地缓存太顽固——无痕也复现，说明问题在服务端或 CDN，不在用户本地。
  2. 看 HTML 的响应头到底命中没命中缓存。最常见的元凶就是 HTML 被某一层（CDN、Nginx）顺手配了强缓存，导致用户拿到的还是指向旧脚本的老入口。
  3. 对比 HTML 里引用的脚本文件名和最新构建产物的文件名是否一致，确认入口指对了。
  4. 直接拿脚本的完整 URL 去请求 CDN 各个节点，看是不是个别节点没刷新、还在分发旧文件——CDN 这层经常需要手动触发刷新（purge），构建发布脚本里最好把它纳进去。

说到底，缓存不是一个孤立的浏览器话题，它串起了构建产物命名、服务端响应头、CDN 分发和发布流程一整条链路。前端能把这条链路在脑子里走通，比记住十个响应头的语义都管用。
