为什么前端要关心可访问性：它不是额外需求，而是页面基本质量

2021-11-03
前端基础

可访问性这个词，很多前端都听过，但真正把它当成日常开发要求的人并不算多。

一个常见误区是觉得它只服务少数特殊用户，或者只有做政务、教育、公共服务类项目时才需要认真考虑。可只要网页面对真实用户，就存在不同设备、不同操作方式、不同能力条件，可访问性其实就是页面基本质量的一部分。

可访问性不是“多做一点”，而是别把门槛做高

前端页面默认面对的用户，并不都使用鼠标和大屏。

有人主要靠键盘操作，有人依赖读屏工具，有人在移动端环境下网络和注意力都有限，还有人只是暂时无法精细操作。一个页面如果只有“标准鼠标用户”才能顺利用，实际上已经把很多人排除在外了。

所以可访问性的核心不是加很多特殊功能，而是别把原本可以顺利用的事情做得更难。

我自己有过一次很直接的体会。有阵子手腕受伤打了石膏，右手几乎用不了鼠标，只能靠键盘和触控板将就。那两周我用自己平时维护的后台系统时，挫败感非常强：很多表格的操作按钮我根本 Tab 不到，下拉菜单一展开就抓不住焦点，分页器只能点。最讽刺的是，这些代码大半是我自己写的。那之前我也"知道"可访问性这回事，但真正卡在自己做的页面前面，才明白它不是抽象的合规要求，而是会实实在在挡住人的东西——而且挡住的可能就是某个阶段的你自己。

语义化结构是最基础的一步

很多可访问性问题，并不需要高深技巧，第一步往往只是用对 HTML。

例如：

  • 导航用 nav
  • 按钮用 button
  • 表单控件配好 label
  • 标题层级保持清晰

这些做法不只是结构更好看，也是在给浏览器和辅助技术提供明确语义。原生标签本身就携带了很多默认能力，能少造轮子就少造。

而 <button> 这些全是免费的。所以我现在写组件库的基础元素时有条铁律：能落到原生语义标签上的，绝不用 div 重新发明。真要做花哨样式，也是 <button> 加 appearance: none 把默认样式抹掉，而不是反过来从 div 把能力一项项补回来。

标题层级也别小看。我见过为了视觉效果，整页只有一个 h1，下面全是加粗的 div。读屏用户有个很常用的操作是"按标题跳读"（NVDA 里按 H 键在标题间跳转），页面没有标题结构，这个能力就直接失效，他们只能从头听到尾。h1 到 h6 别跳级、别为了字号大小去选标签，字号是 CSS 的事。

键盘可用性经常比想象中更重要

很多页面肉眼看起来没问题，但一旦不用鼠标，就会立刻暴露问题：

  • 不能按 Tab 聚焦关键控件
  • 焦点样式被去掉了
  • 自定义按钮只能点，不能键盘触发
  • 弹窗打开后焦点跑丢

如果一个功能只有鼠标用户能顺利完成，那它的可用性其实是不完整的。

所以前端在做交互组件时，至少要常想一件事：不用鼠标，这个流程还能不能走通？

焦点样式被去掉这件事，我得专门说一下，因为它是被误删的重灾区。很多人受不了 Chrome 点按钮后那圈蓝色 outline，全局来一句：

弹窗的焦点管理是另一个经典坑。我自己踩过的版本是：弹窗打开了，但焦点还停在背后那个触发按钮上，键盘用户得 Tab 穿过整个页面才能进到弹窗里；更糟的是关掉弹窗后焦点直接掉到 body，下一次 Tab 又从页头开始。一个合格的弹窗至少要做到三件事——打开时把焦点移进去、关闭时还给触发元素、Tab 不能跑到弹窗外面（焦点陷阱）：

后来上 React 之后这类逻辑我基本不再手写了，弹窗、下拉、Tabs 这些组件直接用经过无障碍打磨的库（比如 Radix、Reach UI 这类），它们把焦点陷阱、aria-* 属性、Esc 关闭都处理好了。自己造这种组件，光焦点这一项就够踩好几轮坑。

提示信息也需要被正确感知

表单报错、提交成功、加载状态变化，这些提示不该只靠颜色或者一闪而过的视觉效果表达。

因为并不是所有用户都能第一时间看见或看懂这些变化。更清晰的做法是：

  • 错误提示靠近对应字段
  • 重要状态变化有明确文本
  • 不只依赖颜色区分成功和失败

前端很多“我已经提示了”的设计，实际只是对能看见且能立刻理解的人提示了。

这里有个很多人没意识到的技术细节：动态插入到页面里的内容，读屏工具默认是不会主动播报的。你用 JS 往页面塞一句"提交成功"，视力正常的人看见了，但读屏用户那边可能一点声音都没有，因为屏幕阅读器并不知道这块区域刚刚更新了。解决办法是用 ARIA 的 live region：

我踩过的一个细节是：这个容器一定要在页面初始渲染时就存在、保持空着，等需要时再往里写文本。如果是临时 createElement 插进去的，很多读屏工具不一定能捕捉到这次变化，等于白做。

表单报错也别只靠红框红字。要把错误文本和对应输入框用 aria-describedby 关联起来，再用 aria-invalid 标出哪个字段错了，这样焦点一落到输入框，读屏就会把错误原因一起念出来：

可访问性做得好，普通用户也会受益

这是很容易被忽略的一点。

例如：

  • 结构清晰的页面更容易阅读
  • 可聚焦按钮更容易操作
  • 文案明确的错误提示更容易修正
  • 对比度合理的文字更容易看清

所以可访问性并不是为了照顾一个“额外群体”，而是在提升整体使用体验。

真正常见的问题，是开发过程中根本没把它纳入检查项

不是大家反对可访问性，而是太多项目默认不检查它。

设计时没考虑，开发时没验证，测试时也不覆盖，于是最后留下来的是一堆“正常用户也许暂时没抱怨，但其实并不友好”的细节。

如果能把最基础的可访问性当成开发习惯，例如优先用语义标签、保留焦点样式、验证键盘流程，页面质量通常会明显更稳。

让"检查"这件事不靠自觉，最有效的办法是把它工具化。我自己常用的几样，按投入产出排个序：

  • 键盘走查：开发完一个交互，先收起鼠标，只用 Tab、Shift+Tab、回车、空格、Esc 把流程走一遍。这条几乎零成本，却能抓出八成问题，是性价比最高的。
  • Lighthouse / axe 插件：Chrome 自带的 Lighthouse 有 Accessibility 评分，axe DevTools 插件能直接在页面上标出对比度不足、缺 alt、label 没关联这类静态问题。注意它们只能查机器能判断的部分，分数满分不等于真的可用。
  • eslint-plugin-jsx-a11y：React 项目我一定会装这个，它在写代码时就提示"img 缺 alt""onClick 加在了非交互元素上"，把问题拦在提交之前。
  • 真机读屏：Mac 上的 VoiceOver（Cmd+F5 开关）、Windows 上免费的 NVDA。第一次用会很不习惯，但亲耳听一遍自己的页面被念出来，比看十篇文章都管用——你会立刻发现那些"视觉上很清楚"的东西念出来根本不知所云。

我现在的习惯是把 axe 和 jsx-a11y 接进 CI，静态问题自动拦；键盘走查写进自测清单；读屏则在做关键流程（登录、下单、表单）时手动过一遍。不求一次做到完美，但至少别让低级问题溜到线上。

它值得被放进前端基础能力里

我一直觉得，可访问性不该只在专题分享或者高标准项目里出现。

它和语义化 HTML、表单体验、交互一致性一样，都属于网页天然应该关心的问题。前端如果只盯着视觉效果和功能完成，而忽略页面是否真正可达、可操作、可理解，那这个页面其实还没做完整。

很多可访问性问题，都是“自定义过度”带出来的

这几年我一个比较明显的感受是，页面越花哨，越容易把浏览器原本已经提供的默认能力拆掉。

例如原生按钮、原生表单控件、原生标题结构，本来就自带不少语义和交互基础。可一旦我们为了视觉统一，把它们全部包装成自定义组件，再顺手把默认焦点样式、键盘响应和结构语义一起抹平，可访问性问题往往就开始堆起来了。

这也是为什么很多组件在设计稿里看起来很完整，上线后却会出现：

  • 键盘无法顺畅操作
  • 读屏工具读不出重点
  • 错误提示只在视觉上存在
  • 焦点位置找不到

问题不一定是开发者不重视，而是默认能力被替换掉以后，没有把同等质量的能力补回去。

最典型的就是自定义下拉选择。原生 <select> 样式确实丑、跨浏览器难统一，于是大家普遍用 div 撸一套。可原生 <select> 自带的能力其实非常多：键盘上下键切换选项、输入首字母快速定位、聚焦时读屏播报当前选中值、移动端唤起系统原生选择器。这些自定义实现里能补齐一半就算用心了。我后来的折中是：表单里没那么强样式诉求的地方，尽量保留原生 <select>，只做有限的样式定制；非要做复杂的搜索下拉，就用现成的无障碍组件，而不是自己从零拼。

ARIA 这里也得提醒一句：它是用来补语义的，不是用来覆盖语义的。有句在圈里流传很广的话叫"No ARIA is better than bad ARIA"——错误的 role 和 aria-* 比不写还糟，因为它会主动给读屏传递错误信息。我见过有人给一个本来就是 <button> 的元素又加 role="button"，纯属多余；也见过 aria-hidden="true" 误加在了包含可聚焦元素的容器上，结果读屏跳过它、键盘却还能 Tab 进去，体验直接错乱。能用原生语义解决的，就别上 ARIA。

把可访问性前置，比上线前补救便宜得多

如果等页面都做完了，再回头专项补可访问性，成本通常会很高。因为这时候你改的已经不是一两个标签，而是整套组件交互和结构表达方式。

所以更稳的做法，是把几个最基础的检查前置成默认动作：

  • 自定义可点击元素前，先判断原生标签能不能满足
  • 做弹窗时，顺手验证打开、关闭和焦点回收
  • 写表单时，把 label、报错位置和键盘路径一起想清楚
  • 改全局样式时，不要把焦点轮廓一刀切掉

这些动作都不重，但它们会直接决定页面是“只有视觉完整”，还是“对真实用户也真正可用”。
