前端性能排查思路：页面卡顿时，不要一上来就怀疑框架

2023-05-18
前端基础性能与缓存

前端性能问题最让人头疼的地方，不只是慢，而是不知道到底哪里慢。

页面卡顿的时候，团队里常见的第一反应通常是：是不是框架太重、是不是组件太多、是不是状态管理有问题。这些方向当然可能有关，但如果一上来就把问题归因给“大框架”或“大项目”，通常并不能真正解决问题。

性能排查最重要的是先分类，再用数据验证。不要先猜答案。

我以前也喜欢凭经验猜。列表卡就先加 useMemo，页面慢就先拆包，接口慢就催后端。后来有次客户反馈“筛选卡顿”，我改了半天 React 渲染，Performance 一录才发现真正耗时的是一个同步权限计算，每次筛选都遍历几万条权限关系。方向猜错时，优化越努力越浪费时间。

现在我会先复现、录制、分类，再改代码。这个顺序慢一点，但结论更可靠。

先区分是哪一种慢

性能问题不是只有一种。常见至少有四类：

  • 首屏加载慢
  • 页面切换慢
  • 滚动卡顿
  • 输入、点击反馈慢

这四类问题对应的排查方向可能完全不同。

如果用户说“页面有点卡”，第一步不是改代码，而是把问题描述具体化：哪个页面、什么设备、什么网络、哪个操作、卡多久、是否必现。没有这个上下文，后面的优化很容易变成到处试错。

如果线上已经有 RUM 数据，就更应该先看真实用户指标。LCP、INP、CLS 这些指标不能替代具体排查，但能告诉你问题主要发生在加载、交互还是布局稳定性上。尤其 INP，比过去只看 FID 更能反映一次交互背后的长任务和渲染延迟。

首屏慢先看资源和请求

如果用户第一次打开页面就慢，优先看资源和请求。

常见原因包括：

  • JS 包体积太大
  • 图片资源没有压缩
  • 首屏接口串行
  • 字体加载阻塞文本渲染
  • 第三方脚本提前加载
  • 首屏加载了低频模块

这类问题实际开发中和框架关系不一定大，更多是资源策略不合理。

比如首页只展示一张简单列表，却把图表库、富文本编辑器、后台管理模块都打进首屏包里，即使用再轻的框架也会慢。

排查时可以先看浏览器 Network 面板：HTML、JS、CSS、图片、接口分别花了多久。再看 Performance 或 Lighthouse，把“下载慢”和“执行慢”分开。

我会把首屏慢拆成三段：资源什么时候到、JS 什么时候执行完、主要内容什么时候画出来。如果资源下载很快但 LCP 仍然高，问题可能在 JS 执行、图片解码或渲染阻塞；如果接口串行拖慢首屏，盲目压缩 JS 也不会明显改善。

接口层还要关注失败路径。性能优化时有人会把请求并行化，但忘了统一错误处理，导致一个非关键接口失败把整个页面打崩。我的做法是区分关键请求和增强请求：核心数据失败就展示错误态，统计、推荐、辅助配置失败可以降级，不要阻塞主流程。

交互卡顿先看渲染链路

如果是点击按钮、切换筛选、输入文本时卡，优先排查渲染链路。

常见原因包括：

  • 大量不必要的重渲染
  • 主线程做了重计算
  • 列表过大但没做虚拟化
  • 频繁读写布局属性导致重排
  • 动画使用了不适合的 CSS 属性
  • 第三方脚本抢占主线程

useMemo 不是性能问题的万能答案。它适合缓存确实昂贵、依赖明确的计算。如果计算本身很轻，滥用反而增加复杂度。

如果计算真的重，也不要只想着 memo。防抖、服务端搜索、分页、虚拟列表、Web Worker 都是选择。比如导入 Excel 后做大批量校验，这种任务放在主线程里会把输入和点击都卡住，拆到 Worker 后用户至少还能继续操作页面。

不要把“重渲染”当成唯一答案

很多性能文章喜欢把问题都归结为重渲染，但现实中不一定。

页面卡可能来自：

  • JS 计算太重
  • DOM 数量太多
  • 样式重排频繁
  • 动画掉帧
  • 图片解码耗时
  • 第三方脚本执行时间过长

所以排查时不能只盯着组件 render 次数。React DevTools Profiler 可以帮助定位 React 层的渲染成本，但如果问题来自图片、布局或脚本执行，还是要回到浏览器 Performance 面板。

Performance 面板里我通常先看三件事：

  • Main 线程有没有超过 50ms 的长任务
  • Layout 和 Recalculate Style 是否频繁出现
  • 交互发生后到下一帧绘制之间卡在哪里

如果火焰图里大头是脚本，就继续看函数栈；如果 Layout 很重，就回到 DOM 数量、样式选择器和读写布局；如果 Paint 很重，就看图片、阴影、滤镜和绘制区域。

列表问题特别容易放大性能缺陷

列表是性能问题高发区。因为一个小问题乘以几百行、几千行之后，成本会被放大。

常见问题包括：

  • 一次渲染所有数据
  • 每一行都有复杂组件
  • 每一行都绑定大量事件
  • 滚动时触发布局计算
  • key 不稳定导致整表重建

如果列表很长，优先考虑虚拟列表，只渲染可视区域。即使暂时不引入库，也要避免一次把几千个 DOM 节点全部渲染出来。

稳定 key 能帮助框架正确复用节点，减少不必要的重建。

列表还要注意“每行都很聪明”。每行组件自己请求权限、自己监听窗口、自己创建复杂 formatter，看起来单行成本很小，乘以几百行就很可观。能提升到列表层统一计算的，就不要每行重复做。

优化要有前后对比

性能优化最怕“感觉快了”。改动前后至少要记录一个指标。

可以记录：

  • 首屏资源总大小
  • LCP
  • INP
  • 接口耗时
  • 主线程长任务数量
  • 某个交互的响应时间
  • 列表渲染行数和耗时

哪怕只是用浏览器工具截图，也比凭感觉判断要可靠。

不要忽略低端设备

开发机上的性能经常有欺骗性。Mac 上 20ms 的计算，在低端安卓 WebView 里可能就是 100ms。Performance 面板可以做 CPU throttling，真机也要尽量覆盖一两台性能普通的设备。

我现在判断一个优化是否有效，会至少看桌面正常环境和低性能模拟环境。只在开发机上“感觉顺了”，还不够。

前端性能排查不要一上来就怀疑框架。先把慢分成首屏、切换、滚动、输入点击等具体场景，再从资源、请求、渲染和主线程四个方向验证。

真正有效的优化通常不是一个神奇配置，而是把问题定位清楚：该拆包就拆包，该并行就并行，该虚拟化就虚拟化，该减少主线程计算就减少计算。只有能被测量的优化，才值得上线。
