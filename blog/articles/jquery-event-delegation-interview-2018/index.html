jQuery 事件委托实战：一张五千行工单表卡出来的经验，顺便聊聊我面试为什么爱问它

2018-06-19
JavaScript前端基础

事件委托最能体现价值的时候，不是在 demo 里绑定几个按钮，而是在一个动态列表越堆越大、按钮越来越多、页面开始一顿一顿地卡的时候。只要还是给每个元素挨个绑事件，性能和维护成本都会一起跟着涨。

我手上这套老 jQuery 工单系统就是典型现场。列表从分页 20 条改成了“加载更多”之后，运营一口气能把几千条工单堆在一页上，而代码里处理点击的方式，还是给每个按钮单独绑事件。页面一慢，事件委托为什么重要，就不再只是面试题了。

这个现象第一次坑我的时候，我盯着代码看了半天：绑定写得明明白白，怎么就不响应？后来才反应过来：$('.delete-btn').on(...) 这行代码执行的那一刻，jQuery 是去 DOM 里找出当时已经存在的所有 .delete-btn，挨个把处理函数挂上去。它不是给"以后所有叫这个类名的元素"登记规则，而是给"现在这一批具体的 DOM 节点"绑事件。Ajax 之后 append 进来的新按钮，是 on 执行之后才出生的，自然没人给它挂。

写这套老代码的人显然也发现了这个问题，他的解法是每次渲染完重新绑一遍：

这条路我自己也走过，越走越窄。一是每次渲染都要记得重新绑，少写一次就有按钮失灵，而且这种 bug 不报错，特别难发现；二是更隐蔽的——.html() 整体替换还好，旧节点连同事件一起销毁了；可这次改成"加载更多"，用的是 .append() 追加，旧节点上的事件还在，新一轮 .on 又给所有匹配节点（包括旧的）再绑一次。旧按钮被绑了两次，点一下触发两次 deleteItem。

这不是理论推演。这套工单系统线上真出过事：运营点一次"作废"作废了两单，查了大半天才定位到重复绑定。这次的卡顿，一部分根源也在这——翻了十几"页"之后，头几批按钮身上已经叠了十几层同样的处理函数。

我用 Chrome DevTools 验证了一下：控制台里 getEventListeners($0)（$0 是 Elements 面板选中的节点）能列出一个元素身上挂的所有监听。随便点开一个第一批加载的按钮，click 底下齐刷刷一排重复的 listener。再算总账：五千行工单，每行删除、编辑、展开三个绑定，光初始就是一万五千个处理函数挂在 DOM 上，还在随翻页翻倍。"靠人记得重新绑"的方案，本质上就是不可靠的，规模一上来还会变成性能问题。

修法：事件委托，一次绑定管所有

修这个问题的正解，jQuery 里一行都不用多写：

注意它和直接绑定形式上很像，区别全在那个中间多出来的选择器参数 '.delete-btn'。没有它，是把事件直接绑到 .list 自己身上；有了它，就变成委托——事件还是挂在 .list 上，但只有当冒泡上来的事件源能匹配 .delete-btn 时才执行处理函数。一个参数之差，机制完全不同，这也是初学者最容易写错的地方。

关键在于：事件绑在 .list 这个一直存在的父容器上，跟它里面的按钮什么时候被创建出来没有任何关系。.list 页面初始化时就有了，事件挂上去就一直待命。后面 Ajax append 进来多少个新按钮，只要落在 .list 内部，点击产生的事件就一定会冒泡到 .list，jQuery 在这里现场判断"事件源匹不匹配 .delete-btn"，匹配就执行。

后续动态添加的按钮自动能响应，不需要在任何渲染后重新绑定——绑一次，管所有现在和将来的按钮。这是它最大的价值：把"绑定时机"和"节点创建时机"彻底解耦。改造之后我写动态列表几乎是条件反射地用委托，根本不操心 append 之后要不要重绑。

一万五千个处理函数变成三个，getEventListeners 再看，清清爽爽。

底层机制：事件冒泡，以及它的另一半

委托能成立，靠的是事件冒泡——事件从目标元素向父级一路上传：

你可以把委托理解成"在半路上设卡检查"：事件从 button 一路往上冒，经过 .list 时被拦下来盘问一句"你是从 .delete-btn 来的吗"，是就放行执行。卡设在 .list 这个固定位置，过往的"车"（事件）是谁、什么时候造出来的都不重要。

我面试时问到这里，常追问另一半：事件除了冒泡（bubbling），还有一个先于它发生的捕获（capturing）阶段——事件先从 document 一路向下走到目标元素，再从目标元素往上冒。完整路径：

stopPropagation：会误伤队友的刀

如果事件在到达委托容器之前，中间某个节点调用了：

事件就不再继续冒泡，委托直接失效。这个坑我真真切切栽过：页面上有个第三方图片预览插件，内部给图片容器绑了点击事件，为了不让点击穿透到背后，调了 stopPropagation。结果我在外层用委托写的"点击行选中"功能，只要点到图片就不生效，点行里其他地方都正常。排查了好久才发现是插件把冒泡掐断了——事件根本没冒到我委托的那一层。

所以不要随便阻止冒泡。stopPropagation 是一把会误伤队友的刀：你为了解决自己这一层的问题掐断冒泡，可能让上层某个完全无关、靠委托工作的功能莫名失灵，而且对方根本不知道是被你掐的。我现在的原则是，只有确实需要阻断父级行为时才用，而且在注释里写清楚为什么——别让后来的人（包括我自己）对着失灵的委托抓狂。

顺带把容易混淆的几个撇清：event.stopPropagation() 阻止的是冒泡，event.preventDefault() 阻止的是默认行为（<a> 的跳转、表单提交），两码事。jQuery 里 return false 等价于同时调这两个，威力更猛，更要慎用——这套老代码里就有人在委托的处理函数里图省事写 return false，顺手把别的功能也掐了。

委托到哪里合适：这次改造里最险的一步

改造时我一度想偷懒，全部委托到 document：

这能用，但范围太大——页面上每一次点击都会走到 document 再做匹配。更推荐委托到稳定的父容器：

"稳定"是关键词，我被它教育过：委托的父容器自己绝对不能在生命周期里被销毁重建。我犯过的错是把事件委托到了一个每次刷新列表都被 .html() 整个替换掉的内层 div 上——第一次能用，刷新列表后那个 div 连同身上的委托一起没了，新 div 上什么都没有。后来把委托上移到外层那个从不重建的容器，问题消失。选委托容器，要选"页面在的时候它一直在"的那个，而不是离按钮最近的那个。

至于 document，不是不能用，它有个特定场景反而合适：当你连一个稳定的、包住所有目标元素的父容器都找不到时——弹窗、Toast 这种被动态塞到 body 末尾、彼此没有共同业务父级的元素——委托到 document 是兜底。但只要有更具体的稳定容器，就别图省事甩给 document，范围小一点，匹配开销小一点，逻辑也更内聚。

弹窗是重灾区，模式我专门写出来。弹窗常是"打开时初始化、关闭时销毁"，初始化里绑事件、关闭时不解绑，开关几次处理函数就叠了好几层：

我习惯在 on 之前先 off 一次同命名空间的事件，让初始化变成幂等操作——哪怕逻辑上某处漏了 closeUserDialog，重复打开也不会累积绑定。这个"先 off 再 on"的小习惯，帮我躲过了不少老页面里"点一次提交，弹三个一模一样成功提示"的诡异 bug。说到底，委托省去了动态节点逐个绑定的麻烦，但绑在父容器上的事件本身仍然要管理生命周期，别因为用了委托就忘了这茬。

不是所有事件都适合委托

点击事件天然冒泡，最适合委托。mouseenter、mouseleave 则要小心：这俩原生其实不冒泡（它们是 mouseover/mouseout 的"不冒泡版"），好在 jQuery 在委托里做了特殊处理，on('mouseenter', '.item', fn) 能正常工作，它内部帮你模拟了。但如果你用原生 addEventListener 想委托 mouseenter，会发现绑了没反应，得换成会冒泡的 mouseover/mouseout 自己判断进出。

表单事件里，focus 和 blur 同样不冒泡（对应的冒泡版是 focusin/focusout），想委托表单聚焦失焦，jQuery 里直接用 focusin/focusout：

这个我在工单系统的动态增删行表单里用得很多——可以"添加一行"的明细表，每行带输入框，用 focusout 委托做校验，新增的行不用任何额外绑定就自带校验，非常省事。

性能上也别把委托当免费午餐。原理是：委托容器上每发生一次该类型事件，jQuery 都要拿事件冒泡路径去和你给的选择器做匹配。选择器越复杂（.a .b > .c:not(.disabled) 这种），单次匹配越贵；再委托到 document，页面上任何一次点击都要跑一遍匹配，高频操作下能感觉到卡。所以"委托到尽量小的稳定容器、选择器尽量简单"不只是整洁问题，也是实打实的性能考量。委托的本质是把"很多个处理函数"换成"一个处理函数 + 每次事件的一点匹配开销"，这笔账在动态、海量节点的场景下绝对划算，在静态、少量、高频的场景下未必。

收工，以及我面试为什么爱问这题

改造上线后我把运营请过来验收：五千条工单堆一页，点"作废"，确认框立刻弹出来，一次只作废一单。她说"早该这样了"，端着杯子走了。

上周面试一个三年经验的候选人，我照例问了事件委托。他没背"利用冒泡机制减少绑定"那套标准答案，而是讲了自己被动态节点绑不上事件坑过一次的经历，讲到 target 和 this 的区别时还主动提了按钮里有图标的场景。我基本当场就想给过——这道题我爱问，不是想听定义，是想分辨"背过"和"踩过"：踩过的人讲起来眼神都不一样。

我现在看事件委托，重点早不在"少绑几个事件"这么简单。它好用，是因为动态节点和长列表都可以交给一个稳定的父节点处理；它麻烦，也正是因为所有点击都会先落到同一个入口里。委托范围选多大、怎么判断真正的 event.target、哪里会被 stopPropagation 截断、模块销毁时能不能解绑干净——这些细节没处理好，事件委托一样会变成排查成本很高的隐患。这套工单系统，就是正反两面的活教材。
