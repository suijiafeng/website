Linux 常用命令：部署前端项目时，不能只会 npm run build

2019-03-19
构建与模块化

前端项目最后总要上线。我刚工作那会儿，以为自己的活儿到 npm run build 就结束了——打包出一个 dist，丢给运维或者后端，剩下的不归我管。直到有一次大半夜上线，页面白屏，运维已经下班，群里一堆人 @我问"你那边没问题吧"。我连服务器都不知道怎么登，只能干瞪眼。那一刻我才明白，前端工程师不会点 Linux，关键时刻是真的会卡住的。

后来我慢慢摸清了一个规律：线上出问题，九成情况不需要你去改代码，而是需要你先把现场搞清楚——日志里报了什么、进程还活着没、端口通不通、Nginx 把请求转到哪去了。这些事 SSH 上去敲几条命令就能看明白，比在群里来回猜快得多。

这篇我就按"上线—排查"这个真实流程，把我自己常年在服务器上敲的命令串一遍。不求全，求能用。每条命令都配上我实际遇到的场景，省得你像我当年那样临场抓瞎。

先说一句前提：下面假设你已经能 ssh user@your-server 登进服务器了。如果连这步都还没通，先去运维那要一个账号和密钥，别用密码登，麻烦还不安全。

第一件事：搞清楚自己站在哪

登上服务器，我做的第一件事永远是确认"我现在在哪个目录、这目录里有什么"。在自己机器上这无所谓，但线上一台机器可能跑着好几个项目，搞错目录改错文件是真出过事的。

ls -la 是我用得最多的形式，-l 给出权限/属主/大小/修改时间，-a 把 .env、.nginx 这种点开头的隐藏文件也列出来。前端项目里 .env.production 经常就是配置出错的源头，不加 -a 你根本看不见它。

删除：线上最该手抖的地方

rm -rf 这条我每次敲都心里发紧。它不进回收站，敲下回车文件就没了。我的几个铁律：

  • 永远不在 rm -rf 后面用变量或通配符前先 echo 一遍。比如想删 rm -rf $BUILD_DIR/*，先 echo rm -rf $BUILD_DIR/* 看清楚展开成什么再说。$BUILD_DIR 万一是空的，那条命令就成了 rm -rf /*，能把整台机器抹平。
  • 删之前先 pwd 确认路径，别在 / 或者 /home 这种地方手贱。
  • 重要文件先 mv 改名留底，而不是直接删，比如 mv app.log app.log.bak。

踩坑提醒：页面 404 别急着改 Nginx 配置。我见过太多人对着 nginx.conf 改半天，最后发现是 dist 没传上去，或者 try_files 把路由指错了。先看错误日志里的真实路径，它会告诉你 Nginx 到底去哪个文件找了没找到，比瞎猜配置快一个数量级。

有个区分特别重要：在服务器上 curl 接口通，不代表浏览器里就能通。服务器之间是机器对机器，没有跨域（CORS）这回事；浏览器有同源策略、有 OPTIONS 预检、有 cookie 和 referer 限制。所以前端报"接口跨域失败"时，你在服务器 curl 出来一切正常是正常的——问题在浏览器和后端的响应头（Access-Control-Allow-Origin 这些），不在接口本身。我刚开始没分清这一点，对着后端同学说"我服务器上 curl 明明能通啊"，结果两边吵了半天才意识到是在说两件事。

权限：permission denied 的真相

部署脚本跑不动，经常是因为没执行权限：

755 是我对脚本的默认权限：属主可读写执行（7），同组和其他人可读可执行（5）。理解这三位数字其实不难——每位是 读(4)+写(2)+执行(1) 的和。配置文件这种不需要执行的，我给 644（属主读写，别人只读）。

碰到 permission denied，先 ls -l 看那一串 -rwxr-xr-x：第一段是属主权限，没有 x 就是不能执行。除了执行位，还有一种坑是文件属主不对——比如文件是 root 的，你用普通账号跑就没权限。这时候用 chown 改属主（需要 sudo）：

前端部署里最典型的权限事故：Nginx 跑在 www-data 用户下，但你 scp 上去的 dist 文件属主是你自己的账号，Nginx 读不了，于是 403。所以传完文件我都会顺手把属主和权限校正一遍。

但 scp 有个毛病：每次都全量传，目录大了又慢又费流量。我更常用 rsync，它只传有变化的部分，断了还能续：

-a 保留权限/时间等属性，-v 显示过程，-z 传输时压缩，--delete 让远端删掉本地已经不存在的文件（保证两边完全一致，但用前要想清楚，它真的会删）。第二次同步同一个项目，rsync 通常几秒就完事，因为绝大多数文件没变。

当然，2019 年正经项目都该走 CI/CD（Jenkins、GitLab CI、GitHub Actions 刚出不久）自动部署，手动 scp 只该是应急或者验证时的手段。但应急的时候，会不会这一手，区别就是"五分钟搞定"还是"等运维上线"。

前端工程师不需要成为 Linux 专家，但这套"看现场"的基本功躲不掉：

  • 定位：pwd / ls -laht / tree——先搞清在哪、有什么、谁最新。
  • 看日志：less / tail -f / 配合 grep 过滤——别 cat 大文件。
  • 搜内容：grep -rn / -C 看上下文 / awk|sort|uniq 做统计。
  • 查服务：ps aux | grep '[n]ode' / lsof -i :端口 / kill。
  • 测接口：curl -I / -v，并且分清服务器和浏览器的差别。
  • 权限与传输：chmod / chown / rsync。

这些命令我建议别死记，而是真到服务器上敲几遍、踩几次坑，自然就长在手上了。线上出事的时候，能不能稳稳地 SSH 上去把问题查明白，是区分"写页面的"和"能扛事的前端"的一道分水岭。我从那个白屏的深夜之后，就再没让自己卡在"登都登不上"的窘境里过。
