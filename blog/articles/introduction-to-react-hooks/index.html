React Hooks 刚上手时，真正容易乱的是副作用和边界

2023-08-15
前端基础React

React Hooks 是 React 16.8 引入的一组能力，它让函数组件也能拥有状态、副作用、上下文和复杂状态管理。Hooks 出现以后，React 组件不再必须依赖 class 才能处理交互逻辑，函数组件逐渐成为主流写法。

不过，Hooks 不只是把 class 换成函数。它背后真正重要的变化是：组件逻辑可以按功能组织，而不是被拆散在生命周期方法里。写得好时，Hooks 能让组件更清晰；写得不好时，也很容易出现重复请求、闭包旧值、依赖数组混乱等问题。

下面从几个常见 Hooks 入手，重点看它们适合解决什么问题，以及使用时要注意哪些边界。

我刚开始从 class 组件切到 Hooks 时，最不习惯的是副作用和依赖数组。以前生命周期方法虽然啰嗦，但执行时机比较直观；Hooks 写起来更轻，但如果没有理解闭包和依赖，很容易出现“请求重复发”“按钮读到旧状态”“effect 一直循环”的问题。所以 Hooks 入门不能只背 API，要理解它们和渲染之间的关系。

useEffect 的常见误区

很多 Hooks 问题都和 useEffect 有关。

第一个误区是把它当成“组件加载时执行一次”。空依赖数组确实只会在挂载后执行，但 useEffect 处理的是副作用同步，不是生命周期方法的简单替代。

第二个误区是依赖数组随便写。依赖漏了，可能读到旧值；依赖多了，可能反复执行。遇到 ESLint 提醒时，不要第一反应禁用规则，而是先检查 effect 里到底使用了哪些外部变量。

第三个误区是在 effect 里做本来可以在事件里做的事。比如点击按钮后提交表单，通常应该在点击事件里直接调用，而不是先改一个状态，再靠 effect 观察这个状态去提交。

useContext：跨层传递数据

当数据需要被多层组件使用时，可以用 useContext 避免层层传 props。

useContext 适合放全局主题、语言、当前用户、权限信息等跨层数据。但它不是所有状态管理问题的答案。

如果一个 context 的值频繁变化，而且被很多组件消费，可能导致较大范围重新渲染。真实项目里要注意拆分 context，避免把“所有全局状态”都塞进一个对象里。

Context 更适合低频变化的全局信息，比如主题、语言、当前用户。把输入框内容、列表筛选、实时计数这类高频状态放进一个大 Context，后面性能问题会很明显。必要时拆 context，或者引入更细粒度的状态管理方案。

自定义 Hook：复用的是逻辑，不只是代码

当多个组件里出现相似逻辑时，可以提取自定义 Hook。

自定义 Hook 的命名必须以 use 开头，这样 React 和 ESLint 才能识别 Hooks 调用规则。

提取 Hook 时要注意边界：它应该复用一段稳定的逻辑，而不是为了减少几行代码强行抽象。如果一个 Hook 需要十几个参数才能兼容不同页面，可能说明抽象得太早。

我现在写自定义 Hook 会先问一句：它复用的是业务规则，还是只是把代码挪走。如果只是为了让组件短一点，把一堆页面专属状态塞进 usePageLogic，其实可读性不一定变好。好的 Hook 应该有明确输入输出，最好能脱离页面名字理解。

Hooks 的基本规则

Hooks 有两条重要规则：

  • 只能在 React 函数组件或自定义 Hook 顶层调用
  • 不能在条件、循环、嵌套函数里调用

React 依赖 Hooks 的调用顺序来关联状态。如果条件执行导致顺序变化，状态就会错乱。

还要注意闭包旧值。定时器、事件监听、Promise 回调里读到的状态，可能是创建回调那一刻的值。遇到这类问题，可以用函数式更新、把依赖补全，或者用 useRef 保存最新值。不要靠“禁用 exhaustive-deps”硬压过去，很多线上问题就是这么来的。

这个“读到旧值”的原理用纯 JS 就能复现，跟 React 没关系——每次渲染相当于用当时的 state 重新创建一批函数，函数闭包住的是那一刻的值：

setInterval(callback, 1000) 的坑就在这：如果它只在挂载时（count 还是 0 的那次渲染）注册了一次，那它永远拿着 callbackFromRender0，之后界面上 count 怎么变，定时器里读到的都是 0。函数式更新 setCount(c => c + 1) 之所以能绕开，是因为它不读闭包里的 count，而是让 React 把最新值传进来。

我后来对 Hooks 的理解，基本是被几个 bug 逼出来的：effect 重复请求、定时器读到旧状态、自定义 Hook 名字很漂亮但里面全是页面细节。

入门时先掌握 useState、useEffect、useContext 和 useReducer 就够了。真正要小心的不是 API 数量，而是几个判断：这份状态该不该存在，effect 是不是必要，依赖数组有没有说实话，自定义 Hook 复用的是规则还是只是搬代码。

Hooks 的目标不是让组件“看起来更函数式”，而是让状态、副作用和业务逻辑的边界更清楚。边界没想清楚，函数组件一样会写成另一种大组件。
