HTTP/2 基础：多路复用为什么能改善页面加载

2019-11-02
请求与异步性能与缓存

前端性能优化里，资源加载一直是大头。

以前我们常做合并 JS、合并 CSS、雪碧图、域名拆分，很多优化都是围绕 HTTP/1.1 的限制来的。HTTP/2 普及以后，一些思路开始变化。不是说以前的经验都没用了，而是要知道网络层能力变了，资源组织方式也要跟着重新判断。

我真正感受到 HTTP/2 的差别，是给一个老项目上 HTTPS 的时候。运维顺手在 Nginx 上开了 HTTP/2（HTTP/2 在浏览器侧基本只跑在 HTTPS 上），我打开 Network 面板一看，几十个静态资源的瀑布图从原来阶梯状的“一批一批排队”变成了几乎齐刷刷一起开始下载。那一刻我才直观理解“多路复用”到底改了什么。这篇就把 HTTP/1.1 的几个老问题、HTTP/2 怎么解决的、以及前端优化思路该怎么跟着调整，按我自己的理解捋一遍。

HTTP/1.1 的连接限制

浏览器对同一个域名的并发连接数有限。

如果页面有很多资源：

请求会排队。前面的请求没完成，后面的请求可能要等。

所以大家会做：

  • 文件合并
  • 图片雪碧图
  • 多域名分发静态资源

这些手段的目的，都是减少请求数或提高并发。

具体限制是多少？大多数浏览器对同一域名的并发连接是 6 个左右。也就是说一个页面如果有 30 个资源挂在同一个域名下，浏览器一次最多并行下 6 个，剩下 24 个得排队等前面的腾出连接。这就是为什么当年“域名拆分”（domain sharding）这么流行——把静态资源散到 static1.xx.com、static2.xxx.com 几个域名上，每个域名各自有 6 个连接的额度，并发数翻几倍。

但域名拆分也有代价：每个新域名都要重新做 DNS 解析、重新建 TCP 连接、HTTPS 还要重新 TLS 握手，这些握手开销在移动网络（高延迟）下相当可观。所以这套优化本质是在“并发不够”和“连接建立成本”之间做权衡，是被 HTTP/1.1 的连接限制逼出来的妥协。理解这个背景，才能明白为什么 HTTP/2 来了之后域名拆分反而成了反优化。

队头阻塞

HTTP/1.1 里，一个连接上的请求响应有顺序限制。前面的响应慢，后面的响应也可能被影响。

这就是常说的队头阻塞。

页面加载时，如果某个大资源慢，会拖累后续资源。

HTTP/1.1 其实有个 pipelining（管线化）特性，理论上允许一个连接上连续发多个请求不等响应。但它要求响应必须按请求顺序返回，第一个响应慢，后面排着的全得等——这就是 HTTP 层的队头阻塞。加上各种代理实现得乱七八糟，pipelining 在实际中基本没人开，浏览器默认都关着。所以现实里 HTTP/1.1 就是“一个连接同一时刻只处理一个请求-响应”，靠开 6 个连接来凑并发。

要分清两层队头阻塞：HTTP/1.1 的队头阻塞在 HTTP 协议层（响应必须按序），HTTP/2 把它解决了；但还有一层 TCP 层的队头阻塞——TCP 要求字节按序到达，一个包丢了，后面的包就算到了也得在内核缓冲区里等重传。HTTP/2 因为所有流跑在同一个 TCP 连接上，反而可能让 TCP 层队头阻塞影响更明显。这个问题要等后来的 QUIC / HTTP/3 用 UDP 才能真正解决，2019 年这会儿先了解到这层就够了。

HTTP/2 多路复用

HTTP/2 可以在一个 TCP 连接里并发传输多个请求和响应。

简单理解：多个资源不必排成单列，一个连接里可以同时传。

这能减少连接数量，也能改善资源排队问题。

对前端来说，资源不一定非要合成一个巨大文件。合理拆分反而更利于缓存和按需加载。

多路复用靠的是“流（stream）”这个概念。HTTP/2 把一个 TCP 连接拆成很多条逻辑流，每个请求-响应占一条流，每条流的数据被切成带流 ID 的二进制帧（frame），这些帧在同一个连接上交错传输，到了对端再按流 ID 重新组装。所以多个请求能真正“同时”跑，而不是排队。这也意味着只需要一个连接，前面说的域名拆分到 HTTP/2 下就成了负优化——拆成多个域名等于强行多建几个连接、多几次握手，还破坏了单连接里的优先级调度和头部压缩共享。HTTP/2 时代正确的做法是资源收敛到同一个域名。

二进制分帧还带来一个副作用要知道：HTTP/2 把请求头、请求体都变成二进制帧传输，不再是 HTTP/1.1 那种纯文本，所以你没法再用 telnet 手敲请求去调试了，得靠浏览器开发者工具或者 nghttp、curl --http2 这类工具。

合理拆分这一点对前端工程化影响挺大：以前 webpack 恨不得把所有东西打成一个 bundle.js，HTTP/2 下更鼓励按路由、按依赖拆成多个 chunk。改一个页面的代码只让对应的小 chunk 缓存失效，其他 chunk 缓存照旧，命中率高很多。多个小文件并行下载在 HTTP/2 下几乎没有额外连接成本，这是和 HTTP/1.1 完全相反的优化方向。

头部压缩

HTTP 请求里有很多重复头：

HTTP/2 使用头部压缩，减少重复传输。

这对接口请求多的页面有帮助，但不要因此无节制塞很多 Cookie。Cookie 仍然会影响请求体积和安全边界。

HTTP/2 的头部压缩用的是 HPACK 算法，它的思路是维护一张动态表：同一个连接上第一次发 User-Agent: ... 时完整传一遍，之后再发同样的头，只传一个索引号。对于一个页面里几十上百个请求、每个都带着一大坨重复的 Cookie 和 UA 的场景，省下来的字节相当可观。HTTP/1.1 里这些头是每个请求都明文重发的，纯浪费。

虽然 HPACK 把重复头压得很狠，但我还是会控制 Cookie 大小，原因有几个：动态表第一次还是要全量传一次；Cookie 会跟着每个同域请求发出去，包括那些根本用不到它的静态资源请求；过大的 Cookie 也容易撞到服务端的 header 大小限制（比如 Nginx 的 large_client_header_buffers，超了直接报 400 Request Header Or Cookie Too Large，这个错我线上见过）。所以“反正会压缩”不能成为往 Cookie 里乱塞东西的理由。静态资源域名最好做到无 Cookie。

Server Push 要谨慎

HTTP/2 支持 Server Push，服务端可以主动推资源。

听起来很美，但实际使用要谨慎。推错资源会浪费带宽，浏览器缓存状态也不容易判断。

很多项目里，与其依赖 Server Push，不如把关键资源 preload 清楚：

优化要能解释，不要为了新特性硬上。

我自己试过 Server Push，最后放弃了，踩到几个实际问题。一是它不看浏览器缓存——服务端不知道客户端已经缓存了这个资源，照推不误，第二次访问就是纯浪费带宽，而 preload 配合正常缓存机制能避免这点。二是推送时机和优先级很难调，推早了占用了首屏 HTML 本该用的带宽，反而拖慢首屏。三是各家 CDN、Nginx 对 push 的支持和配置方式不一致，调起来很折腾。

后来证明 Server Push 在整个行业都没真正流行起来，preload / prefetch 这套声明式的资源提示更可控、更好理解：

preload 是“这个资源当前页马上要用，提前下”，prefetch 是“下个页面可能要用，空闲时下”。这两个我用得很顺手，效果可解释、可度量，比 Server Push 那种“服务端替你做主”的方式靠谱多了。

前端资源策略怎么变

HTTP/2 下，不必再为了减少请求数把所有代码合成一个包。

更合理的是：

  • 首屏代码保持小
  • 路由按需加载
  • 大依赖单独拆分
  • 静态资源带 hash 长缓存
  • HTML 入口短缓存

请求数不是唯一指标。资源是否阻塞首屏、缓存是否稳定、包体是否过大，都要一起看。

讲讲 hash 长缓存这套，因为它和拆包是配套的。静态资源文件名带上内容 hash，配上长 Cache-Control：

webpack 里对应的是 [contenthash]：

逻辑是：内容不变 hash 不变，浏览器一直用缓存（一年都不用再请求）；内容一变 hash 变，文件名就变成新的，HTML 里引用的地址跟着变，浏览器自然去拉新文件。HTML 入口本身不能长缓存，否则改了代码用户拿到的还是旧 HTML、指向旧资源，整个长缓存链就断了。

注意 [contenthash] 和 [hash]、[chunkhash] 不一样：[hash] 是整次构建一个 hash，改任何文件所有资源 hash 全变，长缓存等于白做；[chunkhash] 按 chunk 算，比 [hash] 好但样式抽出来后还是容易牵连；[contenthash] 按文件内容算，粒度最细，是做长缓存该用的那个。这个区别我专门踩过坑——一开始用了 [hash]，发现每次发版用户所有资源缓存全失效，白瞎了长缓存配置。

HTTP/2 不是性能万能药

如果 JS 包本身很大，HTTP/2 也救不了解析和执行成本。

如果图片没压缩，传输仍然慢。

如果接口串行，网络协议再好也会被业务流程拖慢。

所以排查性能时，还是要看 Network 和 Performance，确认瓶颈在哪里。

我判断 HTTP/2 到底有没有生效、有没有带来收益，一般这么看：Network 面板右键调出 Protocol 列，HTTP/2 的请求会显示 h2（HTTP/1.1 显示 http/1.1）；再看瀑布图里同域名的资源是不是大致同时开始，而不是 6 个一批阶梯式排队。如果开了 HTTP/2 但瀑布图还是阶梯状，那多半是没真正生效，或者资源被拆到了多个域名各自建连接。

还有个常被忽略的点：HTTP/2 是端到端的，中间任何一段降级都会回退。比如浏览器到 CDN 走 h2，但 CDN 回源到你的源站还是 HTTP/1.1，那回源那段照样有 1.1 的限制。排查时要看清是哪一段的协议。性能这事没有“配了就万事大吉”，每个环节都得拿数据确认。

小结

HTTP/2 通过多路复用、头部压缩改善资源传输效率，也改变了一部分前端资源优化思路。

面试问 HTTP/2，项目里更要知道：不要机械合并所有资源，也不要以为用了 HTTP/2 就不用管包体。协议能力变强了，资源拆分和缓存策略反而更需要细分。

我自己的总结是：HTTP/1.1 时代的几条优化在 HTTP/2 下要重新评估——域名拆分从优化变成了负优化（该收敛回单域名），过度合并 bundle 从优化变成了缓存杀手（该合理拆 chunk），雪碧图的必要性下降（小图标并发下载成本很低，不过雪碧图还有别的考量）。但有些事永远不变：包体大就是慢、图片不压缩就是慢、接口串行就是慢，这些是协议救不了的。协议是地基，地基好了，上面的房子还得自己好好盖。
