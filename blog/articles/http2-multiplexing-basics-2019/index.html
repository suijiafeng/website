HTTP/2 基础：多路复用为什么能改善页面加载

2019-11-02
请求与异步性能与缓存

前端性能优化里，资源加载一直是大头。

以前我们常做合并 JS、合并 CSS、雪碧图、域名拆分，很多优化都是围绕 HTTP/1.1 的限制来的。HTTP/2 普及以后，一些思路开始变化。不是说以前的经验都没用了，而是要知道网络层能力变了，资源组织方式也要跟着重新判断。

HTTP/1.1 的连接限制

浏览器对同一个域名的并发连接数有限。

如果页面有很多资源：

请求会排队。前面的请求没完成，后面的请求可能要等。

所以大家会做：

  • 文件合并
  • 图片雪碧图
  • 多域名分发静态资源

这些手段的目的，都是减少请求数或提高并发。

队头阻塞

HTTP/1.1 里，一个连接上的请求响应有顺序限制。前面的响应慢，后面的响应也可能被影响。

这就是常说的队头阻塞。

页面加载时，如果某个大资源慢，会拖累后续资源。

HTTP/2 多路复用

HTTP/2 可以在一个 TCP 连接里并发传输多个请求和响应。

简单理解：多个资源不必排成单列，一个连接里可以同时传。

这能减少连接数量，也能改善资源排队问题。

对前端来说，资源不一定非要合成一个巨大文件。合理拆分反而更利于缓存和按需加载。

头部压缩

HTTP 请求里有很多重复头：

HTTP/2 使用头部压缩，减少重复传输。

这对接口请求多的页面有帮助，但不要因此无节制塞很多 Cookie。Cookie 仍然会影响请求体积和安全边界。

Server Push 要谨慎

HTTP/2 支持 Server Push，服务端可以主动推资源。

听起来很美，但实际使用要谨慎。推错资源会浪费带宽，浏览器缓存状态也不容易判断。

很多项目里，与其依赖 Server Push，不如把关键资源 preload 清楚：

优化要能解释，不要为了新特性硬上。

前端资源策略怎么变

HTTP/2 下，不必再为了减少请求数把所有代码合成一个包。

更合理的是：

  • 首屏代码保持小
  • 路由按需加载
  • 大依赖单独拆分
  • 静态资源带 hash 长缓存
  • HTML 入口短缓存

请求数不是唯一指标。资源是否阻塞首屏、缓存是否稳定、包体是否过大，都要一起看。

HTTP/2 不是性能万能药

如果 JS 包本身很大，HTTP/2 也救不了解析和执行成本。

如果图片没压缩，传输仍然慢。

如果接口串行，网络协议再好也会被业务流程拖慢。

所以排查性能时，还是要看 Network 和 Performance，确认瓶颈在哪里。

小结

HTTP/2 通过多路复用、头部压缩改善资源传输效率，也改变了一部分前端资源优化思路。

面试问 HTTP/2，项目里更要知道：不要机械合并所有资源，也不要以为用了 HTTP/2 就不用管包体。协议能力变强了，资源拆分和缓存策略反而更需要细分。
