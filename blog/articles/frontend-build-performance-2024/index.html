前端构建速度优化：别只怪打包工具慢

2024-08-23
前端基础构建与模块化性能与缓存

构建慢很容易被归因到工具。

Webpack 慢，就换 Vite；Vite 慢，就等 Rolldown；CI 慢，就加机器。工具升级当然有价值，但很多项目真正的问题不是工具本身，而是依赖太重、类型检查太散、代码生成太粗、缓存没用起来。

我遇到过一个项目，本地冷启动要几十秒，大家一直说“Webpack 不行”。后来分析发现，首页直接 import 了整个图标库、整个日期库、多语言包和一堆后台页面组件。换工具能快一点，但不解决依赖边界，迟早还会慢回来。

构建速度优化要先找瓶颈，不要先换信仰。

先分清慢在哪里

“构建慢”至少可能慢在几处：

  • 安装依赖慢
  • 开发服务器启动慢
  • 首次页面加载慢
  • 热更新慢
  • 类型检查慢
  • 生产打包慢
  • CI 上传下载缓存慢

每一种对应的解法都不一样。

热更新慢，可能是模块依赖链太大；生产打包慢，可能是压缩和 sourcemap；类型检查慢，可能是 TS 项目边界；安装慢，可能是依赖和 lockfile。

依赖是最常见的隐形成本

依赖越多，构建工具要解析、转换、预构建的东西越多。

几个常见问题：

  • 引入整个工具库，只用一个函数
  • 图标库按包全量导入
  • 日期库 locale 全量打进来
  • 编辑器、图表、地图在首屏同步加载
  • 多个版本的同一依赖并存

TypeScript 要有项目边界

TypeScript 项目大了以后，类型检查会变慢。

常见问题是所有代码都在一个 tsconfig 里，任何改动都可能牵动全量检查。Monorepo 里更明显。

可以考虑使用 project references，把项目拆成有边界的包：

这样 TypeScript 可以复用构建信息，包之间通过声明文件通信。

还有一个现实建议：开发服务器的转译和类型检查可以分开。很多工具在 dev 阶段用 esbuild 或 swc 快速转译，类型检查放到单独进程或 CI。这样热更新不会被类型检查卡住。

但不要因此取消类型检查。只是把它从“每次保存都阻塞页面刷新”改成“后台持续检查或提交前检查”。

缓存要真的命中

CI 里最常见的浪费，是每次都重新安装、重新构建、重新生成。

应该缓存：

  • 包管理器缓存
  • node_modules 或 pnpm store
  • 构建工具缓存
  • TypeScript .tsbuildinfo
  • Next.js / Vite / Babel 缓存

但缓存不是配了就生效。要看命中率和 key。

如果 cache key 每次都变，等于没缓存。如果 key 太宽，可能用到错误缓存。常见做法是用 lockfile 作为依赖缓存 key：

构建缓存还要注意环境变量。不同环境变量可能影响产物，如果缓存没区分，可能引入很隐蔽的问题。

代码生成不要每次全量跑

很多项目有接口类型生成、路由生成、图标生成、国际化生成。

如果每次 dev 启动都全量生成，速度会很慢。更好的方式是：

  • 输入文件没变就跳过
  • 生成结果提交到仓库或作为缓存
  • watch 模式只处理变化文件
  • CI 里校验生成结果是否最新

比如接口类型可以在契约变化时生成，而不是每次启动都拉一次远程 Swagger。远程服务慢或不稳定，还会拖垮本地开发。

sourcemap 和压缩很贵

生产构建里，压缩和 sourcemap 往往占不少时间。

压缩器也会影响速度。Terser 压缩效果稳但慢，esbuild 压缩快但某些压缩效果不同。选哪个要看项目要求，不要盲目追求最小体积。

我的排查顺序

构建慢时，我会按这个顺序查：

  1. 量化安装、启动、热更新、类型检查、生产构建分别耗时
  2. 分析依赖体积和重复依赖
  3. 懒加载首屏不需要的重型模块
  4. 检查 TypeScript 项目边界和类型检查方式
  5. 配 CI 和本地缓存，并确认命中率
  6. 优化代码生成流程
  7. 调整 sourcemap 和压缩策略
  8. 最后再考虑工具迁移

工具升级是手段，不是诊断。构建速度真正变快，通常来自依赖变少、边界变清楚、缓存能命中、无效工作被跳过。
