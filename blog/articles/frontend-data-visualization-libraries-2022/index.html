前端数据可视化库怎么选：我后来不再只看图表类型

2022-05-10
前端基础数据可视化与存储

前端做数据可视化时，最常见的问题不是“有没有库”，而是“该选哪个库”。

图表库很多，ECharts、D3、Chart.js、Recharts、Plotly、deck.gl 都能做可视化，但它们适合的场景并不一样。

选型时我不会先问“哪个库最好”，而是先问几个更具体的问题：图表是否常规、数据量多大、交互有多复杂、团队用什么框架、后续谁维护、是否需要导出图片或服务端渲染。问题越具体，选型越不容易跑偏。

我第一次真正被可视化选型教育，是在一个运营看板项目里。最开始大家只问“用 ECharts 还是 D3”，后来发现真正麻烦的不是画图，而是指标口径、筛选联动、数据量、导出和权限。图表库只是最后一层，前面的数据建模和交互设计没想清楚，换什么库都会难受。

先看需求复杂度

如果只是常见业务图表，比如折线图、柱状图、饼图、地图、仪表盘，优先考虑成熟图表库。

例如 ECharts：

  • 图表类型丰富
  • 中文资料多
  • 配置项完整
  • 适合后台系统和数据看板

对大多数业务项目来说，ECharts 是很稳的选择。

ECharts 的优势是完整。折线、柱状、饼图、雷达、热力图、地图、关系图、仪表盘，这些常见需求基本都有现成能力。它的配置项很多，刚开始看会觉得复杂，但对业务看板来说，这反而是一种优势：大多数需求不用从底层图形开始写。

这类配置式写法很适合中后台，因为需求通常是“把数据准确展示出来，并提供常见交互”，不是每个图都要重新设计视觉语法。

在中后台里，ECharts 还有一个很实际的优势：产品和业务同学能理解它能做什么。折线、柱状、饼图、地图、仪表盘这些模式都很成熟，沟通成本低。很多看板不是为了炫技，而是为了让业务快速判断异常、趋势和结构。

Chart.js 更轻量

Chart.js 比较适合简单图表。

它 API 相对轻，默认效果也不错，适合：

  • 小型项目
  • 简单报表
  • 内容页中的基础图表

如果图表交互非常复杂，或者需要高度定制，Chart.js 可能会不够灵活。

Chart.js 的一个优点是上手轻，适合内容型页面或小型报表。比如在一篇文章里插入一个趋势图，或者在个人项目里展示统计数据，它不会显得太重。

但如果项目后期会不断增加复杂图表、联动筛选、自定义 tooltip、自定义图例，就要提前评估扩展成本。轻量库的边界通常也更早出现。

D3 更像工具箱

D3 不只是图表库，更像一套数据驱动文档的工具。

它给你的自由度很高，也意味着你需要写更多代码。

适合 D3 的场景包括：

  • 高度定制图表
  • 非常规可视化
  • 复杂交互
  • 数据和图形映射关系特殊

如果只是普通柱状图，用 D3 可能有点重。

D3 的核心价值在于数据到图形的映射能力。比例尺、坐标轴、布局、力导向、层级结构，这些能力很适合构建非常规图表。

但自由度意味着更多工程责任。你需要自己处理 DOM 更新、交互状态、动画、坐标计算、响应式布局，甚至可访问性。团队如果没有足够经验，D3 项目很容易变成只有作者能维护。

我会把 D3 放在“需要定制图形语法”的场景，而不是“我想画个图”的默认选择。

我现在会特别警惕一种情况：明明只是常规业务图表，却因为想要“更自由”选了 D3。自由不是免费的，你要自己承担布局、交互、性能和维护。除非图表真的需要特殊视觉表达，否则成熟配置型库通常更适合业务团队。

React 项目可以看 Recharts 和 Nivo

React 项目里，可以考虑组件化图表库。

例如 Recharts 和 Nivo，它们更符合 React 组件使用习惯。

如果团队希望图表也以组件方式组织，这类库会比直接操作 DOM 的方案更自然。

大规模地理数据看 WebGL 方案

如果要渲染大量点、线、面，尤其是地图和地理数据，就要关注性能。

这时 deck.gl、kepler.gl 这类 WebGL 方案更适合。

它们更擅长处理大规模数据渲染和复杂地图交互。

这里涉及一个底层选择：SVG、Canvas 还是 WebGL。

  • SVG 适合元素数量不太大、需要 DOM 级交互和样式控制的图表
  • Canvas 适合较大量数据点和更高绘制性能
  • WebGL 适合大规模点线面、三维或复杂地理可视化

不是 WebGL 一定更高级，而是它解决的问题不一样。普通后台折线图用 WebGL 可能是过度设计；几十万点的地图散点如果用 SVG，就可能卡得很明显。

数据规模比图表类型更重要

很多选型失败不是因为库不好，而是低估了数据规模。

一千条数据、十万条数据、一百万条数据，对前端图表来说是完全不同的问题。数据量上来后，除了渲染，还要考虑：

  • 是否需要后端聚合
  • 是否需要抽样或降采样
  • 是否需要分页或虚拟滚动
  • 是否需要增量更新
  • tooltip 和 hover 是否还能实时响应

比如折线图展示一年每分钟的监控数据，直接把几十万点都画出来，用户未必看得更清楚，性能也会变差。更合理的做法可能是按屏幕宽度降采样，或者按时间范围动态请求聚合数据。

我后来会在接口层就问清楚三件事：

如果用户只是看趋势，把几十万点原样扔给前端没有意义。后端按分钟、小时或天聚合，前端按视口宽度做降采样，通常比单纯换 WebGL 图表库更有效。

交互能力也要提前问清楚

图表不只是画出来，还要能用。

常见交互包括：

  • tooltip
  • legend 开关
  • 缩放和平移
  • 框选
  • 图表联动
  • 点击下钻
  • 导出图片

如果只是静态展示，很多库都能胜任。如果要多个图表联动筛选，或者点击地图区域下钻到城市，再联动右侧表格，就要选成熟度更高、事件系统更完整的方案。

这类需求最好在选型前就问清楚。否则前期用轻量库快速做完，后期每加一个交互都在补底层能力。

数据处理不要都塞进图表组件

图表组件最好接收已经整理好的数据，而不是在渲染时做大量清洗、分组、排序。

数据转换层独立出来有几个好处：

  • 更容易测试
  • 更容易复用
  • 图表组件更清楚
  • 后续换库时影响更小

尤其是接口数据不稳定时，统一转换层还能处理空值、异常值、单位换算和字段兼容。图表库负责展示，不应该承担全部业务数据清洗。

指标口径比图表样式更重要

做业务看板时，我现在会先确认指标口径。

比如“转化率”到底是按访问人数算，还是按访问次数算？“销售额”是否包含退款？“今日数据”按自然日还是业务日？这些问题如果不明确，图表再漂亮也没有价值。

可访问性和空状态

数据可视化经常忽略可访问性。图表颜色不能只靠红绿区分，关键数据最好有文字说明或表格补充。

如果图表加载失败、没有数据、数据过少，也要有明确状态：

不要让用户面对一个空白图表猜原因。对业务系统来说，空状态、错误状态、加载状态和图表本身一样重要。

导出也要提前考虑。很多中后台图表最后都会被放进周报或汇报材料里，所以要问清楚是否需要导出图片、导出 Excel、保留筛选条件和时间范围。导出能力如果后期再补，常常会牵涉图表尺寸、主题色、数据精度和权限。

选择可视化库时，不要只看流行度。

普通业务图表看 ECharts，轻量图表看 Chart.js，高度定制看 D3，React 组件化看 Recharts/Nivo，大规模地理可视化看 deck.gl。先明确图表类型和数据规模，选型会清楚很多。

我现在做可视化选型，会把问题拆成四层：图表类型、数据规模、交互复杂度、团队维护成本。库只是最后的答案，前面的约束条件才真正决定它适不适合。
