WebAssembly 3.0 我会怎么判断该不该用：别把它当成更快的 JS

2025-09-20
前端基础JavaScript性能与缓存

判断该不该上 WebAssembly，我现在的第一个动作不是看它能跑多快，而是先把这个任务归个类：它到底是计算密集，还是只是"看起来重"。

这两类需求做出来的决策天差地别。前者 Wasm 可能真能帮上忙，后者上了 Wasm 只会白白多背一套构建、加载和调试成本。

会形成这个习惯，是被一段真实的返工逼出来的。

年初接手一个图片批处理工具，前一版的实现里，缩放、滤镜、格式转换整条流程都被搬到了 Rust + Wasm 上，本地跑分确实漂亮。但线上指标反而退步：首屏多加载了 2.8MB 的 wasm，移动端用户在 4G 下白屏时间长了将近一秒，而真正用到批处理的用户不到 5%。

也就是说，95% 的人为了一个用不上的功能，先吃了一秒白屏。这之后"该不该上 Wasm"对我来说就成了一个要先过判断标准的问题，而不是看谁跑分高。

先把"更快的 JS"这个误解摘掉

Wasm 不是用来替代 JavaScript 的，它更像给浏览器补了一条高性能执行通道，让 C、C++、Rust 这类语言编译后的代码也能在 Web 里跑。

关键区别在于：它擅长的是"纯计算"，不是"让页面整体更快"。一个按钮点击更跟手、一个列表滚动更顺，这些跟 Wasm 基本没关系——它们慢在渲染、状态和网络，不在计算。

我踩过一个"看起来该上其实不该上"的反例，正好说明这点。

有个需求是给一万行表格做关键字高亮匹配，听着像大规模数据处理，第一反应想上 Wasm。结果用 Chrome Performance 一录，耗时根本不在匹配，而在每次匹配后触发的 DOM 重排——把匹配逻辑搬到 Wasm 一点用都没有，最后靠虚拟滚动加批量 DOM 更新解决的。

从那以后我给自己定了条规矩：怀疑某段 JS 慢，先用火焰图定位，确认热点真的落在纯计算上，再谈 Wasm，否则很可能优化了一个根本不是瓶颈的地方。

所以我理解 Wasm 的方式很朴素：一个任务本来就不适合 JavaScript 做，或者团队已经有一套经过验证的 Rust/C++ 算法，Wasm 才开始变得有意义。

图片压缩、在线音频编辑、浏览器里的 PDF 处理、CAD 查看器、数据可视化计算，这些场景有个共同点——核心压力不在 UI，而在大量计算、二进制数据处理或跨平台算法复用。

3.0 这次实在的几个点

说回 WebAssembly 3.0 本身。抛开规格文档里那些底层措辞，对前端真正有影响的是这么几条：

GC 提案落地，Rust/C++ 之外，Kotlin、Java、Dart 这类带 GC 的语言编译产物体积能明显变小；memory64 突破了原来 4GB 的地址空间限制，处理超大文件时不再动辄撞上限；再加上更完整的异常处理和尾调用。

这几条里我最关注 GC 那条线。

因为它直接决定"某个语言能不能以合理体积编译到浏览器"。

以前带 GC 的语言编译到 Wasm，得把整个运行时的垃圾回收器也塞进产物里，体积很难看；GC 提案让 Wasm 直接复用宿主的回收能力，产物一下就轻了。

这意味着以后能进浏览器的语言更多，但对我这种做业务的人来说，重点还是那句——体积轻了不等于该上，任务不对口，再轻也是负担。

它解决的不是 UI 问题，所以要划清分工

Wasm 不负责声明组件，也不直接替代 Vue、React。现实的分工是：前端框架继续管页面状态、用户交互、进度和结果展示，把性能敏感的核心算法交给 Wasm。

React/Vue/Svelte 那一侧解析用户意图、驱动界面；Wasm 那一侧解析二进制文件、执行图像或几何计算、返回结构化结果。两边各干各擅长的事。

但分工清楚不等于就没成本，JS 和 Wasm 之间的通信本身要算账。

最常见的错误是把一个很小的函数在两边来回调几千次，那开销可能还不如直接写 JS。更合适的是把数据整理成批量输入，一次交给 Wasm，再一次拿回结果：

这类边界清楚的调用，比"每个像素都从 JS 调一次 Wasm"现实得多。设计接口的时候我会刻意让跨边界的调用次数尽量少、每次搬运的数据尽量成块，把频繁的小交互留在同一侧内部消化。

为什么跨边界这么敏感，值得多说一句。

Wasm 的线性内存和 JS 的堆是两块独立的地址空间，字符串、对象这类结构没法直接互通。你从 JS 传一个字符串给 Rust，中间那层胶水代码得先把它编码成字节、写进 Wasm 内存、再在 Rust 侧读出来，返回时又反着来一遍。

用 wasm-bindgen 这类工具时，这些编解码是自动生成的，写起来无感，但它不是零成本。

所以真正吃性能的往往不是算法本身，而是你在边界上来回倒腾数据的次数。我的经验是：能用一个大的 Uint8Array 一次带过去的，绝不拆成一百个小调用。

工具链是决定"敢不敢用"的一半

技术选型除了看能力，还要看进项目后好不好带。

这两年 Rust 到 Wasm 这条链路已经比早期顺不少：wasm-pack 负责编译打包，wasm-bindgen 生成 JS 和 Rust 之间的类型绑定，Vite 侧也有现成插件能把 .wasm 当模块直接 import，不用再手写一堆 WebAssembly.instantiate 的样板。

但顺归顺，我仍然会盯几件事：产物体积能不能压下来（wasm-opt 这一步别省，它经常能砍掉可观的体积）、source map 有没有配好否则线上崩了两眼一抹黑、以及 CI 里 Rust 工具链会不会把构建时间拖长。

这些都是"运行时性能"之外的隐性开销，评估时一并算进去，才不会出现"跑分很香、上线才发现构建慢了三分钟、包大了一截"的尴尬。

该和 Worker 一起考虑

很多适合 Wasm 的任务，本身也是不该阻塞主线程的任务。

图片压缩、PDF 解析、音频分析、几何计算，即使用 Wasm 跑得更快，你把它塞在主线程里连续执行，用户照样能感到卡顿——因为它在算的时候，主线程没法响应点击、没法刷新界面。

跨语言复用是它另一个实在价值

很多业务的核心算法可能已经存在于别的语言里——图形图像、工业软件、音视频工具、游戏、科学计算这些领域尤其明显。

能编译到 Wasm，就不必把这些经过多年验证的代码整个重写成 JavaScript，重写本身就是巨大的风险源。

2025 年再看 Wasm，还有一条值得关注的线是组件模型和 WASI。它们让 Wasm 不只局限在浏览器里，也逐渐进入边缘计算、插件系统和服务端沙箱。

对前端来说这不一定马上改变每天写页面的方式，但会影响一些"跨端核心能力"的设计思路。

一个 Markdown 解析器、图片处理核心、规则引擎，如果能以 Wasm 形式被浏览器、Node、边缘函数甚至桌面应用复用，团队就不必维护多套实现。这种价值在普通页面里不明显，在工具型产品里非常实在。

不过我对这条线的态度是观望多于押注。

组件模型的规格和工具链这一年还在快速变，我只敢在内部工具里试着把一个纯函数式的核心逻辑编成 Wasm 组件跑跑看，还没到敢在对外产品里当基础设施用的程度。判断新东西该不该进生产，我更看它的工具链稳不稳定，而不是它规格上有多先进。

使用成本也要摊开算

Wasm 不是银弹。如果只是普通表单和列表页面，引入它反而让项目变复杂。除了前面说的通信开销，还有几个容易被低估的成本。

第一是加载成本。

Wasm 文件也是资源，体积、缓存、首屏时机都要考虑。为了一个很少使用的功能把几 MB 的 Wasm 放进首屏，用户感受到的不是性能提升，而是页面变慢——开头那个 2.8MB 的教训就是这么来的。真要用，我一般会把 Wasm 模块做成按需加载，用户真正进到批处理界面才去拉，别让它压在首屏。

第二是调试成本。

纯 JavaScript 出问题，可以直接断点、看对象、改代码热更新。Wasm 链路里可能牵扯 Rust/C++ 源码、编译产物、胶水代码、source map 和内存视图，排查门槛高很多。一个数组越界，在 JS 里是一目了然的报错，在 Wasm 里可能就是一段内存被悄悄写坏、现象飘忽的诡异 bug。

我自己排查 Wasm 问题的顺序，也和纯 JS 不太一样。

首先会尽量把复现搬到 Wasm 源语言的原生环境里。

同样一段 Rust 逻辑，在本地跑 cargo test 用原生调试器排查，比在浏览器里隔着几层胶水看内存视图高效得多，确认逻辑没问题了再回到浏览器验证边界。

其次会在跨边界处加日志：进 Wasm 前把输入 dump 一份，出来后把结果 dump 一份。

很多 bug 其实出在编解码那一层，数据在进出边界时就已经变了形，不是算法算错了。

Chrome DevTools 这两年对 Wasm 的支持也在补齐，配好 DWARF 调试信息后能直接在 Rust 源码上打断点，但这套链路要跑通本身也有配置成本，团队得有人愿意去趟这条路。

第三是团队成本。

如果只有一个人懂 Rust 或 C++，那这块能力很容易变成维护风险——那个人一忙或者一走，整块代码就没人敢碰。技术选型不能只看运行时性能，也要看团队能不能长期接住。

数据传输和内存是隐形的账本

Wasm 项目里，很多性能损耗不在计算本身，而在数据搬运。

JS 和 Wasm 之间传大块二进制时，要盯着复制成本、内存峰值和释放时机。图片、视频、PDF 这类文件动不动几十 MB，一次处理里如果同时保留原始文件、Wasm 内存副本、处理结果和预览对象，页面内存很容易飙上去，移动端直接崩标签页。

所以动手前我会先问自己几个问题：输入数据能不能用 ArrayBuffer 批量传，而不是零散地一次次拷；能不能避免多次复制；大文件要不要分块处理，边处理边释放，而不是一口气全读进内存；处理完以后引用是不是及时断掉，让内存能被回收；以及大文件是不是该显示进度、允许中途取消。

这些问题不解决，Wasm 算得再快，用户也可能遇到内存高、标签卡死、移动端崩溃。

这里 memory64 反而要小心用。

它把地址空间上限抬高了，听着是好事，但也容易让人放松警惕——地址空间大不等于用户设备内存大，你能 malloc 出来不代表手机扛得住。上限提高解决的是"想用超过 4GB"的极端场景，日常该做的分块和释放一样不能省。

还有个容易忽略的点是 Wasm 的线性内存只增不减这个特性。

默认情况下，WebAssembly.Memory 可以 grow，但很多运行时不会把已经增长的内存还给系统。也就是说，你处理一个 200MB 的大文件时把内存撑到很高，处理完之后即使把 Wasm 侧的数据结构都释放了，那块已经向系统要来的内存也未必会退回去，整个标签页的内存水位就一直停在高位。

做长时间运行的工具型页面时这点很关键——用户连续处理十几个大文件，页面内存台阶式往上走，最后 OOM。

我的对策是：大文件处理这种高峰内存的活，宁可放到独立的 Worker 里，处理完直接 worker.terminate() 把整个 Worker 连同它的内存一起销毁，下次要用再新建，比指望 Wasm 内部乖乖释放可靠得多。

落地前的一套判断标准

真到要拍板，我会问四个问题：这个任务是不是计算密集型；JavaScript 版本是否已经成为明确瓶颈；是否有成熟的非 JS 实现可以复用；引入 Wasm 后加载、调试和部署成本是否可接受。

如果只有第一个问题答案是"可能是"，通常还不够。

前端性能优化很容易被"更底层"吸引，但很多页面真正慢在网络、渲染、状态管理或不必要的重渲染，Wasm 只能解决它擅长的那一小块。

四个问题之外我还会加一条基准测试原则：一定要用真实数据测，别拿一个小 demo 文件证明 Wasm 快就上。

真实业务里文件大小、格式复杂度、设备性能、浏览器内存限制都会影响结果。我一般会准备几组样本：小文件验证启动和基础流程，中等文件对齐日常用户场景，大文件专门验证内存、进度和取消，再加一组异常文件验证错误处理和兜底。这几种场景都跑过，才知道 Wasm 到手的是收益，还是又一个新风险。

而且测的时候要连"加载 wasm 模块本身"的时间一起算进去，不能只测那个纯计算函数。

用户等的是端到端——从点下按钮到看到结果，中间包括拉取 wasm、实例化、传数据、算、传回来。我会用 performance.now() 把几段分开量：

分开量之后经常会发现一个反直觉的现象：纯计算 Wasm 确实比 JS 快好几倍，但加上启动那几百毫秒，对小文件反而整体更慢——因为 JS 版本没有那个固定的启动税。

这也是为什么我强调按文件大小分档测：小文件很可能 JS 直接做就是最优解，Wasm 的优势要到数据量足够大、把启动成本摊薄之后才显出来。

这个"盈亏平衡点"每个场景都不一样，只能自己拿真实数据量出来，不能拍脑袋。

图片批处理那个工具最后是怎么收的？

我没有全盘推翻 Rust + Wasm，而是把它拆成按需加载，只在用户真正进入批处理界面时才拉起来，首屏恢复干净；同时补齐了 Worker、进度和取消。计算这条通道确实是 Wasm 更合适，错的从来不是技术选型本身，是把它塞进了所有人的首屏。

延伸阅读

想再往深走，推荐看 MDN 的 WebAssembly 文档、WebAssembly 官方站点关于 component model 的介绍、WASI 相关资料，以及 Rust and WebAssembly Book。

它们能帮你从浏览器 API、跨语言编译和运行时边界三个角度理解 Wasm，而不是只把它当成"更快的 JavaScript"。

WebAssembly 3.0 让浏览器的高性能能力继续往前推，但它的边界一直没变：UI 交给前端框架，重计算才是它的主场。判断该不该用它，靠的还是那套顺序——先确认是不是纯计算瓶颈，再把加载、调试、内存、团队维护这些隐藏成本一项项摊到桌面上，最后才轮到看跑分。
