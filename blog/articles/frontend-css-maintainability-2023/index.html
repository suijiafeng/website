CSS 可维护性实践：样式失控通常不是技术问题，而是边界问题

2023-09-14
前端基础构建与模块化

前端项目里，CSS 经常是最容易被低估、也最容易失控的一层。

功能开发阶段，大家通常更关注接口、状态、交互、性能；样式经常被视为“最后补一下”。结果项目做久了以后，最让人不敢动的反而是样式文件。

CSS 在项目里经常出问题，表面看起来像“技术选型不对”，其实更常见的原因是边界不清。

我以前接手过一个样式文件接近一万行的后台项目，最明显的感受不是“写得丑”，而是没人敢删。一个 .title 可能同时影响首页卡片、弹窗标题和某个历史活动页。每次改样式都像拆线头，怕拉动一整片。那次之后我才真正相信：CSS 可维护性首先是边界问题。

样式为什么这么容易变脏

因为 CSS 默认就是全局生效、相互影响的。

这意味着只要你没有主动管理边界，就很容易出现：

  • 修改一个类名影响多个页面
  • 提高优先级去覆盖旧规则
  • 新样式不断叠加补丁
  • 组件样式和页面布局样式混在一起
  • 不知道某段样式是否还能删除

写的时候都合理，叠久了就开始变乱。

样式的职责要分层

一个更稳定的方式，是把样式按职责拆开，而不是全部混在一起。

常见可以分为：

  • 基础样式
  • 组件样式
  • 页面布局样式
  • 状态样式
  • 工具类样式

基础样式负责重置、字体、颜色变量、间距变量。组件样式负责组件本身的外观。页面样式负责页面结构和布局，不应该直接侵入组件内部细节。

删除样式也需要纪律

CSS 难维护的另一个原因是“不敢删”。项目里经常有很多看似没用的规则，但没人确定是否还被某个页面依赖。

降低这类风险的方法包括：

  • 组件样式跟组件文件放在一起
  • 命名带有明确组件前缀
  • 避免全局通用类名
  • 删除组件时同步删除样式
  • 评审时关注新增全局样式

工具能帮助发现一部分未使用样式，但动态类名、服务端渲染和 CMS 内容都会增加判断难度。最根本的还是减少不必要的全局影响。

删除样式前我通常会做三件事：先搜类名引用，再跑关键页面截图或手工检查，最后把删除和功能改动分开提交。样式删除最怕混在大 PR 里，review 的人很难判断这段 CSS 是不是还被某个角落依赖。

页面越多，覆盖越散。升级组件库时，你不知道哪些选择器会失效。

我更倾向于把组件库覆盖集中在一个明确目录里，比如 styles/vendor/element-plus.css，并且只覆盖团队认可的统一规则。页面级特殊覆盖要少，必须写时也要说明原因。第三方样式越集中，升级和排查越容易。

我现在看一个项目的 CSS 健不健康，会先问三个问题：这段样式属于谁，影响谁，能不能删。

回答不上来，就说明边界已经开始糊了。Tailwind、CSS Modules、Sass、CSS-in-JS 都只是工具，它们能帮你收敛一部分问题，也能在没有边界意识时写出另一种混乱。

真正要长期守住的是几条纪律：基础样式、组件样式、页面布局和状态样式各司其职；命名表达归属；页面不要随便侵入组件内部；第三方组件覆盖集中管理；删除样式和业务改动分开做。样式越能看出“属于谁、影响谁、能不能删”，项目就越容易维护。
