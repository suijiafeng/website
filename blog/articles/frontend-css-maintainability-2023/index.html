CSS 可维护性实践：样式失控通常不是技术问题，而是边界问题

2023-09-14
前端基础构建与模块化

前端项目里，CSS 经常是最容易被低估、也最容易失控的一层。

功能开发阶段，大家通常更关注接口、状态、交互、性能；样式经常被视为“最后补一下”。结果项目做久了以后，最让人不敢动的反而是样式文件。

CSS 在项目里经常出问题，表面看起来像“技术选型不对”，其实更常见的原因是边界不清。

样式为什么这么容易变脏

因为 CSS 默认就是全局生效、相互影响的。

这意味着只要你没有主动管理边界，就很容易出现：

  • 修改一个类名影响多个页面
  • 提高优先级去覆盖旧规则
  • 新样式不断叠加补丁
  • 组件样式和页面布局样式混在一起
  • 不知道某段样式是否还能删除

写的时候都合理，叠久了就开始变乱。

样式的职责要分层

一个更稳定的方式，是把样式按职责拆开，而不是全部混在一起。

常见可以分为：

  • 基础样式
  • 组件样式
  • 页面布局样式
  • 状态样式
  • 工具类样式

基础样式负责重置、字体、颜色变量、间距变量。组件样式负责组件本身的外观。页面样式负责页面结构和布局，不应该直接侵入组件内部细节。

删除样式也需要纪律

CSS 难维护的另一个原因是“不敢删”。项目里经常有很多看似没用的规则，但没人确定是否还被某个页面依赖。

降低这类风险的方法包括：

  • 组件样式跟组件文件放在一起
  • 命名带有明确组件前缀
  • 避免全局通用类名
  • 删除组件时同步删除样式
  • 评审时关注新增全局样式

工具能帮助发现一部分未使用样式，但动态类名、服务端渲染和 CMS 内容都会增加判断难度。最根本的还是减少不必要的全局影响。

小结

CSS 可维护性不是靠某个技术选型一次性解决的。Tailwind、CSS Modules、Sass、CSS-in-JS 都能写出好代码，也都能写乱。

真正关键的是边界：基础样式、组件样式、页面布局和状态样式各司其职；命名表达归属；页面不要侵入组件内部；覆盖要克制。样式越能看出“属于谁、影响谁、能不能删”，项目就越容易长期维护。
