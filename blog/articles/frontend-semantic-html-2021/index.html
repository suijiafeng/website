语义化 HTML 为什么重要：它不只是面试题，而是页面质量的基础

2021-08-12
前端基础

刚开始做前端时，不少人第一次接触“语义化 HTML”时，会把它理解成一个偏理论的问题。

因为在页面开发里常见的情况是里，似乎用一堆 div 也能把界面搭出来，看起来并不影响功能。

但只要项目稍微复杂一点，就会发现结构表达清楚和结构表达混乱，长期维护体验差别非常大。

什么叫语义化

语义化的核心不是标签多高级，而是让标签表达内容本身的含义。

例如：

  • 文章用 article
  • 页头用 header
  • 导航用 nav
  • 主要内容区用 main
  • 按钮用 button

这样做的价值，是让页面结构更容易被人和工具理解。

换句话说，HTML 不只是给 CSS 和 JavaScript 挂载的骨架，它本身也在描述页面内容。一个结构清楚的页面，即使暂时去掉样式，也应该能看出大致的信息层级。

我有过一个很直观的体会。有一次接手别人的项目，打开 Chrome DevTools 想找正文区域，结果整个 Elements 面板从头到尾都是 div，只能靠 class 名一层层往下点。后来我换了一个习惯：写完结构以后，用浏览器自带的 Accessibility 面板（DevTools 里的 Accessibility -> Full-page accessibility tree）看一眼生成的可访问性树。如果那棵树里只有一堆 generic 节点，说明结构语义基本是空的；如果能看到 banner、navigation、main、article 这些角色，说明标签用对了。这个检查只要十几秒，但能很快暴露问题。

为什么不能什么都用 div

div 本身没有错，它是一个通用容器。

问题在于，如果一个页面几乎所有地方都靠 div 组织，那结构信息就被大量丢失了。

你虽然看得见页面长什么样，但很难从 DOM 结构里直接判断：

  • 哪里是导航
  • 哪里是正文
  • 哪里是列表
  • 哪里是按钮

这会直接影响后续开发体验。

这里有个很容易踩的坑：section 不是 div 的语义替身，不要看到一块区域就无脑套 section。section 在规范里要求是有主题的内容分组，理想情况下应该带一个标题。如果一块区域只是为了布局或者根本没有标题，套 section 反而会在可访问性树里多出一堆没有名字的 region，读屏用户听到一连串"区，区，区"反而更乱。我的判断标准很简单：这块内容能不能用一句话给它起个小标题？能就用 section（并真的写上 h2/h3），不能就老老实实用 div。

在多人协作和长期维护里，这种清晰度非常重要。

语义化还会影响组件拆分。比如一个商品卡片，如果里面有标题、价格、操作按钮，就不应该只考虑视觉上怎么摆，而要先想它本质上是不是一个列表项、标题层级是否合理、按钮是否真的是按钮。

这里的 li 表示它属于一个列表，article 表示它是一块相对独立的内容，button 表示它会触发动作。以后无论是改样式、加埋点，还是做自动化测试，定位都会更清楚。

自动化测试这点我感受特别深。后来团队上了 Testing Library，它的查询 API 几乎是逼着你把结构写对的。比如 getByRole('button', { name: '加入购物车' })、getByRole('listitem')，这些查询直接读的就是可访问性角色。如果你当初图省事把按钮写成了可点击的 div，测试里就得退化成 getByTestId 或者 container.querySelector('.add-btn')，又脆又难读。结构写得语义化，测试用例往往不用任何额外的 data-testid 就能写出来，这是当初没料到的额外收益。

语义化和可访问性有很强关系

很多语义标签不只是“长得更好看”，它们还会影响辅助技术如何理解页面。

例如：

  • 读屏工具可以更清楚地识别结构
  • 表单控件能获得更合理的默认语义
  • 按钮和链接的行为边界更明确

这就是为什么语义化往往和可访问性一起被讨论。

可访问性不是只服务少数人的额外功能。键盘用户、读屏用户、临时无法使用鼠标的人，都会依赖这些结构信息。语义化做得好，浏览器和辅助技术能直接获得很多默认能力。

按钮和链接尤其容易用错

这是最常见的问题之一。

页面开发里常见的情况是会把一个可点击的 div 当按钮，也会把一个只执行动作的元素写成链接。这样虽然视觉上可行，但语义上是混乱的。

一个比较简单的原则是：

  • 跳转用链接
  • 操作用按钮

这个边界如果守住，很多交互和可访问性问题都会减少。

更具体一点：

前者会改变当前位置或导航到新资源，所以它是链接。后者只是触发页面内动作，所以它是按钮。

还有一个细节是表单里的按钮最好显式写 type：

如果省略 type，按钮在表单中默认可能是提交按钮。这个细节很小，但在弹窗、筛选表单、后台页面里经常造成误提交。

我被这个坑过一次，调试还挺久。一个后台筛选表单里放了好几个按钮，其中一个"重置"按钮没写 type，结果用户每次点重置，整个表单就跟着提交一次，页面莫名其妙刷新。一开始我一直怀疑是事件冒泡或者路由的问题，查了半天才发现是 button 在 form 里默认 type="submit" 在作祟。从那以后，凡是写在 form 里的按钮我都明确标 type，宁可啰嗦也不省这两个字。

还有个相关的反向场景：链接本来是用来跳转的，但有时候我们会拿一个 <a href="#"> 来当按钮用，配合 onClick 阻止默认行为。这种写法点完会在地址栏留个 #，浏览器历史也会被污染，用户按返回键时行为很怪。需要的是动作就用 button，不要用空 href 的链接凑数。

标题层级不要只看字号

语义化里另一个容易被忽略的问题是标题层级。

很多人会根据视觉大小选择 h1、h2、h3，但标题标签首先表达的是文档结构，不是字号。字号应该交给 CSS，标题层级应该跟内容层级一致。

读屏用户有个很常用的操作是按标题快速跳读（很多读屏软件支持按 H 键在标题间跳转，或者直接列出页面所有标题形成大纲）。如果你的标题层级是 h1 -> h3 -> h2 -> h4 这种乱序，对他们来说就像目录被打乱的一本书。我会用浏览器装一个 HeadingsMap 之类的插件，或者直接在控制台跑一行脚本把页面标题大纲打出来检查：

打印出来如果缩进是平滑递进的，结构就是对的；如果缩进忽大忽小，说明有跳级。还有一个常见误区：组件库的卡片标题、弹窗标题这些复用组件，往往写死了一个 h3，但同一个 h3 被复用到不同上下文里，层级未必合适。我后来的做法是让标题组件支持传入 level，由使用方根据所在位置决定渲染成 h2 还是 h3，而不是组件里写死。

什么时候可以用 div

强调语义化，不等于排斥 div。

当一个元素只是为了布局、包裹、分组样式，没有明确内容语义时，div 仍然很合适。例如网格容器、样式包裹层、动画容器，都可以用 div。

语义化对搜索引擎也有实际影响

语义化的另一个收益是搜索引擎更容易理解页面内容。这部分平时摸不着，但它确实在影响页面质量。

爬虫和浏览器一样，是从结构里推断信息的。一个清晰的 h1 加合理的标题层级，等于直接告诉它这个页面讲的是什么、各部分的主次关系。article、time、nav 这些标签也能帮它判断哪块是正文、哪块是发布时间、哪块只是导航。我维护博客的时候就会注意几个点：每篇文章只有一个 h1 且就是文章标题，发布时间用带机器可读属性的 time：

datetime 里是标准格式给机器看的，标签内容是给人看的，两边可以不一样。还有图片的 alt，它既是可访问性的一部分，也是搜索引擎理解图片的依据，空着或者写成"图片1"都是浪费。这些东西单看都很小，但它们和可访问性其实是同一件事的两面：把内容的含义如实表达出来，人、辅助技术、爬虫就都能受益。

语义化不会让你写得更慢

很多人担心语义化会增加开发成本，但实际上大部分时候只是习惯问题。

只要你在搭结构时多想一步“这个区域本来是什么”，写出来的代码通常不会更复杂，反而更稳定。

我在实际开发里通常会按这个顺序判断：

  • 这是页面主内容吗？优先考虑 main
  • 这是导航吗？优先考虑 nav
  • 这是独立内容块吗？考虑 article
  • 这是主题分组吗？考虑 section
  • 这是用户动作吗？用 button
  • 这是资源跳转吗？用 a
  • 只是布局包裹吗？用 div

这个判断过程熟悉以后，并不会拖慢开发速度。相反，它会减少后面补可访问性、改选择器、写测试时的返工。

语义化 HTML 的价值，不在于它是一个标准答案，而在于它让页面结构表达得更清楚。

当你开始把 HTML 当作“内容结构语言”，而不是“页面摆放容器”，代码的可维护性、可访问性和整体质量通常都会更进一步。它并不是额外要求，而是 Web 基础的一部分。
