前端请求库不只是发请求：从 Axios 到 Alova 的思路变化

2023-05-04
前端基础请求与异步Vue

很长一段时间里，前端发请求最常见的选择是 Axios。

它解决了 XMLHttpRequest 写起来麻烦的问题，也提供了拦截器、请求配置、响应处理、取消请求等能力。对很多项目来说，Axios 仍然是一个稳定、清晰、足够好用的 HTTP 客户端。

但今天的前端请求，已经不只是“把接口调通”。页面越来越复杂以后，请求会和状态、缓存、分页、重试、权限、乐观更新、错误展示绑在一起。继续只封装一个 request 函数，很多问题会被推回到业务组件里。

我在后台项目里最常见的重复代码，就是 loading/data/error 三件套。每个列表页写一遍，每个详情页写一遍，最后错误提示、重试按钮、空状态还都不一样。后来才意识到，请求库选型不只是“Axios 还是 fetch”，而是要不要把服务端状态当成一个独立问题来管理。

请求背后还有很多状态

一个普通列表请求，通常不只包含接口调用。

页面还要处理：

  • 加载中
  • 请求失败
  • 空数据
  • 分页
  • 搜索条件变化
  • 缓存和失效
  • 重试
  • 取消请求
  • 乐观更新
  • 重复请求合并

特别是取消请求。用户快速切换 tab 或搜索关键词时，旧请求可能后返回，把新结果覆盖掉。手写页面很容易漏这个边界，最后表现就是“我明明搜的是 A，列表却闪成了上一次的 B”。

Axios 更像基础 HTTP 客户端

Axios 的定位比较清楚：发请求、收响应、处理拦截。

它非常适合做统一 HTTP 层，比如：

  • 统一 baseURL
  • 注入 token
  • 处理响应格式
  • 处理 401 登录过期
  • 处理网络错误
  • 设置超时时间

所以 Axios 更像底层能力。它并不差，只是它解决的问题边界和 Alova、TanStack Query、SWR 这类工具不完全一样。

我仍然会把 Axios 这层保留下来做基础协议封装：baseURL、token、超时、统一错误、登录失效。上层再决定用 Alova、Query 还是页面自己的 composable。底层 HTTP 客户端和服务端状态管理不是互斥关系，很多项目是组合使用。

Alova 这类库关注请求策略

Alova 这类现代请求库更关注“请求策略”。

也就是说，它不只是发出 HTTP 请求，还希望帮你处理请求相关状态。例如：

  • 自动维护 loading
  • 自动维护 error
  • 提供分页请求策略
  • 支持缓存和失效
  • 支持请求共享
  • 支持乐观更新
  • 和 Vue、React 等框架集成

这类思路和 TanStack Query、SWR 等工具有相似之处：把请求当成应用状态的一部分来管理。

比如一个列表页面，真正关心的不只是 GET /posts，而是“当前搜索条件下的文章列表状态”。当关键词变化、页码变化或用户重新进入页面时，工具可以根据策略决定是重新请求、读缓存，还是保留旧数据等待新数据回来。

这比每个页面手写状态更稳定，也更容易形成团队统一风格。

不过请求策略库也不是银弹。缓存时间、失效规则、重试次数、乐观更新回滚，这些都需要团队约定。工具能提供能力，但不会替你判断“订单详情应该缓存多久”“权限接口失败是否要全局退出登录”。

请求状态和服务端状态要分清

前端里有两类状态容易混在一起：本地 UI 状态和服务端状态。

本地 UI 状态包括弹窗是否打开、当前选中的 tab、输入框临时内容。服务端状态包括用户信息、文章列表、订单详情、权限配置。

服务端状态有几个特点：

  • 来源不在前端
  • 可能被其他用户或其他页面修改
  • 需要重新获取或失效
  • 可能存在缓存
  • 请求失败时要有降级展示

如果把服务端状态当成本地状态随便存，很容易出现数据不同步。比如列表页删除一条数据后，详情页缓存还在；或者用户提交成功后，统计数字没有更新。

请求状态管理工具真正解决的就是这类问题。

我现在会把服务端状态的 key 设计当成重点。比如列表请求不能只用 /api/orders 当缓存 key，还要包含页码、筛选条件和排序字段。key 设计不清楚，缓存命中就会变成事故。

这个思想在不同库里写法不一样，但本质相同：请求状态必须能准确描述“这份数据是谁”。

统一错误处理很重要

无论用 Axios 还是 Alova，请求错误都不应该散落在每个页面里随便处理。

统一错误处理还方便做登录失效、权限不足、限流、网络断开等全局逻辑。

错误也要区分层级。401、403、网络断开这类适合全局处理；表单字段错误、业务校验失败更适合页面局部展示。所有错误都弹全局 toast，会让用户很烦；所有错误都交给页面，又会导致体验不一致。

什么时候需要换请求方案

如果项目只是少量接口，Axios 或原生 fetch 完全够用。不要为了“技术更现代”强行引入复杂工具。

但如果项目里有大量列表、搜索、分页、缓存、重复请求和状态同步，继续手写请求状态会越来越累。这时可以考虑引入请求状态管理工具，而不是只封装一个 request 函数。

可以用下面几个问题判断是否值得升级：

  • 页面里是否大量重复 loading/data/error
  • 列表页是否经常处理分页、搜索和刷新
  • 详情页和列表页是否经常数据不同步
  • 是否需要缓存接口结果
  • 是否存在重复请求浪费
  • 是否需要统一处理乐观更新和回滚

如果答案大多是“是”，就说明问题已经不只是 HTTP 客户端层面了。

引入新请求方案时，我不建议一次性全量替换。可以先选列表页、详情页、搜索页这种重复问题明显的模块试点。等团队把缓存、错误、分页、失效这些约定跑顺，再逐步扩展。请求层改动影响面很大，迁移节奏要比 UI 组件更谨慎。

小结

前端请求库的发展方向，已经从“更方便地发请求”变成“更稳定地管理请求状态”。

Axios 仍然适合基础 HTTP 能力；Alova 这类工具则更适合请求状态复杂、页面数量多的项目。选型时要看业务复杂度，而不是只看库名流行不流行。真正重要的是：请求边界清楚、错误处理统一、服务端状态有一致的管理策略。
