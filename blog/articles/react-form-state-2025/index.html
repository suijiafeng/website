React 表单状态管理经验总结：复杂表单不该一路 useState 写到底

2025-09-07
React组件与状态

React 里最容易写、也最容易写乱的东西之一，就是表单。

刚开始做简单输入框时，useState 足够直接。但一旦表单里出现下面这些需求，复杂度会迅速上升：

  • 动态字段
  • 联动校验
  • 草稿保存
  • 分步提交
  • 错误提示
  • 异步校验

这时如果还坚持“一个字段一个 useState”，代码很快就会失控。

最先出问题的通常不是校验，而是状态结构

很多表单越来越难维护，并不是因为规则复杂，而是因为状态没有分层。

一个更清晰的做法通常是把表单拆成三类状态：

  1. 表单值
  2. 校验状态
  3. 提交流程状态

例如：

如果把这些状态混在一起，后面几乎必然出现“改一个字段，顺手影响整个提交流程”的耦合问题。

表单值适合集中，交互状态适合分开

values 可以集中管理，因为它们本质上属于一份数据快照。

但像下面这些状态，不建议都塞进一个大对象里：

  • 当前是否提交中
  • 哪个字段正在异步校验
  • 是否显示确认弹窗
  • 当前步骤是否可前进

这些属于流程或 UI 状态，和表单值不是一个层次。

复杂表单更适合 reducer

当字段很多、更新动作明确时，useReducer 往往比一堆 setState 更稳。

reducer 的价值不只是“统一写法”，而是把状态变化变成显式动作，后面调试和扩展都会更容易。

我一般会把 action 设计得接近业务动作，而不是接近 DOM 事件。比如不要只有一个万能的 set_state，而是区分 update_field、touch_field、validate_success、submit_failed。这样日志里一眼就能看出用户走到了哪一步。

复杂表单里，状态变化本身就是业务流程的一部分。把它显式写出来，会比散在各个组件里的 setSomething 更容易复盘。

校验不要写成“哪里触发就在哪里拼”

表单校验最容易烂掉的方式，是在 onChange、onBlur、onSubmit 里各写一份条件分支。

更靠谱的方式是：

  • 把校验逻辑提成单独函数
  • 明确区分字段级校验和表单级校验
  • 不同触发时机复用同一套规则

异步校验一定要考虑竞态

很多表单会在输入用户名、邮箱、邀请码时做异步校验。

这类场景最容易出现的问题是：

  • 用户输入 A，发请求
  • 很快又输入 B，再发请求
  • A 的结果后回来，把 B 的结果覆盖了

所以异步校验至少要考虑：

  • 请求取消
  • 只处理最新一次响应
  • 加上最小防抖

否则你看到的并不是“校验结果”，而是“返回顺序”。

提交流程不要只维护一个 loading

很多表单最后只有一个 loading 状态，这在简单场景没问题，但复杂一点就不够了。

例如提交过程里可能有：

  1. 本地校验
  2. 图片上传
  3. 主表提交
  4. 成功回跳

这些阶段都叫 loading，等于没有信息。

更实际的做法是用阶段状态来表达：

  • idle
  • validating
  • uploading
  • submitting
  • success
  • error

一旦流程出问题，你会更容易定位卡在哪一步。

什么时候该用表单库

如果你的表单有这些特征：

  • 字段数量多
  • 规则复杂
  • 需要和 UI 组件库深度整合
  • 多个页面都有类似模式

那引入表单库通常是合理的。

但核心依然不是“为了用库而用库”，而是你是否已经清楚：

  • 状态怎么分层
  • 校验怎么组织
  • 提交流程怎么表达

如果这些都没想清楚，换什么库也只是在换一种混乱方式。

2025 年做 React 表单，常见选择仍然是 React Hook Form、Formik、Final Form 这类库，或者直接使用 UI 框架自带的 Form 能力。它们各有取舍：有的偏非受控输入，性能好；有的模型更传统，容易理解；有的和组件库集成更深。

但我不建议因为“复杂表单”四个字就立刻引库。可以先问几个问题：

  • 是否有大量重复的字段注册和错误展示逻辑？
  • 是否需要动态数组字段、嵌套对象、分步表单？
  • 是否需要统一接入组件库的输入组件？
  • 团队是否熟悉这个库的心智模型？

如果答案大多是肯定的，引入表单库是降低成本。如果只是三五个字段，用库反而可能让代码更绕。

我自己的经验

表单代码最容易在“再加一个字段”里慢慢变坏。第一次写的时候很清楚，第二次加一个联动，第三次加一个异步校验，第四次加一个草稿保存，最后就没人敢动。

所以我现在写表单会提前留三个边界：值归值，错误归错误，流程归流程。哪怕一开始代码多一点，也比后面所有状态混成一个大对象要轻松。表单不是一次性页面，它经常会随着业务规则变化。能不能改得动，比第一次写得短更重要。

延伸阅读

推荐看 React 官方文档关于状态结构的章节、React Hook Form 的性能设计说明，以及 Kent C. Dodds 关于 colocating state 的文章。它们能帮助你把表单问题从“用哪个库”拉回到“状态应该放在哪里、规则应该如何复用”。

写在最后

复杂表单的难点从来不只是输入和提交，而是状态、规则和流程三者的组织方式。

在 React 里，表单写得稳不稳，关键不在于用了多少 Hook，而在于你有没有把“数据”“校验”“流程”分开建模。只要这一步做对，后面的代码会清爽很多。
