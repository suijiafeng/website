qiankun 样式隔离与 JS 沙箱：两个子应用同时挂载后的冲突处理实录

2021-10-23
构建与模块化前端基础

周一早上运营提了个工单：营销中心的优惠券弹窗“字都挤在一起了”。我在本地打开营销中心，弹窗好好的。按工单里的操作路径重走一遍才复现——先打开商品中心的页签，再切到营销中心，弹窗就塌了。两个子应用同时挂在主应用里的时候，样式互相污染了。

背景一句话带过：去年评估微前端可行性之后，今年我们真的动手了，把原来那个巨石中后台拆出了商品中心和营销中心两个子应用，qiankun 2.x 接入，九月底先后上线。单独跑都没问题，十月初主应用为了页签间快速切换，把路由模式改成了两个子应用可以同时保持挂载（keep-alive 式的多应用共存），这个工单是共存模式跑了两周后第一个暴露出来的问题。

现象拆解：污染是怎么发生的

弹窗塌掉的直接原因很快查到了。两个子应用都用 Element UI，都把组件库样式全量打进了自己的产物。商品中心今年上半年做过一轮视觉改版，用主题工具改了 $--font-size-base 和一批间距变量，重新编译了一份定制版的 Element UI 样式；营销中心用的是默认主题。

两个子应用的样式表里于是都有 .el-dialog、.el-dialog__body 这些全局类名的规则，选择器一模一样、优先级一模一样——**这时候谁生效只取决于谁的 style 标签在文档里排得靠后。**商品中心后挂载，它那份定制版样式就压住了营销中心的默认版。营销中心的弹窗套上了商品中心的字号和间距变量，于是“字都挤在一起了”。反过来的污染其实也在发生，只是商品中心的页面当时没人盯着看。

在 DevTools 的 Elements 面板里能看得非常直观：同一条 .el-dialog__body 规则出现两次，来自两个不同的 style 标签，上面那条被划了删除线。把商品中心的页签关掉（触发它 unmount），style 标签被 qiankun 摘走，营销中心的弹窗立刻恢复正常——这也解释了为什么单应用模式跑了大半个月没人发现。

qiankun 默认不是有样式隔离吗？有，但它默认做的是“卸载时清理”：子应用 unmount 时，qiankun 把它挂载期间动态插入的 style/link 摘掉，再次 mount 时还原回去。这套机制管的是“应用切换”的时序问题，前提是同一时刻只有一个子应用活着。我们切到共存模式的那一刻，这个前提就没了——两个应用的样式表同时在文档里，清理式隔离对此无能为力。

还有第二个战场：z-index。Element UI 的弹窗层级由一个全局的 popup manager 管理，从 2000 起每弹一层加一。但两个子应用各自打包了各自的 Element UI，就是两个互不知情的 popup manager，各自从 2000 开始数。营销中心先弹了三层（数到 2003），商品中心新弹的第一层还是 2001，被压在别人的遮罩底下——用户看到的现象是“点了按钮弹窗没出来”，其实弹了，在下面。

strictStyleIsolation：Shadow DOM 的代价

qiankun 提供了两个样式隔离开关，先试的是听起来更彻底的 strictStyleIsolation：

开了之后，qiankun 把子应用整个包进一个 Shadow DOM。Shadow DOM 的样式隔离是浏览器原生的、双向的：外面的样式进不来，里面的样式出不去，理论上是最干净的方案。实际跑起来十分钟就翻车了——营销中心所有的弹窗、下拉面板、消息提示全部变成了无样式裸奔，比样式污染惨得多。

原因想一下就通：Element UI 的 Dialog、Select 下拉、Message 这些浮层组件，为了躲开父级 overflow: hidden 和层叠上下文的干扰，默认或可选地把 DOM 节点挂到 document.body 上。子应用的样式表被圈在 shadow root 里面，挂到 body 的弹窗节点在 shadow root 外面，样式够不着它——弹窗逃出了沙箱，样式没跟出去。

除此之外还有连带伤害。子应用里凡是用 document.querySelector 找自己节点的第三方库全部失灵——shadow root 里的节点从 document 上是查不到的，我们有个拖拽库和一个富文本编辑器都栽在这上面。事件系统也有细节差异，Shadow DOM 边界上事件的 target 会被重定向，依赖 event.target 做委托判断的老代码行为会变。

Shadow DOM 方案要能用，前提是子应用里所有东西都规规矩矩待在容器里：不往 body 上挂节点、不从 document 上查元素。对一个用了成熟组件库的存量应用来说，这个前提基本不成立。这个开关关掉了。

experimentalStyleIsolation 与前缀方案

第二个开关是 experimentalStyleIsolation。它不动 DOM 结构，而是在运行时改写子应用的每条样式规则，加一个属性选择器前缀，把作用范围圈在子应用容器内：

这个方向是对路的——两个子应用的 .el-dialog 规则加上各自的前缀之后不再互相覆盖，普通页面内容的隔离立竿见影。但它和 Shadow DOM 栽在同一块石头上：挂到 body 的弹窗不在带 data 属性的容器里面，加了前缀的规则同样够不着它。名字里那个 experimental 也不是白叫的，实测还遇到了 @keyframes、部分媒体查询内规则改写不完整的情况，运行时逐条改写规则在样式量大的页面上也有可感知的开销。

**两个官方开关都卡在“组件库浮层挂 body”这一个点上，说明这个问题只能回到子应用自己的构建层面解决。**最后落地的是构建期前缀化：营销中心改了两处——一是全局配置 Dialog、Drawer 等组件不挂 body（append-to-body 关掉，配合主应用保证子应用容器上没有 overflow: hidden 和意外的层叠上下文）；二是构建时用 postcss 插件给业务样式统一加 .marketing-app 命名空间前缀，子应用根节点挂这个类，SCSS 里原有代码不用动：

exclude 把 .el- 开头的规则排除掉是有意的：Element UI 的样式不加前缀，冲突改由另一个手段解决——商品中心那边反正要维护定制主题，顺势在主题编译时把变量改出差异；真正一劳永逸的做法是像 Element UI 支持的那样改命名空间前缀重新编译组件库样式，我们评估了一下工作量放进了下个迭代。

z-index 的战争则用最土的办法终结：**直接分段包干。**商品中心在主题编译时把 Element UI 的 z-index 起点改成 3000，营销中心保持 2000，两个 popup manager 各数各的，永远不会撞车。分段约定写进了主应用的接入文档：主应用自己的全局浮层 1000～1999，营销中心 2000～2999，商品中心 3000～3999，以后每接一个子应用划一段。层级战争打不打得赢不取决于谁 z-index 写得大，取决于有没有人出来划地盘。

JS 沙箱：快照与多实例的行为差异

样式之外，JS 这边也因为共存模式暴露了一个配置问题。qiankun 的 JS 沙箱有两种工作方式，行为差异我是这次才真正搞清楚。以下都是使用者视角的观察——沙箱底层是用 Proxy 实现的，具体怎么代理的细节以后有空再去源码里深挖，这篇只记行为。

快照沙箱是给不支持 Proxy 的环境（主要是 IE11）准备的降级方案：子应用挂载时给 window 拍一张快照，运行期间随便改，卸载时对比差异、把 window 恢复原样，下次挂载再把上次的改动补回来。这套机制有个天然限制——**window 只有一个，快照和恢复都是全量的，所以快照沙箱只能伺候单实例场景。**两个子应用同时挂载时，A 的恢复动作会把 B 正在使用的全局变量一并抹掉或还原错，互相踩脚是必然的。

支持 Proxy 的环境下，qiankun 给每个子应用一个独立的 window 代理（fakeWindow），子应用代码里对“window”的写入实际落在自己的代理对象上，读取时先查代理再兜底到真实 window。每个子应用各有一个代理，互相看不见对方的写入，这才是多实例共存的基础。

我们的坑在于：去年主应用接入时为了保 IE11 兼容，配了偏向降级的沙箱选项。今年八月产品已经正式宣布中后台放弃 IE 支持了，这个配置一直没人回头改。切共存模式后出现过一次诡异现象：商品中心的页签关掉后，营销中心里 lodash 的 _ 变成了 undefined——两个应用都往全局挂了 _，降级模式的恢复逻辑在多实例下把账算错了，卸载 A 的时候把 B 的也收走了。把沙箱配置改回默认的多实例代理模式后，现象消失。

升级到共存模式之前，应该把当初为单实例场景做的所有配置重新审一遍——沙箱模式只是其中一个，路由的 activeRule 互斥假设、全局 loading 状态的管理，都埋着类似的暗雷，这次顺藤摸瓜清了三处。

卸载不干净：沙箱管不到的全局副作用

沙箱能隔离 window 上的变量读写，但有一类东西它兜不干净：子应用运行期间登记出去的“回调”。这次排查顺带清出来三处，各有代表性。

一是定时器。营销中心有个活动倒计时轮询，setInterval 起的。组件里的那个在 beforeDestroy 清了，但还有一个模块级的轮询（检查活动上下架状态）是在子应用入口文件里起的，不挂在任何组件生命周期上。子应用 unmount 后它还在跑，每十秒打一个已经没有意义的接口，回调里访问已销毁的 Vue 实例，控制台隔十秒报一次错。

二是全局事件。商品中心给 window 挂了 resize 监听重算表格高度，unmount 时没摘。子应用切走后窗口一变化，回调照跑，操作的 DOM 已经不存在，又是一串报错。

三是 echarts 实例。图表组件销毁时没调 dispose，echarts 在全局登记的 resize 监听一直留着，实例引用的 DOM 和数据也释放不掉，页签开关十几次之后内存肉眼可见地涨。

qiankun 的沙箱对其中一部分有兜底——通过 window 代理拦截到的 setInterval、addEventListener，卸载时能帮你清掉。但绕过代理的写法、document 上的监听、第三方库内部登记的回调，它不保证。正确的姿势是不依赖沙箱兜底：子应用导出的 unmount 钩子就是留给你还债的地方，mount 里登记过什么，unmount 里就注销什么：

我们后来给两个子应用各建了一个 globalEffects 小模块统一登记这类副作用——起定时器、挂全局监听都必须走它，unmount 时一把清空。比散落各处靠自觉可靠得多，code review 时看到裸的 setInterval 直接打回。

验证卸载干净与否也有个笨但有效的办法：DevTools 的 Performance Monitor 挂着，反复开关子应用页签二十次，看 JS heap 和 DOM 节点数是不是稳定回落。修完这三处之前，DOM 节点数每开关一轮涨几百个；修完之后曲线是平的。

公共依赖要不要 externals

最后是这次讨论里争议最大的一个取舍。两个子应用各自打包了 Vue 2.6、Element UI、echarts，加起来重复的依赖体积有 1MB 出头（gzip 前）。有同事提议：主应用统一加载这些库，子应用全部 externals 掉，体积立省，还顺带解决了两个 Element UI 实例各自维护 popup manager 的层级问题——只剩一个实例，z-index 自然只有一本账。

好处是真的，代价也是真的。externals 意味着所有子应用的依赖版本被主应用锁死：商品中心想升一个 Element UI 的小版本修表格 bug，得拉着营销中心一起回归测试；以后新子应用想试 Vue 3（生态今年基本追齐了，团队明年多半要认真评估），主应用挂的是 Vue 2，直接堵死。微前端拆分买的就是“各应用独立演进”这个自由，把公共依赖 externals 到主应用，等于把自由又卖回去换体积。

我们最后的决定是分级。Vue 这类版本敏感、直接影响演进路线的，各自打包，重复就重复，1MB 的重复在内网中后台场景里不构成体验问题；echarts 这类版本不敏感、体积大的纯工具库，externals 到主应用统一挂 CDN，子应用 webpack 里声明 externals: { echarts: 'echarts' } 即可。Element UI 本来该归入第二类，但商品中心用的是定制主题编译出来的产物，两边根本不是同一份东西，externals 不成立，继续各自打包——反正 z-index 分段已经把冲突摁住了。

另外这次拆分还有个顺手的收获：两个子应用的构建独立了，各自升到了 webpack 5（主应用还在 4 上跑着，互不影响），持久化缓存让二次构建时间掉了一半多。单体时代这种升级要全仓库一起动，评估三个月都未必敢做，拆开之后“各自演进”的红利第一次真实兑现——这也反过来印证了不把 Vue 做 externals 的决定。

工单关闭

周四下午，前缀方案和 z-index 分段上线，按工单路径重走：先开商品中心，再切营销中心，优惠券弹窗字号间距正常，层级正常，反过来的顺序也正常。让运营同事确认后关了工单。

回头数了一下，一个“字挤在一起”的现象，底下压着四层问题：同名全局类名的加载顺序竞争、两个 popup manager 各自为政、为 IE 留下的单实例沙箱配置、一批卸载不干净的全局副作用。微前端把应用拆开了，但 document、window、z-index 这些东西天生只有一份——**拆的是代码，合的是运行时，冲突全都发生在合的那一侧。**去年评估时我们把精力都花在“要不要拆、怎么拆”上，现在看，拆完之后怎么让它们在同一个页面里相安无事，才是日常真正要面对的那部分。
