CSS Custom Highlight：不改 DOM 也能做文本高亮

2023-03-30
前端基础CSS

网页里做文本高亮，很多人第一反应是给文字包一层 span，再加背景色。

这种方法简单，但有一个问题：它会改变 DOM 结构。如果页面内容来自富文本、文章、代码编辑器或搜索结果，频繁拆分文本节点会让逻辑变复杂，也可能影响选择、复制和渲染性能。

CSS Custom Highlight API 提供了另一种思路：不改 DOM，也能给指定文本范围加样式。

我第一次注意到它，是在做站内搜索高亮时。原来的实现是把命中的词替换成 <mark>，简单页面没问题，但文章里一旦有代码块、链接、加粗文本，字符串替换就很危险。更麻烦的是，用户复制文字时会把插进去的标记结构也带出一些奇怪效果。那次之后我才意识到，高亮本质上更像“视觉标注”，不一定应该改内容结构。

这种方式适合静态内容。但如果高亮范围是动态计算出来的，比如搜索关键词、拼写检查、评论定位，就要不断修改 DOM。

Custom Highlight 的做法是：

  • 用 JavaScript 创建文本范围
  • 把范围注册到浏览器的高亮集合里
  • 用 CSS 控制高亮样式

文字节点本身不用被拆开。对富文本编辑器、在线文档和代码阅读器来说，这一点很重要，因为 DOM 结构通常还承担着内容模型、选区、光标和事件处理。

真正做搜索时，多节点是绕不开的。比如一句话中间夹了一个 <strong>，关键词可能横跨多个文本节点。简单版可以先只支持单节点命中，复杂编辑器或文档系统就要维护一套文本索引，把 DOM 文本节点和全局字符偏移对应起来。这个成本不低，所以不要因为 API 看起来优雅，就低估搜索匹配本身的复杂度。

适合哪些场景

Custom Highlight 很适合这些功能：

  • 页面搜索关键词高亮
  • 在线文档定位内容
  • 代码编辑器标记错误
  • 富文本批注
  • 拼写检查或语法提示

这些场景的共同点是：高亮范围经常变化，但不一定希望改变原始 DOM。

例如搜索结果高亮，如果每次输入关键词都重新给文本插入 mark 标签，就要处理旧标签清理、文本节点合并、选区丢失等问题。Custom Highlight 则把“内容结构”和“视觉标记”分开了。

需要注意的边界

这个 API 也不是所有场景都适合。

首先是兼容性。使用前应该判断浏览器是否支持：

其次，Range 的起止位置依赖具体文本节点。如果内容重新渲染，原来的文本节点可能已经不存在，高亮范围也需要重新计算。

另外，::highlight() 支持的 CSS 属性有限，不是所有样式都能像普通元素一样设置。它更适合背景色、文字颜色、下划线这类文本标记，不适合做复杂布局。

还有一个细节是生命周期。高亮不是创建完就不用管，搜索词变化、文章重新渲染、主题切换时，都要清理旧 highlight 或重新计算 range：

如果不清理，旧范围可能继续存在，或者指向已经被替换掉的文本节点。React/Vue 页面里尤其要在组件卸载时清掉对应高亮，避免跨页面残留。

对普通文章页，我会保持一个降级策略：支持 Custom Highlight 就走 Range，不支持就退回 mark 或干脆只定位不高亮。搜索功能先要保证能找到内容，高亮只是增强体验，不应该为了高亮让页面结构变脆。

我现在做高亮，会先看内容结构能不能被改。

普通静态内容用 mark 最省心，简单、语义也清楚；但文章、富文本、代码块、编辑器这类结构一复杂，往 DOM 里硬插标签就很容易牵出选区、复制、事件和重新渲染问题。Custom Highlight 好用的地方，正是它把“内容结构”和“视觉标注”分开了。

不过它也不是无脑替代。兼容性、文本节点变化、Range 生命周期、::highlight() 样式能力，都要提前想好。我的取舍很简单：结构简单就别折腾；结构复杂、又需要频繁动态高亮时，再上它。
