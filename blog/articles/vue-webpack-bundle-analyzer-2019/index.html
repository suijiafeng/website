Vue 项目包太大时先别慌：Webpack Bundle Analyzer 到底能帮你看清什么

2019-06-29
Vue构建与模块化性能与缓存

Vue 项目包一大，最容易出现的情况就是大家开始凭感觉优化。

有人觉得是图片大，有人怀疑某个 UI 库太重，也有人想先改构建参数。问题是，在没有看到真实体积分布之前，很多判断都只是猜。

这时最值得做的第一步，不是马上删代码，而是先把包看清楚。

Webpack Bundle Analyzer 的价值就在这里：它把“感觉很大”变成可讨论的证据。

Bundle Analyzer 的价值不在图炫

很多人第一次看到打包分析图，会被那一堆彩色方块吸引。但真正重要的不是图好不好看，而是它让你知道体积到底花在了哪里。

例如：

  • 哪个第三方库最重
  • 哪些模块重复出现
  • 哪个页面 chunk 明显偏大

这些问题如果不先搞清楚，后面的优化很容易瞎忙。

看分析图时，我通常先看四件事：

  • 主包里有没有低频页面代码
  • 第三方库是否明显超过预期
  • 同类库是否重复出现
  • 某个业务模块是否被错误打进公共包

不要只盯最大的方块。一个中等体积的库如果被首屏强制加载，也可能比一个很大的懒加载 chunk 更影响体验。

我自己有过一次很典型的经历：首屏卡，第一反应是图片没压缩，折腾半天图片，体积没降多少。后来打开分析图才发现，真正的元凶是 moment.js 把全部语言包都打进来了，一个时间格式化库占了三百多 KB。这种东西不看图根本想不到，全凭感觉只会越优化越偏。所以我现在的原则是：体积出问题，先出报告，再动手。

补一句 analyzerMode 的选择。默认是 server，构建完起一个本地服务自动开浏览器，本地随手看一眼方便。static 是生成一个独立 HTML 文件，适合存档、发给同事、丢进 CI 产物里慢慢看。还有个 json 模式只输出 stats 数据，适合接到别的工具里做体积监控、卡阈值。我现在 CI 上一般用 static 加 openAnalyzer: false，构建产物里带一份报告，需要时下载来看，不打断流程。

如果连分析插件都不想装，webpack --json > stats.json 导出统计数据，再丢到官方的 webpack analyse 在线工具里，也能看个大概，临时排查够用了。

Vue 项目里最常见的膨胀点

实际项目里包体积变大，常见原因通常包括：

  • 引了过重的组件库
  • 路由没有按需拆分
  • 富文本或图表类库直接进了主包
  • 工具库按整个包引入

这类问题很多并不是代码写错，而是结构没有控制住。

典型例子是图表库。报表页需要图表，不代表首页也要跟着下载图表库。

路由也应该按页面拆：

同一业务流程的页面可以放在同一个 chunk，低频重模块可以单独拆出去。给同名 webpackChunkName 是个常用技巧：订单列表和订单详情用户多半连着看，放一个 chunk 里，进列表时把详情也预加载了，点进详情就不用再等。反过来，报表、导出 Excel 这种用户半天点不了一次的功能，单独拆，绝不能拖累首屏。

webpackChunkName 这个魔法注释别拼错，写错了不会报错，只是默默生成一个奇怪命名的 chunk，分析图上你都认不出它是谁。我习惯 chunk 名跟业务目录对齐，看图时一眼能定位。

再说回 moment 那个坑，当年的解法是用 IgnorePlugin 把语言包干掉：

需要中文再单独 import 'moment/locale/zh-cn'。三百多 KB 一下降到几十 KB。当然更彻底的是换成 dayjs，体积差了一个数量级，不过那是后话，老项目里先用 IgnorePlugin 止血也行。

常见优化动作

分析之后再决定动作，通常会更准。

如果是第三方库过大，可以考虑：

  • 是否支持按需引入
  • 是否可以替换为更轻的 API
  • 是否被多个库间接重复引入
  • 是否可以延后到需要时加载

如果是组件库，要看项目本身是否已经配置按需加载。否则一个按钮可能把大量组件样式一起带进来。

如果是业务代码过大，要先看路由拆分是否合理，而不是急着压缩变量名。

组件库按需引入这块多说两句，因为踩的人特别多。比如 Element UI，全量 import ElementUI from 'element-ui' 一下几百 KB 全进来。配 babel-plugin-component 之后写 import { Button } from 'element-ui'，只会打进用到的组件。但有个坑：很多人配了按需，样式却还是 import 'element-ui/lib/theme-chalk/index.css' 整包引进来，JS 瘦了 CSS 没瘦，分析图上 CSS 那块还是一大坨。按需引入要 JS 和样式一起按需，这俩是配套的。

公共依赖被重复打包也很常见，分析图上同一个库名出现在好几个 chunk 里就是信号。这时候要看 optimization.splitChunks 的配置，把多个 chunk 共用的第三方库抽到 vendor 里：

不过 vendor 也不是越大越好，全塞一个 vendor 里，改一行业务代码不影响它，缓存利用率高；但要是某个常变的库混进来，vendor 哈希老变，缓存就白搭了。这块要结合实际更新频率权衡，没有标准答案。

注意 gzip 和实际加载

Bundle Analyzer 展示的体积不一定等于用户实际下载体积。生产环境通常还有 gzip 或 brotli 压缩，浏览器也会缓存静态资源。

所以分析时要区分：

  • parsed size：解析后的模块大小
  • gzip size：压缩后传输体积
  • initial chunk：首屏必须加载的资源
  • async chunk：按需加载的资源

优化首屏时，优先看 initial chunk。一个很大的 async chunk 可能没那么紧急，除非它属于高频路径。

Bundle Analyzer 右上角能切换显示 stat / parsed / gzip 三种尺寸，默认显示的是 parsed。我跟人对体积数据时吃过亏：我看的是 parsed 的 1MB，对方看的是 gzip 的 300KB，两边对不上还吵半天。看之前先确认大家看的是同一个口径。真正决定用户下载时间的是 gzip（或 brotli）后的体积，所以评估首屏成本应该看 gzip size，parsed size 更多是用来定位「谁占的大」。

优化后要验证

优化不是删完就结束。至少要确认：

  • 构建是否通过
  • 路由懒加载页面是否能打开
  • 旧浏览器兼容是否受影响
  • 首屏资源是否真的减少
  • 高频页面是否增加了明显等待

拆包可能会减少首屏体积，也可能让后续页面多一次请求。最终要看用户路径，而不是只看总包变小。

我验证的办法不靠感觉，靠 DevTools 的 Network 面板：勾上 Disable cache、把网络限速调到「Fast 3G」之类，刷新看首屏到底下载了哪些 JS、总大小多少、白屏到可交互花了多久。光看 webpack 输出的体积数字不够，那是「理论值」，真实体验得在限速的浏览器里跑一遍。我优化完一定会前后各录一次，对比首屏请求列表，确认大块头确实被挪到了 async chunk 里、首屏 initial 真的瘦了，而不是自我感觉良好。

别让优化反噬可维护性

最后提个醒，包体积优化容易上头，越拆越细，结果配置一堆 splitChunks 规则、魔法注释满天飞，新人接手完全看不懂。我的原则是：每一处拆分都得能说出「为什么拆、拆给谁省」。说不出收益的拆分就别做。低频重模块懒加载、第三方大库按需、公共依赖抽 vendor，这几样性价比最高，先做这些。变量名混淆、tree-shaking 这些交给生产模式默认配置就行，自己别瞎调。优化是为了让用户更快，不是为了让配置更花哨。

Webpack Bundle Analyzer 最大的作用，是把“感觉有点大”变成“我知道大在哪里”。

前端优化最怕靠直觉。先把体积分布看清楚，再决定删什么、拆什么、延后加载什么，效率会高很多。

真正有效的包体积优化，通常是“先分析，再拆分，再验证”。不要让优化变成一轮凭感觉的代码搬家。
