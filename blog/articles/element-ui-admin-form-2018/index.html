Element UI 后台表单排查记：校验和回显才是真正的重灾区

2018-03-19
Vue前端基础

月初接手了一个已经上线一年多的后台项目，负责这块的同事转岗去做别的模块，交接时留下一句："功能都能跑，就是表单那块问题比较多，你自己看吧。"

这个后台是 Vue 2 + Element UI 2.x，界面看着挺正常——Element UI 把输入框、选择器、日期、弹窗都准备好了，骨架谁搭都不难看。但缺陷列表里挂着的七个 bug 全跟表单有关：编辑商品时分类下拉框偶尔显示一串数字；新增弹窗里残留着上一次编辑的数据；保存按钮偶尔"点了没反应"；还有一个最邪门的——运营反馈"新增两个商品，改了其中一个的名字，另一个也跟着变了"。

我花了一周把这七个 bug 逐个定位清楚。定位下来的感受是：后台表单的工作量从来不在"把控件摆出来"，而在校验、回显、异步数据、提交状态这些看不见的地方——这个项目每一处都精准地踩了坑。下面按定位的顺序记录，每个 bug 都值一个知识点。

分类下拉框显示"5"而不是分类名

这个 bug 缺陷单上写着"偶现，无法稳定复现"，也是排查耗时最久的一个。现象：打开编辑页，分类下拉框有时显示分类名"电子产品"，有时显示一个光秃秃的数字 5，过一两秒又自己变正常。

先看模板，选项是异步取的：

这两段本身没错，loading 状态都处理了。问题在时序：详情接口和分类接口是同时发出去的，谁先回来不一定。el-select 显示文字的原理是拿 value 去 options 里匹配 label——如果详情先回来，form.categoryId = 5 已经设上，而分类接口还没回，categories 是空数组，匹配不到 label，它就只能把原始 value 5 显示出来；等分类接口一回来，文字又自己变正常。网络快慢决定现象有无，所以"偶现、无法复现"。

修法是保证两份数据都到齐再渲染。我用 Promise.all 并行请求，全部 resolve 后再标记 ready：

并行而不是串行，是因为这俩请求互不依赖，Promise.all 能省一个来回，编辑页打开还更快。异步选项 + 异步回显的表单，"谁先到"永远不能假设，这条我记在项目 README 里了。

顺带一提，Promise.all 有个容易被忽略的特性：只要有一个请求 reject，整体立刻 reject，另一个哪怕已经成功也拿不到结果。如果详情和分类接口里有一个偶尔会失败，用 Promise.all 会导致"分类接口明明成功了，但因为详情挂了，页面还是显示加载失败"。这种场景更稳妥的做法是用类似 Promise.allSettled 的手动包装——这个 API 目前浏览器还没有原生实现，我是自己写了个小的 settle 辅助函数，把每个 promise 包一层 .then(value => ({status: 'fulfilled', value})).catch(reason => ({status: 'rejected', reason}))，再用 Promise.all 包装，这样才能各自独立判断成功还是失败，不会一个的失败拖累另一个的成功结果。这个项目里详情和分类都是核心数据，任一个失败整体都该报错，所以最终还是用了 Promise.all，但这个降级方案值得记一笔，以后遇到"次要数据失败不该挡主要流程"的场景就能用上。

一是规则只写"必填"。长度、格式、边界值前端都不挡，全靠后端报错弹 toast，体验很糙。基础规则该配齐：

二是 trigger 全项目清一色 blur。输入框用 blur 没问题——让用户输完离开焦点再校验，边输边报红字很烦人；但选择器、单选、日期这类"选一下就定了"的控件也写 blur，就出现了缺陷单上那条"下拉框选完不报错，点一下别处才报错"。el-input 用 blur，选择类控件用 change，各归各位。

还有个小的：价格字段绑在 el-input 上，规则写了 { type: 'number' }，永远校验不过——el-input 吐出来的是字符串。要么规则里不写 type、validator 里自己转，要么给 v-model 加 .number 修饰符，这类"类型对不上"的坑在数字字段上特别常见。

越重置越乱的 resetFields

排查到弹窗表单这块时，撞上了 resetFields 的经典坑。这个后台的新增/编辑共用一个 el-dialog，重置逻辑是 this.$refs.form.resetFields()。现象：编辑过一次之后再点重置，表单不是回到空白，而是回到"上一次编辑的数据"。

原因在 resetFields 的语义：它重置到的是表单首次渲染时记录的初始值。这个时机非常微妙——如果回显数据是在表单渲染之后才填进去的，它记的初始值就是空的，重置会把回显清光；反过来，如果表单是带着回显数据首次渲染的（比如 v-if="ready" 那种写法），它记的"初始值"就是 A 商品的数据，重置等于回到 A。同一个 API，行为随渲染时机漂移，非常反直觉。

沉淀成约定的部分

一周下来，七个缺陷全部关闭，顺手把这些教训整理成一份表单开发约定放进项目文档：初始值必须走工厂函数；回显手动挑字段；异步选项和详情用 Promise.all 对齐；自定义 validator 通过分支必调 callback()；输入用 blur、选择用 change；提交必带 submitting 加按钮 loading；弹窗表单关闭必重置。

还补了两条这次没直接踩上、但排查过程里顺带发现隐患的规则。一是表单字段的默认值类型要和后端字段类型对齐，比如 status 这种开关字段，后端给的是数字 0/1 还是布尔 false/true 要在 normalize 层就转换清楚，不要让 el-switch 的 active-value/inactive-value 去将就后端的类型，这样将来后端换一种返回类型，只需要改 normalize 那一处。二是 el-form 的 rules 如果是通过 computed 动态生成的（比如某个字段是否必填取决于另一个字段的值），要注意 Element UI 2.x 的 rules 变化后不会自动重新校验已经报错的字段，需要在联动逻辑里手动调一次 clearValidate 或者重新 validateField，否则会出现"条件已经满足了，但红色错误提示还挂在那"的残留状态，和前面 resetFields 的坑是同一类"状态没跟着数据走"的问题。

这些问题每一样单拎出来都不难，难的是它们全都"看不见"，只在特定时序、特定数据下才会现形：字段结构、回显时序、校验规则、提交状态、重置语义，缺一处就是一张新的缺陷单。把这些隐患提前写进约定里，比每次等它们变成线上 bug 再补更划算。
