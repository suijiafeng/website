Element UI 后台表单整理：真正麻烦的是校验和回显

2018-03-19
Vue前端基础

后台系统里最常写的不是图表，也不是复杂动画，而是表单。

我做了两年多管理后台，掐指一算写过的表单没有一百也有八十：新增、编辑、筛选、批量、各种弹窗里的小表单。Element UI 把输入框、选择器、日期、弹窗都准备好了，搭个表单的骨架确实快，半小时就能把界面摆出来。但每次返工、每次被测试提 bug，几乎都不在“组件长什么样”上，而在校验、回显、异步数据、提交状态这些看不见的地方。界面摆完只是开了个头，后面这些细节才是真正吃工时的。

这里记几件我在表单页里反复踩过的坑，技术背景是 2018 年的 Vue 2 + Element UI 2.x。

新增和编辑最好共用一套结构

新增时使用默认值，编辑时回显接口数据：

不要直接 this.form = detail。后端返回字段可能比表单多，也可能缺字段。前端应该明确表单需要哪些值。

我吃过 this.form = detail 的亏。详情接口顺手多返回了 createTime、creator、updateTime 一堆只读字段，直接赋给 form 之后，提交时整个 form 原样 POST 回去，后端校验“creator 不允许修改”直接 400。更隐蔽的是缺字段：某个开关 enabled 在旧数据里压根没存，detail 里就没这个 key，this.form = detail 之后 form.enabled 是 undefined，el-switch 绑上去既不是开也不是关，显示成一个诡异的中间态。所以我现在一律手动挑字段、给默认值，多一个不要，少一个补上。

另外提一句默认值的写法。我会把初始结构抽成一个工厂函数，新增和重置都调它，避免引用共享导致的串数据：

千万别把默认对象写成模块级常量再直接赋值，那样所有实例共用同一个引用，一个表单改了另一个跟着变，这种 bug 极难查。

校验规则要贴近业务

Element UI 校验：

校验规则不要只写“必填”。长度、格式、边界值最好在前端先挡一层，用户体验会好很多。

trigger 选 blur 还是 change 是有讲究的。输入框（el-input）我一律用 blur，让用户输完离开焦点再校验，边输边报红字很烦人；选择器、单选、日期这类“选一下就定了”的，用 change，选完立刻给反馈。早期我图省事全写 blur，结果下拉框选完不触发校验，用户得点一下别处才报错，体验很别扭。

复杂一点的业务规则，内置的 required / min / max 不够用，就上自定义 validator。比如确认密码要和密码一致，或者某个字段格式特殊：

自定义 validator 我踩过的坑就是忘了在校验通过时调 callback()——不调的话这条规则永远处于未完成状态，整个表单 validate 的 Promise/回调一直不返回，提交按钮点了没反应，还以为是接口卡住了。校验通过那条分支的 callback() 千万别漏。

编辑页要注意：详情接口和选项接口谁先返回都可能。不要因为选项还没加载出来，就误以为回显失败。

这个竞态我专门栽过一次，现象很迷惑：编辑页打开，分类下拉框显示的是 categoryId 的数字（比如 5），而不是分类名“电子产品”。第一反应以为是回显代码写错了，查了半天才明白——el-select 是靠 value 去 options 里匹配 label 来显示文字的，如果详情接口先回来、form.categoryId = 5 已经设上了，但分类选项接口还没回来，options 是空数组，匹配不到，就只能把原始 value 5 显示出来。等选项接口一回来，文字又自己变正常了，所以偶现、难复现。

并行而不是串行，是因为这俩请求互不依赖，Promise.all 能省一个来回的等待时间，编辑页打开能快不少。

提交要防重复

按钮：

后台接口慢一点时，重复点击很常见。前端应该挡住重复提交，后端也要保证幂等或唯一性校验。

我专门强调“后端也要”，是因为前端这层 submitting 标志只能挡住“同一个页面连点”，挡不住网络重发、用户开两个 tab 同时提交、或者直接拿 Postman 打接口。真实事故是这样的：表单提交后跳转有点慢，用户以为没点上又点了一下，结果库里多了两条一模一样的数据。前端 loading 加上之后好了很多，但偶尔还是有重复——最后是后端在关键业务字段上加了唯一索引才彻底根治。前端防抖是为了体验，后端幂等才是兜底，两者缺一不可。

还有个小细节：validate 的回调是异步的，submitting 的判断要放在 validate 校验通过之后、真正发请求之前那一段，别放在 validate 外面，否则校验没过也把按钮 loading 上了，转个不停还提交不了，看着像卡死。

弹窗表单要在关闭时重置

后台里很多表单是放在 el-dialog 里的，新增/编辑共用一个弹窗。这种最容易出的问题是：上次编辑的数据残留到下次新增。用户编辑了 A，关掉弹窗，再点“新增”，弹窗里还显示着 A 的内容。

原因是 el-dialog 默认只是 v-show 切换显示，组件没销毁，form 数据还在。我的处理是监听弹窗的关闭事件，在 close 时重置：

或者更省心的办法，给 dialog 加 destroy-on-close，关闭时直接销毁内部内容，下次打开是全新的。不过 destroy-on-close 会让每次打开都重新渲染，表单复杂时有一点点开销，看场景取舍。我一般简单表单用 @close="resetForm"，内部组件重、想图省事就上 destroy-on-close。

表单的价值不在于把控件堆起来，而在于处理那些看不见但常出问题的细节：字段结构、回显、校验、异步选项、提交防重和统一错误提示。把这些做好，能显著减少后续的返工和用户痛点。
