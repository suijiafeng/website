Vue 后台 JWT 登录与权限：菜单藏住了，为什么门还是开着

2018-03-08
Vue组件与状态

菜单隐藏最容易给人一种“权限已经做了”的错觉。可只要路由还是全量注册、接口又没做角色校验，用户在地址栏里直接敲一个路径，就可能把整个后台的门重新推开。

这次问题就是最典型的一种：左侧菜单已经按角色藏干净了，普通账号看不到系统管理入口；但同一个账号手动输入 /system/user，页面照样能打开，接口也真把数据返回来了。说明我们藏住的只是入口，不是权限本身。

案发现场：菜单藏了，门没锁

先看第一现场。我们的"权限控制"是这么写的：菜单组件里按角色 v-if 过滤菜单项，普通商家看不到"系统管理"这一组。但路由表是全量注册的——每个角色的路由都在 router 里躺着，一个不少。

也就是说，我们只是把门牌摘了，门根本没锁。菜单上看不到入口，不代表 URL 不存在；地址栏是用户随便输的，收藏夹里的老链接也可能带着深层路径。

更糟的还在后面。我拿测试环境的普通账号试了下，不但页面能打开，页面里的接口也返回了数据——后端对这个接口也没有做角色校验。前端藏菜单、后端裸奔，整个"权限系统"其实只防住了最不爱折腾的那部分人。

这里先把这个案子最重要的结论放出来，后面所有修复都建立在它之上：**不要把"菜单隐藏"当成权限。前端所有的过滤、隐藏、拦截都是体验层的东西，真正的安全边界必须在服务端。**一个稍微懂行的人打开 devtools 改改 Vuex，或者直接拿 Postman 打接口，前端那点拦截形同虚设。后端加接口级的角色校验，是"必须做"，不是"最好也做一下"。

后端同学当天就开工补接口校验了。但前端这边也一堆债要还，我按从里到外的顺序一层层清。

存哪这个问题值得多说几句。localStorage 用着方便，刷新不丢，但它对 XSS 几乎没有防护——页面一旦被注入脚本，token 是明着送出去的。年初安全扫描那关我们就被挑过这一条。更稳的做法是让后端把 token 放进 HttpOnly 的 Cookie，前端根本碰不到它，请求自动携带。但很多后端图省事就是返回个 token 字段让前端自己存，前后端分离又跨域的话，Cookie 方案要配 withCredentials 和 CORS，扯皮成本高，所以大量项目最后还是落在 localStorage。我的态度是：能上 HttpOnly Cookie 就上，上不了就用 localStorage，但必须把 XSS 防住（输出转义、CSP），别自欺欺人地觉得存哪都一样。

趁这次翻修我还给组里补了一堂 JWT 常识课。JWT 是 header.payload.signature 三段用点连起来的，前两段只是 Base64 编码，不是加密——拿到 token 的任何人都能解出 payload 看内容：

所以 payload 里绝对不能塞手机号、密码哈希这类敏感信息，它就是个可以验签但内容公开的名牌。签名那一段保证的是"内容没被篡改"，不是"内容看不见"。这个误解我在不止一个后端同学那里见过。

还有个小细节：登录成功的跳转我坚持用 replace 不用 push。用 push 的话，用户登录后在首页点浏览器返回，又退回登录页了，体验很怪。replace 把登录页那条历史记录顶掉，返回就直接出应用了。

第三层翻修：路由权限，两条路选一条

门锁上了，接下来是"不同的人开不同的门"。后台的路由权限有两种常见做法。

第一种，前端维护完整路由表，在 meta 里声明角色，按当前用户过滤：

守卫里对目标路由跑一遍 hasPermission，不通过就跳 403 页。这种做法简单，适合角色固定、就那么几种的中小后台。我们商家端的角色其实只有三种，这次修复我先用它把血止住了——从案发到这版上线只花了一天。

第二种，后端返回菜单和权限数据，前端按数据生成菜单，再用 router.addRoutes 把动态路由挂上去。灵活得多，坑也多。最典型的是"后端给的是组件路径字符串，前端要映射成真正的组件"——后端返回 "component": "user/list"，前端得有张映射表：

动态加路由还有个必须处理的时序细节：addRoutes 之后，如果守卫没等路由挂载完就 next()，会出现刷新某个动态路由页面直接 404。正确做法是守卫里判断"权限路由还没加"时，加完用 next({ ...to, replace: true }) 让它带着原地址重新走一遍守卫，这一遍路由就齐了。这个 bug 我在上一个 OA 项目里排查了大半天才反应过来是时序问题。

另外要补一条兜底的 404 通配路由，而且必须在 addRoutes 时最后加——放前面它会把后面真正的业务路由全吃掉，啥都跳 404。

两种方案怎么选？我的判断是看角色矩阵归谁管：角色就那几种、变更走发版，用第一种；权限点要运营在后台随时配、角色能自定义，才值得上第二种。别为了"灵活"提前上动态路由，那套时序和映射的复杂度是要还的。

案中案：403 被当成 401，用户莫名其妙被登出

后端的接口校验上线当天，客服又来报障：有商家点了个按钮，"唰"一下被登出了，一脸问号。

查下来是个经典混淆：后端对无权限的请求返回了 403，而我们前端的响应拦截器把所有认证类错误一锅端当 401 处理——清 token、跳登录。**401 和 403 不是一回事：401 是"没登录 / 登录失效"，该跳登录页；403 是"登录了但没权限干这事"，应该提示"无权限操作"，人还留在原地。**按状态码分开处理后才正常：

401 收进拦截器统一处理之后，页面就不要再自己处理了，否则会出现多个弹窗、重复跳转、状态不一致。

但 401 这条路还有个生产环境特有的恶心问题：token 一过期，页面上同时发出去的好几个接口会同时返回 401，上面那段被触发好几次——弹一堆"登录失效"提示，连着 push 好几次登录路由，控制台报 NavigationDuplicated。解法是加标志位节流，第一次 401 处理时置位，处理完复位，期间再来的 401 直接吞掉：

结案前的加固：token 续期要不要做

整改收尾时产品提了个新诉求：商家填商品上架的长表单，填到一半 token 过期被登出，草稿全没，投诉了好几次。这就牵出 JWT 的天然难题：它是无状态的，签出去在过期前服务端没法主动作废。过期时间设短了，用户被频繁打断；设长了，token 一旦泄露危险期就长。顺带一提，"退出登录"也一样——前端删掉 localStorage 里的 token 只是自己不用了，那个 token 在过期前依然有效，讲究的系统要在服务端配黑名单才算真注销。

折中方案是双 token：短命的 accessToken（比如 30 分钟）跑日常请求，长命的 refreshToken 专门换新。accessToken 过期返回 401 时，前端拿 refreshToken 静默换一个，重发刚才失败的请求，用户全程无感。

整改验收

周五整改上线，我拿普通账号把 /system/user 又输了一遍：前端守卫直接把我导去了 403 页；用 Postman 绕过前端直接打接口，后端也返回 403。门牌摘了，门也锁了，锁芯在服务端。

这周挖出来的问题列在一起看：菜单隐藏被当成权限、接口无校验、fetchProfile 白屏、403 混进 401、并发 401 弹窗轰炸。它们看起来散，其实是同一个病根——一直把登录当成"一个页面"在做。**登录不是一个页面，而是一套状态和权限流程：token 的存取、守卫的分支、用户信息的恢复、接口错误的分流，环环相扣，断一环就出事故。**前端把体验层的拦截和展示做好，安全边界老老实实交给服务端，系统才既安全又好用。
