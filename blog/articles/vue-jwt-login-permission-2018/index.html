Vue 后台登录与权限：token 只是开始，路由守卫才是日常

2018-03-08
Vue组件与状态

后台系统做登录看起来很简单：输入账号密码，拿到 token，存起来，请求时带上。

但真正写起来，问题很快就会出现：刷新页面用户信息没了怎么办？没有权限的路由怎么拦？菜单是前端写死还是后端返回？按钮权限怎么控制？接口返回 401 时要不要跳登录？

登录不是一个页面，而是一套状态和权限流程。我做过两个比较像样的中后台，一个 OA 一个商家管理端，登录这块前后都返工过三四次，基本把能踩的坑踩了一遍。这篇就按我后来稳定下来的那套写法记一记，技术栈是 Vue 2.5 + vue-router 3.0 + axios，2018 年的常规组合。

这里我想多说一句存哪。localStorage 用着方便，刷新不丢，但它对 XSS 几乎没有任何防护——一旦页面被注入脚本，token 就是明着送出去的。当年我们安全扫描那关就被挑过这个。比较稳的做法是让后端把 token 放进 HttpOnly 的 Cookie，前端压根碰不到它，请求自动带上。但那年头很多后端图省事就是返回个 token 字段让前端自己存，前后端分离又跨域，Cookie 方案要配 withCredentials 和 CORS，扯皮成本高，所以大量项目最后还是落到了 localStorage。我的态度是：能上 HttpOnly Cookie 就上，上不了就用 localStorage，但务必把 XSS 防住（输出转义、CSP），别自欺欺人地觉得存哪都一样。

还有个细节，登录成功跳转我用的是 replace 不是 push。用 push 的话，用户登录后在首页点浏览器返回，又退回登录页了，体验很怪。replace 把登录页这条历史记录顶掉，返回就直接出应用了。

路由守卫要避免死循环

登录页本身应该放行：

守卫里最怕逻辑分支不完整，next 调多次或不调。这是 beforeEach 最大的陷阱：少调一次 next，页面卡死白屏；多调一次，控制台报警告还可能跳错地方。我的习惯是每个分支末尾要么 next(...) 要么 next() 之后立刻 return，把 return 当成强制收尾，写完通读一遍确认没有哪条路漏掉。

还有个容易被忽略的点：登录页要在 whiteList 里，但同时已登录用户访问登录页要弹回首页，这两段逻辑顺序别写反。我见过有人把白名单判断放在 token 判断前面，结果已登录用户能反复进登录页，又退出登录又登录，状态来回横跳。上面那段先判 token 再判路径，就是为了把「已登录」这条主干优先处理掉。

动态加路由还有个必须处理的细节：addRoutes 之后，如果守卫里没等路由挂载完就 next()，会出现刷新某个动态路由页面直接 404 的情况。正确做法是在守卫里判断「权限路由还没加」时，加完用 next({ ...to, replace: true }) 让它带着原地址重新走一遍守卫，这次路由就齐了。这个 bug 我排查了大半天才反应过来是时序问题。

另外动态路由还要补一条兜底的 404 通配路由，而且这条必须在 addRoutes 时最后加，否则它会把后面真正的业务路由全吃掉，啥都跳 404。

不管哪种方式，有句话我反复跟新人强调：不要把「菜单隐藏」当成权限。真正的权限必须由后端接口控制。前端这些过滤、隐藏，全是体验层的东西，防止用户看到不能操作的入口而已。一个稍微懂行的人打开 devtools 改改 Vuex、或者直接拿 Postman 打接口，前端那点拦截形同虚设。安全边界永远在服务端，这不是「最好也做一下」，是「必须做」。

这里还有个真实生产环境碰到的恶心问题：token 一过期，页面上同时发出去的好几个接口会同时返回 401，于是上面这段被触发好几次，弹出一堆「登录失效」提示，或者连着 push 好几次登录路由，控制台报 NavigationDuplicated 错误。我的解法是加个标志位做节流，第一次 401 处理时置位，处理完（或者一段时间后）复位，期间再来的 401 直接吞掉：

顺带提一个权限里很容易混淆的概念：401 和 403 不是一回事。401 是「没登录 / 登录失效」，该跳登录页；403 是「登录了但没权限干这事」，应该提示「无权限操作」而不是踢去登录页。我们早期把两者都当 401 处理，结果用户点了个自己没权限的按钮，唰一下被登出了，一脸问号。后来按状态码分开处理才正常。

token 续期：要不要做，怎么做

JWT 有个天然问题：它是无状态的，签发出去在过期前服务端没法主动作废。过期时间设短了，用户填表填到一半被登出，体验差；设长了，token 一旦泄露危险期就长。

折中方案是双 token：一个短命的 accessToken（比如 30 分钟）用于日常请求，一个长命的 refreshToken 专门用来换新的 accessToken。accessToken 过期返回 401 时，前端拿 refreshToken 静默换一个新的，重发刚才失败的请求，用户全程无感。

不过实现起来有个并发坑：同一时刻好几个请求一起 401，不能都去刷新，否则会刷新好几次、甚至旧 refreshToken 被新的顶掉导致互相失效。要做的是「第一个 401 去刷新，其余的挂起排队，刷新成功后统一重放」：

_retry 标志是防止「刷新后重放的请求又 401」导致死循环。说实话 2018 年很多中后台没做到这一步，过期就直接踢登录，简单粗暴但够用。要不要上双 token，看你的用户能不能忍受被频繁打断——填长表单的后台值得做，纯查看类的看板没必要折腾。

权限系统的重心不是 token 本身，而是把登录状态、守卫逻辑、用户信息与接口错误处理串起来。在前端做好体验层的拦截和展示，同时把安全边界留给后端，系统才既安全又好用。
