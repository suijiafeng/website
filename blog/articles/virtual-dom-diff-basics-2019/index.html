虚拟 DOM 和 diff：框架更新页面时到底在比较什么

2019-09-29
JavaScript组件与状态

虚拟 DOM 是框架面试里的常见问题。

很多人会回答：虚拟 DOM 是 JavaScript 对象，diff 后再更新真实 DOM。这个方向没错，但还可以继续问：为什么要用对象描述 DOM？diff 比较什么？列表为什么要写 key？为什么不推荐用 index 做 key？

这些问题和项目里的列表渲染、组件更新都有关系。

我自己第一次真正搞懂虚拟 DOM，不是看面试题看懂的，是被一个线上 bug 逼懂的。当时做一个可拖拽排序的待办列表，用户拖动一项后，已经勾选的复选框状态会跳到别的行去。检查了 data 没问题，状态对得整整齐齐，可页面上的勾就是错位。后来才知道，问题出在我给 v-for 写的 :key="index" 上——排序之后 index 全变了，框架按 index 复用了 DOM 节点，复选框这种"DOM 自身状态"（不受 data 控制的那部分）就跟着错位了。那一刻我才意识到，面试题里那句"index 做 key 会有问题"不是空话，背后是 diff 算法实打实的行为。这篇就按我后来理解的顺序，把这套东西讲一遍。

框架先生成 VNode，再根据 VNode 创建真实 DOM。数据变化后生成新的 VNode，然后和旧 VNode 比较，找出需要更新的部分。

真实框架里的 VNode 字段比这多得多。Vue 2 的 VNode 上挂了 tag、data（属性、事件、指令都塞在这里）、children、text、elm（对应的真实 DOM 引用）、key、componentOptions 等一堆东西。我刚开始看源码时被这些字段吓到，后来想明白了：核心其实就那么几个，tag 描述这是个什么节点，children 描述它里面有什么，key 用来标记身份，elm 是创建出真实 DOM 后回填进来的引用——后面更新时就靠它找到要操作的那个真实节点，不用每次都重新查 DOM。

为什么不直接操作 DOM

直接操作 DOM 当然可以：

但项目复杂后，手动维护 DOM 很容易乱。状态变化、条件渲染、列表更新、组件嵌套都需要同步处理。

虚拟 DOM 的价值不是每次都比手写 DOM 快，而是让 UI 可以由状态描述，框架负责把状态变化映射到 DOM 更新。

这一点我得特别强调，因为面试里太多人把虚拟 DOM 和"快"画等号了。真要论极致性能，针对单个已知节点的精准 textContent 修改，永远比"生成新 VNode → diff → patch"这一整套流程快，因为后者多了创建对象和比较的开销。虚拟 DOM 真正解决的是可维护性：在没有它之前，jQuery 时代的代码长这样——

每加一个字段，就要手动维护一条"数据变了 → 找到对应 DOM → 改它"的链路。状态一多，这些链路互相交织，漏改、错改是家常便饭。虚拟 DOM 把这件事反过来了：你只描述"在当前状态下页面应该长什么样"，至于怎么从旧样子变到新样子，交给框架去算。我宁可让框架多做一点 diff 的计算，也不想再手写那种命令式的 DOM 同步代码——这笔账，对大多数业务页面来说是划算的。

diff 的基本假设

完整比较两棵树成本很高。框架通常会做一些假设：

  • 不同类型的节点，直接替换
  • 同层节点之间比较
  • 通过 key 判断列表项身份

例如：

这条假设背后的道理是：实际项目里，一个 <div> 几乎不可能在下一次渲染时变成 <span> 还想保留原来的子树。与其花成本去比较两棵结构很可能完全不同的树，不如直接销毁旧的、创建新的，反而更快。这就是为什么 diff 的复杂度能从理论上的 O(n³) 降到 O(n)——靠的就是这几条"反正实际情况不会那么刁钻"的工程假设。

updateChildren 是整个 diff 里最精妙的部分，它用了"双端比较"的策略：新旧两个子节点数组各拿首尾两个指针，按"旧头对新头、旧尾对新尾、旧头对新尾、旧尾对新头"四种方式两两试探。为什么要这么折腾？因为真实场景里列表的变化往往是有规律的——往头部插一个、往尾部加一个、或者整个倒序，双端比较能用最少的移动次数命中这些常见模式。四种都不匹配时，才退回到用 key 建一张映射表去找。理解了这个，你就明白下面 key 的重要性到底体现在哪一步了。

key 为什么重要

列表：

key 用来告诉框架：这个节点对应哪一条数据。

如果没有 key，或者 key 不稳定，框架可能复用错误节点，导致输入框内容错乱、动画异常、组件状态串掉。

key 的作用，正是在上面说的 updateChildren 双端比较都没命中时，让框架能用 key → 旧节点位置 的映射表，O(1) 地找到"这条新数据对应的旧节点在哪"，从而尽量移动复用而不是销毁重建。没有 key 时，Vue 会退化成"按位置就地复用"（in-place patch）——也就是第一个新节点复用第一个旧节点，第二个对第二个，依次往下。这在列表只追加不打乱时没问题，一旦顺序变了就出事。

我前面那个拖拽列表的 bug 就是典型。还有一类更隐蔽的：列表项里带了非受控状态。比如每行有个 <input>，用户在第二行输了字还没提交，这时候列表头部插入了一项。如果用 index 做 key，框架会认为"第二行还是第二行"，于是把新数据的内容渲染上去，但那个 input 里用户敲的字（DOM 自己持有的、不在 data 里的状态）却留在原地，结果就是数据和输入框对不上。这种 bug 用 console.log 打 data 永远是对的，因为问题根本不在 data 层，特别容易让人怀疑人生。

如果列表只是静态展示，问题不大。

这里有个常见的纠结：如果数据本身没有 id 怎么办？我的处理顺序是这样——后端能给稳定 id 最好，直接用；后端给不了，但某个字段组合能保证唯一（比如 code 或 name + type），就用那个组合；实在没有唯一标识，就在数据进入前端时，由前端补一个稳定的本地 id：

关键词是"稳定"——同一条数据，无论它在数组里排第几，这个 key 都不能变。我见过有人图省事写 :key="Math.random()"，那是最糟的做法：每次渲染 key 全是新的，框架认为整个列表全换了，所有节点销毁重建，不光性能差，过渡动画、输入焦点全部丢失。还有人写 :key="item.name + index"，以为加了 index 更"唯一"，其实只要带上 index，顺序一变 key 就跟着变，等于白搭。

什么时候 index 做 key 是安全的？三个条件同时满足：列表是纯静态展示（不增删不排序）、列表项内部没有非受控状态（没有输入框、没有组件内部 state）、不依赖列表过渡动画。满足这些，用 index 没问题，没必要为了"规范"硬造 id。规则是用来理解的，不是用来无脑套的。

diff 不是免费

虚拟 DOM 让更新模型更清楚，但 diff 本身也有成本。

如果列表很大，每次都重新渲染整块区域，也会慢。

项目里要注意：

  • 大列表分页或虚拟滚动
  • 避免无意义重新渲染
  • key 保持稳定
  • 组件拆分合理

不要把“用了虚拟 DOM”当成性能万能答案。

我自己踩过的一个性能坑：一个监控大屏，左侧是一张几百行的实时表格，右侧每秒推一次新数据。最初的写法是每次数据来了，整个 tableData 数组重新赋值。结果页面卡得风扇狂转。排查下来，问题不在 diff 本身，而在于我每次都生成了全新的数组和对象引用，导致几百行全部进入 patch 流程，再加上每行里还有格式化函数在 render 时反复执行。后来做了两件事就好了：一是只更新真正变化的那几行（按 id 定位后局部更新），二是把行内重计算搬到 computed 里缓存。这件事让我明白，虚拟 DOM 帮你算出了"哪里变了"，但它没法帮你减少"你让多少东西参与了比较"——后者得靠你自己控制数据的变更范围。

另一个常被忽略的点是 v-if 和 v-show 在 diff 视角下的区别。v-if 是真的从 VNode 树里增删节点，切换时会触发组件的创建和销毁；v-show 只是改 display，节点一直在树里。频繁切换的东西用 v-show，能省掉反复 patch 和组件重建的成本；只渲染一次、之后基本不动的，用 v-if 省掉常驻开销。这种取舍，本质上也是在跟 diff 的工作方式打交道。

虚拟 DOM 是用 JavaScript 对象描述 UI，diff 是比较新旧描述并更新真实 DOM。

面试问它，通常会继续问 key、列表更新、diff 策略和性能边界。项目里真正重要的是：让 key 稳定，让状态清楚，让框架能正确复用节点。
