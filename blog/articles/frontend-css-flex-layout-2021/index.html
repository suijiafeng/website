Flex 布局为什么这么常用：从主轴思维到常见踩坑

2021-01-19
前端基础

现在做页面布局，Flex 几乎已经成了默认选项。

无论是导航栏、卡片列表、按钮组，还是左右结构、垂直居中，很多场景第一反应都是先看能不能用 Flex。

它之所以流行，不只是因为写法简洁，而是因为它提供了一种更贴近布局问题本身的思路。

我还记得刚工作那两年用 float 加 clearfix 写两栏布局的日子，左浮右浮、清浮动、算 margin，一不小心高度塌了，还得专门去查为什么父容器没撑开。后来用 display: table 和 display: inline-block 凑过居中，inline-block 之间还会莫名其妙多出几像素的空隙，得靠把 HTML 标签写在一行、或者父级设 font-size: 0 这种偏方去消。等真正切到 Flex 之后，那一堆历史包袱基本一次性扔掉了，这也是我愿意把它当默认选项的原因——它解决的不是某个具体效果，而是一整类"东西怎么排"的问题。

先别背属性，先理解主轴和交叉轴

很多人学 Flex 时容易一上来就记：

  • justify-content
  • align-items
  • flex-grow
  • flex-shrink

属性背下来当然有用，但如果不先理解主轴和交叉轴，后面还是会混。

Flex 容器里最核心的两条线是：

  • 主轴
  • 交叉轴

默认 flex-direction: row 时，主轴是水平方向，交叉轴是垂直方向。

这意味着：

  • justify-content 控制主轴上的分布
  • align-items 控制交叉轴上的对齐

很多人把这两个属性记反，本质上不是记忆问题，而是没先想清楚当前主轴朝哪边。

那主轴就变成了垂直方向，交叉轴变成水平方向。于是 justify-content 管上下分布，align-items 管左右对齐。

我自己后来用一个很土的办法帮自己记：主轴永远是 flex-direction 指的那个方向，justify-content 跟着主轴走，align-items 永远是"另一边"。一旦把方向定下来，剩下两个属性谁管哪边就是确定的，不用每次都凭感觉试。真正坑人的是 flex-direction: row-reverse 和 column-reverse，主轴方向被反转之后，justify-content: flex-start 看上去会"从右边开始排"，我第一次做一个 RTL 适配的需求时就是栽在这——元素全跑反了，盯着 justify-content 改半天，最后才发现是 direction 和 row-reverse 叠加在一起,主轴起点整个翻了过来。所以 start/end 这种相对值比 left/right 更值得信任，它们本来就是为了跟着主轴和书写方向走的。

还有个容易混的点：align-items 是给容器统一设交叉轴对齐的，而 align-self 是单个子项的"我不听话"开关。比如一排卡片整体顶部对齐，唯独某个操作按钮要贴底，就在那一个子项上加 align-self: flex-end，不用去拆容器结构。这个区分清楚了，很多看似要改 DOM 的对齐问题其实一行样式就能搞定。

Flex 最实用的地方，是它把“剩余空间怎么分”说清楚了

flex: 1 好用，但不要把它当成魔法

flex: 1 是最常见的写法之一，但不少人会误以为它等价于“宽度自动铺满”。

实际上它描述的是伸缩规则，通常可以理解为：

  • 允许增长
  • 允许收缩
  • 基础尺寸为 0

这也是为什么两个 flex: 1 的子项通常会平分剩余空间。

但如果某个子项内部内容很长，或者另一个子项设置了固定宽度，最终结果还是会受到内容和其他规则影响。Flex 不会无视现实条件，它只是给了浏览器一套更合理的分配方式。

flex: 1 其实是个简写，展开是 flex: 1 1 0%，三个值分别是 flex-grow、flex-shrink、flex-basis。我有次看同事代码写的是 flex: 1 1 auto，看着差不多，结果两个子项内容长度不一样时分出来的宽度完全不对等。原因就在 basis：flex: 1（basis 为 0）是先把全部空间当成"剩余空间"来平分，所以两边一样宽；flex: auto（basis 为 auto）是先按内容算出各自尺寸，再把多出来的空间平分，内容多的那项就更宽。需要严格等分用 flex: 1，想"按内容打底再分剩余"用 flex: auto，这俩别混。

还有个反直觉的点：只写 flex-grow: 1 而不动 basis，元素并不会自动平分，因为默认 basis 是 auto，会先把内容尺寸占掉。我早期总纳闷"我明明写了 grow 怎么不均匀"，根上就是没理解 basis 在这套规则里其实是优先级最高的那个起点。

最常见的坑之一：子项为什么不肯收缩

这个问题在真实项目里很常见。

例如左右布局中，右边内容区本来应该自适应，但里面有一段很长的文本、一个超长链接或者一张没限制宽度的图片，结果整个容器被撑开。

很多时候问题不在父元素，而在子项默认的最小尺寸。

这时经常要补一个：

min-width: 0 看起来不起眼，但它能告诉浏览器：这个子项允许在需要时继续收缩，否则内容可能会用“我不能再小了”的方式把布局撑坏。

这个坑的本质是：Flex 子项的 min-width 默认值不是 0，而是 auto，意味着它的最小尺寸至少是内容的"最小内容宽度"。一段不带空格的长 URL、一个没设宽度的 <img>、一个 white-space: nowrap 的标题，都会把这个最小宽度顶得很大，于是子项就死活不肯往下缩，要么撑爆容器，要么把旁边的兄弟挤没。min-width: 0 是把这个底线放开。

这确实很好用，特别适合弹窗、图标按钮、空状态区。

但也不要一看到对齐就无脑上 Flex。比如文本行内对齐、简单按钮内图文对齐，有时候 line-height、vertical-align 或者更直接的布局方式会更轻。

Flex 的优势是在“多个子项之间如何分布和对齐”，不是所有局部样式都必须交给它处理。

  • 不用处理最后一项
  • 横向和纵向切换时更容易维护

如果项目环境允许，用 gap 管子项间距通常比手写一堆 margin 更清晰。

不过 gap 在 Flex 上的浏览器支持是 2021 年前后才慢慢普及的（Safari 直到 14.1 才支持 Flex 的 gap），所以那阵子我做需要兼容老 Safari 的项目时还不敢全量铺开。如果项目要兜底，老办法是给父容器加负 margin、子项加 padding 来模拟，但那个写法又丑又容易出错，能上 gap 我是绝不回去手算的。

另外 gap 和 justify-content 是会叠加的，这点踩过一次。我想做一排按钮"两端对齐 + 中间留固定间距"，结果写了 justify-content: space-between 又写了 gap，间距被加了两遍。后来想清楚了：space-between 本身就负责把多余空间塞进缝里，固定间距的诉求和它是冲突的。要固定间距就别用 space-between，让容器靠 gap 排，整体对齐用别的方式控制。

默认情况下 Flex 是不换行的，子项再多也会硬挤在一行里收缩。做标签云、筛选项这种数量不定的列表，就得开 flex-wrap: wrap：

但有件事坑过我：单行的时候我们用 align-items 控制交叉轴对齐，一旦换成多行，控制"行与行之间怎么分布"的其实是 align-content，不是 align-items。这俩在单行时看不出区别，多行时行为完全不同。我有次做一个固定高度的卡片墙，想让多行卡片整体顶部聚拢，改了半天 align-items 没反应，最后才反应过来该改 align-content: flex-start。

Flex 适合一维布局，这点要记住

Flex 很强，但它的强项是一维布局，也就是一行或者一列上的分布。

如果问题变成：

  • 同时控制行和列
  • 卡片网格需要严格对齐
  • 二维结构关系更重要

那 Grid 往往更合适。

不少布局用 Flex 也能硬写出来，但后面会越来越绕。不是 Flex 不够强，而是它不该承担所有事情。

一个很具体的判断标准：如果你发现自己在 Flex 里嵌套 Flex、为了让两行的列对齐又在子项上反复调 width 和 basis，那基本就是该上 Grid 的信号了。最典型的是表单——多个"标签 + 输入框"的行，想让所有标签右对齐、所有输入框左边线齐平。用 Flex 得给每个标签写死宽度，标签文字一长就乱；用 Grid 的 grid-template-columns: auto 1fr 一句话就解决，列对齐是天然的。我现在的习惯是：行内一串东西的分布、对齐、伸缩，交给 Flex；需要行列同时对齐的二维结构，直接 Grid，两者经常是搭着用的，外层 Grid 分区、区块内部再用 Flex 排小元件。

真正常用的不是“会写属性”，而是形成布局判断

我后来对 Flex 的理解越来越简单：先看是不是一维分布问题，再看主轴朝哪边，然后决定谁固定、谁伸缩、谁对齐。

如果这个判断顺了，属性其实不会太多。

前端布局很多时候并不是靠记住多少属性取胜，而是靠你有没有一个稳定的思考顺序。Flex 之所以常用，就是因为它把这种顺序表达得很自然。
