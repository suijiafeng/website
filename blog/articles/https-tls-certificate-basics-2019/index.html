HTTPS、TLS 和证书：为什么登录页不能再裸奔

2019-09-18
杂项

去年我们公司一个内部后台被人薅了羊毛，查了半天才发现，问题压根不在业务逻辑，而是那套后台一直跑在 HTTP 上，登录接口的用户名密码就这么明文飘在内网里。攻击者其实就是同一个办公网段的人，抓个包就拿到了运营同事的账号。那次复盘之后，我才认真把 HTTPS 这一整套东西从头捋了一遍。这篇就是当时的笔记，加了不少后来踩过的坑。

很多人对 HTTPS 的理解停留在「地址栏多了个小锁」，觉得是运维该操心的事。但凡涉及账号、Token、支付、个人信息的页面，前端都绕不开它，而且出问题的往往是前端这一侧——混合内容、Cookie 属性、本地开发证书，这些都是我们的活儿。

先看清 HTTP 到底裸在哪

HTTP 是明文协议。所谓明文，不是「容易被破解」，而是根本没加密，链路上任何一个节点都能直接读。

明文还有第二个问题，比窃听更阴险：篡改。HTTP 没有完整性校验，运营商往页面里插广告、把你的 JS 换成挖矿脚本、给响应尾巴塞一段 iframe，这些在国内的 HTTP 站点上当年是家常便饭。我自己就遇到过某地市宽带在我们的 H5 活动页底部硬塞了一条浮动广告，用户截图来投诉，我们才发现页面源码根本没有那段代码。

所以 HTTP 的问题可以拆成三句话：能被看见、能被改、看不出有没有被改。

HTTPS 到底加了什么

HTTPS 不是另一个协议，它就是 HTTP over TLS——在 HTTP 和 TCP 之间塞了一层 TLS。应用层照样发 HTTP 报文，只是这些报文先进了 TLS 这层「加密管道」。

它解决的恰好是上面三件事：

  • 加密传输：链路上的人只能看到一堆密文。
  • 身份认证：通过证书确认「我连的确实是 example.com，不是冒充的」。
  • 完整性保护：报文被改一个字节，对端校验就会失败、直接断开。

注意第二点经常被忽略。光有加密是不够的——如果你不能确认对端身份，攻击者完全可以冒充服务器，跟你建一条「加密」连接，你的密文照样是发给他的。这就是中间人攻击（MITM）。证书就是用来堵这个洞的。

TLS 握手：一次连接里发生了什么

2019 年线上主流还是 TLS 1.2，TLS 1.3 刚开始铺（Chrome、Nginx 1.13+ 支持），所以这里按 1.2 的经典流程说，顺带提一句 1.3 的改进。

一次 TLS 1.2 握手大致是这样的（以最常见的 ECDHE + RSA 为例）：

  1. ClientHello：客户端把自己支持的 TLS 版本、加密套件列表、一个随机数发过去。
  2. ServerHello：服务器选定一个加密套件，回一个自己的随机数。
  3. Certificate：服务器把证书链发给客户端，客户端用本地信任的 CA 公钥去验证。
  4. ServerKeyExchange：服务器用私钥对 ECDHE 参数签名发过去，客户端用证书里的公钥验签——这一步既交换了密钥材料，也证明了「持有私钥的就是证书拥有者」。
  5. ClientKeyExchange：双方各自用 ECDHE 算出同一个 pre-master secret，再结合前面两个随机数推导出对称会话密钥。
  6. Finished：双方用会话密钥加密一段校验数据互发，确认握手没被篡改。

握手完成后，后续的 HTTP 数据全部用这个对称会话密钥加密。

-servername 千万别漏，它对应 TLS 的 SNI 扩展。现在一台服务器一个 IP 上挂几十个域名是常态，不带 SNI 服务器不知道该返回哪张证书，你很可能拿到一张默认证书然后一脸懵。我有次半夜排查「证书域名不匹配」，折腾一小时才想起来是自己命令里忘了 -servername。

TLS 1.3 把握手压缩到了 1-RTT，还支持 0-RTT 会话恢复，砍掉了一堆老旧不安全的套件（比如静态 RSA 密钥交换、CBC 模式那些）。如果你的 Nginx 和用户浏览器都够新，开 1.3 基本是白捡的性能和安全收益。

对称还是非对称？为什么两个都要

握手里其实混用了两种加密，各干各的活，这是 TLS 设计最精妙的地方。

非对称加密（RSA、ECDSA、ECDHE 这类）有公钥和私钥一对，公钥加密私钥解、私钥签名公钥验。它的好处是双方事先不用共享秘密就能安全协商，但运算很重，拿它加密整个 HTTP body 性能会崩。

对称加密（AES 这类）加解密用同一把钥匙，速度极快，适合加密大量数据，但难点在于「这把钥匙怎么安全地告诉对方」——直接发等于没加密。

TLS 的解法就是各取所长：用非对称的能力在握手阶段安全地协商出一把对称密钥，之后所有业务数据都用这把对称密钥加密。 一次昂贵的非对称运算，换来整条连接的高速对称加密，账算得很清楚。

证书：信任是怎么传递的

证书本质上是一份由 CA（证书颁发机构）签名的「身份声明」，里面写着域名、公钥、有效期、签发者等信息。浏览器拿到证书后会做几件事：

  • 是不是由本地信任的 CA（或其信任链）签发的
  • 证书里的域名跟你访问的域名是否匹配
  • 有没有过期
  • 有没有被吊销（CRL / OCSP）

任何一项不过，浏览器就弹安全警告。这里我想强调一个工程纪律：永远不要训练用户去点「继续访问（不安全）」。 一旦用户养成无视证书警告的习惯，真正的中间人攻击来了他也照点不误，证书这层防护就形同虚设。

证书是有链的，不是孤零零一张。典型是「服务器证书 → 中间 CA 证书 → 根 CA 证书」，根证书内置在操作系统/浏览器里。最常见的线上事故就是只配了服务器证书、漏了中间证书。 这种情况在 Chrome 上可能正常（它会缓存或补全中间证书），但在某些 Android 老机型、Java 客户端、curl 上就直接报「unable to verify the first certificate」。我们当年就栽过：PC 浏览器一切正常，App 里的 WebView 死活连不上，最后发现是 Nginx 的 ssl_certificate 只放了 cert.pem 没拼上 chain.pem。

几种证书方案的取舍：

  • DV（域名验证）：只证明你控制这个域名，签发快、免费，Let's Encrypt 就是这类。绝大多数业务够用。
  • OV / EV（组织/扩展验证）：会验证企业实体，签发慢、要钱。EV 当年还能在地址栏显示绿色公司名，但 2019 年之后浏览器陆续把这个特殊 UI 取消了，所以 EV 的「视觉信任」价值大幅缩水，普通业务没必要花这个钱。
  • 自签证书：自己当 CA 给自己签，浏览器默认不信任。只适合内网/本地开发，绝不能上生产。

混合内容（Mixed Content）：前端最容易踩的坑

页面整体走了 HTTPS，但里面又去加载 HTTP 资源，就叫混合内容。这是站点迁移 HTTPS 时最高频的故障来源，而且基本都落在前端头上。

浏览器把混合内容分两档：脚本、iframe、XHR/fetch 这类「主动内容」风险高，直接拦截、功能直接坏；图片、音视频这类「被动内容」一般放行但会降级安全标识。我经历过最坑的一次：页面本身没问题，但接口请求里有一个第三方统计 SDK 偷偷往 http:// 上报，控制台一片红的 Mixed Content 报错，业务功能还看不出毛病，排查了好久才定位到那个 SDK。

排查和兜底的几个手段：

  1. 源头改造：所有资源、接口统一改成 https://，这是根治。
  2. 协议相对 URL（//cdn.example.com/app.js）当年很流行，跟随页面协议。但现在不推荐了，含义不清晰、在非 http 场景（比如本地 file://）会出问题，直接写死 https:// 更好。
  3. 自动升级：加一行响应头，让浏览器把页面内所有 HTTP 子资源请求自动升级成 HTTPS，作为过渡期的安全网：

迁移 HTTPS 时，记得把静态资源、AJAX 接口、图片、字体、第三方 SDK、WebSocket（ws:// 要改 wss://）全都过一遍，漏一个就是一个隐患。

Cookie 的安全属性别漏配

登录态通常落在 Cookie 里，HTTPS 之外还得靠 Cookie 的几个属性兜底：

  • Secure：这个 Cookie 只在 HTTPS 请求里发送。不加它，一旦用户不小心走了 HTTP（比如手敲了 http 地址），登录态就明文泄露了。
  • HttpOnly：JavaScript 读不到这个 Cookie（document.cookie 拿不到），能挡住 XSS 偷 Token 的常见手法。
  • SameSite：控制跨站请求是否带上 Cookie。Lax 是个不错的默认值，能挡掉大部分 CSRF；Strict 更严但会影响外链跳转后的登录态；None 必须搭配 Secure 使用。

2019 年正好是 SameSite 的关键节点——Chrome 80 宣布要把未显式声明的 Cookie 默认当作 SameSite=Lax（2020 年初生效）。所以那会儿我就开始提醒团队：依赖跨站 Cookie 的场景（比如嵌在别人页面里的 iframe 业务）必须主动声明 SameSite=None; Secure，否则升级后会突然「莫名其妙登录态丢了」。提前改完的项目平稳过渡，没改的后来都吃了亏。

前端能落地的清单

安全从来不是前端一家的事，但前端是用户入口，这几条是我们能直接管住的：

  • 所有接口、所有静态资源统一 HTTPS，杜绝混合内容。
  • 用 CSP 的 upgrade-insecure-requests 做迁移期兜底。
  • 敏感信息（Token、密码、身份证号）绝不放进 URL——URL 会进日志、进 Referer、进浏览器历史。
  • 登录态 Cookie 配齐 Secure、HttpOnly、SameSite。
  • 提前规划好 SameSite 策略，跨站场景显式声明 None; Secure。
  • 本地用 mkcert 起 HTTPS，跟生产环境的行为对齐，避免「本地好好的，上线全是混合内容报错」。
  • 任何证书警告都当成红灯，绝不引导用户绕过。

小结

HTTPS 解决的就是传输过程中的三件事：加密、身份认证、防篡改。TLS 用非对称加密在握手阶段协商出对称密钥，再用对称加密跑业务数据；证书负责把「信任」从内置的根 CA 一路传递到你的服务器；前端则要守好混合内容、Cookie 属性和本地开发这几道关。

面试问 TLS 握手和证书链当然要会，但更值钱的是在项目里说得清：登录页、后台、支付页为什么必须 HTTPS，证书链漏配会在哪些客户端炸掉，迁移时混合内容怎么排查。说到底就一句——只要涉及账号和敏感数据，明文传输就不该存在。我们公司那次薅羊毛事故，全套整改下来其实就花了一下午：上 Let's Encrypt、补全证书链、Cookie 加属性、混合内容清干净。代价小得很，可惜是出事之后才做的。
