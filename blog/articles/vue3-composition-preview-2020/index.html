Vue 3 Composition API 初看：它不是为了替代一切，而是为了解决组织问题

2020-11-28
Vue组件与状态

Vue 3 刚出来时，我身边很多人的第一反应是：又换写法了。

这很正常。毕竟从 Options API 切到 Composition API，表面上最明显的变化就是组织方式完全不一样。

可如果只把它理解成“语法新不新”，就很容易低估它真正想解决的问题。

我真正开始理解 Composition API，不是在看最简单的计数器 demo，而是在维护一个已经变胖的业务组件时。那个组件里有搜索、分页、列表请求、弹窗、权限判断、表单校验。每块逻辑本身都不难，但它们被拆散在 data、computed、watch、methods、生命周期里，读起来像在翻一叠被打乱的纸。

Composition API 主要解决的是组织问题

Options API 在小组件里其实很好用，data、methods、computed 一眼就能看明白。

问题主要出在组件越来越大时。

一个功能要跨 data、watch、methods、生命周期来回跳，读代码会越来越碎。这时候 Composition API 的价值才会显出来：把同一类逻辑收拢到一起。

比如搜索逻辑，我更愿意把它收成一个组合函数：

这里不是为了显得高级，而是让“搜索”这件事有自己的状态、动作和错误处理。组件里使用时，逻辑边界会清楚很多。

它不是为了让代码更短

有些例子会把 Composition API 写得很紧凑，看起来像是“更高级的写法”。但真实项目里，它更大的价值不是短，而是能把一个功能模块放在一起看。

比如搜索逻辑、分页逻辑、表单逻辑，各自可以有自己的状态和动作，不必再拆散在不同选项里。

组合函数处理的是页面状态，接口函数处理的是网络细节。两边边界清楚，组件才不会变成异常处理的垃圾桶。

它不该替代一切

我并不认为 Composition API 出现后，Options API 就没有价值了。

小组件、展示组件、逻辑很少的组件，用 Options API 仍然很舒服。它直观、稳定，团队新人也容易读。

我会在这些场景更倾向 Composition API：

  • 一个业务逻辑跨了多个选项
  • 同一套逻辑要在多个组件复用
  • 组件状态很多，但可以按功能域拆开
  • 需要把请求、分页、筛选、表单等逻辑独立测试

如果组件只有十几行，硬改成 Composition API 并不会让它更专业。

写在最后

Composition API 真正值得关注的地方，不是新，而是它给了 Vue 组件一种新的组织方式。

如果你的组件规模还很小，Options API 依然很好用；但一旦逻辑开始变长、横切面增多，Composition API 的优势就会越来越明显。

我现在看它，不会把它当成“新语法”，而是当成一种整理复杂度的工具。它真正有价值的地方，是让一个活生生的业务功能可以被放在一起理解，而不是散落在组件的各个角落。
