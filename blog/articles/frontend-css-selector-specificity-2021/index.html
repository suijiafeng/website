CSS 优先级为什么总打架：选择器、继承和覆盖规则怎么理解

2021-04-06
前端基础

写 CSS 时，经常会遇到一种很烦的情况：明明样式写上去了，浏览器却没有按你想的显示。我印象最深的一次是改一个按钮的背景色，本地怎么改都不生效，盯着代码看了十分钟，最后打开 DevTools 才发现我写的那行被画了删除线，真正生效的是组件库里一条更高优先级的规则。那一刻的感受是：不是我不会写 CSS，是我没看清楚浏览器到底听谁的。

这时候很多人的第一反应是继续把选择器写得更长，或者直接加 !important。短期看问题似乎解决了，长期却会把样式系统越写越乱。我自己早期就干过这种事，一个页面里十几个 !important 互相压制，后来谁都不敢动，因为不知道删掉哪一个会让哪个地方塌掉。

CSS 优先级之所以重要，不只是为了答面试题，而是它直接决定项目里的样式维护成本。理解它之后你会发现，大多数"样式不生效"的问题根本不需要更复杂的选择器，只需要看清楚当前是哪条规则在赢。

为什么会出现“我写了但没生效”

一个样式没有生效，常见原因通常就这几类：

  • 选择器优先级不够
  • 后面的同优先级样式把前面覆盖了
  • 样式被继承链或默认样式影响
  • 条件类名没有真正挂上去
  • 写错了属性值或单位，浏览器直接丢弃了这条声明

很多时候不是浏览器有问题，而是有另一条更强的规则正在起作用。我的排查习惯是先别急着改代码，打开 DevTools 的 Elements 面板，选中那个元素看右侧的 Styles。被删除线划掉的就是被覆盖的，灰色的是无效声明（比如 width: 100 没写单位，或者 colour 拼错了），实际生效的会标在最上面的 Computed 里。这一步通常能在几秒内告诉你问题属于上面哪一类，比盲改高效太多。

优先级不是看谁写得长，而是看选择器组成

CSS 选择器优先级常见比较方式，核心在于它包含了哪些部分。

我习惯把优先级想成一个三位的计数 (a, b, c)：

  • a：id 选择器的个数
  • b：类、属性选择器、伪类的个数
  • c：标签选择器、伪元素的个数

比较时从左往右逐位比，高位大的直接赢，跟字符长度无关。

这里有几个值得记住的细节，都是我实际踩过的：

  • 内联样式 style="..." 比任何选择器都高，相当于多了一位 (1, 0, 0, 0)，只有 !important 能盖过它。
  • :not()、:is()、:where() 本身不计权重，但里面的参数算。特别要注意 :where() 永远是 0 权重，这点后面会用到。
  • 通配符 * 和组合符 >、+、~ 都不增加权重。

很多人看到样式不生效，就不断往前面加父级类名，以为越长越强。实际上如果本质上还是一串类选择器，权重只在同一位上累加，跨不过更高位的那条；反而会让结构耦合越来越重，组件挪个位置样式就崩了。

这个可以自己验证：:where(.btn) 整条选择器的权重是 (0, 0, 0)——:where() 把里面参数的权重全抹成 0。所以业务方随便一个 .btn { color: red }（权重 (0, 1, 0)）都能盖过它。对照一下，如果当初写的是普通的 .btn { color: #333 }（同样 (0, 1, 0)），那就要拼谁后写、谁加载在后面了，覆盖关系一下子变得不可控。

同优先级时，后写的会覆盖先写的

这就是为什么组件库样式、页面样式、主题样式叠在一起时，经常会出现"本地改了没用"的情况。问题不一定在优先级高低，也可能只是加载顺序。

我被这个坑过最惨的一次，是用 webpack 打包时样式顺序在开发环境和生产环境不一致。本地用 style-loader 是按引入顺序插 <style>，生产用 mini-css-extract-plugin 抽成文件后，顺序由依赖图决定，结果两个环境里同优先级的两条规则谁在后面是反的，本地好好的页面一上线就错位。后来才明白，一旦你的样式覆盖关系是依赖"后写的赢"，那它就和构建顺序强绑定了，而构建顺序是很不稳的东西。这件事之后我尽量不靠加载顺序去做覆盖，能用更明确的类名区分就用类名。

顺便提一句容易混的点：优先级永远比顺序优先。只有在优先级完全相等时，才轮到"后写的赢"。所以判断时先比 (a, b, c)，相等了再看顺序，别一上来就数谁在文件下面。

继承会让问题看起来更复杂

有些 CSS 属性天然可以继承，比如文本颜色、字体相关属性。

这意味着你可能并没有直接给某个元素写样式，它却已经从父元素那里拿到了值。

继承本身很有用，可以减少重复代码。但如果不了解哪些属性会继承，调样式时就会误以为"这个元素被某条神秘规则控制了"。一个典型例子是 <input>、<button>、<textarea> 这些表单元素，它们默认不继承父级的 font-family 和 color，浏览器给了自己一套 UA 样式。所以你会看到正文字体改好了，唯独表单里还是系统默认字体，得专门写一行：

继承相关的属性值还有几个好用的关键字，我经常拿来精确控制：inherit 强制继承父值，initial 回到属性的 CSS 规范初始值，unset 则是"能继承的就继承、不能继承的就用初始值"。调那种被一层层覆盖搞乱的元素时，all: unset 有时候是最干净的重置手段。

还有一点容易忽略：DevTools 里 Computed 面板能直接告诉你某个属性的值是从哪个父元素继承下来的，会标 "Inherited from xxx"。比起在脑子里推继承链，直接看这个准得多。

特别是在文章正文、表单、组件嵌套较深的页面里，字体和颜色常常会受到上层容器影响。我现在写富文本正文样式时，会刻意把规则收在一个 .prose 类下面，让继承的边界清晰，而不是直接写到 body 上到处扩散。

!important 为什么不该成为常规武器

!important 确实能强行提升规则优先级，所以它很容易让人上瘾。

问题是，一旦项目里到处都是 !important，后面再覆盖时就只能继续加更多 !important，最后整个样式层会陷入谁都不服谁的局面。

它不是不能用，而是应该保留在少数明确场景里，例如临时兼容第三方样式、处理极个别覆盖问题。大多数项目级样式问题，还是应该通过更清晰的结构和加载顺序解决。

还有个反直觉的细节得知道：!important 自己也有"内部优先级"。当两条规则都带 !important 时，又退回到比 (a, b, c)，谁高谁赢。所以一旦开了这个头，你就会被迫写出 #app .modal .btn { color: red !important } 这种又长又带 important 的怪物去压上一条 important，越滚越大。我见过最夸张的代码是把 important 加在了一个本来就最高优先级的 id 选择器上，结果同事想覆盖只能去改源码，因为正常手段已经够不着了。

我自己定的土规矩是：业务代码里写 !important 之前，先问一句"是不是因为有另一条不该存在的高优先级规则"。如果是，去把那条规则降下来，而不是再叠一层。真正合理的 important 场景其实很窄，比如工具类 .hidden { display: none !important }，这种本来就是要无条件生效的，加了反而符合语义。

与其算谁更高，不如让规则都待在低权重

修过几次优先级冲突之后，我的结论是：大多数打架不是某条规则写错了，而是样式组织本身就在制造冲突——全局样式范围过大、选择器嵌套太深、组件没边界、页面随手覆盖基础样式。这些做法会让权重分布越来越参差，覆盖需求也越来越多。

我自己后来形成的几个习惯，效果很明显：选择器尽量扁平，能用单个类名就不写后代选择器，权重越平后续覆盖越简单；命名用 BEM 那种 .card__title--active，让状态体现在类名里而不是靠嵌套结构表达；组件内部样式用 CSS Modules 隔离——它把类名编译成 card_title__3xK9 这样的哈希，天然避开跨组件命名冲突，权重又始终是单个类的 (0, 1, 0)，几乎不可能打架。换上它之后，我们项目里 !important 的数量肉眼可见地降了下来。

这些做法的共同点都是主动把权重压低、压平，而不是去比谁高。真实项目里样式来源本来就多——全局基础样式、组件库默认样式、页面局部覆盖、临时活动页补丁，叠在一起后问题往往不是“哪条规则大”，而是“这条规则到底从哪儿来”。所以我调样式时会先在 DevTools 里看清元素命中了哪些规则、每条来自哪一层，再决定是调优先级、调导入顺序还是回头改结构。优先级规则本身不会变，决定项目好不好维护的，是有没有让简单规则在大多数时候就够用。
